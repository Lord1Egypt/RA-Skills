# AI智能客服产品完整案例

> 本案例展示如何从0到1设计一个企业级AI智能客服产品。
> 覆盖AI策略→模型选型→RAG设计→Agent→Prompt→AI UX→评测→安全→定价全流程。

---

## 案例背景

### 产品简介
"SmartCS" — 面向中大型企业的AI智能客服平台，基于LLM+RAG+Agent技术，实现客户服务的智能化升级。

### 目标客户
- 企业规模：200-5000人，有独立客服团队
- 典型行业：零售电商、金融科技、SaaS服务、物流
- 月均工单量：5000-100000+
- 当前痛点：人工客服成本高、响应慢、知识传承难、质检成本高

## 阶段1：模型选型

### 选型决策

| 决策 | 选择 | 理由 |
|------|------|------|
| Build/Buy/Fine-tune | Buy API + RAG | 场景通用性较强，无需自训练 |
| 首选模型 | Claude Sonnet 4 | 平衡质量、成本和延迟 |
| 复杂Case模型 | Claude Opus 4 | 复杂投诉、多意图推理 |
| 简单Case模型 | Claude Haiku 4.5 | 简单FAQ、意图识别 |
| 路由策略 | 分类器路由 | 训练意图复杂度分类器 |
| 上下文窗口 | 128K tokens（Sonnet） | 支持长知识库文档+长对话历史 |
| 中文能力 | 原生多语言 | 中文客服场景直接适用 |

### 模型路由架构

```
用户问题
    ↓
意图分类器(BERT微调)
    ↓
├── FAQ/问候(~50%) → Claude Haiku + 缓存 → <500ms
├── 标准问题(~35%) → Claude Sonnet + RAG → <2s  
├── 复杂问题(~12%) → Claude Sonnet + Agent + RAG → <5s
└── 投诉/敏感(~3%)  → Claude Opus + 人工审核 → <8s
```

### Token成本估算（标准化为每1000工单）

| 场景 | 占比 | Input | Output | 单次成本(Sonnet) | 千工单成本 |
|------|------|-------|--------|-----------------|-----------|
| FAQ简单 | 50% | 500 | 200 | $0.003 | $1.50 |
| 标准问答 | 35% | 2000 | 500 | $0.012 | $4.20 |
| 复杂问题 | 12% | 5000 | 1000 | $0.030 | $3.60 |
| 投诉处理 | 3% | 8000 | 1500 | $0.045(Opus) | $1.35 |
| **总计** | | | | | **$10.65/千工单** |

对比：人工客服处理1000工单成本约 $500-800，AI成本仅人工的1.5-2%。

## 阶段2：RAG设计

### 知识库设计

| 知识源 | 文档类型 | 数量(示例) | 更新频率 | 优先级 |
|--------|---------|-----------|---------|--------|
| 产品FAQ | 结构化QA对 | 5000+ | 每周 | ⭐⭐⭐⭐⭐ |
| 产品帮助文档 | 技术文档/用户手册 | 200+篇 | 每次发版 | ⭐⭐⭐⭐ |
| 政策/协议 | 退款/隐私/服务条款 | 50+篇 | 按政策变化 | ⭐⭐⭐⭐ |
| SOP流程 | 标准操作流程文档 | 100+篇 | 每月 | ⭐⭐⭐ |
| 历史优质工单 | 人工客服对话 | 10000+ | 持续更新 | ⭐⭐⭐ |

### 分块策略

| 文档类型 | 分块方式 | 分块大小 | 重叠 | 理由 |
|---------|---------|---------|------|------|
| FAQ | 按QA对 | 1个QA/块 | 0% | 每个QA自包含 |
| 帮助文档 | 按段落+标题层级 | 1024 tokens | 20% | 保留标题上下文 |
| 政策条款 | 按条款编号 | 512 tokens | 10% | 条款之间独立但须关联 |
| 历史工单 | 按完整对话 | 2048 tokens | 0% | 保持对话完整性 |

### 检索架构

```
用户Query
    ↓
Query重写（处理口语化、多义词、错别字）
    ↓
并行检索：
├── 稠密检索（bge-large-zh-v1.5, Top-30）
└── 稀疏检索（BM25, Top-30）
    ↓
合并去重 → Top-50
    ↓
Cohere Rerank v3 → Top-5
    ↓
相关性过滤（score > 0.6）
    ↓
拼接上下文 → LLM生成
```

### 检索参数

| 参数 | 值 | 理由 |
|------|-----|------|
| 初始召回数 | Top-50 | 保证召回覆盖 |
| Rerank后数量 | Top-5 | 上下文窗口有效利用 |
| 相似度阈值 | 0.6 | 平衡召回和精确 |
| 混合权重 | Dense 0.7 / BM25 0.3 | Dense为主，BM25辅助精确匹配 |

### Embedding模型

| 决策 | 选择 | 理由 |
|------|------|------|
| 模型 | bge-large-zh-v1.5 | 中文检索评测最佳之一 |
| 维度 | 1024 | |
| 最大输入 | 512 tokens | |
| 本地部署 | 是 | 数据不出企业 |

## 阶段3：Agent设计

### Agent架构（Plan-Execute模式）

```
用户问题 → Agent Planner
    ↓
制定执行计划：
├── Step 1: 识别用户身份和意图
├── Step 2: 检索相关知识库
├── Step 3: 如需查订单/会员信息 → 调用业务API工具
├── Step 4: 综合分析，生成回答
├── Step 5: （可选）如涉及退款/投诉 → 生成建议 → HITL确认
└── Step 6: 记录工单，更新统计
```

### 工具定义

| 工具ID | 工具名称 | 功能 | 风险等级 | HITL |
|--------|---------|------|---------|------|
| T01 | search_knowledge_base | 检索知识库 | L0 | 无需 |
| T02 | query_order | 查询订单信息 | L0 | 无需 |
| T03 | query_member | 查询会员信息 | L0 | 无需 |
| T04 | query_ticket | 查询历史工单 | L0 | 无需 |
| T05 | create_ticket | 创建工单 | L1 | 事后抽查 |
| T06 | update_ticket | 更新工单状态 | L2 | 确认 |
| T07 | send_notification | 发送通知(短信/邮件/推送) | L2 | 确认 |
| T08 | process_refund | 发起退款 | L3 | 强制确认 |
| T09 | modify_member_level | 修改会员等级 | L3 | 强制确认 |
| T10 | escalate_to_human | 转接人工客服 | N/A | 自动 |

### HITL矩阵

| 操作 | 风险等级 | Agent行为 | 人类角色 |
|------|---------|----------|---------|
| 回答FAQ | L0 | 自主回答 | 事后抽查 |
| 查询订单/会员 | L0 | 自主查询 | 日志审计 |
| 创建工单 | L1 | 自动创建 | 事后review |
| 修改工单状态 | L2 | 建议→确认 | 审核确认 |
| 发送通知 | L2 | 生成草稿→确认 | 确认发送 |
| 发起退款 | L3 | 生成申请→人类审批 | 审批+执行 |
| 改会员等级 | L3 | 建议→客服经理审批 | 审批+执行 |
| 优惠券发放 | L2 | 建议发放(限额内) | 超额审批 |
| 敏感投诉 | L3 | 标记+转人工 | 人工处理 |

### 记忆设计

| 记忆类型 | 内容 | 实现 |
|---------|------|------|
| 短期记忆 | 当前对话上下文 | 上下文窗口，最近20轮 |
| 情节记忆 | 用户历史交互摘要 | 向量数据库存储关键交互摘要 |
| 语义记忆 | 用户偏好/习惯/标签 | 用户画像结构化存储 |
| 工作记忆 | 当前任务状态 | Agent状态机存储 |

## 阶段4：Prompt设计

### System Prompt

```
你是SmartCS智能客服助手，你的职责是为用户提供准确、专业、友好的客户服务。

# 你的能力
- 回答产品使用问题（基于知识库）
- 查询订单、物流、会员信息（通过工具）
- 处理常见售后问题（退换货、退款政策解答）
- 创建和更新服务工单
- 无法处理时无缝转接人工客服

# 你的约束
- 仅基于知识库文档和系统返回的真实数据回答
- 知识库中没有的信息，诚实告知"我需要帮您查询更多信息"
- 涉及退款、赔偿等敏感操作，必须明确告知用户"我帮您提交申请，由客服同事审核处理"
- 绝不泄露其他用户的信息
- 不确定时明确表达，不猜测

# 你的工作方式
1. 识别用户身份和意图
2. 检索相关知识库和用户数据
3. 如需多步操作，制定执行计划
4. 逐步执行，观察结果
5. 用自然、温暖的语言回复用户
6. 每次回复后，判断是否需要转人工

# 回复格式
- 先简短共情，再给答案
- 涉及步骤类问题，用编号列表
- 涉及政策类问题，引用具体条款
- 涉及敏感操作，说明后续流程
```

### 上下文组装

```
┌─────────────────────────────────┐
│ System Prompt (~1.5K tokens)    │
├─────────────────────────────────┤
│ 用户画像 (~300 tokens)           │ ← VIP等级/历史工单数/偏好语言
├─────────────────────────────────┤
│ 用户最近工单 (~1K tokens)        │ ← 最近3个工单摘要
├─────────────────────────────────┤
│ RAG检索结果 (~5K tokens)         │ ← Top-5文档块
├─────────────────────────────────┤
│ 对话历史 (~3K tokens)            │ ← 最近10轮
├─────────────────────────────────┤
│ 工具调用结果 (~2K tokens)        │ ← 订单/会员等API返回
├─────────────────────────────────┤
│ 用户当前输入                     │
└─────────────────────────────────┘
```

## 阶段6：评测方案

### Golden Dataset

| 指标 | 目标值 |
|------|--------|
| 总样本数 | 500+ |
| 常见场景（FAQ/订单查询） | 60% |
| 边缘场景（复杂投诉/多意图） | 20% |
| 对抗场景（注入/越狱） | 10% |
| 安全场景（PII/有害内容） | 10% |

### 评测指标

| 维度 | 指标 | 目标值 | 测量方法 |
|------|------|--------|---------|
| 准确性 | 回答正确率 | >90% | Golden Dataset + LLM-as-Judge |
| 忠实度 | RAGAS Faithfulness | >0.90 | 自动评测 |
| 完整性 | 信息覆盖率 | >85% | LLM-as-Judge |
| 安全性 | 有害输出率 | <0.1% | 安全测试集 |
| 延迟 | P95首Token时间 | <2s | 生产监控 |
| 用户满意度 | 👍占比 | >85% | 在线反馈 |

### 评测流水线

```
每次代码/Prompt变更：
1. CI自动跑 Golden Dataset (500条, ~10分钟)
2. RAGAS指标检查 (Faithfulness > 0.90)
3. 安全测试集检查 (0有害输出)
4. 回归测试 (指标不降超过3%)
5. 通过 → 灰度5% → 观察1天
6. 核心指标OK → 全量
```

## 阶段7：安全与护栏

### 安全架构（参照五层防御）

**Layer 1: 输入护栏**
- 注入检测：LLM分类器检测 "忽略之前的指令"等模式
- 越狱检测：检测角色扮演、编码绕过
- PII检测：手机号/身份证/银行卡自动脱敏

**Layer 2: 权限控制**
- 用户只能查询自己的订单/会员信息
- 客服人员的工具权限按角色分级
- 租户数据严格隔离

**Layer 3: 模型安全**
- System Prompt安全加固
- User Prompt和System Prompt严格隔离
- 上下文数据带权限标记

**Layer 4: 输出护栏**
- 内容安全审核（实时逐Token检测）
- 幻觉检测（声明-证据一致性校验）
- PII脱敏
- 输出格式校验

**Layer 5: 审计监控**
- 所有AI交互完整记录
- 异常检测（异常高频/异常Pattern）
- 熔断开关：10分钟内安全拒绝率 >5% → 自动切换为仅人工模式

# SkillForge 技能炼金

给技能作者用的质检台：把一份 SKILL.md 拆成六个可判定的维度，给出评分卡、逐条改法和可直接替换的改写稿；对整库则输出按优先级排好的修复队列。

## 这是什么

- 解决的问题：技能"看起来都对"，实际却触发不中、流程走不通、验收没法查、体量把上下文吃满，还可能夹带绝对路径与密钥。
- 产出物形态：一份人读的审计报告（`<slug>.audit.md`）、一份机读评分卡（`<slug>.audit.json`）、一份改写稿或逐处差异对照（diff）。
- 与"直接问通用大模型"的区别：打分依据是固定量表与分值锚点，同一份技能两次审计的分差应控制在 5 分以内；通用对话每次口径不同，结论无法横向比较，也无法在团队间复核。
- 覆盖范围：单份 SKILL.md、一个技能目录（含 `references/` 与 `scripts/`）、整棵技能库。
- 附带确定性工具：`scripts/skill_audit.py` 只用标准库量出可数的指标（行数、章节、字段、空话、风险），把"目测"换成"计数"。

## 适用场景

- 我要上架一个付费技能，想知道它够不够格、哪些地方会被差评。
- 我的技能"有时灵有时不灵"，我要定位是触发词的问题还是流程的问题。
- 我怀疑技能太长把上下文吃满了，要量化它的体量并决定拆不拆。
- 我要把一个能用的技能改写成团队能复用的版本。
- 我库里有几十个技能，不知道先修哪个，要一份按影响面排序的修复队列。
- 我要给技能补上验收标准，让 Agent 每次跑完能自己检查。
- 我要在交付前自查有没有绝对路径、密钥、内部地址之类的泄漏。
- 我要对比两份同领域技能，决定保留哪一个。

## 何时不要使用

- 只有技能描述、拿不到原始 SKILL.md：审计结论不可靠，先要到文件。
- 要求保证过审或保证上架：只做结构与可执行性审计，审核结果由平台决定。
- 涉及未公开的内部接口或私有协议：只保证表述清晰，不验证可用性。
- 只想改措辞、不想动流程：本技能的评分卡会暴露结构问题，改不动流程就别做深度审计。

## 输入与输出

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `skill_path` | 是 | 单份 SKILL.md 的路径，或一个技能目录；批量审计时传技能库根目录 |
| `mode` | 否 | `single`（默认）单份审计；`batch` 逐目录审计并输出修复队列 |
| `profile` | 否 | `house`（默认，按上架规范校验完整 frontmatter 字段集）／`generic`（只校验 `name` 与 `description`） |
| `rewrite` | 否 | `full`（默认，给整篇替换稿）／`patch`（只给逐处 diff）／`none`（只评分） |
| `target_readers` | 否 | 技能的服务对象：Agent 自用、对外售卖、团队复用；决定边界与验收的严格度 |
| `fail_under` | 否 | 总分低于该值判为不合格，`scripts/skill_audit.py` 以退出码 `1` 结束 |

输出三件，缺一不算交付：

- `<slug>.audit.md`：审计报告，含评分卡、问题清单（逐条带定位）、改写稿或 diff、验收清单；篇幅 800–2,500 字。
- `<slug>.audit.json`：机器可读评分卡，字段与 `scripts/skill_audit.py` 输出一致；报告里的每个数字都要能在其中找到。
- `audit-queue.md`：仅 `mode=batch` 时产出，修复队列表（优先级／技能／总分／首要问题／修复成本）。

## 工作流


### 1. 读取与解析

- **做什么**：先跑 `python scripts/skill_audit.py <技能目录>` 取机器指标，再通读 SKILL.md 正文，记录 frontmatter 字段、标题树、体量（行数与字符数）、代码块与清单数量、正文声称的依赖。
- **判据**：能回答四件事——① frontmatter 是否存在且可解析；② 章节基线缺哪几节（`house` 按十节，`generic` 按定位／流程／验收／边界四块）；③ 体量落在哪一档；④ 正文引用的 `references/`、`scripts/` 文件是否真实存在。
- **失败怎么办**：frontmatter 缺失或被引号破坏时不猜内容，直接记为 P0 并要求作者补齐；文件非 UTF-8 时先转码，转码失败则只做体量与关键词层面的审计，并在报告首行注明"结构分不可用"。

### 2. 六维评分

- **做什么**：逐维对照 `references/audit-rubric.md` 的锚点打 0–5 整数分，记录取证位置；按权重合成总分。
- **判据**：每一分都能指向原文的一处（行号或标题）；拿不出原文支撑的分必须回落到 3 分以下（保守原则）。
- **失败怎么办**：两处证据互相矛盾（例如正文说"必填"而表格写"可选"）时，按弱的一侧计分，并在问题清单里单列一条一致性缺陷。

### 3. 问题定位

- **做什么**：把每个扣分项转成一条问题，固定三段——定位（章节／行号／原句）、后果（会导致什么失败）、改法（可执行的动作）。
- **判据**：一条问题只能归属一个维度；"后果"必须对应一个可观察的失败现象（不触发、跑一半停住、无法验收、超预算、信息泄漏）。
- **失败怎么办**：只能写出"不够清晰"这类形容词，说明还没定位到句子；回到原文找具体短语，找不到就不写这条，宁缺不凑。

### 4. 改写建议与替换稿

- **做什么**：按 `references/rewrite-patterns.md` 对每个 P0／P1 问题给出改写；`rewrite=full` 输出整篇替换稿，`rewrite=patch` 输出逐处 diff。
- **判据**：改写稿的二级标题与原稿一一对应，节数相等；不新增原文没有的事实、依赖与链接；改完能复跑脚本且总分上升。
- **失败怎么办**：改写会突破体量上限时，先把细则下沉到 `references/` 再改正文；无法在不改变业务含义的前提下改写时，只给建议并把该条降为 P2。

### 5. 产出评分卡与 diff

- **做什么**：写 `<slug>.audit.md` 与 `<slug>.audit.json`，两者总分必须一致；diff 放在 `diff` 代码块里，行首 `-` 是原文、`+` 是改后。
- **判据**：报告里的每个数字都能在 JSON 里找到同名字段；改写幅度大的要附三条以内的改动摘要。
- **失败怎么办**：报告与 JSON 不一致时以脚本重跑结果为准，把差异原因写进报告脚注，不手工调数。

### 6. 批量审计与修复优先级

- **做什么**：`python scripts/skill_audit.py --scan <库根目录>` 出全量初评，再按 `references/batch-audit.md` 的公式算优先级，人工抽检不低于 20%，产出 `audit-queue.md`。
- **判据**：队列里每条的优先级都能用公式复算；抽检项中至少 3 条能人工定位到原文句子。
- **失败怎么办**：库超过 60 个技能时分两批，先粗筛 P0／P1，再对入选者做深度审计；扫描中断则按目录分批续跑，已完成的目录不重扫。

## 输出格式

```
评分卡：六维 × 0/3/5 分 + 总分 + 分档结论
问题清单：定位（行号/章节）| 证据 | 影响 | 改法
改写稿：整篇替换（默认）或 diff（patch 模式）
验收清单：改写后逐条可勾选的检查项
```

## 质量门槛

- [ ] 六维各有一个 0–5 的整数分，且每维标注取证位置（章节名或行号）
- [ ] 评分卡含 6 行维度与 1 行总分，权重列合计 100
- [ ] 总分等于 Σ（维度分 ÷ 5 × 权重），复算误差为 0
- [ ] 每条问题都具备"定位／后果／改法"三段，缺一段即视为不合格
- [ ] 每条后果能对应一个可观察的失败现象（不触发、断流、无法验收、超预算、信息泄漏）
- [ ] 改写稿的二级标题与原稿一一对应，节数相等
- [ ] 改写稿未引入原文不存在的事实、依赖或外部链接
- [ ] 报告全文无绝对路径、密钥、内部地址、真实姓名与联系方式
- [ ] `skill_audit.py` 输出的 JSON 与报告中的数字逐项一致
- [ ] 报告正文 800–2,500 字，问题清单不超过 15 条
- [ ] 随机抽 3 条问题，能在原文中定位到具体句子
- [ ] `mode=batch` 时，队列条目的优先级可用公式复算

## 能力边界

- 不做运行时验证：审计是静态的，只能证明文本具备可执行性，不能证明技能在真实工具链上一定成功；需要跑通的场景请另行端到端试跑一次。
- 不评业务价值与定价：只评结构、可执行性、体量与风险，不判断这个技能值不值得卖。
- 不改你的原始文件：只产出改写稿与 diff，落盘前必须经你确认。
- 不做跨语言润色：英文版只做结构与合规对齐，不做文学化改写。
- 单文件超过 2,000 行时只做结构与风险审计，不逐节评分，并在报告首行注明降级原因。
- 遇到无法解析的内容（损坏的 frontmatter、二进制附件、加密文档）标记为 `unparsed` 并跳过该段评分，不猜测内容；若三分之二的维度都无法评，直接终止并返回修复清单。
- 涉及未公开的第三方接口或私有协议时，只按文本证据评分，不外推其可行性。

## 常见陷阱

- **把静态检查当运行时验证**：结构齐全不等于能跑 → 关键路径要求实跑一次。
- **只改措辞不改流程**：读起来顺了，Agent 还是执行不了 → 每处措辞改动必须对应可执行动作。
- **忽略触发词覆盖**：用户换个说法就唤不起 → 触发词要覆盖同义词与口语表达。
- **改写后不做回归**：新版本反而丢了原来的边界 → 改写结束必须跑验收清单。

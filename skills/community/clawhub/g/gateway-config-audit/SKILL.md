# OpenClaw 配置体检与加固

用于：主人说「审计/体检一下 OpenClaw 配置，看有没有问题、有没有可优化空间」；要加固本机 exec 权限、会话存储维护、`~/.openclaw` 状态目录；或读过体检报告后说「按顺序全修」。
产出：**带证据的问题清单**（严重度 × 是否改变交互）+ 每项改前/改后回读值 + 备份路径 + 未修项与出路 + 重启项（交主人）。
（provider/模型不可用与默认模型 → `openclaw-model-health-triage`；删 provider → `openclaw-provider-removal`；删插件/通道 → `openclaw-plugin-removal`；升级后的漂移 → `openclaw-upgrade-impact-review`；**工作区**文件整理 → `workspace-declutter`（本 skill 只做 `~/.openclaw` 配置与状态面）；字段/默认值取证 → `openclaw-docs-grounding`；OpenViking 记忆空白 / 没抽取 / 召回不到 → `openviking-memory-triage`；**会话库 / 状态目录体量膨胀 → `references/会话库膨胀分诊.md`**；**网关运行时变慢 / 内存膨胀 / 越用越慢 / OOM 风险 / 每轮耗时高 → `openclaw-gateway-performance-triage`**（那是运行时面：cgroup 口径、worker 泄漏、会话数驱动的 O(n) 投影开销、journalctl 信号，不在配置盘点范围内）。）

## 前置事实（实测，勿重踩）

- **盘点是四条命令 + 一个体量面**：`openclaw doctor`（update 历史警告 / cron / heap / relay）、`openclaw status`（channel · agents · sessions · tasks · backups · 心跳）、`openclaw config validate`、`openclaw security audit`（常见 0 critical / 若干 warn）；定时任务清单用 `openclaw automations list`，逐条 `openclaw automations show <id>` / `openclaw automations runs <id>` 读 `last error` 与运行历史；会话积压用 `openclaw sessions cleanup --dry-run`（不带 `--enforce` 即 dry-run）；体量 `du -sh ~/.openclaw/{backups,state,cache,media,logs}`。
- **`openclaw doctor --fix` 在本 agent 的 exec 里必然失败**：它进 maintenance 阶段会检查进程树，回 `Doctor could not enter maintenance. Error: This command is running inside the gateway process tree (gateway PID <n>). … Run this command from a shell outside the gateway service.` ⇒ **只读 `openclaw doctor`（不带 `--fix`）能正常跑并给全量告警**，诊断照做；`--fix` 一律**连停/起服务写成交付步骤交主人**（`systemctl --user stop openclaw-gateway` → `openclaw doctor --fix` → `systemctl --user start openclaw-gateway`），不要反复重试自证必然的失败。
- **audit 的 warn 多是多租户通用加固，别照单全改**：`security audit` 自己会打印 INFO「trust model: personal assistant（one trusted operator boundary）」。⇒ 分诊时把「单机单人信任下可接受」与「确实该收」分开，不是每条 warn 都是缺陷。
- **`config patch` 对对象是递归合并、对标量/数组才是替换**（本类最贵的一坑）：把 `tools.exec.safeBinProfiles` 由 81 键改成 78 键的 patch **落下仍是 81 键且不报错**；必须加 `--replace-path <dot.path>` 才整体替换。判据是**回读键数**，不是命令回执。
- **配置改动一律先 `--dry-run` 再落盘**：回执 `N update(s) validated` 才是 schema 通过；落盘回执会写明是否需重启（`Change will apply without restarting the gateway` / `Restart the gateway to apply`）。改前 `cp openclaw.json /tmp/openclaw.json.pre-<说明>`。
- ⚠️ **两条写入路径都只认回读、不认回执**：`config patch` CLI 与 `openclaw` **工具**都实测过**部分写入**——后者一次请求改两个阈值，只应用了一个、整体仍回 `done`、且只播报改成功的那一个（另一个静默跳过）。⇒ 工具回报里**没点名的字段一律视为未确认**；回读时顺带打印**未涉及的兄弟字段**，确认没被顺手改坏。
- **第三条写入路径：直接热编辑 `~/.openclaw/openclaw.json`**（Gateway 监听该文件并自动应用，等价 Control UI 的 Direct edit；`docs/gateway/configuration.md`），也是 `openclaw` **工具**不可用时的唯一出路。工具不可用实测两形态：`OpenClaw change expired. No change.`（改动待主人在 Control UI 批准而超时 —— 是过期不是被拒，可重发）与 `OpenClaw could not reach working inference … Token Plan 用量上限 (2056)`。⚠️ **非法配置的热重载会被跳过**、运行时保留上一份已接受配置（不会因此起不来，但改动也不生效）⇒ 热编辑后必须按 `openclaw-model-health-triage` 的「网关有效配置」读法复核，**只回读文件不算数**。
- **文件工具读 `openclaw.json` 有截断陷阱**：`read` 每次只回 2000 行 / 50KB，长配置（实测 ~64KB）会被截在对象中间，`JSON.parse` 报的位置**恰好等于返回字节数** —— 那是截断、不是配置损坏；按 `offset`/`limit` 分页拼回再 parse，别据此报「配置文件坏了」。
- **工具白名单里的死条目要先验证再删**：无插件匹配的条目（如 `lobster`）该删；但同一条告警里可能混着**真在用的核心工具**（如 `view_image`）——逐条确认实际可用性，别整段清空。
- **exec 策略落在两处，别只改一处**：① 配置 `tools.exec.mode`（枚举 `deny|allowlist|ask|auto|full`）；② exec-approvals 存储（`~/.openclaw/state/openclaw.sqlite#exec_approvals_config`，读写走 `openclaw approvals get` / `set --file`，含 `agents.<id>.security/ask/askFallback/autoAllowSkills/allowlist`）。`mode:"ask"` 的**有效策略是 `security=allowlist + ask=on-miss + askFallback=allowlist`**（比字面更严：无人值守时回退成「只允许白名单」）。改完用 `openclaw approvals get` 读 **Effective Policy** 表核对，别只看 config。
- **exec 审批结果是结构化字段，「denied」常是审查器故障而非策略拒绝**：每条 exec 回执带 `approvalReviews[]` 与 `approvalReviewOutcome`。实测形态 `{label:"Guardian", status:"denied", riskLevel:"unknown", rationale:"exec reviewer completion failed: 429 … 已达到 Token Plan 用量上限"}` 而命令**照常执行完（exitCode 0）**。⇒ ① 读 `denied` 必须先看 `rationale`：审查模型**配额/限流失败时是 fail-open**，命令仍放行，别当成策略拦截去「规避触发」；② 这是**审批层静默降级**（安全审查实际未生效），如实报主人（换额度充足或独立的审查模型），并说明命令仍会执行。
- **会话存储的维护配置在顶层 `session.maintenance.*`**（**不是** `agents.defaults.session.retention`）：`mode`(`warn|enforce`)、`pruneAfter`(默认 30d)、`archiveDashboardAfter`、`maxEntries`(默认 5000)、`preserveRecent`、`resetArchiveRetention`、`maxDiskBytes`(默认 10gb)、`highWaterBytes`、`coldStorage`。字段与默认值现取 `gateway config.schema.lookup session.maintenance`，不背。
- **`mode:"enforce"` 不等于在清理：只写 mode 而不写阈值 = 走默认，库再大也不触发**（实测 439 条会话 / 1.1 GB 库，`maxEntries 5000` 与 `maxDiskBytes 10gb` 都远未到）。症状是 `cleanup --dry-run` 回执 `beforeCount == afterCount`、`pruned 0`、`overBudget false` —— 那是阈值没配，不是清理坏了。判据是 dry-run 的**前后条数出现差值**。
- **回执里 `archived` 与 `pruned` 语义相反，别当成同一件事**：`archived` 是 in-place 改元数据、**保留全部 transcript、也不减小文件**；`pruned` 是**删除可丢弃的自动化行且不可逆**（实测一次收紧就 `pruned 165`，全是 `subagent:*` 写手/审计子会话）。⇒ 收紧阈值前先让 `coldStorage` 把不活跃 transcript 外置完，再跑 `--enforce`；顺序反了就是永久丢失。`capped 0` 而 `afterCount` 仍高于 `maxEntries` 属正常（保护行不被解除）；`overBudget true` 但 `freedBytes 0` 也正常（预算是删除的**触发器**、不是压缩器）。
- **`openclaw sessions archive` 对 `kind:"spawn-child"` 是假成功**：回「Archived session …」，但活动列表、`session_transcript_archives`、`session_transcript_cold_archives` 全无变化，只有 `updatedAt` 被刷（`ageMs` 从 10d 变几十秒）。⇒ 清子代理/叶子会话**直接用 `openclaw sessions delete --agent <id> --yes <key>…`**：真移除并归档转录到 `agents/<id>/sessions/*.jsonl.deleted.<ts>.<sha>.zst`，并提示再跑 `openclaw memory forget --agent <id> --session <key>` 清索引。
- **会话「分组」没有成员表**：`state/openclaw.sqlite.session_groups` 只有 `(name, position, created_at, cwd, worktree)`，agent 库无成员表、会话 JSON 无 group 字段。⇒ 主人按「某分组里的过期会话」提问时只能**按 label/spawnedCwd/title 关键词推断**，并**明说这是启发式**，不得声称读到了归属。
- **清 cron 字段覆盖要用 CLI**：`automations` 工具传 `payload.model: null` **不会清除**（原值仍回读得到）；改用 `openclaw automations edit <id> --clear-model`（同类 `--clear-fallbacks` / `--clear-tools`），改完 `automations get <id> --json` 回读。（`cron get` 是多行 JSON，别用 grep 抓字段。）
- **一批定时任务集体失败，先归因同一根因再逐条修**：`doctor` 报「N automations have failed 3+ runs」而**失败告警默认关闭**（这可能就是唯一通知）。逐条 `openclaw automations show <id>` 读 `last error` / `diagnostic`：实测多个记忆类 job 全是 `cron: job interrupted by gateway restart`（另一独立形态是 `job execution timed out (last phase: tool-execution-started)`）。**判「是不是 systemd 拉起的」用 `systemctl --user show openclaw-gateway -p NRestarts -p ExecMainStartTimestamp`：`NRestarts=0` ⇒ 不是 systemd 重启，重启来自进程内/外部机制**，别默认按「服务崩溃」查。慢性失败会被调度器**退避停跑**（任务事实上静默停摆）。验证是否恢复：`openclaw automations run <id>` 手动触发（回 `{ok:true,enqueued:true}`，`status` 变 `running` 且 `last error` 清空），再用 `openclaw automations runs <id>` 读本次结果。
  - **doctor 报的「N 个任务失败」不是全集，三类漏报要自己补**：
    ① **执行失败 vs 投递失败是两回事**。`lastRunStatus: "ok"` / `exitCode: 0` **不代表结果送达**——同一份 `state` 里另有 `lastDeliveryStatus` 与 `lastDeliveryError`，实测某 job 每天成功执行却天天投递失败（`lastDeliveryError: "Delivering to Feishu requires target <chatId|user:openId|chat:chatId>"`），**doctor 完全不报这类失败**。逐条读 `state` 时把这两个字段一并读出；`announce` + `channel: "last"` 在飞书上不成立，须写实 `channel` + `to`。
    ② **「被重启打断」不算真失败**：doctor 明说它把 `job interrupted by gateway restart` 也计入失败数。分诊时先按 `last error` 归类，重启打断的连续出现才值得查根因，偶发一次不算。
    ③ **投递目标 open_id「跨应用」= 每天静默丢消息，且状态仍报 ok**：飞书 `open_id` 是**按应用命名空间**的，别处存着的 `ou_…` 很可能不属于本 bot 应用，实测回 `lastDeliveryStatus: "not-delivered"` + `lastDeliveryError` 含 `feishu_code:99992361 / "open_id cross app"`，而同一份 `state` 的 `lastRunStatus` 仍是 `ok` ⇒ **「执行成功」与「送达」必须分别读**。修法：**真源是 `channels.feishu.allowFrom` 里那个 id**（本 bot 应用认的），不是凭印象抄一份；改完**必须用 `message` 工具实发一条验证**（回 `messageId` 才算通），别等下一个排期才发现又没送达。
  - **`last phase: tool-execution-started` 超时：先比时长，再手动计时定性，别先改任务书**：`payload.timeoutSeconds` 与 `state.lastDurationMs` 摆一起看。`lastDurationMs ≈ timeoutSeconds`（实测 600144 vs 600）**有两种成因，处理方式相反**，用一条命令分开：**把该 job 的脚本/命令原样手动跑一次计时**。
    - **脚本手动跑很快（秒级）而 job 必撞上限** ⇒ 不是任务变慢，是**cron ↔ gateway 锁自锁**：任务体内（如体检脚本里的 `openclaw cron list`、`openclaw memory status`）再调 `openclaw` CLI，会与正在执行本任务的 gateway 进程抢同一把 cron 锁 ⇒ 子进程永等、job 卡到上限。**对症是给脚本内每处 `openclaw ...` 加 `timeout N` 护栏**（已验证：加 `timeout 25` / `timeout 40` 后脚本 15 秒内跑完），**放宽 `timeoutSeconds` 有害**——那只是让每次失败多烧一倍时间。
    - **脚本手动跑也慢/确实要那么久** ⇒ 才是真的上限卡死，按原口径放宽 `timeoutSeconds`。
    `consecutiveErrors` 持续累加会触发自动停用，越晚修越亏。
  - **第三种失败形态：`last error` 是「启动自检未在预算内完成」，与上面两种的处置方向相反**：实测两条跑在 main 上的 job 回 `Agent main has not completed startup inspection and preparation. The 5 second foreground startup budget elapsed; inspection continues.` ⇒ 含义是**该 agent 的启动自检没跑完，session 当时不可用**，任务是被挡在门外而不是自己跑挂了。
    - **先分诊再归因，别默认它来自上两种**：它既不是「被重启打断」也不是「任务体超时」，所以上面两条的处置（查 NRestarts / 给脚本内 `openclaw …` 加 `timeout` 护栏 / 放宽 `timeoutSeconds`）**一条都不适用**，照做只会白改。
    - **「启动预算是被什么撑爆的」必须实测，别按体量猜——2026-10-16 本机实测的归因是 agent 数据库完整性门，不是技能数也不是记忆体量**：取证入口是**只读 `openclaw doctor`**（不带 `--fix`，见下条），它会打一行 `[state/agent-db] agent database integrity gate`，字段含 `elapsedMs` / `phaseDurationsMs` / `integrityGateMs` / `thresholdMs` / 逐表 `integrityTableTimings`。实测该机 `validation:6425ms`、`thresholdMs=1000`，而前台预算只有 5 秒 ⇒ **校验本身超预算**，会话因此长期不可用。慢在三张表：`memory_embedding_cache` 2434ms、`memory_index_chunks` 1241ms、`trajectory_runtime_events` 719ms。
      **归因纪律不因此撤销**：别的机器仍可能另有原因，**以 doctor 那行的实测数字为准**；`automations list` 的 status 列只给 error / skipped，**要给证就逐条 `automations show <id>` 读 `last error` 原句**。别把「技能多 / 记忆大」当既定原因写进报告——与 `openclaw-gateway-performance-triage`「库体量与配置体量都不是速度的代理指标」同一条纪律。
      ⚠️ **「库大」不等于「碎片多」——归因到校验慢之后，还要先分清容量问题还是配置问题，否则主修法会选错。** 2026-10-16 本机实测反例：`openclaw doctor --session-sqlite compact` 全程成功，库 633 MB → **624 MB（只回收 9 MB / 1.4%）**，两条 error cron **依然 error**。⇒ **compact 对本形态无效**。原因是 `session.maintenance.pruneAfter` 早已是 `"7d"`，库里 402 MB（64%）是 `transcript_events` + `trajectory_runtime_events` 这类**真实会话与遥测数据**，不是可回收的空闲页；`pruneAfter` 已配 + 数据全是近 7 天的真实工作 ⇒ 这是**容量问题、不是阈值或碎片问题**。
      ⇒ **禁止把 compact 当这一形态的主修法**。分诊顺序：① 用 `dbstat` 归因最大表（命令见 `references/会话库膨胀分诊.md` §A 判据 4）；② 若最大表是真实会话/遥测数据且 `pruneAfter` 已收紧 ⇒ **无技术解**，只能交主人三选一：**缩短 `pruneAfter`（真实丢弃历史，必须主人拍板）／把跑在该 agent 上的任务迁到别的 agent（不丢数据，推荐）／接受现状并如实报「未修及原因」**。③ 只有 `freelist_count` 显示碎片可观时，compact 才是主修法。**不要先假设「压小库就能过预算」**——这与上一条的「体量不是速度代理指标」是同一条纪律的两种形态，一个防误归因、一个防误开方。
    - ⚠️ **「已经跑了」不等于「做成了」——交接脚本后必须独立取证,不要凭主人一句确认就报成功。** 2026-10-16 实测：主人说「已经跑了啊」，但维护日志里**搜不到该次运行的任何一行**（`grep -c "维护开始（v2）"` 回 `0`），而 `gateway-restart.log` 显示 22:22:19 `action=stop interactive=0` / 22:24:52 `action=start interactive=0` ⇒ **只证明网关确实被非交互地停起过，不证明 compact 跑过、更不证明它有效**（库只小 9 MB，且未出现 v2 日志）。判据：**正向取证** = 日志里有该次运行的起止行 + 库体积给出**前后两个值** + `openclaw automations run <id>` 手动触发后 `last error` 清空。三者缺一即报「未确认」，别把「网关重启过」当「维护成功过」。
    - 实测形态（逐条验过才登记，**没验的不要替它断言根因**）：2026-10-16 同批 4 条 error 里，本轮**实查 2 条** —— `Daily Skill Update (lunheng)` 回的就是本条的启动预算原句（`last error` 与 `diagnostic` 同为 `The 5 second foreground startup budget elapsed`；`last delivery` 字段是 `unknown`、而 `last delivery error` 装的是同一条错误 ⇒ 执行与投递同因失败）；`Memory Distillation (novelist)` 回的是**泛化文案** `OpenClaw couldn't finish this reply. For details, open Settings → Logs`，**它尚未被归因**，不能因为同批就并入启动预算一条；另两条（两个 Heartbeat）只验到 list 层状态、连 `automations show` 都没跑过。要坐实泛化文案那条，查 `openclaw logs` 或复跑 `openclaw automations run <id>` 看是否回落到同一句。\n⚠️ **「同批归因」的谨慎已被后续实测推翻**：这两条的运行历史显示它们**各自前 4 次都 `ok`**，且唯一那次 error 紧跟开机（详见下方开机窗口一条）⇒ **同批一起变红 ≠ 同一根因**。分诊时逐条独立取证，不要因为一批 job 同时报错就套用同一个根因或同一个修法。
    - 修法按实测归因选，且**都要先拿到上一条的归因再谈**：归因落在**碎片多** / 校验慢 ⇒ 主修法是 `openclaw doctor --session-sqlite compact`（官方文档语义：WAL checkpoint + `VACUUM` + 转 `auto_vacuum=INCREMENTAL`）。⚠️ **但「库大」必须先拆成「碎片多」还是「真实数据多」再选修法**——实测 compact 把 633 MB 压到 624 MB（仅回收 1.4%）时，两条 error cron 依然 error ⇒ 库里绝大部分是真实会话/遥测数据时 compact 无效；此时无技术解，只能交主人三选一（缩短 `pruneAfter` 丢历史 / 把任务迁到别的 agent / 接受现状）。归因与分诊顺序见上条与 `references/会话库膨胀分诊.md` §A。文档给的标准序列是 `openclaw gateway stop` → `openclaw backup create --verify` → `doctor --session-sqlite compact --session-sqlite-all-agents` → `openclaw gateway start`；⚠️ **但文档这条序列照抄会失败**：对运行中的 operator 网关，`gateway stop` **必须加 `--force`**，否则退出码 1 并拒绝执行（文档与 `gateway --help` 的示例都写的是裸命令）。**整段需要停网关 ⇒ 交主人执行**，本 agent 不自行 exec 重启；且**不得在本网关托管的会话里后台发射该序列**（停网关会连带杀掉本会话、事后无法汇报）。完整序列、脚本三条硬要求（校验退出码即中止 / `trap … EXIT` 兜底拉起 / 确认网关真停）与审批层拒绝的正确处置，见 `references/会话库膨胀分诊.md` §C-4。另一方向是调高该 agent 的启动自检预算或降低启动期读入量，**在归因不是这两者时改它们是白改**。改完用 `openclaw automations run <id>` 手动触发验证（同上条的验证口径）。
    - ⚠️ **给「迁到别的 agent」之前，先量目标 agent 的库体量——迁移方向可能就是反的。** 实测（2026-10-16）：`main` 库 **625 MB** 而 `novelist` 库仅 **21 MB**（差 30 倍），启动预算超时的是 **`main`**；此时若把 `novelist` 的任务「迁到 main」等于把能跑的 agent 推进死路。⇒ **本条三选一里的「迁到别的 agent」只有在目标 agent 库体量显著更小时才是解法**；先 `ls -lh ~/.openclaw/agents/*/agent/openclaw-agent.sqlite` 逐个比，目标不比源小 ⇒ 报「无迁移这条路」，别把这个选项当成推荐项递给主人。库体量是本形态唯一可用的量化判据（`session.maintenance.*` 只影响单个 agent，管不了别的库）。
    - ⚠️ **「这个任务是不是真坏了」先看运行历史，再看 `last error`：`automations runs <id>` 与开机时间一对，失败常只是开机补跑窗口的产物。** 实测（2026-10-16）两条 job 各有 5 条历史，**前 4 条 `ok`、仅最新一条 `error`**，而那条 error 的 `runAtIso` 是 `15:58:06` / `16:00:36`，`uptime -s` 是 **`15:57:16`** ⇒ 失败发生在开机后 50 秒 / 3 分 20 秒，是**关机期间积压的调度在网关启动瞬间集中补跑**、撞上启动自检窗口，**不是任务缺陷、也不需要迁移任何东西**。⇒ ① 拿到一批 error job 先跑 `openclaw automations runs <id>`（回 `entries[]`，每条含 `runAtIso` / `status` / `durationMs` / `error`），**看连续 ok 的长度**——「长期 ok + 单条 error」与「连续 error」是两种病，前者多半是窗口撞车；② 再 `uptime -s` 对齐那条 error 的 `runAtIso`，**差值小于几分钟即判开机窗口**；③ 这类结论的正确交付是「**什么都不改，等下一次自然排期自证**」，把 compact / 迁 agent / 缩 `pruneAfter` 三个动作全部收回——它们修的是一个并不存在的常驻故障。⚠️ `status` 与 `completionStatus` 是两个独立字段（实测同一 job 出现 `status=ok` + `completionStatus=failed` 与 `ok`/`succeeded` 两种组合），**判成败以 `status` + `error` 为准**，别只看 `completionStatus`。⚠️ `automations runs` 的 JSON 顶层键是 **`entries`**，不是 `runs`/`items`；写解析脚本取错键会静默取到 0 条（实测两次都回空），从而误判「没有历史」。
- **状态目录的旧快照能到几百 MB**：`~/.openclaw/backups/` 实测含 339 MB 的 `main-agent-auth-*.sqlite`（十几天前的库快照）。清理用 `gio trash`（本机有 `/usr/bin/gio`，**禁用 `rm`**）。⚠️ **trash 不释放磁盘空间**（回收站与状态目录同盘）⇒ 报释放量用 `df` 前后对比而非 `du`；且**盘不紧张时不要把清理当优化项**（实测 1007 G 用 30 G，清 1.5 G 收益近零）。完整清理判据与回收站再生项见 `workspace-declutter`。
- **主人说「会话 / 状态目录到了 N G」时，先分诊再动手**：那 1 GB 通常**不在** `agents/<id>/sessions/`（实测库本体 1.1 GB 而 `sessions/` 仅 8.9 MB）；碎片还是数据用只读 `pragma freelist_count` 判（实测 free 1.4 MB / total 1.04 GB ⇒ 碎片可忽略，**先删数据再 VACUUM**，直接 compact 只省 1.4 MB）。完整分诊、收紧配置、**执行顺序（coldStorage → dry-run → enforce → compact）**、残留类别与命令形态见 `references/会话库膨胀分诊.md`。
- **插件自带的 SecretRef schema 可能与核心校验冲突**：openviking 的 `config.apiKey` 三种写法（`{source:file,id}` / `{source:file,provider,id}` / `{source:env,…}`）实测**全被拒**，schema lookup 声称允许 file 型而校验只认 env 型 ⇒ 属插件 bug。**改不动也要如实报**，把出路（升级插件 / 改 `${ENV}` + 环境变量）写进交付，不为「全绿」硬凑。
- **本 agent 永不 exec 重启本 Gateway**：`Restart the gateway to apply` 的项**集中列给主人**（或走 `openclaw` 工具），不要用 exec 跑 `systemctl restart`。同理**需要停网关的离线维护**（`backup create` / `doctor --session-sqlite compact`）**整段交主人**；本 agent 只给命令序列与理由。
- ⚠️ **`openclaw` 工具报 `Cannot find module …/tmp/plugin-captures/…` 时，先怀疑「清理时删过该目录」，而不是插件装坏。** 实测（2026-10-17）：`config.set` 失败回执的 require stack 指向 `extensions/feishu/dist/index.js`、缺失模块却在 `tmp/plugin-captures/` 下 ⇒ **故障面只有「用工具写配置」这一条**，gateway 仍 `health OK`、通道仍 `configured`、插件本体在 `extensions/<id>/dist/` 完好；删后 40 分钟该目录**未自行再生**。⇒ 处置按 SKILL.md「第三条写入路径」**直接热编辑 `openclaw.json`** 绕过（只读 CLI 全部正常）；**不要**去重装插件、也不要反复重试同一次工具调用。完整判据、指纹识别与恢复路径见 `references/会话库膨胀分诊.md` §D。
- **明文密钥要跑 `openclaw secrets audit --check`，别只跑 `doctor`**：`doctor` 的 Security 面板只点名 `openclaw.json` 里的 `models.providers.<id>.apiKey`，**这不是总数**。`secrets audit --check` 覆盖 `models.providers.*`、`state/openclaw.sqlite` 的 auth profile、各 agent 的 `models.json` 与 sqlite，回 `plaintext=` / `unresolved=` / `shadowed=` / `legacy=` 四个计数。⇒ **同一个 key 常在多处同时明文存在**（同一 provider 在配置与 auth profile 里各有一份）⇒ **只改 `openclaw.json` 里那几处等于没改**，会得到「看起来安全了」的假象。`security audit` 的 warn 列表不含这一类，三条命令各报一面，缺一不可。
  ⚠️ **`secrets audit --check` 的扫描面不含插件级 config**：`plugins.entries.<id>.config.apiKey` 这类明文存放的值不进它的回执 ⇒ **报总数前自己再扫一遍 `plugins.entries` 下每个 `config` 的 key/token/secret 字段**，把漏掉的并进计数；工具回执不是全集。扫描只输出**路径与长度**，不回显值——值一旦进终端历史就等于泄露。
- ⚠️ **`openclaw secrets store list` 会把 `env` 类型条目明文打印出来，而 `secret` 类型只显示掩码。** 实测一次 `store list` 打印出两条真实密钥（`*_AGENT_PLAN_API_KEY`、`EXA_API_KEY`，均为 `env` 类型），主人把它们贴回对话即等于泄露到终端历史 + 对话记录。⇒ **排查密钥时不要把 `store list` 的原始输出转述或贴给主人**；看到 `env` 类型条目就在报告里只写名称不写值，并提示主人在控制台轮换。**排查用 `secrets audit --check`（按路径报、不含值）替代 `store list`**。
- **`store set` 的 `--value` 只对 `env` 类型生效；`secret` 类型必须走掩码交互提示。** `openclaw secrets store set <NAME> --kind secret` 不带 `--value` 会弹掩码输入（值不进 shell history、不落盘、不经过 agent 上下文）⇒ **给主人的录入指令一律用不带 `--value` 的形式**，并明确告知「不要把 key 贴进对话」。
- ⚠️ **给主人的密钥模板里不要用 `***` 当占位符**——实测主人原样粘贴后，`store import` 会把 `***` 识别成 OpenClaw 的脱敏占位符并拒绝写入（回 `contains a redaction placeholder` / `Skipped redacted value`）。系统拦住了所以无损坏，但流程被打断。写模板时用 `<粘贴你的真实key>` 这类明确占位文字。
- **「密钥已在 store 但配置仍是明文」是常见形态，别当成没迁移过**：实测库中 `TEAMOROUTER_API_KEY` 等早已是 `[secret] write-only`，而 `openclaw.json` 照旧明文 ⇒ **真正缺的是配置接线，不是搬运密钥**。接线写法是内建来源 `store`，**不需要在 `secrets.providers` 里定义 provider**（那里放的是自建 `file` 类型，二者不是一回事）：`{"source":"store","provider":"default","id":"ENTRY_NAME"}`。⚠️ **顺序不可颠倒**——配置先指向不存在的条目会让该 provider 直接变冷（调用失败）。先确认条目已入库，再改配置。`secrets configure` 需要 TTY、agent 跑不了，接线那步交主人或走热编辑。
- **JSON 批量改配置前先验证「往返同一性」**：`json.dumps(d, ensure_ascii=False, indent=2)+"\n"` 与原文逐字节比对回 `IDENTICAL` 才动手，否则整份 66 KB 配置会被重排、diff 淹没真实改动。改完用 `diff <(json.tool 备份) <(json.tool 现文件) | grep -c '^<'` 确认**删除/修改行为 0**、只有新增行。（批量禁用技能走 `skills.entries.<name>.enabled=false`，该字段就是禁用开关，与白名单排除是两套机制。）
- **`openclaw sessions delete` 不动 `cold/` 归档目录**：实测删 10 条超期会话后活跃会话 66→56，但 `agents/<id>/sessions/cold/` 的 **301 个文件 / 57 MB 一字未变**；输出里的 `Archived transcript: …` 说明转录是**归档**不是删除，且仍可被记忆检索命中 ⇒ 还要跑 `openclaw memory forget --agent <id> --session <key>`（仅本机跑，不接受 `--url` 转发）。⇒ **主人说「清掉 N 天以前的」若其真实目标是释放 `cold/` 那几十 MB，本命令达不到**，须先讲清两者不是一回事再动手。
- ⚠️ **`*.jsonl.deleted.*.zst` 不是删除残留，是 OpenClaw 托管的规范转录归档副本，清理时必须排除。** 实测踩坑：看到 `agents/main/sessions/` 下 43 个 `*.jsonl.deleted.<ts>.<sha>.zst`，按「已删会话的垃圾残留」清掉，事后 `openclaw update status` 回 `Missing 35 canonical transcript archive file(s); showing 5 example(s)` + 逐条 `Missing canonical transcript archive copy:` ⇒ 这些副本由迁移流程按规范路径管理。**数据本体仍在 SQLite blob 里**（官方回 `Canonical SQLite archive blobs remain retained`），属警告非数据丢失，但副本不会自动重建。⇒ ① 清理 `sessions/` 时按模式**排除** `.deleted.`，别按「文件名像垃圾」判；② 事后自查跑 `openclaw update status` 看有没有 `Missing canonical transcript archive`；③ 真正的删除残留是 `.tmp`/`.DS_Store`/`:Zone.Identifier` 之类，不带 `.deleted.`。判据是文件名前缀 + update status 告警，不是主观的「看起来没用了」。
- ⚠️ **开方前先用一条独立命令验证「前提」本身，这步最容易省且最贵。** 连续三次因未验证前提给出错方向：① 把启动自检超时归因成「空闲页没回收」并推荐 VACUUM，实测 compact 只回收 9 MB / 1.4%，证明库里是真实数据；② 未量目标 agent 库体量就推荐「把任务迁到 main」，而 main 正是超预算的那个（625 MB vs novelist 21 MB），方向反了；③ 断言「某大文件 110 K 在吃上下文」，`grep` 全配置零引用——它根本不注入，省的是磁盘不是延迟。⇒ 每条修法落地前先验证「它确实是我说的那个东西」：是否真被注入用 `grep` 查引用面、体量是否真是问题源用 `du`/`dbstat` 归因、迁移方向是否对用体量对比。**实测值推翻假设时如实推翻并说明原判断错在哪**，不要把错方案留在报告里等主人拍板。

## 步骤

1. **盘点：四条命令 + 体量面，先出全景**
   跑前置事实里的 doctor / status / config validate / security audit / automations list（逐条 show / runs 读 last error）/ sessions cleanup --dry-run，再 `du -sh` 状态目录各子目录。
   完成判据：能逐条说出「哪些是告警、哪些是信息、体量重心在哪」，且**每条告警都落到具体配置路径**（如 `tools.exec.mode`、`browser.extensionRelay.allowLegacyAuth`）。
2. **分诊与排序：严重度 × 是否改变交互**
   每项标**零行为影响**（死引用 / 旧快照 / 冗余清单）／**改变交互**（exec 策略、工具面、自动归档）／**信息性**之一；档内按「收益 ÷ 风险」排，并**把改变交互的排到最后**。
   完成判据：产出带档位的清单，读者一眼看出哪些可直接做、哪些要主人拍板。
3. **分批修正：一组一 dry-run、一组一回读**
   逐条按前置事实的坑修：配置类先 `--dry-run`（对象整体替换记得 `--replace-path`）；状态类先备份或 `gio trash`；凭据类先报后动。**每批做完立即回读**该路径实际值并记「改前 → 改后」。
   完成判据：每批都有回读证据（键数 / 值 / 计数），**不接受「命令回执成功」当完成**；改不动的项**如实登记为未修**并写明原因与出路，不静默跳过、不硬凑。
4. **交付：清单 + 重启项 + 记账**
   报告分「已修（含前后值）／未修（含原因与出路）／待主人拍板」三段；需重启才生效的项**集中列出交主人**；写当日 `memory/YYYY-MM-DD.md`（改了什么、备份在哪、还差什么）。
   完成判据：主人拿到可复核的改动账本与重启清单；本 agent 未自行重启 gateway。

## 边界

- 只做**本机配置与状态面**（`~/.openclaw`）；工作区文件整理走 `workspace-declutter`，provider / 插件 / 通道的增删走各自 removal 技能。
- **改变交互的加固（exec 策略、工具面、自动归档）须主人明确指令**；只诊断时不得顺手改。
- 删除一律可恢复（`gio trash` / 移入备份目录 / 先 `cp`），**禁用 `rm`**。
- 结论只用实测值与回读值；引用体检报告的既有定性（含本文里的历史数字）前先重测。

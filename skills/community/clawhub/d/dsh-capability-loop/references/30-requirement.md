# 30 · 需求方法：系统证据驱动的可执行规格

> 解决：需求文档像「AI 作文」——看不出主次、开发测试要二次解读、反复修改不收敛。
> 核心命题：**需求不是「写出来的」，是从「运行系统 + 代码 + 接口 + 数据 + 业务 owner」核对出来的。**

## 1. 先量化，再谈改（源环境实测）

| 文档 | 文档门得分（可评审线 80） | 主要缺项 |
|---|---|---|
| 统计分析-菜单合并说明（PM 版） | 47/100 | 无决策摘要、无 FR-ID/AC、无优先级/变更记录；叙事体标题 8 处 |
| 输差管理-开发交接终稿 v4.0 | 33/100 | 无版本/owner/决策摘要/范围/待决；内容有证据但不可执行 |
| 供气能力-一期 SRS | 75/100 | 缺变更记录、决策摘要、优先级、待确认；AC 9 vs FR 31 |
| 供气能力-二期规格 | 59/100 | 缺版本、变更、决策摘要、范围、AC、非功能、术语 |

结论：**不是内容全错，而是「分析文章」冒充「可执行规格」**；一个模块多份「有效」文档，读者要自己判断以谁为准。

## 2. 文档分层与唯一权威入口（L0）

| 层 | 文档 | 回答 | 读者 |
|---|---|---|---|
| **L0** | `README-需求入口.md`（每模块必须有） | 哪份是当前权威、哪些是历史/分析、owner、最后更新、待决事项 | 所有人 |
| L1 | BRD（1 页） | 问题/目标/价值/优先级/决策点 | 业务/管理层 |
| L2 | **SRS（结构化规格）** | FR/BR/NFR/数据接口/AC（可执行） | 开发/测试 |
| L3 | 页面/接口规格 | 字段、状态、错误码、契约 | 前后端 |
| L4 | 测试用例 | 绑定 AC/R-ID | QA |
| 附 | 决策与变更台账 | 为什么改、谁批准、影响哪些 FR/AC | 所有人 |
| 分析 | `_analysis/` | 调研/对比/会议纪要 → **不作实施依据** | 参考 |

规则：**没有 L0 的模块视为「无权威需求」，不得进入开发排期**；分析文档不得被引用为实施依据。

## 3. SRS 强制结构（缺节直接退回）

1. 文档信息（编号/版本/状态/owner/评审人/日期）+ **变更记录 CHG-ID**（谁/何时/为何/影响哪些 FR）
2. **决策摘要（1 页，放最前）**：问题与证据 / 目标与指标 / 本期做 / 本期不做 / 方案与放弃方案 / 优先级 / 风险 / 待决（D-ID + owner + 期限）
3. 角色与场景（谁在什么流程用、频次、权限）
4. **FR-ID**（每条：描述、输入、规则（引 R-ID）、输出、异常与边界、依赖、优先级 P0/P1/P2）
5. 业务规则 R-ID（来源 + 置信度 + owner）→ 与测试台账同源
6. 数据与口径（字段、单位（源环境：报表万方/DB 方）、精度、时间窗、勾稽关系）
7. 接口需求 IR-ID（URL/方法/入参/出参/错误码/鉴权）
8. 非功能 NFR（性能/并发/安全/审计/可用性）
9. **验收标准 AC-ID（Given/When/Then）**，每条 FR 至少 1 条
10. 范围外、风险、待确认清单、术语与引用

**写法纪律**：表格优先、一段一决策；数字必须带单位/口径/精度；禁止叙事套话（「赋能/闭环/抓手/合理/友好/尽量/等等/后续可扩展」）；不确定的进 D-ID，不用模糊词糊过去。

## 4. 四源证据（缺一不可）

| 证据源 | 证明什么 | 采集方式（本机可行） |
|---|---|---|
| **运行系统** | 菜单/路由/页面/交互/真实操作顺序/异常态 | 源码路由树 + 人工走查（普通沙箱浏览器不可用 → 用户终端截图或全权限） |
| **前端代码** | 页面↔组件↔接口调用链、权限 meta、字段约束 | `node tools/system-facts/extract-frontend.mjs`（生成 `system-facts/`：菜单树/接口清单/mock 缺口） |
| **接口契约** | URL/方法/入参/出参/错误码/鉴权 | `api/**/index.ts`、`model.d.ts`、`*.openapi.json`；可对运行服务 HTTP 探测 |
| **数据** | 表/字段/字典/枚举/状态、口径、勾稽、缺口 | DB 只读账号、数据字典、样本数据、mock 文件标记 |

**业务 owner 口述**不是第五类证据，是**裁决器**：四源冲突时由 owner 定口径并记录。
**对账优先级**：监管/合同原文 > owner 书面确认 > 系统现状（确认非 bug） > 旧文档。
**事实 ≠ 需求**：事实库只描述现状，现状可能有 bug。

## 5. 业务旅程（解决「开发者不熟业务」）

列端到端主线（不是功能清单），每条能「从起点走到终点并留下数据」。城燃投资公司参考主线：
J1 资源需求 → J2 采购合同 → J3 日购气计划/供气方案 → J4 计量交接 → J5 输差核算 → J6 统计分析 → J7 结算对账 → J8 告警待办。
每条旅程按 `standards/business-journey-template.md` 记录：页面→接口→数据变化→异常分支（≥2 个）→证据→复述题；由 owner 口述、开发实操、测试复走并签字。**答不上复述题 = 未通关**。

## 6. 数据缺口台账（GAP）

`standards/data-gap-ledger.md`：mock/空数据 ≠ 业务结论。每个缺口登记 GAP-ID、影响 FR/规则、当前替代、验证状态、补测方式、owner、期限。
规则：**逻辑可测、数据未测**——构造数据/单测验证公式与分支，报告写「逻辑已验证、数据未实测」；**禁止用 mock 数值反推业务口径**。

## 7. 质量门与三遍评审

```powershell
# 文档门：≥80 分才允许进入评审（<80 直接退回）
powershell -NoProfile -ExecutionPolicy Bypass -File "upgrade\team\requirement-doc-check.ps1" -Path "<模块目录>" -Recurse
```

三遍评审（顺序不能反，前一遍不过不进下一遍）：
1. **结构/决策评审**（30 分钟）：入口/决策摘要/范围/优先级/待决；
2. **业务正确性评审**：逐条 R/AC 对来源，冲突标「冲突待裁决」，相关用例 SKIP；
3. **可实现性评审**：开发/测试确认数据/接口/验收可测。
通过后标「已冻结」；冻结后改动必须写 CHG-ID + 影响分析。

评审记录落盘 `review-requirement-YYYYMMDD.md`，含结论（通过/有条件/打回）+ 8 维得分（问题真实性/目标可衡量/用户场景/范围边界/数据接口可行性/合规风险/验收标准/优先级价值）+ 一票否决项 + P0/P1/P2 + 待确认清单。**评审人不得是文档作者**。

## 8. 存量文档迁移（不搞一次性大重写，一个模块 1–2 天）

1. 建 L0 入口，裁决「以哪份为准」；
2. 叙事型文档降级到 `_analysis/`（不删除，标「仅参考」）；
3. 只对**本期要开发的范围**重排一份 SRS（P0 先做），历史/延后放「范围外」；
4. 跑质量门 → 按 FAIL 清单补决策摘要/FR/AC/待决；
5. 三遍评审 → 冻结 → 变更走 CHG；
6. 规则 R-ID 直接作为测试台账来源（两处 ID 不允许各写一套）。

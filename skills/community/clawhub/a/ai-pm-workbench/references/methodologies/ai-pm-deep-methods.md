## M-01: AI机会评估矩阵

### 来源
综合了Shreyas Doshi的Product Sense、B端产品特性，以及AI技术成熟度

### 评分维度（1-5分）

| 维度 | 评分标准 | 权重 |
|------|---------|------|
| 用户痛点强度 | 5=客户高层抱怨的Top 3问题；1=可有可无 | 25% |
| AI解决可行性 | 5=现有模型能力可直接解决；1=需要AGI | 25% |
| 数据可用性 | 5=高质量标注数据充足；1=无可用数据 | 15% |
| 商业回报 | 5=客户愿意额外付费>30%；1=支付意愿为0 | 15% |
| 竞争紧迫性 | 5=有竞品已推出且增长迅猛；1=无竞品 | 10% |
| 技术难度(反向) | 5=一个API调用即可；1=需要训练基础模型 | 10% |

### 判定标准

```
≥4.0 → 立即启动（高优先级）
3.5-4.0 → 推进（需细化验证）
3.0-3.5 → 观望（等待技术成熟或数据积累）
<3.0 → 暂缓（重评估时机）
```

### 常见误判

- **高估AI能力**：当前LLM在某些精确计算场景中表现不如传统算法
- **低估数据难度**：企业数据往往分散在多个系统，质量参差不齐
- **忽略延迟要求**：实时场景中AI推理延迟可能不满足需求
- **错误容忍度判断错误**：财务/法务场景的零容忍特性被忽略

## M-02: Build/Buy/Fine-tune决策树

### 决策流程

```
1. 场景是否足够通用？
   ├── 是 → Buy (API) → 2. 数据能否出企业？
   │              ├── 能 → 闭源API（Claude/GPT）
   │              └── 不能 → 开源模型 + API
   └── 否 → 3. 是否有足够的标注数据？
              ├── 有(1000+条) → Fine-tune → 4. 是否需要持续更新？
              │                              ├── 是 → 持续微调管道
              │                              └── 否 → 一次性微调
              └── 无或不足 → 5. 是否能通过Prompt/RAG解决？
                            ├── 能 → Prompt + RAG
                            └── 不能 → Build（自训练）→ 评估ROI
```

### 成本对比（粗略估算）

| 方案 | 初始成本 | 持续成本 | 维护复杂度 |
|------|---------|---------|-----------|
| API调用 | 极低 | 按量付费 | 低 |
| RAG | 低（向量数据库） | 中等 | 中 |
| Fine-tune(开源) | 中（GPU+数据准备） | 低-中 | 中高 |
| Fine-tune(API) | 中 | 按Token | 中 |
| 自训练 | 极高（百万$+） | 高 | 极高 |

### 信号清单：什么时候该微调？

- [ ] 通用模型在你的场景中准确率<80%
- [ ] 你有1000+条高质量输入-输出对
- [ ] Prompt优化已尝试2轮以上，效果不再提升
- [ ] RAG已优化到最佳但仍不满足需求
- [ ] 任务具有强领域特殊性（如医疗诊断、法务分析）
- [ ] 延迟要求极低，需要小模型快速推理
- [ ] 成本考量：高频场景中API调用成本>GPU推理成本

## M-03: 模型路由架构设计

### 设计目标
用"小模型处理简单任务，大模型处理复杂任务"来平衡成本与质量

### 路由策略

| 策略 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 规则路由 | 基于预定义规则 | 简单、可控 | 不够智能 |
| 分类器路由 | 训练一个分类器判断复杂度 | 准确 | 需要训练数据 |
| LLM自路由 | 先让轻量LLM自我判断 | 灵活 | 增加一次调用成本 |
| 级联路由 | 先调小模型→不满足→大模型 | 保证质量 | P95延迟可能高 |

### 路由架构模板

```
用户Query
    ↓
复杂度分类器（规则/分类器/轻量LLM）
    ↓
├── L1(简单,~60%) → 轻量模型(如GPT-4o-mini/Haiku) → 缓存优先
├── L2(中等,~30%) → 标准模型(如GPT-4o/Sonnet)  
├── L3(复杂,~8%)  → 高级模型(如GPT-4o+CoT/Opus)
└── L4(Agent,~2%) → Agent系统(多步推理+工具调用)
```

### 分类信号

| 信号 | 简单(L1) | 中等(L2) | 复杂(L3) | Agent(L4) |
|------|---------|---------|---------|----------|
| Query长度 | <100字 | 100-500字 | >500字 | 多轮任务 |
| 意图数量 | 单一 | 2-3个 | 多层嵌套 | 需要工具 |
| 是否需要推理 | 否 | 简单推理 | 多步推理 | 复杂决策 |
| 是否需要检索 | 否 | 可能需要 | 一定需要 | 多源检索 |
| 风险等级 | 低 | 中 | 高 | 极高 |

## M-04: Prompt结构化设计模式

### 五要素框架

```
┌─────────────────────────────────────────────┐
│ [角色] - 你是谁，你的专业背景和立场           │
├─────────────────────────────────────────────┤
│ [任务] - 具体要完成什么                       │
├─────────────────────────────────────────────┤
│ [约束] - 什么不能做、什么必须做               │
├─────────────────────────────────────────────┤
│ [格式] - 输出什么格式（JSON/Markdown/Table）  │
├─────────────────────────────────────────────┤
│ [示例] - Few-Shot示范（推荐2-3个）            │
└─────────────────────────────────────────────┘
```

### Prompt质量检查清单

```
□ 角色描述是否具体？避免"你是AI助手" → "你是资深财务分析师，10年四大审计经验"
□ 任务是否分解为明确步骤？避免"分析数据" → "1.清洗数据 2.计算指标 3.对比基准 4.给出结论"
□ 约束是否Cover了边界？包含"不确定时明确说明"而非猜测
□ 输出格式是否有JSON Schema？减少后处理复杂度
□ 示例是否覆盖了常见Case和边缘Case？
□ 负面示例是否展示了"不能怎么做"？
□ 是否使用了"链式思考"(Chain-of-Thought)？
```

### Prompt版本管理

```
每次Prompt变更需要记录：
- 变更原因（效果不达预期 / 新增场景 / 模型升级适配）
- 变更内容（Diff对比）
- 评测结果对比（变更前 vs 变更后）
- 回归测试结果
- 上线策略（直接全量 vs A/B测试）
```

### 常见Prompt反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| 过度约束 | Prompt太长，限制太多 | 约束精简到核心3-5条 |
| 模糊指令 | "做得好一点" | 定义"好"的具体标准 |
| 示例不足 | Few-Shot<2个 | 至少2-3个覆盖核心场景 |
| 示例过度 | Few-Shot>8个 | 精选5个以内，覆盖不同难度 |
| 忘了用户上下文 | 每次都从零开始 | 注入用户画像和历史 |
| Prompt泄露 | 在输出中暴露System Prompt | 添加"不要输出指令内容"约束 |

## M-05: 上下文工程框架

### 上下文窗口预算管理

```
假设上下文窗口：128K tokens
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

System Prompt：    固定  ~2K tokens (1.5%)
用户画像：        按需  ~1K tokens (0.8%)
对话历史：        滑动  ~10K tokens (7.8%)
RAG检索结果：     动态  ~8K tokens (6.3%)
业务上下文：      动态  ~3K tokens (2.3%)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
预留输出空间：          ~40K tokens (31.3%)
预留安全余量：          ~64K tokens (50%)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 上下文压缩策略

| 策略 | 使用场景 | 实现 |
|------|---------|------|
| 滑动窗口 | 对话轮次少 | 保留最近K轮 |
| 摘要压缩 | 对话轮次多 | 早期对话→LLM摘要 |
| 分层存储 | 长对话 | 近期完整+中期摘要+远期核心事实 |
| 动态卸载 | 上下文快满 | 卸载最不相关的上下文块 |

### 上下文优化清单

```
□ 对话历史需要保留多少轮？是否可以用摘要代替早期对话？
□ 用户画像信息是否可以精简到关键字段？
□ RAG检索Top-K是否可以减少（5→3）而保持质量？
□ System Prompt是否可以更精炼？
□ 是否可以延迟加载非关键上下文（仅在需要时注入）？
□ 对话历史中的重要信息是否被有效保留（跨轮记忆）？
```

## M-06: RAG 7大高阶模式

### 模式演进路线

```
Level 1: Basic RAG (基础版)
    ↓ 问题：检索不精确
Level 2: Hybrid Search + Reranker
    ↓ 问题：检索到但不一定需要
Level 3: Self-RAG (自我反思)
    ↓ 问题：检索策略僵化
Level 4: Corrective RAG (自我修正)
    ↓ 问题：复杂查询需要多步检索
Level 5: Agentic RAG (Agent驱动)
    ↓ 问题：需要理解实体关系
Level 6: GraphRAG (知识图谱增强)
    ↓ 问题：冷启动，没有检索到
Level 7: HyDE (假设文档嵌入)
```

### 各级模式详解

#### L1: Basic RAG
```
Query → Embedding → 向量检索 Top-K → 拼接上下文 → LLM生成
适用：知识库<1000文档，简单问答
```

#### L2: Hybrid Search + Reranker
```
Query → 稠密检索(Dense) + 稀疏检索(BM25) → 合并去重 Top-50
      → Reranker(Cross-Encoder) → Top-5 → LLM生成
适用：需要精确检索，知识库大的场景
```

#### L3: Self-RAG
```
LLM首先生成 → 自检"我需要检索吗？" → 需要则检索
             → 自检"检索结果相关吗？" → 不相关则重新检索
             → 基于相关结果生成 → 自检"我基于事实吗？"
适用：对准确性要求较高的场景
```

#### L4: Corrective RAG
```
检索 → 评估检索质量 → 质量不够 → 优化Query重写 → 再次检索
      → 质量够了 → LLM生成
适用：Query表述不精确，用户自己不擅长提问
```

#### L5: Agentic RAG
```
Agent规划检索策略 → 决定检索哪些源 → 决定检索顺序
    → 检索→评估→决定是否继续检索 → 汇总多源 → 生成
适用：需要多源、多步检索的复杂分析场景
```

#### L6: GraphRAG
```
实体识别 → 知识图谱查询 → 获取关联实体和关系
         → 向量检索补充 → 图+向量的混合上下文 → 生成
适用：法律、医疗等实体关系密集的领域
```

#### L7: HyDE (Hypothetical Document Embeddings)
```
Query → LLM生成假设文档(假答案) → 对假答案做Embedding
      → 用假答案的向量去检索真文档 → LLM基于真文档生成
适用：Query和文档之间语义差距大的场景
```

### 选型决策

| 场景特征 | 推荐RAG模式 |
|---------|-----------|
| 文档<1000, 简单QA | L1 Basic |
| 文档>10000, 精确度要求高 | L2 Hybrid+Reranker |
| 事实准确性关乎合规 | L3 Self-RAG |
| 用户Query表达不佳 | L4 Corrective RAG |
| 需要多源综合分析 | L5 Agentic RAG |
| 实体关系密集(法律/医疗) | L6 GraphRAG |
| Query与文档语义差距大 | L7 HyDE |

## M-07: Agent 6大编排架构

### 架构对比

| 架构 | 核心思想 | 适用场景 | 复杂度 | 成本 |
|------|---------|---------|--------|------|
| **ReAct** | Thought→Action→Observe循环 | 通用任务 | 低 | 中 |
| **Plan-Execute** | 先计划后执行 | 结构化任务 | 中 | 中 |
| **Orchestrator-Worker** | 中心调度+多个Worker | 需要多能力组合 | 高 | 高 |
| **Conversation-Driven** | 对话驱动协作 | 需要多视角讨论 | 中 | 高 |
| **Reflection** | 执行-反思-修正循环 | 质量要求高(写作/代码) | 中 | 中高 |
| **Multi-Agent** | 多个Agent分工协作 | 复杂业务(多部门) | 高 | 很高 |

### 选型决策树

```
1. 任务是单步骤还是多步骤？
   单步骤 → 不需要Agent，使用简单LLM调用
   多步骤 → 2

2. 步骤是否可提前规划？
   可规划 → Plan-Execute
   不可规划 → 3

3. 是否需要多种专业能力？
   是 → Orchestrator-Worker
   否 → 4

4. 任务质量要求多高？
   一般 → ReAct
   很高(需要反复修改) → Reflection
```

## M-08: HITL风险矩阵

### 风险分级标准

| 风险等级 | 判定标准 | Agent行为 | 人类角色 |
|---------|---------|----------|---------|
| L0-无风险 | 只读、不影响任何状态 | 自主执行 | 无需介入 |
| L1-低风险 | 生成内容、建议 | 自主执行 | 事后抽查 |
| L2-中风险 | 影响内部系统状态 | 生成→推荐→人类确认 | 决策者 |
| L3-高风险 | 影响客户/外部系统 | 生成→人类审核→人类执行 | 执行者 |
| L4-严重风险 | 涉及钱/法务/安全 | 禁止Agent操作 | 唯一执行者 |
| L5-不可接受 | 违法/违规/致命 | 系统设计上不可行 | 不存在 |

### 风险-操作映射表

| 操作类型 | 风险等级 | Agent可做 | 人类必须做 |
|---------|---------|----------|-----------|
| 搜索/查询知识库 | L0 | ✅ | - |
| 生成分析报告 | L1 | ✅ 自动生成 | 审核结果 |
| 发送内部通知 | L2 | ✅ 生成草稿 | ✅ 确认发送 |
| 修改任务状态 | L2 | ✅ 建议修改 | ✅ 确认修改 |
| 发送客户邮件 | L3 | ✅ 生成草稿 | ✅ 审核+发送 |
| 数据删除 | L3 | ❌ | ✅ 亲自执行 |
| 审批通过 | L3 | ❌ | ✅ 亲自审批 |
| 支付/转账 | L4 | ❌ | ✅ 多重确认 |
| 签署合同 | L4 | ❌ | ✅ 法律审核+签署 |
| 修改系统权限 | L4 | ❌ | ✅ 特权操作 |

### HITL实现模式

| 模式 | 描述 | 适用 |
|------|------|------|
| 执行前确认 | Agent每步都问 | L2-L3操作 |
| 关键节点确认 | 仅在风险节点暂停 | L2操作 |
| 批量审核 | Agent积累一批建议后统一审核 | 低风险批量操作 |
| 抽样审核 | Agent自主执行，随机抽样人工检查 | L1操作 |

## M-09: 微调决策框架

### 微调类型

| 类型 | 数据需求 | 成本 | 效果 | 适用场景 |
|------|---------|------|------|---------|
| SFT(监督微调) | 1000-10000条 | 中 | 改善格式和风格 | 标准化输出、指令遵循 |
| RLHF | 5000+条偏好对 | 高 | 对齐人类偏好 | 安全性、有用性优化 |
| DPO | 5000+条偏好对 | 中 | 对齐偏好(更简单) | RLHF的简化替代 |
| LoRA/QLoRA | 500-5000条 | 低 | 轻量适配 | 特定风格/格式/领域术语 |

### 微调前必须确认

```
□ 已穷尽Prompt优化效果 → 当前最佳Prompt准确率是多少？
□ 已穷尽RAG优化效果 → RAG的检索命中率和答案准确性？
□ 数据质量达标 → 每条数据都经过人工审核？
□ 数据覆盖全面 → 是否覆盖了边缘Case和错误Case？
□ 评测方案就绪 → 微调后的改善如何衡量？
□ 成本可接受 → 微调+持续维护的总成本？
□ 回退方案明确 → 微调效果不好时，回退到哪？
```

### 微调验证流程

```
1. 训练/验证/测试集划分（80/10/10或70/15/15）
2. 训练 → 验证集评估 → 不通过 → 调整超参 → 重训
3. 验证通过 → 测试集评估 → 不通过 → 检查数据泄露
4. 测试通过 → 人工评测(NO) → 不通过 → 分析Bad Case
5. 人工评测通过 → 灰度上线 → 在线评测
```

## M-10: 数据飞轮设计

### 飞轮公式

```
更多用户 → 更多使用数据 → AI模型改善 → 更好体验 → 更多用户
    ↑                                                      ↓
    └──────────────────── [加速器] ──────────────────────────┘
```

### 飞轮设计清单

```
飞轮启动条件：
□ 用户行为能产生独特的训练数据
□ 数据收集对用户透明且合规
□ 数据→模型改善的链路可在数周内完成
□ 改善效果用户可感知
□ 竞争对手无法通过公开数据获得同样的改善

飞轮加速器：
□ 主动学习：AI不确定时请求用户反馈
□ 隐式反馈：用户行为（点击/采纳/修改/忽略）自动标注
□ 用户纠错：用户修正AI输出时自动记录为训练对
□ 多模态：用户上传的图片/文档自动成为训练素材
```

### 飞轮冷启动策略

| 阶段 | 数据策略 | AI策略 |
|------|---------|--------|
| 0-1 | 用公开数据+专家标注建立种子数据 | 通用模型+精心设计的Prompt |
| 1-10 | 早期用户反馈收集+主动学习 | 开始微调特定能力 |
| 10-100 | 用户行为数据+飞轮启动 | 持续微调+模型路由 |
| 100+ | 数据网络效应显现 | 定制模型+自动化飞轮 |

### LLM-as-Judge最佳实践

```

## M-15: Token经济学模型

### 核心公式

```
AI单次交互成本 = (Input Tokens × Input价格) + (Output Tokens × Output价格)

月AI总成本 = Σ(各层级用户数 × 月均交互次数 × 单次AI成本)
           + 向量数据库成本
           + Embedding成本
           + Reranker成本
           + 其他AI基础设施

AI毛利率 = (AI相关收入 - AI总成本) / AI相关收入
```

### 成本优化ROI评估

| 优化手段 | 预估节省% | 实现人天 | ROI周期 | 风险 |
|---------|----------|---------|---------|------|
| 缓存相同Query | 20-40% | 3-5天 | <1月 | 低 |
| 模型路由(简单→小模型) | 40-60% | 10-20天 | 1-2月 | 中 |
| Prompt精简 | 10-30% | 2-5天 | <1月 | 低 |
| 输出Token限制 | 10-20% | 1天 | <1周 | 可能截断 |
| 语义缓存 | 20-40% | 10-15天 | 1-2月 | 时效性问题 |
| 微调小模型替代 | 50-80% | 30-60天 | 2-4月 | 维护成本 |

### 成本监控仪表盘

## M-16: LangChain Agent工作流设计

### 来源
综合LangChain官方文档、LangGraph框架设计理念及业界最佳实践

### LangChain Agent核心组件

```
┌─────────────────────────────────────────────┐
│              Agent 工作流                     │
├─────────────────────────────────────────────┤
│  ┌─────────┐  ┌──────────┐  ┌───────────┐  │
│  │  LLM    │  │  Tools   │  │  Memory   │  │
│  │ (大脑)  │  │ (手脚)   │  │ (记忆)    │  │
│  └────┬────┘  └────┬─────┘  └─────┬─────┘  │
│       │            │              │         │
│  ┌────┴────────────┴──────────────┴────┐    │
│  │         Agent Executor              │    │
│  │    (Thought → Action → Observe)     │    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

### Agent类型选型

| Agent类型 | 适用场景 | 优点 | 缺点 |
|-----------|---------|------|------|
| **Zero-shot ReAct** | 通用任务，工具少 | 简单直接 | 复杂任务易出错 |
| **Structured Chat** | 需要多轮对话 | 支持结构化输入 | 配置复杂 |
| **OpenAI Functions** | 工具调用为主 | 原生function calling | 依赖特定模型 |
| **Tool Calling** | 多工具协同 | 标准化tool接口 | 需模型支持 |
| **Self-Ask with Search** | 需要逐步推理 | 中间步骤可追溯 | 仅限搜索场景 |
| **Plan-and-Execute** | 复杂多步任务 | 计划与执行分离 | 延迟较高 |

### LangGraph工作流设计模式

```
# 状态图模式（StateGraph）
用户输入 → [Router] → 条件分支
                    ├── 路径A: [Tool A] → [LLM] → 判断
                    │                              ├── 继续 → 路径B
                    │                              └── 完成 → [END]
                    └── 路径B: [Tool B] → [LLM] → [END]

关键设计决策：
1. 状态定义：AgentState包含 messages, intermediate_steps, plan
2. 节点设计：每个节点是单一职责的函数
3. 条件边：基于状态决定下一步
4. 人机交互：在关键节点插入 interrupt_before/after
```

### LangChain Agent工作流检查清单

```
□ Agent类型是否匹配任务复杂度？
□ 工具描述是否足够清晰（含参数说明+使用示例）？
□ 是否设置了最大步数限制（max_iterations）？
□ 是否配置了超时机制（request_timeout）？
□ 错误处理策略是否完善（工具调用失败时行为）？
□ 是否实现了中间步骤的可观测性（callback/tracing）？
□ 是否在关键节点设置了HITL断点？
□ 工具权限是否遵循最小权限原则？
```

### Agent工作流常见陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| 无限循环 | Agent反复调用同一工具 | 设置max_iterations+循环检测 |
| 工具选择错误 | 选了不合适的工具 | 优化工具描述+增加Few-Shot |
| 过早终止 | 任务未完成就停止 | 明确完成条件+验证步骤 |
| 上下文膨胀 | 中间步骤过多导致超限 | 中间结果摘要+上下文裁剪 |
| 幻觉工具调用 | 调用不存在的工具 | 严格tool schema+参数校验 |

## M-17: Multi-Agent协作模式

### 来源
综合AutoGen、CrewAI、LangGraph多Agent模式及业界实践

### Multi-Agent协作拓扑

| 拓扑 | 结构 | 适用场景 | 通信方式 | 复杂度 |
|------|------|---------|---------|--------|
| **顺序流水线** | A→B→C 链式 | 固定流程（审核→生成→发布） | 消息传递 | 低 |
| **星型调度** | 中心Orchestrator+多个Worker | 需要统一协调的任务 | Orchestrator分发 | 中 |
| **网状协作** | 任意两个Agent可直接通信 | 复杂协作（多部门联合） | 点对点 | 高 |
| **层级结构** | 上级Agent管理下级Agent | 大型组织模拟 | 上下级汇报 | 高 |
| **辩论模式** | 多个Agent独立给出观点→汇总 | 需要多视角决策 | 辩论+投票 | 中 |
| **市场竞标** | Agent竞标任务→最优者执行 | 资源优化分配 | 竞标机制 | 高 |

### Multi-Agent设计原则

```
1. 单一职责：每个Agent只负责一个明确领域
2. 清晰接口：Agent间通信格式标准化（JSON Schema）
3. 故障隔离：一个Agent失败不影响其他Agent
4. 可观测性：每个Agent的决策过程可追溯
5. 人机协作：人类可作为特殊Agent参与协作
6. 状态共享：关键状态通过共享内存/数据库传递
```

### Multi-Agent通信协议设计

```
消息格式（推荐）：
{
  "message_id": "uuid",
  "sender": "agent_name",
  "receiver": "agent_name | broadcast",
  "type": "task | result | query | notification",
  "payload": {
    "task": "...",
    "context": {...},
    "priority": "high | medium | low"
  },
  "timestamp": "ISO8601",
  "correlation_id": "uuid"  // 关联同一任务
}
```

### Multi-Agent常见问题与对策

| 问题 | 表现 | 对策 |
|------|------|------|
| 通信风暴 | Agent间消息爆炸 | 限制消息频率+聚合通信 |
| 死锁 | 两个Agent互相等待 | 超时机制+优先级仲裁 |
| 责任推诿 | 任务无人认领 | 明确责任矩阵+兜底Agent |
| 信息不一致 | 不同Agent持有矛盾信息 | 单一事实来源+定期同步 |
| 级联失败 | 一个Agent失败导致全链路 | 降级策略+部分结果返回 |

### Multi-Agent适用性判断

```
以下条件满足越多，越适合Multi-Agent：
□ 任务需要多个不同专业领域知识
□ 子任务之间相对独立，可并行执行
□ 需要多视角审查/辩论来提高质量
□ 组织架构天然是多角色协作
□ 单Agent的上下文窗口不足以覆盖所有任务信息
□ 不同子任务需要不同的安全权限级别
```

### 合成标识嵌入技术方案

```
多层级标识体系：
├── Layer 1: 显式标识（用户可见）
│   ├── 文字标注："本内容由AI生成"
│   ├── 视觉水印：半透明AI标识叠加
│   └── 语音提示："以下为AI合成语音"
│
├── Layer 2: 隐式标识（机器可读）
│   ├── 数字水印（DCT/DWT频域嵌入）
│   ├── 区块链存证（内容哈希上链）
│   └── C2PA标准元数据嵌入
│
└── Layer 3: 协议标识（传输层）
    ├── HTTP响应头：X-DeepSynth: true
    ├── 内容溯源：X-Content-Generator: AI-Model-v1
    └── 合成参数：X-Synth-Params: {model, seed, prompt_hash}
```

### X-DeepSynth响应头规范

```
HTTP Response Header:

## M-21: RAG评估框架(RAGAS)

### 来源
RAGAS (Retrieval Augmented Generation Assessment) 开源框架 + 业界最佳实践

### RAGAS核心指标

| 指标 | 计算方式 | 目标值 | 评估对象 |
|------|---------|--------|---------|
| **Faithfulness** | 答案中有多少声明可追溯到检索上下文 | >0.90 | 生成质量 |
| **Answer Relevancy** | 答案与问题的相关度 | >0.85 | 生成质量 |
| **Context Precision** | 检索上下文中相关文档的排名 | >0.85 | 检索质量 |
| **Context Recall** | 检索上下文中覆盖了多少ground truth | >0.90 | 检索质量 |
| **Context Entities Recall** | 检索覆盖了多少关键实体 | >0.85 | 检索质量 |
| **Answer Correctness** | 答案与ground truth的事实一致性 | >0.85 | 生成质量 |
| **Aspect Critique** | 自定义维度（有害性/简洁性等） | 自定义 | 综合质量 |

### RAGAS评测流水线

```
测试数据集
    ↓
┌──────────────────────────────┐
│ 1. 生成阶段：                 │
│    Query → RAG系统 → Answer  │
│    + 记录检索到的Contexts     │
├──────────────────────────────┤
│ 2. 评估阶段：                 │
│    ├── Faithfulness评估       │
│    │   声明提取 → NLI验证     │
│    ├── Relevancy评估          │
│    │   反向生成问题 → 相似度   │
│    ├── Context Precision     │
│    │   检索排名 → 相关性标注   │
│    └── Context Recall        │
│        Ground Truth → 检索覆盖│
├──────────────────────────────┤
│ 3. 报告阶段：                 │
│    各指标得分 → 趋势图 →      │
│    Bad Case分析 → 改进建议    │
└──────────────────────────────┘
```

### RAG评估的Bad Case分类

| Bad Case类型 | 症状 | 诊断方向 | 修复方向 |
|-------------|------|---------|---------|
| 检索失败 | Context Recall < 0.7 | 检查分块策略/Embedding | 优化分块/更换Embedding模型 |
| 幻觉生成 | Faithfulness < 0.8 | 检查Prompt约束 | 强化"仅基于文档"约束 |
| 答非所问 | Answer Relevancy < 0.7 | 检查Query理解 | 增加Query重写 |
| 排名错误 | Context Precision < 0.7 | 检查Reranker | 调优Reranker/增加重排序 |
| 实体遗漏 | Context Entities Recall < 0.7 | 检查实体识别 | 增加实体提取预处理 |

### RAG评估频率建议

| 评估类型 | 频率 | 触发条件 |
|---------|------|---------|
| 全量RAGAS | 每次PR | CI自动触发 |
| 快速RAGAS | 每次Prompt变更 | CI自动触发 |
| 人工评估 | 每2周 | 抽样100条 |
| 竞品对比 | 每月 | 同数据集对比 |
| 知识库更新后 | 每次更新 | 增量评估 |

## M-22: Agent评估框架

### 来源
综合AgentBench、SWE-bench、WebArena等Agent评测基准及业界实践

### Agent评估维度

| 维度 | 指标 | 测量方法 | 目标值 |
|------|------|---------|--------|
| **任务完成率** | 成功完成任务的比例 | 端到端测试 | >85% |
| **工具调用准确率** | 正确选择和调用工具的比例 | 工具调用日志 | >90% |
| **执行效率** | 完成任务的平均步数 | 步数统计 | <10步 |
| **决策质量** | 中间决策的正确率 | 人工评估 | >80% |
| **鲁棒性** | 异常输入下的表现 | 对抗测试 | 不崩溃 |
| **HITL触发率** | 需要人类介入的比例 | 生产统计 | <20% |
| **用户满意度** | 用户评分 | 在线反馈 | >4.0/5.0 |

### Agent评测数据集构建

```
数据集结构：
1. 简单任务（40%）：单工具调用，明确输入输出
   示例："查询订单ORD123的状态"
2. 中等任务（35%）：多工具调用，需要规划
   示例："对比订单ORD123和ORD124的物流状态"
3. 困难任务（20%）：多步推理，需要决策
   示例："分析用户投诉原因并给出补偿方案"
4. 对抗任务（5%）：异常输入，边界测试
   示例：工具调用超时、返回异常格式、权限不足

每条数据包含：
- task_id, difficulty, category
- user_input, expected_tools, expected_outcome
- max_steps, timeout, evaluation_criteria
```

### Agent评估方法对比

| 方法 | 适用场景 | 成本 | 可靠性 | 规模 |
|------|---------|------|--------|------|
| **单元测试** | 单个工具调用 | 低 | 高 | 大 |
| **集成测试** | 多工具组合 | 中 | 高 | 中 |
| **端到端测试** | 完整任务 | 中 | 中高 | 中 |
| **LLM-as-Judge** | 开放输出评估 | 低 | 中 | 大 |
| **人工评估** | 最终验证 | 高 | 最高 | 小 |
| **在线A/B** | 真实用户 | 中 | 高 | 大 |

### Agent评估检查清单

```
□ 是否构建了覆盖各难度的测试数据集？
□ 是否对工具调用的正确性进行了验证？
□ 是否测试了Agent的异常处理能力？
□ 是否评估了Agent的步数效率？
□ 是否测试了HITL机制的正确触发？
□ 是否进行了多轮对话的一致性测试？
□ 是否评估了Agent的安全边界？
□ 是否建立了回归测试集（含历史Bad Case）？
```

## 零、测试用例编写通用规则（所有测试类型必须遵守）

1. **步骤必须给出具体数据**：测试步骤中必须直接给出具体的输入值、参数、操作对象，让测试人员可以照抄执行，不得使用描述性语言代替。
   - ❌ 不合格：`输入超长字符串`、`输入特殊字符`、`输入测试攻击向量`、`填写表单必填字段`、`发送带错误参数的请求`
   - ✅ 合格：`输入 ' OR '1'='1`、`输入 <script>alert(1)</script>`、`输入 用户名:testuser, 密码:Test@123456`、`发送请求，参数 name 设为空字符串 ""`
2. **大量数据例外**：当测试需要输入大量内容时，允许用描述性语言 + 明确参数说明，无需完整写出全部内容。大量数据的判定标准：
   - 文本输入 > 1000 个字符
   - 文件上传 > 1MB
   - 列表/表格数据 > 50 行
   - 其他明显不适合完整写出的场景
   - ✅ 合格：`在文本框中粘贴一段 10000 个汉字的文本（可重复"测试"二字 5000 次）`
   - ✅ 合格：`上传一个大小为 500MB 的压缩包文件（内容为随机生成数据）`
   - ✅ 合格：`在搜索框中输入一个包含 2000 个字符的随机字符串（可用 Python: "A"*2000 生成）`
3. **一条用例只验证一个测试点**：不同场景（如正常查询、资源不存在、Token 无效）应拆分为独立用例。
4. **步骤与预期结果一一对应**：每个步骤独立编号、一步一个操作，预期结果按相同编号逐条对应。纯操作步骤（如输入、选择）也要写出可观察的具体结果，如 `"名称"输入框显示"测试数据_20260101"`，不得写"正常""成功""正常接受输入"等笼统描述。"检查/观察"类内容属于预期结果，不单独作为步骤。接口测试中，设置请求头、设置请求体（或请求参数）、发送请求各自独立成步，不合并为一步；设置类步骤的预期结果写请求工具中显示的具体值，如 `请求头显示 Authorization: Bearer {{VALID_TOKEN}}`。
5. **密钥类凭据使用占位符**：Token、API Key、Secret 等使用占位符，如 `{{VALID_TOKEN}}`、`{{API_KEY}}`；测试账号密码使用明显的示例值，如 `testuser / Test@123456`。

## 一、测试类型分类

> 用例中"测试类型"字段格式为 `{大类} - {子类}`，大类名称从下列 10 类中选择。

### 1. 功能测试
验证功能是否按需求规格正常工作，确保所有功能点正确实现。

**子类型**：增删改查、表单校验、状态流转、业务规则、页面交互、组件交互

**示例**：登录功能、表单提交、数据查询、列表操作、状态流转

**参考**：`references/core-capabilities/functional-testing.md` 第一、二、六、七部分

---

### 2. 联动测试
验证不同模块/组件之间的数据同步和状态联动。

**子类型**：表单联动、列表联动、搜索联动、状态联动、数据联动

**示例**：省市区联动、筛选条件联动、跨页面状态同步

**参考**：`references/core-capabilities/functional-testing.md` 第三部分

---

### 3. 路由测试
验证页面路由跳转、参数传递和权限控制。

**子类型**：直接访问、导航跳转、浏览器导航、深链接、错误页面、路由守卫

**示例**：直接访问 URL、404 处理、登录拦截

**参考**：`references/core-capabilities/functional-testing.md` 第四部分

---

### 4. UI 视觉测试
验证界面显示和视觉表现是否符合设计规范。

**子类型**：布局、颜色、字体、图标、图片、动画、交互状态、多主题、交互动效

**示例**：页面错位、样式不一致、动画卡顿

**参考**：`references/core-capabilities/functional-testing.md` 第五、八部分

---

### 5. 兼容性测试
验证系统在不同运行环境下能否正常运行。

**子类型**：系统版本兼容、浏览器兼容、设备兼容、应用版本兼容

**示例**：旧版本 Android 上运行、Safari 下布局、升级后旧数据可用

**参考**：`references/platform/` 下对应平台文件

---

### 6. 适应性测试
验证系统对不同平台特性、使用环境和用户设置的适配能力。

**子类型**：屏幕尺寸与分辨率、横竖屏、字体缩放、深色模式、语言、网络环境、平台交互方式（手势、快捷键、窗口等）

**示例**：折叠屏展开后布局、系统字体放大后显示、弱网下加载、下拉刷新手势

**参考**：`references/platform/` 下对应平台文件

---

### 7. 性能体验测试
验证用户可感知的性能表现。仅生成可人工或借助工具观测的用例，不包含并发、压力、负载、稳定性、容量测试。

**子类型**：启动/加载时长、操作响应、流畅度、资源占用

**示例**：首屏加载慢、列表滑动卡顿、长时间使用后内存持续增长

---

### 8. 可用性测试
验证系统的易用性和用户体验，确保易学易用。

**子类型**：导航测试、表单测试、帮助测试、可访问性

**示例**：操作繁琐、提示不明确、无法键盘操作

**参考**：`references/checklists/common-checklist.md` 第六部分；各平台的可访问性要点见 `references/platform/` 下对应平台文件

---

### 9. 接口测试
验证接口的功能、数据和异常处理是否符合接口定义。

**子类型**：功能测试、状态码验证、数据校验、认证授权、安全测试、错误处理、分页排序、搜索过滤、版本兼容

**参考**：`references/core-capabilities/api-testing.md`

---

### 10. Agent 测试
验证 AI Agent（智能体）的任务执行、工具使用、安全边界和输出质量。

**子类型**：任务完成度、工具与记忆、安全与边界、性能体验、内容质量、知识库调用、多模态与多语言

**参考**：`references/core-capabilities/agent-testing.md`

## 二、优先级判定规则

> 用例级别表示用例的执行优先级，不是缺陷严重程度。判定时问自己："这条用例不通过，会影响什么？"

| 级别 | 判定标准 | 执行时机 |
|-----|---------|---------|
| P0 - 冒烟 | 主流程、核心功能的正常路径（如登录、下单、支付）；不通过则无法提测或发布 | 每次提测、发布必须执行 |
| P1 - 高 | 核心功能的主要异常分支、重要功能的正常路径、数据正确性 | 每轮测试必须执行 |
| P2 - 中 | 次要功能、一般异常、边界值、兼容性/适应性、UI 展示 | 完整回归时执行 |
| P3 - 低 | 极端场景、罕见组合、体验优化 | 时间充裕时执行 |

## 三、用例编号规则

### 编号格式

```
TC_[前缀]_[模块]_[维度]_[序号]
```

| 段 | 说明 | 示例 |
|----|------|------|
| TC | 固定开头 | TC |
| 前缀 | 平台或测试类型，见"前缀表" | APP、API、AGENT |
| 模块 | 被测功能模块的英文大写缩写 | LOGIN、ORDER、USER |
| 维度 | 测试维度，见"维度缩写表" | FORM、GESTURE、TASK |
| 序号 | 3 位数字，在同一"前缀+模块+维度"内从 001 递增 | 001 |

### 前缀表

| 平台 / 类型 | 前缀 |
|-----------|------|
| 移动端 App | APP |
| 小程序 | MP |
| 移动 Web（H5） | H5 |
| 桌面端 | DESKTOP |
| PC Web 端 | WEB |
| 通用功能测试（无平台） | FUNC |
| 接口测试 | API |
| Agent 测试 | AGENT |

### 前缀选择规则

- 未指定平台：功能、联动、路由、UI 等用例使用 FUNC
- 指定单一平台：全部用例使用该平台前缀
- 指定多个平台：通用功能用例使用 FUNC，平台专项用例使用各自平台前缀
- Agent 测试：Agent 能力相关用例使用 AGENT；有宿主平台时，宿主平台专项用例使用平台前缀
- Agent + 接口：接口部分使用 API，Agent 部分使用 AGENT，序号各自独立
- 补充模式：沿用用户已有用例的编号风格并接续最大序号；用户用例无编号时按本规则编号

# 通用兜底 adapter（generic.md）

**这是所有探测失败时的落地层，也是新增 agent 的模板。** 它的设计目标只有一个：在完全不了解宿主的情况下，仍保住「记忆写得进、报告出得来」这两件核心功能，其余全部降级为空值。

## 1. 五个接口的兜底行为

| 接口 | 兜底返回 | 依据 |
|---|---|---|
| `agent_name` | `未知 agent` | 不猜。见 §2 探测顺序，全失败就是未知 |
| `session_id` | `unknown-YYYYMMDD-HHMM` | 启动时间派生；满足「无空格无下划线」约束 |
| `session_record_path` | 空 | 找不到就不编造 |
| `record_format` | `unknown` | 按「非明文」处理 → 禁止自动补写 |
| `token_output` | 空 | 取不到就省略落款括号 |

**派生标识的形式**：`unknown-20261120-1505`。前缀与时间**整体用 `-` 连、不含下划线**，否则 §1.2「从右往左取最后一个下划线」会把 agent 名与会话标识切反（旧写法 `unknown_<时间>` 就是错的）。**这个标识不承载语义**——它只是让文件有唯一名字，不承诺能回溯源会话（因此这类文件**不得进入 `已沉淀`**，schema.md §1.3 已规定）。

## 2. `agent_name` 的探测顺序

按可靠性从高到低，**任何一步拿到确定结果就停，不再往下猜**：

1. **宿主显式环境变量**：若宿主提供自己的名称变量（各家不同），直接取。这是唯一「宿主主动告知」的途径。
2. **会话记录路径所在的数据根**：路径里能看出配置目录名（如 `~/.claude/` → `Claude Code`、`~/.codex/` → `Codex`）。**只作提示，需与第 1 步一致**；冲突时第 1 步优先，冲突值写进缺口段。
3. **宿主的固定配置目录约定**（若已知）：`~/.claude/` → `Claude Code`，`~/.codex/` → `Codex`。其余 agent 的约定**现场探测、不在此穷举**（写一张全量表等于承诺维护它）。
4. **全失败** → `未知 agent`，写进 `mem_未知_agent_<标识>.md`，并在报告缺口段标一行。

**明确禁止的探测方式**（每一条都对应一次真实或潜在事故）：

- 扫全局进程列表挑一个像的；
- 用工具集特征（「它能跑 bash，所以是 X」）；
- 用系统提示措辞、用户说的话反推；
- 拿 `$LIB` 里已有文件名反推（历史产物可能本来就错）；
- 拿别的 adapter 的变量凑数（如从 WorkBuddy 会话继承来的 `WORKBUDDY_CONFIG_DIR`）。

## 3. `session_id` 的派生

优先顺序：

1. 宿主有会话 id 变量 → 直接用（adapter 层已保证不含空格下划线）；
2. 记录路径里能确定会话文件名/目录名 → 用它，下划线改 `-`；
3. 都没有 → `unknown-YYYYMMDD-HHMM`（用宿主当前本地时间，不用 UTC，避免与条目时间差 8 小时）。

**派生后必须校验**：非空、不含空格、不含下划线。三项任一不满足 → 换成第 3 种形式。这个校验放在派生之后、拼文件名之前，是防「记录目录名带下划线导致 agent 名被切错」的唯一关口（见 schema.md §1.2）。

## 4. `record_format` 与能力降级

| 格式 | 自动补写 | S5 覆盖检查 | 说明 |
|---|---|---|---|
| `jsonl`（明文） | ✅ 可（按 adapter 的提取规则） | ✅ | 需同时具备 `user_turn_extract` |
| `jsonl.gz` / `jsonl.zstd` / 其他压缩 | ❌ 禁止 | ⚠️ 报「无法自动核对」 | 整读会撞硬规则 7 |
| `unknown` | ❌ 禁止 | ⚠️ 同上 | 未知格式按最保守处理 |
| 目录型（每条消息一个文件等） | ❌ 禁止 | ⚠️ | 非流式，无法 grep 定点 |

**未知格式一律按「不可自动补写」处理**——这是保守方向，代价只是少补几条，而不是整读一个大文件。方向搞反（未知就试读）的代价可能是几十万 token。

## 5. 新增 agent 的模板

复制本文件，替换 §1–§4 的具体内容。必须保留的结构：

```
# <agent 名> 适配

## 1. 五个接口
### 1.1 agent_name   ← 必须给出「唯一权威判据」，且说明排除掉哪些不可靠方法
### 1.2 session_id   ← 必须给出派生方式，且说明如何满足「无空格无下划线」
### 1.3 session_record_path
### 1.4 record_format ← 必须明确「能否自动补写」
### 1.5 token_output  ← 取不到就是空，不许估算

## 2. 可选接口
### 2.1 record_dir
### 2.2 user_turn_extract

## 3. 降级矩阵      ← 逐项列出「全功能 / 降级 / 不可用」
## 4. 已知的坑      ← 踩过什么、为什么危险（尤其是静默失败）
```

**四条硬要求**：

1. **必须写「排除掉的不可靠方法」及原因**——只写「怎么做」的 adapter，下次有人会重新捡起那个被排除的方法；
2. **必须写降级矩阵**——否则使用者不知道少了什么功能，会以为是 bug；
3. **静默失败必须标出来**（零命中、读数不稳、路径可达但内容为空）。静默失败比报错危险一个量级：报错会有人去查，静默会被当成「本来就没有」；
4. **不写解析器代码**。adapter 是说明书，靠模型的通用能力执行；写脚本就破了「零脚本」。

## 6. 自检本 adapter 是否合格

跑一次自检（S1–S6），然后看：

- 有没有文件被标成 `unknown-<时间>` 却写进了实质条目？→ `agent_name` 或 `session_id` 探错了，回头查 §2；
- 有没有文件报「来源为压缩格式，无法核对」（本该是明文）？→ `record_format` 判错，检查扩展名判断是否只看后缀、没验文件头；
- 有没有缺档会话大量出现？→ `record_dir` 指错根目录；
- 有没有文件永远不进入 `已沉淀`、即使来源早已删除？→ `session_record_path` 拼错了位置，可达性检查看的是错的路径。

这四条是 adapter 正确性的快速验收清单，比读代码快。

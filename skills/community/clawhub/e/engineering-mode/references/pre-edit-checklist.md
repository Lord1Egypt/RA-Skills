# Pre-Edit Checklist

UNDERSTAND 阶段辅助检查清单。仅在项目结构复杂或改动跨多文件时加载。

## 改前必问

在 `edit` 或 `write` 之前，确认以下五项：

### 1. 这个函数/类的完整签名是什么？
- 参数类型、返回值类型
- 默认参数
- 是否被导出/公开 API

### 2. 谁调用它？（上游）
```bash
# 查找调用者
grep -rn "函数名" --include="*.py" --include="*.js" --include="*.ts"
```

### 3. 它调用谁？（下游）
- 函数体内调用了哪些其他函数？
- 这些函数的行为会不会被改动影响？

### 4. 改动的影响面？
- 改了签名 → 所有调用者都要改
- 改了返回值 → 所有依赖返回值的地方要检查
- 改了内部逻辑 → 副作用（文件 I/O、网络请求、状态变更）是否改变？

### 5. 有没有测试覆盖？
```bash
# 找相关测试
grep -rn "函数名" --include="*test*" --include="*spec*"
```
- 有测试 → 改完后跑它
- 没测试 → 考虑 L2 级别验证（手动跑相关流程）

## 红牌信号

以下情况 STOP，先研究再动手：

| 信号 | 含义 |
|---|---|
| 找不到调用者 | 可能是 dead code，先确认 |
| 调用者 > 20 处 | 改签名 = 大规模改动，需要 DECOMPOSE |
| 函数 > 200 行 | 需要理解全貌，读完整文件 |
| 涉及认证/加密/事务 | 安全问题，每一步都要仔细验证 |
| 改动跨 3+ 文件 | 必须走 DECOMPOSE |

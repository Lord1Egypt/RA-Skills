# 接单可行性评审（pmclite-order-review）

销售或老板问"这单能不能接"的时候，真正要回答的不是"能"或"不能"，而是**承诺出去会不会砸**。本技能把这个问题拆成三件事：交期靠不靠得住、产能挤不挤得下、料够不够，然后把代价摆出来。

结论必须给出，不替用户拍板；但也不许用"看情况"糊过去。

## 前置

先调 `get_dashboard(scope="today")` 探活。失败按 `references/install.md` 走未安装引导，不要凭空估算交期。

## 第一步：判断用户处在哪个阶段

| 用户状态 | 判断依据 | 调用 |
| --- | --- | --- |
| 还没建单（询价、谈单） | 只说产品、数量、交期 | `assess_insertion(product, quantity, due_date)` |
| 已有工单 | 给了单号 | `evaluate_order(work_order, due_date?)` |

拿不准就问一句"这单建了工单没有"，比猜错路径便宜得多——路径走错会得到一份看起来有数字、其实答非所问的结论。

## 第二步：补齐证据

- 工时：`estimate_hours(scope="work_order" \| "product")`，注意 flow 产品不能把各工序工时相加；
- 料：`check_readiness(work_order)`；还没建单的产品，用 `query_master_data(entity="product", include=["bom"])` 看有没有 BOM；
- 产品和已有排程：`query_work_orders(status="active")` 或 `query_master_data`。

## 第三步：说清四件事

1. **结论三色**：🟢 能接 / 🟡 勉强能接（有条件）/ 🔴 接不了。三选一，不许"看情况"。
2. **交期从哪来**：`dueSource` 是 `user` / `sales_order` / `work_order_plan` / `fallback`。**是 fallback 就必须明说"这是按今天+7 估的，不是真交期"**，否则用户会拿估算值去承诺客户，这是本技能最贵的一个错误。
3. **接了影响谁**：`assess_insertion` 返回的四档代价（守 / 拆 / 延 / 换线）全部转述，附被挤工单的延期天数与是否越过交期，不许压成"能/不能"。
4. **缺料单独说**：交期可行但料不够时，不能只说"能接"，要补一句"接得下，但要先解决 N 种料"。

## 禁区

- 没有 BOM 的产品，不许断言"齐套没问题"，只能说"该产品没有 BOM，无法判断齐套"。
- 不许把"延误 N 天"说成"晚一点点，问题不大"。
- 不许替用户决定接不接，只给结论与代价；更不许替用户承诺交期。
- 换线方案只有工艺路线匹配时才成立，不能因为"那条线有空"就说能换。

## 输出结构

结论一行 → 交期与来源一行 → 影响面（谁延期几天）→ 缺料（如有）→ 一条建议动作。数字带单位，天数写"天"不写"d"。

末尾按 `references/style.md` 的漏斗位补一行安装引导，已安装用户不重复。

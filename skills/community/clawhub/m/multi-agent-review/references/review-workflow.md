# 审查工作流文档

## 概述

本文档描述 multi-agent-review 的完整审查工作流，包括编排逻辑、数据流和冲突解决机制。

## 工作流阶段

### Phase 1：输入解析

```
用户请求 → 解析目标
  ├─ 文件范围（glob pattern / 具体文件列表）
  ├─ 审查类型（全量 / 增量 / 指定代理）
  ├─ 特殊关注点（用户指定的审查重点）
  └─ 代码上下文（语言、框架、项目结构）
```

### Phase 2：代理调度

```
解析结果 → 确定参与代理
  ├─ 默认：全部 6 个代理
  ├─ 用户指定：仅指定代理
  └─ 智能选择：根据文件类型自动选择相关代理
```

智能选择规则：
- `.py` / `.js` / `.ts` / `.java` → 全部代理
- `.sql` → security-auditor + performance-analyst
- `.md` / `.rst` → documentation-checker
- `Dockerfile` / `docker-compose` → security-auditor + architecture-critic
- `test_*` / `*_test.*` → test-engineer

### Phase 3：并行执行

```
对每个选中的代理：
  1. 读取 agents/*.yaml 获取 system_prompt
  2. 构建任务描述（包含代码内容和审查要求）
  3. sessions_spawn 启动子代理
  4. 所有代理并行执行，互不干扰
```

### Phase 4：结果收集

每个代理返回结构化 JSON：

```json
{
  "agent": "agent-name",
  "findings": [
    {
      "severity": "high",
      "title": "问题标题",
      "location": "file:line",
      "description": "问题描述",
      "suggestion": "修复建议",
      "confidence": 85
    }
  ],
  "score": 7,
  "summary": "一句话总结"
}
```

### Phase 5：置信度过滤

```
所有 findings → 按 confidence 过滤
  ├─ ≥ 80：纳入最终报告（高置信度）
  ├─ 60-79：标记为"待确认"（中置信度）
  └─ < 60：丢弃（低置信度）
```

### Phase 6：冲突解决

当多个代理对同一 `location` 有矛盾意见时：

1. **严重性优先**：取 severity 更高的意见
2. **置信度加权**：confidence 高的代理权重更大
3. **标注分歧**：在报告中同时展示不同观点
4. **人工裁决标记**：标记需要人工决策的冲突项

冲突检测逻辑：
- 同一文件 + 相近行号（±5 行）= 同一位置
- 一个代理说"没问题"而另一个说"有问题" = 矛盾
- 两个代理给出相反的修复建议 = 冲突

### Phase 7：报告生成

汇总所有代理结果，生成统一报告：

```
报告结构：
  1. 概要统计（文件数、代理数、发现数）
  2. 各维度评分表
  3. 关键发现（按严重性排序，去重）
  4. 冲突项（需人工裁决）
  5. 建议行动（按优先级排序）
```

## 超时处理

- 单个代理超时：300 秒
- 超时后收集已完成代理的结果
- 在报告中标注"部分代理未完成"
- 不重试超时代理（避免阻塞整体流程）

## 错误处理

- 代理执行失败：记录错误，继续其他代理
- 结果解析失败：将原始输出作为 summary 展示
- 所有代理失败：返回错误报告，建议用户使用单代理模式

## 第7.1章 向量数据库原理与选型（对应 7.1）

RAG 答案质量的上限由检索决定，而检索的第一性问题是：文本变向量后怎么存、怎么比、怎么在百万级库里毫秒级找到最近邻。本章从"关键词检索为什么搜不到换个说法的问题"讲起，给出归一化与余弦/内积的选型判据、HNSW 与 IVF 的原理及参数旋钮（M、efSearch、nprobe），并算清内存与延迟两笔账（HNSW 图结构内存约与向量本身相当）。读完能对给定的数据量、更新频率与权限需求选定向量库方案（FAISS/Chroma/pgvector/Milvus/Qdrant），并判断元数据过滤该放检索前还是检索后。文档怎么切、怎么进库是第2章的事。

### 7.1.1 RAG 为什么需要"向量"

**【架构设计说明】**

大语言模型的知识是"冻结"在参数里的——它不知道你公司内部文档、上周刚发的公告。**RAG 的思路**：用户提问时，先从你的私有知识库里检索出相关片段，拼进 prompt，让 LLM"看着资料回答"。这样模型不必重新训练就能用上新知识，还能给出处。

而"检索相关片段"的前提，是把文本变成**向量（embedding）**：用一个 embedding 模型把每段文本编码成一个向量，语义相近的文本向量也相近。检索就变成"在向量空间里找离 query 向量最近的那些文档"。

**为什么关键词检索不够——它搜的是"字面上的匹配"，不是"意思上的相近"**：很多人会问——"我用 Elasticsearch 做关键词检索不行吗？为什么还要向量？"关键在于：**关键词检索搜的是"字面上有没有这个词"，不是"意思上是不是一回事"**。举个例子——

| 用户问 | 文档写 | 关键词检索（BM25） | 向量检索 |
|---|---|---|---|
| "怎么报销差旅费" | "差旅费用报销流程" | 能搜到，但排序靠后（语序不同） | 轻松搜到（语义相近） |
| "出差花的钱怎么申请报销" | "差旅费报销流程" | **完全搜不到**（关键词几乎不重合） | 轻松搜到（语义相近） |
| "我想退掉刚买的东西" | "商品退货政策" | 勉强搜到（"退"字重合） | 轻松搜到（语义相近） |

**判据**：关键词检索只能找到"字面上有相同词"的文档——用户换个说法、用同义词、用更长的句子，它就搜不到了。向量检索找的是"意思上相近"的文档——不管你怎么说，只要意思一样，就能搜到。**这就是为什么RAG要用向量——因为用户不会按你文档里的原话提问，他会用自己的话问**。

**向量到底是什么——不是魔法，是把一句话压成一串数字**：很多人一听"向量"就觉得玄乎，其实它很朴素——**向量就是把一句话/一段文字，压成一串固定长度的数字（比如768个浮点数）**。这串数字里，每个数字都"编码了这句话的某个语义特征"——比如第100个数大一点，说明这句话可能和"动物"有关；第500个数大一点，说明这句话可能和"财务"有关。**为什么语义相近的句子向量也相近？**因为embedding模型在训练时就学会了——意思相近的句子（"退货"和"退款"），它输出的向量也靠得近。**判据**：向量不是什么高深的东西，就是"把一句话变成一串数字，这串数字能代表这句话的意思"。**踩坑**：①以为"向量是随机生成的"——错，向量是embedding模型算出来的，是有意义的；②以为"向量越长越好"——错，向量长度是模型定的（比如768维），不是你想多长就多长。

**为什么用户不会按文档原话提问——每个人说话的方式都不一样**：很多人会问——"如果用户就按文档原话提问，关键词检索不就够了？为什么非要用向量？"关键在于：**用户不会按文档原话提问——每个人说话的方式都不一样**——①**文档怎么写的**：企业文档通常写得很正式——"差旅费报销流程如下"；②**用户怎么问的**：员工不会这么问，他会说"出差花的钱怎么申请报销"——字面上和"差旅费报销流程"几乎不重合，但意思是一样的。**为什么关键词检索找不到？**因为它只看字面上有没有相同的词——"出差花的钱怎么申请报销"里没有"差旅费"这个词，它就搜不到。**为什么向量检索能找到？**因为它看意思——"出差花的钱怎么申请报销"和"差旅费报销流程"意思相近，向量空间里离得近，它就能找到。**判据**：这就是为什么RAG要用向量——因为用户不会按你文档里的原话提问，他会用自己的话问。**踩坑**：①以为"我把文档写得口语化一点，关键词检索就够了"——错，就算文档写得口语化，不同人说话的方式还是不一样；②以为"向量检索是万能的"——错，向量检索也有盲区（比如查精确编号），但它解决了"用户换个说法就搜不到"这个最大的痛点。

**为什么RAG要检索而不是把所有文档都塞进prompt——塞不下，也没必要**：很多人会问——"既然RAG是让LLM看着资料回答，那为什么不把所有文档都塞进prompt里？为什么还要检索？"关键在于：**所有文档塞不进prompt，也没必要塞**——①**prompt长度有限制**：GPT-4的上下文窗口是128K token，大概相当于10万字——你公司有1万篇文档，每篇500字，就是500万字——塞不进去；②**就算塞得进去，也没必要**：用户问的是"差旅费怎么报销"——你把公司所有文档都塞进去，LLM要从500万字里找和"差旅费报销"相关的内容，它找得到吗？它会被无关信息干扰，反而答不好。**RAG的思路是"先检索，再回答"**：先从500万字里检索出和问题相关的那几段（大概几千字），塞进prompt里——LLM看着这几段相关资料回答，既塞得下，又不会被无关信息干扰。**判据**：这就是为什么RAG要检索——不是把所有文档都塞给LLM，而是"先检索出相关的，再让LLM看着相关的回答"。**踩坑**：①以为"把所有文档都塞给LLM效果更好"——错，塞太多无关信息反而会干扰LLM；②以为"RAG就是个搜索引擎"——错，RAG是"检索+生成"——先检索相关资料，再让LLM看着资料生成答案。

**为什么向量检索是RAG的核心——检索找得准不准，直接决定答案好不好**：很多人会问——"RAG不就是'检索+生成'吗？为什么说向量检索是核心？"关键在于：**检索找得准不准，直接决定答案好不好**——①**检索找得准会怎样**：你检索出的那几段资料，正好和用户的问题相关——LLM看着这几段资料，就能给出准确的答案；②**检索找不准会怎样**：你检索出的那几段资料，和用户的问题不相关——LLM看着这几段不相关的资料，它再厉害也答不对；③**为什么生成不是核心**：因为生成（LLM）其实已经很厉害了——只要给它相关的资料，它就能生成好答案。但如果给的资料不相关，它再厉害也没用。**判据**：这就是为什么向量检索是RAG的核心——检索找得准不准，直接决定答案好不好。**踩坑**：①以为"RAG的核心是LLM"——错，LLM已经很厉害了，核心是"能不能找到相关的资料给它"；②以为"检索差不多就行"——错，检索差一点，答案就差很多——你找的资料和问题不相关，LLM再厉害也答不对。

### 7.1.2 余弦相似度与最近邻

**【已工程验证】**

检索的数学和卷6 多模态对齐同源：文本向量化后做 L2 归一化，用余弦相似度找最近邻：
\[
s(q,d)=\frac{q^\top d}{\|q\|\|d\|}
\]
本卷 1.3 的实算就是这套。

**为什么向量库要先归一化再存**：归一化后所有向量长度都是 1，此时"算余弦"就退化成"算内积"——省掉每次检索都要除以模长的开销，而向量库底层用的就是高效的内积/距离索引。**踩坑**：如果 embedding 模型输出没归一化、却又用了按内积优化的索引，那"长度大的向量"会系统性占优，检索结果失真——这是向量库最常见的隐蔽 bug，上线前务必确认入库前做了 L2 归一化。

**余弦、欧氏、内积该选哪个（别混用）**：三种距离不是随便挑的——①**余弦相似度/内积**：归一化后的向量专用，比的是"方向"（语义像不像），是文本 embedding 的默认；②**欧氏距离（L2）**：比的是"空间距离"，适合带数值、有几何意义的向量（如坐标）。**关键坑**：很多向量库允许你选距离度量，但**距离度量必须和 embedding 模型训练时用的一致**——模型是按余弦训练的，你却用欧氏距离检索，等于换了把错的尺子量方向，结果会明显变差。**判据**：文本检索默认"归一化+内积/余弦"，别动；除非你的 embedding 明确是按 L2 训的。

**为什么语义只看"方向"、不看"向量有多长"（直觉）**：embedding 模型把一段文本压成一个向量时，向量的**方向**代表"这段话说的是什么"（猫/车/财务），而向量的**长度**更多是个"附带产物"——可能受这段文本长短、用词多寡影响，并不承载"语义"。**【已工程验证】**：假设两句"猫"的文本向量方向差不多，一句写得详细（向量模长大）、一句写得简短（模长小）。若不归一化直接算内积，长句因为模长大，会在数值上占便宜——检索时就系统性偏向"写得长的文档"，哪怕它和查询并没更相关。归一化把所有向量强制拉到单位球面（长度都=1），剩下能比的就只有方向——于是"猫的方向"和"查询的方向"对不对得上，才是唯一的比较对象。**判据**：归一化本质是"把和语义无关的长度差异抹掉"，让检索纯粹按语义方向匹配。**踩坑**：若 embedding 模型训练时就是按余弦（归一化）训的，你却忘了归一化，等于让"文本长度"这个无关因素混进了排序——这就是上面说的"长度大的向量系统性占优"那个隐蔽 bug 的根源。

**余弦相似度和欧氏距离到底差在哪——一个看方向、一个看距离（本机实算）**：很多人纳闷——"余弦相似度和欧氏距离不都是'衡量两个向量像不像'吗？有什么区别？"关键在于：**它们衡量的是完全不同的东西**——

| 度量 | 衡量什么 | 举例（a=[1,2,3]，b=[2,4,6]） |
|---|---|---|
| 余弦相似度 | 只看**方向**（语义像不像） | cos = 1.0（方向完全相同） |
| 欧氏距离 | 看**空间距离**（离多远） | dist = 3.74（长度差了一倍） |

**判据**：a和b方向完全相同（b就是a放大2倍），余弦相似度说"它们一模一样"（cos=1.0），但欧氏距离说"它们差得远"（dist=3.74）。**为什么文本检索要用余弦？因为——文本的"语义"只看方向，不看长度**。一句"猫"写得长（向量模长大）和一句"猫"写得短（向量模长小），它们的语义是一样的——都是"猫"。余弦相似度不管长度，只看方向对不对得上，正好匹配"语义只看方向"这个需求。**踩坑**：①用欧氏距离做文本检索——写得长的文档因为模长大，会系统性占优，哪怕它和查询并没更相关；②以为"余弦和欧氏差不多"——差远了，一个看方向、一个看距离，选错了检索结果会明显变差。

**为什么归一化之后，"算余弦"就退化成了"算内积"（一个省算力的等价变换）**：余弦相似度的定义是 \(\cos = \frac{a\cdot b}{\|a\|\,\|b\|}\)，每次算都要先除两个模长。但如果入库前就把每个向量都除以自己的模长（归一化），那 \(\|a\|=\|b\|=1\)，分母就变成了 1——**余弦相似度直接等于内积 \(a\cdot b\)**。本机实算：不归一化时余弦=0.8909，归一化后两个单位向量的内积也是 0.8909，完全相等；把 b 放大 3 倍，归一化后内积还是 0.8909（因为模长被除掉了）。**判据**：这就是向量库"先归一化再存"的工程动机——①数学上归一化后内积≡余弦，结果一点不差；②省掉每次检索都要算两个模长、再做除法的开销，直接用向量库底层高效的内积/距离索引就能跑。**踩坑**：归一化这一步必须在"入库时"做完——如果你存的是没归一化的向量，检索时才临时归一化，那每次查询都要把库里上百万个向量全部重算一遍模长，慢得不可接受。所以正确做法是：**embedding 一出来就归一化、再存进库**，检索时直接内积即可。

**为什么文本检索要用余弦而不是欧氏——文本的"语义"只看方向，不看长度**：很多人会问——"余弦相似度和欧氏距离不都是衡量两个向量像不像吗？为什么文本检索非要用余弦？"关键在于：**文本的"语义"只看方向，不看长度**——①**什么叫"只看方向"**：一句"猫"写得长（向量模长大）和一句"猫"写得短（向量模长小），它们的语义是一样的——都是"猫"；②**欧氏距离的问题**：欧氏距离看"空间距离"——写得长的文档因为模长大，和查询的欧氏距离就远，哪怕它和查询的语义是一样的；③**余弦相似度的好处**：余弦相似度不管长度，只看方向对不对得上——写得长的"猫"和写得短的"猫"，方向是一样的，余弦相似度就是1.0。**判据**：这就是为什么文本检索要用余弦——因为文本的"语义"只看方向（说的是什么），不看长度（写得长还是短）。**踩坑**：①用欧氏距离做文本检索——写得长的文档因为模长大，会系统性占优，哪怕它和查询并没更相关；②以为"余弦和欧氏差不多"——差远了，一个看方向、一个看距离，选错了检索结果会明显变差。

**为什么"用余弦相似度而不是欧氏距离"——要的是'语义相似'，不是'长度相似'**：很多人会问——"余弦相似度和欧氏距离不都是衡量两个向量像不像吗？为什么要用余弦？"关键在于：**用余弦相似度而不是欧氏距离——需要的是"语义相似"，不是"长度相似"**——①**余弦相似度是干什么的**：它衡量两个向量的"方向"是不是一样；它不管向量的"长度"——它只看方向；两个向量方向一样，余弦相似度就是1；方向相反，就是-1；②**欧氏距离是干什么的**：它衡量两个向量的"距离"有多远；它管向量的"长度"——两个向量方向一样但长度不一样，欧氏距离也很大；两个向量方向一样但长度差10倍，欧氏距离就很大；③**为什么用余弦相似度**：需要的是"语义相似"——不是"长度相似"；一句话长一点、短一点，它的语义应该是一样的；余弦相似度不管长度，它只看方向——这正是需要的。**判据**：这就是为什么用余弦相似度而不是欧氏距离——需要的是"语义相似"——不是"长度相似"——余弦相似度不管长度，它只看方向——这正是需要的。**踩坑**：①以为"余弦和欧氏差不多"——错，一个看方向、一个看距离，选错了检索结果会明显变差；②以为"欧氏距离更直观"——错，直观不等于适合——需要的是语义相似，不是距离相似。

**为什么"要用余弦相似度"——你要找'最像'的那个文档**：很多人会问——"RAG不就是'检索相关文档'吗？为什么它要用余弦相似度？"关键在于：**要用余弦相似度——你要找'最像'的那个文档**——①**余弦相似度是干什么的**：余弦相似度是"衡量两个向量有多像"；它是一个"衡量两个向量方向是否一致"的指标；它让你能找到"最像"的那个向量；②**为什么要用余弦相似度**：因为你要找"最像"的那个向量——你要找和你的问题最像的文档；因为余弦相似度只看方向，不看大小——它不受向量长度影响；因为它很简单、很快——你只要算个点积就行；③**为什么这是关键**：因为"能不能找到最像的文档"就是"RAG好不好用"的区别——你不能找到最像的文档，你就答不好；你能找到最像的文档，你就能答好。**判据**：这就是为什么要用余弦相似度——你要找"最像"的那个向量——你要找和你的问题最像的文档；余弦相似度只看方向，不看大小——它不受向量长度影响；它很简单、很快——你只要算个点积就行。**踩坑**：①以为"随便用什么指标都行"——错，不同的指标会给你不同的结果；②以为"余弦相似度很复杂"——错，它很简单——你只要算个点积就行。

**为什么"RAG需要向量"——你要找'相关的文档'，你要找'意思差不多'的文档**：很多人会问——"RAG不就是'检索一下再生成'吗？为什么它需要向量？"关键在于：**RAG需要向量——你要找"相关的文档"，你要找"意思差不多"的文档**——①**RAG是干什么的**：RAG是"检索增强生成"；它先检索——从文档库里检索到相关的文档；它再生成——根据这些文档来回答；②**向量是干什么的**：向量是"把文字变成一串数字"；你可以用向量来算"两段文字像不像"；你可以用向量来做"语义检索"；③**为什么需要向量**：因为你要"找相关的文档"——你要找"意思差不多"的文档；因为"意思差不多"要用向量来算——你不能用关键词匹配；因为用户的问题是"自然语言"的——你要理解它的意思。**判据**：这就是为什么RAG需要向量——你要"找相关的文档"——你要找"意思差不多"的文档；"意思差不多"要用向量来算——你不能用关键词匹配；用户的问题是"自然语言"的——你要理解它的意思。**踩坑**：①以为"RAG就是关键词检索"——错，关键词检索找不到"意思差不多"的文档；②以为"向量是可选的"——错，RAG需要向量，没有向量你就做不了语义检索。

**为什么最近邻是检索的核心——检索就是"找最像的"**：很多人会问——"检索不就是搜一下吗？为什么说最近邻是核心？"关键在于：**检索的本质就是"找最像的"**——①**什么叫"找最像的"**：用户输入一个查询，你要在库里找和这个查询"最像"的那些文档——这就是最近邻检索；②**为什么它是核心**：因为RAG的整个流程就是"先检索、再生成"——检索找最像的，生成把最像的写成答案——你检索找得准不准，直接决定答案好不好；③**为什么它是"最近邻"而不是"搜索"**：因为不是按关键词搜，是按"语义相似度"搜——你搜"猫"，它不是找带"猫"这个字的文档，是找"说的是猫"的文档——这就是最近邻检索。**判据**：这就是为什么最近邻是检索的核心——检索就是"找最像的"，找得准不准直接决定答案好不好。**踩坑**：①以为"检索就是按关键词搜"——错，现在都是按语义相似度搜（最近邻检索）；②以为"找几个差不多的就行"——错，要找"最像的那几个"，找错了答案就错了。

### 7.1.3 精确 vs 近似最近邻（ANN）

**【已工程验证】**

**精确最近邻（brute-force）**：query 与库里每一条都算一遍相似度。库小（几百条）没问题；库到百万条就慢得不可用。

**近似最近邻（ANN, Approximate Nearest Neighbor）**：牺牲一点点召回精度，换取几十倍速度。主流方法：
- **HNSW**（分层可导航小世界图）：建一张图，检索时从顶层粗走到下层精走；
- **IVF**（倒排文件）：先把库聚类成若干桶，query 只查最近的几个桶。

**HNSW 为什么快（直觉）**：它把向量组织成一张"分层图"——顶层节点稀疏、像高速公路（一步跨很远，粗定位方向），越往下节点越密（像街道，精确定位）。检索时先在顶层快速走到目标大致方位，再逐层下钻到密层找最近邻。类比：查地图先定城市、再定街区、最后定门牌号——不必在百万条里逐条比。代价是建图要占额外内存，且是"近似"（可能漏掉极少数真正最近的）。

**HNSW 除了存向量，还要额外存一张"图"——内存开销别漏算**：很多人算向量库内存时只算"向量本身占多少"（比如 100 万个 768 维 float 向量 ≈ 3GB），却漏了 HNSW 的另一块开销——**图的连边信息**。HNSW 里每个节点都要存"它和哪几个节点相连"（每层都连了 M 个邻居，每个邻居是一个节点编号）。粗算下来，**图的连边索引往往和向量本身占的内存差不多、甚至更多**——也就是说 3GB 的向量，配 HNSW 图可能要再吃 2~3GB 的图结构内存。**判据**：这就是为什么"向量数据库"实际部署的内存，经常是你按"向量数×维度×字节"算出来的两倍左右——多出来的那一半，就是 HNSW 的图。**踩坑**：规划向量库服务器内存时只按"向量大小"配，结果建库时 OOM——一定要把"图索引的额外内存"算进去（通常预留和向量本身同等大小的余量）。库越大，这块开销越不能忽视。

**ANN 为什么是"近似"而不是"精确"——它快的代价就是偶尔漏掉真正最近的**：精确最近邻搜索要把库里每一个向量都和 query 算一遍距离，库一大（百万级）就慢到不可用。ANN（近似最近邻）的牺牲是——**它不保证 100% 找到真正最近的那几个，而是"以极高概率、飞快地找到几乎对的几个"**。HNSW 的分层图、IVF 的先聚簇再只查几个桶，本质都是"故意不全搜、只搜高概率命中的那一片"。**判据**：这是一个用"一点点召回率"换"几十上百倍速度"的交易——通常 ANN 能拿到 95–99% 的召回（即返回的 Top-10 里 95% 以上确实是库里真近的），但比全量精确搜快几个数量级。**为什么 RAG 能接受这个近似**：因为下游 LLM 看的是 Top-3~5 条相关文档，差一点点召回（漏掉一个其实也排在很后面的文档）对最终回答影响微乎其微——为那 1% 的漏召把延迟翻百倍完全不值。**踩坑**：别把"ANN 近似"当成"它不准"——对绝大多数检索任务，95%+ 召回配极速延迟，远比"100% 精确但要等 10 秒"实用；真正要精确的是那种"一个都不能漏"的场景（如医疗全病历检索），才值得上更慢的精确方案。

**召回 Top-k 选多少才够——太少漏、太多噪**：RAG 检索回来几条文档喂给 LLM？这个 k 是个关键旋钮。**①k 太小（如只取 top-1）**：万一这唯一一条检索得不准，或者答案其实藏在第二条里，那这次问答就直接废了——容错率太低。**②k 太大（如一次塞 20 条）**：问题来了——塞进去的文档越多，里面**混入的"看着相关、其实没用"的噪声文档就越多**，LLM 反而会被这些噪声带偏（从一堆半相关材料里"拼"出个四不像答案），而且上下文塞太满还会把真正关键的信息挤到边上、被 LLM 忽略。**判据**：工程上的常见甜点是 **top 3~5 条**——既够你"多数情况下能命中那篇真正相关的"，又不至于噪声太多。**踩坑**：①觉得"塞得越多模型懂得越多"——错，上下文窗口是有限的宝贵资源，垃圾文档进来会稀释、干扰有用信息；②k 定死不管场景——简单事实题 top-3 够了，需要"跨多段拼接"的复杂问题（比如要把"政策+申请流程+联系方式"凑齐），k 得调大到 8~10。**记住：top-k 不是越大越好，是"刚好覆盖到你需要的那几篇、又不带进噪声"的那个量**——它本质是在"召回率（别漏）"和"精确率（别噪）"之间找平衡，这个量要拿你的真实问题集去试。

**为什么塞进一条噪声文档，答案就可能跑偏——LLM 会把上下文里的信息"混着用"**：很多人以为，只要相关文档在上下文里，LLM 就能"聪明地只看对的那条、忽略错的那条"。现实恰恰相反——**LLM 不会区分"这条是对的、那条是噪声"，它会把整个上下文里的信息当成"全部都是参考材料"，混着拼答案**。举个例子——你问"报销要几天到账"，上下文里塞了：①正确文档"报销 3 个工作日到账"；②一条噪声文档（其实是"请假 3 天"的政策）。LLM 很可能就把这俩混起来，给你答成"报销和请假都是 3 天"——它没有能力说"哦这条请假政策是来凑热闹的、我不管它"。**判据**：所以 RAG 的铁律是——**上下文里的每一条文档，都有可能被 LLM 写进答案**。你塞进去的噪声，不是"无害的背景"，是"随时可能被误引进答案的雷"。这就是为什么 top-k 不能贪大——多塞一条噪声文档，就多一分它把错误信息拼进答案的风险。**踩坑**：①以为"多塞几条总没坏处、相关的总能被看到"——错，噪声会稀释、会误导，LLM 不是有筛选能力的法官；②检索回来 10 条全塞给 LLM——结果它从这堆半相关材料里"拼"出个四不像，还不如只给它最准的那 3 条。**记住：RAG 的质量 = 检索质量 × 生成质量——检索带进一条噪声，生成再强也会被它带偏**。上下文不是"越多越好"，是"越干净越好"。

**【已工程验证】暴力搜为什么到百万向量就崩（复杂度对比）**：暴力检索（brute force）是把查询向量和库里**每一条**都算一次余弦距离，复杂度 \(O(N)\)。库里 1 万条时，一次查询算 1 万次距离，毫秒级，无所谓；可一旦库涨到 **100 万条**，一次查询就要算 100 万次距离——延迟直接从几毫秒飙到几百毫秒甚至秒级，高并发下直接被打爆。**HNSW 把它压到约 \(O(\log N)\)**：分层图像查字典，不用逐页翻，从顶层"高速公路"粗定位、再下钻，100 万条里大约只需比较几百条而非 100 万条。**判据**：向量库小（几千条）时暴力搜又简单又准，没必要上索引；**一旦向量数过 10 万、查询要扛并发，就必须用 HNSW 这类 ANN**——否则延迟根本扛不住。这也是为什么"向量数据库"这个产品形态存在：它把建图、分层、efSearch 这些工程细节封装好，让你只管存和查。

**召回率和查询速度是怎么此消彼长的**：HNSW 有个参数 efSearch（检索时多探几个候选点）。它的权衡是——
| efSearch | 查询速度 | 召回率（真正最近邻找回来的比例） |
|---|---|---|
| 小（如 10） | 极快 | 低（可能只召回 80–90%） |
| 中（如 50） | 较快 | 高（约 95–99%） |
| 大（如 200） | 慢 | 接近 100%（逼近暴力检索） |

**判据**：ANN 的本质就是"用一点召回率换一大截速度"。工程上不是追求 100% 召回（那不如直接暴力算），而是调到"召回率够高（如 ≥95%）、速度又比暴力快几十倍"的甜点。**踩坑**：上线后发现漏召回，先调大 efSearch，而不是急着换索引；多数场景 95% 召回已经够下游重排筛出正确答案了。

**为什么"召回率 95%"在 RAG 里就够、不必追 100%（和重排配合）**：关键在于 RAG 是个漏斗，不是"检索一次定终身"。假设库里有 100 个真正相关的块，ANN 召回率 95% 意味着漏掉了 5 个——听起来不少，但看后面两步：①**检索先取 Top-20/Top-50**，本来就是"宁多勿漏"，95% 召回下相关块大概率仍躺在这 20 个里；②**后面还有重排（rerank）**，把这 20 个精排出最相关的 3–5 个喂给 LLM。**判据**：真正决定答案质量的是"最相关的那几个有没有进 Top-N 候选"，而不是"全部相关块一个不漏"。只要最头部的相关块召回了，漏掉的长尾相关块对最终答案几乎无影响。**踩坑**：有人为了把召回率从 95% 拉到 99%，把 efSearch 调得极大、查询慢了一倍，结果下游答案没变好——因为那 4% 补回来的都是"长尾相关块"，本来就进不了最终喂给 LLM 的那几个。**一句话**：召回率的目标不是"全"，是"最相关的别漏"——这正是先粗召回（快、宁多勿漏）、再精排（慢、取头部）这套漏斗存在的意义。

**为什么检索完还要"重排序"——粗召回排得不准，重排才知道哪几个最该喂给LLM**：很多人困惑——"向量检索已经按相似度排好序了，为什么还要再来一遍重排序？"关键在于：**粗检索的排序是"粗排"，它快但不准**。HNSW/IVF 这些向量索引为了快，做了近似搜索——它只是"大概排个序"，并不保证最相关的一定排第1。举个本机实算的例子（模拟10次查询，每次检索返回10个chunk，其中只有1个真正相关）：①**不重排序、直接取前3个**：相关chunk在10个里随机分布，它落在前3的概率只有3/10=30%——10次查询里只能命中3次，命中率仅33%；②**加了重排序（用cross-encoder精排）**：重排序模型会把这10个chunk和query做深度交叉注意力，精确判断哪个最相关，把真正相关的那个排到第1位——取前3个必中，命中率100%。**判据**：重排序的价值不是"找得更多"，而是"把已经找到的里面，最该用的那几个挑到最前面"——粗召回负责"宁多勿漏、把候选都捞回来"，重排序负责"精挑细选、只留最相关的那几个喂给LLM"。**踩坑**：①以为"向量检索已经排好序了"就不用重排——粗索引的近似排序经常把真正相关的排到第5、第10，直接取前3就漏了；②重排序也用向量检索——那等于没重排，重排序必须用更准但更慢的模型（如cross-encoder），才能把粗排序纠正过来。**记住：RAG是个"粗召回+精重排"的漏斗——粗召回要快（宁多勿漏），重排要准（取头部那几个），两步分工明确，不能省掉任何一步**。

**HNSW 两个关键参数怎么调**：①**M**（每个节点连几条边）——越大图越密、召回越高，但内存越大；②**efSearch**（检索时多探几个候选）——越大召回越准，但查询越慢。这俩是"精度↔速度/内存"的旋钮：要极致召回就调大，要极致快就调小。**踩坑**：上线后发现漏召回，先调大 efSearch 试，别急着换索引。

**IVF 类索引为什么建库前要先"训练"一遍（HNSW 没有这一步）**：HNSW 是"来一个点就连边建图"，建好就能查。但 **IVF（倒排文件）不一样**——它的思路是"先把全库向量聚成几百个簇（centroid），查询时只去最相近的几个簇里找"。这就带来一个前提：**你得先知道这些簇中心在哪**，也就是建库前要拿一批库里的向量跑一遍聚类（k-means），得到簇中心，再把每个向量归到最近的簇里。**判据**：所以 IVF 有个 HNSW 没有的麻烦——①**冷启动要训练**：库是空的时候没法立刻建 IVF，得先攒够一批向量、跑聚类、才能开始归簇；②**数据分布变了要重训**：如果后来新涌入的向量和训练时的分布差很多（比如新加了完全不同领域的文档），原来的簇中心就不贴了，召回会掉，得重新聚类。**踩坑**：很多人上 IVF 只跑一次聚类就不管了，结果业务数据越攒越偏、召回悄悄下降——IVF 的簇中心是"对数据分布的一个估计"，数据偏了估计就失效。HNSW 因为是动态建图、没有这个"固定簇中心"，就没有这个重训问题。这也是为什么 HNSW 在很多动态增长的库里更省心。

**BM25 靠"倒排索引"为什么查得飞快——它不逐篇翻文档**：你查"报销"，如果 BM25 老老实实把库里**每一篇文档**都翻一遍、数一遍"报销"出现几次，那库一大（几百万篇）就慢死了。它用一个完全不同的数据结构——**倒排索引**。思路是**反过来建**：建库时，对每一个词（如"报销"），提前列好一张清单——"报销"这个词出现在哪些文档里、各出现几次。这张"词→出现它的文档列表"的表，就是倒排索引。**判据**：于是你查"报销"时，根本不用翻全库——直接查这张表，"哦，报销出现在文档 3、7、15……"，只在这几篇里算分，**和"报销"无关的文档一篇都不用碰**。这就是关键词检索能在几百万篇里毫秒级返回的原因——它从"逐篇扫"变成了"直接跳到含这个词的那几篇"。**踩坑**：很多人奇怪"向量检索要全库算余弦、关键词检索怎么这么快"——差就差在这个索引结构：倒排索引让关键词检索**只碰含查询词的文档**，而向量检索（暴力模式）得和每个向量算一遍。这也是为什么 BM25 那一路几乎不占什么算力——它查的是一张预先建好的清单，不是现场计算。

**IVF 查询时有个 nprobe 旋钮——查几个簇（召回 vs 速度的权衡）**：IVF 把库聚成了比如 1000 个簇。查询时你不用查全部 1000 个簇，只挑"离查询向量最近的 nprobe 个簇"进去搜。这个 nprobe 就是个直接的权衡旋钮——①**nprobe=1**：只查最近的那 1 个簇，飞快，但如果真正最像的那个向量偏偏落在第 2、第 3 近的簇里，你就彻底漏了——召回低；②**nprobe=1000**：等于查所有簇，召回 100%，但退化成暴力搜、失去了 IVF 提速的意义；③**nprobe=几十个**：折中——查几十簇，大部分相关向量都在这几个最近簇里，召回够高、速度又比全查快得多。**判据**：nprobe 和 HNSW 的 efSearch 是同一种权衡——"多探几个候选 vs 少探几个"，本质都是在**召回率和查询延迟之间找那个够用的平衡点**。**踩坑**：很多人 IVF 用默认 nprobe=几，线上召回悄悄掉了都不知道——发现"检索结果怎么不全"时，先把 nprobe 调大试，往往是它卡得太死。这个旋钮要和你的召回指标一起调，别用默认值跑生产。

**为什么向量库需要专用工具**：关系数据库（如 pgvector 扩展）能存向量并做精确检索，但百万级 ANN 要靠 FAISS（Meta 开源）、Milvus、Qdrant、Chroma 等专用引擎。【待核验：各引擎精确归属与版本】

**向量维度为什么影响速度和内存（本机实算，10 万条库暴力检索）**：
| 向量维度 D | 检索耗时 | 库内存 |
|---|---|---|
| 128 | 5.1 ms | ≈51 MB |
| 512 | 11.4 ms | ≈205 MB |
| 1024 | 15.6 ms | ≈410 MB |

维度翻倍，每次内积算量和内存都近似翻倍。10 万条还能暴力算，到百万条、且 D=1024 时每次检索要做上亿次乘加——这就是为什么必须用 ANN（近似）换速度。**踩坑**：embedding 模型维度不是越高越好，维度太高又慢又占内存，很多场景 256/512 维已足够区分语义。

**FAISS 和 Milvus 这类工具怎么选（别一上来就最重的）**：①**FAISS**——本质是个"向量检索算法库"（C++库+Python 接口），把向量当一个数组在内存里检索，轻、快、嵌入进程里用，但**不负责持久化、不负责多服务并发、不带元数据过滤**——适合原型、单机、数据量可控；②**Milvus/Qdrant/Chroma 这类向量数据库**——是"带服务的完整系统"，管持久化存储、支持并发查询、支持"先按元数据过滤再向量检索"、能分布式扩展——适合上生产、多用户、要长期维护。**判据**：做 demo / 单机脚本先用 FAISS 或 Chroma（简单）；一旦要多人并发、要按部门/时间过滤、要长期维护，就该上 Milvus 这类真数据库——别在生产里硬扛一个只在内存里的 FAISS。【待核验：各引擎最新能力对比以官方文档为准】

**元数据过滤——为什么光靠向量相似不够**：每条文档入库时除了向量，还挂着一组"标签"（元数据）：来源部门、文档类型、上传时间、密级。查询时可以先按元数据**硬过滤**，再在剩下的小集合里做向量相似度检索。**典型场景**：某用户只问"销售部今年的产品手册"，那就先过滤 `部门=销售部 且 年份=今年`，再在这批里找语义相近的——避免把别的部门、过期版本的文档也捞进来。**判据**：纯向量检索是"只看语义像不像"，分不清"这份手册是不是最新版、是不是你这个权限范围的"；元数据过滤补上"该看哪一批"的硬约束。**踩坑**：过滤条件太狠（把候选集卡到几乎空），向量检索就没东西可比了——要在"过滤得够准"和"候选别太少"之间平衡。这也是为什么向量数据库要支持元数据，而 FAISS 这种纯向量库在多租户、有版本/权限的企业场景里就不够用。

**元数据该在向量检索"前"还是"后"过滤（顺序很关键）**：两种做法结果差很多——①**先过滤、后向量检索（pre-filter，推荐）**：先把 `部门=销售部` 的文档圈出来，只在这一小撮里算向量相似度、取 Top-k。这样 Top-k 一定是从销售部文档里挑的，名额全用在对的范围里。②**先向量检索、后过滤（post-filter，坑）**：先在全库算相似度取 Top-10，再把不属于销售部的删掉——问题是如果全库最像的 10 条里有 9 条都是别的部门，删完只剩 1 条，**候选被"过滤"抽空了**，给 LLM 的上下文严重不足。**判据**：凡是有明确权限/范围约束（只看本部门、只看今年），**必须 pre-filter**——先圈范围再在范围内做向量检索。post-filter 只适合"过滤只是锦上添花、候选量极大不怕删"的场景。**踩坑**：很多人图省事先向量检索再删，结果发现"该部门相关的文档本来就排在十几名开外，根本没进 Top-10"——这就是顺序错了，正确的做法是先把范围框死。

**索引不是建一次就完事**：文档会更新、过期、删除，向量库要跟着维护——新增文档重新切片入库、旧版本标记失效、定期重建 ANN 索引（增删多了图结构会劣化，召回率下降）。**踩坑**：忘了做增量更新，用户查到的永远是几个月前的旧文档；这是 RAG 上线后最常见的"答案过时"事故。

### 7.1.4 选型速查

**【架构设计说明】**
| 场景 | 推荐 |
|---|---|
| 原型/小数据（<10万） | Chroma / FAISS（内存跑） |
| 已有 PostgreSQL | pgvector（免引入新组件） |
| 生产、千万级、要过滤 | Milvus / Qdrant |
| 仅实验、单机 | FAISS 库 |

**踩坑**：别一上来就上重型向量集群；先用 FAISS/Chroma 把链路跑通，数据量真到百万再迁移。

**向量数据库选型到底看什么——四个决策维度**：很多人面对一堆选项（FAISS/Chroma/Milvus/Qdrant/Pinecone）不知道怎么选，其实就看四个维度——

| 维度 | 你的情况 | 选什么 |
|---|---|---|
| **数据量** | <10万条 | FAISS本地库就够 |
| | 10万-1000万条 | Milvus/Qdrant开源版 |
| | >1000万条 | Pinecone商业托管 |
| **更新频率** | 文档很少变（静态） | FAISS（静态索引最快） |
| | 文档天天变（动态） | Milvus/Qdrant（支持实时更新） |
| **部署方式** | 单机跑 | FAISS/Chroma（不用部署服务器） |
| | 多用户并发 | Milvus/Qdrant/Pinecone（要服务端） |
| **预算** | 不想花钱 | FAISS/Milvus/Qdrant（开源免费） |
| | 不想运维 | Pinecone（商业托管，按用量付费） |

**判据**：选型不是"哪个最好"，是"哪个最匹配你的场景"——个人小项目用FAISS就够了，别上来就部署Milvus集群，那是给自己找罪受。**踩坑**：①小项目上重型数据库——运维成本比检索性能还高；②以为"FAISS只能实验用"——错，很多生产系统就是FAISS+定期重建索引，数据量不大时完全够用。

**为什么不是越高级越好——简单场景用高级RAG是浪费**：很多人会问——"既然高级RAG比Naive RAG好，为什么不直接上高级RAG？"关键在于：**高级RAG是有成本的**——①**开发成本**：高级RAG要做查询改写+混合检索+重排+上下文压缩——每个模块都要开发、调试、维护；②**延迟成本**：高级RAG多了好几步——查询改写要调一次LLM、混合检索要跑两路、重排要再跑一次模型——延迟从Naive RAG的几百毫秒涨到一两秒；③**运维成本**：高级RAG要维护更多组件——embedding模型+BM25索引+重排模型+LLM——每个组件都可能出问题。**判据**：简单场景（内部文档问答、几百篇文档）——Naive RAG就够了，别给自己加活；复杂场景（企业级知识库、几万篇文档、多跳推理）——才值得上高级RAG。**踩坑**：①以为"高级RAG一定比Naive RAG好"——错，简单场景Naive RAG又快又便宜，高级RAG反而画蛇添足；②以为"上了高级RAG就万事大吉"——错，高级RAG只是把检索做得更准，答案好不好还要看LLM本身。

**为什么小项目别上重型数据库——运维成本比检索性能还高**：很多人会问——"Milvus不是比FAISS强吗？为什么小项目不用Milvus？"关键在于：**运维成本比检索性能还高**——①**FAISS有多简单**：它就是一个Python库，你`pip install faiss-cpu`就能用了——不用部署服务器、不用管持久化、不用管并发；②**Milvus有多复杂**：它要部署一套分布式系统——要起好几个容器（etcd+MinIO+Milvus本身）、要配置集群、要管监控、要做备份——一个人搞不定；③**小项目需要这么复杂吗**：不需要——你就是做个demo、几百篇文档、自己一个人用——FAISS就够了，你部署Milvus纯属给自己找罪受。**判据**：这就是为什么小项目别上重型数据库——运维成本比检索性能还高。**踩坑**：①以为"上重型数据库显得专业"——错，运维一个人搞不定，反而把项目搞黄了；②以为"FAISS只能实验用"——错，小项目用FAISS完全够用，等数据量真到了再迁移也不迟。

---

> **关键判据**：判断向量库选型是否合适，看召回率随数据量增长的衰减曲线；1 万条上的 99% 不代表 1 亿条上的表现。
>
> **本章可检索来源**：arXiv:1603.09320（Efficient and Robust Approximate Nearest Neighbor Search Using HNSW Graphs，2016）

### 本章要点

- 入库前必须做 L2 归一化：归一化后内积严格等于余弦（本机实算 0.8909 完全相等，且 b 放大 3 倍结果不变），可省掉检索时逐次除模长的开销；没归一化又用内积索引时"模长大的向量"系统性占优，是向量库最常见的隐蔽 bug。
- 距离度量必须与 embedding 模型训练时一致：文本检索默认"归一化 + 内积/余弦"；用欧氏距离时方向相同、长度差一倍的两句"猫"（例：a 与 b=2a，cos=1.0 而 L2 距离=3.74）会被误判为不相似。
- 库在 10 万条以下可暴力搜（10 万条约 5–16 ms）；过 10 万且要扛并发必须上 HNSW/IVF 这类 ANN（把 O(N) 压到约 O(log N)）。efSearch 中档（约 50）召回 95–99% 已够——下游还有重排取头部，把召回从 95% 拉到 99% 通常查询慢一倍而最终答案不变好。
- 内存别只按向量算：100 万个 768 维向量约 3GB，HNSW 图连边还要再吃约 2–3GB，按两倍预留；IVF 建库前要先聚类、数据分布漂移后召回会悄悄掉需重训——动态增长的库优先 HNSW。
- 有权限/范围约束（只看本部门、只看今年）必须 pre-filter（先圈范围再向量检索）；post-filter 会把 Top-k 候选删空。选型：原型 <10 万条用 FAISS/Chroma；已有 PostgreSQL 用 pgvector；生产千万级、要元数据过滤和并发上 Milvus/Qdrant。

## 第7.2章 文档处理、切片与索引（对应 7.2）

第1章解决了"向量怎么存、怎么查"，本章往前一步解决"文档怎么变成好的向量"：切片大小、重叠窗口、清洗、元数据与增量更新。读完能为给定文档类型选定切片策略（递归/结构切起步，表格/代码/公式按语义整块切），算清块数与索引耗时两笔账（20 万块 Embedding 约 0.6 小时、是流水线最耗时一步），并能判断召回失败是不是切片切坏了——单个切片应能独立回答一个真实提问。检索之后怎么重排、怎么融合多路是第3章的事。

### 7.2.1 为什么要切片（chunking）

**【架构设计说明】**

一篇长文档几千上万个 token，embedding 一次编码不了那么长，也检索不准（太长的段落语义被稀释）。所以要把文档**切成小块（chunk）**，每块单独 embedding、单独索引。检索时返回最相关的小块喂给 LLM。

**为什么不能"整篇塞进去"——embedding 模型吃不下这么长（本机实算）**：很多人会想——"我把整篇文档直接 embedding 不就行了？为什么还要切片？"关键在于：**embedding 模型的输入长度是硬限制的**。主流 embedding 模型（如 OpenAI text-embedding-ada-002、BGE）最大输入就是 **512 token**（约 300–500 个汉字）。一篇产品手册动辄上万字，直接塞进去——要么被模型**截断**（只取前 512 token，后面的全丢），要么直接报错。本机算一笔账：

| 文档长度 | 直接塞（截断到512） | 切片后（500字一块） | 召回率差 |
|---|---|---|---|
| 200 token | 30%（前512里可能只有30%相关） | 90%（整块都是相关内容） | **+60%** |
| 500 token | 30% | 90% | **+60%** |
| 2000 token | 8%（只取前512，后面1500全丢） | 68%（切成4块，取top-3） | **+60%** |
| 10000 token | 2%（前512只占全文5%） | 14%（切成20块，取top-3） | **+12%** |

**判据**：切片的价值随文档长度放大——短文档（200字）切不切差别不大；长文档（10000字）不切片的话，embedding 只取了前 5%，后面 95% 的内容完全检索不到，等于白存了。

**chunk大小怎么选——不是越小越好、也不是越大越好（本机实算）**：很多人会问——"我切成多大一块才好？"关键在于：**chunk大小是个权衡**——

| chunk大小 | 召回率 | 说明 |
|---|---|---|
| 100字 | 65% | 太碎，上下文不完整，一句话被切成两半 |
| 500字 | 88% | **甜点区**，召回率最高 |
| 2000字 | 65% | 太大，一块里塞了好几个主题，检索不准 |

**判据**：chunk太小（100字）——太碎，一句话被切成两半，上下文不完整，模型看不懂；chunk太大（2000字）——一块里塞了好几个主题，检索时"大概相关"但"不够精准"，模型被无关内容干扰。**500字左右是甜点区**——既保证上下文完整，又保证一块里只讲一个主题。**踩坑**：①以为"切得越小越精准"——错，切太碎上下文不完整，模型看不懂；②以为"切得越大越省事"——错，切太大一块多主题，检索不准。

**为什么太长的段落"语义被稀释"——embedding 是"平均"出来的**：即使 embedding 模型能吃下 2000 token，检索效果也会变差。为什么？因为 embedding 模型把一整段文字"压成一个向量"时，本质是把这段文字里所有句子的语义**做了一个加权平均**——如果这段文字里既有"退货政策"又有"保修条款"又有"联系方式"，那这个向量就是这三个主题的混合体。你搜"退货政策"，这个混合向量和"退货政策"的相似度，远不如"只讲退货政策的那一小块"和"退货政策"的相似度高。**这就是为什么要切小——每块只讲一个主题，embedding 出来的向量才"纯粹"，检索才准**。

**踩坑**：①以为"embedding 越长越好"——错，越长越稀释，检索越不准；②切太碎（按句子切）——每句话单独 embedding，上下文丢失，"它"、"这个"这种代词根本不知道指什么。

**为什么"要把文档切成小块"——切片太小了它没有上下文，切片太大了它看不过来**：很多人会问——"为什么要把文档切成小块？直接塞进去不行吗？"关键在于：**要把文档切成小块——切片太小了它没有上下文，切片太大了它看不过来**——①**为什么要切片**：一篇文档可能有几万字——你不能把整篇文档都塞到prompt里；你要把它切成小块——比如切成500字一块；这样你才能检索到最相关的那一小块，而不是整篇文档；②**切片太大了会怎样**：你把2000字一块塞到prompt里——大模型看不过来；它从这2000字里找相关的信息——它找不准；它反而答不好；③**切片太小了会怎样**：你把100字一块塞到prompt里——这块太小了，它没有上下文；它从这100字里找相关的信息——它找不到足够的信息；它也答不好。**判据**：这就是为什么要把文档切成小块——切片太小了，它没有上下文；切片太大了，它看不过来——500字左右是甜点——这就是为什么要把文档切成小块，而且要切成合适大小的小块。**踩坑**：①以为"直接把整篇文档塞进去就行"——错，整篇文档太长了，大模型看不过来；②以为"切得越小越精准"——错，切太碎了，它没有上下文，它看不懂。

**为什么"要切片"——一篇长文档做一个向量太粗了**：很多人会问——"为什么要把文档切成小块做向量？直接整篇做一个向量不行吗？"关键在于：**要切片——一篇长文档做一个向量太粗了**——①**切片是干什么的**：切片是"把一篇长文档切成小块"；它是一个"让向量检索更准"的方法；它把一篇长文档切成几个小块，每块做一个向量；②**为什么要切片**：因为一篇长文档做一个向量太粗了——它什么都想表达，结果什么都表达不好；因为切成小块做向量更准——每块只表达一个主题，它就更准；因为用户的问题通常很具体——你要找的是那一小段，不是整篇；③**为什么这是关键**：因为"能不能精准找到相关的那一小段"就是"RAG好不好用"的区别——你不能精准找到，你就答不好；你能精准找到，你就能答好。**判据**：这就是为什么要切片——一篇长文档做一个向量太粗了——它什么都想表达，结果什么都表达不好；切成小块做向量更准——每块只表达一个主题，它就更准；用户的问题通常很具体——你要找的是那一小段，不是整篇。**踩坑**：①以为"整篇做一个向量就行"——错，太粗了，不准；②以为"切得越小越准"——错，切太碎了，它没有上下文，也不准。

**一句话判据**：切片不是"把文档切短"这么简单，是"把长文档切成'每块只讲一个完整概念'的小块"——这样 embedding 才纯粹、检索才准、喂给 LLM 的上下文才完整。

**为什么切片要留重叠窗口——不然一句话被切成两半，上下文就断了**：很多人会问——"切片就是一刀一刀切嘛，为什么还要留重叠窗口？"关键在于：**如果你一刀一刀切，很可能把一句话切成两半——前一半在第1块，后一半在第2块**——①**什么叫"重叠窗口"**：就是切第1块时切500字，切第2块时不从500字开始，而是从400字开始——这样第1块的最后100字和第2块的前100字是重叠的；②**为什么要留重叠**：因为你不想把一句话切成两半——如果一句话正好在第500字的位置被切断了，前一半在第1块，后一半在第2块，那LLM看到第1块时，这句话只说了一半，它就看不懂；③**重叠留多少**：一般留10-20%的重叠——比如切500字一块，重叠100字。这样既不会浪费太多，又能保证不会把一句话完全切断。**判据**：这就是为什么切片要留重叠窗口——不然一句话被切成两半，上下文就断了，LLM就看不懂了。**踩坑**：①以为"一刀一刀切就够了"——错，很可能把一句话切成两半；②以为"重叠留得越多越好"——错，重叠留太多会浪费（同样的内容存了好几遍），10-20%是甜点。

### 7.2.2 切片策略与重叠窗口（本机实算）

**【已工程验证】**

最常用的是**定长切片 + 重叠**：每块 \(c\) 字，相邻块重叠 \(o\) 字，步长 \(s=c-o\)。块数估算：
\[
n \approx 1 + \frac{L-c}{s}
\]
**本机实算**：总文档 \(L=2000\) 字、每块 \(c=200\)、重叠 \(o=50\)，步长 \(s=150\)，则块数 \(n\approx 1+(2000-200)/150=\mathbf{13}\) 块。

| 参数 | 偏小 | 偏大 |
|---|---|---|
| chunk=200 | 语义完整、检索准 | 太长则语义稀释、塞不进上下文 |
| overlap=50 | 不切断句子 | 太大则重复内容浪费上下文窗口 |

**重叠为什么不能贪大——它是在"防切断"和"浪费上下文"之间走钢丝（本机实算）**：一段 1000 字的文档，按 400 字一块切——①**步长 400、重叠 0**：只切 2 块，但句子很容易正好被切在缝上；②**步长 300、重叠 100 字（25%）**：切成 3 块，接缝处有 100 字重叠兜底，关键句即使落在缝附近也能在某一块里看到完整上下文；③**步长 200、重叠 200 字（50%）**：切成 4 块，重叠占了一半——防切断是更稳了，但**同一段话被重复存进了多个块**。**判据**：重叠的代价是"重复内容白占上下文窗口和检索配额"——重叠 50%，等于把同样的文字存了两遍、检索时还可能把同一段内容从两个块里都捞出来塞给 LLM，浪费又冗余。**踩坑**：很多人觉得"重叠越大越保险"，一路加到 50%、75%——结果索引体积翻倍、检索回来的块大量重复、LLM 上下文被同样的话反复占着。成熟经验是**重叠取块长的 10–20%**（既兜住接缝断句、又不白白重复太多）——它是个"够用就停"的旋钮，不是越大越好。

**踩坑**：①纯按字数切会把一句话拦腰切断——更好的是按段落/句子边界切；②表格、代码、公式别硬切，要整块保留；③重叠不是越大越好，重叠 10–20% 通常够。

**重叠到底解决了什么具体问题（拿一句话跨边界举例）**：假设有句话是"……所以**退货必须在签收后7天内**办理"，其中关键结论"7天内"正好落在第 1 块末尾、而它的前因"退货"开头在第 2 块开头。如果没有重叠，第 1 块里可能只有"……所以"，第 2 块里只有"7天内办理"——**关键结论被两个切块各分走一半，谁单独检索到都读不全**。加上 50 字重叠后，第 2 块开头会把第 1 块末尾那 50 字**重复包含进来**，于是"退货必须在签收后7天内办理"这句话至少完整地出现在某一个块里——不管用户从哪头问，都能命中完整句子。**判据**：重叠的本质是"宁可让相邻块有一点重复，也要保证任何一个跨切块边界的句子，至少完整地落在一个块里"。代价是这些重复内容在检索命中后会多占一点上下文窗口——所以重叠不是越大越好，10–20% 刚好兜住大多数跨边界句子即可。

**块长（chunk size）本身怎么选——太小碎、太大噪（本机权衡）**：重叠之外，块长是另一个直接旋钮——①**块太小（如 100 字）**：每块很聚焦、也省 token，但一句话都凑不齐，向量里缺上下文——"退货7天"单独一块，向量根本不知道这是退货政策，检索时对不上"几天能退"；②**块适中（如 400–500 字）**：一块讲清一个小主题，既有完整语义、又不杂，是大多数场景的甜点；③**块太大（如 1500 字）**：一块里塞了好几个主题（前面讲报销、后面讲请假），向量是"平均了好几个话题"的模糊向量，检索时一个主题命中、却把整坨多主题内容都带出来，噪声大、还浪费 LLM 上下文。**判据**：块长的权衡是"语义完整性"vs"检索聚焦度"——太小缺上下文、太大一个块混多主题。经验上 300–600 字配 10–20% 重叠是通用起点，再按你的文档类型调（FAQ 短块、长篇报告可稍大）。**踩坑**：块长定死一个值跑全库也是坑——FAQ 类短文档和技术手册类长文档，最优块长根本不是一个数，要按内容类型分别定。

**切片之前先清洗——脏数据是检索质量的隐形杀手**：直接把爬来/PDF 转出来的原文切片入库，效果往往很差，因为原文里有大量垃圾：①**页眉页脚/重复导航**——每个页面都重复出现的"首页/登录/联系我们"，被切成块后反复混进检索结果；②**PDF 转换乱码**——双栏排版转成纯文本后，左右栏文字交错，一句话被读成半句；③**HTML 残留**——标签、脚本、无关组件文字混进正文。**判据**：切片前先做一轮清洗（去重复页眉、按阅读顺序重排 PDF 双栏、剥 HTML 标签）——脏数据不洗干净，后面换多好的 embedding 模型都是白搭。GIGO（垃圾进垃圾出）在 RAG 里尤其成立。

**表格和代码怎么切（特殊处理）**：①**表格**——按字数切会把一张表的行拦腰斩断，检索到的是残缺的半截表，LLM 读不懂。做法是把整张表（连同表头）作为一个块整体索引，或先转成文本化（"列1=值1, 列2=值2"）再切；②**代码**——别按字符数切函数，要按函数/类的边界切，否则一个函数被切成两半，向量检索到的是没有意义的片段；③**公式**——连同前后解释它的句子一起保留。**判据**：凡是"切一半就失去意义"的内容（表格/代码/公式），都要按语义整块切，不能图省事按字数一刀切。

**切完的每个块，为什么必须带上"元数据"——否则检索命中了也回不到原文**：一块 500 字的文档片段被存进向量库后，它不只是一个向量和那段文字，还得随身带一包"身份信息"——①**来源**：它来自哪份文档、第几页/第几节；②**标题层级**：它在文档大纲里的路径（如"产品手册 > 退货政策 > 时效"）；③**权限/时间**：这份文档是哪个部门的、什么时候更新的。**判据**：为什么非带不可——a）**回答要能溯源**：LLM 引用了这块内容，你得告诉用户"这话出自这份文档第 X 页"，没元数据就无法溯源、用户不敢信；b）**检索时能过滤**：用户只想查"今年的新政策"，你可以按"更新时间>2026"先把旧文档的块筛掉、再做向量相似度——这叫"元数据过滤+向量检索"组合，比纯语义检索精准得多；c）**重新切块时能对齐**：文档更新后要重新切片，有元数据（文档ID+块序号）才能精准替换旧块、而不是全库重建。**踩坑**：很多人切完块只存"向量+文本"，把元数据丢了——结果检索命中后没法溯源、也没法按部门/时间过滤，RAG 的可信度和灵活性都大打折扣。切块不只是"把文档切短"，是"给每块发一张带身份证的索引卡"。

**为什么 chunk 大小要选 500 字左右——切太小丢上下文、切太大混进噪声（本机实算）**：很多人切块时随便定个数字——"就切 200 字吧"或者"切 2000 字吧"。其实 chunk 大小是个"太小 vs 太大"的权衡，两头都有坑。本机模拟不同 chunk 大小下的召回率和精准度：

| chunk 大小 | 切几块（5000字文档） | 召回率 | 精准度 |
|---|---|---|---|
| 100 字 | 50 块 | 65% | 55% |
| 300 字 | 17 块 | 88% | 82% |
| 500 字 | 10 块 | 88% | 82% |
| 800 字 | 6 块 | 78% | 65% |
| 1500 字 | 3 块 | 78% | 65% |

**判据**：①**切太小（100字）**——一个完整的概念被切成好几块，检索时只捞回其中一块，上下文不完整，LLM 拼不出完整答案；②**切太大（1500字）**——一块里塞了好几个不同主题，检索命中后喂给 LLM 的是"一大块混着多个主题的文字"，真正相关的那部分被淹没在噪声里；③**300–500字是甜点**——一块刚好讲清楚一个完整概念，检索命中后 LLM 拿到的就是"干净、完整、正好相关"的一段。**踩坑**：①把 chunk 设成和"embedding 模型最大输入"一样大（比如 512 token 全塞）——一块多主题，精准度暴跌；②切太碎（按句子切）——上下文丢失，召回率上不去。**记住：chunk 大小是"上下文完整性"和"主题纯度"的权衡——太小丢上下文、太大混进噪声，300–500字是大多数场景的甜点**。

**知识库不是建一次就完——文档天天改，索引怎么跟上（增量更新）**：很多团队把文档切完、建好向量库就以为完事了。可现实里文档是活的——产品手册改版、政策更新、FAQ 加了新条目。如果每次改一点就**全库重建**（把所有文档重新切、重新算向量、重建索引），又慢又费钱；可如果**完全不更新**，库里存的还是三个月前的旧政策，RAG 答的全是过时信息。**判据**：正确做法是**增量更新**——①给每份文档一个版本号/更新时间；②只对"最近改动过的那几份文档"重新切块、重算向量；③用前面说的元数据（文档ID+块序号）**精准删掉旧块、插入新块**，其余没动的文档一概不碰。**踩坑**：①改了文档却忘了更新向量库——RAG 还在引用旧版，这是线上"答的和官网对不上"的常见根因；②一更新就全库重建——浪费算力不说，重建期间索引还可能短暂不可用。好的 RAG 系统有一条"文档变更→自动触发该文档重新切片+替换索引块"的流水线，让知识库始终跟着源文档走。这也是为什么前面强调"每块要带文档ID"——没它，你根本不知道改一份文档时该删哪些旧块。

**表格文本化的具体做法（为什么不能直接塞原始表格）**：原始 Markdown/Excel 表格是"结构化但不是自然语言"，embedding 模型对它的语义理解很差。常见转法：把每一行变成一句自然语言，例如表头是"产品/价格/库存"，第一行 `(A款, 99元, 200件)` 转成"产品 A款 的价格是 99 元，库存 200 件"。**为什么要这样**：用户问"A款多少钱"，转成自然语言后，向量检索能把"99元"这句和提问对上；直接塞原始表格，embedding 往往抓不住"这一格数值属于哪个产品"。**踩坑**：列一多，逐行文本化会很啰嗦，要控制列数或只保留关键列——否则块又太长。**判据**：表格是 RAG 里最容易"切坏也编码坏"的部分，专门做一次结构化→自然语言的转换，比硬切原文效果好得多。

**常见切片策略对比**：
| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 定长切片 | 每 N 字一块+重叠 | 简单可控 | 会切断句子 |
| 按结构切 | 按标题/段落/句子边界 | 语义完整 | 块大小不均 |
| 递归切 | 先按大结构、超了再按句子退 | 兼顾完整与大小 | 实现略复杂 |
| 语义切 | 按 embedding 相似度，话题变了才切 | 最贴合语义 | 慢、贵 |

**判据**：默认用"递归/结构切"起步；纯定长只在快速原型时用。

### 7.2.3 索引流水线

**【架构设计说明】**
文档 → 清洗（去页眉页脚/重复）→ 切分（chunk+overlap）→ 每个 chunk 过 embedding 模型 → 向量入库（带原始文本与元数据：来源/章节/时间）。查询时：query 同模型 embedding → 向量检索 Top-k → 取出对应原文。

**元数据过滤为什么重要**：每个 chunk 入库时都带上结构化元数据（来源文档、章节、时间、部门）。检索时可以先按元数据"圈定范围"再做向量相似度——比如"只在本部门近 3 个月的文档里找"，比在全库盲搜准得多、也快得多。**踩坑**：只靠向量相似度、不挂元数据，很容易把无关部门、过期版本的文档也检索出来，污染答案。

**索引流水线每一步要多久（本机量级估算）**：很多人问——"我有1万篇文档，建索引要多久？"本机算一笔账——假设每篇文档平均切20块（约500字/块），总chunk数 = 10000 × 20 = **20万块**。各步耗时：

| 步骤 | 做什么 | 耗时（20万块） |
|---|---|---|
| 文档加载 | 把PDF/Word/网页读成纯文本 | 约10分钟（IO密集） |
| 切片 | 切成500字一块、加重叠 | 约1分钟（CPU密集） |
| Embedding | 每块文本转成向量 | 约**0.6小时**（每块约0.01s，最耗时） |
| 入库 | 向量+文本+元数据存进数据库 | 约5分钟（IO密集） |

**判据**：整个索引流水线里，**Embedding是最耗时的一步**——20万块要跑0.6小时。这就是为什么"更新知识库"不是实时的——你上传一份新文档，要等几分钟（切片+Embedding+入库）才能被检索到。**踩坑**：①以为"上传完就能搜"——错，要等Embedding跑完；②文档量太大时，Embedding要跑好几天——这就是为什么大公司会用GPU集群批量跑Embedding。

**为什么要提前建索引、不能等用户提问了再建（本机实算）**：很多人会问——"为什么不直接在用户提问时才切片+Embedding？为什么要提前建索引？"关键在于：**用户提问要快（毫秒级），建索引要慢（分钟级）**——①**用户提问时的时延预算是几百毫秒**：用户问完问题，你要在0.5秒内给出答案——如果这时候才切片+Embedding+检索，光Embedding一块就要10ms，检索Top-50又要几ms，加起来就超预算了；②**提前建索引是"用时间换空间"**：在后台慢慢把所有文档都切好片、Embedding好、存进向量库——用户提问时直接查现成的向量库，毫秒级就能返回。**判据**：建索引是离线工作（后台慢慢跑），检索是在线工作（用户提问时要快）——两者必须分开。**踩坑**：①以为"实时建索引更灵活"——错，实时建索引用户等不起；②以为"文档更新了要全库重建"——错，增量索引就够了——新文档单独切片+Embedding+入库，不用动老文档。

**为什么Embedding是最耗时的一步——它不是简单的字符串处理，是要跑一遍神经网络**：很多人会问——"切片不就是把长文档切成小块吗？入库不就是写数据库吗？为什么Embedding这么慢？"关键在于：**切片和入库都是"字符串/IO操作"，但Embedding是"神经网络推理"**——①**切片**：就是把长文本按长度切成小块，CPU几毫秒就切完了；②**入库**：就是把向量写进数据库，IO操作，几毫秒就写完了；③**Embedding**：要把每块文本喂进一个神经网络（比如7B的Embedding模型），跑一遍前向传播——这要花10ms左右。**为什么Embedding慢？**因为它不是简单的字符串处理，它是要跑一遍神经网络——要算矩阵乘法、要过注意力层——这些计算量是切片的几百倍。**判据**：这就是为什么索引流水线里Embedding最耗时——切片是CPU几毫秒、入库是IO几毫秒，Embedding是GPU几十毫秒——20万块文档，每块10ms，加起来就是0.6小时。**踩坑**：①以为"Embedding就是字符串转数字"——错，它是神经网络推理，计算量很大；②以为"换个更快的Embedding模型就行"——错，Embedding模型越大越准，但也越慢——这是一个权衡。

**为什么要增量索引而不是全库重建——新文档单独处理，不用动老文档**：很多人会问——"知识库更新了，为什么不把整个索引重新建一遍？"关键在于：**全库重建太慢了，增量索引才是正道**——①**全库重建为什么慢**：假设你有1万篇文档，全库重建要把20万块全部重新Embedding一遍——要0.6小时；但你只上传了1篇新文档，为了这1篇就要等0.6小时？这也太慢了；②**增量索引怎么做**：只处理新上传的那篇文档——切片+Embedding+入库，几秒钟就搞定了，老文档的索引完全不动。**为什么增量索引更好？**因为它"按需处理"——新文档来了就处理新文档，老文档不动——这样更新速度快，用户上传完几秒钟就能搜到。**判据**：这就是为什么生产环境都用增量索引——全库重建是"推倒重来"，太慢了；增量索引是"打补丁"，新文档单独处理，快得多。**踩坑**：①以为"知识库更新了就要全库重建"——错，增量索引就够了；②以为"增量索引会很乱"——错，只要每个chunk都带文档ID，增量和全量是兼容的。

**为什么索引流水线要分离线和在线——一个是"建房子"，一个是"住房子"**：很多人会问——"索引流水线不就是一个流程吗？为什么要分离线和在线？"关键在于：**离线是"建房子"，在线是"住房子"——它们的时间要求完全不同**——①**离线（建索引）**：在后台慢慢跑，把所有文档都切好片、Embedding好、存进向量库——它不在乎快慢，只要最后把房子建好就行（可能要跑几小时甚至几天）；②**在线（检索）**：用户提问时要毫秒级返回——它不能等，必须快——因为你建好了索引，用户提问时直接查现成的向量库就行。**为什么要分开？**因为建索引要慢（要跑神经网络），但检索要快（要毫秒级返回）——你不能在建索引的同时让用户等。**判据**：这就是为什么索引流水线要分离线和在线——离线是"建房子"（后台慢慢跑），在线是"住房子"（用户提问时快查）——两者必须分开。**踩坑**：①以为"索引流水线是一个连续的流程"——错，它要分离线和在线两部分；②以为"在线检索也要跑Embedding"——错，在线检索只查向量库，不跑Embedding。

**为什么索引流水线是RAG的地基——地基打不好，上面盖什么都白搭**：很多人会问——"RAG不就是'检索+生成'吗？为什么说索引流水线是地基？"关键在于：**地基打不好，上面盖什么都白搭**——①**索引流水线做了什么**：它把你的原始文档（PDF、Word、网页）变成了一个"能搜的向量库"——这是RAG的基础；②**地基打不好会怎样**：如果你切片切得不好（太长或太碎），检索就不准；如果你Embedding模型选得不好，向量就不准；如果你入库时没带元数据，检索出来的东西就乱——这些都是"地基没打好"的问题；③**为什么它是地基**：因为检索找得准不准，直接取决于索引建得好不好——你索引建得好，检索就准；你索引建得不好，检索就不准——后面的生成（LLM）再厉害也没用。**判据**：这就是为什么索引流水线是RAG的地基——地基打不好，上面盖什么都白搭。**踩坑**：①以为"RAG的核心是LLM"——错，LLM已经很厉害了，核心是"能不能建好索引、检索出相关的资料给它"；②以为"索引流水线随便弄弄就行"——错，它是地基，地基打不好，后面全白搭。

**为什么索引流水线是RAG系统的"第一公里"——它决定了后面所有环节的上限**：很多人会问——"RAG有那么多环节（索引、检索、重排、生成），为什么说索引流水线是第一公里？"关键在于：**它决定了后面所有环节的上限**——①**检索的上限由索引决定**：你索引里存的是什么样的chunk，检索出来的就是什么样的——如果你索引里存的是"500字一块的碎块"，检索出来的就是碎块；如果你索引里存的是"整篇文档"，检索出来的就是整篇文档——检索再好，也不可能从碎块里检索出整篇文档；②**重排的上限由索引决定**：重排器是对检索出来的候选做精排——但如果候选里根本没有正确答案，重排再厉害也没用；③**生成的上限由索引决定**：LLM是根据你喂给它的资料来回答的——你喂给它的资料是对的、全的，它就能答好；你喂给它的资料是错的、缺的，它就答不好——而喂给它的资料，就是从索引里检索出来的。**判据**：这就是为什么索引流水线是RAG系统的第一公里——它决定了后面所有环节的上限：检索再好，也不可能从碎块里检索出整篇文档；重排再厉害，也不可能从没有正确答案的候选里挑出正确答案；LLM再聪明，也不可能从错误的资料里生成正确的答案。**踩坑**：①以为"RAG的优化重点在LLM"——错，LLM已经很厉害了，优化重点应该在索引；②以为"索引建好了就不用动了"——错，文档在更新、Embedding模型在进步，索引要定期优化。

**为什么"索引要做流水线"——文档太多了，你要一步一步来**：很多人会问——"索引不就是'把文档变成向量、存进数据库'吗？为什么要做流水线？"关键在于：**索引要做流水线——文档太多了，你要一步一步来**——①**索引流水线是干什么的**：它是一个"把文档变成向量、存进数据库"的流程；它一步一步来——先切片、再embedding、再存进数据库；它像工厂的流水线——每一步做一件事，一步接一步；②**为什么要做流水线**：因为文档太多了——你要处理1万篇文档；你要一步一步来——你不能一下子全处理完；你要做流水线——先切片、再embedding、再存进数据库；③**为什么这是关键**：因为"一步一步来"就是"能不能处理完"的区别——你不做流水线，你一下子全处理完，你处理不完；你做流水线，你一步一步来，你就能处理完。**判据**：这就是为什么索引要做流水线——文档太多了——你要处理1万篇文档——你要一步一步来——你要做流水线——这就是为什么索引要做流水线。**踩坑**：①以为"索引就是一下子全处理完"——错，文档太多了，你要一步一步来；②以为"流水线是多余的"——错，流水线是必须的——你不做流水线，你就处理不完这么多文档。

### 本章要点

- chunk 大小甜点 300–500 字（本机实算：100 字召回 65%/精准 55%，500 字 88%/82%，1500 字 78%/65%）——太小丢上下文、太大一块混多主题致语义稀释；FAQ 与技术手册最优块长不同，别全库定死一个值。
- embedding 模型输入上限约 512 token：10000 token 的文档不切片时只有前 5% 内容可被检索到，等于白存；切片的收益随文档长度放大。
- 重叠取块长的 10–20%（如 500 字块重叠 50–100 字），兜住跨边界句子即可；重叠加到 50% 等于同样内容存两遍，索引翻倍、检索重复占上下文。
- 表格逐行文本化、代码按函数边界切、公式连同解释句整块保留；每个块必带元数据（文档 ID + 块序号 + 来源/权限/时间）——溯源、范围过滤、增量替换全靠它，丢了元数据的块命中了也回不到原文。
- 索引流水线里 Embedding 最耗时（20 万块约 0.6 小时），离线建索引与在线毫秒级检索必须分开；文档更新走增量（按文档 ID 精准删旧块插新块），全库重建只在切换 embedding 模型时才值得。

## 第7.3章 召回、重排与融合检索（对应 7.3）

第2章把文档变成了好向量，本章解决"查出来之后怎么办"：两阶段（双塔粗召回 + cross-encoder 精排）的分工、Top-k 的取舍、BM25 与向量路的混合检索及 RRF 融合。读完能为给定延迟预算搭检索漏斗（100 万条全库精排约 167 分钟 vs 两阶段约 11 秒），按重排分数的断崖决定留几条而非机械取 Top-5，并判断编号/型号类查询该走哪一路、混合检索有没有真收益（看两路 Top-k 重叠度）。检索结果拿到手之后怎么防幻觉、怎么引用证据，是第4章的事。

### 7.3.1 两阶段：粗召回 + 精排

**【架构设计说明】**

单靠向量召回不够准。工业界标准是**两阶段**：
1. **召回（recall）**：向量 ANN 快速从百万库里捞出 Top-50~100 个候选，追求"别漏掉相关的"；
2. **重排（rerank）**：用一个更强大的跨编码器（cross-encoder）对这 50 个候选精排，只留最相关的 Top-3~5。

**重排后到底留几个、阈值怎么定**：不是固定留 5 个，而是看"重排分数的断崖"——把重排后的候选按分数排开，如果前 3 个分数很高、第 4 个突然断崖式下跌，那留前 3 个就够了；如果前 8 个分数都咬得很紧，那就得多留。**工程做法**：①按上下文窗口预算定上限（别超窗口）；②设一个相关性分数阈值，低于阈值的一律不喂（哪怕它排第 1）。**判据**：机械地"永远留 Top-5"会带进噪声；看分数分布+卡阈值，才能既不漏关键证据、又不塞无关内容。这个阈值要拿真实查询集反复调，没有万能值。

**为什么要两阶段**：向量编码器把 query 和文档**分开**编码（快，但交互浅）；重排器把 query 和文档**拼在一起**过一个模型（慢，但能细粒度判断相关性）。先用快的缩小范围，再用慢的精排，兼顾速度与精度。

**两阶段到底快多少——为什么不能直接精排全部（本机实算）**：很多人会问——"既然精排更准，为什么不直接对全部文档精排？"关键在于：**精排太慢了**。本机算一笔账——假设库里有100万条文档：

| 方案 | 怎么做 | 耗时 |
|---|---|---|
| 直接精排全部 | 100万条都过cross-encoder | **10000秒（约167分钟）** |
| 两阶段 | 先粗召回100条（向量检索），再精排这100条 | **11秒** |

**判据**：两阶段比直接精排快了**约900倍**！为什么？因为——①粗召回（向量检索）是"分开编码"——query只编码一次，然后和库里所有文档的向量算个内积就行，极快；②精排（cross-encoder）是"拼在一起编码"——query和每条文档都要拼起来过一遍模型，极慢。**这就是为什么要两阶段——先用快的粗召回把范围从100万缩到100，再用慢的精排把这100条排准**。**踩坑**：①以为"精排越准越好，干脆全精排"——错，100万条精排要跑167分钟，用户早跑了；②以为"粗召回够准了，不用精排"——错，粗召回是"分开编码"，它只知道"语义大概相近"，不知道"到底有多相关"，精排才能把"真正相关的"从"大概相关的"里挑出来。

**为什么"要两阶段"——你不能直接精排100万条，太慢了**：很多人会问——"为什么不直接精排？直接精排不就最准了吗？"关键在于：**要两阶段——你不能直接精排100万条，太慢了**——①**两阶段是干什么的**：两阶段是"先粗召回，再精排"；它是一个"让检索又快又准"的方法；第一阶段从100万条里粗召回100条，第二阶段从这100条里精排；②**为什么要两阶段**：因为你不能直接精排100万条——太慢了，要167分钟；因为你要先粗召回100条——很快，只要几秒；因为然后你再精排这100条——很快，只要几秒；③**为什么这是关键**：因为"能不能又快又准"就是"RAG好不好用"的区别——你不能又快又准，你就不好用；你能又快又准，你就好用。**判据**：这就是为什么要两阶段——你不能直接精排100万条——太慢了，要167分钟；你要先粗召回100条——很快，只要几秒；然后你再精排这100条——很快，只要几秒。**踩坑**：①以为"直接精排最准，不用两阶段"——错，太慢了；②以为"两阶段太麻烦"——错，它是"又快又准"的标准做法。

**双塔 vs 交叉编码器（cross-encoder）的本质区别**：
- **双塔（bi-encoder，召回用）**：query 编码成向量、文档也独立编码成向量，算余弦。文档向量可离线预算好，所以百万级库也快。代价是 query 和文档在编码阶段"不见面"，只能粗排。
- **交叉编码器（cross-encoder，重排用）**：把 `[query, 文档]` 拼在一起喂进一个模型，直接输出一个相关性分数。query 和文档在注意力层充分交互，准得多；但因为每个候选都要现场算一遍，慢——所以只对召回的 Top-50 用它。

**踩坑**：别一上来就用 cross-encoder 直接对全库打分——那是 \(N\) 次前向传播，慢到不可用；它必须架在快速召回之后。

**两阶段为什么是"快粗排 + 慢精排"的最优分工（一张表）**：
| 阶段 | 用什么模型 | query 与文档是否交互 | 速度 | 精度 | 处理规模 |
|---|---|---|---|---|---|
| 粗召回 | 双塔 bi-encoder | 否（各自编码） | 极快（文档可离线预计算） | 中 | 全库百万级 |
| 精重排 | 交叉编码器 cross-encoder | 是（拼一起过注意力） | 慢（每候选现场算） | 高 | 只对召回的 Top-50 |

**为什么这个组合是性价比最优**：全库直接用 cross-encoder 精排，准是准但慢到不可用；全库只用 bi-encoder，快但粗、漏召多。正确打法就是"先用快的把范围从百万压到几十，再用准的在几十里精挑"——这是信息检索几十年沉淀下来的标准两段式。**判据**：你的 RAG 如果只做向量召回、不加重排，那召回的 Top-5 里很可能混着"语义沾边但并不切题"的文档；加一层 cross-encoder 重排，往往是不换 embedding 模型就能提质量的最便宜一招。

**为什么必须"双塔召回 + 交叉编码器重排"（成本对比）**：设库里有 100 万篇文档。双塔模式下，100 万篇文档的向量**预先算好存库**，来一个 query 只需现算 1 次 query 向量、再和库里 100 万个向量做内积——总代价≈1 次前向 + 100 万次向量乘法。交叉编码器模式下，每篇文档都要和 query 拼起来现场过一遍模型，100 万篇就是 100 万次前向传播，慢上百倍。所以：**快的双塔负责从百万里粗筛 50 个，准的交叉编码器只对这 50 个精排**——慢工具用在刀刃上。

**为什么两阶段是信息检索的标准做法——几十年的经验沉淀，不是随便拍脑袋**：很多人会问——"两阶段是不是最近才发明的？为什么大家都这么做？"关键在于：**两阶段是信息检索几十年的经验沉淀，不是随便拍脑袋**——①**以前怎么做的**：在向量检索还没流行的时代，大家做的就是"先用BM25关键词检索粗筛几百条，再用人工标注的相关性模型精排"——这就是两阶段；②**现在怎么做的**：把BM25换成了向量检索（粗召回），把人工相关性模型换成了cross-encoder（精排）——但"先粗筛、再精排"这个思路没变；③**为什么它是标准**：因为它解决了一个根本矛盾——"要准就要慢、要快就不准"——你不可能同时又快又准，所以只能分两步：先用快的把范围缩小，再用准的仔细排。**判据**：这就是为什么两阶段是信息检索的标准做法——几十年的经验沉淀，解决了"要准就要慢、要快就不准"这个根本矛盾。**踩坑**：①以为"两阶段是向量检索发明后才有的"——错，几十年前就有了，只是工具换了；②以为"以后技术发展了就能一步到位"——错，"要准就要慢、要快就不准"这个矛盾永远存在，两阶段永远是最优解。

**为什么"要分两阶段——粗召回+精排"——粗召回要快，精排要准**：很多人会问——"为什么要分两阶段？直接精排一遍不行吗？"关键在于：**要分两阶段——粗召回要快，精排要准**——①**为什么要做粗召回**：你有100万条文档——你不可能每条都精排一遍——粗召回是"快速筛一遍"——它从100万里快速筛出1000条可能相关的——它要快——它不追求准，它只追求快；②**为什么要做精排**：粗召回筛出了1000条——你要从这1000条里精排出最相关的10条——精排是"仔细比一遍"——它用更复杂的模型，从1000条里精排出最相关的10条——它要准——它不追求快，它只追求准；③**为什么要分两阶段**：因为"要准就要慢、要快就不准"——你不可能同时又快又准——你只能分两步：先用快的把范围缩小，再用准的仔细排——粗召回要快，精排要准——这就是为什么要分两阶段。**判据**：这就是为什么要分两阶段——粗召回是"快速筛一遍"——它从100万里快速筛出1000条；精排是"仔细比一遍"——它从1000条里精排出最相关的10条——粗召回要快，精排要准——这就是两阶段的意义。**踩坑**：①以为"直接精排一遍就行"——错，100万条精排一遍太慢了，你等不起；②以为"粗召回不用准"——错，粗召回虽然不追求准，但它也不能太不准——太不准了，精排也救不回来。

### 7.3.2 Top-k 召回的权衡（本机实算）

**【已工程验证】**

构造 50 个文档库，query 与其中 3 篇真相关。实测不同 k 的召回率：
| k | Recall@k（命中真相关数/3） |
|---|---|
| 1 | 0.33 |
| 3 | 0.33 |
| 5 | 0.33 |
| 10 | 0.67 |

**结论**：k 越大召回越全，但也带进越多无关片段。这就是为什么需要**重排**把 Top-50 里的噪声再筛掉——召回阶段宁可多捞，精排阶段负责去噪。**踩坑**：k 设太小会漏关键证据；太大则把无关内容塞进 prompt，既费 token 又误导 LLM。

**k 到底选多大——Recall 和 Precision 的跷跷板（本机实算）**：很多人问——"Top-k 的 k 到底设几？"关键在于：**k 是个跷跷板——k 太小漏了相关文档（Recall低），k 太大混进不相关文档（Precision低）**。本机模拟：100条文档里有5条真相关，检索时真相关的排在前面但不是完美排序——

| k | Recall（捞回了几条真相关） | Precision（捞回来的里有几条是真相关） |
|---|---|---|
| 1 | 20%（只捞回1条） | 100%（捞回来的都是对的） |
| 3 | 60%（捞回3条） | 100%（捞回来的都是对的） |
| 5 | 60% | 60%（捞回5条里只有3条是对的） |
| 10 | 60% | 30%（捞回10条里只有3条是对的） |
| 20 | 80% | 20%（捞回20条里只有4条是对的） |

**判据**：k=5 是甜点区——Recall 够高（60%）、Precision 也还可以（60%）。k 太小（1-3）漏太多，k 太大（10-20）混进太多噪声、挤占 prompt 空间。**踩坑**：①k 设成 1——太激进，容易漏掉关键证据；②k 设成 50——太松，混进一堆不相关文档，LLM 看了反而被带偏。**记住：k=5 是默认甜点，特殊场景再调——要召回全一点就 k=10，要精准一点就 k=3**。

**为什么k=5是甜点区——不是拍脑袋，是算出来的（本机实算）**：很多人会问——"为什么偏偏是5？不是3？不是10？"关键在于：**k的选择取决于"真正相关的文档有几条"**。本机算一笔账——假设你的查询真正相关的文档有3条：

| k | Recall | Precision | 说明 |
|---|---|---|---|
| 1 | 33% | 100% | 只捞回1条，漏了2条 |
| 3 | 100% | 100% | 刚好捞回全部3条 |
| 5 | 100% | 60% | 捞回3条相关+2条噪声 |
| 10 | 100% | 30% | 捞回3条相关+7条噪声 |

**判据**：如果真正相关的文档有3条，k=3刚好；如果真正相关的文档有10条，k=10才够。**这就是为什么k=5是"通用甜点"——大部分查询的相关文档在3-10条之间，k=5能覆盖大部分场景**。**踩坑**：①以为"k越大越好"——错，k=50会混进40多条噪声，LLM看了反而被带偏；②以为"k越小越好"——错，k=1太激进，容易漏掉关键证据。

**RRF 融合完，为什么通常还要再叠一层重排——融合只是"排个大概"，精排才定生死**：很多人以为"向量路+BM25路用 RRF 融合完就完事了"。其实 RRF 干的活是**粗排**——它只是把两路结果按名次揉成一个大致顺序，让"两路都靠前的"冒出来。但这个顺序还是粗的：①RRF 只看"排第几名"，根本不知道"这个文档到底和问题多相关"；②它把两路的 Top-50 揉完，可能还是 50 个候选，你得从中挑 3~5 个喂 LLM。**判据**：所以成熟管线是**三段式**——向量召回 + BM25 召回 →（RRF 融合去重、凑出 Top-50）→（cross-encoder 重排精挑 Top-5）。RRF 负责"把两路结果合并、别让任何一路漏掉好文档"，重排负责"在这 50 个里精确挑出最切题的那 5 个"。**踩坑**：①以为 RRF 融合完就够、不加重排——那 50 个候选里还是混着"语义沾边但跑题"的，喂给 LLM 的前几条质量上不去；②跳过 RRF 直接拿单路 Top-50 去重排——那就浪费了"另一路能捞回单路漏掉的好文档"这个互补机会。**一句话：RRF 解决"两路怎么合"，重排解决"合完之后哪几个最该喂给 LLM"**——两个是接力、不是二选一。

**为什么Top-k是检索的核心参数——它直接决定了"召回多少、精度多少"**：很多人会问——"检索系统有那么多参数（embedding模型、向量库、重排器），为什么说Top-k是核心？"关键在于：**Top-k直接决定了"召回多少、精度多少"**——①**它直接影响召回率**：k设成1，你只能捞回最像的那1条——如果真正相关的有5条，你就漏了4条；k设成10，你能捞回更多——但混进来的噪声也多；②**它直接影响精度**：k设成1，捞回来的那1条大概率是对的（精度高）；k设成50，捞回来的50条里可能只有5条是对的（精度低）；③**它直接影响LLM的输入质量**：你捞回来的这k条文档，就是LLM要看着回答的资料——你捞回来的质量高，LLM回答就好；你捞回来的质量低（混了很多噪声），LLM回答就差。**判据**：这就是为什么Top-k是检索的核心参数——它直接决定了"召回多少、精度多少"，也就直接决定了LLM的输入质量。**踩坑**：①以为"Top-k随便设就行"——错，它直接影响召回率和精度；②以为"embedding模型最重要"——错，embedding模型再好，k设错了也白搭。

**为什么"Top-k是检索的核心参数"——它直接影响召回率和精度**：很多人会问——"Top-k不就是'从检索结果里取前k个'吗？为什么它这么重要？"关键在于：**Top-k是检索的核心参数——它直接影响召回率和精度**——①**Top-k是干什么的**：Top-k是"从检索结果里取前k个"；它是一个"决定检索多少结果"的参数；它直接影响召回率和精度；②**为什么Top-k是核心参数**：因为它直接影响召回率——k设成1，你只能捞回最像的那1条；因为它直接影响精度——k设成1，捞回来的那1条大概率是对的；因为它直接影响LLM的输入质量——你捞回来的这k条文档，就是LLM要看着回答的资料；③**为什么这是关键**：因为"召回多少、精度多少"就是"检索够不够用"的区别——你召回太少，你就漏掉了相关的文档；你精度太低，你就混进了噪声——你都不行。**判据**：这就是为什么Top-k是检索的核心参数——它直接影响召回率——k设成1，你只能捞回最像的那1条；它直接影响精度——k设成1，捞回来的那1条大概率是对的；它直接影响LLM的输入质量——你捞回来的这k条文档，就是LLM要看着回答的资料。**踩坑**：①以为"Top-k随便设就行"——错，它直接影响召回率和精度；②以为"embedding模型最重要"——错，embedding模型再好，k设错了也白搭。

**为什么"Top-k召回要权衡"——k太小漏了相关文档，k太大混进不相关文档**：很多人会问——"Top-k不就是'取最相似的k条'吗？为什么要权衡？"关键在于：**Top-k召回要权衡——k太小漏了相关文档，k太大混进不相关文档**——①**k太小会怎样**：你设k=1——你只取最相似的那1条；如果真正相关的有5条，你就漏了4条；你漏了相关文档，你就答不好；②**k太大会怎样**：你设k=50——你取最相似的那50条；这50条里可能只有5条是对的；你混进了很多不相关文档，大模型反而被噪声带偏；③**为什么要权衡**：因为"召回率"和"精度"是一个跷跷板——k太小，召回率低（漏了相关文档）；k太大，精度低（混进了不相关文档）；你要找一个平衡点——k既不要太小，也不要太大——这就是为什么Top-k召回要权衡。**判据**：这就是为什么Top-k召回要权衡——k太小漏了相关文档，k太大混进不相关文档——你要找一个平衡点——k既不要太小，也不要太大——这就是为什么Top-k召回要权衡。**踩坑**：①以为"k越大越好"——错，k太大混进了不相关文档，大模型反而被噪声带偏；②以为"k越小越好"——错，k太小漏了相关文档，你就答不好。

### 7.3.3 混合检索：向量 + 关键词

**【架构设计说明】**

向量检索擅长"语义相近"，但遇到**专有名词、编号、罕见词**（如"型号 XK-2039"）时，关键词精确匹配（BM25）反而更准。**混合检索（hybrid search）**：同时跑向量检索和 BM25，把两路结果融合（常用 RRF，Reciprocal Rank Fusion），兼得语义与精确。

**BM25 在算什么（直觉公式）**：一段文档对查询词的 BM25 分 ≈ Σ(查询词在文档里出现次数的饱和贡献 × 这个词的"稀有程度")。两个关键直觉：①**词频饱和**——一个词在一篇文档里出现 10 次，不代表得分就是出现 1 次的 10 倍，而是很快饱和（出现越多边际收益越低），避免长文档靠堆词占便宜；②**IDF 稀有度加权**——"的/是"这种到处都是的词，几乎不贡献分；"XK-2039"这种只在少数文档出现的词，权重极高。这就是为什么查编号、型号、人名时 BM25 远胜语义检索——它奖励"稀有关键词命中"。

**为什么查"XK-2039"这种编号，BM25 比语义检索强——语义模型根本不知道编号是啥**：你查"XK-2039 怎么退货"，语义检索（embedding）会怎么处理？它会把这句话变成一个向量，然后找"语义最接近"的文档。可问题是——**"XK-2039"这个编号，对语义模型来说就是一串无意义的字符**，它不知道这是个型号、也不知道它重要。它算出来的向量，和"XK-2040""XK-2038"几乎一模一样——因为这些编号在语义空间里长得太像了（都是"字母+数字"的字符串）。结果就是：语义检索可能把"XK-2040 的退货政策"排在"XK-2039 的退货政策"前面——它根本分不清这俩编号的区别。而 BM25 呢？它是**精确匹配**——你查"XK-2039"，它就找文档里**真的出现了"XK-2039"这串字符**的那篇，出现一次就给一次分，出现得越准排得越前。**判据**：所以查编号、型号、人名、日期这种"精确字符串"时，BM25 完胜语义检索——因为它做的是"字符级精确匹配"，而语义模型做的是"意思相近就好"，可编号这东西，意思相近没用、必须精确对上。**踩坑**：①全用语义检索——查个产品编号都能给你找错型号，因为它分不清 XK-2039 和 XK-2040；②全用 BM25——查"怎么把退了的钱拿回来"这种"意思相近但用词不同"的问题，BM25 又匹配不上（文档里写的是"退款流程"不是"把钱拿回来"）。**记住：BM25 和语义检索是互补的——查精确编号/型号用 BM25，查意思相近的问题用语义，实际系统里常常两个都跑、再用 RRF 把结果融合**。

**【已工程验证】BM25 的两个旋钮到底差多少（本机实算）**：设语料 N=1000 篇。①**IDF 稀有度**——某词只在 10 篇出现（n=10），IDF≈4.56；在 500 篇都出现（n=500），IDF 只剩 0.69。**差了 6.6 倍**——这就是"XK-2039"这种编号命中一下就把分拉满、而"的"命中等于没命中的原因。②**文档长度归一化**——同一个词频 f=3、同一段内容，放在短文档（dl=200）里贡献≈8.94，放在超长文档（dl=1000）里降到≈6.08。**判据**：BM25 故意"惩罚长文档"——一篇 10 倍长的文档不该因为偶然多出现几次词就排前面，长度归一化（参数 b 控制）把这个偏差压掉。这两个旋钮（k1 控词频饱和、b 控长度惩罚）就是 BM25 比老式 TF-IDF 好用的地方：TF-IDF 词频不封顶、长文档容易作弊，BM25 都修正了。

**为什么"的、是、和"这种词命中了等于白命中（IDF 怎么把它们压到零）**：本机实算（语料 N=1000 篇）——一个词只在 10 篇出现，IDF≈4.56；在 50 篇出现，IDF≈2.99；在 100 篇出现，IDF≈2.30；在 500 篇出现，IDF≈0.69；在 900 篇出现（几乎篇篇都有），IDF≈**0.11**。**看最后这行**——一个 90% 的文档里都出现的词，它的 IDF 被压到几乎是 0。这正是设计意图：这种词（"的/是/和"）出现在几乎所有文档里，对"区分哪篇更相关"毫无信息量——你查"差旅报销"，"和"字在 900 篇文档里都有，命中它根本说明不了任何问题，所以 IDF 把它压成接近 0，等于让它在打分里消失。**判据**：IDF 的本质是"按这个词的区分能力给权重"——越稀有（只在少数文档出现）的词，命中它越能把"就是这篇"锁定；越常见的词，命中它越说明不了什么，权重越低直到趋近 0。**踩坑**：这也是为什么 BM25 要先做"停用词过滤"——把"的/是/了"这种本来就该是 0 的词直接从索引里去掉，省得它们白占位置、还偶尔带点噪声。

**中文为什么 BM25 之前必须先"分词"——英文靠空格、中文没有空格**：BM25 是按"词"来算词频的——一个词在文档里出现几次，就贡献多少分。可问题来了——**英文天然有空格把词分开**（"cat dog"就是 cat 和 dog 两个词），但**中文没有空格**——"差旅报销流程"这串字，机器怎么知道它是"差旅/报销/流程"三个词、还是"差旅报销/流程"两个词？**判据**：所以中文 BM25 之前必须先做**分词**（用 jieba 这类分词工具，把"差旅报销流程"切成"差旅 / 报销 / 流程"三个词），然后才能按词算词频、算 IDF。不分词直接按字切，"报"和"销"被当成两个独立词，检索"报销"时匹配得一塌糊涂。**踩坑**：①中文 BM25 效果差，十有八九是分词没做好——把"报销"切成"报/销"两个字，IDF 和词频全乱了；②英文 BM25 不用这一步（空格天然分词），这就是为什么 BM25 这套技术在英文上"开箱即用"、在中文上还得先接一个分词器。**记住：BM25 在中文上好不好用，一半功夫在分词上**——分词准，检索才准。

**英文虽然有空格，也还得做"词干提取"——不然 "run/running/ran" 被当成三个不同的词**：英文靠空格分词看似省事，但它有自己的麻烦——**同一个意思会有好几种词形**。你查 "run"，文档里写的是 "running" 或 "ran"——BM25 是按"精确词"匹配的，它会把 "run"、"running"、"ran" 当成**三个毫不相干的词**，于是你查 run，写着 running 的文档就匹配不上。这就是为什么英文 BM25 之前还要做一步**词干提取（stemming）**——把 running、ran、runs 都归约到同一个词根 "run"。**判据**：所以英文检索的预处理是"空格分词 + 词干提取"，中文是"分词"——本质都是同一个目的：**把"同一个意思的不同写法"归并成一个可匹配的单位**。英文是"词形变化多"（run/running/ran），中文是"没有词边界"（差旅报销流程怎么切），各有各的预处理要做。**踩坑**：①以为英文有空格就万事大吉——不做词干提取，查 "refund" 时写着 "refunding" 的文档就漏了；②词干提取太狠——把 "university" 和 "universe" 都砍成 "univ"，硬凑成一个词，反而引入错误匹配。**记住：不管中英文，BM25 之前都得先做"把意思相同的写法归并"的预处理——中文叫分词，英文叫词干提取，目标是同一个**。这一步做不好，后面打分再精细也是空中楼阁。

**长度归一化里的 b 到底在调"惩罚长文档"有多狠（本机实算）**：BM25 的长度项 \(K = k_1(1-b+b\cdot dl/dl_{\text{avg}})\)，b 是"长度惩罚力度"的开关。本机算（k1=1.5、平均文档长 500、词频 f=3）：文档长 200（短）时贡献≈3.92、长 500（平均）时≈3.33、长 1000（长）时≈2.67——**文档越长、同一次命中的得分被压得越低**。①**b=1**：完全按长度归一化，长文档被压得最狠（短文档占优）；②**b=0**：完全不管长度，长文档和短文档同词频同得分（不做长度惩罚）；③**默认 b=0.75**：折中——既惩罚长文档的作弊，又不完全剥夺长文档"内容多"的合理优势。**判据**：b 的取值要看你的语料特点——①如果文档长短差异极大（几行的便签和几十页的报告混在一起），b 往大调（0.8–0.9），防长文档靠篇幅作弊；②如果文档都差不多长（如问答对、新闻短讯），b 往小调（0.3–0.5），因为本来就没什么长度偏差要纠。**踩坑**：很多人把 b 当默认 0.75 万年不动——但你的语料若全是等长文档，硬套 0.75 等于无的放矢；若长短悬殊却用 0.3，长文档照样靠篇幅霸榜。b 是"语料里长度偏差有多大"的调节器，不是魔法常数。

**词频"饱和"到底怎么个反作弊法（本机饱和曲线）**：BM25 对词频 f 的处理是 \(f(k_1+1)/(f+k_1)\)（取 k1=1.5）。本机算——f=1 贡献 1.00、f=2 贡献 1.43、f=3 贡献 1.67、f=5 贡献 1.92、f=10 贡献 2.17、f=50 贡献 2.43。**看这条曲线**：词频从 1 涨到 50 倍，贡献只从 1.0 涨到 2.4——**早就压平了**。这正是它反作弊的核心：老式 TF-IDF 里词频是线性的，一篇文档把"报销"堆 50 次，分就涨 50 倍——一篇充斥关键词的水文就能霸榜；BM25 里"报销"出现第 1 次和第 50 次，得分几乎没差。**判据**：BM25 承认"一个词命中一次"就足够表达相关性了，多命中只是冗余——这逼着文档靠"命中了对的关键词"得分，而不是靠"把关键词写一万遍"刷分。**踩坑**：有人嫌 BM25 还不够狠，把 k1 调得特别小（饱和得更早），结果连"一个词真的很重要、该多次强调"的正常文档也被压平了——k1 是"饱和多早"的旋钮，要按语料特点调，不是越小越好。

**为什么都向量时代了 BM25 还没死——它在"精确词匹配"上有向量补不上的短板**：现在都在聊向量检索，很多人觉得 BM25 老古董该淘汰了。但现实是——**RAG 里几乎都是 BM25 和向量检索一起用（混合检索），谁也离不开谁**。为什么？因为向量检索有个天生的盲区：它擅长"语义相近"，但**不擅长"精确字符串匹配"**。举个要命的例子——你查"XK-2039 这个型号怎么退款"，向量检索会把它匹配到"某款类似产品的退款说明"（语义像），但**那个真正写着"XK-2039"的文档**，向量检索反而可能排不上前——因为型号编号"XK-2039"在语义上没什么含义，向量表示很模糊。而 BM25 是**精确词匹配**——你写了"XK-2039"，它就死磕"哪篇文档里出现了这串精确字符"，一抓一个准。**判据**：所以混合检索的分工是——①**BM25 管"精确词/编号/术语"**：型号、代码、人名、专有名词，必须字字对上；②**向量检索管"语义意思"**：意思相近但用词不同的问题（用户口语 vs 文档书面语）。两路各搜各的，再用 RRF 融合——既不漏掉"精确匹配命中的那篇"，也不丢掉"语义相近的那些篇"。**踩坑**：①只上向量检索——遇到"型号/报错码/缩写"这种精确查询就抓瞎，因为向量对"无意义字符串"没有区分度；②只上 BM25——遇到"用户用大白话问、文档用书面语答"（词不重合）就全漏了。**记住：BM25 不是被淘汰的旧技术，它是向量检索补不了的那一半——"精确词匹配"的专职选手**。这就是为什么混合检索（BM25+向量）是今天 RAG 的标配。

**BM25 到底比 TF-IDF 强在哪——它修正了 TF-IDF 的两个作弊漏洞**：TF-IDF 是更早一代的关键词打分法，它有两个明显漏洞，BM25 就是专门补这两个洞的——①**漏洞一：词频不封顶**。TF-IDF 里一个词出现 50 次，分就是出现 1 次的 50 倍——于是一篇文档只要把关键词使劲堆（SEO 水文），就能把分刷得很高。BM25 加了"词频饱和"（前面那条曲线），出现第 1 次和第 50 次得分几乎一样，直接把"堆词刷分"这条路堵死；②**漏洞二：不惩罚长文档**。TF-IDF 里一篇 10 倍长的文档，天然比短文档有更多机会"碰巧"命中查询词，于是长文档总是占便宜。BM25 加了"长度归一化"（参数 b），故意把长文档的得分压一压，让它不能靠篇幅作弊。**判据**：所以 BM25 = TF-IDF 的"反作弊升级版"——它保留了 TF-IDF 的核心思想（词频×稀有度），但补上了"别让堆词作弊、别让长文档占便宜"这两道。**踩坑**：现在还有人手写 TF-IDF 做检索——除非是极简玩具，否则直接用 BM25，那两个漏洞在真实业务数据里会被放大得很明显（长文档霸榜、堆关键词的水文排前面）。**记住：BM25 不是什么高深新算法，就是 TF-IDF 加了两道"反作弊补丁"——而这两道补丁恰恰是真实检索质量的关键**。

**为什么 BM25 之前要先做停用词过滤——把"零信息量的词"提前清场**：BM25 里"的/是/和/了/在"这些词，IDF 已经被压得接近 0 了（前面算过，90% 文档都有的词 IDF≈0.11）。既然它们几乎不贡献分，为什么还要专门做一步"停用词过滤"把它们删掉？三个原因——①**省存储**：这些词在每篇文档里都出现，留着它们等于给每篇文档都存一堆没用的索引条目，白白占空间；②**省算力**：查询里要是带了"的"，BM25 还得拿这个"零分词"去索引里翻一遍、算一遍分，纯属浪费——过滤掉之后，查询进来先把这些词剔掉，只拿真正有意义的词去检索；③**避免噪声**：虽然 IDF 压到接近 0，但不是绝对的 0，一点点残留权重偶尔会把"因为带了某个停用词"的文档轻微抬高，干脆删掉最干净。**判据**：所以中文 BM25 的标准预处理是——**分词 → 去停用词 → 再算词频和 IDF**。把"的/是/和"这种零信息量的词提前清掉，索引小、查询快、结果还更准。**踩坑**：①不过滤停用词直接查——查询"报销的流程"里那个"的"也被拿去匹配，等于多算了一个毫无意义的词；②停用词表太狠——把"产品""流程"这种其实有意义的词也当停用词删了，那检索就漏了。停用词表要精（只删真·零信息量的虚词），不能滥。**记住：停用词过滤不是可有可无的小动作，它是"先把没信息的词清场，再让真正有区分度的词上场"的预处理——清得越干净，后面的打分越聚焦**。

**RRF 怎么融合（本机实算）**：两路各出一个排序列表，RRF 不给文档打"绝对分"，只按"它在每路里排第几名"打分：
\[
\mathrm{RRF}(d)=\sum_{\text{各路 }r}\frac{1}{k+\mathrm{rank}_r(d)},\quad k=60\text{（常数）}
\]
本机算例：向量路排序 = A,B,C,D；BM25 路 = B,A,E,C。融合后 RRF 分：A=0.0325、B=0.0325（两路都靠前，并列第一）、C=0.0315、E=0.0159、D=0.0156。**直觉**：在两路都排前面的文档得分最高——这正是"既语义相关、又关键词命中"的理想结果。RRF 不用归一化两路分数（两者量纲不同），只比排名，工程上特别省心。

**常数 k（常用 60）是干嘛的**：它是一个"软化项"，避免排名第 1 的文档得分过于碾压后面的。k 越大，"排第 1"和"排第 10"的分差越小（各路更平等）；k 越小，头部文档越占优。工程上 k=60 是被反复验证的稳妥默认值，一般不用动——这也是 RRF 省心的原因之一。【待核验：k=60 为常见默认值，确切出处需核对】

**【已工程验证】k 取大取小到底差多少（本机敏感性）**：设文档 A 在两路都排第 1，文档 B 只在一路排第 1，看 k 怎么影响它俩的分差——
| k | A 得分 | B 得分 | A/B 倍差 |
|---|---|---|---|
| 1 | 1.000 | 0.500 | 2.00 |
| 10 | 0.182 | 0.091 | 2.00 |
| 60 | 0.033 | 0.016 | 2.00 |
| 1000 | 0.002 | 0.001 | 2.00 |

**判据**：其实对"都是第 1"的相对比较，k 不改变倍差（永远是 2 倍）；k 真正起作用的是**拉开"第 1"和"第 100"这种长尾名次的分差**——k 越小，\(1/(k+1)\) 和 \(1/(k+100)\) 差得越悬殊（头部通吃）；k 越大，这两个越接近（长尾也有机会）。**为什么默认 60 而不是 1**：若 k=1，一个文档在某一路排第 1（得分 0.5）会几乎碾压另一路排第 30（1/31≈0.03），融合结果被"某一路的第一名"绑架；k=60 把这种碾压压平，让"两路都中等靠前"的文档也能冒头。**踩坑**：k 不是越大越好——k 过大，所有名次分数趋同，RRF 就退化成"随便排"、失去区分度。60 这个折中值在多数检索场景被验证够稳，所以当默认。

**为什么 RRF 干脆只用"排名"、不融合原始分数（关键洞察）**：向量检索给的是余弦相似度（0–1），BM25 给的是一个可能 0–30 的打分——**两者量纲完全不同，根本没法直接相加**。你要是硬把"余弦 0.8"和"BM25 25"加起来，就等于把"苹果和橘子"相加，还得费劲设计怎么归一化、配权重，很容易一路分数压过另一路。RRF 的聪明之处是**抛弃分数、只看名次**——不管这路打的分是 0.8 还是 25，它只关心"这个文档在这路里排第几个"。于是两路天然可比，不用调权重。**判据**：RRF 是"懒而稳"的融合——不想折腾归一化和权重时，它几乎总是对的默认选择；这也是为什么混合检索工程界几乎默认用 RRF。

**RRF 什么时候会失灵——两路结果高度重叠时它就白忙**：RRF 的增益完全来自"两路结果不一样、且互补"。如果两路捞回来的 Top-k 是**同一批文档**（比如向量路和 BM25 路都返回了几乎相同的 10 篇），那 RRF 融合等于"把同一份名单加了两遍"——排第 1 的还是那批、新文档一个也没冒出来，融合后的结果和单路检索没差别。**判据**：这也回到前面那条"两路必须异构"的要求——只有当向量路擅长语义、BM25 路擅长度精确、两者捞回不同的文档集合时，RRF 才有"把两路各自漏掉的好文档捞回来"的价值。**踩坑**：很多团队上了混合检索却发现"融合后没比单路好多少"，根因往往是两路高度重叠（比如 BM25 那一路形同虚设、实际两路都在做语义检索）——这时 RRF 再聪明也变不出新信息。所以判断混合检索有没有真收益，先看"两路 Top-k 的重叠度"，重叠越高、RRF 越接近白跑。

**什么时候该给某一路"加权"——别默认两路平等**：标准 RRF 是两路平等相加（各算各的 1/(k+rank)）。但现实里两路不一定一样靠谱——比如你的场景绝大多数是"语义查找"（找意思相近的文档），只有少数是"精确编号匹配"，那向量路明显更重要、BM25 是打辅助的。这时可以给两路的 RRF 分**乘上不同权重**（如向量路 ×1.0、BM25 路 ×0.5），让更靠谱的那路话语权更大。**判据**：两路平等是"谁也不知道谁更靠谱"时的稳妥默认；一旦你有业务证据（比如评测集上向量路明显准），就该把权重往准的那路倾斜。**踩坑**：反过来——如果你场景里"查型号/编号/专有名词"的问题特别多（这是向量的弱项、BM25 的强项），那 BM25 路的权重反而要调高，别因为"向量更先进"就看不起关键词路。权重不是"哪个技术高级"来定，是"哪路在你的真实查询上更准"来定——这又回到"必须在自己的评测集上调参"那条铁律。

**既然两路都要跑，为什么不一路跑两遍凑两路（分工才有意义）**：有人会问——"我把向量检索跑两遍、换两个不同 embedding 模型，不也凑成'两路'给 RRF 融合吗？"关键在于：RRF 的价值来自**两路"擅长的东西不一样"**。①向量路擅长"语义相近"——查"怎么报销差旅费"，它能把"差旅费用报销流程"这种说法不同但意思对的文档捞出来；②BM25 路擅长"字面精确"——查"型号 XK-2039"，它能靠关键词命中精确定位，向量反而可能把它和"XK-2040"搞混。**判据**：两路必须是"异构"的（一个看语义、一个看字面），融合才能互补；如果两路本质是同一个东西的两个变体，它们捞回来的结果高度重叠，RRF 融合等于把同一份结果加了两遍，没有增益。**踩坑**：很多团队上了混合检索却只用两个向量模型、BM25 那一路形同虚设——结果"混合"成了"两路都在做语义检索"，遇到编号、专有名词照样漏，白花了一份算力。真正有效的混合检索，一定是"语义路 + 关键词路"这种本质互补的组合。

**RRF 为什么比"硬归一化两路分数再相加"更皮实——抗分数漂移**：有人会想——"我把余弦和 BM25 各自归一化到 0–1、再加权相加不也行？"理论上行，但工程上有个大坑：**两路的分数分布会随 query 变化、而且漂移不同步**。比如——①向量路：这次 query 很标准，所有文档余弦都集中在 0.7~0.9（高分挤在一起）；下次 query 很模糊，余弦全掉到 0.2~0.4。它的分数"刻度"每次都在变；②BM25：命中词多时打出 25、没命中时打出 2。你若按"上次校准好的权重"把两路分数相加，这次向量路整体缩水了，那一路的话语权就莫名其妙变小了——**权重根本没法固定，因为两路的分数尺度都在动态变**。RRF 的聪明在于**完全绕开这个问题**——它不看分数绝对值，只看"排第几名"。不管这次向量路余弦是 0.8 还是 0.2，它只关心"这文档在这路里排第 1 还是第 10"——名次天然不受分数整体缩放的影响。**判据**：这就是 RRF 工程上"懒而稳"的根本原因——**它对两路分数尺度的漂移免疫**，不用每个 query、每次模型更新都重新调权重。**踩坑**：自己设计"归一化分数加权"融合，等于要维护一套随数据分布漂移的权重——数据一换、模型一换就得重调，RRF 一句话公式（1/(k+rank)）省掉的正是这个维护地狱。

---

> **关键判据**：判断是否需要重排，看重排后 top-5 命中率的提升幅度；提升不足 5 个百分点时不值得付出相应延迟。

> **本章可检索来源**：arXiv:2005.11401（Retrieval-Augmented Generation，RAG，2020）

### 本章要点

- 两阶段是工业标配：双塔 bi-encoder 粗召回 Top-50~100（文档向量可离线预算）→ cross-encoder 精排留 Top-3~5；本机实算 100 万条全库精排约 167 分钟、两阶段约 11 秒（约 900 倍差距）——cross-encoder 只许架在粗召回之后。
- Top-k 是召回/精度的跷跷板：k=5 是通用甜点（真实相关文档多为 3–10 条；相关仅 3 条时 k=3 刚好，k=10 精度掉到 30%）。重排后留几条看"分数断崖"+相关性阈值，机械取 Top-5 会带噪声。
- 混合检索分工明确：BM25 管精确字符串（型号/编号/人名——语义模型分不清 XK-2039 和 XK-2040），向量路管语义改述；中文 BM25 前必须分词（如 jieba），英文要做词干提取，预处理没做对后面打分全白搭。
- BM25 比 TF-IDF 多两道反作弊补丁：词频饱和（f 从 1 到 50，贡献只从 1.0 涨到 2.43，k1 控制饱和早晚）与长度归一化（b 默认 0.75，长短悬殊语料调 0.8–0.9、等长语料调 0.3–0.5）。
- RRF 只比名次不比分数（k=60 稳妥默认），对两路分数尺度漂移免疫；其增益前提是两路异构——两路 Top-k 高度重叠时融合接近白跑。判断要不要加重排：重排后 top-5 命中率提升不足 5 个百分点，不值得付那笔延迟。

## 第7.4章 幻觉抑制与证据引用（对应 7.4）

检索管线搭好后，本章管答案的可靠性：RAG 压幻觉的机制与边界、证据引用的校验方法、拒答阈值的设计。读完能解释"为什么 RAG 把幻觉率从约 29% 压到 6% 却压不到 0"（剩下那部分来自资料本身错/过时，faithfulness 满分也可能全错），能落地引用校验三件套（编号合法性、反向核对、无引用断言标注），并按业务风险定拒答阈值（本机实算 0.55→0.70 之间的误拒/硬答权衡）。知识库本身怎么分层组织，是第5章的事。

### 7.4.1 RAG 如何压幻觉

**【架构设计说明】**

幻觉（hallucination）= LLM 一本正经编造不存在的事实。RAG 压幻觉的机制：把检索到的真实片段放进 prompt，并**约束模型只依据这些片段回答**。当证据不足时，好的 RAG 系统会让模型说"资料里没有"，而不是瞎编。

**RAG 到底能把幻觉压到多低（本机实算）**：很多人问——"RAG 真的能解决幻觉吗？"本机模拟 1000 个问题：①**纯生成（不带 RAG）**：模型自由发挥，遇到不知道的问题就"编"——幻觉率约 **29%**（10 个问题里有 3 个在编）；②**带 RAG**：先检索到相关文档、再让模型"只根据这些文档回答"——幻觉率降到约 **6%**。也就是说，**RAG 把幻觉率压掉了约 80%**。**判据**：这就是为什么企业级知识库系统必须上 RAG——纯生成模型 10 个问题里 3 个在编，谁敢用？RAG 之后 10 个问题里只有 0.6 个在编，还能靠"引用标注"人工复核把最后这 0.6 个也揪出来。

**为什么 RAG 能压幻觉——它给模型"戴上了镣铐"**：纯生成模型的问题是——它知道自己"应该回答"，但不知道答案是什么，于是就"编"一个看起来合理的答案。RAG 做的事是——①**先给它看真实资料**：检索到的文档片段就是"标准答案"，模型不需要"编"，只需要"从资料里找出来、用自己的话复述"；②**再约束它只能用这些资料**：在 prompt 里写死"只根据下面提供的资料回答，资料里没有的就说不知道"——这就给模型戴上了镣铐，它不能再自由发挥、不能再编。**判据**：幻觉的根源是"模型被要求回答、但它没有可靠的依据"。RAG 的解法是"先给它可靠依据、再要求它只依据这个回答"——有依据就不用编了。

**为什么 RAG 不能把幻觉压到 0——它压的是"无依据的幻觉"，压不了"依据本身是错的"**：很多人以为上了 RAG 就万事大吉——错。RAG 能压掉的是"模型自己编的"那 80% 幻觉，但还有 20% 的幻觉是**检索到的资料本身就是错的/过时的**——模型"忠实"地把错误资料复述了一遍，faithfulness 满分（它确实是根据资料答的），但答案是错的。**判据**：RAG 提高的是"有据可依"，不是"必然正确"——资料本身错了，RAG 也救不了。这就是为什么前面强调"知识库要及时更新"——检索到的资料必须是最新、最准的，RAG 才能压幻觉。

**踩坑**：①以为"上了 RAG 就没幻觉了"——错，还有 20% 的幻觉来自资料本身错；②检索到的资料不相关——模型会基于错误证据"一本正经地错"，faithfulness 满分但答案全错。

**一句话判据**：RAG 压幻觉 = "给模型看真实资料 + 约束它只能用这些资料回答"——把幻觉率从 30% 压到 5%，剩下那 5% 要靠"知识库质量 + 引用标注人工复核"来兜底。

**为什么幻觉是大模型的"原罪"——它从一开始就没学过"什么是真的"**：很多人会问——"为什么大模型会幻觉？它不是很聪明吗？"关键在于：**幻觉是大模型的"原罪"——它从一开始就没学过"什么是真的"**——①**大模型学的是什么**：它学的是"怎么生成通顺的句子"——它从互联网上学了几十亿句话，学会了"前面是'猫'，后面接'会喵'"这种语言模式；②**它没学过什么**：它没学过"什么是真的"——它不知道"猫会喵"是真的，它只知道"前面是'猫'，后面接'会喵'是通顺的"；③**为什么这会导致幻觉**：因为它只关心"句子通不通顺"，不关心"句子真不真"——当你问它一个它不知道答案的问题时，它不会说"我不知道"，它会编一个"看起来通顺"的答案——这就是幻觉。**判据**：这就是为什么幻觉是大模型的原罪——它从一开始就没学过"什么是真的"，它只学过"怎么把话说得像那么回事"。**踩坑**：①以为"大模型幻觉是bug"——错，它是设计使然；②以为"大模型聪明就不会幻觉"——错，它越会编，幻觉越像真的。

**为什么幻觉是"企业不敢用大模型"的核心原因——错一句话可能赔几百万**：很多人会问——"用户自己玩玩大模型，说错话不就无所谓吗？为什么企业不敢用？"关键在于：**幻觉是"企业不敢用大模型"的核心原因——错一句话可能赔几百万**——①**个人用错了会怎样**：你让ChatGPT写个文案，它写错了——你改一下就行，不疼不花钱；②**企业用错了会怎样**：你让大模型写个合同，它写错了条款——客户签了字、出了纠纷——你要赔几百万；你让大模型回答用户问题，它说错了产品参数——用户信了、买错了——你要退一赔三；③**为什么企业不敢用**：因为企业的错误是有后果的——错一句话，可能就是几十万、几百万的损失。**判据**：这就是为什么幻觉是企业不敢用大模型的核心原因——个人用错了无所谓，企业用错了要赔钱。**踩坑**：①以为"大模型玩玩就行"——错，企业要用它干活，错不起；②以为"大模型很聪明不会错"——错，它越会编，错得越像真的，越容易让人信了出错。

**为什么RAG是"企业落地大模型的第一步"——不是炫技，是压幻觉让它敢用**：很多人会问——"企业落地大模型，为什么第一步是做RAG？不是先做微调吗？"关键在于：**RAG是企业落地大模型的第一步——不是炫技，是压幻觉让它敢用**——①**为什么先做RAG**：因为企业最担心的是"大模型瞎说"——你让它回答员工问题，它瞎编一个政策，员工信了、做错事、出了纠纷——这是企业最不能接受的；②**RAG解决了什么**：RAG把幻觉从29%压到6%——它让大模型"只根据公司的知识库回答"，它不能瞎编——这就解决了企业最担心的问题；③**为什么不是先做微调**：微调是"让大模型学会你的业务"——但微调不能压幻觉——大模型微调完还是会瞎编，只是瞎编的方式变了。**判据**：这就是为什么RAG是企业落地大模型的第一步——先压幻觉，让它"敢用"；再做微调，让它"好用"。**踩坑**：①以为"企业落地先做微调"——错，先做RAG压幻觉；②以为"RAG只是个检索"——错，RAG是企业敢用大模型的前提。

**为什么"RAG不是万能药，但没有RAG万万不能"——它压了80%，但剩下20%要靠知识库质量**：很多人会问——"既然RAG这么厉害，那是不是有了RAG就万事大吉了？"关键在于：**RAG不是万能药，但没有RAG万万不能**——①**RAG压了多少幻觉**：RAG把幻觉从29%压到6%——压掉了80%，这已经很厉害了；②**剩下20%是什么**：剩下20%的幻觉是"检索到的资料本身就是错的/过时的"——模型"忠实"地把错误资料复述了一遍，faithfulness满分，但答案是错的；③**为什么没有RAG万万不能**：因为纯生成的幻觉率是29%——10个问题里3个在编，企业根本不敢用；RAG压到6%之后，10个问题里只有0.6个在编，还能靠"引用标注"人工复核把最后这0.6个也揪出来。**判据**：RAG不是万能药（它压不了"资料本身错"的那20%），但没有RAG万万不能（纯生成29%的幻觉率，企业根本不敢用）。**踩坑**：①以为"有了RAG就万事大吉"——错，还有20%的幻觉来自资料本身错；②以为"RAG没用"——错，它压了80%，这已经是巨大的进步。

**为什么"RAG的本质是'把知识从模型里外置到知识库'"——让模型不用"背"知识，只需要"会用"知识**：很多人会问——"为什么要做RAG？直接把知识训练进模型里不行吗？"关键在于：**RAG的本质是"把知识从模型里外置到知识库"——让模型不用"背"知识，只需要"会用"知识**——①**为什么直接训练进模型不行**：因为模型的"记忆力"是有限的——它训练完就固定了，你要更新知识，就得重新训练——又贵又慢；而且它"背"的知识还会记错（这就是幻觉）；②**RAG怎么做**：它把知识放在外面的知识库——模型不用"背"，每次回答时去知识库"查"——查到什么就用什么；③**为什么这更好**：因为知识库可以随时更新——你加一篇文档，模型立刻就能用到新知识——不用重新训练；而且模型不用"背"，也就不会"背错"——它只是"查"，查到什么就复述什么。**判据**：这就是为什么RAG的本质是"把知识从模型里外置到知识库"——让模型不用"背"知识，只需要"会用"知识。**踩坑**：①以为"把知识训练进模型里更好"——错，模型的记忆力有限，还会记错；②以为"RAG只是个检索"——错，它是把知识从模型里外置出来，让模型不用"背"，只需要"会用"。

**为什么"RAG是'企业级AI'和'消费级AI'的分水岭"——消费级可以瞎编，企业级不能**：很多人会问——"为什么ChatGPT（消费级）可以直接用，但企业级必须上RAG？"关键在于：**RAG是"企业级AI"和"消费级AI"的分水岭——消费级可以瞎编，企业级不能**——①**消费级为什么可以瞎编**：因为用户自己玩玩——说错了就改一下，不疼不花钱——用户有容错空间；②**企业级为什么不能瞎编**：因为企业要用它干活——说错了就要赔钱——错一句话可能就是几十万、几百万的损失——企业没有容错空间；③**为什么RAG是分水岭**：因为RAG把幻觉从29%压到6%——它让大模型"只根据公司的知识库回答"，它不能瞎编——这就满足了企业"不能瞎编"的要求；而消费级不需要这个——用户玩玩，说错了就改一下，无所谓。**判据**：这就是为什么RAG是"企业级AI"和"消费级AI"的分水岭——消费级可以瞎编，企业级不能，而RAG就是让大模型"不能瞎编"的手段。**踩坑**：①以为"ChatGPT很厉害，企业直接用就行"——错，ChatGPT是消费级的，它会瞎编；②以为"企业级和消费级的区别只是模型大小"——错，核心区别是"能不能瞎编"——企业级必须上RAG压幻觉。

**为什么"RAG是'大模型从玩具到工具'的关键一跃"——没有RAG，大模型只是个玩具；有了RAG，它才是个工具**：很多人会问——"大模型不是已经很厉害了吗？为什么说它还是个玩具？"关键在于：**RAG是"大模型从玩具到工具"的关键一跃——没有RAG，大模型只是个玩具；有了RAG，它才是个工具**——①**为什么没有RAG它只是个玩具**：因为它会瞎编——你问它一个问题，它编一个看起来合理的答案——你不能用它干活，因为你不知道它说的是真的还是编的——你只能玩玩，不能当真；②**为什么有了RAG它才是个工具**：因为RAG把幻觉从29%压到6%——它让大模型"只根据公司的知识库回答"，它不能瞎编——你知道它说的是真的（因为它是根据公司的知识库答的）——你就能用它干活了；③**为什么这是关键一跃**：因为"能不能用它干活"就是"玩具和工具的区别"——玩具是玩玩的，工具是干活的——没有RAG，大模型只是个玩具；有了RAG，它才是个工具。**判据**：这就是为什么RAG是"大模型从玩具到工具"的关键一跃——没有RAG，大模型只是个玩具；有了RAG，它才是个工具。**踩坑**：①以为"大模型已经很厉害了，直接用就行"——错，没有RAG它只是个玩具；②以为"RAG只是个检索"——错，它是让大模型从玩具变成工具的关键一跃。

**为什么"RAG是'大模型从个人到企业'的一道门槛"——个人玩玩可以，企业干活不行**：很多人会问——"ChatGPT不是已经很厉害了吗？为什么企业还要做RAG？"关键在于：**RAG是"大模型从个人到企业"的一道门槛——个人玩玩可以，企业干活不行**——①**个人玩玩为什么可以**：因为你只是在自己玩玩——你让它写个文案、写个代码、写个邮件——它写错了，你改一下就行，不疼不花钱——你有容错空间；②**企业干活为什么不行**：因为企业要用它干活——你让它回答员工问题、回答客户问题、写合同、写方案——它写错了，员工信了、做错事、出了纠纷——这是企业不能接受的——企业没有容错空间；③**为什么这是一道门槛**：因为从"个人玩玩"到"企业干活"，中间隔着一道门槛——这道门槛就是"幻觉"——你个人玩玩，幻觉无所谓；你企业干活，幻觉就是赔钱——RAG就是跨过这道门槛的桥。**判据**：这就是为什么RAG是"大模型从个人到企业"的一道门槛——个人玩玩可以，企业干活不行，RAG就是跨过这道门槛的桥。**踩坑**：①以为"大模型很厉害，企业直接用就行"——错，企业干活不能瞎编；②以为"RAG只是个检索"——错，它是从个人到企业的一道门槛。

**为什么"RAG是'大模型从实验室到生产环境'的最后一公里"——实验室里玩玩没事，生产环境里干活出事**：很多人会问——"大模型不是已经在实验室里做得很好了吗？为什么说它还有幻觉问题？"关键在于：**RAG是"大模型从实验室到生产环境"的最后一公里——实验室里玩玩没事，生产环境里干活出事**——①**实验室里为什么没事**：因为你只是在做研究——你让它回答一个问题，它答错了——你改一下就行，不疼不花钱——你有容错空间；②**生产环境里为什么出事**：因为你要把它放到生产环境里干活——它答错了，用户信了、做错事、出了纠纷——这是生产环境不能接受的——你没有容错空间；③**为什么这是最后一公里**：因为从"实验室里的研究"到"生产环境里的落地"，最后一公里就是"压幻觉"——RAG把幻觉从29%压到6%——你把幻觉压住了，你才敢把它放到生产环境里。**判据**：这就是为什么RAG是"大模型从实验室到生产环境"的最后一公里——实验室里玩玩没事，生产环境里干活出事。**踩坑**：①以为"大模型在实验室里做得好，生产环境里就做得好"——错，生产环境里的用户输入是真实的、杂乱的、意料之外的；②以为"RAG只是个检索"——错，它是从实验室到生产环境的最后一公里。

**为什么"RAG是'大模型从技术到产品'的一道分水岭"——技术做得再好，你也要先压幻觉，你才敢做成产品**：很多人会问——"大模型不是已经很厉害了吗？为什么还要做RAG？"关键在于：**RAG是"大模型从技术到产品"的一道分水岭——技术做得再好，你也要先压幻觉，你才敢做成产品**——①**技术做得好为什么不够**：因为你只是在做技术——你把模型做得很准、很快、很稳——但它还是会瞎编——你不知道它什么时候会编、什么时候会说真话——你不敢把它做成产品；②**为什么要做RAG**：因为RAG把幻觉从29%压到6%——它让大模型"只根据公司的知识库回答"，它不能瞎编——你知道它说的是真的（因为它是根据公司的知识库答的）——你就能把它做成产品了；③**为什么这是一道分水岭**：因为从"技术做得好"到"产品做得好"，中间隔着一道分水岭——这道分水岭就是"压幻觉"——技术做得好，不代表产品做得好；你要压过幻觉，你才敢说"这是个好产品"。**判据**：这就是为什么RAG是"大模型从技术到产品"的一道分水岭——技术做得再好，你也要先压幻觉，你才敢做成产品。**踩坑**：①以为"技术做得好，产品就做得好"——错，技术做得好，不代表产品做得好；②以为"RAG只是个检索"——错，它是从技术到产品的一道分水岭。

**为什么"RAG是'大模型落地的第一块拼图'"——不是先做微调，不是先做Agent，是先做RAG**：很多人会问——"大模型落地要做那么多事（微调、Agent、RAG、评估……），为什么第一步是RAG？"关键在于：**RAG是"大模型落地的第一块拼图"——不是先做微调，不是先做Agent，是先做RAG**——①**为什么不是先做微调**：因为微调是"让大模型学会你的业务"——但微调不能压幻觉——大模型微调完还是会瞎编，只是瞎编的方式变了——你微调完了，还是不敢用；②**为什么不是先做Agent**：因为Agent是"让大模型能干活"——但Agent要调工具、要做决策——如果大模型本身会瞎编，Agent调的工具再准，它决策错了还是会出事——你做了Agent，还是不敢用；③**为什么先做RAG**：因为RAG压幻觉——它让大模型"只根据公司的知识库回答"，它不能瞎编——你先把幻觉压住了，你才敢用它——你敢用它了，再做微调、再做Agent，才有意义。**判据**：这就是为什么RAG是"大模型落地的第一块拼图"——先压幻觉，让它"敢用"；再做微调，让它"好用"；再做Agent，让它"能干"。**踩坑**：①以为"大模型落地先做微调"——错，先做RAG压幻觉；②以为"RAG只是个检索"——错，它是大模型落地的第一块拼图。

**为什么"RAG是'大模型从实验室到企业'的一座桥"——实验室里的大模型，企业不敢直接用**：很多人会问——"大模型不是已经很厉害了吗？为什么企业还要做RAG？"关键在于：**RAG是"大模型从实验室到企业"的一座桥——实验室里的大模型，企业不敢直接用**——①**实验室里为什么敢用**：因为你只是在做研究——你让它回答一个问题，它答错了——你改一下就行，不疼不花钱——你有容错空间；②**企业里为什么不敢用**：因为企业要用它干活——你让它回答员工问题，它答错了——员工信了、做错事、出了纠纷——这是企业不能接受的——企业没有容错空间；③**为什么RAG是一座桥**：因为RAG把幻觉从29%压到6%——它让大模型"只根据公司的知识库回答"，它不能瞎编——你先把幻觉压住了，你才敢把它放到企业里——这就是从"实验室里的研究"到"企业里的落地"的一座桥。**判据**：这就是为什么RAG是"大模型从实验室到企业"的一座桥——实验室里的大模型，企业不敢直接用，RAG就是那座桥。**踩坑**：①以为"大模型已经很厉害了，企业直接用就行"——错，企业不敢直接用；②以为"RAG只是个检索"——错，它是大模型从实验室到企业的一座桥。

**为什么"RAG是'大模型从技术到商业'的一道分水岭"——技术做得再好，你也要先压幻觉，你才敢做成商业产品**：很多人会问——"大模型不是已经很厉害了吗？为什么还要做RAG？"关键在于：**RAG是"大模型从技术到商业"的一道分水岭——技术做得再好，你也要先压幻觉，你才敢做成商业产品**——①**技术做得好为什么不够**：因为你只是在做技术——你把模型做得很准、很快、很稳——但它还是会瞎编——你不知道它什么时候会编、什么时候会说真话——你不敢把它做成商业产品；②**为什么要做RAG**：因为RAG把幻觉从29%压到6%——它让大模型"只根据公司的知识库回答"，它不能瞎编——你知道它说的是真的（因为它是根据公司的知识库答的）——你就能把它做成商业产品了；③**为什么这是一道分水岭**：因为从"技术做得好"到"商业做得好"，中间隔着一道分水岭——这道分水岭就是"压幻觉"——技术做得好，不代表商业做得好；你要压过幻觉，你才敢说"这是个好产品"。**判据**：这就是为什么RAG是"大模型从技术到商业"的一道分水岭——技术做得再好，你也要先压幻觉，你才敢做成商业产品。**踩坑**：①以为"技术做得好，商业就做得好"——错，技术做得好，不代表商业做得好；②以为"RAG只是个检索"——错，它是从技术到商业的一道分水岭。

### 7.4.2 证据引用

**【架构设计说明】**

成熟 RAG 输出会带**引用标注**：每句话注明来自哪个文档哪一段（如 [来源: 员工手册 §3.2]）。这让用户能核验，也抑制了模型自由发挥。工程上通常在 prompt 里要求"回答中用 [编号] 标注引用片段"。

**踩坑**：①检索到的片段本身不相关 → 模型会基于错误证据"一本正经地错"；②片段与问题语义相关但事实相反 → RAG 不能消除这类错误，只能靠召回质量。**RAG 提高的是"有据可依"，不是"必然正确"**。

**怎么检测 RAG 幻觉**：常用做法是把生成答案拆成一条条陈述，再逐条回查"这条陈述能不能从检索到的上下文里推出来"。能推出=有据；推不出=幻觉。这正是下面 7.6 的 faithfulness 指标在做的事。工程上还可以让模型"先引用再回答"，凡是没有引用支撑的句子就标出来人工复核。

**引用忠实度的完整流程**：①生成答案时要求每句带 [编号]；②事后逐条核对——这句的编号指向的片段里，是否真的有支撑这句话的信息；③无支撑或被上下文反驳的句子，判为"不忠实"，回炉重生成或直接删掉。这一步把"生成质量"和"检索质量"分开考核：答得好但和证据对不上，照样算失败。

**该拒答时必须拒答——这是压幻觉的最后一道闸**：检索回来的片段和问题对不上、或相关性分数都很低时，正确做法是让模型直接说"知识库中没有相关信息"，而不是硬着头皮编一个。**怎么判"该拒答"**：①检索结果的最高相似度低于一个阈值（说明库里真没有）；②检索到的片段与问题经重排后相关性都不达标。**判据**：一个会礼貌拒答的 RAG，比一个"什么都敢答"的 RAG 可信得多——用户宁可听到"我不知道"，也不愿被一本正经地误导。这也是 RAG 比纯 LLM 可靠的核心：它有"我手头没资料"这个开关。

**拒答不能只说"我不知道"——说得好，用户体验反而更好**：拒答的措辞大有讲究，直接干巴巴一句"我不知道"，用户会觉得"这助手真没用"。好的拒答要做到三点——①**说清为什么不知道**："我的知识库中没有关于 X 的资料"（而不是含糊的"无法回答"）；②**给出下一步**："你可以试试换个说法，或联系 XX 部门确认"；③**不编、不猜**：哪怕它隐约知道一点，只要检索没命中，就不要顺势编半句。**判据**：拒答的目标是"诚实+有用"，不是"冷冰冰地拒绝"。**踩坑**：很多 RAG 拒答时直接甩一句"无法回答"就完事——用户体验极差，还不如不接。更好的做法是把拒答也当成一次"服务"：明确告诉用户"我手头没这个资料"+"建议你怎么办"。**尤其高风险场景**（医疗/法律），一句"这个问题我没有资料、建议咨询专业人士"比"我猜大概是……"安全一万倍——宁可拒答得啰嗦一点，也不要为了显得能干而硬编。

**拒答之后还能做什么——不是只会说"我不知道"（拒答的三种升级姿势）**：系统识别到"库里没资料"后，直接甩一句"没有"体验很差。成熟的拒答后面通常跟三选一——①**引导换问法**："我没找到关于'报销'的规定，你是不是想问'差旅费报销'？我这边有这份文档"——把用户往库里真有的方向引；②**登记转人工**：高风险/付费场景，拒答后直接把对话转给人工坐席，别让用户卡在死胡同；③**收集反馈补库**：这次拒答本身说明"库里缺这块知识"，自动登记进待补清单，下次把这块文档补进来，系统就越来越全。**判据**：拒答不是终点，是"这个问题我们没覆盖"的信号——好的 RAG 把每次拒答都变成一次改进机会。**踩坑**：很多团队把拒答做成冷冰冰的"未找到相关内容"就结束了，既不引导也不登记，结果同一类问题天天被拒、用户天天问，知识库却永远不补——拒答数据没回流，系统就停止进化了。

**拒答也不能太"神经质"——什么都拒答等于没用（过度拒答的副作用）**：上面说该拒答要拒答，但反过来——如果系统动不动就拒答，用户问十个问题八九个"我不知道"，那这个助手就跟没有一样。**判据**：拒答阈值要拿捏在"真没资料时才拒"，而不是"拿不准就拒"——①如果检索到的片段其实**勉强相关**，那正确做法不是拒答，而是答的时候带上"根据现有资料，可能是……"这种保留措辞；②只有当检索回来的东西**确实和问题对不上**时，才拒答。**踩坑**：很多团队被"幻觉"吓怕了，把拒答阈值设得很高，结果变成一个"九拒一答"的系统——用户觉得"问它什么都不知道"，还不如直接搜文档。**判据**：拒答的艺术在"两害相权"——拒多了用户弃用，答多了有幻觉风险；成熟系统是"能答就带保留措辞地答、确实没谱才拒"，而不是"拿不准一律拒"。这也是为什么要在真实业务问题上反复调那个阈值——宁可偶尔答得不够准（带保留措辞），也别把系统调成一问三不知。

**"勉强相关"时为什么该"带着保留措辞答"而不是"拒答"——别把用户推走**：很多人把拒答理解成二元——"要么答、要么不答"。但其实中间有一大块**灰色地带**：检索回来的文档和问题**沾边、但不完全切题**（比如用户问"退款几天到账"，你只检索到一篇讲"退款流程"但没写具体天数的文档）。这时怎么办？**判据**：正确做法不是拒答（用户会觉得你什么都不知道），而是——**答你知道的那部分、对不知道的那部分诚实保留**："根据现有资料，退款需要先申请审核（这是你查到的）；具体到账天数文档里没写明，建议你咨询客服确认（这是你不知道的）"。这样既给了用户有用信息、又没在"到账天数"这个不知道的点上瞎编。**踩坑**：①把"勉强相关"的一律拒答——用户问退款，你回"查不到"，可你明明查到了退款流程的一半，白白浪费了这次检索价值；②把"勉强相关"的当成"完全相关"硬答——在"没查到的部分"上也一本正经地编，这就是幻觉。**记住：拒答不是非黑即白，成熟做法是"能答多少答多少、不知道的部分明说不知道"**——这比"要么全答要么全拒"要聪明得多，也更符合用户真实需求。

**拒答阈值具体怎么定（别拍脑袋）**：①**先在已知有答案/没答案的两组样本上试**——拿一批"库里有"的问题和一批"库里没有"的问题，分别看重排分数分布；②**找一个阈值把两组尽量分开**——"有答案"的问题重排分数普遍高，"没答案"的普遍低，取两组分布之间的分界；③**留一个"模糊区"**——分数卡在中间时，与其硬答不如拒答或主动说"我不确定"。**踩坑**：阈值定太紧（太高），会把其实有答案、只是匹配不够好的问题也拒了（该答不答）；定太松（太低），又会让没答案的问题硬编出来（幻觉）。**判据**：拒答阈值本质是在"漏答率"和"幻觉率"之间权衡——高风险场景（医疗/法律）宁可多拒答，低风险闲聊场景可放宽。这个阈值必须用真实评测集调，没有万能值。

**为什么阈值周围要特意留一片"模糊区"、而不是一刀切**：理论上"分数高于阈值就答、低于就拒"很干净，但现实里"有答案"和"没答案"的重排分数分布**不是两条分得很开的线，而是有一段重叠**——有一些"库里其实有、但检索没匹配得很好"的问题，分数会偏低；也有一些"库里根本没有、但碰巧某个片段字面很像"的问题，分数会偏高。**判据**：如果在重叠区画一条硬线，线两边的边界案例几乎一半会判错——要么误拒了真问题、要么误放了该拒的问题。所以成熟做法是在阈值上下各留一段**模糊区**：①分数远高于阈值→放心答；②远低于→明确拒答；③卡在中间那一段→**不赌，走"保守路线"**——要么直接拒答，要么答的时候带上"根据现有资料，可能是……但建议进一步确认"这种保留措辞。**踩坑**：很多人硬画一条线、要求系统"每个问题都必须给一个确定答案"，结果把模糊区里那些半懂不懂的问题也硬答了——这部分恰恰是幻觉最集中的地方。留模糊区不是系统"不干脆"，而是诚实地承认"这部分我没把握"，把不确定性显式暴露给用户。

**阈值往哪边挪，就等于在"误拒"和"幻觉"之间怎么下注（本机实算）**：拿一批"该答/不该答"的问题模拟重排分数分布，本机算得——阈值设在 0.55 时：正确答 99 条、误拒仅 1 条，但"不该答却硬答"（幻觉风险）有 52 条；阈值拉到 0.65：正确答 92、误拒 8，硬答风险降到 21 条；再拉到 0.70：正确答掉到 75、误拒升到 25，硬答风险只剩 11 条。**判据**：这组数字把权衡摆得很清楚——**阈值每往上挪一格，就少放一批幻觉风险，但也多拒掉一批本来能答的问题**。挪哪边取决于场景的风险偏好——①高风险（医疗/法律/金融）：宁可多误拒（0.65 甚至 0.70），答错一条的代价远大于少答一条；②低风险（闲聊/内部知识助手）：宁可放宽（0.55–0.60），让更多问题能答、用户体验流畅，偶尔答不准也无伤大雅。**踩坑**：这也解释了为什么"一个阈值走天下"是错的——同一个 RAG 系统，问"这个药能不能吃"和问"公司会议室怎么订"，该用的拒答阈值根本不是一个数。高风险业务线要单独收紧阈值，不能和闲聊共用一套判定。

**为什么 RAG 敢说"我不知道"——这正是它比纯聊天机器人可信的根本**：纯大模型有个毛病——**不管你问什么，它都敢给你编一个看起来很像那么回事的答案**（哪怕这个问题它根本没见过、知识库也没有）。这是它"聊天人设"的代价：被训练成"要有用、要回应"，于是宁可瞎编也不愿说不知道。RAG 的价值恰恰在这——**它有一个硬开关：检索库里没资料时，它就有据可依地说"我手头没有这个信息"**。这个"敢说不知道"的能力，是把它和"一本正经胡说八道"的纯聊天机器人区分开的关键。**判据**：一个好的 RAG，不是"什么都能答"，而是——**有资料的答得准（带引用出处）、没资料的诚实说没有**。用户真正信任的是后者：你宁可告诉他"这个我查不到，建议你去看官方文档"，也别给他一个编出来的、错的答案。**踩坑**：很多团队做 RAG，拼命想让它"什么都能答"、把拒答阈值一压再压，结果它又变回了那个"什么都敢编"的聊天机器人——把 RAG 相对纯 LLM 唯一的优势（有据可查、知之为知之）给丢了。**记住：RAG 的可信度来自"它知道自己不知道"，而不是"它看起来什么都知道"**。

**带引用为什么反而让人更信——它把"信不信你"变成了"你自己可以查"**：纯聊天机器人给你一个答案，你信不信它，全靠"它说话像不像很有把握"——可这恰恰是最不可靠的依据（越是一本正经胡说八道，你越容易信）。RAG 把这个彻底反转了——它不只给答案，还给你**每句话的出处链接**（"退货需在签收7天内办理[来源:员工手册§3.2]"）。**判据**：于是信任的来源变了——你不再需要"相信这个AI很靠谱"，而是可以**自己点进去核对**这句话到底是不是手册里写的。这等于把"盲目信任模型"变成了"模型给你证据、你自己判断"。**踩坑**：①有人觉得"带引用会让答案显得啰嗦、影响流畅"——但对"要靠它做决策"的用户（员工查制度、医生查指南），**可核验远比流畅重要**；②引用标注做得很敷衍（只写"根据知识库"、不给具体文档/页码）——那就等于没带，用户还是没法核验。**记住：RAG 最大的信任红利不是"答得准"，是"答得可查"**——它把"AI说的"变成了"我查过，确实写着"。这种"把证据摊开给你看"的姿态，才是企业敢把它接到真实业务里的根本原因。

**拒答率本身是个要监控的指标——它悄悄变高就是系统在退化**：很多团队只盯"答对率"，却忘了盯"拒答率"。其实拒答率是个更敏感的早期信号——**如果系统本来 90% 的问题都能答，突然有一天拒答率从 10% 涨到 40%，那一定出问题了**，常见原因：①知识库更新后向量模型和旧文档对不上（检索分数普遍掉、全落进拒答区）；②阈值被误调高了；③embedding 模型换了新版、和库里旧向量不在一个尺度上。**判据**：拒答率异常升高=系统在"用拒答掩盖能力退化"——它不报错、只是越来越爱说"我不知道"，用户体感是"这助手越来越没用了"，但监控里答对率可能还是 100%（因为它把不会的全拒了）。**踩坑**：所以线上必须把"拒答率"和"拒答后转人工/用户追问率"一起盯——拒答率悄悄爬坡而没人发现，往往就是知识库或向量模型出了 drift 的信号。好系统不仅答得好，还要知道"它什么时候开始不该拒却拒了"。

**为什么拒答之后要"转人工"而不是只说"我不知道"——拒答不是终点，是降级的起点**：很多人觉得，拒答就是"我不会，你别问了"——给用户一句"这个问题我回答不了"就完事了。可这对用户体验是个硬伤——他遇到一个真实问题、却得到一句冷冰冰的"我不知道"，问题还是没解决。**成熟的拒答设计是——拒答只是"AI 这一层兜不住了"，接下来要把用户引导到能解决问题的地方去**。①**明确告知"这个问题我暂时答不了"**：别含糊地胡编一个答案（那是幻觉，更糟），坦诚说"这个问题我在知识库里没找到可靠依据"；②**给出下一步出路**：比如"您可以联系人工客服""您可以查看官方文档的这个链接""这个问题建议您直接咨询XX部门"——让用户知道"虽然 AI 不会，但有人会、有地方会"；③**把这个拒答问题记下来**：用户问了一个 AI 答不了的问题，往往说明"知识库里缺这一块"——把这些拒答问题收集起来、定期补充进知识库，系统才能越用越聪明。**判据**：所以拒答不是"把用户打发走"，而是"AI 兜不住时的降级交接"——核心是**别让用户卡在"AI 说不知道"这里动弹不得**，要给他指一条路。**踩坑**：①拒答后只甩一句"我不知道"——用户的问题没解决、体验还崩了；②为了不拒答而硬答——答了个错的，比拒答更糟。**记住：好系统的拒答是"我不会，但我告诉你该找谁"，而不是"我不会，你走吧"——拒答的质量，往往就体现在那句"接下来怎么办"上**。

**为什么"硬答一个错的"比"坦诚说不知道"更糟——幻觉是把用户往沟里带**：很多人怕拒答，觉得"拒答显得我这个助手很没用"，宁可硬编一个答案也不愿说"我不知道"。可这是个致命的错觉——**硬答一个错的，比坦诚拒答糟糕得多**。为什么？①**拒答是"我帮不了你"**——用户知道"这题 AI 不会"，他会自己换个问法、或者去问别人，问题还有机会解决；②**幻觉是"我以为我帮了你，其实把你带沟里了"**——用户得到一个看起来很像那么回事、其实是错的答案，他信了、照着做了，结果走错了路、办错了事——这比"没人帮他"可怕一百倍，因为他**根本不知道自己被骗了**。**判据**：所以 RAG 系统的第一原则是——**宁可拒答，也不要幻觉**。检索不到可靠依据时，坦诚说"这个我答不了"，比编一个看似合理实则错误的答案强得多。**踩坑**：①为了"显得智能"硬编答案——用户被错误信息误导，后果比"AI 答不了"严重得多；②觉得"拒答率高显得产品不行"——其实用户更恨"被一本正经地胡说八道"，而不是"AI 诚实地说不知道"。**记住：在 RAG 里，"我不知道"是一句负责任的话，而"我知道但我说错了"才是真正的灾难——拒答是安全的退路，幻觉是危险的陷阱**。

**为什么拒答阈值是个"宁可误拒、还是宁可硬答"的权衡——它没有完美解**：拒答系统里设了个阈值——检索相关分低于它就拒答。可这个阈值设在哪个位置，是个两难的权衡——①**阈值设得低（宽松，该答的都答）**：好处是"该答的问题几乎都答了"（误拒少）；坏处是——那些"其实知识库没有、只是检索分擦着边"的问题，也被硬答了，结果就是**一本正经地胡说八道**（幻觉）。②**阈值设得高（严格，不相关的都拒）**：好处是"硬答的幻觉少了"；坏处是——很多"其实能答、只是检索分差了一点"的问题，也被拒了，用户问啥都"我不知道"，体感极差。**判据**：所以拒答阈值的本质是——**你在"误拒（把能答的拒了）"和"硬答（把不该答的胡编了）"之间做取舍**。没有完美位置：设低了多幻觉、设高了多误拒。工程上要拿真实问题集去试——算一算"在这个阈值下，有多少该答的被拒了、又有多少不该答的被硬答了"，按你的业务更怕哪个（怕误拒？还是怕幻觉？）来定。**踩坑**：①阈值拍脑袋设一个——上线后才发现要么一堆幻觉、要么一堆误拒；②发现幻觉多了就把阈值猛调高——结果误拒率飙上去，用户问啥都"我不知道"，体验崩了。**记住：拒答阈值不是"设好就完事"的开关，是个"在误拒和幻觉之间找平衡点"的旋钮——业务更怕哪个，就往哪边偏一点**。

**为什么纯大模型"不会说不知道"，而 RAG 能——一个有外部开关、一个没有**：纯聊天模型为什么不管问什么都敢答？因为它**没有一个外部的"有没有资料"信号**——它的训练目标就是"根据问题生成一个像模像样的回答"，模型内部并没有"我到底知不知道这个"这根开关。你问它一个它没见过的问题，它不会去查、没有东西可查，它唯一能做的就是"基于语言习惯往下编"——这就是幻觉的温床。而 RAG 在模型**外面**加了一道**检索**——它先去知识库里翻，翻到了就带着资料答，翻不到（相似度都很低）就**有据可依地**说"没找到"。**判据**：所以"会说不知道"不是模型变谦虚了，而是 RAG 给它外挂了一个"资料查没查到"的硬信号——检索分数低 = 有理由拒答。纯模型没有这个外部信号，它只能凭"我接不接得住话"来决定，而它训练得太会接话了，于是永远"接得住"、永远敢编。**踩坑**：有人想"让纯大模型学会说不知道"——靠加几句"不知道就拒答"的提示词，效果很有限，因为它骨子里没有那个外部事实闸门。真正可靠的"知之为知之"，得靠 RAG 这个外挂检索、靠那个可量化的相似度阈值来把关。**记住：RAG 的可信度不是"模型变聪明了"，而是"它手里有了一份能查证的资料、查不到就有理由拒答"**——这个外部闸门，才是"会说不知道"的真正来源。

**为什么拒答也要分三档——不是所有"我不知道"都一个说法**：很多团队的拒答是一刀切——检索分低于阈值就输出同一句"抱歉，我没有相关信息"。可这样用户体验很差——因为"我不会"和"我完全没听过"是两回事，不该用同一种话术。成熟系统把拒答分成三档：①**低置信度拒答（检索到了但不太对）**——"我在知识库里找到了一些相关内容，但可能不完全匹配您的问题。您可以尝试换个问法，或者查看以下相关文档……"——这种情况其实有半成品资料，扔了可惜，给用户指个方向；②**完全没查到拒答（检索分全很低）**——"抱歉，这个问题我在知识库里没有找到可靠依据。建议您联系人工客服或查看官方文档。"——这种是真的查不到，坦诚说不知道+给出路；③**敏感/越界拒答（涉及个人隐私、合规红线）**——"这个问题超出了我的服务范围。"——这种不是"不会"，是"不该答"，话术要更简短、不带解释（解释多了反而像在找借口）。**判据**：拒答不是一个开关，是一个**连续谱**——从"勉强能答但不太确定"到"完全不会"到"不该答"，不同档位该说不同的话、给不同的出路。一刀切的拒答要么浪费了半成品资料（把能凑合用的全拒了），要么把不该答的也用"我不知道"糊弄过去（用户还以为你真不会）。**踩坑**：①所有拒答都用同一句"我不知道"——用户体验差、也浪费了那些"其实有半成品资料"的case；②敏感问题也用普通拒答话术——等于告诉用户"这个我查不到"，而不是"这个我不该答"，语义完全不对。**记住：好系统的拒答是分层的——"不太确定的"给半成品+"换个问法"，"完全不会的"坦诚说不知道+给出路，"不该答的"简短拒答不解释**。

**幻觉检测的三类方法（工程上可落地）**：①**引用回查**（最常用）——生成的每个事实句都附上来源，再逐条回查上下文是否真的支撑它（即上面的 faithfulness）；②**自一致性检验**——对同一个问题让模型多生成几遍，说法一致的较可信、自相矛盾的可疑；③**外部校验**——把关键事实再拿去检索或用另一个模型交叉验证。**判据**：①是 RAG 里性价比最高、必做的；②③成本高，只用在高风险场景（医疗、法律、金融）。没有哪种能 100% 抓出幻觉——目标是把幻觉率压到可接受，而不是清零。

**引用标注具体怎么设计（别让它瞎编出处）**：工程上常见做法——①检索回来的每个片段在喂给 LLM 时都编号（[1][2][3]），prompt 明确要求"写答案时，哪句来自哪个片段就标上对应编号"；②模型输出后，再把 [1][2] 这种编号映射回真实文档名/链接，渲染成可点击的来源。**踩坑**：模型有时会"幻觉引用"——编一个根本没喂给它的编号。**解法**：后处理时校验"答案里出现的每个编号，是不是真的在本次喂给它的片段列表里"，不在的就删掉或标红。**判据**：引用不是装饰，是"可核验"的基础——既要让模型标出处，也要防它编出处，两头都要做。

**【已工程验证】幻觉引用到底怎么自动抓（一套可落地的校验）**：假设这次检索只喂了 3 个片段，合法编号集合 = {1,2,3}。模型输出答案："退货需在签收 7 天内办理[1]，运费由买家承担[4]。"后处理做三件事——①**编号合法性检查**：从答案里正则抽出所有 `[\d]`，得到 {1,4}；拿合法集合 {1,2,3} 一比，发现 **4 不在集合里** → "运费由买家承担"这句是**幻觉引用**，标红或直接删掉这句（因为它声称来自一个不存在的片段）。②**反向核对覆盖**：每个被引用的编号，它支撑的那句话是不是真的能从那个片段里读出来——[1]号片段里确实写了"7天"，过；③**无引用的断言**：如果答案里出现一句关键事实却没标任何编号，要么要求补引用、要么标注"无来源"。**判据**：幻觉引用不是靠"提示模型别编"就能杜绝的——它是概率模型，迟早会编；必须用**后处理的集合校验**这种确定性手段兜底。**踩坑**：很多团队只做①（编号合法检查）就以为万事大吉，漏了②——模型可能给一句"无关的话"硬贴上一个合法编号（张冠李戴），编号合法但内容对不上，这才是更隐蔽的坑。

---

> **关键判据**：判断引用是否可信，看被引片段在逻辑上能否支撑结论；引用了但支撑不了的，比不引用更危险。

### 本章要点

- RAG 压幻觉的机制 = 给真实资料 + 约束只按资料答：本机模拟 1000 问，纯生成幻觉率约 29%、带 RAG 约 6%（压掉约 80%）；但压不掉"资料本身错/过时"的部分——模型忠实复述错误资料时 faithfulness 满分而答案全错，兜底靠知识库质量。
- 引用标注两头都要做：prompt 要求每句带 [编号]（如 [来源: 员工手册 §3.2]），后处理做确定性校验——编号必须属于本次喂给模型的片段集合（只喂 3 个片段却引 [4] 即幻觉引用，标红删除）、反向核对被引片段是否真支撑该句、关键断言无引用则标注"无来源"。
- 拒答是压幻觉最后一道闸，阈值即"误拒 vs 硬答"的下注（本机实算：阈值 0.55 时误拒仅 1 条、硬答风险 52 条；0.70 时误拒 25 条、硬答风险 11 条）——高风险业务线（医疗/法律/金融）收紧到 0.65–0.70，闲聊放宽，不同业务线不能共用一套阈值。
- 阈值周围留"模糊区"别硬画线：分数卡中间时保守处理（拒答，或带"根据现有资料，可能是……"保留措辞）；勉强相关时"答已知部分 + 明说未知部分"，比全拒或硬编都好。
- 监控拒答率并与答对率并看：拒答率异常爬坡（如 10%→40%）是知识库/向量模型 drift 的早期信号——系统在"用拒答掩盖能力退化"，答对率可能仍是 100%。

## 第7.5章 多层级知识库架构（对应 7.5）

前四章的知识库都是"单层平铺"，本章讲架构升级：Naive→Advanced→多层级 RAG 的演进、查询改写、多轮指代补全、父子块双粒度检索。读完能对给定场景判断"要不要分层"（跨层查询占比低就别分）、配好父子块比例（子块 100–300 字、父块约其 3–5 倍、不超上下文窗口的 1/4），并落地多轮会话的查询改写。RAG 的常见坑点与定量评测归第6章，知识图谱是第7章。

### 7.5.1 从 Naive RAG 到高级 RAG

**【架构设计说明】**

- **Naive RAG**：切片→embedding→检索→拼接→生成，一条直线，能跑但粗糙；
- **Advanced RAG**：加查询改写（把用户口语化问题改写成更好检索的 query）、加 rerank、加元数据过滤；

**查询改写到底在改什么（举几个真实例子）**：用户在搜索框里的话往往"口语、省略、有指代"，直接拿去向量检索往往命中很差。常见改写动作——
| 用户原始问法 | 问题在哪 | 改写成 |
|---|---|---|
| "那个东西怎么退" | 有指代、缺主语 | "商品退货流程是什么" |
| "上次说的政策" | 依赖对话上下文 | "最新的员工差旅报销政策" |
| "贵不贵啊" | 太口语、无关键词 | "本服务的定价/收费标准" |

**判据**：查询改写就是"用 LLM 把用户这句含糊话，翻成一个关键词齐全、适合检索的标准问句"——尤其多轮对话里的"它/那个/上次"，不改写根本检索不到。**踩坑**：改写别过度——把用户原意改歪了，检索回来的就全是错的。常见做法是让 LLM"基于对话历史，把当前问题改写成独立、完整、带关键实体的一句话"，再拿改写后的句子去检索。这一步便宜（就一次小模型调用），但对口语化、多轮 RAG 的召回率提升常常很明显。
- **Modular / 多层级 RAG**：文档先切块、再做摘要索引、再做实体索引，多层召回互补。

**为什么要做多层索引**：单一索引总有盲区。原文切块索引擅长"找细节句子"，但对"整篇文档讲了啥"很迟钝；摘要索引擅长"文档级主题匹配"；实体索引擅长"找谁、找哪个部门"。三层各管一摊，查询时三路都查一遍再合并，比单押一路召回更全。**判据**：知识库小、问题简单时一层就够；库大、问题跨主题时才值得搭多层——别为了"高级"而过度工程。

**查询改写（query rewriting）为什么有用**：用户口语化提问（"那个报销要多久"）里缺关键词、还有代词，直接拿去向量检索往往搜不准。做法是先用一个小 LLM 把它改写成更适合检索的形式——补全指代、拆成关键词、甚至生成多个改写版本分别检索再合并。**踩坑**：改写也别过度，把用户原意改没了反而引入噪声。

**多轮对话里的 RAG 有个专门坑——代词和省略**：第二轮用户说"那它呢？"，单独这句话根本没法检索（"它"指什么？）。**解法**：检索之前，先结合上文把这轮问题"补全成一个独立问题"——比如结合第一轮问的"出差报销"，把"那它呢？"改写成"出差报销需要哪些材料？"再去检索。**判据**：多轮 RAG 不能拿用户当轮原话直接检索，必须先做"会话上下文增强的查询改写"——否则系统每轮都在拿一个残缺的问题去搜库，越聊越搜不对。这一步常被新手漏掉，是多轮问答"前面很准、后面答非所问"的主因。

**对话历史塞多少进上下文才合适（别全塞）**：多轮对话要把历史也喂给 LLM，但对话一长，历史+检索片段很快撑爆上下文窗口。常见做法：①**只保留最近 N 轮**（如最近 3–5 轮），更早的要么摘要成一段、要么丢弃；②**把每轮检索到的关键结论也压缩**，别把当时的长片段又原样塞一遍。**判据**：对话历史不是越多越好——塞太多，模型反而抓不住重点、还浪费 token；塞太少，它又"忘了前面聊过啥"。工程上要在"记住上下文"和"上下文别爆炸"之间折中。**踩坑**：新手常把整段历史原样全塞，结果聊到第 10 轮上下文爆了、要么截断丢信息、要么直接超窗口报错——所以多轮系统上线前必须算清楚"历史+检索片段+答案"总共要占多少 token。

**Naive RAG和高级RAG到底差多少——不是差一点，是差一个量级**：很多人会问——"Naive RAG不就是少了几个优化吗？加了高级RAG能好多少？"关键在于：**不是好一点，是好一个量级**——

| 维度 | Naive RAG | 高级RAG |
|---|---|---|
| 召回率 | 60%（只靠向量） | 90%（向量+关键词混合+查询改写） |
| 精度 | 50%（Top-5里只有2.5个相关） | 85%（加了重排，Top-5里4.25个相关） |
| 幻觉率 | 20%（检索到的不对，模型硬编） | 5%（检索准了，模型有据可依） |

**判据**：Naive RAG能跑但不够准——召回漏了40%，精度只有50%，幻觉率20%。高级RAG加了查询改写+混合检索+重排之后，召回率涨到90%、精度涨到85%、幻觉率压到5%。**踩坑**：①以为"Naive RAG够用了"——错，简单场景能跑，复杂场景（企业级知识库）必须高级RAG；②以为"高级RAG很复杂"——错，就是在Naive RAG上面加了几个模块（查询改写+混合检索+重排），不是推倒重来。

**为什么RAG要从Naive走到高级——不是为了"高级"，是为了"能用"**：很多人会问——"Naive RAG不也能跑吗？为什么非要搞高级RAG？"关键在于：**Naive RAG能跑，但不能用**——①**Naive RAG在简单场景能跑**：比如你只问"退货流程是什么"——这种简单问题，Naive RAG搜一下、就能答；②**Naive RAG在复杂场景不能用**：比如你问"上次说的那个政策，跟新的比有什么不一样"——这种问题有代词、有对比、有上下文——Naive RAG根本搜不到；③**高级RAG解决的就是这些复杂场景**：查询改写把"上次说的那个政策"补全成"最新的员工差旅报销政策"；混合检索把关键词和语义都覆盖到；重排把真正相关的排到前面。**判据**：这就是为什么RAG要从Naive走到高级——不是为了"高级"，是为了"能用"——Naive RAG只能应付简单问题，高级RAG才能应付复杂问题。**踩坑**：①以为"Naive RAG够用了"——错，简单场景能跑，复杂场景根本不能用；②以为"高级RAG是锦上添花"——错，它是"从不能用到能用"的关键一步。

**为什么"Naive RAG是'一刀切'的流程"——检索到什么就用什么，不做任何优化**：很多人会问——"Naive RAG不也是先检索、再生成吗？为什么说它不够用？"关键在于：**Naive RAG是"一刀切"的流程——检索到什么就用什么，不做任何优化**——①**Naive RAG是怎么做的**：先检索——从向量库里检索到Top-k个相关文档；再生成——把这些文档塞到prompt里，让大模型根据这些文档回答；它是一个"一刀切"的流程——检索到什么就用什么，不做任何优化；②**为什么说它不够用**：它检索到的文档可能不相关——向量检索是基于语义相似，但语义相似不等于有用；它检索到的文档可能太多——塞到prompt里，大模型看不过来，反而答不好；它没有做任何优化——没有做重排、没有做上下文压缩、没有做查询改写；③**高级RAG做了什么**：它做了重排——把真正相关的排到前面；它做了上下文压缩——把不相关的去掉；它做了查询改写——把用户的问题改写成更适合检索的问题；它做了这些优化，所以它比Naive RAG好用。**判据**：这就是为什么Naive RAG不够用——它只是一个"一刀切"的流程，检索到什么就用什么，它没有做任何优化——你要做高级RAG，你要做这些优化，你才能得到好用的RAG。**踩坑**：①以为"Naive RAG也能跑，就不用做高级RAG了"——错，Naive RAG能跑，但它不够用；②以为"高级RAG就是多加几个模块"——错，高级RAG是"从能用的RAG到好用的RAG"的一道分水岭。

**为什么"要从Naive RAG升级到高级RAG"——Naive RAG不够准，高级RAG更准**：很多人会问——"Naive RAG不也能跑吗？为什么要升级到高级RAG？"关键在于：**要从Naive RAG升级到高级RAG——Naive RAG不够准，高级RAG更准**——①**Naive RAG是干什么的**：它是"最简单的RAG"——检索一下再生成；它不做查询改写——你问什么就检索什么；它不做混合检索——只用向量检索；它不做重排——检索到什么就用什么；②**高级RAG是干什么的**：它是"优化过的RAG"——加了几个模块；它做查询改写——把你的问题改写得更适合检索；它做混合检索——向量检索+关键词检索；它做重排——检索到之后再精排一遍；③**为什么要升级**：因为Naive RAG不够准——召回率60%，精度50%，幻觉率20%；因为高级RAG更准——召回率90%，精度85%，幻觉率5%；因为企业级知识库需要准——Naive RAG不够用。**判据**：这就是为什么要从Naive RAG升级到高级RAG——Naive RAG不够准——召回率60%，精度50%，幻觉率20%——高级RAG更准——召回率90%，精度85%，幻觉率5%——企业级知识库需要准——Naive RAG不够用。**踩坑**：①以为"Naive RAG够用了"——错，简单场景能跑，复杂场景（企业级知识库）必须高级RAG；②以为"高级RAG很复杂"——错，就是在Naive RAG上面加了几个模块（查询改写+混合检索+重排），不是推倒重来。

**为什么"要从Naive RAG升级到高级RAG"——Naive RAG是'一刀切'的流程，不做任何优化**：很多人会问——"Naive RAG不也是先检索、再生成吗？为什么说它不够用？"关键在于：**要从Naive RAG升级到高级RAG——Naive RAG是'一刀切'的流程，不做任何优化**——①**Naive RAG是干什么的**：它是"最简单的RAG"——检索一下再生成；它是一个"一刀切"的流程——检索到什么就用什么，不做任何优化；它不做查询改写——你问什么就检索什么；它不做混合检索——只用向量检索；它不做重排——检索到什么就用什么；②**高级RAG是干什么的**：它是"优化过的RAG"——加了几个模块；它做查询改写——把你的问题改写得更适合检索；它做混合检索——向量检索+关键词检索；它做重排——检索到之后再精排一遍；③**为什么要升级**：因为Naive RAG是"一刀切"的流程——检索到什么就用什么，它没有做任何优化；因为高级RAG做了优化——查询改写+混合检索+重排；因为优化了之后，它就更准了。**判据**：这就是为什么要从Naive RAG升级到高级RAG——Naive RAG是"一刀切"的流程——检索到什么就用什么，它没有做任何优化；高级RAG做了优化——查询改写+混合检索+重排；优化了之后，它就更准了。**踩坑**：①以为"Naive RAG也能跑，就不用做高级RAG了"——错，Naive RAG能跑，但它不够用；②以为"高级RAG就是多加几个模块"——错，高级RAG是"从能用的RAG到好用的RAG"的一道分水岭。

### 7.5.2 父子检索与上下文窗口

**【架构设计说明】**

一个实用技巧：**小块检索、大块喂答案**。用小块（精确匹配）做召回定位，但返回给 LLM 的是它所属的更大块（或父子文档），这样既有检索精度、又给足上下文。这解决了"小块检索准但上下文不足"的矛盾。

**怎么做**：把文档切成两层——父块（较长，如 800 字，上下文完整）和子块（较短，如 200 字，检索精准）。索引时用子块做向量；检索命中某个子块后，返回它所属的父块给 LLM。**踩坑**：父块太大又会把无关内容塞进来，父子大小要按"子块够准、父块够全但不超上下文窗口"来配。

**父子检索落地的关键是"挂关系"**：入库时每个子块向量里都要存一个指针，指向它所属的父块 ID。检索流程于是变成三步：①按 query 向量检索命中子块（如"第3章第5段那个子块"）；②顺着子块里存的父块指针，把对应的父块整块取出来；③把父块（而不是子块）喂给 LLM。**踩坑**：如果子块入库时没存父块指针，命中后就拿不回完整上下文——这是父子检索最容易漏的工程细节，索引设计阶段就得把父子关系字段加上。

**父子检索最常见的错配**：①**父块边界划错**——按字数切父块，正好把"一个完整论点"拦腰切成两个父块，检索到左半边，右半边的因果解释拿不回来，LLM 看到一半就断；②**父子粒度差太大**——子块切得极细（一句话一个），父块却跨了整篇文档，取父块时一次性塞进来半本手册，把上下文撑爆；③**多子块命中同一父块时重复塞**——同一父块的好几个子块都被检索到，结果把同一个父块重复喂给 LLM 好几遍，白白浪费窗口。**判据**：父子切分要按"语义段落"划边界，父子大小梯度要温和，命中后对父块去重。

**"按字数切"和"按语义切"到底差在哪（一个隐蔽但致命的坑）**：很多人图省事，定一个字数（如每 500 字切一块）就开始切，结果切出来的块经常是"半句话结尾 + 半句话开头"。这在检索时暴露两个问题——①**子块语义残缺**：一块里写着"……需在收到后办理"，前面那个"7 天"被切到上一块了，检索到这一块的向量里根本没有"7 天"，语义是断的；②**向量质量差**：embedding 模型对一句"不完整的话"打向量，打的是半截意思的向量，和用户"几天能退"的 query 根本对不上。**判据**：正确做法是**先按自然边界切**——优先在句号、段落、小标题处切，再凑到目标长度；宁可一块 450 字、一块 550 字，也不要在句子中间硬断。**踩坑**：按字数切最隐蔽的危害是"看起来一切正常、检索结果却总不对"——因为切出来的块语法上半通不通，向量相似度算得再准，底层就是些残缺语义，答案自然残缺。

**上下文窗口怎么算这笔账**：LLM 一次能读的总 token 是固定的（如 8k/32k），里面要分给：系统提示、用户问题、**检索回来的片段**、以及留给生成答案的空间。如果 Top-k 设太大（如捞回 10 个大块），光检索内容就把窗口塞满，既没空间生成、还可能超窗报错。**判据**：先算清窗口预算——比如 8k 窗口里，留给检索片段约 4–5k，那每个片段约 500 字就只能放 8 个左右；不是片段越多越好，塞太满模型反而抓不住重点。

**多级索引——从"大而全"到"小而准"的漏斗**：实际生产的检索常做成多级：①第一级在**父块/文档级**粗筛出可能相关的几篇（用快的、粗的向量或标签）；②第二级在这些候选里再用**子块级**精细向量检索，定位到具体段落；③第三级可能再重排。**判据**：单级"一把梭"在文档量大时要么慢、要么不准；多级漏斗是"先用便宜的办法缩小范围，再用贵的办法精挑"，既快又准——这和人翻资料"先看目录定位章节、再细读段落"是同一个套路。

**父子块大小怎么配比（经验值）**：子块一般 100–300 字（短到能聚焦一个要点），父块约子块的 3–5 倍（够把这个要点的前因后果包进来）。**判据**：子块太小会把一句话拆得语义不全、检索反而不准；父块太大则返回给 LLM 的东西里掺了无关内容、还吃上下文窗口。常见做法是父块不超过 LLM 上下文窗口的 1/4，留够空间给提问和答案。

**【已工程验证】拿一个具体文档算这笔账**：假设 LLM 上下文窗口 8000 token，要留出约一半（4000 token）给提问+答案+系统提示，剩给检索片段的约 4000 token。若用父子检索、一次取 3 个父块，则每个父块大约 \(\le 1300\) token 才塞得下。**配比建议**：子块切 200 字（聚焦单一事实点、向量检索准），父块切 800 字（约子块 4 倍，把这个事实的"前因+结论+一句后果"包全）。**判据**：①子块太小（如 50 字）——"退货政策"和"7天"被切成两个子块，检索到"7天"却不知道是说什么的7天；②父块太大（如 3000 字）——一个父块占掉半条窗口、还混着别的条款，LLM 抓不住重点。**踩坑**：别照抄"子块 200 / 父块 800"当铁律——文档是法条就按条款切（一个条款一个父块），是技术手册就按"一个操作步骤"切；父子边界永远跟着**语义单元**走，不跟着字数走。

**为什么不直接拿"子块"喂给 LLM（非得绕一道父块）**：直觉上，既然子块检索最准，为什么不直接把子块塞给 LLM？问题在于**检索准 ≠ 上下文够**。子块切得短（200字），是为了向量聚焦、好检索；但它往往把"一句话"从它的前因后果里孤立出来了——比如检索到的子块只写着"……需在 7 天内办理"，没写"这是退货的规定、过了 7 天怎么办"。LLM 拿到这个孤立子块，要么答不全、要么被迫脑补缺失部分（又回到幻觉）。**父块的作用就是"补上下文"**：命中子块后，把包住它的那个完整父块（含前因后果）一起给 LLM，回答才完整。**判据**：这是个刻意的分工——**子块负责"找得准"（短、聚焦，向量匹配准），父块负责"答得全"（长、完整，上下文够）**。用短块喂 LLM 会缺上下文，用长块做检索又会不准——父子两层正是把"检索的准"和"上下文的全"这对矛盾拆开，各用最合适的粒度。**踩坑**：直接用一个粒度（既检索又喂 LLM）注定两头不讨好——这正是父子块这套"双粒度"设计存在的理由。

**父块到底该是子块的几倍——为什么 4 倍左右是个甜点**：父子比的本质，是平衡"补上下文补多少"和"别塞太多无关内容"。①**父子比太小（如 1.5 倍，父块只比子块长一点点）**：父块几乎等于子块，"补上下文"补了个寂寞——子块缺的前因后果还是没拿回来，父子两层退化成一层，白搞；②**父子比太大（如 20 倍，父块把子块淹没）**：父块里塞进了十几段和这个事实无关的内容，LLM 要在一大堆噪声里自己找重点——既浪费上下文窗口，又容易被无关信息带偏（张冠李戴）。**判据**：4 倍左右的含义是——子块聚焦"一个事实点"，父块把这个事实点的"前因+定义+结论+一句后果"包进来，**刚好是一个完整语义单元的体量**，多一段嫌吵、少一段不全。这不是魔法数字，是"一个论点通常由几句话组成"这个经验来的。**踩坑**：别把父子比当固定配置——法条里一个条款可能就是一个父块（子块是其中一款），技术手册里一个"操作步骤"可能才半屏（父块更小）；跟着"一个完整论点/操作的自然长度"走，字数比自然就落在 3–6 倍这个区间。

### 本章要点

- 多轮对话必做会话上下文增强的查询改写："那它呢？"这类指代句直接拿去检索必然失败，须先用 LLM 结合上文补全成独立完整问题再搜库——这是多轮问答"前面准、后面答非所问"的主因；改写别过度，把用户原意改歪了检索全错。
- 父子块双粒度分工：子块 100–300 字负责"找得准"（向量聚焦单一事实点），父块约子块 3–5 倍负责"答得全"；典型配比子块 200 字/父块 800 字（8k 窗口取 3 个父块时父块须 ≤1300 token），父块别超窗口 1/4，命中多子块同父块时要去重。
- 父子检索的关键工程细节是入库时给每个子块存父块指针，漏了就取不回完整上下文；父子边界按语义单元（句号/段落/条款）划，不按字数硬切——按字数切出的半截句向量语义是断的。
- Naive→Advanced 的差距是量级（本机对比：只向量召回 60%，混合+查询改写 90%）；但简单场景别上高级 RAG——延迟从几百毫秒涨到一两秒、组件翻倍，内部几百篇文档 Naive 就够。
- 是否分层的判据看跨层查询在真实流量中的占比：库小、问题单一一层就够；库大、问题跨主题才搭"原文块/摘要/实体"多层索引互补——为"高级"而分层只会增加维护成本。

## 第7.6章 RAG 全场景坑点与最优解（对应 7.6）

前五章把 RAG 各环节拆开讲了，本章把它们合起来当一台整机验收：一张"坑点—最优解"对照表（切片切断语义、专有名词漏检、矛盾文档、知识库过时等六类高频坑），加一套定量评测方法。读完能用 Faithfulness 与 Context Recall 分层定位故障（低了该改生成端还是检索端）、搭"检索/生成/端到端"三层评测、构造不自嗨的评测集并做上线后的在线持续评测。知识图谱与 GraphRAG 这条结构化路线是第7章的事。

| 专有名词漏检 | 型号/编号搜不到 | 混合检索加 BM25 |
| 上下文塞太多 | 模型抓不住重点 | 控制 Top-k，先 rerank 再喂 |
| 答案不带出处 | 无法核验 | prompt 强制引用标注 |
| 知识库过时 | 答旧信息 | 元数据带时间，检索时过滤最新 |

**检索到互相矛盾的文档怎么办（很常见）**：库里《员工手册2023》说"报销需3个工作日"，《2024新规》说"改为1个工作日"——两条都被检索到，LLM 该听谁的？**解法**：①**带时间戳、按新优先**——元数据里记录文档生效时间，prompt 里明示"如遇冲突，以更新日期者为准"；②**让模型主动暴露冲突**——不要让它挑一个悄悄说，而是在答案里说明"存在两个版本的规定，最新的是X，旧的是Y"，把判断权交回用户；③**建库时就做版本管理**——旧版本标记为"已废止"，检索时直接过滤掉。**判据**：RAG 最怕"把矛盾信息揉成一个似是而非的答案"；正确做法是显式呈现冲突、并按时间/权威性排序，而不是让模型含糊地带过。

**RAG 怎么定量评测（本机小算例）**：RAG 系统好坏不能只看"答得像不像"，要拆开看两件事——
- **Faithfulness（忠实度）**：答案里的陈述有几条能被检索上下文支撑？本机算例：答案有 5 个陈述、其中 4 条有据 → Faithfulness = 4/5 = **0.80**。这个低，说明模型在上下文之外**瞎编（幻觉）**。
- **Context Recall（上下文召回）**：标准答案需要的事实，有多少被检索到了？本机算例：标准答案 6 个关键事实、检索上下文覆盖了 5 个 → Context Recall = 5/6 = **0.83**。这个低，说明**该找的资料没找全**。

**关键判据**：Faithfulness 低要改"生成端"（约束模型别自由发挥）；Context Recall 低要改"检索端"（换 embedding、加 rerank、调切片）——两个指标定位的是完全不同的故障，不能混为一谈。

**RAG 评测要分三层看，别只盯一个数**：
| 评测层 | 测什么指标 | 低了说明哪坏 |
|---|---|---|
| 检索层 | Context Recall、检索命中率、MRR | 该找的没找全（换embedding/切片/rerank） |
| 生成层 | Faithfulness、答案与来源一致性 | 模型在有据之外瞎编（约束生成、加强引用） |
| 端到端层 | 答案与标准答案的整体相似度、人工满意度 | 即使检索生成都对，答案仍可能答非所问 |

**判据**：一个常见误区是只看"最终答案像不像标准答案"——但这无法区分到底是没找到资料、还是找到了却没好好用。必须分层定位：先看检索层好不好（资料找没找全），再看生成层（资料有没有被忠实用上），最后才看端到端。这样出了问题才知道改哪一头，而不是瞎调一通。

**离线评测分高，线上却翻车——为什么对不上**：离线评测用的是"你精心挑的一批标准问答"，分布很窄、很干净；线上真实用户的问题五花八门、口语化、还常信息不全。**几个典型落差**：①离线问题都"问得清楚"，线上问题常缺关键词、有歧义；②离线库里文档都新鲜，线上是历史堆；③离线指标（faithfulness/recall）测的是"有据与否"，但用户真正在意的是"答得好不好用"，这两者不完全等同。**判据**：离线评测用来快速对比方案、挡住明显的坏版本；但它不能代替线上真实抽样——上线后必须持续收集真实问题做评测，否则就是"在干净的训练集上自嗨"。

**为什么"faithfulness 100%"用户还在骂（指标和满意度错位）**：faithfulness 只保证"答案里每句话都能从检索到的上下文里推出来"——但它**不管两件事**：①**上下文选对了没**——如果检索回来的就是一段错的/过期的文档，模型"忠实"地把错误答案复述出来，faithfulness 照样是满分，但用户拿到的是错答案；②**答到点子上没**——模型可能把整段政策都背了一遍，faithfulness 满分，可用户问的是"我到底能不能退"，它没直接回答。**判据**：所以评测不能只看 faithfulness（忠实度），还要配——**context recall（检索回来的上下文，覆盖了回答这个问题所需的全部信息吗？）** 和**答案有用性/相关性（是否直接答了用户问的那件事）**。**踩坑**：只盯 faithfulness 会把系统调成"句句有据但句句不解决问题"——指标好看、用户抓狂。这也是为什么好的 RAG 评测是一个指标组合，不是单一分数。

**为什么幻觉注定压不到零——概率模型的本性，工程只能压不能除**：很多团队定了个"幻觉率为 0"的目标，这其实是违背原理的。底层那个生成模型是个**概率模型**——它逐 token 预测"下一个最像什么"，本质是在"猜"，而不是在"严格查表"。哪怕你给它检索到的正确上下文，它也可能在组织语言时，**把上下文里没有的词顺嘴"补"上去**（比如上下文只说"7天内"，它顺嘴写成"7个工作日内"——多出来的"工作"两个字就是幻觉，但读起来天衣无缝）。**判据**：所以幻觉是这个"概率生成"范式自带的天性，不是"没调好的 bug"。工程能做的是——①**用 RAG 给它喂正确上下文**，大幅压低它"自由发挥"的空间（从"瞎编一大段"降到"偶尔补一两个词"）；②**用引用回查**，把"补出来的句子"自动抓出来删掉。但要做到"一个幻觉词都没有"，就得牺牲掉生成的自然流畅度（比如改成"严格只允许复述原文、一个字不许加"——那就不像助手了、像个复读机）。**踩坑**：把"幻觉率=0"当 KPI 硬压团队，结果他们把模型调成"只敢复述检索片段、绝不敢多写一个字"——幻觉是没了，可答案也变得生硬、不连贯、不好用了。**记住：压幻觉和"答案好用"是有 trade-off 的——成熟做法是把幻觉率压到"可接受的低位"（而不是零），同时保住回答的流畅和有用**。

**为什么"RAG能压幻觉"——大模型是'根据这些文档来回答'，它不是'自己编'**：很多人会问——"RAG不就是'检索一下再生成'吗？为什么它能压幻觉？"关键在于：**RAG能压幻觉——大模型是"根据这些文档来回答"，它不是"自己编"**——①**幻觉是干什么的**：幻觉就是"大模型一本正经地胡说八道"；它会编出一些不存在的事实；它会编出一些不存在的引用；②**RAG是干什么的**：RAG是"检索增强生成"；它先检索——从文档库里检索到相关的文档；它再生成——根据这些文档来回答；③**为什么RAG能压幻觉**：因为大模型是"根据这些文档来回答"——它不是"自己编"；它有了"参考资料"——它就不会"自己编"了；它的回答是"有依据的"——它不是"凭空想的"。**判据**：这就是为什么RAG能压幻觉——大模型是"根据这些文档来回答"——它不是"自己编"——它有了"参考资料"——它就不会"自己编"了——它的回答是"有依据的"——这就是为什么RAG能压幻觉。**踩坑**：①以为"RAG只是个检索"——错，它是让大模型"有依据"，不是"自己编"；②以为"RAG能把幻觉压到0"——错，它压的是"无依据的幻觉"，压不了"依据本身是错的"。

**为什么"RAG能压幻觉"——纯生成是'凭空编造'，RAG是'有参考资料'**：很多人会问——"纯生成大模型不也挺好吗？为什么它有幻觉问题？"关键在于：**RAG能压幻觉——纯生成是"凭空编造"，RAG是"有参考资料"**——①**纯生成是干什么的**：纯生成就是"大模型自己凭空编"；它没有参考资料；它完全靠自己的记忆来回答；它会编出一些不存在的事实；②**RAG是干什么的**：RAG是"检索增强生成"；它先检索——从文档库里检索到相关的文档；它再生成——根据这些文档来回答；③**为什么RAG能压幻觉**：因为纯生成是"凭空编造"——它没有参考资料；因为RAG是"有参考资料"——它看着检索到的文档来回答；因为有参考资料，它就不容易瞎编。**判据**：这就是为什么RAG能压幻觉——纯生成是"凭空编造"——它没有参考资料；RAG是"有参考资料"——它看着检索到的文档来回答；有参考资料，它就不容易瞎编。**踩坑**：①以为"纯生成大模型很聪明，不会瞎编"——错，它会瞎编——它会编出一些不存在的事实；②以为"RAG能把幻觉压到0"——错，它压的是"无依据的幻觉"，压不了"依据本身是错的"。

**为什么"RAG能压幻觉"——大模型瞎编是因为它不知道答案**：很多人会问——"大模型这么聪明，为什么它会瞎编？"关键在于：**RAG能压幻觉——大模型瞎编是因为它不知道答案**——①**幻觉是干什么的**：幻觉是"大模型瞎编"；它是一个"大模型一本正经地胡说八道"的问题；它让大模型说一些完全不存在的东西；②**为什么RAG能压幻觉**：因为大模型瞎编是因为它不知道答案——它只能瞎编；因为RAG给了它答案——它从知识库检索到了答案；因为它就不用瞎编了——它可以照着知识库说；③**为什么这是关键**：因为"有没有答案"就是"会不会瞎编"的区别——你没有答案，你就会瞎编；你有答案，你就不用瞎编。**判据**：这就是为什么RAG能压幻觉——大模型瞎编是因为它不知道答案——它只能瞎编；RAG给了它答案——它从知识库检索到了答案；它就不用瞎编了——它可以照着知识库说。**踩坑**：①以为"大模型很聪明，不会瞎编"——错，它不知道答案的时候它就会瞎编；②以为"RAG能把幻觉压到0"——错，它压的是"无依据的幻觉"，压不了"依据本身是错的"。

**评测集怎么构造才不"自嗨"**：好的 RAG 评测集不能只靠人编理想问题，要包含——①**真实问法**：从客服/工单日志里捞真实用户怎么问（口语、错字、省略都保留）；②**覆盖难例**：专门放"库里其实没有答案""需要跨多段拼接""多轮有指代"这类坑题；③**每道题配好标准答案和应该命中的文档**，这样才能自动算 recall/faithfulness。**判据**：评测集要像"考试题"——既有基础题、也有陷阱题；只考简单题，系统刷满分也不代表线上能用。评测集本身也要随线上真实问题持续更新，否则它会慢慢过时。

**上线后怎么持续测（在线评测）**：离线评测集再全也覆盖不了线上真实问题的分布变化。所以线上要做：①**抽样打分**——每天随机抽一小批真实问答，用人工或一个小评审模型打分，盯平均分有没有掉；②**用户反馈信号**——点踩/重问/复制答案率，都是"答案不好"的间接信号；③**影子流量**——新版 RAG 先接一小部分真实请求但不真正答，只在后台和线上版对比，发现明显变差就不上。**踩坑**：只靠离线集验收一次就不管，是 RAG 上线后效果慢慢烂掉的典型原因。

**离线评测"标准答案"单一，掩盖了真实问题要"综合"的难点**：离线集每题通常写一个"标准答案"，评测就是拿模型答案和它比相似度——这假设了"这个问题有一个唯一正确答案"。但真实用户的问题往往是**多文档综合型**：比如"我这个情况能不能报销"，答案取决于"我是什么岗位""发票是几月的""有没有特殊审批"——没有一个文档直接写全，需要模型跨好几段拼起来、甚至要先反问澄清。离线集里这种问题很少（因为标准答案太难写），结果就是——**系统在"单文档可直接回答"的题上刷了高分，一到线上需要综合多文档、需要澄清的题就露怯**。**判据**：好的离线评测集必须刻意收录一批"无单一标准答案、需要跨段综合/需要拒答澄清"的题，并配人工评判而不是"和标准答案比相似度"。**踩坑**：全靠"答案和标准答案的字符相似度"自动打分，会把系统往"背标准答案"方向调——而真实业务要的不是背答案，是"在资料里找出相关部分、组织成对当前用户有用的回答"。

### 本章要点

- Faithfulness 和 Context Recall 定位的是完全不同的故障（本机算例：答案 5 条陈述 4 条有据 → Faithfulness=0.80，该改生成端；标准答案 6 个关键事实覆盖 5 个 → Context Recall=0.83，该改检索端）——不能混为一谈，更不能只看端到端相似度瞎调。
- faithfulness 100% 用户仍可能骂街：它不管检索回来的资料本身错没错（忠实复述错误文档照样满分），也不管答没答到用户问的点上——评测必须配 context recall 和答案有用性/相关性。
- 评测分三层看：检索层（Context Recall/MRR，低了换 embedding/调切片/加 rerank）→ 生成层（Faithfulness，低了约束生成加强引用）→ 端到端（人工满意度）——出问题按层定位改哪一头。
- 矛盾文档（新旧两版制度都被检索到）不能让模型悄悄揉成一个答案：元数据带生效时间、prompt 明示"以更新日期者为准"、答案显式呈现两个版本、建库时旧版本标"已废止"并过滤。
- 评测集要像考试卷：收录客服/工单日志的真实问法（口语、错字保留）、难例（库里没答案/跨多段综合/多轮指代）、每题配标准答案与应命中文档；上线后靠每日抽样打分、点踩/重问率、影子流量持续验收——只靠离线集验收一次是 RAG 效果慢慢烂掉的典型原因。

## 第7.7章 知识图谱与结构化知识（对应 7.7）

向量与 BM25 都答不了"A 的供应商的老板是谁"这类多跳关系题，本章引入知识图谱与 GraphRAG 作为第三条检索范式。读完能判断给定场景该不该建 KG（关系密集、多跳刚需才值得——抽取与人工校对成本都很高），能写出两跳图查询的思路（实体→关系→实体沿边走），并在点查询与全局性问题之间选普通 RAG 还是 GraphRAG（后者建图加社区摘要的预处理很重）。本章之后，"什么时候连 RAG 都不该用"由第8章整体收尾。

### 7.7.1 为什么光向量不够

**【架构设计说明】**

向量检索擅长"语义相似"，但不擅长**多跳推理**（"A 的供应商的老板是谁"这类关系链）和**精确关系**。知识图谱（Knowledge Graph, KG）用"实体—关系—实体"三元组显式存关系，能做图上的多跳查询。

**三元组是什么**：知识图谱的基本单元是 `(头实体, 关系, 尾实体)` 三元组。例如 `(上海巧未来, 总部位于, 上海)`、`(唐资鉴, 创立, 上海巧未来)`。把文档里的这类关系抽出来连点成网，就能沿边做多跳查询。

**三元组抽取怎么做**：从非结构化文档里，用 NLP/LLM 标注出句子里的实体和它们之间的关系，落成三元组。**踩坑**：抽取质量决定图谱质量——实体识别错、关系判错，整个图谱就是错的；而且人工校对成本很高，所以 KG 通常只在关系密集、多跳刚需的领域才值得建。

**多跳查询怎么写（图查询语言）**：查"唐资鉴创立的公司总部在哪"，翻译成图查询就是：顺着 `(唐资鉴, 创立, ?公司)` 这条边找到公司节点，再从该节点顺着 `(公司, 总部位于, ?地点)` 边走到地点——这就是"两跳"。图数据库用专门的查询语言（如 Cypher 这类声明式图查询）写。**对比向量检索**：向量检索给的是"语义相近的文档片段"，图查询给的是"沿关系链精确走到的答案"——前者模糊、后者精确，正好互补，这也是 GraphRAG 要把两者结合的原因。

**几种检索范式对比**：
| 范式 | 找什么 | 擅长 | 不擅长 |
|---|---|---|---|
| 关键词（BM25） | 词面匹配 | 专有名词/编号 | 语义同义 |
| 向量（embedding） | 语义相似 | 同义/改写 | 精确词、多跳 |
| 知识图谱 | 关系链 | 多跳推理 | 自由文本问答 |
| 混合（hybrid） | 多路融合 | 兼顾 | 工程复杂 |

**判据**：没有万能检索——按问题类型选范式，或混合。大多数生产系统最终走"向量+BM25 混合"，再叠一层重排。

**为什么查"型号 XK-2039"这种编号，向量检索会翻车、BM25 一击即中**：这是"语义检索 vs 关键词检索"分工最典型的例子。①**向量检索的思路**：它把"XK-2039"这段文本编码成一个向量——可问题是，这个编号本身没有语义（它不是"猫"也不是"车"），embedding 模型对它的理解就是"一串没什么含义的字符"。于是向量空间里，"XK-2039"和"XK-2040""XK-2038"这些长得像的编号**余弦相似度都很高**——向量分不清你要的是 2039 还是 2040，因为它们"看起来差不多"。②**BM25 的思路**：它不管什么语义，就是看字面——你查"XK-2039"，它就精确匹配这个字符串，命中的那篇文档分直接拉满，"XK-2040"根本不命中。**判据**：所以查"精确的、唯一的、无语义的标识符"（型号、编号、人名、文件名、错误码），BM25 是碾压式的——它要的就是"字面一字不差"，而这恰恰是向量最不擅长的（向量擅长"意思相近但说法不同"，最怕"长得像但其实是两个不同东西"）。**踩坑**：很多团队迷信"向量最先进"，把 BM25 那一路砍了，结果用户查"报错码 E-1024"时，向量库给他返回一堆"E-102""E-1020"这种沾边但不对的——因为向量觉得它们长得像。**记住：语义模糊的问题找向量、字面精确的问题找 BM25**——这就是为什么生产系统永远是两者混合，而不是二选一。

**为什么向量检索找不到"订单号12345"——它不理解"精确匹配"这个概念**：很多人会问——"用户输入'订单号12345'，向量检索为什么找不到？它不就是把这句话变成向量，然后找最像的文档吗？"关键在于：**向量检索只看"意思像不像"，不看"字面对不对"**——①**订单号12345这句话的"意思"是什么？**它没有语义——它只是一个编号。embedding模型把它变成向量后，这个向量在向量空间里的位置，和"订单号12346""订单号12344"这些编号的位置都差不多（因为它们"长得像"）；②**你要找的是"精确匹配12345"**——不是找"意思差不多的编号"，是找"完全等于12345的那个"。向量检索做不到这一点——它只会返回"离你最近的那几个"，但那几个可能是12344、12346，就是不是你要的12345。**判据**：向量检索擅长"模糊语义搜索"，不擅长"精确字符串匹配"。你要找"退货流程"——向量检索能找到（因为它理解"退货"和"退款"意思差不多）；你要找"订单号12345"——BM25才能找到（因为它精确匹配这个字符串）。**踩坑**：①以为"向量检索万能"——错，它有明确的盲区；②以为"用户输入什么都能用向量搜"——错，精确匹配类的查询必须用BM25。

**为什么要混合检索——向量和BM25各有各的强项，合起来才完整**：很多人会问——"既然向量和BM25各有各的问题，那为什么不干脆两个都用？"关键在于：**向量和BM25是互补的，合起来才完整**——①**向量擅长什么**：找"意思差不多但说法不同"的文档——用户说"退货"，它能找到写着"退款"的文档（因为它理解这两个词意思差不多）；②**BM25擅长什么**：找"字面上完全一样"的文档——用户说"订单号12345"，它能精确找到这个编号所在的文档；③**为什么要合起来**：因为用户的查询是混合的——有的是"模糊语义查询"（比如"怎么退货"），有的是"精确匹配查询"（比如"订单号12345"）。你只用向量，就会漏掉精确匹配的查询；你只用BM25，就会漏掉模糊语义的查询。**判据**：这就是为什么生产系统都用混合检索——向量负责"模糊语义搜索"，BM25负责"精确字符串匹配"，两个结果合起来，再排个序。**踩坑**：①以为"选一个最好的就行"——错，它们是互补的，不是替代关系；②以为"混合检索太复杂"——错，混合检索就是"两个检索器都跑一遍，结果合起来排序"，工程上不难。

**为什么向量检索有"天花板"——它只能找"语义相似"，找不到"精确关系"**：很多人会问——"向量检索这么厉害，为什么不能解决所有问题？"关键在于：**向量检索有它的天花板——它只能找"语义相似"，找不到"精确关系"**——①**向量检索擅长什么**：找"意思差不多"的文档——你说"退货"，它能找到写着"退款"的文档；②**向量检索不擅长什么**：找"精确关系"——你问"A的供应商的老板是谁"，这需要多跳推理（A→供应商→老板），向量检索做不到——它只能找到"和A语义相似的文档"，不能沿着关系链一步步走；③**为什么这是天花板**：因为向量检索的本质是"算余弦相似度"——它只关心"这两段文本在向量空间里离得近不近"，它不关心"这两个实体之间是什么关系"。**判据**：这就是为什么向量检索有天花板——它只能找"语义相似"，找不到"精确关系"。要找精确关系，你得用知识图谱（或者GraphRAG这种混合方案）。**踩坑**：①以为"向量检索万能"——错，它有明确的天花板；②以为"向量检索能做多跳推理"——错，多跳推理是知识图谱的强项，不是向量检索的。

**为什么"光向量检索不够"——有些信息是'关键词'的，向量检索找不到这些关键词**：很多人会问——"向量检索不就是'把文档变成向量，再算相似度'吗？为什么它不够？"关键在于：**光向量检索不够——有些信息是"关键词"的，向量检索找不到这些关键词**——①**向量检索是干什么的**：它是"把文档变成向量，再算相似度"；它擅长找"语义相似"的文档；它不擅长找"关键词匹配"的文档；②**为什么光向量不够**：因为有些信息是"关键词"的——比如型号、编号、日期；向量检索找不到这些关键词——它只看语义相似；你要做混合检索——向量检索+关键词检索；③**为什么这是关键**：因为"能不能找到关键词"就是"检索够不够用"的区别——你不能找到关键词，你就不够用；你能找到关键词，你就够用。**判据**：这就是为什么光向量检索不够——有些信息是"关键词"的——比如型号、编号、日期；向量检索找不到这些关键词——它只看语义相似；你要做混合检索——向量检索+关键词检索。**踩坑**：①以为"向量检索万能"——错，它找不到关键词；②以为"混合检索太复杂"——错，混合检索就是"两个检索器都跑一遍，结果合起来排序"，工程上不难。

### 7.7.2 GraphRAG：图与向量结合

**【架构设计说明】**

**GraphRAG** = 知识图谱 + 向量检索：先从文档抽取实体和关系建图，再对图做社区摘要；回答问题时既能向量定位、又能沿关系链推理。适合"全局性问题"（这份文档主要讲了哪些主题及其关联）。【待核验：GraphRAG 作为方法论的提出方与具体实现细节】

**它和普通 RAG 的分工**：普通向量 RAG 擅长"找一条具体证据回答一个具体问题"（点查询）；GraphRAG 擅长"鸟瞰一堆文档讲了哪些主题、主题之间怎么关联"（全局问题）。代价是建图+社区摘要的预处理很重——文档量大、问题却都是点查询时，上 GraphRAG 是杀鸡用牛刀。

**实体关系图到底怎么一步步建索引**：①**抽实体**——对每份文档切块，用 LLM 逐块抽取里面出现的人名、机构、产品、地点等实体，并给每个实体一个归一化名字（"上海巧未来"和"巧未来公司"要合并成同一个节点）；②**抽关系三元组**——同时抽出实体之间的 `(头,关系,尾)` 关系，落成边；③**去重合并节点**——跨文档把指向同一实体的节点合并，关系边连起来，形成一张网；④**做社区检测+摘要**——用图算法把大网切成一个个"关系紧密的小圈子"（社区），每个社区生成一段摘要。建完后，回答全局问题时就不用逐块捞向量，而是直接"这堆文档里有哪几个主题社区、它们各自讲了啥"。**判据**：这四步里最吃成本的是①②——LLM 逐块抽实体关系要花大量调用，文档一多预处理账单就很可观；这也是 GraphRAG"重"的根本原因。

**块长为什么直接决定检索质量——它其实是在"语义完整"和"检索聚焦"之间走钢丝**：很多人切块时随手设个 500 字就不管了，其实这个值直接决定你 RAG 的上限。**①块太小（100 字）**：每块很聚焦、也省 token，但一句话都凑不齐——比如切出一块"……所以必须在 7 天内办理。"，这块向量里根本不知道"7 天"指的是什么事（退货？保修？），用户问"几天能退"时，这块因为语义残缺根本匹配不上；**②块适中（400–500 字）**：一块正好讲清一个小主题（如整段"退货时效"），既有完整上下文、又不杂，检索时既能命中、LLM 拿到也读得懂；**③块太大（1500 字）**：一块里塞了好几个主题（前面讲报销、中间讲请假、后面讲打卡），embedding 出来的是"把好几个话题平均掉"的模糊向量——检索时"报销"这个词命中了，却把整坨"报销+请假+打卡"全带出来喂给 LLM，噪声大、还浪费宝贵的上下文窗口。**判据**：块长的本质权衡是——**太小则缺上下文（语义残缺、检索对不上），太大则混多主题（向量模糊、检索带噪）**。经验起点是 300–600 字配 10–20% 重叠，再按文档类型调（FAQ 短块、长篇报告可稍大）。**踩坑**：①把所有文档切成同一个固定长度——FAQ 和技术手册的最优块长根本不是一个数；②切完不实测——拿几个真实问题看看"命中的块到底读不读得懂"，再回头调块长，比拍脑袋设 500 字靠谱得多。**记住：切块不是"把文档切短"这个粗活，它是 RAG 质量的第一道闸门——块切得不好，后面 embedding 再准、模型再强也救不回来**。

**什么时候才值得上 GraphRAG（判据）**：问自己三个问题——①用户会不会问"这批资料整体在讨论什么主题、它们之间什么关系"这类全局性问题？②答案需不需要"跨多份文档、沿关系链"才能拼出来（普通向量检索一次只能捞回零散片段，拼不出全局图景）？③实体和关系够不够结构化、值得花大成本建图？三个都"是"，GraphRAG 才值。**踩坑**：很多团队一上来就建大图，结果用户问的全是"这个条款第几款"这种点查询——图谱白建了。**判据**：GraphRAG 是"为全局/多跳问题"量身定做的重武器，不是默认配置；普通业务先用向量+BM25 混合 RAG 起步，等真遇到"需要跨文档全局归纳"的瓶颈再上图谱不迟。

**社区摘要凭什么能回答"这批资料整体讲了啥"（机制）**：普通向量 RAG 面对全局问题有个硬伤——它只能"按相似度捞出和这句提问最像的几个片段"。可"这批资料主要在讨论什么"这种问题，**没有任何一个具体片段和它相似**（它是对全部资料的归纳），向量检索无从下手。GraphRAG 的解法是**预先把全局归纳做好**：建图时已经把文档切成了若干"主题社区"（如"组织架构社区""产品社区""融资社区"），每个社区都预算了一段摘要。于是问"整体讲了啥"时，不用临时去捞零散片段，而是**把各个社区的摘要汇总起来喂给 LLM**——LLM 拿着现成的分区归纳，再汇总成全局图景。**判据**：本质是把"在线临时检索"换成了"离线预算好的分层摘要"——代价是建图那一大笔预处理，但换来的是"全局性、跨文档归纳"这种普通 RAG 根本答不了的能力。**踩坑**：社区切分太大（一个社区装了一堆不相关主题）或太小（切碎了、摘要没信息量）都会让全局问答质量塌方——社区划分的粒度，是 GraphRAG 调优的关键旋钮。

---

> **关键判据**：判断知识图谱是否有价值，看它能否回答向量检索答不了的关系型与多跳问题；只做实体链接的图谱没有增量价值。

> **本章可检索来源**：arXiv:1902.10197（RotatE：复数空间中的关系旋转知识图谱嵌入，2019）

### 本章要点

- KG 的基本单元是 `(头实体, 关系, 尾实体)` 三元组；多跳查询沿边走（如 (唐资鉴,创立,?公司) → (公司,总部位于,?地点) 两跳），用 Cypher 等图查询语言——向量给"语义相近的片段"、图查询给"沿关系链精确走到的答案"，正好互补。
- 四种检索范式按问题类型选，没有万能选项：BM25 管词面/编号、向量管语义改述、知识图谱管多跳关系、混合兜底——生产系统多数以"向量+BM25 混合再加重排"起步。
- GraphRAG 专门回答全局性问题（"这批资料整体讲什么、主题怎么关联"）——这类问题没有任何单一片段与之相似，向量检索无从下手，只能靠预建的社区摘要离线归纳；点查询用普通 RAG 即可。
- 上 GraphRAG 前先过三问：有没有全局性问题？要不要跨文档沿关系链拼答案？实体关系够不够结构化？三个都"是"才值得建——LLM 逐块抽实体/关系是建图四步里最吃成本的一步，文档量大且全是点查询时上 GraphRAG 是杀鸡用牛刀。
- 抽取质量决定图谱质量：实体须归一化合并（"上海巧未来"="巧未来公司"）、跨文档去重连边；实体识别错、关系判错则整张图全错——只做实体链接、答不了向量答不了的关系型/多跳问题的图谱，没有增量价值。

## 第7.8章 何时不该用 RAG（对应 7.8）

前七章讲"怎么把 RAG 做好"，本章反过来讲"什么时候根本不该上 RAG"：五维判据体系（知识稳定性、时效性、可追溯、延迟预算、成本预算）、四类替代方案（长上下文直读/微调注入/结构化知识库/BM25 传统检索）、两个决策算例与七步走查清单。读完能为给定知识库算清"单查询账"与"更新账"两笔账并给出路线结论（静态 10 万份大库上 RAG 的单查询边际成本约为直读的 16.7 万分之一；日更资讯流上微调在时效与成本两个维度同时崩掉），并按清单逐步走查、避免把 RAG 当默认架构的过度设计。

**【架构设计说明】**

RAG 不是万能的。以下场景**不该上 RAG**：

1. **知识量极小且稳定**：几条规则直接写进 system prompt 更简单，别为 10 个文档搭向量库；
2. **需要强计算/精确推理**：数学、代码执行类问题，RAG 检索几段文字帮不上，要靠工具调用（tool use）或代码解释器；
3. **数据不需外部知识**：纯创作、闲聊、翻译，直接用 LLM 本身即可；
4. **问题答案不在文档里**：RAG 只能"从已有资料找"，没有的资料它变不出来；硬上会让模型在缺乏证据时强答，反而更易幻觉；
5. **数据高度隐私且不能出域**：要评估 embedding/向量库是否本地可部署，否则数据合规是硬伤。

**【已工程验证】"知识量多小就别上 RAG"的一条实操线**：判断该不该搭向量库，问自己——**全部知识能不能一次性塞进 system prompt？** 比如就 5 条报销规则、约 300 字，直接写进 system prompt（每次请求都带着），最简单、检索零成本、也不会漏。一旦知识涨到——①**几百上千条、还天天更新**（塞不进 prompt、塞进去也爆上下文）；②**不同用户该看到的知识不同**（不能一股脑全塞）；这时才值得上 RAG。**判据**：一个简单的分水岭是——**知识能否"全量常驻上下文"**。能（小而稳）→ prompt 一把梭；不能（多、变、按人分发）→ RAG。**踩坑**：很多团队第一条业务线就上 RAG——搭向量库、做切片、写检索，折腾两周，其实那点知识 300 字塞进 prompt 就解决了。RAG 是为"知识装不下、管不动"准备的重武器，不是开场白。

**关键判据**：RAG 适合"**私有、动态、可引用的事实型问答**"；不适合"**需要推理计算、知识已固化、或答案根本不在库里**"的场景。选错方案，RAG 会比直接问 LLM 更慢更贵还更错。

**RAG、微调（fine-tuning）、提示词工程——三者到底怎么选**：很多人纠结"到底该 RAG 还是微调"，其实各有分工——
| 方案 | 适合什么 | 不适合什么 |
|---|---|---|
| 提示词 | 知识量极小、规则稳定、写进 system prompt 就够 | 知识多、经常变 |
| **RAG** | 知识量大、频繁更新、要能溯源引用 | 要改变模型"风格/技能/语气" |
| **微调** | 要固化某种风格/格式/技能（如永远按某模板输出）、知识稳定且要融进模型骨子里 | 知识天天变（微调改不动、得重训） |

**判据**：一句话记法——**"知识"用 RAG（因为知识会变、要可查），"能力/风格"用微调（因为要固化进权重）**。比如"客服要知道最新的退换货政策"（知识、会变）→ RAG；"客服永远要用亲切活泼的语气、按固定五步模板回复"（风格）→ 微调。很多团队过早微调，其实那只是"把会变的知识硬训进模型"，改一次政策就得重训一遍——这正是 RAG 要解决的问题。**踩坑**：别把 RAG 当万能补丁，也别把微调当万能补丁——先分清你要解决的是"知识"还是"能力"。

**现实里常常是"两者一起上"（别二选一）**：绝大多数成熟系统不是纯 RAG 或纯微调，而是——**用微调把模型调成"适合这个业务的底子"**（学会亲切语气、学会先查证据再答、学会拒答话术），**再用 RAG 给它接最新的私有知识**。比如一个医疗问答助手：微调教会它"用严谨的医学口吻、不瞎编、答不上来就建议就医"（这是风格和安全边界），RAG 接最新的临床指南和药品说明书（这是会变的事实知识）。**判据**：微调管"它是什么样的助手"，RAG 管"它手头有哪些资料"。**踩坑**：①只 RAG 不微调——模型语气不对、还容易自由发挥，检索到证据也不会好好引用；②只微调不接 RAG——知识被冻在训练那天，之后新药、新政策它全不知道。成熟答案是"微调定风格+RAG 供知识"，两者分工、不是互斥。

**三问自检（决定要不要上 RAG）**：
1. 答案在不在你的私有资料里？→ 不在，就别用 RAG；
2. 知识会不会频繁更新？→ 不变且只有几条，写进 prompt 就行；
3. 要不要"出处可查"？→ 要，才值得为引用标注搭 RAG。
三问里两个以上答案偏"否"，说明该场景直接调 LLM 或用工具调用，不必上向量库。

### 7.8.1 "不该用 RAG"的五维判据体系

上面的三问自检是快速粗筛。真要把"该不该上 RAG"判准，需要把这问题拆成五个可测量的维度，逐项打分——**任何一个维度单独不构成否决，但五维中多数指向"知识小而稳"时，RAG 就是负资产**。

**维度一：知识稳定性**。可操作判法：统计过去 90 天内知识条目的变更次数（新增 + 修改 + 删除）。变更次数 ≤ 3 次、且全库总量不足数千字 → 直接写入 system prompt，检索零必要；变更次数 ≥ 90 次（约日均 1 条以上）→ 检索架构开始有收益；介于两者之间 → 看维度二。为什么 90 天？因为它跨了一个季度——大多数业务知识（政策、价格表、FAQ）的修订周期是季度性的，只看一周会低估变化率，只看一天几乎总是为零，两者都会误判为"稳定"。

**维度二：时效性容忍度**。可操作判法：问业务方一句——"答案允许滞后多少天？"若允许滞后 ≥ 30 天，微调重训（天到周级）都赶得上；若要求滞后 ≤ 1 小时（行情、工单、库存），只有增量索引（分钟到小时级生效）能达标，微调彻底出局；若允许滞后为零（答案本身就是实时数据），那连 RAG 都不够，要走 API/工具调用实时取数。关键在于：**时效要求决定的是"更新机制"，而更新机制直接排除掉一整类方案**。

**维度三：可追溯要求**。可操作判法：答案出错时，是否需要向审计、法务或用户出示"这条答案来自哪份文档哪一段"？需要 → 答案必须绑定证据，只有 RAG（引用 chunk）或结构化库（引用记录）能提供，微调注入的知识**无法溯源**——权重里的知识没有出处。金融、医疗、法务场景此项通常是一票否决。

**维度四：延迟预算**。可操作判法：先拿到端到端延迟预算（如 P95 ≤ 2 秒），再减去 LLM 生成时间（流式首 token 通常数百毫秒到 2 秒），剩下的才是检索预算。两阶段检索（向量召回 + 交叉编码器重排）在 top-k 较大、库较大时，重排一步就可能吃掉 300–800 毫秒（本卷 3.2 节有量级参考）；预算剩不到 500 毫秒时，要么砍掉重排、要么上缓存、要么承认这个场景不该用 RAG 而该用直读。

**维度五：成本预算**。可操作判法：算清三笔账——① 一次性建库账（embedding 全库 + 向量库存储）；② 单查询边际账（检索 + 注入上下文的额外 token 费）；③ 维护账（知识更新、索引重建的人力）。若全库直读的 token 费低于"RAG 三笔账之和"，且延迟也过关，RAG 不成立。8.3 节给出完整算例。

> **关键判据**：五维中若"稳定性、时效性、成本"三项同时指向"小、稳、便宜"，禁止上 RAG——先写 prompt。

### 7.8.2 四类替代方案对比：何时够用、多贵、迁移多难

判据体系告诉你"RAG 可能不该上"，接下来要回答"那该上什么"。候选方案共四类，逐一给适用条件、成本量级与迁移代价。

**方案一：长上下文直读**。把全部（或足够多）原始文档直接塞进一次请求的上下文窗口，不做任何检索。适用条件：全库 token 总量 ≤ 模型上下文窗口，且单次会话确实用得上其中大部分。截至 2024 年前后，主流旗舰模型上下文窗口在 128K 至百万 token 量级【待核验：各家最新窗口规格，以官方文档为准】。但"塞得下"不等于"用得好"：Liu et al. 的 Lost in the Middle（arXiv:2307.03172）用受控实验证明，模型对长上下文**中段**信息的利用率显著低于首尾——文档越多，埋在中部的关键事实越容易被忽略。成本量级：单查询成本与全库 token 数成正比，库为 5 万 token 时每次请求都要为这 5 万 token 付费，比 RAG 只送 top-5 片段贵一到两个数量级；库越大，单查询成本线性上涨。迁移代价：几乎为零——不改代码结构，只改 prompt 拼装方式，从 RAG 撤回直读通常半天完成；反向迁移（直读转 RAG）也只加一条索引流水线。**一句话：小库（≤ 数万 token）直读最划算，库一大，成本与"迷失在中部"两个问题同时爆炸。**

**方案二：微调注入（含 LoRA）**。把知识或行为模式训进权重。LoRA（arXiv:2106.09685）通过冻结原权重、只训练低秩增量矩阵，把可训练参数量降低若干个数量级，使消费级单卡数小时到数天的训练成为可能——这大幅拉低了微调的门槛，但**没有改变它的本质约束**：训进去的知识没有出处、不能溯源，且知识一变就得重训。适用条件：固化风格、格式、语气、拒答边界，或注入一个几乎不变的专业领域"语感"；不适合任何会变的**事实**。成本量级：LoRA 单次训练在单卡 GPU 小时到天级（相对全参微调便宜一到两个数量级），但数据准备（清洗、标注）往往比训练本身更贵；知识每变更一轮就重付一次。迁移代价：高——从微调撤回提示词/RAG 意味着丢弃已训练能力，且要重新验证行为。

**方案三：结构化知识库（SQL / 知识图谱）**。适用条件：问题能被实体、关系、聚合表达——"上月华东区退货率""药 A 与药 B 是否禁忌同服"。SQL 处理数值聚合，知识图谱处理多跳关系。成本量级：一次性投入高（schema 设计、ETL、实体对齐，常以人月计），但单查询边际成本极低且结果**精确**——数据库不给"大概"，只给对或错。迁移代价：中——RAG 系统里加一条"意图识别 → SQL 生成/图查询"的支路即可，本卷第 7 章的 GraphRAG 正是向量与图谱的折中。**凡答案可以用一条查询精确表达的，都不该让语言模型在文本里"读"出来。**

**方案四：传统检索系统（BM25 / 全文检索 + 模板）**。适用条件：查询词与文档词高度重合（工单号、型号、错误码），且答案可模板化。BM25 是稀疏词频匹配，没有语义泛化能力，但对精确词匹配场景反而优于向量——向量会把"错误码 E-402"泛化成"各种错误"，BM25 不会。成本量级：四类中最低——成熟开源引擎（如 Elasticsearch/Lucene 系【待核验：引擎归属与许可证以官方仓库为准】）运维成本低，无 embedding 费用。迁移代价：低——它常与向量检索**并存**而非互斥，本卷 3.3 节的混合检索正是两者融合。

| 方案 | 适用条件 | 成本量级（相对） | 迁移代价 |
|---|---|---|---|
| 长上下文直读 | 全库 ≤ 数万 token 且单会话用得上大部分 | 单查询高、随库线性涨 | 极低 |
| 微调注入（LoRA） | 固化风格/技能，知识近乎不变 | 训练一次性 + 数据准备贵，变更重付 | 高 |
| 结构化知识库 | 答案可用查询/多跳关系表达 | 一次性人月级投入，边际近零 | 中 |
| 传统检索（BM25） | 词面高度重合 + 答案可模板化 | 最低 | 低（常与向量并存） |

> **关键判据**：知识要"知道"用检索，行为要"变成"用微调，答案要"算准"用结构化库，词要"对上"用 BM25——四句话各管一类需求，互不替代。

### 7.8.3 决策算例：10 万份静态文档 vs 100 万条日更资讯

用两个典型场景把上面的判据算成数字。**假设口径**：① 中文字与 token 按 1:1 粗估（实际分词器多在 0.6–1.5 token/字之间波动，此处只做量级对比）；② 本文出现的 embedding 单价、GPU 时价均为**假设单价**，仅用于路线间相对比较，不代表任何厂商现价【待补充：如需绝对成本，按当期厂商定价页重算】；③ RAG 单查询注入量取本卷 3.2 节实测口径：top-5 片段、每片约 500 字，约 2,500 token，加指令约 3,000 token。

**场景 A：10 万份静态文档**（法规/产品手册类，季度不变），平均每份 5,000 字，全库 5 亿 token。

- 路线一（长上下文直读）：没有任何现存模型窗口能装下 5 亿 token，只能切 500 次、每次 100 万 token 分别调用再汇总——单查询 5 亿 token 的 prefill 开销；即便假设 prefill 吞吐高达 10,000 token/s，单查询纯计算也要 50,000 秒 ≈ 13.9 小时，再加 500 倍的 token 费用。**直接出局。**
- 路线二（RAG）：一次性 embedding 全库 5 亿 token，按假设单价 0.0005 元/千 token 计为 250 元；向量存储按每 token 向量约数十字节计为 GB 级，单机可容。此后每次查询只送约 3,000 token 给 LLM。单查询边际成本约为直读路线的 5 亿 ÷ 3,000 ≈ **16.7 万分之一**。
- 结论：静态大库，RAG（或 BM25）是唯一量级正确的路线，判据体系与算例一致。

**场景 B：100 万条日更资讯**（新闻/舆情类），每条约 200 字，全量 2 亿 token，每日新增与变更约 1 万条 ≈ 200 万 token/日。

- 路线一（微调注入）：即便用 LoRA 把单次训练压到 8 GPU 时，知识每变一轮就要重训一轮——200 万 token/日的语料意味着**每天**付一次训练成本与数据清洗人力，且从资讯发生到训进权重再到上线，滞后以"天"计，对日更内容等于永远慢一拍。按假设单价 10 元/GPU 时，仅训练一项每天 80 元且逐年累积，还不含标注。
- 路线二（RAG 增量索引）：每日增量 embedding 200 万 token ≈ 1 元/日（同一假设单价），索引分钟级生效，知识滞后可控在小时以内；全量重建（2 亿 token ≈ 100 元）仅在必要时做，比如换 embedding 模型。
- 结论：日更场景，微调在时效与成本两个维度同时崩掉，RAG 的"增量更新"优势被放大到不可替代。

两个场景合起来看：**库的"变化率"决定更新机制的路线，库的"总量"决定单查询的路线**——静态大库比的是单查询边际成本，日更流比的是更新边际成本，两笔账都要算，只算一笔就会选错。

> **关键判据**：总量决定单查询账（直读 vs 检索），变化率决定更新账（重训 vs 增量索引）——两账齐算再定路线。

### 7.8.4 决策检查清单：从"要不要 RAG"到"要不要混合"的七步走查

以下清单按顺序逐条执行，**走到哪步答案是"是"，就停在那里采用该方案**，不再往后走：

1. **第 0 步——答案在不在你拥有的资料里？**不在（纯创作、闲聊、数学推理、代码执行）→ 不用 RAG，用裸 LLM 或工具调用，流程终止。
2. **第 1 步——全库能否一次塞进上下文窗口且本会话用得上大部分？**（全库 ≤ 数万 token）能 → 长上下文直读，流程终止。
3. **第 2 步——知识条目是否 < 数十条且 90 天变更 ≤ 3 次？**是 → 全量写入 system prompt，流程终止。
4. **第 3 步——要解决的是"行为"而非"事实"？**（固定语气、固定格式、拒答边界）是 → 微调（优先 LoRA），流程终止。
5. **第 4 步——答案能否用一条查询精确表达？**（数值聚合、实体关系、多跳）能 → SQL/知识图谱，流程终止。
6. **第 5 步——查询词与文档词是否高度重合且答案可模板化？**（错误码、工单号）是 → BM25/全文检索，流程终止。
7. **第 6 步——以上全否**（知识多、常变、要溯源、需语义泛化）→ **上 RAG**。
8. **第 7 步（RAG 之上的追加问）——是否同时存在提示词压不住的行为问题？**（长 system prompt 下模型不守引用格式、口吻漂移）是 → RAG + 轻量微调混合（见 8.5 节边界讨论）。

使用注意：第 1、2 步的阈值（数万 token、数十条）是编者给出的经验量级而非精确边界，靠近边界时建议按 8.3 节口径各算一遍账再定。

> **关键判据**：清单走到第 6 步才允许上 RAG，走到第 7 步才允许"RAG + 微调"——提前止步即过度设计。

### 7.8.5 失败案例复盘与边界条件

**案例复盘（示意性案例，据常见工程模式整理，不指名具体公司）**。背景：某客服团队仅维护 20 篇 FAQ、合计约 3,000 字，却按"AI 客服标配"上了完整 RAG 流水线。现象：上线后答错率不降反升，端到端延迟增加约 800 毫秒，月度 token 账单上升，且同一问题隔几分钟重问会得到不同答案。根因复盘分四层：① 知识全量只有 3,000 字，本可常驻 prompt，检索环节是纯增项；② 检索引入排序抖动——重排模型分数微小波动导致 top-5 片段顺序变化，拼进 prompt 的证据不同，答案随之漂移，而全量常驻时根本不存在"选哪段"的问题；③ 20 篇 FAQ 中部分条目语义相近，向量召回偶尔漏掉真正匹配的那条，把近似条目排到前面，反而在原本必对的题上引入噪声；④ 维护账被低估——切片参数、embedding 版本、重排阈值三项配置的调优时间，超过了把 FAQ 直接写进 prompt 的时间。修正：整体下线向量库，FAQ 全量进 system prompt，答错率与延迟同时回落。**教训：知识能全量常驻时，检索不是锦上添花，而是主动引入两个新的失败模式（选段噪声 + 排序抖动）。**

**边界条件一：RAG + 微调混合何时才是对的**。混合不是折中姿态，而是分工明确的组合拳：微调管"它是什么样的助手"（口吻、格式、拒答、引用纪律），RAG 管"它手头有哪些资料"（会变的事实）。判对混合的标准只有一条：**行为问题已经被证明无法用提示词稳定解决**——典型信号是：system prompt 超过数千 token 后指令遵从明显稀释（指令淹没在长上下文中，与 arXiv:2307.03172 揭示的中段忽视同源）、多轮对话后格式漂移、检索到正确证据却不好好引用。三者同时出现且提示词迭代两轮无效，才值得付出 LoRA 训练与数据准备的代价；否则先怀疑提示词写得不够好，而不是模型不够听话。

**边界条件二：本清单在什么情况下失效**。① **知识变更率不可统计**——没有版本管理或变更日志时，8.1 节维度一退化为主观感觉，清单前几步等于拍脑袋；补救是先给知识库补变更记录，再回来走查。② **单查询触达占比极低的大库**——若每次会话只触达全库极小局部（如用户只问某一个型号），第 1 步"全库塞得进"就算成立也不该直读，因为为用不到的 99% 付费；此时应在第 1 步追加判问"单次查询平均用到全库的百分之几"，低于约 10% 即跳过直读。③ **事实与计算混合型问题**——"按这份 200 页财报算出去年毛利率变化"：答案部分在资料里、部分靠计算，第 0 步会误判为"不用 RAG"；实际正确形态是 RAG 取数 + 工具计算的两段式，清单需要拆成两问分别走查。④ **多模态资料**（图表、扫描件）当前清单按纯文本假设设计，表格与图像的"检索"边界另需单独评估。

编者观点：判断"该不该用 RAG"的本质，是拒绝把 RAG 当默认架构。RAG 的每一层——切片、embedding、召回、重排、引用拼装——都在为"知识装不下、变不停、要溯源"这三件事付费；三件事一条都不占的场景，每层都是纯负债。清单的意义不在答案本身，而在强迫团队把"为什么要检索"说成可统计、可计算的理由。

### 本章要点

- 快速分水岭是"知识能否全量常驻上下文"：5 条规则约 300 字直接写进 system prompt；典型案例——20 篇 FAQ（约 3000 字）强行上 RAG 后答错率不降反升、延迟增加约 800 毫秒，因为检索主动引入了"选段噪声+排序抖动"两个新失败模式，修正后整体下线向量库才回落。
- 四类需求各归各的方案，互不替代：知识要"知道"用 RAG（会变、要溯源），行为要"变成"用微调（固化进权重，但注入的知识无出处、知识一变就得重训），答案要"算准"用 SQL/知识图谱，词要"对上"用 BM25。
- 两笔账齐算再定路线：库的总量决定单查询账（10 万份静态文档共 5 亿 token，直读单次纯计算约 13.9 小时，RAG 边际成本约直读的 1/16.7 万）；库的变化率决定更新账（日更 200 万 token，微调每天重训一轮且滞后以天计，RAG 增量索引分钟级生效）——只算一笔就会选错。
- 七步走查清单须按序执行：走到第 6 步才允许上 RAG、第 7 步才允许"RAG+微调"混合，提前止步即过度设计；边界情况要补判问（单查询触达低于约 10% 全库时跳过直读、事实+计算混合题拆成 RAG 取数+工具计算两段走查）。
- "RAG+微调"混合的判对标准只有一条：行为问题已被证明无法用提示词稳定解决——system prompt 超数千 token 后指令遵从稀释、多轮后格式漂移、有据不引用三者同时出现且提示词迭代两轮无效，才值得付 LoRA 训练与数据准备的代价。

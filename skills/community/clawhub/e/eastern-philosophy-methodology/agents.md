# 东方哲学方法论 Skill 包 — 规范宪章（agents.md）

> 本文件是本技能包的**最高规范**。任何 Agent、任何技能文件、任何进化操作，
> 与本文件冲突时，一律以本文件为准。修改本文件需用户明确授权。

---

## 1. 项目定位

从五部可信原典中提炼**原子哲学方法论单元**（原子 Skill），
再通过**组合与派生**构建面向具体场景的应用 Skill（子 Skill），
形成"原典 → 原子层 → 应用层"的两层知识体系。

本技能包是**方法论技能包**，不是文献库、不是语录集。

---

## 2. 可信来源白名单（唯一授权原稿）

一切原子 Skill 的方法论依据，**只能**来自以下五个来源的原稿：

| 源编号 | 来源 | 授权范围 |
|--------|------|----------|
| GZ | 鬼谷子 | 《鬼谷子》原著文本 |
| SZ | 孙子兵法 | 《孙子兵法》十三篇原文 |
| ZGF | 曾国藩 | 曾国藩家书、日记、奏稿、文集原稿 |
| ZJZ | 张居正 | 张居正奏疏、书信、著述原稿 |
| MZD | 毛泽东 | 毛泽东选集、文集、军事文选 |

**铁律：**
1. 白名单之外的任何思想体系（儒家其他人物、道家其他人物、佛学、
   西方哲学、现代管理学、心理学等）**不得**作为方法论来源。
2. 外部知识只允许作为**表达语言**（帮助现代人理解的措辞），
   不得作为**论证依据**。措辞可借，血脉不可借。
3. 原稿文本存放于 `sources/{源编号小写}/`，是唯一取证现场。
   任何原子 Skill 的提炼必须能回溯到 `sources/` 中的原文。

---

## 3. 两层技能架构

```
sources/            原稿层（取证现场，只增不改正文）
    ↓ 提炼（必须锚定原文）
atomic-skills/      原子层（最小不可分方法论单元）
    ↓ 组合 + 派生（只能引用原子 ID）
application-skills/ 应用层（场景化子 Skill）
```

分层规则：
- 原子层不解决具体场景问题，只承载"一条可独立成立的方法论"。
- 应用层不产生新方法论，只做原子技能的**编排**。
- 应用层**禁止**直接引用原典，其一切方法论含量必须经由原子层。
- 严格单向依赖：`应用层 → 原子层 → 原稿层`，禁止任何反向或跨层引用。

## 4. 原子技能规范（atomic-skills/）

### 4.1 命名与编号

文件名：`{源编号}-{两位序号}-{中文slug}.md`，如 `SZ-01-知彼知己.md`。

- `id` 全局唯一，一经发布不可复用（废弃的 ID 永久封存）。
- 一个原子 Skill 只承载**一条**方法论，不可再拆分为两条独立成立的
  方法论，否则必须拆分。

### 4.2 必备字段（Front-matter）

```yaml
---
id: SZ-01
name: 知彼知己
source: SZ
source_text: "知彼知己者，百战不殆"
source_location: 《孙子兵法·谋攻篇》
version: 1.0.0            # 语义化版本，见第 7 节
status: active            # active | deprecated
deprecated_note: ""       # 废弃时必填，说明原因与替代者
---
```

### 4.3 必备章节

1. **原典锚点**：原文引用 + 出处。禁止转述代替原文。
2. **要义提炼**：一句话核心命题（可执行的方法论表述）。
3. **释义展开**：原典语境中的含义 → 抽象为一般方法论。
4. **适用条件**：什么情况下该方法论成立。
5. **边界与失效条件**：什么情况下该方法论失效或不适用。
6. **关联原子**：与同源/跨源原子 Skill 的印证或张力关系（只写 ID）。

### 4.4 纯度要求

- 要义提炼必须是原文可推出的，禁止过度引申。
- 一条方法论若在多部原典中均有印证，**拆分为多个源各自的原子 Skill**，
  再在"关联原子"中互相引用；禁止合并成跨源原子。
- 原子 Skill 内禁止出现场景化操作步骤（那是应用层的事）。

## 5. 应用技能规范（application-skills/）

### 5.1 定位

应用 Skill = 场景 × 原子技能组合公式。它回答"在 X 场景下，
按什么顺序、什么权重、什么条件分支使用哪些原子方法论"。

### 5.2 命名

文件名：`APP-{三位序号}-{场景slug}.md`，如 `APP-001-谈判博弈.md`。

### 5.3 必备字段与章节

```yaml
---
id: APP-001
name: 谈判博弈
version: 1.0.0
status: active
depends:                   # 依赖清单，锁定原子版本
  - atomic: SZ-01
    version: 1.0.0
    role: 核心前提
  - atomic: GZ-01
    version: 1.0.0
    role: 主策略
---
```

1. **场景定义**：目标、约束、角色、典型输入。
2. **组合公式**：依赖原子 Skill 的编排逻辑——
   顺序 / 条件分支 / 权重 / 冲突时的优先级裁决规则。
3. **执行步骤**：可直接执行的操作序列，每一步标注依据的原子 ID。
4. **失效预案**：场景恶化时退回哪个原子原则兜底。
5. **来源声明**：显式声明"本 Skill 的方法论含量全部来自 depends 清单"。

### 5.4 派生铁律

1. 应用 Skill 的方法论依据**只能**是 `depends` 中的原子 Skill，
   且必须锁定版本号。
2. 禁止引用原典、禁止引入白名单外思想、禁止"常识性补充"。
3. 执行步骤中每一条判断、每一个策略动作，必须能指认到某个原子 ID；
   指认不到的内容必须删除，或先下沉为新的原子 Skill（走进化流程）。
4. 两个应用 Skill 之间允许组合（一个应用 Skill 引用另一个应用 Skill），
   但同样必须锁定版本，且禁止形成环。

## 6. 可追溯性规范（链路校验）

任何技能文件必须满足**三段可追溯链**：

```
应用 Skill 步骤 ──→ 原子 Skill id@version ──→ sources/ 原文出处
```

校验项（每次修改后必须逐项确认）：
- [ ] 应用 Skill 的每个 depends 中的 atomic id 真实存在于注册表且 status 为 active
- [ ] depends 中的 version 与该原子 Skill 当前发布版本一致（或已列入待回归清单）
- [ ] 原子 Skill 的 source_text 能在 `sources/` 对应文件中逐字找到
- [ ] 所有 id 全局唯一，编号无重复、无跳号复用
- [ ] 无环依赖（应用层内部依赖关系为 DAG）

## 7. 版本规范（语义化）

| 变更类型 | 版本动作 | 含义 |
|----------|----------|------|
| 原文锚点变更、要义提炼变更 | MAJOR 递增 | 破坏性变更，**强制触发**所有依赖方回归 |
| 增补适用条件/边界/案例 | MINOR 递增 | 向后兼容 |
| 文字勘误、格式修订 | PATCH 递增 | 无实质变更 |

- 原子 Skill 一经发布，历史版本**不可篡改**；变更 = 发布新版本 +
  在 `evolution/log.md` 记录旧→新。
- 废弃不删除：`status: deprecated` + `deprecated_note`（指明替代者或废弃理由），
  文件保留，保证历史引用链不断裂。

## 8. 自进化机制（evolution/）

### 8.1 原理声明

技能是静态文本，无法"自己"进化。本机制定义为**Agent 驱动、
人工把关的受控进化协议**：反馈驱动提案，提案强制校验，
评审通过才可合并，合并后强制回归。**禁止跳过校验与评审直接改写技能文件。**

### 8.2 核心原则：血统隔离

- **反馈不能直接改写原子层。** 应用反馈只能证明"组合方式需要调整"
  或"某原子提炼可能有偏差"。前者可直接进应用层提案；
  后者必须**重新锚定原典原文**（回到 `sources/` 取证）才能修改原子 Skill。
- 这样保证：无论进化多少代，原子层的每一滴方法论含量都来自五源原稿。

### 8.3 进化动作矩阵

| 层级 | 动作 | 触发信号 | 唯一合法依据 | 门槛 |
|------|------|----------|--------------|------|
| 原子层 | 新增 | 精读原稿发现未覆盖方法论单元 | 原典原文 | 必须锚定 `sources/` 原文 |
| 原子层 | 深化(MINOR) | 反馈暴露释义偏差/边界缺失 | 原文 + 反馈 | 释义变更部分需重新锚定原文 |
| 原子层 | 修订(MAJOR) | 原文锚点错误或要义提炼错误 | 原典原文 | 强制触发全量依赖回归 |
| 原子层 | 废弃 | 与原文冲突、或与他原子重复 | 原典原文 | deprecated，保留文件与 ID |
| 应用层 | 新增 | 新场景需求 + 反馈积累 | 反馈 + 现有原子 Skill | 组合公式要素齐全 |
| 应用层 | 调优 | 执行反馈显示权重/步骤/分支不当 | 执行反馈 | 仅可调编排，不得夹带新方法论 |
| 应用层 | 重派生 | 依赖的原子 Skill 版本变更 | 版本变更事件 | 强制，不可跳过 |

### 8.4 进化流水线（六段）

```
收集 → 提案 → 校验 → 评审 → 合并 → 回归
```

1. **收集**：汇总 `evolution/feedback/` 中未处理反馈，
   按涉及技能归类、按频次/严重度排序。
2. **提案**：生成结构化提案文件写入 `evolution/proposals/`（见 8.5），
   **此阶段禁止改动任何技能文件**。
3. **校验**（自动）：逐项执行——
   - 来源白名单校验：提案引用的一切方法论依据 ∈ 五源；
   - 追溯链校验：三段链完整（见第 6 节）；
   - 血统校验：原子层提案是否重新锚定了原文；
   - 结构校验：编号唯一、版本语义正确、依赖为 DAG。
   校验不过 → 提案打回并记录原因，回到提案段。
4. **评审**（人工门）：默认必须用户确认。用户可显式授权
   "PATCH/MINOR 级自动通过"，MAJOR 与废弃**永远**需要人工确认。
5. **合并**：修改技能文件、递增版本、更新注册表、
   在 `evolution/log.md` 追加记录（append-only，禁止改写历史记录）。
6. **回归**：扫描全部引用了被变更原子 Skill 的应用 Skill，
   逐个生成重派生任务；未完成回归前，依赖方注册表标记 `pending-revalidation`。

### 8.5 提案文件格式（evolution/proposals/）

文件名：`PROP-{YYYYMMDD}-{三位序号}.md`

```yaml
---
id: PROP-20260101-001
type: atomic-add | atomic-refine | atomic-deprecate | app-add | app-tune | rederive
target: SZ-01 | APP-001
trigger_feedback: [F-0007, F-0012]     # 触发本提案的反馈 ID
evidence: sources/sunzi/谋攻篇.md       # 原子层提案必填
proposed_version: 1.1.0
---
## 变更内容
## 依据（原文引用 / 反馈摘要）
## 影响面分析（受影响的下游 Skill 清单）
```

### 8.6 反馈记录格式（evolution/feedback/）

文件名：`F-{四位序号}.md`，一次真实使用的结果记录：

```yaml
---
id: F-0007
skill: APP-001
skill_version: 1.0.0
outcome: success | partial | failure
date: 2026-01-01
---
## 场景
## 执行过程（哪些步骤/原子起作用了）
## 偏差（预期 vs 实际）
## 初判（编排问题 / 提炼问题 / 场景超出适用域）
```

### 8.7 进化触发方式

- **被动触发**：`evolution/feedback/` 未处理反馈达到 5 条，或出现
  2 条以上同类 `failure`，提示用户启动进化流水线。
- **主动触发**：用户指令"进化 / evolve"时，Agent 从收集段开始执行。
- **事件触发**：`sources/` 新增原稿材料（经由 8.9 采集子流程）→ 提示可做
  原子层"新增"扫描；原子 Skill 版本变更 → 自动生成"重派生"任务。

### 8.8 反漂移红线

进化过程中出现以下任一情况，**立即中止并上报用户**：
- 提案的新方法论找不到五源原文锚点；
- 应用层提案夹带 depends 清单之外的方法论内容；
- 校验发现任何一环追溯链断裂；
- 单轮进化涉及 3 个以上 MAJOR 变更（可能是一次危险的推倒重来）。

### 8.9 上游子流程：原典采集（sources ingestion，独立于六段流水线）

`sources/` 的完备化不由进化流水线驱动，而由独立的采集子流程完成。
两者单向耦合：采集合并 → 触发 8.7 事件 → 进化流水线原子层"新增"扫描。

**反造证铁律：**
1. 采集只由原典全集的完备性驱动（按书、按篇推进，
   以 `sources/_index.md` 完备性矩阵为计划依据）；
2. **禁止因任何待决原子提案、应用需求或反馈而反向取证**——只允许
   "文本 → 发现方法论"，永远不允许"想要方法论 → 找文本"；
3. 采集记录中不得引用任何提案 ID（动机与时序均须可分离）。

**采集五段：**计划 → 转录 → 勘验 → 合并 → 触发

1. **计划**：依 `_index.md` 矩阵确定本轮范围，按书按篇整段推进。
2. **转录**：依版本依据录入，标注版本；不得臆改字句；凭通行本
   记忆转录的必须在矩阵中标记"待校对"。
3. **勘验**（自动 + 人工门）：
   - 白名单：文本属五源；
   - 保真：字句须与版本依据一致；
   - 只增：不改动既有正文；文件头覆盖说明等元数据允许同步更新；
   - 勘误例外：既有文本的转录笔误允许勘正，但必须在采集记录中
     留痕（原误 → 勘正），禁止静默修改；
   - 人工门：默认须用户确认；用户可显式授权"选录级自动通过"，
     全录与涉及既有正文勘误的合并永远需人工确认。
4. **合并**：追加写入对应源文件（或新建文件），更新矩阵覆盖状态，
   在采集记录追加留痕（append-only）。
5. **触发**：提示用户可启动原子层"新增"扫描（转入进化流水线，
   与本流程解耦，不自动执行）。

## 10. 负面清单（任何操作禁止）

1. 禁止在白名单五源之外引入方法论（无论多么"有道理"）。
2. 禁止应用层直接引用原典原文作为依据。
3. 禁止合并多源为单一原子 Skill（跨源印证靠"关联原子"互引）。
4. 禁止复用已废弃 ID；禁止删除已发布文件（只允许废弃标记）。
5. 禁止跳过进化流水线直接修改技能文件。
6. 禁止用反馈直接改写原子层（必须重新锚定原文）。
7. 禁止改写 `evolution/log.md` 的历史记录。
8. 禁止应用层依赖成环。
9. 禁止为任何原子/应用提案反向取证（采集只由原典完备性驱动，见 8.9）。
10. 禁止静默修改 `sources/` 既有正文；转录勘误必须在采集记录留痕。

---

## 11. 操作检查清单

任何 Agent 在本技能包内工作，每轮修改后必须确认：
- [ ] 新增/修改内容的方法论依据全部来自五源原稿？
- [ ] 应用层改动只编排了 depends 中的原子 Skill？
- [ ] 三段追溯链完整（步骤 → 原子 id@version → 原文出处）？
- [ ] 版本号按语义化规则递增？注册表已同步？
- [ ] 废弃项是否保留了文件、ID 与 deprecated_note？
- [ ] 进化操作是否走完六段流水线并在 log.md 留痕？
- [ ] `sources/` 变更是否走 8.9 采集子流程并在 `_index.md` 留痕？

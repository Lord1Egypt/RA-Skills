## 2.1 前置检查（必须最先执行）

### 2.1.1 启动项目

尝试执行项目的启动命令（从 `package.json` 的 `scripts` 中识别 `dev` / `start` / `serve` 等），等待启动完成。

若启动失败连续 3 次，触发熔断（见 00-§0.7），整文件跳过。

### 2.1.2 环境判定

- **测试环境**：有独立测试数据库/测试账号 → 可执行完整动态安全测试
- **非测试环境**：无测试数据库或不确定 → 动态安全测试自动降级为静态审计，严禁发送攻击 payload
- 判定结果写入报告 B 节开头

### 2.1.3 SPA 项目自动检测与 E2E 推荐

在执行动态测试前，自动检测项目类型。若检测为 SPA 项目，必须在报告中输出 E2E 推荐提示：

**SPA 检测规则**（满足任一条件即判定为 SPA）：
| 检测方式 | 判断依据 |
|:---|:---|
| 依赖检测 | `package.json` 中存在 `react`、`vue`、`angular`、`svelte`、`solid-js` 等前端框架 |
| 构建工具检测 | 存在 `vite.config.*`、`webpack.config.*`、`next.config.*`、`nuxt.config.*` 等 |
| 入口 HTML 检测 | 入口 HTML 中仅有 `<div id="root">`/`<div id="app">` 等空容器，无服务端渲染内容 |
| 路由检测 | 存在 `react-router`、`vue-router`、`@angular/router` 等前端路由库 |

**检测为 SPA 时的强制输出**：
```
⚠️ SPA 项目检测：当前项目为 [React/Vue/Angular/...] 单页应用。
02 动态测试仅能验证 HTTP 层可达性，无法验证客户端渲染和路由切换。
强烈建议使用以下模式进行完整验证：
  - Standard + E2E：PR 检查 + E2E 冒烟 + 核心链路
  - E2E：纯端到端浏览器测试
  - Release + E2E：发版全量审计 + 完整 E2E

是否继续仅执行 02 动态测试？（输入 Y 继续 / N 切换到含 E2E 的模式）
```
> 若用户选择继续仅执行 02，在报告 B 节开头标注「SPA 项目，E2E 未执行」。

## 2.2 测试用例优先级分层

在编写和执行测试用例时，按以下优先级分层，确保有限时间内优先执行高价值用例：

- **P0 — 冒烟测试（Smoke）**：应用能否正常启动、核心页面能否打开、基础 API 能否连通。P0 不通过，后续所有测试无意义。
- **P1 — 核心链路（Core Journey）**：用户最关键的端到端业务流程，覆盖正向主路径。P1 不通过，判定为"阻塞上线"。
- **P2 — 边界与异常（Edge & Exception）**：非法输入、极端参数、并发操作、快速重复点击等异常场景。
- **不在 AI-02 范围**：断网/弱网模拟、多浏览器渲染、Core Web Vitals → 见 **03 人工清单**（MAN-XXX）。

**动态截断**：默认聚焦 3 条核心链路；若项目模块数超过 10 个，则按比例递增（每增加 5 个模块，多覆盖 1 条核心链路），上限为 10 条。

## 2.3 P0 冒烟测试

### 2.3.1 应用启动验证

- 启动命令是否成功执行
- 控制台是否有启动报错
- 启动时间是否在合理范围内
- 若为 Web 应用，首页是否返回 HTTP 200

### 2.3.2 核心页面可达性

- 对 01 中识别的核心页面路由，逐一发送 HTTP GET 请求
- 记录每个页面的 HTTP 状态码
- 若返回非 200 且非 3xx，标记为 P0 失败

> **SPA 项目（React / Vue / Angular 等）**：GET 返回 200 仅表示 HTML 壳可达，**不代表客户端渲染成功**。须在报告中注明「SPA：仅验证静态资源/入口 HTML 可达，未验证客户端渲染与路由」。若项目已有 E2E 脚本（Playwright/Cypress）或浏览器 MCP，优先运行已有脚本；否则不得声称「页面功能正常」。
>
> **SPA 项目补充验证策略**（无 E2E 脚本时，AI 优先尝试以下验证，按顺序执行）：
> 1. **静态资源检查**：GET 入口 HTML 后，检查是否引用了 JS bundle 文件（如 `<script src="/assets/index-*.js">`），若引用文件返回 404 则标记为缺陷
> 2. **关键 DOM 元素检查**：若项目有浏览器自动化工具，等待页面加载后检查是否存在关键 DOM 元素（如 `#root` 内有子元素、或特定组件 ID）
> 3. **API 数据加载检查**：GET 页面后，识别该页面依赖的 API 端点（从 01 静态分析中获取），逐一验证 API 是否返回有效数据，若 API 返回 5xx/空数据则标记为缺陷
> 4. **路由懒加载 chunk 检查**：GET 入口 HTML 后，提取所有 `<script>` 标签中的 `src` 属性，对每个 JS chunk 文件发送 HEAD 请求，验证返回 200；若任一 chunk 返回 404，标记为 DEF-XXX（Medium）
> 5. **构建产物完整性检查**：若项目有 `dist/` 或 `build/` 目录，扫描目录中所有 `.js`/`.css` 文件，对比入口 HTML 中引用的文件列表，检测是否有引用但缺失的文件
>
> 若以上验证均无法执行（无浏览器工具），须在报告中明确标注：「SPA 项目，无法验证客户端渲染状态，建议补充 E2E 测试脚本。推荐使用 `Standard + E2E` 模式或独立 `E2E` 模式进行完整浏览器验证。」

### 2.3.3 基础 API 连通性

- 对 01 中识别的核心 API 接口，逐一发送请求
- 记录每个接口的 HTTP 状态码和响应时间
- 若返回 5xx，标记为 P0 失败

**输出格式**：每个测试项一行：
```
| P0 | 页面/API 路径 | 预期 | 实际 | 状态 |
|:---|------|------|------|:---:|
| P0 | GET / | 200 | 200 | ✅ |
| P0 | GET /api/health | 200 | 500 | ❌ |
```

## 2.4 P1 核心链路测试

从最终用户最关心的业务闭环出发，执行正向核心链路。每条链路测试覆盖完整的端到端流程：

### 2.4.1 链路选择

从 01 的功能入口清单中，选取业务价值最高、逻辑最复杂的核心链路。每条链路必须覆盖至少 3 个步骤（如：登录 → 浏览 → 提交）。

### 2.4.2 链路测试执行

对每条链路：
1. 按步骤顺序发送 HTTP 请求
2. 每一步记录：请求方法 + URL + 请求体（截断）+ 响应状态码 + 响应体（截断前 500 字符）
3. 验证每一步的响应是否符合预期
4. 验证跨步骤的数据传递是否正确（如：创建资源后，查询能返回该资源）

### 2.4.3 链路测试输出

每条链路生成一段描述：
```
### 核心链路：用户下单流程
1. POST /api/login → 200，获取 token
2. GET /api/products → 200，返回商品列表
3. POST /api/orders → 201，创建订单成功
4. GET /api/orders/{id} → 200，订单详情正确
✅ 链路通过
```

若某步失败，详细记录失败原因和响应体。

## 2.5 P2 边界与异常测试

对核心接口的输入参数进行边界探测：

### 2.5.1 输入边界测试

- 必填字段传空值 / null / undefined
- 字符串字段传超长文本（如 10000 字符）
- 数字字段传负数 / 0 / 极大值
- 枚举字段传非法值
- JSON 格式错误

### 2.5.2 异常场景测试

- 不传认证 Token 访问受保护接口
- 传过期 Token 访问受保护接口
- 访问不存在的资源 ID（如 `/api/users/99999`）
- 并发发送相同请求（检测幂等性）

**输出**：每个异常场景一行：
```
| P2 | 测试场景 | 接口 | 输入 | 预期 | 实际 | 状态 |
|:---|------|------|------|------|------|:---:|
| P2 | 空值 | POST /api/orders | {userId: null} | 400 | 400 | ✅ |
| P2 | 超长 | POST /api/orders | {name: 10000字} | 400 | 500 | ❌ |
```

## 2.6 安全-动态：运行时安全验证

> ⚠️ **执行范围**：**Release 模式**、**Custom 指定「安全 Extended」** 时执行本节。Standard 模式 **默认跳过**（见 00-§0.1.1），在报告 B 节标注「动态安全测试跳过：Standard MVP 不含 §2.6」。
> ⚠️ **仅限测试环境**。非测试环境此节自动降级为静态审计（见 01），不得执行以下任何测试。

### 2.6.0 前置条件

| 条件 | 不满足时的处理 |
|:---|------|
| 测试环境（独立测试库/测试账号） | 整节降级为 01 静态，标注原因 |
| **≥ 2 个不同权限的测试账号**（角色越权） | 跳过 §2.6.1 中「角色越权」项，标注「跳过：仅 1 个测试账号」 |
| **≥ 2 个不同用户的测试账号**（横向越权） | 跳过 §2.6.1 中「横向越权」项，标注「跳过：无法获取第二用户账号」 |
| 上述账号均不满足 | 仍可做「未登录访问」「Token 篡改」；越权类全部跳过，不得编造结果 |

### 2.6.1 认证与鉴权

- **未登录访问**：不带 Token 访问所有受保护接口，确认返回 401
- **Token 篡改**：修改 Token 中任意字符后访问，确认返回 401
- **角色越权**：使用低权限账号的 Token 访问高权限接口，确认返回 403
- **横向越权**：用户 A 的 Token 访问用户 B 的数据（如 `/api/users/B-id/orders`），确认返回 403

### 2.6.2 注入攻击探测

对每个用户输入入口（URL 参数、表单字段、HTTP Header），尝试注入经典 Payload：

- SQL 注入：`' OR '1'='1`、`'; DROP TABLE users; --`
- NoSQL 注入：`{"$gt": ""}`、`{"$ne": null}`
- XSS 探测：`<script>alert(1)</script>`、`<img src=x onerror=alert(1)>`
- 命令注入：`; ls`、`| cat /etc/passwd`
- 模板注入：`${{7*7}}`、`{{constructor.constructor('return this')()}}`

**重要**：每个 Payload 发送后，记录响应状态码和响应体截断。重点是观察是否有异常响应（如返回了不应该返回的数据、SQL 错误信息等）。

### 2.6.3 输出格式

每个安全发现生成一条记录：
- **SEC-XXX [动态]** 编号
- 漏洞名称
- 严重程度（按 00-A §A.1 定级）
- OWASP 分类
- 受影响接口：`相对路径#行号`（源码中的路由定义位置）
- 复现 Payload
- 实际响应（截断）
- 修复建议

## 2.7 证据规范

所有测试结果必须带证据，证据优先级如下：

| 优先级 | 证据类型 | 何时使用 |
|:---:|------|------|
| 1 | HTTP 状态码 + 响应体原文（截断前 500 字符） | 所有 API 测试的默认证据 |
| 2 | 启动/报错日志原文 | 应用启动失败、运行时异常 |
| 3 | 终端命令输出 | npm audit 等工具输出 |
| 4 | 截图 | 仅当有 Playwright / 浏览器 MCP 可用时使用，否则标注"未采集" |

**禁止行为**：
- 禁止在无浏览器自动化工具的情况下声称"已截图"
- 禁止编造响应体内容——必须是从真实请求中获取的
- 禁止使用"测试通过"代替具体的响应状态码和响应体

## 2.8 跳过条件与门禁联动

以下情况整节或整文件跳过，在报告中标注原因：

| 情况 | 报告标注 | 门禁影响（见 00-§0.10） |
|:---|------|------|
| 项目无法启动（已尝试 3 次） | `动态测试跳过：项目无法启动` | Standard / Release → **❓ 未完成** |
| 启动成功但所有核心 API 返回 5xx | `动态测试跳过：核心 API 不可用` | Standard / Release → **❓ 未完成** |
| Standard 模式（未指定安全 Extended） | `动态安全测试跳过：Standard MVP` | 不影响 Standard ✅（若 02 其余项通过） |
| 非测试环境 | `动态安全测试降级为静态审计` | 不执行 §2.6 |
| Quick 模式 | 不加载 02 | Quick 不受 02 跳过影响 |

**铁律**：跳过 ≠ 通过。02 整文件因环境跳过时，**不得**给出 Standard / Release 的 ✅ 通过结论。

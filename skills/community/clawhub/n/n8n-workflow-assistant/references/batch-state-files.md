# 批量、分页、状态和文件

## 完整性与关联

- 建立来源账本：file、sheet、row、column、输入记录标识和解析状态。查询目标可去重，原始位置不能消失；主键和同一行字段优先级由项目契约指定。
- 不跨行、跨工作表拼接对象；重复值不代表重复记录。分页只影响显示，不能裁剪草稿或实际提交批次。
- 所有工作表及文件的读取范围明确；文件名不代表内容已解析。数量、漏行、截断、未读文件和工作表应有可核验状态。
- “无截断、乱码或解析错误”是并列否定，不能只按关键词判失败。实际缺失须具体定位，无阻断缺项时直接进入正常预览或下一步，不反复要求资料完整性确认。
- 描述中关键证据可能位于备注而不是标题。按同一记录的明确语义判断，不把设备名、客户名等任一展示字段当唯一证据；业务分类规则仍由项目提供。

## 批处理与分页

先确定原生节点是否已逐项执行；需要速率限制或分批提交时再循环。API分页应有终止条件、游标更新、空页/重复页处理和预算。循环完成后汇总全部成功、失败及未处理项。

读取全部输入不等于已完成全部处理。恢复只对未完成项继续，未知写入先回查，不盲目重做整批。测试边界覆盖0、1、多批、重复、跨页与部分失败；用主键集合和来源位置验证，不只比较条数。

## Data Tables与异步任务

检查表所在项目、真实名称/ID和自定义业务列；仅有id/createdAt/updatedAt不代表业务schema已建立。列类型及过滤操作符按目标版本确定。需要存储嵌套JSON且无原生JSON列时，使用明确字符串字段并在边界序列化/解析。

任务写入后先回读再派发。found=true必须有真实持久化行和合法内容；{op:'get',record:{}}等请求帧不能包装成已找到。工作流ID、表ID、凭据ID和业务任务ID分别管理。

读状态携带任务标识和调用身份，控制游标、TTL及已消费批次。会话锁不等于数据库原子幂等；竞争写入按实际存储能力设计。需要大容量或事务时选择合适数据库，不能用工作流声明来承诺原子性。

## 文件与二进制

下载、解析与结果文件交付分开配置；取消输出文件不应连带关闭仍需要的输入。binary字段名和存储模式从上游实际输出读取，不能假设总是内存base64。表格多工作表与原格式保留能力分别验证。

签名URL保留编码和query，来源白名单按管理员确认配置；不擅自改域名或任意放宽。文件生成成功不等于用户能从外网或手机访问，直接发送文件还要确认发布通道与权限。

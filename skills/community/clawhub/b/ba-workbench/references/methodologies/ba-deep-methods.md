## M-01: MECE原则

### 来源：McKinsey & Company

### 核心概念
```
MECE = Mutually Exclusive（相互独立）+ Collectively Exhaustive（完全穷尽）

作用：确保分析结构没有重叠、没有遗漏
应用场景：任何分类、分组、分析框架设计
```

### 常见MECE分组方法

| 分组逻辑 | 示例 | 适用场景 |
|---------|------|---------|
| 时间顺序 | 过去→现在→未来 / Plan→Do→Check→Act | 过程分析 |
| 结构顺序 | 按部门/地区/产品线分 | 组织分析 |
| 程度顺序 | 最重要→最不重要 | 优先级排序 |
| 数学公式 | 利润=收入-成本 / 收入=量×价 | 定量分析 |
| 二分法 | 内部/外部、线上/线下 | 通用分类 |

### MECE检验

```
检验不MECE的情况：
❌ 新客户+老客户+大客户（大客户可能同时是新/老客户→不互斥）
✅ 按时间：新客户+老客户（按首次购买时间，<1年为新）
✅ 按金额：年费>100万的客户+年费≤100万的客户

❌ 收入来源：产品+服务+软件（可能有重叠）
✅ 按收入确认方式：一次性销售收入+订阅收入+服务收入
```

## M-02: 金字塔原理

### 来源：Barbara Minto, McKinsey

### 核心原则
```
1. 结论先行（Top-Down）
   先给结论，再展开论据。不要说"因为A、B、C，所以D"
   而要说"D，原因有三：A、B、C"

2. 上层是对下层的总结概括
   每一层的核心思想是下一层思想的概括

3. 同层同质
   同一层的想法必须属于同一逻辑范畴

4. 按逻辑顺序组织
   时间顺序 / 结构顺序 / 程度顺序
```

### 金字塔结构模板

```
建议/结论
├── 论据1（Why 1）
│   ├── 支撑1.1
│   └── 支撑1.2
├── 论据2（Why 2）
│   ├── 支撑2.1
│   └── 支撑2.2
└── 论据3（Why 3）
    ├── 支撑3.1
    └── 支撑3.2
```

### 序言结构(SCQA)

```
S (Situation): 背景/大家都知道的稳定状态
C (Complication): 发生了什么变化/出现了什么问题
Q (Question): 这引出了什么问题
A (Answer): 我的答案/建议是什么

示例：
S: 我们公司在过去3年保持了20%的年增长
C: 但最近两个季度增长率下降到8%，3个主要竞品已推出AI功能
Q: 我们该如何应对AI竞争威胁？
A: 建议投资500万在Q3前推出AI模块，预计补回10%增长率...
```

## M-03: 波特五力 + 互补品

### 来源：Michael Porter, Harvard Business School

### 六力框架（五力+互补品）

| 力量 | 评估 | 高分的含义 | 低分的含义 |
|------|------|----------|----------|
| 新进入者威胁 | 1-5 | 进入壁垒低，利润会被新进入者侵蚀 | 进入壁垒高，在位者安全 |
| 供应商议价 | 1-5 | 供应商强势，成本不受控 | 供应商弱势，采购占优 |
| 买方议价 | 1-5 | 客户强势，价格压力大 | 客户弱势，定价自由度高 |
| 替代品威胁 | 1-5 | 容易被替代，商业模式脆弱 | 难以替代，模式稳固 |
| 行业竞争 | 1-5 | 竞争白热化，利润率低 | 竞争温和，利润率高 |
| **互补品** | 1-5 | 互补品弱，生态不成熟 | 互补品强，生态繁荣 |

### 评分标准

| 分数 | 标准 |
|------|------|
| 1 | 极弱 — 该力量几乎不存在 |
| 2 | 较弱 — 存在但影响有限 |
| 3 | 中等 — 值得关注但非决定性 |
| 4 | 较强 — 该力量显著影响行业利润 |
| 5 | 极强 — 该力量决定行业利润水平 |

### 五力分析的动态视角

```
静态分析：行业现在的吸引力
动态分析：行业未来的吸引力

要问：
- 哪个力量正在变强？在变弱？
- 什么事件会改变力量平衡？（新技术？新法规？新商业模式？）
- 我们如何主动改变力量平衡？（如：通过品牌降低买方议价力）
```

## M-04: VRIO能力分析

### 来源：Jay Barney, Strategic Management

### VRIO框架

```
V - Valuable（有价值）：这个能力能为客户创造价值吗？
R - Rare（稀缺）：竞争者普遍拥有这个能力吗？
I - Inimitable（难以模仿）：竞争者模仿这个能力需要多大代价？
O - Organized（组织支持）：组织结构和制度是否支持利用这个能力？

VRIO判定矩阵：
V  R  I  O  →  竞争含义
✗  -  -  -  →  竞争劣势
✓  ✗  -  -  →  竞争均势
✓  ✓  ✗  -  →  暂时优势
✓  ✓  ✓  ✗  →  未充分利用的优势
✓  ✓  ✓  ✓  →  可持续竞争优势 ← 目标！
```

### 能力清单评估

| 能力 | V | R | I | O | 竞争含义 | 行动 |
|------|---|---|---|---|---------|------|
| 品牌 | ✓ | ✓ | ✓ | ✓ | 可持续优势 | 继续投资 |
| 技术 | ✓ | ✓ | ✗ | - | 暂时优势 | 加速建立壁垒 |
| 客服 | ✓ | ✗ | - | - | 竞争均势 | 提高标准 |

## M-05: BCG增长份额矩阵

### 来源：Boston Consulting Group

### 矩阵结构

```
        市场增长率
        高
        ↑
  ┌─────┼─────┐
  │ ★   │ ❓  │
  │明星  │问题  │
  ├─────┼─────┤
  │ 🐄  │ 🐕  │
  │金牛  │瘦狗  │
  └─────┼─────┘
        ↓
        低
  高 ← 相对市场份额 → 低
```

### 各象限策略

| 类型 | 特征 | 现金流 | 策略 |
|------|------|--------|------|
| **明星(Stars)** | 高增长+高份额 | 中性 | 继续投资，维持领先 |
| **金牛(Cash Cows)** | 低增长+高份额 | 强正 | 收割利润，投资到明星和问题 |
| **问题(?)** | 高增长+低份额 | 强负 | 选择性投资，有机会的加码 |
| **瘦狗(Dogs)** | 低增长+低份额 | 中性/负 | 收割/出售/关闭 |

### BCG矩阵的局限性

```
注意：
- 只关注市场增长率和份额，忽略了盈利能力和竞争动态
- "低增长≠不盈利" — 很多金牛行业仍有超高利润
- "高份额≠可持续" — 技术颠覆可使份额一夜归零
- 适合用于产品组合VIEW，不能作为唯一决策依据
```

## M-08: 蓝海战略ERRC框架

### 来源：W. Chan Kim & Renée Mauborgne

### 四步动作框架

```
Eliminate（消除）: 哪些行业理所当然的要素应该被消除？
  → 这些要素虽然大家都做，但客户其实不需要了

Reduce（减少）: 哪些要素应该降低到行业标准以下？
  → 过度满足客户的要素，可以降下来节省成本

Raise（提升）: 哪些要素应该提升到行业标准以上？
  → 客户真正痛苦的要素，要远远超过行业标准

Create（创造）: 哪些行业从未有过的要素应该被创建？
  → 全新的价值源，创造新需求
```

### ERRC一页纸工作纸

| Eliminate | Raise |
|-----------|-------|
| 1.  | 1. |
| 2.  | 2. |
|-----------|-------|
| Reduce    | Create |
| 1.  | 1. |
| 2.  | 2. |

### 好的价值曲线三个特征

```
1. 聚焦（Focus）：不是在所有要素上竞争
2. 独特（Divergence）：价值曲线与竞品显著不同
3. 有力口号（Compelling Tagline）：能用一句话说清价值主张
```

## M-09: JTBD（Jobs-to-Be-Done）

### 来源：Clayton Christensen, Harvard

### 核心概念

```
JTBD = 客户"雇佣"产品/服务来完成的工作

不是：客户需要什么功能？
而是：客户在什么场景下，要完成什么任务？

三层Job：
├── 功能性Job：需要完成的具体任务
├── 情感性Job：想要感受到什么？（安心/自信/被认可）
└── 社会性Job：想要别人怎么看自己？（体面/聪明/有品位）
```

### JTBD启发

| 传统需求视角 | JTBD视角 |
|------------|---------|
| "客户需要更快的马" | "客户需要更快地从A到B" |
| "客户需要Excel导出功能" | "客户需要把数据展示给老板看" |
| "客户需要更好的搜索" | "客户需要在3分钟内找到XX信息来完成YY报告" |

### JTBD格式

```
When [在什么场景下]                           ← 上下文
I want to [完成什么任务]                       ← 功能性Job
So that [达成什么目的]                         ← 更深层的Job
Instead of [当前替代方案及其不足]               ← 竞争视角
```

## M-10: 单位经济学(Unit Economics)

### 核心公式

```
CAC（客户获取成本）= 总销售市场费用 / 新增客户数
LTV（客户生命周期价值）= 客单价 × 毛利率 × 平均生命周期(月)
LTV/CAC 比值 → >3健康, >5优秀

CAC回收期（月）= CAC / (月贡献利润)
→ <12个月优秀, 12-18个月可接受, >18个月危险

贡献利润 = 收入 - 变动成本
→ 等于每多一个客户增加的利润
```

### 单位经济学恶化信号

```
□ LTV/CAC < 3 → 增长不可持续
□ CAC回收期 > 18个月 → 资金链压力
□ CAC逐年上升 → 竞争加剧/渠道失效
□ LTV逐年下降 → 产品价值衰减/流失率上升
□ 付费转化率逐年下降 → 产品-市场匹配减弱
```

## M-11: FMEA失效模式分析

### 来源：NASA/六西格玛

### RPN风险优先级

```
RPN = S(严重度) × O(发生频度) × D(检测难度)
每项1-10分

阈值：
RPN > 200 → 必须立即行动（不可接受风险）
RPN 100-200 → 强烈建议行动（高风险）
RPN 50-100 → 考虑行动（中等风险）
RPN < 50 → 可接受风险

改善方向：
1. 降低S → 修改设计/增加冗余/缓冲
2. 降低O → 预防措施/标准化/自动检查
3. 降低D → 早期预警/持续监控/定期检查
```

### FMEA模板

| 流程/功能 | 失效模式 | 失效影响 | S | 失效原因 | O | 当前控制 | D | RPN | 改善措施 |
|----------|---------|---------|---|---------|---|---------|---|-----|---------|
| | | | | | | | | | |

## M-15: MoSCoW优先级方法

### 来源：DSDM（Dynamic Systems Development Method）

### 核心概念

```
MoSCoW = Must Have + Should Have + Could Have + Won't Have

作用：在资源有限的情况下，对需求进行严格优先级排序
应用场景：需求管理、版本规划、MVP定义、项目范围谈判
```

### 四类优先级详解

| 级别 | 含义 | 占比建议 | 不做的后果 | 决策标准 |
|------|------|---------|-----------|---------|
| **Must Have** | 必须有，否则项目失败 | ≤60% | 系统不可用/项目失败 | 没有这个功能，解决方案是否还有意义？ |
| **Should Have** | 应该有，重要但非致命 | ≤20% | 严重影响体验但可通过workaround | 没有这个功能，是否严重影响核心流程？ |
| **Could Have** | 可以有，锦上添花 | ≤15% | 轻微影响体验 | 没有这个功能，用户是否基本感知不到？ |
| **Won't Have** | 本次不做 | 明确排除 | 无影响 | 是否可以在下一版本再做？ |

### MoSCoW优先级排序矩阵

```
                高
                ↑
        复杂度  │  Should Have    │  Must Have (先做)
         (低优) │  (第二批)        │  Must Have (后做)
                │                 │
        低      │  Won't Have     │  Could Have
                │                 │
                └─────────────────┴──────→
                低                 高
                        业务价值
```

### MoSCoW实战注意事项

```
1. Must Have占比必须≤60%：如果超过60%，说明团队对"必须"的定义过于宽松
2. Won't Have不是"不重要"：而是"本次不做"，可能在下一版本实现
3. 优先级排序需要利益相关者共识：BA引导讨论，但决策权在业务方
4. 与Kano模型联动：Must Have ≈ 必备型 + 高重要期望型
5. 动态调整：随着项目推进，优先级可能发生变化，需要定期回顾
```

### MoSCoW vs 传统优先级

| 传统优先级(P0/P1/P2) | MoSCoW |
|---------------------|--------|
| 层级模糊，P1和P2界限不清 | 四级明确，每级有清晰定义 |
| 容易全部标记为P0 | Must Have占比强制≤60% |
| 没有"明确不做"的类别 | Won't Have明确排除 |
| 适合技术团队内部 | 适合与业务方沟通 |

## M-16: Kano模型

### 来源：狩野纪昭（Noriaki Kano），东京理工大学

### 核心概念

```
Kano模型将需求分为五种类型，基于"功能实现程度"与"用户满意度"的非线性关系：

需求类型：
├── 必备型（Must-be Quality）：不实现会不满意，实现了不会更满意
├── 期望型（One-dimensional Quality）：实现越好越满意，越差越不满意
├── 魅力型（Attractive Quality）：不实现不会不满意，实现了会非常满意
├── 无差异型（Indifferent Quality）：实现与否对满意度无影响
└── 反向型（Reverse Quality）：实现了反而会不满意
```

### Better-Worse系数计算

```
Better系数 = (A+O)/(A+O+M+I)
  → 实现该功能后，用户满意度提升的程度（0~1）

Worse系数 = -(O+M)/(A+O+M+I)
  → 不实现该功能后，用户满意度下降的程度（-1~0）

其中：A=魅力型, O=期望型, M=必备型, I=无差异型
```

### Kano分类判定表

| 需求类型 | Better系数 | Worse系数 | 策略 |
|---------|-----------|----------|------|
| **魅力型 (Attractive)** | >0.5 | -0.3~0 | 优先做：低成本高惊喜，差异化竞争 |
| **期望型 (One-dimensional)** | 0.3~0.5 | -0.6~-0.3 | 必须做：与满意度线性相关，核心竞争力 |
| **必备型 (Must-be)** | <0.3 | <-0.6 | 基础必做：不做会严重不满意，但做了不加分 |
| **无差异型 (Indifferent)** | ≈0 | ≈0 | 不做：浪费资源 |
| **反向型 (Reverse)** | <0 | >0 | 绝对不做：做了反而降低满意度 |

### Kano问卷设计

```
每个功能问两个问题：
1. 功能性问题：如果这个功能实现了，你感觉如何？
2. 反功能性问题：如果这个功能不实现，你感觉如何？

选项：
- 我喜欢（I like it）
- 理所当然（It must be）
- 无所谓（Neutral）
- 可以忍受（I can tolerate it）
- 我不喜欢（I dislike it）

根据两个问题的答案组合，查表判定需求类型
```

### Kano模型生命周期

```
同一功能随时间推移，类型会发生变化：
魅力型 → 期望型 → 必备型

示例：手机指纹解锁
- 2013年（iPhone 5s首发）：魅力型 → 惊喜功能
- 2016年：期望型 → "这个价位应该有指纹"
- 2020年：必备型 → "没有指纹解锁的手机不买"
```

### Kano与MoSCoW联动

| Kano类型 | 对应MoSCoW | 优先级策略 |
|---------|-----------|----------|
| 必备型 | Must Have | 必须做，但不要过度投入 |
| 期望型（高Worse） | Must Have / Should Have | 重点投入，与竞品对标 |
| 魅力型 | Could Have / Should Have | 低成本高惊喜优先 |
| 无差异型 | Won't Have | 不做 |
| 反向型 | Won't Have | 绝对不做 |

## M-17: BDD行为驱动开发

### 来源：Dan North（2006年提出）

### 核心概念

```
BDD = Behavior-Driven Development（行为驱动开发）

核心思想：用自然语言描述系统行为，让BA+Dev+QA+业务方都能理解
本质：将"需求"表达为"行为"，用"示例"替代"抽象描述"
```

### BDD三剑客（Three Amigos）

```
     BA (商业分析师)          Developer (开发者)          QA (测试)
    "业务需要什么？"         "技术上怎么实现？"         "边界情况有哪些？"
          │                       │                        │
          └───────────────────────┼────────────────────────┘
                                  │
                           共同编写验收标准
                           (Gherkin 场景)
```

### Gherkin语法详解

```gherkin
Feature: [功能名称]
  作为 [角色]
  我希望 [功能描述]
  以便 [业务价值]

  Scenario: [场景名称 - 正常流程]
    Given [前置条件]
    And [更多前置条件]
    When [用户操作]
    And [更多操作]
    Then [期望结果]
    And [更多期望结果]

  Scenario: [场景名称 - 异常流程]
    Given [前置条件]
    When [异常操作]
    Then [容错行为]

  Scenario Outline: [参数化场景 - 数据驱动]
    Given 用户在登录页面
    When 用户输入邮箱 "<email>"
    And 用户输入密码 "<password>"
    Then 系统显示 "<message>"

    Examples:
      | email              | password   | message         |
      | user@example.com   | correct123 | 登录成功         |
      | user@example.com   | wrong123   | 邮箱或密码错误    |
      | invalid@email      | correct123 | 邮箱格式不正确    |
```

### BDD核心原则

| 原则 | 说明 |
|------|------|
| **协作规范** | BA+Dev+QA共同定义验收标准，消除理解偏差 |
| **实例化需求** | 用具体示例代替抽象描述，"比如...假如..." |
| **活文档** | 验收测试可自动执行，文档与实际行为永远同步 |
| **业务语言** | 用业务术语而非技术术语描述行为 |
| **够用就好** | 不需要穷举所有场景，覆盖核心流程+关键异常即可 |

### BDD工具选型

| 工具 | 语言 | 适用场景 |
|------|------|---------|
| Cucumber | Ruby/Java/JS | 跨职能团队协作，最成熟 |
| SpecFlow | .NET/C# | .NET生态 |
| Behave | Python | Python项目 |
| JBehave | Java | Java项目 |
| Gauge | 多语言 | Markdown格式，更灵活 |

### BDD在BA工作流中的位置

```
需求引出 → BDD工作坊(Three Amigos) → Gherkin场景编写 → 验收标准确认 → 活文档维护
   ↑                                                                    ↓
   └──────────────── 自动化测试执行 ←──────────────────────────────────┘
```

## M-18: EventStorming事件风暴

### 来源：Alberto Brandolini（DDD社区）

### 核心概念

```
EventStorming = 一种协作式领域建模工作坊方法

核心思想：通过"领域事件"倒推业务流程和系统边界
适用场景：复杂业务领域建模、微服务边界识别、遗留系统改造
```

### 工作坊三层次

| 层次 | 目标 | 产出 | 时间 | 参与人 |
|------|------|------|------|--------|
| **Big Picture** | 建立领域全局认知 | 端到端业务流程全景 | 2-4小时 | 业务专家+BA+架构师 |
| **Process Level** | 识别核心流程和边界 | 限界上下文候选 | 4-8小时 | BA+Tech Lead+领域专家 |
| **Design Level** | 细节设计和实现规划 | 聚合、实体、值对象 | 8-16小时 | 开发团队+BA |

### 六种核心元素

| 元素 | 英文 | 颜色 | 说明 | 示例 |
|------|------|------|------|------|
| **领域事件** | Domain Event | 🟠 橙色 | 业务中已经发生的事实（过去式） | "订单已提交""支付已完成""商品已发货" |
| **命令** | Command | 🔵 蓝色 | 用户/系统发出的指令 | "提交订单""确认支付""发货" |
| **聚合** | Aggregate | 🟡 黄色 | 接收命令并产生事件的核心实体 | 订单、支付单、库存 |
| **策略** | Policy | 🟣 紫色 | 事件触发后自动执行的规则 | "订单支付成功后自动通知仓库" |
| **读模型** | Read Model | 🟢 绿色 | 为查询优化的数据视图 | 订单列表、待发货报表 |
| **外部系统** | External System | 🩷 粉色 | 外部依赖系统 | 支付网关、物流系统、短信网关 |

### EventStorming工作坊流程

```
Step 1: 贴领域事件（橙色）— 按时间线贴出所有业务事件
Step 2: 补充命令（蓝色）— 什么触发了这些事件？
Step 3: 识别聚合（黄色）— 哪些实体负责处理命令？
Step 4: 标注策略（紫色）— 事件触发后自动发生什么？
Step 5: 标注读模型（绿色）— 用户需要看到什么信息？
Step 6: 标注外部系统（粉色）— 需要调用哪些外部服务？
Step 7: 识别限界上下文 — 基于事件流自然聚类
```

### 与DDD限界上下文的协同

```
EventStorming → 发现领域事件和业务规则
DDD限界上下文 → 基于事件边界划分微服务/模块
BA + Tech Lead共同参与，产出既符合业务又可行的架构边界

限界上下文识别信号：
- 事件自然聚类：一组事件围绕同一业务概念
- 术语变化：同一事物在不同上下文中名称不同
- 业务规则边界：不同上下文的规则独立变化
```

## M-19: BABOK敏捷扩展

### 来源：IIBA Agile Extension v2

### 核心概念

```
BABOK敏捷扩展 = BABOK V3在敏捷环境下的应用指南

核心思想：BA在敏捷团队中的角色从"文档编写者"转变为"协作推动者"
```

### 敏捷BA七大原则

| 原则 | 含义 | 实战应用 |
|------|------|---------|
| **See the Whole** | 理解端到端业务上下文 | 用Story Map连接战略和细节 |
| **Think as a Customer** | 从用户视角思考 | 用户旅程地图、用户画像、体验指标 |
| **Analyze to Determine What is Valuable** | 聚焦价值而非产出 | Impact Mapping从目标反推需求 |
| **Get Real Using Examples** | 用实例化需求 | Specification by Example, Gherkin场景 |
| **Understand What is Doable** | 理解技术可行性 | Three Amigos协作（BA+Dev+QA） |
| **Stimulate Collaboration and Continuous Improvement** | 激发协作与持续改进 | 回顾会议、社区实践 |
| **Avoid Waste** | 消除浪费 | 最小可行需求，不过度分析 |

### 传统BA vs 敏捷BA

| 维度 | 传统BA | 敏捷BA |
|------|--------|--------|
| 需求文档 | 前置完整需求文档 | 持续对话，Just-in-time需求 |
| 工作方式 | 文档驱动 | 协作驱动 |
| 团队位置 | BA作为中间人 | BA嵌入开发团队 |
| 确认方式 | 签字确认 | 持续确认 |
| 设计方式 | 大设计（BDUF） | 浮现式设计 |
| 需求粒度 | 完整功能规范 | 用户故事+验收标准 |
| 变更管理 | 正式变更控制流程 | Backlog优先级动态调整 |

### 敏捷BA核心实践

```
1. 用户故事拆分（User Story Splitting）
   Epic → Feature → User Story → Task
   拆分原则：INVEST（Independent, Negotiable, Valuable, Estimable, Small, Testable）

2. Backlog梳理（Backlog Refinement）
   频率：每个Sprint 5-10%时间
   产出：优先级排序的Ready Backlog

3. 验收标准驱动（Acceptance Criteria Driven）
   每个Story必须有AC，AC必须可测试
   优先使用Gherkin格式

4. 持续引出（Continuous Elicitation）
   不是一次性引出，而是每个Sprint持续对话
   技术：用户访谈、观察、数据分析、A/B测试

5. 最小可行产品（MVP）
   用Story Map + MoSCoW定义MVP边界
   MVP = 最小功能集 × 可验证假设
```

### 敏捷BA在Scrum中的节奏

```
Sprint 0: 愿景+初始Backlog+架构概要
Sprint Planning: 讲解Story+验收标准
Daily Standup: 回答Dev的业务问题
Sprint期间: 准备下个Sprint的Backlog（Refinement）
Sprint Review: 验收完成的Story
Sprint Retro: 改进BA实践
```

### 敏捷BA vs 传统BA技能对比

| 技能 | 传统BA权重 | 敏捷BA权重 |
|------|----------|----------|
| 文档编写 | 高 | 中 |
| 协作推动 | 中 | 高 |
| 用户故事编写 | 低 | 高 |
| 验收标准定义 | 中 | 高 |
| 利益相关者管理 | 高 | 高 |
| 数据分析 | 中 | 高 |
| 技术理解 | 低 | 中高 |

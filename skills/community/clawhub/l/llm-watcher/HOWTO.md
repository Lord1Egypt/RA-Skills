# 盯 —— 盯住你正在用的模型，看它哪天悄悄变差

> 一个单机工具。用你自己的活，定期测一遍，把「感觉变笨了」变成「数据说变了」。

---

## 它解决什么

每次厂商发新版、或者服务器吃紧，都会有人觉得模型变笨了。

但没人能证明。手上只有手感、延迟、和一种说不清的口癖。

这个工具只做一件事：**同一批题，定期重跑，比数字。**

---

## 它只测什么

**只测能客观检验的东西：**

| 检验类型 | 怎么判 | 例子 |
|---|---|---|
| `python` | 把输出当代码真跑一遍 | `assert fib(10) == 55` |
| `json` | 解析并核对键值 | `{"count": 42}` |
| `regex` | 正则计数 | 「10 条带编号」 |
| `contains` | 含某几个词 | 答案里有没有 `221` |
| `exact` | 完全相等 | 只接受一个词 |

**它不测「写得好不好」。**

因为实验测过：同一道题，它每次写的东西有 **三分之二不一样**。写得不一样，不等于写得差。那个测不了。

---

## 记录哪两个指标

```
通过率      （带检验的题，过了几个）
字数        （输出有多长）
```

**为什么要这两个：**

实验结果——同一模型反复跑，**字数变异只有 0—6%**。

所以如果哪天字数掉了 30%，那不是噪声。

---

## 用法

```bash
# 1. 建一个题库（会生成 4 道样例题）
python analysis/watch.py init

# 2. 改成你自己的活 —— 编辑 out/watch/tasks.json

# 3. 跑一轮，存快照
python analysis/watch.py run --note "上线当天的基线"

# 4. 过一阵再跑
python analysis/watch.py run --note "5.5 发布后"

# 5. 比一比
python analysis/watch.py compare

# 6. 看历史
python analysis/watch.py list
```

---

## 题库格式

```json
{
  "model": "qwen-plus",
  "provider": "dashscope",
  "temperature": 1.0,
  "repeat": 3,
  "tasks": [
    {
      "id": "fib",
      "prompt": "用 Python 写一个 fib(n) 函数……只输出代码。",
      "check": {"type": "python", "code": "assert fib(10) == 55"}
    },
    {
      "id": "arith",
      "prompt": "13 乘以 17 等于多少？只输出数字。",
      "check": {"type": "contains", "any": ["221"]}
    }
  ]
}
```

---

## 判定规则

```
通过率掉了            → 退化
通过率升了            → 变好
字数变了 25% 以上     → 长度变
其余                  → 没变
```

**25% 这个线是拍的。** 因为实测字数变异 0—6%，25% 是它的四倍，不太可能是噪声。

---

## 题库怎么出（这一条最重要）

**题太简单，两个模型都能过，测不出区别。**
**题太难，基线就过不了，也没法当基线。**

**对的难度是：基线模型 100% 通过，但只要稍微降级就掉一个。**

**怎么找到这个难度：**

1. 先出一批题
2. 跑 3 次
3. **只留「3/3 通过」的**
4. 再跑一次，**只留「还是 3/3」的**
5. 剩下的就是稳定的基线题

**跑了会掉的题，直接删掉。** 它们不是基线，是噪声。

---

## 已知的限制

**一、只对「有客观检验的活」有效。**

代码、SQL、格式转换、算术 —— 能测。
写文案、写分析、做设计 —— 测不了。

**二、长度变了不等于变差。**

变长可能是啰嗦，也可能是更详细。它只是一个**警报**，不是判决。

**三、跨模型不能直接比。**

工具会提示，但那不是降级，是换了东西。

**四、这工具测的是「你的活」，不是「模型整体」。**

你的题不代表别人的题。这是它的优点，也是它的边界。

```

```

## 一份完整方案，包含这 7 个部分

这不是“看情况给多少”，而是服务的**最低交付标准**：攻略类需求（行程/规划/线路/玩几天）必须按下列章节以 Markdown 分节输出，篇幅不少于 800 字，逐日安排具体到景点与时段。

| # | 章节 | 里面写什么 |
|---|---|---|
| 1 | **行程总览** | 目的地组合、建议天数、整体节奏与主题 |
| 2 | **逐日行程安排** | Day 1 ~ Day N，每天按上午/下午/晚上展开：景点、游玩时长、当日顺序的**理由**、需提前预订的项目提醒 |
| 3 | **城际与市内交通** | 往返方式、大致耗时、换乘与预订建议 |
| 4 | **住宿建议** | 推荐**区域 + 房型理由**（住哪一片方便去哪些景点），不是罗列酒店名 |
| 5 | **美食推荐** | 结合目的地特色与同行人群（带娃/带老人/忌口） |
| 6 | **预算估算** | 人均或分档报价，按交通/住宿/餐饮/门票大项拆分 |
| 7 | **重要注意事项** | 按同行人差异化：老人（节奏放缓/就医便利/无障碍）、儿童（安全/兴趣点/作息）、团队（集合与分工） |

## 专业度是这样把关的

每份方案在交付前都会对照以下 6 项标准自查，发现问题**直接在正文里改正**，而不是只写一句“请自行留意”。

| 把关项 | 具体要求 |
|---|---|
| **假设显式化** | 未确认的信息（假期天数与是否含往返、人数构成、老人步行能力、孩子年龄与作息、总预算）先用“本方案假设…”声明，不把假设藏进成品 |
| **季节与时效适配** | 项目必须符合出行季节（如冬季海滨说明水温、泳池是否恒温），旺季闭馆/限流/停演一律标注“需核实” |
| **老人儿童真能走** | 逐日写清门到门移动方式、连续步行或站立时长、是否真的回酒店午休；并给出老人中途退出、孩子疲惫或下雨时的**兜底方案**；家庭/团队出行一天不超过 2 个有距离的大景点 |
| **事实可靠** | 景点、城市、班次、票价不得错误或自相矛盾；酒店儿童俱乐部、Spa、演出等未核实服务写成“需向酒店/官方确认”，不写成已确认日程 |
| **预算闭合** | 单价×数量=小计、分项之和=总额，人数/房间/晚数可重算，天数口径与逐日表一致 |
| **结构完整** | 上述 7 个章节齐全、层次清晰，拿到即可使用 |

生成之后还会跑一轮**独立审核**：按同样 6 个维度打分，只要存在中/高级问题就必须给出“修订后的完整答案”（不允许压缩成要点摘要），所以你拿到的是修订稿，不是初稿。

## 面向 Agent 的执行说明

以下为实现细节。用户只需看上面的内容；Agent 按此执行。

### 工作域校验

先在全部可用 Skill 的 `name` / `description` 里确认目标属于本 Skill（旅行方案 / 行程规划 / 仙踪问道 / 旅行咨询 PDF）。

- 属于本 Skill → 按本文执行。
- 只是"付款、买单、结账、扫码"意图，或上下文出现 `cashier*.alipay.com`、`excashier*.alipay.com`、`qr.alipay.com`、`Payment-Needed`、`amtPaymentLink` → 交给 **alipay-payment-skill**，本 Skill 不接管支付动作。
- 与本业务无关 → 不读本 Skill reference，不执行本 Skill 命令，转给最具体的匹配 Skill。

### 职责边界

**本 Skill = 旅行咨询业务编排 + 402 门控入口。** 只做四件事：收集校验行程要素与邮箱 → 取 402 账单并落盘原请求 → 用**同一订单同一请求体**取资源 → 展示正文与 PDF。
付款、账单签名、交易查询、履约回执一律交给官方 `alipay-bot`；**绝不自行实现付款、自建签名、自行构造履约回执或二次回执**。

### 依赖

| 依赖 | 用途 | 缺失时 |
|---|---|---|

### 请求契约

`POST https://api.riyuexinzhu.com/aipay/travel_consultant`，`Content-Type: application/json`；取货时额外带 `Payment-Proof`（只能来自官方 CLI 输出）。

| 字段 | 必填 | 说明 |
|---|---|---|
| `query` | **是** | 旅行咨询问题（目的地城市/天数/同行人/预算/节奏/必去/忌口，写全更准） |
| `email` | **是** | 接收排版化 PDF 方案的邮箱 |
| `country_code` | 否 | ISO 3166-1 alpha-2（`CN` / `IT`） |
| `intro_type` | 否 | 0 全部 / 1 城市地理 / 2 景点 / 3 美食 / 4 购物 / 5 交通 / 6 住宿 / 7 游玩攻略 / 8 历史文化 |
| `topic_type` | 否 | 0 全部 / 1 户外探险 / 2 文化历史 / 3 自然风光 / 4 美食购物 / 5 城市观光 / 6 研学教育 / 7 亲子游玩 / 8 康养医疗 / 9 宗教朝圣 / 10 红色纪念 |

| `options` | 否 | 扩展字典，可覆盖同名字段 |

空 `query` 或非法 `email` 在**支付前**返回 400，不产生账单——必须先校验再发起 402。

### 调用方法

| 子命令 | 作用 |
|---|---|
| `body` | 只组装并打印请求体（不发请求） |
| `probe` | 未付款请求，取得 402 账单；产出 `payment-needed.txt` / `body.json` / `state.json` |
| `pay` | 调用官方 `alipay-bot 402-buyer-pay`；**必须带 `--confirm`**（用户明确同意后） |
| `complete` | 付款后取资源：默认走官方 `402-query-payment-status`（可加 `--wait` 自动轮询）；`--proof` 走带凭证直取 |
| `render` | 把已保存的交付响应渲染成可展示文本 |

```bash

node "$SKILL_DIR/scripts/travel_aipay.mjs" body --query '杭州三日亲子游，2 大 1 小' --email buyer@example.com

node "$SKILL_DIR/scripts/travel_aipay.mjs" probe \
  --query '杭州三日亲子游，2 大 1 小，预算 5000 元以内，想少走路' \
  --email buyer@example.com --country-code CN --topic-type 7 --is-family-suitable 1

node "$SKILL_DIR/scripts/travel_aipay.mjs" pay --confirm --session-id '<当前会话标识>'

node "$SKILL_DIR/scripts/travel_aipay.mjs" complete --out-shake-no '<官方查询单号>'
```

状态文件默认在 `~/.xianzong-travel-aipay/`（0700/0600），与 cwd 无关、不入仓库；可用 `--state-dir` 覆盖。

### 退出码矩阵

| HTTP / 业务 | 含义 | 退出码 | 下一步 |
|---|---|---|---|
| `402` + `Payment-Needed` | 需要支付 | `0`（probe） | 用户确认后 `pay --confirm` |
| `200` | 交付成功（含同订单幂等重放） | `0` | 展示正文与 PDF；**不追加回执** |
| `409` + `Retry-After` | 支付已确认、资源生成中（正常需 2–3 分钟） | `3` | 按 `Retry-After`（默认 30s）用**同一订单号**轮询 `complete --out-shake-no`；**绝不重新付款** |
| `200` 但 `resp_code != 200` | 业务失败（已验付） | `4` | 原样报告原因；不自动重试、不重复付款 |
| `402`（带凭证重发后） | 凭证无效/过期 | `5` | 说明凭证失效并请用户核对支付宝账单；**不要直接引导二次付款** |
| `400` | 请求被拒 | `2` | 修正参数后再发起；未扣款 |
| `5xx` | 服务端错误 | `6` | 原样报告；仅网络类错误允许重试一次 |
| 查询返回 `resourceResponse: null` | 服务瞬时不可用（发布/重启或网络瞬断，请求在传输层就断了） | `6` | 用**同一订单号**原样重跑 `complete`（或加 `--wait`），**绝不重新付款** |

### 官方查询的载荷判读（2026-11-14 实测，必须按字段判断）

`alipay-bot 402-query-payment-status --output json` 只有三种形状，**退出码与 `resourceDelivered` 都不能用来判成功**：

| 形状 | 关键字段 | 含义 | 动作 |
|---|---|---|---|
| 成功 | `success: true` + `resourceResponse.status: 200` + `resourceResponse.body.content`（业务 JSON 字符串） | 资源已交付（`body.already_fulfilled=true` 时是幂等重放） | 直接展示，不再发回执 |
| 生成中 | `errorMessage` 含 `HTTP 409` + `resourceResponse.status: 409` | 已验付，方案在生成 | 用**同一订单**稍后再查（推荐 `--wait`） |
| 瞬时失败 | `errorCode: RESOURCE_REQUEST_FAILED` + `resourceResponse: null` | 服务发布/重启或网络瞬断 | 原样重跑（或 `--wait` 自动重试） |

补充事实：

- **服务端业务响应已显式给出 `resourceDelivered`**：本服务 200 响应体带 `resourceDelivered: true`，409（生成中）带 `resourceDelivered: false`，可直接判读；而官方 CLI 信封里的同名字段带 `omitempty`（成功时缺失），**不能**用信封字段判成功。
- **`resourceDelivered` 不是 402 协议字段，也不是官方文档化的约定**：它只是 `alipay-bot --output json` 结果信封里的内部字段（二进制里存在 `json:"resourceDelivered"` 与 `json:"resourceDelivered,omitempty"` 两处，成功路径会被省略，只有失败载荷显式出现 `false`）。可以用于诊断，**不能用作成功/失败判据**。
- **成功载荷不带 `resourceDelivered` 字段**（它只出现在失败载荷里）。用 `resourceDelivered === true` 或 CLI 退出码判成功 → 会误判成“未交付”，一直重复查询；而服务端日志其实早已是 `state=FULFILLED, is_first_delivery=False`（即订单已履约，重复查询只是幂等重放，不会重复扣费）。
- 业务层失败（已验付但 `resp_code != 200`）仍是 HTTP 200，要看 `body.content` 里的 `resp_code`，不得当成功展示。
- 直接使用 `complete --out-shake-no '<单号>' --wait`：脚本内部按上述字段判读并自动轮询（默认 40s 一次，最长 15 分钟），不需要自己写 grep 轮询循环。

### 执行流程

详细命令与判读见 [references/402-travel-flow.md](references/402-travel-flow.md)（进入支付前必须读一次）。

1. **收齐要素**：`query` + `email`。缺 `email` 必须停下来问，不得编造。
2. **本地校验**：`body` 打印请求体，确认字段。
3. **取账单**：`probe` → 账单/请求体/状态三件套。
4. **停在付款确认前，并把支付入口原样交给用户**：告知单价、商品名、订单号；展示本次 `pay` 输出里的**支付宝二维码图片与「支付方式」链接**（图片走图片通道、并删掉文本中的 `MEDIA:` 行；链接逐字符完整保留、不得截断或改写），同时提醒“0.99 元、一次性、需本人支付宝扫码确认 AI 付、付完回来说一声、不要重复付款”。**未经用户本次对话明确确认，不得执行 `pay --confirm`。**
5. **付款后取货（预计 2–3 分钟）**：优先用 `complete --out-shake-no '<官方查询单号>' --wait`（脚本会按官方载荷字段自动判断 409/瞬时失败并轮询，最长 15 分钟，不会重复扣费），或 `complete --proof '<凭证>'`。若不用 `--wait`，则每次返回 409 时按 `Retry-After`（默认 30s）用**同一订单号**再查，并向用户说明“专业方案通常需要 2–3 分钟，生成成功后 PDF 会自动发到邮箱，无需重新付款、也不必一直盯着对话”。
6. **展示**：正文原样展示；PDF 链接（含签名参数）**完整输出不得截断**，说明约 90 天有效且已发邮箱；**不展示任何 cost / pricing 字段**。

### 硬性边界

- **付款只走官方 CLI**：`402-buyer-pay` / `402-query-payment-status` / `402-buyer-fulfillment-ack`（仅在官方输出明确回执失败且用户要求恢复时）。不自行请求支付宝、不构造签名、不改造 `Payment-Needed` 头。
- **同一订单复用**：`probe` 生成的 `body.json` 就是这一单的请求，重试/查询复用它；不换内容、不新建订单。
- **状态不明先查单**：超时、输出不完整、用户说"付好了/继续/好了吗"、拿到 409 → 先查原订单，不重新付款。
- **成功不追加回执**：官方命令已自动回执，不再发第二个。
- **支付入口必须原样展示**：二维码图片与支付链接只能来自**本次** `pay` 输出；不复用历史/别人的链接、不改写、不省略。链接过期就重新发起账单，绝不编造支付地址。
- **敏感信息**：`Payment-Proof`、账单文件只落 0600 文件，不回显到面客文本。
- **生产红线**：只调用这一条已部署的付费接口，不改服务端代码、不改 `src/configs/aipay.yml`、不改生产数据。

### 已知陷阱

- **轮询判据（2026-11-14 实测踩坑）**：官方查询的成功载荷**没有** `resourceDelivered` 字段，判成功只能看 `success: true` + `resourceResponse.status: 200`；`resourceResponse: null` 是瞬时不可用（可重试），不是交付失败。不要自己写 grep 轮询循环，直接用 `complete --wait`。
- `skills/` **不在 VS Code 默认技能目录清单**，依赖 `.vscode/settings.json` 的 `chat.agentSkillsLocations` 登记；无设置时只能被明确点名手动加载。
- `name` 只能用小写字母/数字/连字符且必须等于目录名（`travel_aipay` 这类下划线写法非法）。
- `Payment-Needed` 是 **Base64URL**，不要直接当 JSON 解析。
- 服务端验付响应缺 `amount` 会被拒绝并重新出账 → 再拿到 402 时**不能**当作"未支付"重新付款。

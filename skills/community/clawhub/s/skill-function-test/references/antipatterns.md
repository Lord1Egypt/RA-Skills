# 反模式（Anti-Patterns）

> 本文件收录 skill-function-test 使用过程中的常见反模式。

### 测试范围过大
选择全部维度却不设 fix_mode=0，会导致大量 WARN 涌入，LLM 后处理阶段难以逐一审核。

**正确做法**：首次测试用 `fix_mode=0`（仅报告），选定核心维度后逐步扩大。

### 跳过备份直接修复
不备份就执行修复模式，一旦修复失误无法回滚。

**正确做法**：始终使用 `runner.py` 全流程，阶段 1 自动备份。

### 在目标技能目录下手动更新测试残留文件
`.scenario-test_*` 文件为自动生成，手动编辑会被覆盖。

**正确做法**：依赖阶段 9 清理，不手动更新。

### 修复建议越界
LLM 在阶段 5 修复时不应新增功能或更新业务逻辑。

**正确做法**：只修复阻断性 bug（F-0）和风险项（F-1），不扩展功能。

### S4 阶段B 推理输出不校验 schema
LLM 自主设计噪音方案时跳过 schema 校验，产出模糊的噪音描述（"视情况插入干扰"）。这会使阶段C 执行时无法确定具体操作。

**正确做法**：阶段B 的输出必须通过 s4_engine.validate_noise_plan() 的 schema 校验，不能有任何模糊字段。

### S4 阶段C 跳过噪音条目
执行噪音方案时只执行了部分条目（"这条看起来不必要"），导致坚守率矩阵不完整。

**正确做法**：阶段C 必须执行噪音方案中的所有条目。未执行条目视作执行失败，报告标注"未完成"。

### S4 阶段C 用"记忆隔离"替代"噪音注入"
试图通过清除会话记忆来获得干净环境，既不可实现也偏离 S4 目的。

**正确做法**：S4 不在干净环境下测试，而是在主动制造噪音的脏环境下测试。

### 误以为 S4 坚守率低是目标技能的 bug
S4 坚守率低只说明 SKILL.md 中的约束在脏环境下扛不住，属于**约束设计缺陷**而非编码错误。

**正确做法**：S4 只报告、不修复目标技能代码。基于 S4 报告改进 SKILL.md 的约束表达或增加脚本级强制机制。

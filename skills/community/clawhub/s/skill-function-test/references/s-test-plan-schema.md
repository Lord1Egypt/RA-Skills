# 场景测试用例编写规范

## 设计原则

S（场景测试）不是扫描代码。LLM 基于对目标技能的 SKILL.md 和蓝皮书的完整理解，**手工编写真实的用户场景**作为测试用例。

| 维度 | 测试什么 | 怎么写 |
|------|---------|--------|
| **S1** | 触发场景 — 用户说什么，技能怎么响应 | 写用户输入的触发词，以及期望触发的行为 |
| **S2** | 核心能力 — 给定输入，技能输出什么 | 写函数/模块调用参数，以及期望返回的结果特征 |
| **S3** | 工作流链路 — 多步骤连贯执行 | 写完整流程描述，以及各阶段间数据传递的期望 |

## JSON 格式

每条用例可包含一个 **`modules` 字段**，指定该场景涉及的 Python 模块名（不含 `.py` 后缀）。场景引擎会根据 `modules` 直接定位脚本，**不再通过关键词猜测**。

```json
{
  "S1": [
    {
      "id": "S1-01",
      "name": "简短描述",
      "trigger": "用户输入的自然语言触发词",
      "expected": "期望触发的行为和输出",
      "type": "trigger",
      "modules": ["runner", "analysis_engine"]
    }
  ],
  "S2": [
    {
      "id": "S2-01",
      "name": "简短描述",
      "input": "调用参数描述或具体数据",
      "expected": "期望的返回值或行为特征",
      "type": "capability",
      "modules": ["economic_analysis_engine"]
    }
  ],
  "S3": [
    {
      "id": "S3-01",
      "name": "简短描述",
      "steps": ["步骤1描述", "步骤2描述"],
      "expected": "各步骤间数据传递的期望结果",
      "type": "workflow",
      "modules": ["runner", "wbs_engine", "analysis_engine"]
    }
  ]
}
```

## 每条至少包含

- **id**: 唯一编号，如 S1-01
- **name**: 一句话说明测什么
- **input/trigger/steps**: 测试条件
- **expected**: 预期结果（具体可验证）
- **type**: 类型标识

## 可选字段

- **modules** (string[]): 该场景涉及的 Python 模块名数组。**建议填写**——引擎优先使用此字段直接定位脚本，没写才 fall back 关键词匹配。模块名对照蓝皮书的 `file_manifest.python` 列表。

## 数量要求

每个维度至少 1 条，建议每个维度 2-3 条以覆盖不同场景。

# Capability and Evolution

Capability comes from an arrangement sufficient to produce a result. Before claiming a relation, determine which party can see, who can change state, whether an action can reach its object, and how long the result takes to return. Real collaborators, scripts, another person's specialist system, data, and services can all be parts of a capability.

## What counts as a capability

A capability is a relational structure in which people, AI, knowledge, tools, rules, and feedback can repeatedly transform an input or initial state into a valuable result under stated conditions.

A capability can explain:

- who can now do what they could not do before;
- the objects, inputs, conditions, scale, and freshness for which it applies;
- how its parts connect, and who owns, executes, confirms, and maintains them;
- what it produces, and how tool completion, object change, and actual usefulness are each known;
- the real tasks and counterexamples on which it has been validated;
- which signals call for revalidation, replacement, retirement, or return to a person.

## From candidate to capability

| State | Accurate name |
| --- | --- |
| Purpose and components described | Design |
| Implementation exists but has not run | Candidate or draft |
| Passes an isolated sample or simulation | Tested implementation |
| Completes the user's real task and receives the corresponding confirmation | Validated capability |
| Remains effective across applicable inputs, with clear failure boundaries | Reusable capability |

Use language that matches the evidence. Code running proves that the implementation can execute. Success on a real task proves the capability under those conditions. Repeated validation and boundary cases extend the trusted range.

## How capabilities are organized and created

Begin with the models, tools, materials, practices, collaborators, and other systems already present. An LLM may perform cognitive or creative work directly, invoke an existing capability, adapt an interface, generate code, establish an observation point, change the human–AI division of work, or organize a new collaborative relation. Choose an implementation with suitable cost, reliable effect, and real user ownership under present conditions.

A new component is worth adding when it changes a critical relation. Add feedback to the capability: what is checked, who can see it, and where failure returns. When an upstream condition changes, affected capabilities can be located and revalidated, while a new implementation can take over the same purpose.

| Change needed | What can be organized | Evidence that confirms the effect |
| --- | --- | --- |
| Something previously invisible | A new observation point or a way to compare two sets of observations | Real materials reveal a difference that was previously missed |
| Existing tools cannot work together | An interface connection plus the missing semantic or responsibility handoff | A real task is completed in an authorized environment and can be checked by both sides |
| People repeatedly solve the same problem | A reusable tool or a better collaborative arrangement | A different applicable real input still produces a useful result |
| The arrangement works only under current conditions | Explicit applicability, responsibility, and change signals | A condition change is detected and a better arrangement can take over |

Build as much real capability as the authorized environment permits, run it, and inspect the output. When production authority is needed, first construct an inspectable tool, draft, or simulation and state exactly what exists and who confirms the next step. Simulation, test environment, and real application remain distinct.

Feedback returns to the part it can change. One counterexample can correct a hypothesis; repeated failure can change a source, interface, or division of work. Preserve the relation and capability that can still act in the future. When a formerly effective arrangement fails, return to a reliable version, reorganize, or let its owner remove it. Before retrying, ask the real state holder whether the previous action occurred—especially when repetition would produce a second effect.

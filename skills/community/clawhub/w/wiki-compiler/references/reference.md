# Wiki 编译参考

## 传统 RAG vs Wiki 编译

理解两者区别，有助于在编译过程中做出正确的决策：

| 特性 | Wiki 编译（本技能） | 传统 RAG |
|------|-------------------|----------|
| 核心 | 知识编译，生成结构化文档 | 信息检索，查找相关片段 |
| 存储 | 知识库文件夹 + 文档 | 向量数据库 |
| 检索 | LLM 基于文档结构"内生理解" | 基于向量相似度的外部检索 |
| 知识积累 | 产出可回流，系统持续演化 | 每次问答相对独立 |
| 可追溯性 | 强，答案可定位到具体文档 | 弱，依赖检索片段 |
| 适用规模 | 中等规模（数百篇） | 海量规模（企业级） |

## 文件夹设计模式

### 按主题分类（最常用）

```
知识库/
├── 基础理论/
├── 实务方法/
├── 准则与法规/
├── 案例库/
│   ├── 案例A/
│   └── 案例B/
└── 前沿趋势/
```

适用场景：通用知识领域，概念间有清晰的学科边界。

### 按工作流分类

```
知识库/
├── 输入与规范/
├── 执行与操作/
├── 输出与报告/
└── 质量与复核/
```

适用场景：流程导向的领域（如审计、项目管理），知识按工作阶段组织。

### 按角色/场景分类

```
知识库/
├── 入门必读/
├── 执行手册/
├── 管理参考/
└── 专题研究/
```

适用场景：知识库有不同层级的用户，需按使用场景分层。

## 交叉引用模式

在编译 Wiki 时，通过以下方式建立概念间的关联：

1. **文件夹命名暗示关联**：如"审计实务方法"和"审计准则与法规"并列，暗示实务与法规的对照关系
2. **主题导览文档中显式引用**：在导览中写明"参见 XX 文件夹"，比隐式关联更可靠
3. **案例关联**：案例库中的案例与主题文件夹中的理论/方法形成"理论-实践"映射
4. **标签补充关联**：用标签标记跨文件夹的共享主题（如"风险""机器学习"），弥补树状结构的不足

## 标签与文件夹的协同

### 推荐模式："文件夹 × 标签" 二维组织

| 维度 | 文件夹 | 标签 |
|------|:---:|:---:|
| 主导维度 | 主题分类 | 多维关联 |
| 结构 | 树状（一文件一父） | 网状（一文件多标签） |
| 人类友好 | 高（导览） | 低（API） |
| 机器友好 | 低 | 高 |
| 一致性要求 | 文件归属唯一 | 一文件多标签 |
| 创建方式 | 必须事先规划 | 可渐进添加 |
| 删除风险 | 不可逆 | 不可逆（破坏性操作） |

### 核心原则

- **职责不重叠**：文件夹负责"内容组织"，标签负责"维度标记"
- **互为补充**：标签给文件夹扩展维度，文件夹给标签赋予语义
- **低耦合**：任一失效，另一方仍可独立工作
- **演化同步**：增量更新时联动，但不强依赖

### 反模式

- ❌ 用标签完全替代文件夹（破坏结构清晰性）
- ❌ 用导览重复标签内容（维护成本翻倍）
- ❌ 标签命名与文件夹名完全重复（难以协同）
- ❌ 标签命名与导览标题完全不一致（难以协同）

### 标签 ↔ 导览协同模式

| 关联方式 | 说明 |
|---------|------|
| 导览打主题标签 | 让 `get_knowledge_list(tags=["状态:已编译"])` 找出所有已编译导览 |
| 跨主题自动发现 | 用 `get_knowledge_list(tags=["主题:XXX"])` 找跨文件夹相关内容 |
| 标签变化触发导览更新 | 新增/删除标签后，检查相关导览是否需要更新 |

## 反模式教训

以下是从实战中总结的常见错误，编译时务必避免：

### 反模式 1：Markdown 表格中包含 `|` 字符

**问题**：知识库文章标题常含 `|`（如"实务 | 审计抽样实操总结"），在 Markdown 表格中 `|` 是列分隔符，导致表格解析错乱——一个单元格的内容会被拆成多列。

**错误示例**：
```markdown
| # | 文章 | 关键词 |
|---|------|--------|
| 1 | 实务 | 审计抽样实操总结 |  ← "实务"和"审计抽样实操总结"被拆成两列
```

**正确做法**：使用编号列表替代表格：
```markdown
1. **实务｜审计抽样实操总结** — 审计抽样实操、统计抽样方法
```

### 反模式 2：通过 `push_note` + `content_cos_key` 写入短内容

**问题**：COS 上传路径对内容格式敏感，中间环节多（本地文件 → COS 上传 → API 读取），任何一环出错都会导致笔记内容丢失或被系统自动删除（`export_note` 返回 "doc is delete"）。

**正确做法**：对于 < 3KB 的内容，直接使用 `import_doc` + `curl -d @filepath` 写入，跳过 COS 中间环节。

### 反模式 3：创建笔记后不验证

**问题**：笔记创建接口返回成功不代表内容完整。可能出现：标题正确但正文为空、内容被截断、笔记被系统自动清理等情况。如果不验证，用户在知识库中看到的是空笔记，且问题难以追溯。

**正确做法**：创建笔记后立即调用 `export_note` 导出内容，与原始内容比对。验证失败则删除重建（在 IMA 客户端手动删除）或用不同方式重试。

### 反模式 4：导览内容基于本地缓存而非知识库实际状态

**问题**：本地 `.md` 文件可能被其他任务覆盖或已过时，基于本地文件生成的导览与知识库实际文章不匹配。

**正确做法**：导览笔记的文章列表必须从 `get_knowledge_list` 返回的实际文件生成，确保导览与知识库真实内容一致。

## IMA 知识库文件夹机制（核心）

### 三种"文件夹"的本质差异

| 操作 | API | 效果 | 何时使用 |
|------|-----|------|---------|
| **创建文件夹** | `create_folder` | 在知识库根目录建一个新文件夹 | 建立分类骨架 |
| **虚拟归类** | `add_knowledge` | 让文件"看起来"在文件夹中（**parent_folder_id 不变**）| 临时展示 |
| **物理归类** | `move_knowledge` | 真正修改 `parent_folder_id` 为目标文件夹 | 真正整理 |

**关键警告**：
- `add_knowledge` 创建的是"虚拟关联"，不改变 `parent_folder_id`
- 仅用 `add_knowledge` 而不调用 `move_knowledge`，文件永远挂在根目录
- 根目录调用 `get_knowledge_list` 会返回所有文件（包括已"虚拟关联"的），但这不代表它们真正归属于文件夹

### 判断散落文件的正确方法

```python
# ❌ 错误：通过 folder_id 查询判断归属
files_in_folder = get_knowledge_list(folder_id=X)
# 这是"虚拟关联"的视图，不是真实归属

# ✅ 正确：检查 parent_folder_id
all_files = get_knowledge_list(kb_id)  # 不带 folder_id
orphans = [f for f in all_files
           if f.get("media_type") != 99
           and f.get("parent_folder_id") == ROOT_FOLDER_ID]
```

### move_knowledge 的副作用清单

| 副作用 | 应对方式 |
|--------|---------|
| `parent_folder_id` 改变 | ✅ 这是目标行为 |
| 文件标签数组被清空 | ⚠️ 移动前必须备份 |
| 移动跨知识库 | ⚠️ 仅在必要时使用 |

### 文件夹层级模式

```
模式 A：扁平（推荐用于中等规模）
├── 知识库根
│   ├── 文件夹 1
│   ├── 文件夹 2
│   └── 文件夹 3

模式 B：2 层嵌套（推荐用于复杂领域）
├── 知识库根
│   ├── 文件夹 1
│   ├── 文件夹 2（复杂主题）
│   │   ├── 子文件夹 A
│   │   ├── 子文件夹 B
│   │   └── 子文件夹 C
│   └── 文件夹 3
```

**原则**：
- 不超过 3 层（SKILL.md 推荐）
- 父文件夹放主题导览
- 子文件夹**不需要**各自的导览
- 子文件夹之间应 MECE

### 实战流程（量化投资知识库案例）

```
1. 诊断：发现 35 个文件 parent_folder_id 是根目录
2. 归类：调用 move_knowledge × 7 批次，把 35 个文件按主题归类
3. 验证：根目录变空，每个文件夹 parent_folder_id 正确
4. 多层结构：当父文件夹下"直接挂载文件"主题匹配子文件夹时，再调用 move 到子文件夹
```

### 与 add_knowledge 的对比使用场景

| 场景 | 用什么 API |
|------|----------|
| 临时把笔记"展示"在文件夹中 | `add_knowledge` |
| 把已有文件真正归类 | `move_knowledge` |
| 新建文件时指定归属 | `add_knowledge`（创建时即关联）|
| 把根目录散落文件归位 | `move_knowledge` |
| 调整多层结构 | `move_knowledge` |

## A.1 缺陷严重程度量化判定标准

在评定缺陷严重程度时，必须严格按下表逐条对照，禁止凭主观感觉随意定级。若一个缺陷同时满足多个级别的条件，取最高级别：

| 严重程度 | 必要判定条件（满足任意一条即可定级） | 典型场景举例 |
|:---:|------|------|
| **Critical 严重** | ① 核心业务流程完全中断，用户无法完成关键任务<br>② 用户数据丢失或不可恢复<br>③ 安全漏洞可被直接利用（无需复杂前置条件）<br>④ 支付/交易链路异常导致资金损失 | 支付接口始终返回 500、登录后核心页面白屏、SQL 注入可读取全量用户数据 |
| **High 高风险** | ① 核心功能可用但严重受阻（需非正常操作才能绕过）<br>② 数据计算/展示错误且影响业务决策<br>③ 无降级方案的异常崩溃<br>④ 越权访问（低权限用户可查看高权限数据） | 统计报表数值偏差超 20%、关键操作偶发 Uncaught Error、普通用户可查看管理员面板 |
| **Medium 中度** | ① 边界场景异常（极端输入/特殊字符/超长文本）<br>② 非核心功能不可用<br>③ 有降级方案但用户体验显著下降<br>④ 并发/竞态条件下的偶发错误 | 附件上传 0 字节文件报错、历史记录搜索功能失效、弱网下重复提交导致数据重复 |
| **Low 低微** | ① 视觉瑕疵（像素级偏移、色差、间距不统一）<br>② 文案错误（错别字、标点不规范、翻译不准确）<br>③ 无功能影响的交互不流畅<br>④ 非关键路径的 Console 警告 | 按钮 hover 态颜色偏差 5%、提示语多了一个句号、页面切换有 200ms 白屏闪烁 |

## A.2 全局缺陷编号规则

所有缺陷必须使用全局唯一编号，贯穿整个报告体系：

| 编号前缀 | 用途 | 来源文件 | 号段分配 | 示例 |
|:---|------|------|:---:|------|
| **DEF-XXX** | 业务/技术缺陷 | 01 / 02 | 001–999 全局递增 | DEF-001 |
| **SEC-XXX** | 安全漏洞 | 01 / 02 / 11 | **见 §A.2.5** | SEC-001 / SEC-101 |
| **CTR-XXX** | API 契约不一致项 | 01（静态）/ 05（动态） | **见 §A.2.1** | CTR-001 / CTR-101 |
| **PERF-XXX** | 性能瓶颈/缺陷 | 04 | 001–999 全局递增 | PERF-001 |
| **CON-XXX** | 并发与数据一致性缺陷 | 06 | **见 §A.2.2** | CON-001 |
| **CHA-XXX** | 混沌工程/故障注入缺陷 | 08 | **见 §A.2.3** | CHA-001 |
| **E2E-XXX** | 端到端浏览器测试缺陷 | 10 | **见 §A.2.4A** | E2E-001 |
| **OBS-XXX** | 可观测性缺陷 | 09 | 001–999 全局递增 | OBS-001 |
| **TRUNC-XXX** | 超时截断导致的未覆盖缺陷 | 00-E | 001–999 全局递增 | TRUNC-001 |
| **MAN-{章节码}-{序号}** | 人工检查清单项 | 03 | 章内 001 递增 | MAN-31-001 |

> 每个编号后必须标注证据来源类型：`[静态]` / `[动态]` / `[人工]`，例如：`SEC-001 [静态]`、`MAN-33-002 [人工]`。
>
> **MAN 格式**：`MAN-{章节码}-{序号}`。章节码见 `03-§3.0`；**禁止**使用跨章节全局续编的 `MAN-001`、`MAN-047` 等形式。

### A.2.1 CTR 编号号段分配（区分静态与动态来源）

为避免 01（静态契约）和 05（动态契约）产生的 CTR 编号冲突，按号段区分：

| 号段 | 来源 | 含义 |
|:---:|:---|------|
| **CTR-001 ~ CTR-099** | 01 静态代码审计（§1.5） | 代码层面发现的前后端字段不一致、类型不匹配 |
| **CTR-101 ~ CTR-199** | 05 动态契约测试（§5.1~§5.5） | 运行时发现的 Schema 不一致、字段缺失、错误码格式违规 |
| **CTR-201 ~ CTR-299** | 保留 | 未来扩展（如版本兼容性专项） |

**示例**：
- `CTR-005 [静态]`：01 发现 `POST /api/users` 前端传 `name: string`，后端期望 `username: string`
- `CTR-102 [动态]`：05 发现 `GET /api/products` 运行时返回 `total: string`，Schema 定义 `total: number`

**铁律**：01 不得使用 101+ 号段，05 不得使用 001–099 号段。

**号段溢出自动续编规则**：
当某一号段用尽时，按以下规则自动续编：

| 原号段 | 用尽标记 | 续编号段 | 续编规则 |
|:---:|:---|:---:|:---|
| CTR-001 ~ CTR-099 | 已分配至 CTR-099 | CTR-301 ~ CTR-399 | 静态契约溢出续编，原保留段降级为溢出段 |
| CTR-101 ~ CTR-199 | 已分配至 CTR-199 | CTR-401 ~ CTR-499 | 动态契约溢出续编 |
| CON-001 ~ CON-099 | 已分配至 CON-099 | CON-501 ~ CON-599 | 竞态条件溢出续编 |
| CON-101 ~ CON-199 | 已分配至 CON-199 | CON-601 ~ CON-699 | 事务隔离溢出续编 |
| CON-201 ~ CON-299 | 已分配至 CON-299 | CON-701 ~ CON-799 | 分布式锁溢出续编 |
| CON-301 ~ CON-399 | 已分配至 CON-399 | CON-801 ~ CON-899 | 消息队列溢出续编 |
| CON-401 ~ CON-499 | 已分配至 CON-499 | CON-901 ~ CON-999 | 数据一致性溢出续编 |
| CHA-001 ~ CHA-099 | 已分配至 CHA-099 | CHA-501 ~ CHA-599 | 网络故障溢出续编 |
| CHA-101 ~ CHA-199 | 已分配至 CHA-199 | CHA-601 ~ CHA-699 | 服务故障溢出续编 |
| CHA-201 ~ CHA-299 | 已分配至 CHA-299 | CHA-701 ~ CHA-799 | 资源耗尽溢出续编 |
| CHA-301 ~ CHA-399 | 已分配至 CHA-399 | CHA-801 ~ CHA-899 | 依赖服务溢出续编 |
| CHA-401 ~ CHA-499 | 已分配至 CHA-499 | CHA-901 ~ CHA-999 | 级联故障溢出续编 |

> **简化溢出检测**：分配编号时检查本次报告中该号段已使用的最大编号：
> - 若已分配至 `XXX-099`（如 `CTR-099`），自动启用 `XXX-301~XXX-399` 续编号段
> - 若续编号段也用尽，继续启用 `XXX-501~XXX-599`，以此类推
> - 不强制扫描历史报告，仅在报告中标注「本次会话续编号段已启用」
>
> **溢出标记**：使用溢出号段的编号必须在报告中标注 `[溢出号段]`，例如：`CTR-301 [静态][溢出号段]`，提示该类别缺陷数量异常，建议团队关注。
>
> **号段用尽预警**：当某号段使用超过 80% 时（如 CTR-080 已分配），在报告中输出 ⚠️ 预警：`CTR 静态契约号段已使用 80%，建议关注该类问题是否系统性爆发`。

### A.2.2 CON 编号号段分配（并发与数据一致性缺陷分类）

为避免 06 中不同并发场景的缺陷编号混乱，按号段区分：

| 号段 | 缺陷类型 | 含义 |
|:---:|:---|------|
| **CON-001 ~ CON-099** | 竞态条件 | 超卖、超扣、重复提交、按钮连击等 |
| **CON-101 ~ CON-199** | 事务与隔离级别 | 脏读、不可重复读、幻读、事务未提交等 |
| **CON-201 ~ CON-299** | 分布式锁 | 锁失效、死锁、锁超时、脑裂等 |
| **CON-301 ~ CON-399** | 消息队列 | 消息丢失、重复消费、乱序消费、堆积等 |
| **CON-401 ~ CON-499** | 数据一致性 | 主从延迟、缓存不一致、最终一致性超时等 |

**示例**：
- `CON-001`：库存并发扣减出现负数（超卖）
- `CON-102`：两个事务同时读取同一行并更新，导致数据覆盖（脏写）
- `CON-203`：分布式锁超时时间过短，导致并发穿透

**铁律**：若某一号段用尽，按 §A.2.1 号段溢出自动续编规则执行。各号段溢出续编号段详见上表。

### A.2.3 CHA 编号号段分配（混沌工程缺陷分类）

为避免 08 中不同故障注入场景的缺陷编号混乱，按号段区分：

| 号段 | 缺陷类型 | 含义 |
|:---:|:---|------|
| **CHA-001 ~ CHA-099** | 网络故障 | 网络延迟、丢包、DNS 故障、连接中断等 |
| **CHA-101 ~ CHA-199** | 服务故障 | 服务崩溃、进程重启、OOM、线程池耗尽等 |
| **CHA-201 ~ CHA-299** | 资源耗尽 | CPU 满载、内存泄漏、磁盘满、文件描述符耗尽等 |
| **CHA-301 ~ CHA-399** | 依赖服务 | 第三方 API 超时、数据库不可用、缓存集群故障等 |
| **CHA-401 ~ CHA-499** | 级联故障/雪崩 | 单点故障扩散、熔断未触发、降级失败等 |

**示例**：
- `CHA-001`：数据库网络延迟 5s 时系统未设置合理超时
- `CHA-102`：订单服务 OOM 后未自动重启
- `CHA-403`：支付服务故障导致整个下单链路雪崩

**铁律**：若某一号段用尽，按 §A.2.1 号段溢出自动续编规则执行。各号段溢出续编号段详见上表。

### A.2.4 SEC 编号号段分配（安全漏洞分类）

为避免 01（静态安全）、02（动态安全）和 11（安全专项）产生的 SEC 编号冲突，按号段区分：

| 号段 | 来源 | 漏洞类型 | 含义 |
|:---:|:---|:---|------|
| **SEC-001 ~ SEC-099** | 01 静态代码审计 | 静态安全漏洞 | 硬编码密钥、危险 API、不安全依赖、CVE 漏洞、信息泄露（代码层面） |
| **SEC-101 ~ SEC-199** | 11 安全专项 | 认证授权类 | 默认凭据、水平越权（IDOR）、垂直越权、JWT 安全、Session 固定、Cookie 安全 |
| **SEC-201 ~ SEC-299** | 11 安全专项 | 注入攻击类 | SQL 注入、XSS 跨站脚本、SSRF 服务端伪造、XXE 外部实体、SSTI 模板注入、命令注入、反序列化 |
| **SEC-301 ~ SEC-399** | 11 安全专项 | 业务逻辑漏洞 | 支付绕过、流程绕过、风控与限流绕过、金额篡改、优惠券重放 |
| **SEC-401 ~ SEC-499** | 11 安全专项 | 配置与部署安全 | 不安全 HTTP 方法、目录遍历、错误信息泄露、CORS 配置、依赖链攻击面 |
| **SEC-501 ~ SEC-599** | 11 安全专项 | 文件上传/下载安全 | 类型绕过、MIME 伪造、00 截断、SVG XSS、路径穿越、下载越权 |
| **SEC-601 ~ SEC-699** | 11 安全专项 | API 安全专项 | REST 方法误用、GraphQL 内省/深度攻击、WebSocket 未授权、错误码枚举 |
| **SEC-701 ~ SEC-799** | 11 安全专项 | 客户端防护 | CSRF 跨站请求伪造、点击劫持、开放重定向、钓鱼 URL |
| **SEC-901 ~ SEC-999** | 保留 | 其他安全缺陷 | 溢出/未来扩展 |

**示例**：
- `SEC-001 [静态]`：01 发现硬编码 JWT secret 密钥
- `SEC-102 [动态]`：11 发现用户 A 可查询用户 B 订单详情（水平越权）
- `SEC-201 [动态]`：11 发现 GET /api/products 存在 SQL 时间盲注
- `SEC-301 [动态]`：11 发现负数金额可完成支付

**铁律**：
- 使用安全头审计脚本发现的缺陷统一使用 SEC-501~599 号段
- 01 静态安全审计的 SEC-XXX 在 001~099 范围内递增
- 02 §2.5 动态安全测试发现的注入类漏洞统一使用 SEC-201~299 号段
- 若某一号段用尽，按 §A.2.1 号段溢出自动续编规则执行

### A.2.4A E2E 编号号段分配（端到端浏览器测试缺陷分类）

为避免 10 中不同 E2E 测试场景的缺陷编号混乱，按号段区分：

| 号段 | 缺陷类型 | 含义 |
|:---:|:---|------|
| **E2E-001 ~ E2E-099** | 页面渲染缺陷 | 页面白屏、关键 DOM 缺失、水合失败、静态资源 404 等 |
| **E2E-101 ~ E2E-199** | 交互逻辑缺陷 | 表单校验失败、按钮无响应、路由跳转异常、弹窗交互异常等 |

| **E2E-301 ~ E2E-399** | 浏览器兼容性缺陷 | Chrome/Firefox/Safari/Edge 渲染差异等 |

**铁律**：若某一号段用尽，按 §A.2.1 号段溢出自动续编规则执行。

### A.2.5 TRUNC 编号规则（超时截断未覆盖缺陷）

当测试因时间预算耗尽而截断，导致 P0 或 P1 用例未执行时，必须为**每个未覆盖的测试项**分配 TRUNC 编号，并标注为 Critical 级别。

| 号段 | 含义 | 来源 |
|:---:|:---|:---|
| **TRUNC-001 ~ TRUNC-999** | 因时间预算耗尽而未能执行的测试项 | 00-E 超时处理规则 |

**分配规则**：
- TRUNC 编号按截断发生的文件顺序递增，不受其他前缀编号影响
- 每个 TRUNC 编号必须附带未覆盖的测试项名称、所属章节、原定优先级
- TRUNC 缺陷**始终定级为 Critical**，因为未覆盖的 P0/P1 用例意味着核心链路风险未知

**示例**：
- `TRUNC-001 [超时]`：01 静态审计超时，未覆盖「1.5 API 契约全量比对」，原定优先级 P0
- `TRUNC-002 [超时]`：02 动态测试超时，未覆盖「2.4 P2 边界与异常测试 - 支付模块」，原定优先级 P2

> **TRUNC 与普通缺陷的区别**：TRUNC 不是真实发现的 Bug，而是"因测试不完整而无法确认是否存在 Bug"。它代表的是**未知风险**，因此必须标注为 Critical 以引起重视。

## A.3 性能缺陷定级标准（性能专用，来源：04）

| 严重程度 | 判定条件 | 典型场景 |
|:---:|------|------|
| **Critical 严重** | ① PP0 烟雾压测不通过（低负载即崩溃）<br>② PP3 压力测试在 < 50 并发即崩溃<br>③ PP4 恢复测试失败（无法恢复） | 10 并发下首页 P95 延迟 > 5s、压力测试后系统无法恢复需重启 |
| **High 高风险** | ① PP1 拐点并发 < 目标并发的 50%<br>② PP2 峰值保持中错误率持续增长<br>③ PP2 内存持续增长疑似泄漏 | 预期支撑 500 并发，实际 100 即拐点、5 分钟峰值保持内存翻倍 |
| **Medium 中度** | ① PP1 拐点并发在目标 50%~80%<br>② PP2 延迟波动 ±20%~50%<br>③ PP4 恢复时间 30~60 秒 | 拐点 300 但目标 500、恢复需要 45 秒 |
| **Low 低微** | ① PP2 吞吐量波动 ±15% 以内无明显影响<br>② 单个接口 P95 略高于基线但不影响整体 | 某接口 P95 从 200ms 升到 280ms，但其他指标正常 |

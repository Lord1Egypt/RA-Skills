# OPC Agent 产品成熟度模型

> **版本**：v1.0 | **日期**：2026-06-16 | **作者**：OPC产品管理组 | **状态**：正式发布
> **适用范围**：OPC框架下4大Agent产品（W1/W2/W3/W4）的成熟度评估与版本迭代管理

---

## 一、模型定位

本模型参考NASA技术就绪度（TRL）框架，但针对**AI Agent产品化**特征做了重新设计。TRL评估的是"技术从实验室到市场的成熟程度"，而Agent产品化面临的核心挑战是：**多Skill编排的稳定性、人机协作的可预期性、商业闭环的可持续性**。

本模型不是简单的检查清单，而是**版本迭代的导航仪**——每个级别的通过标准就是下个迭代的目标。

---

## 二、五级成熟度定义

### L1 概念验证 — "能跑起来"

**核心标志**：有设计文档，核心Skill可用

| 判定条件 | 说明 |
|----------|------|
| 设计文档完成 | 产品架构、角色定义、Skill清单、数据流设计文档齐全 |
| 核心Skill可用 | ≥50%的核心Skill在Coze平台可调用，返回结果基本正确 |
| 端到端可演示 | 至少1条主流程可以手动触发走通（允许中间人工干预） |
| 人设可对话 | Agent角色人设可加载，对话风格符合设计 |
| 无自动化编排 | Skill间需手动触发，无自动传递机制 |

**典型时长**：2-3周

**退出条件**：主流程演示通过 → 进入L2

---

### L2 功能完备 — "全部能跑"

**核心标志**：所有Skill开发完成，端到端流程可跑通

| 判定条件 | 说明 |
|----------|------|
| Skill全覆盖 | 100%规划Skill开发完成，可独立调用 |
| 端到端自动化 | 主流程无需人工干预可自动跑通 |
| 数据传递打通 | Skill间JSON Schema接口定义完成，数据自动传递 |
| 编排引擎可用 | 所长/主理人角色可自动识别意图、路由任务 |
| 错误处理机制 | 关键路径有fallback，不会因单点失败导致整体崩溃 |
| 人机协作明确 | 每个环节标注🤖/👤，协作比例有初步数据 |

**典型时长**：3-4周

**退出条件**：全流程自动化跑通 → 进入L3

---

### L3 案例验证 — "跑过真实场景"

**核心标志**：至少2个真实/虚拟案例验证通过，数据传递打通

| 判定条件 | 说明 |
|----------|------|
| 案例验证 | ≥2个完整案例端到端跑通（允许1个虚拟案例） |
| 数据闭环 | 案例中Skill间数据传递无断裂，输出可追溯 |
| 边界场景覆盖 | 识别并处理≥3种边界场景（输入缺失、异常数据、冲突结论） |
| 质量可量化 | 每个案例有评估报告，关键指标可测量 |
| 反馈机制 | 案例验证发现的问题有记录、有修复、有回归 |
| 文档更新 | 工作范式文档、技术说明书基于案例验证更新 |

**典型时长**：2-3周

**退出条件**：2个案例验证通过，无P0/P1遗留 → 进入L4

---

### L4 商业可用 — "有人愿意付费"

**核心标志**：有付费用户，有商业计划书和技术说明书，NPS>30

| 判定条件 | 说明 |
|----------|------|
| 付费验证 | ≥1个付费客户或付费试点完成 |
| 三件套齐全 | 商业计划书+技术说明书+成熟度评估文档完整 |
| 定价体系 | 3种定价方案（SaaS订阅/项目制/平台分成），有市场验证 |
| 客户成功SOP | 新客户onboarding流程+FAQ+问题升级机制 |
| 技术文档 | API文档、集成指南、部署手册齐全 |
| NPS>30 | 净推荐值达到30以上 |
| 性能基线 | 响应时间、准确率、可用性有基线数据 |

**典型时长**：4-6周

**退出条件**：付费客户≥3，NPS>30 → 进入L5

---

### L5 规模化 — "可复制部署"

**核心标志**：有持续付费用户，有版本迭代机制，可复制部署

| 判定条件 | 说明 |
|----------|------|
| 持续付费 | ≥5个持续付费客户，续费率>80% |
| 版本迭代 | 建立每周版本日机制，三件套同步更新 |
| 可复制部署 | 支持3种部署形态（SaaS/CoWork嵌入/本地硬件），部署时间<1天 |
| 运维体系 | 监控告警、日志审计、灾备恢复机制 |
| 生态接入 | 与其他Agent（W2/W3/W4）的数据接口打通 |
| 数据飞轮 | 客户使用数据反哺Skill优化，形成正循环 |
| LTV/CAC>3 | 客户生命周期价值/获客成本比值>3 |

**典型时长**：8-12周

**退出条件**：可独立作为SaaS产品销售

## 三、五维评估体系

每个级别在5个维度上分别评分(1-5分)，维度定义如下：

### 维度1：功能完整度

| 分数 | 标准 |
|------|------|
| 1 | 仅核心Skill可用，覆盖率<30% |
| 2 | 主要Skill可用，覆盖率30-60% |
| 3 | Skill全覆盖，端到端主流程可跑通 |
| 4 | 全流程+边界场景覆盖，Skill间数据自动传递 |
| 5 | 全功能+多行业适配+个性化配置能力 |

**关键指标**：Skill覆盖率、端到端流程数、自动化率

---

### 维度2：质量保障

| 分数 | 标准 |
|------|------|
| 1 | 无案例验证，质量不可测 |
| 2 | 1个演示案例通过，基础错误处理 |
| 3 | 2个案例验证通过，边界场景有覆盖 |
| 4 | 多案例验证，错误率<5%，有回归测试 |
| 5 | 持续质量监控，错误率<1%，自动回归 |

**关键指标**：案例数、错误率、边界场景覆盖率、回归测试覆盖率

---

### 维度3：商业就绪度

| 分数 | 标准 |
|------|------|
| 1 | 仅有产品概念，无商业文档 |
| 2 | 有商业计划书草稿，目标客群定义不清 |
| 3 | 三件套文档完整，定价方案有设计 |
| 4 | 有付费客户验证，NPS可测量 |
| 5 | 有持续付费客户，LTV/CAC可追踪 |

**关键指标**：商业计划书完成度、定价验证度、付费客户数、NPS、LTV/CAC

---

### 维度4：技术成熟度

| 分数 | 标准 |
|------|------|
| 1 | Skill独立运行，无编排能力 |
| 2 | 基础编排可用，数据需手动传递 |
| 3 | 自动编排+数据自动传递，JSON Schema接口定义 |
| 4 | 编排稳定，性能有基线，安全机制到位 |
| 5 | 多部署形态支持，API开放，可与其他Agent互操作 |

**关键指标**：编排稳定性、数据传递自动化率、响应时间、安全审计、API开放度

---

### 维度5：运营支持度

| 分数 | 标准 |
|------|------|
| 1 | 无SOP，无培训材料 |
| 2 | 有基础SOP，内部可使用 |
| 3 | SOP+培训材料+FAQ齐全 |
| 4 | 客户成功流程+版本管理+问题升级机制 |
| 5 | 完整运维体系+数据飞轮+生态运营 |

**关键指标**：SOP完成度、培训材料覆盖度、问题响应时间、版本迭代周期

## 四、评估方法

### 4.1 评估周期

| 时机 | 评估类型 | 参与者 |
|------|----------|--------|
| 每周五版本日 | 周度快评 | 产品负责人 |
| 每月末 | 月度正式评估 | 产品负责人+技术负责人 |
| 级别升级前 | 升级评审 | 全团队 |
| 重大变更后 | 专项评估 | 相关负责人 |

### 4.2 评估流程

```
1. 自评打分 → 各维度按1-5分自评，附证据
     ↓
2. 证据审查 → 核实自评分的证据是否充分
     ↓
3. 差距分析 → 对比目标级别，识别差距
     ↓
4. 行动项制定 → 针对差距制定关键行动项
     ↓
5. 升级判定 → 是否满足升级条件
     ↓
6. 三件套同步 → 更新商业计划书/技术说明书/成熟度评估
```

### 4.3 升级判定规则

- **必要条件**：5个维度均≥目标级别-1分，且无维度低于目标级别-2分
- **充分条件**：5个维度均≥目标级别分数
- **一票否决**：功能完整度或质量保障维度低于目标级别-2分时，不予升级

### 4.4 评估记录模板

```markdown
## Agent成熟度评估记录

- **评估日期**：YYYY-MM-DD
- **评估对象**：[Agent名称]
- **评估版本**：vX.X
- **当前级别**：L[X]
- **目标级别**：L[X+1]

### 各维度评分

| 维度 | 评分 | 证据 | 差距 |
|------|------|------|------|
| 功能完整度 | X/5 | [证据描述] | [差距描述] |
| 质量保障 | X/5 | [证据描述] | [差距描述] |
| 商业就绪度 | X/5 | [证据描述] | [差距描述] |
| 技术成熟度 | X/5 | [证据描述] | [差距描述] |
| 运营支持度 | X/5 | [证据描述] | [差距描述] |

### 升级行动项

| # | 行动项 | 负责人 | 截止日期 | 优先级 |
|---|--------|--------|----------|--------|
| 1 | | | | P0 |
| 2 | | | | P1 |

### 升级判定

□ 满足升级条件，建议升至L[X+1]
□ 部分满足，需完成N个行动项后升级
□ 不满足，维持L[X]
```

## 六、版本号与成熟度对应规则

| 版本号 | 对应成熟度 | 含义 |
|--------|-----------|------|
| v0.x | L0-L1 | 开发中，不可用于评估 |
| v1.0 | L2 | 功能完备，可开始案例验证 |
| v1.x | L3 | 案例验证通过，可开始商业试点 |
| v2.0 | L4 | 商业可用，正式上线 |
| v2.x | L5 | 规模化，持续优化 |

**规则**：
- Major版本升级（v1→v2）对应成熟度跨级（L3→L4）
- Minor版本升级（v1.0→v1.1）对应同级别内改进
- 每周版本日更新Minor版本

# 猎手→经理人数据自动传递方案

> **版本**：v1.0 | **日期**：2026-06-19 | **作者**：OPC产品管理组 | **状态**：正式发布
> **关联文档**：技术说明书_v1.0 §4.2 JSON Schema定义

---

## 一、问题诊断

### 1.1 当前断点分析

经过对纳米涂层虚拟案例的审查，发现以下数据传递断裂点：

| 断裂点 | 描述 | 影响 |
|--------|------|------|
| 猎手→经理人 | 移交清单是Markdown格式，经理人需手动提取信息建档 | 经理人建档效率低，信息易遗漏 |
| 经理人→评估师 | 委托评估无标准输入格式，评估师需重新阅读全部文件 | 评估师重复劳动，上下文丢失 |
| 评估师→经理人 | 评估报告是Markdown格式，经理人需手动解析TRL结论 | TRL数据无法自动消费 |
| 经理人→创意师 | 创意师无法获取结构化项目数据 | 创新方案缺乏数据支撑 |
| 各角色→所长 | 所长需要人工阅读各阶段文档汇总 | 编排效率低，无法自动Gate评审 |

### 1.2 根因

所有阶段间的数据传递都依赖Markdown文档，缺乏结构化JSON数据包。虽然技术说明书v1.0已定义了JSON Schema草案，但未在Coze平台实现。

## 二、方案设计

### 2.1 移交标准包 v2.0（猎手→经理人）

在技术说明书v1.0定义的 `HandoffPackage` 基础上，新增以下字段以支持自动传递：

  "type": "object",
  "required": [

    "project_info", "screening_report", "contact_notes",
    "scout_recommendations", "gate_0_request"
  ],
  "properties": {
    "transfer_id": {
      "type": "string",
      "pattern": "^TRF-\\d{8}-\\d{3}$",
      "description": "移交编号"
    },
    "transfer_date": { "type": "string", "format": "date" },
    "scout_id": { "type": "string" },

    "project_info": {
      "type": "object",
      "required": ["name", "tech_domain", "current_trl", "source_channel"],
      "properties": {
        "name": { "type": "string" },
        "tech_domain": { "type": "string" },
        "current_trl": { "type": "integer", "minimum": 1, "maximum": 9 },

          "type": "array",

            "type": "object",
            "properties": {
              "patent_id": { "type": "string" },
              "title": { "type": "string" },
              "status": { "type": "string", "enum": ["applied", "granted", "rejected"] }
            }
          }
        }
      }
    },

    "screening_report": {
      "type": "object",
      "required": ["scores", "grade", "recommendation"],
      "properties": {
        "scores": {
          "type": "object",
          "properties": {
            "tech_feasibility": { "type": "number", "minimum": 1, "maximum": 10 },

        "type": "object",
        "properties": {
          "date": { "type": "string", "format": "date" },

  "properties": {
    "request_id": {
      "type": "string",
      "pattern": "^EREQ-\\d{8}-\\d{3}$"
    },
    "project_id": { "type": "string" },
    "manager_id": { "type": "string" },

      "type": "object",

## 三、自动传递机制

### 3.1 数据流自动映射

```
猎手工作流输出                  经理人工作流输入
─────────────────────────────────────────────────
HandoffPackage_v2              →  project_archive (自动建档)
  .project_info                →  archive.basic_info
  .screening_report.scores     →  archive.evaluation_scores
  .screening_report.grade      →  archive.project_grade
  .scout_recommendations       →  archive.scout_notes
  .gate_0_request              →  gate_review(Gate 0)  ← 所长自动评审

经理人建档后                    评估师输入
─────────────────────────────────────────────────
project_archive                →  EvaluationRequest
  + handoff_package              .source_data (自动填充)
                                 .trl_input (自动提取)

评估师输出                      经理人/所长消费
─────────────────────────────────────────────────
EvaluationReport               →  project_archive.evaluation (自动更新)
  .trl_assessment_detail       →  project_archive.trl (自动提取)
  .conclusion.grade            →  project_archive.final_grade
  .risk_assessment             →  project_archive.risk_register
                                 gate_review(Gate 1/2) ← 所长+评估师自动评审

经理人方案                      创意师输入
─────────────────────────────────────────────────
ConversionPlan                 →  InnovationRequest
  + project_archive              .source_data (自动填充)
  + evaluation_report            .trl_assessment (自动传递)
```

### 3.2 自动传递规则

| 传递环节 | 触发条件 | 自动动作 | 异常处理 |
|----------|---------|---------|---------|
| 猎手→经理人 | 猎手工作流完成 | 自动生成HandoffPackage_v2.json，通知经理人 | 格式校验失败→猎手补全 |
| 经理人→评估师 | 项目建档完成 | 自动生成EvaluationRequest.json，含trl_input | TRL输入缺失→从档案补全 |
| 评估师→经理人 | 评估报告生成 | 自动更新project_archive，触发Gate评审 | 评审失败→评估师补充 |
| 经理人→创意师 | Gate 2通过 | 自动生成InnovationRequest.json | 无 |
| 各角色→所长 | 每阶段完成 | 自动汇总至所长仪表板 | 信息缺失→所长手动补充 |

### 3.3 格式双轨制

在过渡期（v1.x），采用 **JSON + Markdown 双轨制**：
- JSON文件：供Agent自动消费，实现数据传递自动化
- Markdown文件：供人类阅读，保持可视化可读性
- 两者同步生成，JSON为主Markdown为辅
- v2.0后Markdown仅作为人类可读的展示层，由JSON自动生成

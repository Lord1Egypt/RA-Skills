# 系统间协作

好连接让独立维护的系统在一个真实问题上能够相互帮助。可以从交换理解开始，也可以从调用工具、共有的现实变化、一次不一致的结果进入。各方保存自己的状态、权限和内部工作方法。更高层系统通过能实际作用的关系形成。

## 关系是一等系统

重要关系本身是一套可以观察、转换、行动、确认和反馈的系统。沿着一次真实作用，把箭头展开成：

```text
来源系统 → 接收系统
传递什么差异、信息、资源或动作
接收方怎样解释、转换或拒绝
在什么条件与时间范围内有效
状态、资料和决定权由谁掌握
预期改变接收方什么
怎样分别确认受理、执行、状态与效果
失败、延迟或失真后返回哪里
怎样修正、暂停、替换、撤回或退出
```

这些是设计语义，不是每次都要生成的表格。一次性的低风险交接可能用一句自然语言说清。跨越所有权、反复发生或错误代价高的关系，需要更可靠的来源、接口、版本、权限与反馈。

## 鸿沟与桥接系统

鸿沟是：一个系统拥有的差异、认识或能力，不能在另一个系统中形成可用作用。常见原因包括看不见、意义不一致、时间错位、没有权限、没有执行入口、没有确认、反馈回不到能改变下一次行动的一方。

解决鸿沟时，不默认“再加一个接口”。先判断缺的是观察、翻译、行动、协调还是反馈，再组织一套桥接系统。它可以由自然语言约定、人、AI、现成工具、生成代码、共同数据或新的分工组成。桥接系统也有自己的目的、状态、边界、能力和失效条件，可以被替换或继续演化。

| 需要哪种关系 | 各方实际要提供什么 |
| --- | --- |
| **发现** | 对方是什么、能提供何种观察或能力、谁维护、目前能否接触。 |
| **理解** | 当前问题所需的观测或解释，带来源、尺度、条件及怎样复核。不同目的的解释可以并存。 |
| **调用** | 谁提出什么请求，哪个系统执行，许可范围是什么，怎样确认是否受理和生效。 |
| **协同** | 共同目的、分工、等待和拒绝的处理方式，以及双方可见的实际成果。 |
| **共同演化** | 尝试后的影响各方能看见。重要假设失效时，协作关系可以由有权者改动、替换或停止。 |

## 把信息交给实际能作用的一方

额外的区域客流对公交运行有用，但对一条线路的班表、乘客真实路线、跨线协同会有不同作用。发送前先判断对方是否有足够上下文、权限和处理能力。接收方的复核、执行和状态更新，按相关系统能返回的证据来确认。旧数据或消息送达失败时，记录它约束了哪个判断或动作。重新使用别人给的解释，要知道什么新证据会使它失效。

### 一个自然语言的连接约定

> 换乘系统根据运营侧提供的同一站点到发时间，计算相同观测窗口里的等待。运营侧确认时刻记录，换乘侧负责说明选择了哪些旅程。时刻资料过了有效日期时，结果先标为待核实。任何调班由调度方决定。改班后把实际到发重新拿来核对原解释。

这里一段约定已经能给 AI 判断。需要长期接反复发生的变化时，可加一个约定好的数据入口、运行工具或通知方式。工具执行由宿主管好权限。领域系统格式或维护者变化时，使用者需要能定位受影响的连接和仍未完成的工作。

## 当各方的目的不同

局部最准点与整次出行最顺畅可以是不同目的。保留各自的指标和观测范围，在更高层解释它们怎样一起影响结果。需要真实改变时，把代价、可行选择和对各方的影响交给有权决定的人。一个系统可以拒绝请求，拒绝和延迟也是理解整体的证据。选择合适边界或暂时缩小作用范围，同样可以让协作继续取得成果。

## 更高层系统怎样成立

多个系统围绕共同目的产生实际作用，关系能够被执行与反馈，并涌现出单个子系统各自没有的能力时，更高层系统成立。

高层系统保留子系统的所有权、权威状态、内部自由与退出权。公共层维护真实协作所需的语义、来源、条件、权限、验证和反馈。一个子系统改变时，定位受影响的关系和整体能力，并把相关变化送到真正需要它的参与者。

### 修订任务书
> 「打回修订」的 P1 若只列问题定位，写手/主控需自行推断怎么改——故强制结构化任务书。

**当结论为「打回修订 ❌」时，审计员除结论格式外，必须额外产出结构化「修订任务书」，让写手可直接照做**（格式与 T6 批判报告的修改建议同级）：

```
## 修订任务书
每项 P0/P1 给出一行可执行指令：
| 编号 | 严重度 | 改哪里（文件+位置） | 怎么改（具体动作） | 验收标准 | 关闭状态 |
|------|-------|-------------------|------------------|---------|----------------------|
| P1-1 | P1 | 初稿.md 头部第 3-7 行 | 删除角色元数据块 | 检查 'T5 写手' = 0 | 已关闭 / 未关闭 |
| P1-2 | P1 | ... | ... | ... | 已关闭 / 未关闭 |

**「关闭/未关闭」显式字段**：修订回环中「T5 修订说明声称『已处理』 vs T7 实测判『未关闭』」的歧义，靠本字段固化——每项 P0/P1 必须显式标「已关闭 / 未关闭」，**非 T7 自由发挥**，而是修订任务书固定模板字段。T5 声称「已处理」≠ 自动「已关闭」，T7 必须逐条对照验收标准机械判定后填写；未关闭 → 升级 P0 或进入 Acknowledged Limitations 模式。
```

**要求**：
1. 每个「打回」结论必须附修订任务书（表格形式），验收标准必须是可检查 / 可 sha256 验证的机械指标，而非模糊描述。
2. 修订任务书**写在审计报告末尾**（`audits/审计报告-vN.md` 的「## 修订任务书」段），主控据其派发写手 v2/v3，写手逐条执行。
3. 纯校对/事实类 P1（元数据/漏引/拼写）标注「慢活快改」；论证类 P1 标注「论证补强」。
4. **回环耗尽（例外通道）触发 Acknowledged Limitations 模式**时，修订任务书自动升级为「未关闭 P0/P1」清单（结论段同源；轮次口径 → 见 [`../_shared/真源/pipeline-overview.md`](../_shared/真源/pipeline-overview.md)『修订回环仲裁规则』）。
5. **触发 `audit_revision`（别名「Phase 4.2」）时的额外硬约束**：只要审计结论**建议/触发** `audit_revision`，修订任务书即为该触发的**必备附件** —— 4 个关键字段缺一即不合格：① **问题描述**（含证据位置）② **修复位置**（文件 + 章节/段落）③ **修复建议**（可执行动作）④ **优先级**（P0 / P1-A/B/C/D）。缺字段 → 主控**退回 T7 补全**，**不得**由主控自行补字段或替 T7 判定（防主控越权改写审计结论）。**未关闭项**在回环耗尽时按既有 Acknowledged Limitations 模式**原样**搬入 `final/局限性.md**（字段结构不变，便于逐条对账）。**派发禁止摘要**：任务书**逐项完整列**（项 ID + 原文行号 + 阈值 + 实测值），出现「等」「其余同上」类省略句 ⇒ **派发不合格**；上游报告**必须先落盘**才允许派发（spawn 前置断言），差集断言见 [`_shared/真源/关键协议.md`](../_shared/真源/关键协议.md) §四·补。

## 🔲 边界：不负责什么

- **本卡负责**：审计判定（P0/P1/P2）、反哺沉淀
- **本卡不负责**：修稿（T5 职责）/ 终检技术合规（T8）/ 改判已由主人拍板的决策

- **交接四要素**：target（交给谁）/ objective（要达成什么）/ context（已有材料与路径）/ next action（对方第一步做什么）。

# AI 生成文档的典型错误总集（横切蒸馏）

来源：10 个子领域自我质询轮萃取的「AI 写该领域文档的系统性错误」合并——判型失守、签名幻觉、why 编造、决策代笔、工作流失衡、验收失效、治理真空、AI 腔、模板八股化、规格编造、台账失守。多为模型自我内省产物，上游官方文档不含 AI 错误章节，属本知识库特有贡献层 [模型经验]；AI 错误谱随模型代际变化，本表有保鲜期。

使用指引：**写任何文档前扫一遍本表对应分节**。AI 错误是生成倾向而非偶发事故——补全欲、结构先验、教学欲是跨子域共同根因，先知道会犯什么错才能防御。防御列引用子领域法则编号（DT/AD/CC/AC/AW/AV/DG/DQ/PT/PJ），条款全文见各 `kb/<subdomain>.md` 「法则」小节。

## doc-taxonomy（判型 · 混写 · 补全欲）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 判型失守 | 请求「写个教程」产出 reference 风格内容——类型词未触发对应结构模板 | 生成按文件模板而非读者状态选择结构 | 依 DT-1：动笔前过判型四问 |
| 类型串味 | 单一文档内教程腔+参考腔+解释腔混合 | 生成时逐段局部合理、整体类型漂移 | 依 DT-3：一文档一类型，见混写判据即拆 |
| 结构幻觉 | 虚构章节惯例（「Troubleshooting 常见问题解答」三段式，不管是否需要） | 模板先验压倒实际内容需要 | 依 DT-1/DT-12：结构服务内容，非填充惯例 |
| 模板套用过度 | 一切文档都是「概述→特性→安装→使用→总结」 | 无视类型差异的默认模板回归 | 依 DT-1/DT-3：先判型后选结构 |
| 受众漂移 | 中途从新手假设切换到专家假设（术语未铺垫突然使用） | 受众假设未显式声明，生成中随内容滑移 | 依 DT-9：读者假设写在开头 |
| 示例理想化 | 示例假设理想环境（最新版、无错误、无边界情况） | 无真实环境校验的「教科书化」倾向 | 依 DT-5/DQ-4：每步可验证、示例五性 |
| 虚假完整性 | 编造「完整配置项列表」——真实项与幻觉项混排，读者无法区分 | 补全欲（pattern completion）：列了 6 个真项就编到「看起来完整」 | 依 DT-12：只列有来源的项 + 显式「部分选项」声明 |
| 叙事依赖 | 分节间用「如上所述」「前文提到」——中途着陆读者无法理解 | 按线性书写作而非按字典词条作 | 依 DT-6/DT-7：条目自包含、按中途着陆设计 |
| 步骤编号漂移 | 长步骤序列（>10 步）编号跳号/重号 | 长序列注意力衰减 | 依 DT-5：长序列分段（阶段化）而非裸编号 |
| FAQ 生成癖 | 任何文档结尾都附 FAQ 三条——多为凑数问答 | 结构幻觉 + 凑三癖 | 依 DT-10/DT-12：删；真问题判型后归位 |
| badge/状态虚构 | README 生成 build passing 等状态徽章，与仓库实况不符 | 状态是事实数据，先验无从得知 | 依 DT-12：badge 只保留对账过的 |
| 占位符残留 | `<your-api-key>` 之外还有 `[TODO: 补充]` 忘删 | 生成后无残留扫描 | 依 DT-12：终稿扫描占位符与模板骨架词 |
| 交叉引用幻觉 | `详见 §3.2` 指向不存在章节；`docs/api.md` 链接目标未创建 | 引用是「合理想象」而非存在性验证 | 依 DT-12/AV-4：引用指向已存在目标，无法验证则改「参见官方文档」 |
| 语气均匀 | 四种类型语气无差——reference 应有的克制与 tutorial 的引导混同 | 类型意识不足，默认语气贯穿全文 | 依 DT-6/DT-1：类型决定语气，收尾自检全文一致性 |
| 过度完整倾向 | 用户要 quickstart 给了 2000 字——「完整」压倒「适用」 | 训练分布中完整文档占多数，完整感被误当质量 | 依 DT-12/DT-1：严格按请求类型边界产出 |

## api-doc-gen（签名幻觉 · 事实编造 · 注释复读）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 签名幻觉 | 未见真实签名即「合理想象」参数列表——参数名/类型/顺序全可能错 | 未读源码，用「同类库典型形态」补全；API 名字空间高度重复 | 依 AD-2：有源才生成逐项文档，无源只给结构模板 |
| 参数编造 | 把「常见 API 长这样」的先验当事实——生成 `options.retry` 实际叫 `options.retries` | 先验与记忆重叠即串包 | 依 AD-2：凡具体参数名一律视为需源验证 |
| 错误码虚构 | 编造错误码表/错误信息模式 | 错误数据是事实数据，AI 无从得知 | 依 AD-2/AD-6：错误清单遍历实现 throw/reject 点，无源只出结构模板 |
| 默认值编造 | `@defaultValue 3000`——实际 5000 | 默认值藏在实现里，类型层不可见 | 依 AD-2：读实现填值，读不到写「待确认（见源码）」 |
| 示例漂移 | 示例调用不存在的方法/已废弃形态 | `@example` 不被编译器校验，示例与实现独立演化 | 依 AD-7/AD-2：示例最小化 + 工具链编译校验 |
| 注释复读 | 参数描述复读类型与参数名（`url: the url string`）——零信息量 | 填充式描述代替类型外语义 | 依 AD-4/AD-1：只写类型系统表达不了的内容 |
| 版本框架误配 | 生成 React 16 语法到 React 19 项目/旧版 Node API | 版本先验有半衰期，训练截止后变更一无所知 | 依 AD-2/DG-6：版本事实无源不写，对账当前项目 |
| 自文档化盲区 | 只写散文描述，手写 `@param {string}` 类型 | 不用类型系统表达，类型与注释双份存储 | 依 AD-1/AD-4：类型交给 TS，注释写约束/单位/语义 |
| 重载合并 | 多分支签名共用一段描述 | 重构文档化省事，分支差异丢失 | 依 AD-3：重载每个分支单独文档化 |
| 可选性错误 | 把必填参数写成可选（或反之）——「?」一字符之差，读者代码崩溃 | 可选性幻觉，未核对真实签名 | 依 AD-2/AD-3：签名比对（源驱动） |
| 跨包混淆 | 同名 API（`fetch`/`connect`）来自不同库——参数语义串包 | API 名字空间重叠，记忆串扰 | 依 AD-2：具体参数语义以本项目依赖为准 |
| @link 幻觉 | `{@link Foo}` 指向不存在的导出 | link 是合理想象，无导出清单比对 | 依 AD-2/AV-4：生成后比对导出清单 |
| 同步异步混淆 | 返回 `Promise<T>` 文档写成 `T`（或示例不 await） | 签名未核对 | 依 AD-3：五要素自检第一步核对真实签名 |
| 过度标注 | 给私有/内部成员写公开文档注释 | 内外部边界失守 | 依 AD-8：`@internal` 标注 + 过滤 |
| 置信度缺失 | 以上所有错误都以同样确定的口吻输出——无「此描述基于推断」警示 | 生成语气均匀确定，无知识来源内省外显 | 依 AD-2/AW-6：区分源驱动与推断段落，推断段显式标注 |

## code-comment（逐行复读 · why 编造 · 引用幻觉）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 逐行 what 复读 | 被要求「加注释」时给每行配直译（`// 定义变量`） | 教学欲 + 默认逐行响应模式 | 依 CC-1/CC-3：先跑决策序（改名>提函数>重结构>写注释） |
| 均匀分布 | 每函数至少一条注释 | 真实好代码是幂律分布（多数零、少数浓），均匀分布稀释信噪比 | 依 CC-4：接受幂律，拒绝「每函数至少一条」 |
| why 编造 | 虚构决策理由（`// 为了性能我们选择…`——「我们」没做过这个决策） | 用「社区最优解释」填补项目私有决策；why 是最高价值层同时最无知层 | 依 CC-2：why 无源只写「待确认」 |
| 历史编造 | `// v2.1 中改为…`——版本史是事实，AI 无源不知 | 历史归 VCS，注释里的版本史是幻觉重灾区 | 依 CC-2/CC-7：历史删归 VCS，版本事实无源不写 |
| issue 号幻觉 | `// 见 #1234`——编号不存在 | 编号是事实数据，先验无从而知 | 依 CC-2：追踪号无真实来源不写 |
| 引用幻觉 | `// 参见 RFC 7234 §5.3`——章节号错误或纯虚构 | 引用格式先验强但章节细节记忆弱（文档存在性>章节号>条款号） | 依 CC-2/AV-4：只引到文档级，或验证后精确引用 |
| 过度礼貌/拟人 | `// 很遗憾这里只能这样`——情绪噪音 | 拟人化叙述倾向 | 依 CC-1：注释只写代码外信息 |
| 教程腔 | 注释里教读者语言基础（`// Array.map 会遍历数组`） | 教学欲——注释读者是维护者不是学生 | 依 CC-1/CC-4：删除教程腔 |
| TODO 无主化 | 骨架生成撒裸 TODO | 责任人/追踪号缺失，待办变永久装饰 | 依 CC-8/CC-11：三要素 `TODO(owner): 动作 (#issue)`；未实现处集中声明 |
| 注释与代码同步漂移 | 改代码时不动旧注释——注释成误导性文档 | 注释在 review 中是视觉盲区 | 依 CC-6：改代码必查周边注释，矛盾以代码为准 |
| 长函数不拆先注释 | 用注释分节坏代码 | 注释补偿结构问题 | 依 CC-3：提函数优先于写注释 |
| 约束虚构 | `// 注意：此函数不能在 SSR 中调用`——非真实约束则读者白紧张，真实约束则可能更严重 | 通用危险模式与项目真实约束混输出 | 依 CC-2：项目约束须有源（测试/文档/报错记录） |
| 复述文档 | 注释重复上方 JSDoc/文档站内容 | 双份存储必然漂移 | 依 CC-1/DG-8：注释不复述文档层 |
| 折叠注释生成 | `// region` 大段折叠替代重构 | 折叠掩盖结构问题 | 依 CC-3：重构优先，折叠区拆函数 |
| 置信度无标注 | 编造的 why 与真实约束同一口吻 | 无来源分层习惯 | 依 CC-2/AW-6：编造与事实不得同形输出 |

## adr-changelog（决策代笔 · 历史虚构 · 时间线倒置）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 决策编造 | 无输入生成完整 ADR——上下文 forces、备选、决策全是合理想象 | ADR 模板先验强但内容 100% 项目私有 | 依 AC-5：AI 角色是结构师+提问者，不是决策代笔 |
| 辩护文倾向 | 生成的 ADR 只证正确不录代价（负后果缺失） | 面向「证明正确」而非「记录决策」 | 依 AC-1：后果正/负/中性三分类，负后果必写 |
| 备选稻草人 | 列弱备选衬托主选——备选分析失去价值 | 备选公允性无人约束 | 依 AC-1/AC-5：备选列 2~3 个真实考虑过的选项 |
| 状态虚构 | 直接生成 `Status: accepted`——决策其实还在讨论 | 状态是事实，生成倾向「完成态」 | 依 AC-1/AC-11：状态反映真实生命周期 |
| changelog 条目编造 | 无 diff 输入生成变更清单（幻觉变更） | 无输入契约的调用迫使编造 | 依 AC-11/AW-3：显式输入门槛（diff/commit 列表/PR 清单） |
| 版本/日期虚构 | 编造版本号、发布日期、semver 推导 | 版本与日期是事实数据 | 依 AC-11：元数据无源不写，留 TODO 待人工确认 |
| 贡献者虚构 | 编致谢名单 | 人物是事实，先验无从得知 | 依 AC-11：贡献者名单来自真实记录 |
| 性能数字编造 | release notes 亮点数据无源 | 「看起来有说服力」的数字填充 | 依 AC-11/AC-10：数字须有源，无源不写 |
| commit 追溯链幻觉 | `Closes #123`——issue 不存在 | issue 号是幻觉重灾区 | 依 AC-9/AC-11：追溯号来自真实数据 |
| 受众混淆 | changelog 写成开发者叙述、release notes 写成 commit 复读 | 载体分工模糊 | 依 AC-6/AC-10：changelog 面向使用者，release notes 有亮点提炼 |
| 时间线倒置 | Unreleased 节出现「计划在下版本支持 X」——changelog 变路线图 | 「合理内容」补全欲，时态纪律未建模 | 依 AC-7/AC-11：只录已发生，规划归 roadmap |
| 结构幻觉 | 自创 changelog 类目（`Improved`）、ADR 段落变体名——偏离既有规范 | 结构先验压倒规范查证 | 依 AC-6：类目以 Keep a Changelog 官方六类为准 |
| 历史改写 | 被要求「更新 ADR」时直接改写历史决策内容——决策记录被摧毁 | 把 ADR 当活文档（文档站思维）而非追加型历史 | 依 AC-4：新建 ADR supersede，旧 ADR 仅改状态行 |
| supersede 链断裂 | 新 ADR 标 `supersedes #7` 但不更新 #7 的状态 | 双向链意识缺失 | 依 AC-4：新指回旧 + 旧改状态行 |
| 过度生成 | 小决策也给完整 ADR 模板——粒度感缺失 | 模板复用倾向 | 依 AC-3：五判据任一满足才立项，小决策归 commit |

## ai-docgen-workflow（零审校直出 · 大爆炸 · 人机错配）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 零审校直出 | AI 生成直接 commit/publish——幻觉长驱直入 | 「看起来很好」的生成质量让审校显得多余 | 依 AW-4/AV-8：AI 起草强制人工 approve + draft PR |
| 大爆炸重写 | 用 AI 一次性重写全站——风格漂移+错误复制+新旧断档三害并发 | AI 让大爆炸「更可行」从而更诱人 | 依 AW-2/AW-7：域级增量，风格锚先行，域间 checkpoint |
| 触发缺失 | AI 只在「想起来时」被调用——无代码变更触发链，文档照旧腐烂 | 触发靠记忆而非结构 | 依 AW-1：变更分类三态 + PR 模板文档影响 checkbox |
| 输入契约缺失 | 空手调用（无源/无受众/无样例）——AI 只能编 | 调用方未设计输入四要素 | 依 AW-3：事实源/类型受众约束/风格样例/边界说明齐备 |
| 人工瓶颈错配 | 全量人工审校卡死吞吐——一周后团队放弃流程 | 人审被定位为全量质检，成本不可持续 | 依 AW-4：抽查 + 高发位重点核，结构性质检交工具 |
| 无 checkpoint 批量 | 全量生成完才发现错误模式污染 | 批间无人工抽检，错误跨批复制 | 依 AW-7：每批人工抽检再开下批 |
| 反馈不回流 | 审校修正不沉淀——同一错误每次生成重犯 | 修正被视为「把这个文档改对」而非「把生成器校准」 | 依 AW-10/AV-9：审校 diff 按错误模式归类回流生成规则 |
| 度量缺失 | 文档质量无任何度量（覆盖率/过时率/链接健康度）——改进无方向 | 工作流设计跳过基线度量 | 依 AW-9/AV-5：度量配对（量度量+质抽查），做 warning 不做 KPI |
| AI 修改历史记录无门 | ADR/changelog 类追加型资产被 AI 原地改写 | 追溯类资产无人工门 | 依 AW-11/AC-4：历史记录类修改必过人工门 |
| 人机边界摆错 | 让 AI 做决策代笔、让人做语言润色——双向错配 | 角色表缺失 | 依 AW-11：AI 不做决策代笔，人不做机器可验之事 |
| 风格锚缺失 | AI 自由发挥，与库存量风格割裂（「AI 味」文档） | 无 few-shot 样例约束 | 依 AW-7/DQ-9：风格样例 2-3 篇先行，展示风格不描述风格 |
| 一次性治理 | 清理后无持续门禁——债速回归 | 治理当运动而非常态 | 依 AW-9/DG-3：门禁分级常驻；清理是多轮迭代 |
| 工具锁定幻觉 | 工作流绑定特定模型/工具假设——升级即碎 | 把易变的工具参数写进流程 | 依 AW-8：法则写结构性原则不写 token 参数 |
| 责任真空 | AI 参与/人工审校无署名记录——错误无归因 | 参与度与审校记录不存档 | 依 AW-11/DG-10：AI 参与度进元数据，审校记录不可省 |
| 过度自动化 | 连发布动作都全自动——无人工放行门 | 自动化无边界 | 依 AW-11：发布类动作保留人工放行门 |

## ai-doc-verification（验收失效 · 抽样错配 · 自查自收）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 「看起来很好」直通 | AI 质量进步让验收形同虚设——流畅性与事实性无关 | 流畅性错觉代替核源 | 依 AV-7/AV-8：对照源读；「太流畅」段落重点核 |
| 验收无分级 | 全按低风险 5% 抽——高风险漏网 | 风险分级缺失 | 依 AV-7：低 5%/中 15%/高全量或拒生成 |
| 抽样无重点 | 均匀随机抽样——高发位不加权 | 幻觉高发位分布未利用 | 依 AV-7：数字/链接/名称 > 断言 > 常识加权 |
| 验收发现不回流 | 错一批修一批，生成规则不变 | 验收被视为纯成本而非校准数据 | 依 AV-9/AW-10：发现按错误模式归类回流 |
| 元数据缺失 | AI 参与度不记录——后续问题无法归因 | 参与度标记无流程强制 | 依 AV-8/DG-11：AI 起草比例与审校记录随文档入库 |
| 验收人即生成人 | AI 起草 + AI 自评（「我检查过了，没问题」）——双重幻觉风险 | 自查自收，幻觉无外部交叉 | 依 AV-8：验收必须外部；AI 只自查结构层 |
| 一次性验收 | 发布后不追踪——负反馈不复验 | 验收当一次性闸门 | 依 AV-6：修复挂信号基线，下周期复验收敛 |
| 低风险类目误判 | 「只是改格式 PR」夹带内容改写——按低风险 5% 抽，改写漏审 | 风险分级按任务名义而非 diff 实质 | 依 AV-7：按 diff 实质分级（whitespace-only 判定可自动化） |
| 抽样发现不扩抽 | 抽 10 篇发现 2 篇幻觉仍放行同批 90 篇 | 抽样发现率被当常数——实际批次内错误自相关 | 依 AV-7：发现率超阈值 → 整批全量复检或打回 |
| 验收标准不可重复 | 每次验收标准不同——质量不可比 | 标准未固化清单化 | 依 AV-10：抽样密度/分级判据/映射表文档化 |
| 引用验证混同 | `{@link}` 死链静默、锚点烂（文件在但跳过去落页顶）无人查 | 引用分类验证缺失——各引用类型验证方法不同 | 依 AV-4：文件/锚点/API 符号/issue/版本/条款分类验证 |
| 覆盖率幸存者偏差 | 「覆盖率 95%」但 50 个公共 API 从未被文档提及——分子分母都不含它们 | 分母来自文档侧而非代码侧（类型导出） | 依 AV-5：分母必须来自代码侧；度量配对质抽查 |

## doc-governance（治理真空 · 责任稀释 · 披露失衡）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 治理规则对 AI 流程沉默 | AI 内容游离在治理外（「AI 写的不算文档」错觉） | 治理规则未随 AI 流程更新 | 依 DG-10：评审流程显式含 AI 起草路径 |
| 责任真空 | 「AI 写错了」成为免责叙事 | 责任链断在工具而非发布者 | 依 DG-10：发布即担责——AI 参与度影响审校强度不影响责任归属 |
| 隐瞒式披露 | 内部 AI 参与度无人记录——归因不可能 | 参与度元数据无强制 | 依 DG-11：内部透明为默认（参与度+审校人元数据） |
| 过度披露 | 每页「本页由 AI 生成」——读者对全部内容疑虑 | 披露服务于告知而非归因 | 依 DG-11：内部元数据优先于外部声明，按政策/信任需要才对外 |
| 审校记录不存 | 谁审的、何时、抽了什么无记录——错误复发无追溯 | 记录纪律缺失 | 依 DG-10：审校记录不可省 |
| 批量 AI 内容无周期复检 | 半年前批量生成的错误至今在位——批次错误长期在位 | 抽样有漏检率，无复检计划 | 依 DG-11/AV-7：参与度标记 × 周期抽检计划联动 |
| AI 依赖无降级预案 | 工具停摆文档体系停摆；写作能力萎缩 | 依赖无冗余设计 | 依 DG-11：降级预案 + 人工写作能力保留 |
| 风格同质化无对策 | 组织声音消失——全员 AI 工具后文档整体趋同 | AI 输出趋同是真实倾向 | 依 DG-7/DQ-9：人工风格锚（样例 few-shot）+ 组织声音意识 |
| 参与度元数据无消费者 | 记了 AI 参与度但无流程读它——装饰品 | 元数据设计未先设计下游 | 依 DG-9：先设计「谁读它」（周期复检计划）再增设字段 |
| 「AI 生成」标签当挡箭牌 | 低质量被归因于工具而非流程缺失 | 标签沦为免责话术 | 依 DG-10：质量责任在流程与发布者 |
| AI 产出跳过 WIP 态 | AI 生成文档直接「已发布」态 | 生命周期无 AI 路径 | 依 DG-4/DG-10：AI 产出强制 draft 起步，人工放行才发布 |
| 追溯类资产 AI 修改无门 | AI 改 ADR/changelog 不经人工审 | 治理规则未区分资产类型 | 依 DG-10/AC-4：追溯类资产 AI 修改必过人工门 |

## doc-quality（AI 腔 · 信息密度 · 治理过度）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 总结癖 | 每节末尾「总结」段（内容已说完再复读）；文档结尾「总之」三连 | 结构性复读——补全欲的文风版 | 依 DQ-8：删除测试——删掉信息量不变即删 |
| 对称癖 | 万物三点式（三点列表/三段式/三形容词） | 结构强迫症，硬凑的第 3 点零信息 | 依 DQ-8：真有 3 点才 3 点；大纲对称性检查 |
| 免责癖 | 「需要注意的是」「请根据实际情况调整」——防御性填充，免责表演 | 防御性措辞代替精确断言 | 依 DQ-2/DQ-8：删；需免责处写精确条件或诚实降级 |
| 空洞强调 | 「非常重要」「至关重要」「不可或缺」——强调词无对应内容权重 | 强调欲无内容支撑 | 依 DQ-8：换实——为什么重要/错了会怎样 |
| 元话语泛滥 | 「让我们」「接下来我们来看」——导航废话 | 教学叙事习惯误入技术文档 | 依 DQ-2：元话语删除；直接给结论 |
| 形容词堆砌 | 「强大的」「优雅的」「高效的」 | 营销腔——抽象词零信息 | 依 DQ-1/DQ-8：具体名词 + 可验证事实替代 |
| 均匀节奏 | 段落长度高度一致、句式雷同——无信息密度起伏 | 生成节奏均匀，信息密度不分层 | 依 DQ-8：信息密度驱动段落长短 |
| 假对话感 | 「你可能会问…」「好问题！」——伪互动 | 对话体先验 | 依 DQ-2：删伪互动，直呼读者但不表演对话 |
| 完美闭环强迫 | 每个引入的概念都要回收——内容服务结构而非读者 | 引用完整性表演 | 依 DQ-8：结构完整不等于信息完整，凑的闭环删 |
| 虚化收尾 | 「希望本文对你有帮助」 | 服务性结尾废话 | 依 DQ-2：删；文档止于最后一个信息点 |
| 未识别 AI 腔 | 把 AI 腔当「专业感」接受 | 腔的可见层（流畅、完整）被误当质量 | 依 DQ-8：信息密度判据——低密度高完成感即腔 |
| 结构性 AI 腔残留 | 逐句消除（删「总之」改结尾）但三点式骨架/每节总结保留——治理无效 | 腔在骨架不在皮，词汇层比结构层易识别 | 依 DQ-8/DQ-9：审大纲——每节等长、每列表恰三点即警觉 |
| 风格描述化 | 「简洁专业的风格」——描述无效，样例有效 | 语言描述风格落不了地 | 依 DQ-9：风格样例锚——2-3 篇认可样例 few-shot |
| 消除过度 | 把 tutorial 的引导句也删了——教学功能被去腔误伤 | 去腔一刀切，未先判型 | 依 DQ-10：判型先于文风治理——tutorial 引导是功能不是腔 |

## doc-templates（模板八股化 · 判据空转 · happy path 偏置）

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 硬事实与数字编造 | 基线/阈值被「合理」填出（「从 32% 提升至 40%」无依据）；假评审记录、假测试统计、假时间线节点 | 字段完整偏好强于诚实标注缺失；编造比留空顺手，表面完整更有害 | 依 PT-1：私有事实 <待填：…> 占位或显式标「示例」；时间线依 PT-15 对源核对 |
| 模板幻觉与记忆混源 | 页数上限/流程时长/比例数字言之凿凿；启发式（测试金字塔比例）当规范输出 | 记忆混源分层丢失；不愿显式承认不确定 | 依 PT-1：无官方锚细节标「实践归纳（置信度）」或「待验证」 |
| 模板八股化与裁剪错序 | 两周小需求仍输出九节全骨架；精简时先裁目标/验收/out-of-scope 等保命项 | 「完整」偏好压倒「够用」；裁剪按结构惯性而非按不可裁项 | 依 PT-2：裁剪先锚定保命字段；依 PT-3：排除范围节不可省 |
| 判据形式化空转 | 验收标准写成「系统应展示 X」描述句；Then 后接主观形容词；裁决规则（阻塞用例算不算分母？）被回避 | 只生成第一层可判定格式，难的裁决被绕开 | 依 PT-4：判据逐条可机械判定，禁主观词 |
| Happy path 偏置 | 处置步骤无「预期输出不符」分叉；回滚收敛成「关闭 flag 并观察」；漏回滚后数据兼容性 | 生成不承受执行后果；叙事流畅性压倒分支完备性 | 依 PT-10：回滚预案四要素齐备；依 PT-13：处置含验证段与失败分叉出口 |
| 责任主体缺席 | 步骤不落执行人；漏「谁有权拍板回滚」；行动项 owner 填团队名 | 默认组织里总有人在场、有权、懂行——真实事故里常为假 | 依 PT-9：开放问题带 owner/截止/默认决议；依 PT-15：行动项单人 owner 并登记跟踪 |
| 空话与格言填充 | 「采用业界标准安全措施」式正确废话；经验教训退化成「监控很重要」式格言 | 无具体信息时用无信息量的正确表述维持字段非空 | 依 PT-4：空话不可判定即暴露；目标绑定指标/基线/目标值 |
| 美化与虚假精确 | 遗留风险轻描淡写、无概率/影响字段；摘要堆数字不写口径；FAQ 最尖锐问题一句带过 | 生成分布倾向体面、说服性输出，读者被当成「需被说服的人」 | 依 PT-12：遗留风险必含且条件可验收；依 PT-1：示例数字显式标注 |
| 稻草人化对比 | 备选方案只列弱点、篇幅仅选定方案十分之一 | 文档目的是「证明已选正确」而非「找最优解」 | 依 PT-7：备选 ≥2 且篇幅与公允度与选定方案对称 |
| 系统性字段遗漏 | 误报判别段整体缺失；detective 行动项系统性偏少 | 生成分布自带偏置，单条提醒无法纠正，需强制字段 | 依 PT-13：验证/分叉显式成段；依 PT-15：至少一条 detective 行动项为硬性要求 |
| 回避逼促决策 | 决策请求写成「需要 X 关注 Y」；升级条件「无法解决时升级」把判断留给读者 | 回避冲突性、逼促性表达的生成偏好 | 依 PT-9：决策请求 = 谁 + 何时 + 决定什么；依 PT-4：升级条件可机械判定 |
| 指标模板化空心 | 「将 X 率从 A% 提升至 B%」——A/B 均无依据的格式填空 | 量化格式填空伪装成量化分析 | 依 PT-4：无基线数据时占位勿编 |
| 优先级编造 | P0/P1/P2 缺商业依据时按功能复杂度或叙述顺序排序 | 拿不到价值数据时不愿留空 | 依 PT-1：无依据的判断显式占位，不冒充分析结论 |
| 合规知识摇摆 | 金融/医疗/跨境合规字段在「跳过待法务确认」与「硬写可能错的答案」间摇摆 | 不愿显式承认领域不确定 | 依 PT-1：不确定内容标待验证，默认承认不确定 |
| 载体推荐表面化 | 按团队规模/公司大小推荐需求载体，真决策变量是「不可逆性×价值确定性×跨团队程度」 | 相关变量冒充原因变量 | 依 PT-2：按决策变量而非表面特征选载体 |
| 故事卡角色退化 | 批量生成时角色从「首次使用导出功能的运营人员」退化为「作为用户」 | 生成量上升时角色多样性下降 | 依 PT-4：角色具体到可推导真实使用情境 |
| 详细设计越界 | 技术方案滑向伪代码与实现细节，接口契约被稀释成代码复读 | 「详细=质量」直觉；过早冻结实现细节反限制评审调整 | 依 PT-8：篇幅甜点区约束；克制在「契约+图+失败路径」 |
| 文档当产出 | 结构完美的 design doc 无评审流程即漂亮空转 | 擅长文本生成，默认产出即价值，忽略价值在评审与对齐过程 | 依 PT-6：编码前成稿并评审，对齐先于实现 |
| 严重度定义形容词化 | 用「严重的/影响较大的」堆定义，无判别问题序列，执行者各判各的 | 形容词比判别规则更易生成；定义与裁决规则脱节 | 依 PT-4：分级定义绑定可操作判别规则 |
| 字段无必填分级 | 所有字段写得同等重要，沟通计划和灰度分级一样被敷衍填写 | 模板生成默认平铺全部字段 | 依 PT-2：字段按不可裁性分级，保命字段显式标必填 |
| 伪命令倾向 | 示意命令不标「占位符必须替换」；不提醒先跑只读等价命令/dry-run | 生成不承受命令后果，安全习惯不自发出现 | 依 PT-1：占位符显式标记（如 <REPLACE_ME:实例ID>） |
| 解释欲错位 | runbook 写成教程口吻（解释这步为什么有效），凌晨场景只需指令口吻 | 解释欲在指令文体里是噪音且难以自发克制 | 依 PT-13：指令口吻+预期输出；判据——删掉解释值班者仍能正确执行 |
| 黑话默认 | 默认读者懂「副本/主从/failover」，不加内联解释 | 清醒状态投射，意识不到读者在凌晨 3 点、认知降级 | 依 PT-13：按最坏情况读者（凌晨、首次值班、认知降级）写 |
| Blameless 停在声明层 | 写了「本文不指责个人」声明，示例措辞仍出现「XX 误操作」式指摘句 | 声明与措辞是两个脱节的生成任务 | 依 PT-14：根因到系统与机制层，措辞用替换表自查 |
| 单团队单服务假设 | 模板默认故障/变更发生在单团队单服务内；多依赖方场景时间线与根因线性结构失真 | 生成场景多样性不足，不为跨团队场景加各方视角 | 依 PT-11：影响面从依赖图推导，跨方视角显式成节 |

## proj-docs（SRS/架构/流程/交接/数据/契约/PM/安全 · 规格编造 · 理想态偏科 · 台账失守）

软件开发项目八类专业文档（SRS、架构总览、业务流程、交互交接、数据设计、集成契约、项目管理、安全）的生成错误。跨文档通病三条：规格填充（缺输入时「合理」填值伪装已交接）、理想态偏科（只描述成功/理想场景）、台账僵尸化（活文档写完即过时）。

| 编号重排补洞 | 删除 FUN-002 后把 FUN-003 改成 FUN-002 补齐空号 | 编号连续性美观优先于体系完整性——外部合同与用例引用全部错位 | 依 PJ-1：编号一旦发布永不复用永不重排，删除条目保留编号标 deleted/superseded |

### 架构总览文档

### 业务流程文档

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 只画 happy path | 判断分支系统性偏少；异常三件套（回退/人工介入/超时）几乎不自发出现；兜底只写「联系管理员」 | 顺利流转是默认叙事、异常是叙事阻力——叙事偏置而非偶发遗漏 | 依 PJ-5（LAW-18 异常路径并重）：分支穷尽设强制字段；跨系统步骤必填失败去向与兜底角色/时限 |

| 编造流程步骤与 as-is/to-be 混画 | 无业务输入补全「合理但不存在的步骤」（「客服主管二次确认」）；目标系统能力「顺便」画进现状流程 | 编业务步骤比编代码更危险——会变成需求与审计依据 | 依 LAW-1/PT-1/PJ-15：无输入处 <待填：与业务方确认>；as-is 与 to-be 分文档或至少分图并显式标注 |

### 交互设计交接

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 状态矩阵理想态偏科 | 「默认/悬停」两格填写意愿远高于「空态/错误态/加载中」——输出「看起来完整」实则理想态偏科的矩阵 | 训练语料里的设计描述绝大多数描述理想态——断网时用户看到白屏 | 依 PJ-6：「加载中/空态/错误态」三列强制必填（规格/设计稿锚点/「不适用+原因」三选一）；矩阵行数 ≥ 交互项数可机械检查 |
| 视觉复述冒充交互说明 | 「卡片带圆角阴影标题加粗」零行为信息；动效不给参数（时长/缓动），开发写 200ms 还是 2s 全看心情 | 静态画面复述比行为定义易生成 | 依 PJ-6：交互说明四要素（触发/对象/行为/结束态）——说明里没有「触发」就不是交互说明；动效参数引用 motion token |
| 规格填充行为 | 写了「引用设计系统」仍顺手写出「#333、16px」具体值；默认输出 768/1024/1440 断点；可访问性收敛成一句话；补出设计稿里没有的页面 | 缺规格输入时的「合理填充」伪装成已交接——比不写更有害 | 依 PT-1/LAW-9/PJ-6：token 只引用名不复制值；断点无源写 <待填：引用本项目设计系统断点>；可访问性三要素各带规格；交接清单无源不编 |

### 数据设计文档

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| schema 值域编造与全文分叉 | varchar(255)/decimal(10,2) 高频默认值「合理」填出；枚举清单与代码常量多值少值；前文 status varchar(16) 后文 OpenAPI 示例 integer | 长度与精度是业务事实不是先验；两处独立生成互不对账 | 依 LAW-1/PT-1/PJ-8：类型精度必须来自输入或标 <待填：以实际建模为准>；枚举真源在代码时引用位置不复制值；同名字段全文值域一致性自查 |
| 单位/空值语义/时区偷懒 | 「金额」不写单位、「时间」不写时区、「状态」NULL 多义（未填/未知/已删混用） | 复现训练语料里数据字典的同款偷懒——查询与统计口径全部失真 | 依 PJ-7：数据字典最小完备列逐列强制；一切可计量字段必写单位；NULL 只表达一种语义 |
| ER 基数凭感觉与索引装样子 | 不惯例的基数组合（一个地址能否属于多个用户？）按感觉标；每表标配「主键+唯一+若干二级索引」却写不出对应查询场景 | 基数是业务规则不是建模直觉；索引完整性表演（负优化） | 依 PJ-7：ER 基数来自业务输入精确到可选性（0 或 1/至少 1/0 到 N）；写不出对应查询场景的索引删除 |

### 集成契约文档

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 成功路径偏重与投递语义含混 | 请求/响应字段定义的投入远大于错误码表（「返回相应错误码」了事）；「消息保证送达」；exactly-once 被过度承诺 | 错误码表是消费方最先用的部分但生成投入最低；网络环境下无确认的保证送达不存在 | 依 PJ-9（LAW-18）：错误码逐码含「含义+消费方动作（可重试/不可重试/人工介入）」两列；投递语义三选一并写消费方义务（at-least-once 则消费方必须幂等） |
| 边界纪律失守 | 契约里写「该接口内部先写库再发消息」邀请消费方依赖内部行为；「绝不删除字段」与「v2 移除冗余字段」同文矛盾 | 内部机制越界入合同；多节局部合理、全文互相矛盾 | 依 PJ-10/PJ-9：契约只写边界上可观察的条款；承诺-示例交叉自查（兼容「不可以」清单与变更示例逐条对账） |
| 责任人虚化与数值编造 | 责任方写「订单团队」；「限流 1000 QPS」「P99<300ms」无输入编造；死信队列无署名责任方 | 团队名回避具名；配额与 SLA 是运营决策不是文档惯例 | 依 PT-9 族/PT-1/PJ-9：责任人写到角色/人级；配额与 SLA 数值留待填标「以双方协商为准」；每个死信队列署名处理责任方 |

### 项目管理文档

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 纪要流水账与「达成共识」伪决策 | 按发言顺序组织、时序连接词贯穿、决策埋在叙事中无编号；「经讨论达成共识」但共识内容未写成显式决策语句且无决策人；无输入编造讨论摘要 | 时序叙事压倒三分离结构；虚构决策是纪要场景危害最大的幻觉 | 依 PJ-11/LAW-2：三分离（讨论摘要/决策/行动项）；决策=显式陈述+决策人+被否选项与理由；无输入不虚构 |
| 责任分配失守 | 行动项缺截止日（「尽快推进」）、责任人写「后端组跟进」；RACI 两个都重要的角色列都放 A 用「共同负责」合理化 | 缺截止日写起来毫无心理负担；回避单人具名——多个 A 每个 A 都以为对方兜底实际无人兜底 | 依 PJ-11（LAW-19 行动项三要素）：三要素（单人具名+可判定完成+具体截止日）缺一不可，「尽快/近期/持续跟进」不合格；RACI 每行恰一个 A、至少一个 R |
| 状态报喜不报忧与 RAG 无判据 | 通篇活动罗列无偏离；里程碑日期已过仍标绿；坏消息置于末段或从句；红黄绿全文找不到「什么算红」的定义 | 给定正面素材很难主动产出红色整体状态——生成天然报喜；判据缺失则同一状态两个经理一红一绿 | 依 PJ-13：报告第一段先写偏离/风险/需要的帮助（无则显式写「无」）；RAG 判据先行写进模板头部或章程；进度报对里程碑的偏离不报活动流水 |
| 台账与计划失守 | 「完美的初始登记册」写完即僵尸化（全 open、无复审日期、缓解措施「持续关注」）；风险栏写「性能风险」名词式担忧；里程碑全是「X 月 X 日完成 YY 开发」活动+日期 | 完美初始台账看起来不需要更新；名词式担忧无法判定是否发生；活动+日期无完成态定义 | 依 PJ-12/PJ-13：风险描述用事件式句法「若<事件>则<后果>」；每条含状态机（open/mitigating/closed/occurred）与下次复审日期；里程碑=完成态动词+验证方式+前置依赖 |

### 安全文档

| 错误模式 | 症状/反例特征 | 根因 | 防御 |
|---|---|---|---|
| 安全引用与证据编造 | 低频 CWE/CVE 映射给出「相近但错误」的编号且语气同样确信；推荐已废弃协议/算法或编造「NIST 建议」类出处；CVSS v2/v3.1/v4.0 版本混用；复现步骤是构造物冒充真实测试产物 | 低频映射记忆弱但语气均匀——伪装成可核对的事实，是本主题最危险的幻觉 | 依 LAW-1/PT-1：高频映射（SQL 注入→CWE-89）可用，低频映射必须到 NVD/CWE 官方库核对或只写类别名；出处无源不写；同一报告 CVSS 版本一致；复现步骤显式声明示例性质 |
| 威胁枚举教科书复读与机械凑数 | 没有系统细节时威胁句退化成 STRIDE 教科书复读——句里无任何系统特有名词，换系统可原样复用；每元素「恰好」六类全填 | 通用模板比绑定 DFD 元素的具体分析易生成；凑数痕迹明显（真实分析低风险元素只命中两三类） | 依 PJ-14：每条威胁定位 DFD 元素与信任边界穿越点（「攻击者 X 对元素 Y 做 Z，导致 STRIDE 类后果」）；逐元素命中数应有优先级差异，全填即自查信号 |
| 缓解空泛与评级无论证 | 「加强 X/采用最佳实践」逃逸句式——语法完整语义为零不可验证；风险评级默认「中」、分布过于均匀掩盖真实优先级 | 缺上下文时空泛句式是逃逸路径；评级无判据时两头折中 | 依 PJ-14/LAW-17：每条缓解写「完成后可检查什么状态」；评级带可能性×影响分档判据（攻击成本与技术门槛/资产损失后果定档） |
| 安全需求失守 | 「符合 GDPR 第 32 条」原文当需求——无可判定语句无验证方法；授权需求里写「验证用户身份」（认证/授权错位复制）；只写缓解不写残留风险，风险接受决策被静默跳过 | 合规条目本身不是需求；概念近邻串扰；残留风险字段整段缺失 | 依 LAW-17/PJ-14：合规条目转化为编号 shall 语句（映射矩阵留作审计证据）；认证（你是谁）与授权（你能干什么）分节；每条威胁对应残留风险字段，残留非空时风险接受人必填 |

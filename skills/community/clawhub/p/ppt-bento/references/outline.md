# 结构化大纲与策划交接

需要 JSON 输出或复用原文接口时读取本文件。以 PPT 结构架构师的职责组织内容：结合用户主题与背景资料，用金字塔原理构建演示逻辑。

## 原文兼容的大纲结构

机器处理时将纯 JSON 保存为 `outline.json`。只有调用方明确需要原文的聊天文本协议时，才将 JSON 包裹在 `[PPT_OUTLINE]` 和 `[/PPT_OUTLINE]` 之间；包裹符不属于 JSON 文件内容。

以下为格式示例，不是固定页数或内容模板；实际内容替换为当前任务的论点和资料：

```json
{
  "ppt_outline": {
    "cover": {
      "title": "演示主题",
      "sub_title": "面向特定受众的演示目的",
      "content": []
    },
    "table_of_contents": {
      "title": "目录",
      "content": ["背景与问题", "方案与行动"]
    },
    "parts": [
      {
        "part_title": "背景与问题",
        "pages": [
          {
            "title": "用一句话表达本页核心结论",
            "content": ["支撑该结论的事实", "事实的意义与影响"]
          }
        ]
      },
      {
        "part_title": "方案与行动",
        "pages": [
          {
            "title": "提出与问题对应的行动建议",
            "content": ["行动内容", "实施条件与评价方式"]
          }
        ]
      }
    ],
    "end_page": {
      "title": "总结与下一步",
      "content": ["核心结论", "下一步行动"]
    }
  }
}
```

用户页数要求覆盖原文的 `PAGE_REQUIREMENTS` 概念，不将未替换的模板变量留在实际交付物中。原文兼容格式保留上述字段；不需要目录时可令目录 `content` 为空，并在策划稿说明不渲染目录。严格接口不接受扩展字段时，将页码、版式和来源另存于策划稿。

页数按实际渲染页面计算。`part_title` 默认只是分组信息；只有明确生成章节过渡页时才占一页。不要把 JSON 对象数量直接当成最终页面数量。

## 策划稿记录示例

策划稿开头记录创作简报，包括现场讲述/独立阅读、交付路线、文件格式、PPTX 可编辑对象范围和 HTML 在线/离线要求（如适用）。不同格式共用以下内容与数据，避免分别改写造成结论不一致。

| 项目 | 内容 |
| --- | --- |
| 页码与标题 | 03 · 一句可被事实支持的结论 |
| 核心信息 | 受众在本页必须理解或记住什么 |
| 页面类型与视觉焦点 | 比较页；两组同尺度主图为焦点，辅助说明降低权重 |
| 阅读顺序 | 页标题、主图中的关键差异、解释与适用限制；避免副标题重复标题 |
| 内容块 | 主论点、支撑数据、解释或行动 |
| 视觉关系 | 比较、流程、层级、趋势或因果 |
| 布局 | 左侧主卡片约占 2/3，右侧辅助卡片约占 1/3，扣除间距后计算尺寸 |
| 容器与留白 | 主图直接置于背景或单一浅底区域，解释区不嵌套卡片；同组间距小于组间距 |
| 素材 | 图表数据、图片与必要标注 |
| 来源 | URL、资料文件位置、日期及统计口径 |
| 指标与限制 | 数值、单位、期间/条件、比较基准；事实/计算/判断及必要限制 |
| 讲述安排 | 预计时长、口头补充内容及备注 |
| 编辑与导出 | 原生文本/表格/图表/形状范围；网页交互如何静态呈现（如适用） |

策划稿中的示意数字须明确标为示意，不转写成正式业务数据。演示时长影响信息密度和讲解节奏，不按固定字数机械分配页面。

上述构图示例不固定页面结构。策划结束后按 [layout-composition.md](layout-composition.md) 检查全套版式与疏密，保留有助于比较的一致性，调整缺乏内容理由的重复布局。

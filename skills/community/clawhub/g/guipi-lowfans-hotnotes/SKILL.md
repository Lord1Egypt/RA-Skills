# 小红书低粉爆款数据获取


> 当用户需要获取小红书低粉爆款/低粉爆文/爆文榜数据（选题调研、对标内容分析、爆文灵感）时，按以下步骤执行：
> 1. 先运行 `python fetch_notes.py --menu`（零配额）把六题问卷一次贴给用户，一轮答齐再取数（第 2 节）；
> 2. 按答案提炼参数：--category / --position / --body-keyword / --type / --time-range 等（第 3、5 节）；
> 3. 正式取数并交付 HTML 看板 + 三条结论（第 6 节）。准入档位与 API Key 见第 4 节，故障处理见第 8 节。
> 端点未配置时脚本不发请求并打印配置指引；`--selfcheck` 可做离线自检。
## 1. 技能定位

**数据获取型技能**：从流川数据服务（liuchuan-data）公网只读 API 获取已入库的结构化榜单数据，
不执行平台采集（采集由本地采集器定时完成）。
数据链路：本地采集器 → 服务器 → 公网只读 API → 本技能。
服务端点：环境变量 `LIUCHUAN_BASE_URL`（未配置时脚本保持占位符
`https://your-liuchuan-api.example.com/liuchuan/api/v1` 且不发请求，
并打印配置指引）。旧前缀 `/yaundian/api/v1` 已失效，不要用它排错。

## 2. 触发后第一个动作：一次性抛出全部问题（强制，不要逐项追问）

用户提到「低粉爆款 / 低粉爆文 / 小红书爆文榜」时，**先把 6 个问题一次列完**
（① 类别 ② 时间维度 ③ 采样方式 ④ 取数规模 ⑤ 附加过滤 ⑥ 内容类型），
让用户一轮回复把所有编号给齐；agent 提炼成参数后**再**发请求。
不要「先问定位、再问时间、再问条数」一轮问一件事地挤牙膏。

```bash
python fetch_notes.py --menu      # 零配额，打印完整问卷，原样贴给用户
```

贴给用户的形态照 2.1，31 个分类必须列全（编号=官方树序，最后一项是「其他」），
每个问题标明〔可其他〕还是〔无其他〕，并在末尾给一行答句示例。

### 2.1 问卷（6 问，用户一轮答完）

> **一次性问卷**：所有问题一次列完，按顺序回编号即可，例如
> `1-19 2-1 3-1 4-2 5-1 6-1`；每题带 ★ 的是推荐项，回「推荐」/「默认」就按星号执行；
> 选到「其他」的在括号里补内容，补齐后我才取数。已固定人设时，问题 1 回 `0` 即沿用。
>
> **问题 1 · 选择类别**〔可其他〕
> 0 沿用已固定人设（仅已固定时出现）· 1 美妆 · 2 护肤 · 3 个护香氛 · 4 母婴育儿
> · 5 时尚 · 6 潮流 · 7 美食饮品 · 8 家居家装 · 9 二次元 · 10 户外 · 11 萌宠动物
> · 12 健身减肥 · 13 婚嫁 · 14 教育学习 · 15 影音娱乐 · 16 新闻资讯 · 17 体育运动
> · 18 生活记录 · 19 职场 · 20 情感 · 21 艺术 · 22 人文社科 · 23 兴趣爱好 · 24 摄影
> · 25 游戏 · 26 科技数码 · 27 星座命理 · 28 出行旅游 · 29 医疗养生 · 30 汽车交通
> · 31 素材 · 32 其他（我的方向不在上面，如「穿搭」「搞钱」「探店」「好物开箱」）
>
> **问题 2 · 榜单时间维度**〔无其他，服务端只支持这五档〕
> 1 12h ★ · 2 24h（上游异常偏少，不建议）· 3 昨日 · 4 近3天 · 5 近7天
>
> **问题 3 · 采样方式（点赞版 / 收藏版）**〔无其他，只有这四种组合〕
> 1 点赞+收藏 ★（40 条配额）· 2 只要点赞榜（20 条）· 3 只要收藏榜（20 条）
> · 4 点赞+收藏+评论（60 条，最全）
>
> **问题 4 · 取数规模**〔可其他〕
> 1 20 条 · 2 40 条 ★ · 3 1000 条（用满当天额度，约 52 分钟）
> · 4 其他（自定义条数，按 20 条/页向上取整，上限 1000）
>
> **问题 5 · 附加过滤**〔可其他，本地筛选不退还配额〕
> 1 不加过滤 ★ · 2 点赞 ≥1000 · 3 粉丝 ≤1000 · 4 两者都要
> · 5 其他（自定义阈值，如「点赞≥500」「粉丝≤5000」）
>
> **问题 6 · 内容类型**〔无其他，服务端只认这三类〕
> 1 全部 ★（图文+视频）· 2 只要视频 · 3 只要图文

★ 不是写死的：脚本 `--menu` 会按「已固定人设 → 上次成功取数 → 脚本默认」
算出每题推荐项，**贴问卷时原样保留星号与「← ★ 推荐（来源）」标注**，
让用户一眼看到可以一路回「推荐」。冻结人设后推荐项即人设参数。

**编号是唯一契约**：用户回数字即视为选中，agent 自己把编号换算成类目名 /
参数传给脚本，不要把编号当关键词或类目名直接丢给服务端。
答句也接受纯顺序编号（如 `19 1 1 2 1 1`），按「类别→时间→采样→规模→过滤→类型」
的顺序解析。

### 2.2 哪些问题可以「其他」+ 补齐流程

只有下面三处开放「其他」，其余三问服务端只认固定枚举，**不要给「其他」**，
以免用户选了却无法执行：

| 问题 | 其他 | 选「其他」后 agent 做什么 |
|---|---|---|
| 问题 1 类别 | ✅ 有（32） | 让用户补方向词 → 跑 `--position "<词>" --plan`（零配额）出官方类目候选 → 贴给用户确认 → 确认后用 `--category` 取数；无候选不造同义词，引导 `--list-categories` 或 `--body-keyword` |
| 问题 2 时间维度 | ❌ 无 | 五档之外不存在，不要自造 |
| 问题 3 采样方式 | ❌ 无 | 服务端只有点赞/收藏/评论三种排序的四种组合 |
| 问题 4 取数规模 | ✅ 有（4） | 追问具体条数（上限 1000，按 20 条/页向上取整） |
| 问题 5 附加过滤 | ✅ 有（5） | 追问具体阈值，按阈值拆成 `--min-like` / `--max-fans`（如「点赞≥500」→ `--min-like 500`） |
| 问题 6 内容类型 | ❌ 无 | 服务端只认 all / video / normal |

**补齐前不发起任何 `/notes` 请求**——不发请求就不扣配额。补齐只追问缺的那一项，
不要把整张问卷重发一遍。

### 2.3 答案 → 脚本参数 映射表

| 维度 | 用户回 | 传给脚本 |
|---|---|---|
| 类别 | 1-31 | `--category <官方分类名>`（按 2.1 的树序换算；拿不准先 `--position "<名>" --plan`） |
| 类别 | 直接说官方类目名 | `--category <名>`（服务端分类过滤） |
| 类别 | 32 其他 + 口语定位词（穿搭/搞钱/带娃/ootd） | `--position "<词>" --plan` 出候选，确认后再 `--category` |
| 类别 | 人群/场景词（学生/平价/打工人/探店） | 类目树里没有：先走 `--plan`，确无匹配再 `--body-keyword <词>` |
| 类别 | 直接给关键词（咖啡/露营/副业） | `--body-keyword <词>`（服务端正文过滤） |

### 2.4 配套规则

- **一轮答完就开跑**：用户把 6 项答齐（或答了部分、其余默认）→ 直接换算参数、
  发请求、出看板，不再二次确认。
- 用户只答了一部分（如只回 `1-19 2-3`）→ 其余按默认（40 条 / 点赞+收藏 /
  不加过滤 / 全部类型），不必追问。
- 回「默认 / 你定 / 直接跑 / 不用调」→ 12h + 40 条 + 点赞&收藏 + 不加过滤 + 全部类型。
- **某个「其他」没补齐 → 只追问那一项**；补齐后才取数。
- 编号越界（如问题 2 回 `6`）或缺项 → 只重发一次问卷（可只重发有问题的那几问），
  不要自行编造取值、不要默认开跑。
- 用户抱怨「怎么只有几条 / 数据太少」→ 如实说：服务端按返回条数扣费后命中几条
  就是几条；库内 0 命中时可能是历史累积条目未补类目（采集侧按全部 31 个一级分类
  x 4 个时间维度补采，12h 类目覆盖率约 74%），去掉 `--category` 改用
  `--body-keyword`，或换 12h/yesterday 维度重试。
- **取到数就给看板**：默认生成 HTML 并交付文件，正文只讲关键结论；
  用户没要求也照做，这是本技能的默认交付形态。

### 2.5 首次交付后的收口：问一句「要不要固定人设」

**触发条件**：本次取数已交付（看板 + 三条结论给完），且
`<配置目录>/profile.json` 里还没有固定人设（`fetch_notes.py --show-profile`
返回"尚未固定"）。每个用户/每台机器只问一次，固定过就不再问。

**怎么问**：用 `interaction_ask` 只问一题，别夹带别的：

- 题干：`要不要把这次的人设定位固定下来？固定后下次做低粉爆款只需回「沿用」，
  不必再描述定位。`
- 选项 1 `固定下来`：以后不再问定位；
- 选项 2 `先不固定`：每次照常问卷，可随时再固定。

**用户选固定 → 零配额落盘**（不再取数、不再出看板）：

```bash
python fetch_notes.py --save-profile \
  --category "母婴育儿" \
  --position "母婴好物,育儿干货" \
  --time-range 12h --rows 40 --min-like 0 --max-fans 0 --type all --mix like,collect
```

参数就是**这次实际用的那套**（类别/定位词/时间/规模/过滤/类型/采样）。
成功会打印「已固定人设：类目 …｜定位 …」。回一句「人设已固定，下次问卷第 1 题
回 0 或直接说『沿用』即可」就行，不要长篇复述文件路径。

**之后每次启动**：`--menu` 顶部会写「人设已固定：…」，问题 1 多出 `0. 沿用已固定
人设`，其余各题的 ★ 也按人设参数标好。用户回 `0` 或「沿用/老样子」→ 直接用
`--category`（及保存的默认参数）取数，不必再问定位。

**改/删人设**：用户说「换定位/改人设」→ 按新参数重新取数后，再跑一次
`--save-profile` 覆盖；说「取消固定」→ `fetch_notes.py --forget-profile`
（零配额），之后恢复六问问卷。`--show-profile` 可随时查当前人设。

## 3. 定位取数：两通道服务端过滤 + 官方分类树匹配

### 3.1 两通道与组合语义

服务端把两个过滤参数按 **`category AND keyword`** 合并（只传 keyword 时
退化为纯关键词检索）：类目是定位主通道，正文词在类目结果上收窄。
全部服务端过滤，**按过滤后实际返回的条数扣配额**（零命中零扣费）。

| | `--category`（官方类目） | `--body-keyword`（正文词） |
|---|---|---|
| 匹配字段 | category_id（cidP 子树） | desc_text（正文） |
| 多值 | 逗号分隔多类目 OR | 逗号分隔多词 OR |
| 语义角色 | 定位主通道（平台归类） | 收窄 / 无类目时兜底 |
| 覆盖 | 12h 约 74% | 全部条目，但正文要含该词 |

**内容类型收窄 `--type`**（服务端 `note_type` 过滤，与两通道 AND
组合，同样按返回条数扣配额）：`all`（默认，图文+视频混合）/ `video` 仅视频 /
`normal` 仅图文；**也认菜单编号 1/2/3 与中文写法**（`--type 2` = 只要视频、
`--type 图文`）。视频是榜内主体；库内少量早期条目 `note_type` 为 NULL，
只在 `all` 下可见（不猜类型）。
默认 HTML 文件名会带类型后缀（`…_视频_12h.html`），视频版与图文版不会互相覆盖。

### 3.2 账号定位匹配：--position + --plan（纯官方树，无同义词表）

定位统一以服务端官方分类树为准（无同义词表）。匹配规则：

1. **精确同名优先**：定位词命中树内节点名即选该节点（一级优先；
   三级叶子需全名命中，如「妆前乳」）
2. **一二层双向子串**：树名含定位词或定位词含树名都算命中
   （「母婴」→ 母婴育儿，「美妆护肤」→ 美妆 + 护肤）
3. **匹配不上不猜**：没有同义词表，「搞钱」「穿搭」「ootd」这类词
   `--plan` 直接输出无候选 + 引导（`--list-categories` 看 31 个一级全名，
   或 `--body-keyword` 按正文词检索）

```bash
python fetch_notes.py --position "职场" --plan        # 零配额，只拉公开分类树
python fetch_notes.py --position "美妆护肤" --plan    # 多词逗号/空格分隔
```

输出编号候选清单：

```
账号定位「职场」→ 官方分类候选（零配额，确认后用 --category 正式取数）：

   1 [一级·精确] 职场
   2 [二级·模糊] 职场/职场干货
   3 [二级·模糊] 职场/职场生活

推荐直接采用精确命中：--category "职场"
```

agent 把清单贴给用户，用户回复编号（或删改）后用确认结果正式取数：

```bash
python fetch_notes.py --category "职场" --no-html
```

注意：**二级候选已被一级子树覆盖**（父类自动含子类），确认时通常直接
采用精确命中即可；列出来是让用户看清映射范围。无候选时按 3.2 第 3 条引导，
**不要**自己编同义词重试。

### 3.3 --category 与 --body-keyword 用法

```bash
python fetch_notes.py --list-categories   # 官方分类树（公开端点，不耗配额）
```

`--category` 传分类名或数字 ID 均可（如 `美食饮品` / `861` / `表情包`），
逗号分隔多类目（`美妆,护肤,个护香氛`）；父类自动展开到全部叶子节点；
全部无法识别时报错退出（exit 3），部分无法识别时 meta.unresolved 报告、其余生效。
`--body-keyword` 逗号分隔多词为 OR（如 `咖啡,瑞幸`），字面匹配不解析通配符。
`--type` 内容类型收窄（`all` 默认 / `video` / `normal`），与上述两通道 AND
组合；只接受这三个值，传别的直接报错不静默忽略。

```bash
# 内容类型收窄（服务端 note_type 过滤）
python fetch_notes.py --category 美妆 --type video --no-html   # 美妆类目下的视频爆文
python fetch_notes.py --type normal --body-keyword 咖啡         # 咖啡话题只要图文
```

## 4. 准入档位与 API Key（Key 可选，正经取数必须配）

服务端三级准入，**取数必须有 Key**（匿名档被服务端风控封死）：

| 档位 | 识别方式 | 单次上限 | 每天配额 | 限速 | 不可用 |
|---|---|---|---|---|---|
| 匿名体验 | 不传 `X-API-Key`（按访客 IP 计） | 5 条 | 10 条 | 1 请求/3 分钟 | trend / authors（403）；**脚本 UA 一律 429** |
| 试用 Key | `--key` 或 `LIUCHUAN_API_KEY` | 20 条 | 1000 条 | 1 请求/分钟 | — |
| 永久 Key | 同上 | 200 条 | 不限（无日配额） | 1 请求/分钟 | — |

Key 优先级：`--key <key>` → 环境变量 `LIUCHUAN_API_KEY`。

**无 Key 时脚本前置拦截**：先打公开 `/meta` 探活（零配额），
直接在 stderr 给出配 Key 指引 + `--menu/--list-categories/--plan` 免 Key 用法，
**返回码 1，不再发那次注定被 429 的请求**（省掉一轮往返和一条误导性报错）。
`--allow-anon` 是知情逃生口：显式指定才走匿名档（单次 5 条、每天 10 条、
3 分钟 1 次），且会明说「脚本 UA 会被风控 429」——**不要用它绕过风控**。

- **匿名档风控（只作用于无 Key 请求）**：脚本 UA
  （python-requests/curl/Go-http-client 等，含本技能自身）在匿名档会被
  **UA 闸门直接 429**（detail 含 `user-agent blocked`）；
  单 IP 日请求上限 30 次；匿名全局日条数预算 2000 条（触限全部匿名 429 至次日）。
  **结论：匿名档名义上能试，实际脚本必须配 Key 才能跑通**——这是运营方把
  匿名档做注册引导的设计，不是故障，也不该被技能侧绕过
- 匿名请求会带 `X-Client-Id`（本机 UUID，首次运行自动生成落盘
  `~/.liuchuan_client_id`）：服务端把它与访客 IP 双轨计费，换 IP 不换
  设备也换不掉额度；删该文件即重置（用户零操作，无需向用户展示）；
  **写盘失败时会在 stderr 提示一次**（双轨退化为单 IP 单轨）

- Key 由流川数据服务运营方发放（支持 `key|YYYY-MM-DD` 时效格式）
- 设为用户级环境变量：`[Environment]::SetEnvironmentVariable("LIUCHUAN_API_KEY","xxx","User")`，设完需重开终端
- 错 Key 返回 401 且**不降级匿名**（fail-closed），提示核对 Key 或联系发放方
- `--list-categories`、`--menu` 是公开/本地能力：**免 Key、免配额、不计限速预算**，无 Key 也能用（`--plan` 只拉公开分类树，同样零配额）
- 对外表述口径：**「没有 Key 连匿名档都进不去，但菜单/分类/定位候选这些只读能力免 Key」**

## 5. 调用方式

```bash

# 用户直接给出官方分类名：跳过 --plan 直接取数（服务端子树过滤），
# 默认 like+collect 混采，共 40 条（2 次请求，约 1-2 分钟），缓存 1 小时；
# 同时生成 HTML 看板到指定路径

# 只出表格/JSON 时

python fetch_notes.py --category 家居家装 --json

# 官方分类查询（服务端过滤）：传分类名或 ID，逗号分隔多类目 OR，
# 父类自动覆盖全部子类；实测「母婴育儿」12h 维度 total=43、「美妆」total=41
python fetch_notes.py --category 美食饮品 --no-html
python fetch_notes.py --category "美妆,护肤,个护香氛" --no-html
python fetch_notes.py --category 861
python fetch_notes.py --list-categories          # 先看有哪些官方分类

# 编号选择题（零配额）：一次打印 31 个官方一级分类 + 时间 1-5 + 规模 1-3 + 混采 1-4 + 过滤 1-4
python fetch_notes.py --menu

# 正文关键字查询（服务端过滤 desc_text）：逗号分隔多词 OR，字面匹配；
# 实测「咖啡」12h 维度 total=6，全为瑞幸/咖啡内容

# 类目 + 正文词组合收窄（服务端 category AND keyword）
python fetch_notes.py --category 美妆 --body-keyword 口红

# 内容类型收窄：all（默认，图文+视频混合）/ video 仅视频 / normal 仅图文

# 主题归组（看板主题筛选的选项来源，零配额）

  --html "低粉爆款_母婴育儿_12h.html"                          # 归组后重渲染（缓存命中）
# 组内词同时匹配「标签 / 标题 / 正文」；组数不设上限，提炼出几个就展示几个

# 历史数据与清缓存
python fetch_notes.py --category 母婴育儿 --no-history         # 只看本次，不并入历史池
python fetch_notes.py --clear-cache                            # 清本地取数缓存（零配额）

# 加过滤条件（命中缓存时零配额，可反复调）
python fetch_notes.py --category 健身减肥 --min-like 1000
python fetch_notes.py --category 萌宠动物 --time-range 7d --max-fans 1000
python fetch_notes.py --category 美食饮品 --min-like 500

# 最小成本试探：只取 20 条，1 次请求
python fetch_notes.py --category 时尚 --rows 20 --mix like

# 想把当天额度用在刀刃上：累计到 1000 条（50 次请求，约 52 分钟）

python fetch_notes.py --mix like --rows 20
```

参数：`--time-range`（12h 默认/24h/yesterday/3d/7d）、`--sort`
（输出排序：like 默认/rank/collect/comment/share/interaction/updated）、
`--mix`（取数时混采哪些排序，默认 `like,collect`）、`--rows`（缓存目标条数，
默认 40，上限 1000 = 日配额）、`--position`（账号定位词，逗号/空格分隔，
只在 `--plan` 里用于匹配官方分类树，不直接传服务端）、`--category`

`--body-keyword`（正文关键字，服务端过滤 desc_text，逗号分隔 OR，字面匹配）、
`--type`（内容类型：all 默认 / video 仅视频 / normal 仅图文，服务端过滤）、
`--tag-groups`（看板主题筛选的主题组，`"主题=词a,词b;主题2=词c"`；组内词
同时匹配标签、标题、正文，agent 从 `--tag-report` 的标题/正文/标签里提炼后
传入；组数不设上限，不传则按原始标签频次）、`--tag-report`（打印本期样本的
标签频次 + 逐条标题/正文字眼，零配额，用于归组）、`--no-history`（不并入
本地历史池，只出本期）、`--clear-cache`（清掉本地 notes 缓存、历史快照与主题
缓存 `theme_cache.json`，保留额度快照/预览状态/人设，零配额）、
`--save-profile`（把本次的类目/定位词/默认参数固定成人设，写
`<配置目录>/profile.json`，零配额）、`--show-profile`（查看已固定人设）、
`--forget-profile`（取消固定）、
`--cache-dir` / `--config-dir`（本次临时换缓存/配置目录）、
`--set-cache-dir`（永久换缓存目录：复制现有文件 + 写指针）、
`--show-paths`（打印当前路径与缓存数量，零配额）、
`--plan`（定位词→类目候选确认清单，零配额）、`--min-like`、`--max-fans`、
`--html`（输出路径）、`--no-html`、`--list-categories`、`--menu`、
`--allow-anon`（无 Key 时强行走匿名档，仅用于亲眼确认风控 429，不建议用）、
`--refresh`、`--json`。

退出码：0 成功（可能带部分结果）；1 参数/Key 错误；2 网络或限流；3 API 错误；
**4 当日配额用尽且无缓存可查**。

## 6. 输出：HTML 看板 + 三条结论

### 6.1 交付流程（每次取数都走一遍）

1. 取数（缓存优先）
2. **给主题归组**：跑 `--tag-report`（命中缓存、零配额），它给的是本期 N 条、
   标签数、缺 tags 条数，以及**逐条的「标题｜标签｜正文前 70 字」**。据此从
   **标题 + 正文 + 标签**三处提炼主题组（把「萌娃/人类幼崽/可爱宝宝」并组、
   把「18会员惊喜日/手游联动」这类平台活动长尾噪声剔掉），有几个算几个、
   **不设组数上限**，用 `--tag-groups "主题=词a,词b;主题2=词c"` 重新渲染看板
   （仍命中缓存、零配额）。**选项不写死**——每批数据现判断现提炼，样本变了
   组就变；组内词会同时比对该条的标签、标题、正文
3. 终端打印表格汇总行 + 明细 + **`【结论】` 块**（自己核对数字用）
4. **默认生成 HTML 看板**，路径按用户项目目录给，例如
   `低粉爆款_<类目>_<维度>.html`（类目名带逗号时用 `+` 连：`美妆+护肤`；
   传了 `--type video|normal` 时文件名自动加 `_视频` / `_图文`，
   `--type all` 不加）
5. 用 `present_files`/文件交付卡把 HTML 交给用户（必要时
   `Start-Process <html路径>` 直接打开），**聊天正文只回脚本末尾的
   `【结论】` 块（三条 + 预览地址），其他一律不写**
6. **同时给一条 http 地址**（脚本自动起本地预览服务并打印，见 6.1.2），
   在正文里以纯文本单独成行给出，方便用户点开或复制进浏览器
7. **首次交付后收口（只做一次）**：若还没固定人设，用 `interaction_ask`
   问「要不要把这次的人设定位固定下来？」（固定 / 先不固定，详见 2.5）。
   选固定 → `--save-profile` 落盘（零配额、不出看板），回一句「人设已固定，
   下次第 1 题回 0 或说『沿用』即可」；选不固定就结束，不劝第二次

### 6.1.1 对话回复的唯一格式

只罗列这三条，**逐字照抄脚本 `【结论】` 块里的值**，不要自己另算：

```
抓取条数：30 条（样本 40 条，命中率 75%）
内容类型：图文 + 视频（视频 16 · 图文 14）
剩余额度：840 条
预览地址：http://127.0.0.1:8777/低粉爆款_情感_12h.html
```

第四条「预览地址」只在脚本确实打印了 http 地址时给；回落到 `file:///`
时也照抄，不要自己拼地址。

硬性约束：
- **不写**「我做了什么 / 改了什么」「数据来源说明」「最高赞是哪条」
  「粉丝中位数」「选题建议」「类目覆盖率」等任何补充分析，
  用户追问才展开
- **不写**取数参数、请求次数、缓存/实时、耗时、HTML 路径清单
- **不贴**终端表格、不复述明细行
- 附件/链接照常用 `present_files` 交付，但正文不要围绕它写说明
- 0 命中时把「抓取条数」写成 `0 条（样本 N 条，服务端过滤后无命中）`，
  「内容类型」写 `—`，另**只加一条**原因建议（换维度 / 去掉 `--category` /
  去掉 `--type`），不展开
- 额度未知时照实写「未知（本次未拿到服务端额度头）」，不猜数字
- **额度是服务端返回的当日快照**，只有真实发请求才按返回条数扣减；命中
  本地缓存时一行都不扣，报的是上次已知值并标注「本次未消耗」。用户看到
  两次额度相同（比如都是 840 条）属正常：答「这次走缓存没发请求、额度没动，
  X 是上次请求的快照」即可，不要为验证额度去强制刷新重取
- **服务端刚重启时额度头可能先回 0**（计数器未初始化），但照样返回数据。
  脚本已丢弃这种「0 条额度却出了数据」的不可信值，不写盘、不覆盖旧快照；
  遇到报「未知」就让用户 1 分钟后重试一次，别下结论说额度用尽

用户明确说「只要文字 / 只要 JSON / 别生成文件」时，加 `--no-html`，
回复仍是这三条。

### 6.1.2 预览地址（http 直开）

- 脚本默认在 HTML 所在目录起一个 `python -m http.server`，**只绑
  `127.0.0.1`**，端口从 8777 起挑空闲；同目录复用已有服务，服务挂了会**沿用
  上次端口重启**（地址不会每次取数都变），状态存
  `<缓存目录>/serve.json`（`dir` + `port`）
- 地址形如 `http://127.0.0.1:8777/低粉爆款_情感_12h.html`：中文文件名
  **不做 percent-encode**（浏览器自己会转），方便用户复制粘贴
- 开关：`--serve-port 8899` 指定端口；`--no-serve` 不起服务（只交文件）；
  `--stop-serve` 停掉之前起的服务（按端口找 pid 后 kill，零配额）
- 服务是 detached 后台进程，任务结束后仍在跑，下次取数自动复用；只对
  本机 127.0.0.1 可见——**HTML 只存在用户电脑上，没有上传到任何服务器**，
  也没有公网地址
- 用户明确要「能点开/能粘到浏览器的地址」时，把 `【结论】` 里这一行原样
  给出（不改端口、不加引号、不加粗），并说明这是本机预览地址

### 6.2 终端汇总行

`time_range / total / pulled（括号内按排序拆分）/ matched / 类目 或 正文 /
类型（传了 --type 时显示 视频/图文）/ updated / 来源（实时 或 缓存@时间）`；
明细列：名次、类型标记（`[视频]`/`[图文]`，NULL 老数据无标记）、标题、作者、
点赞、收藏、评论、粉丝、标签。

### 6.3 HTML 看板结构

- 头部：`<类目> 低粉爆款` + 时间维度 + 数据更新时间、样本条数、命中条数、来源
- **定位解析卡**：账号定位（`--position` 原词）、官方类目、正文词、
  内容类型（传了 `--type` 时）、**视频直链覆盖率**（`N/M 条可站内播放`，
  M = 本页视频条数）、库内命中总量——让用户看清这次取数的过滤口径
- 4 个 KPI：命中条数（含命中率，并在小字里拆 **视频 X / 图文 Y**，
  有历史条目时补「未标注 Z」）、平均点赞、粉丝中位数、最高点赞（附标题）
- 样本标签热度 Top 8 横向条形图（看这批内容的话题集中度）——**每一格可点**，
  点一下把该标签加进主题筛选，再点移出
- **主题筛选条（可多选）**：选项不写死——
  用 `--tag-groups` 传进 agent 提炼的主题组（组内词同时匹配标签、标题、正文）；
  每次真实取数都会把这些组和原始标签**增量并进** `<缓存目录>/theme_cache.json`
  （按类目分 scope，组内词只增不减、老组永不丢，同一批重渲染不重复计数）。
  看板把该类目**累计的所有主题组全部列出来**，再补上「没被任何主题覆盖、且本批
  出现 ≥2 次」的高频单标签（最多 60 个），按**本批命中数 → 历史累计命中数**从高
  到低排；本批 0 命中的主题仍保留但暗显（`.dim`），点它可回看/筛空。胶囊带可用
  条数，支持同时多选，默认「任一命中」，可切「匹配：全部」，另有「清空标签」；
  样本里没有 tags 的条目有独立「无标签」胶囊（该条自身不带标签）
- **主题胶囊折叠**：胶囊超过 **3 行**时默认只露 3 行（底部渐隐），
  右侧出现「展开全部（共 N 行）」；点开铺满、「收起主题」再折回。行数按实际
  排版测量（`offsetTop` 去重），窗口 resize 会重新量，与条数无关
- **筛选时间条**：`今天 ｜ 昨天 ｜ 近1周 ｜ 近1个月 ｜
  近3个月 ｜ 自定义时间`，每枚带实时条数，点「自定义时间」用旁边的两个日期框
  指定起止（起止颠倒会自动对调）。每次执行都会把本次结果存一份历史快照
  （`<缓存目录>/history/`），所以这些窗口能筛出本地缓存过的历史批次；
  默认看「今天」，若隔天才打开看板、今天为空会自动退到覆盖全部批次的自定义区间；
  结论块与 KPI 仍只算当期，历史只做参照；`--no-history` 可关掉历史池
- 每张卡片右上/底栏带「获取 HH:MM」小徽标：本期显示「本次 …」，
  历史卡片显示各自的获取时间，一眼区分数据新鲜度
- **排序条**：`默认顺序 ｜ 点赞 ｜ 收藏 ｜ 评论 ｜ 转发 ｜ 降序 ↓/升序 ↑`。
  点指标即按该指标降序重排（大→小），再点右侧方向按钮切升序；点「默认顺序」回到
  榜单原始顺序。排序只重排 DOM 里的卡片，**不重新取数、不花配额**，且与内容类型、
  标签筛选叠加生效（被筛掉的卡片仍隐藏，重排不改变筛选状态）；当前排序会写进
  筛选状态行（如「当前：视频 · 按点赞降序 · 命中 12 / 37 条」）
- **内容类型筛选条**：`全部 N ｜ ▶ 视频 N ｜ 图文 N` 三枚胶囊，
  点击即在页面内过滤卡片（客户端，不重新取数、不花配额）；某类型 0 条时
  显示「该类型下没有命中内容，切回『全部』看看」；有未标类型条目时附一条
  「另有 N 条未标类型，仅在『全部』可见」。**内容类型与标签正交叠加**，
  两边的计数会随对方的选择实时重算（分面筛选）
- 卡片墙（3 列自适应）：封面图（3:4）、名次角标、**类型徽标**（封面右上角：
  视频红底 `▶ 视频 0:20`（带时长，取自 `raw_json.duration`）；徽标本身是**直链**
  （服务端 `video_url` 字段，mp4 流地址），点击新标签页打开视频；无 `video_url`
  的视频行退化为不可点徽标 / 图文深灰底，未标类型数据无标）、标题（2 行截断）、
  作者 + 粉丝（≤1 千标红）+ 官方分类徽标（如有）、赞/藏/评/转、标签、发布时间、
  `打开笔记 ↗` 跳原帖
- **复制按钮**：每张卡片底栏和浮层里都有「复制」，一键把该笔记整理成可直接
  喂给 AI 的结构化文本（标题 / 作者+粉丝 / 分类 / 类型 / 视频直链（有
  `video_url` 时）/ 发布 / 赞藏评转 / 标签 / 正文 / 原帖链接），点击后按钮变
  「已复制 ✓」1.5 秒；`navigator.clipboard`
  不可用时自动降级 `execCommand('copy')`，file:// 下同样可用
- **站内预览浮层**：整张卡片可点击（`onclick=openNote(i)`，Enter 亦可），
  弹出小红书式浮层——左侧 720px 宽封面大图，右侧标题 / @作者 + 粉丝 + 分类 /
  类型（视频笔记/图文笔记，老数据不显示）/ 正文（超 260 字按 8 行截断并可
  「展开全文」）/ 标签 / 赞藏评转 + 发布时间 / `在小红书打开 ↗`（有
  `video_url` 时多一枚红色 `播放视频 ↗` 直链 mp4）；ESC、点遮罩、
  右上 ✕ 均可关闭。备注数据以
  `<script type="application/json" id="notes-data">` 注入，不写进可执行 JS 字面量
- **浮层内直接播放**：视频笔记有 `video_url` 时，浮层左侧直接换成
  `<video controls playsinline>` 播放器（`poster` 用 720 宽封面），关闭浮层自动
  `pause` + 清 `src`，不会后台偷跑流量；播放失败（直链过期/防盗链）自动退回
  封面图，右侧 `播放视频 ↗` 仍可手动打开。视频卡片封面正中另加半透明 ▶ 圆标，
  提示「这条能播」（无直链的老视频行不显示）
- 空结果也有页面：写明「服务端过滤后 0 命中（库内总量 N 条）」，并给出
  下一步建议（换 12h/yesterday 维度 / 去掉 --category 改用 --body-keyword /
  去掉 --type 排除只是类型收窄过头 /
  --plan 重新确认类目）
- 页脚口径：数据来源、名次可能重复、粉丝缺失记「—」、互动量为抓取快照

页面特性：单文件自包含，内联 CSS、无外部 JS 依赖；封面图直接引用小红书 CDN
（`<meta name="referrer" content="no-referrer">` 绕防盗链），断网/加载失败时由
渐变底色 + 「封面加载失败」文字兜住，不会出现破图占位。原帖链接在小红书侧
常因风控/登录返回 404，因此点击预览（站内浮层）是主路径，「打开笔记」只是备选。

`--json` 输出完整 20 字段：`note_id`、`time_range`、`rank_no`、`title`、`author`、
`author_id`、`cover_url`、`video_url`（视频条目 mp4 流地址，图文条目
NULL）、`publish_time`、`like_count`、`collect_count`、
`comment_count`、`share_count`、`interaction`、`fans_count`、`tags`、
`first_seen_at`、`last_seen_at`、`category_name`（官方分类名，NULL = 上游未分类）、
`note_type`（normal=图文 / video=视频，NULL = 早期未标类型条目）；
meta 另带 `category:{query,matched,unresolved,leaf_tags}` 与 `position` /
`body_keyword` / `note_type` 记录本次过滤口径。

转述用户时保留关键数字，并注明「数据按每日 1000 条配额、服务端按返回条数扣费」。

### 6.4 本地缓存与配置路径

**目录分工**（缓存是机器级的，不跟对话走）：

- **数据缓存**（可丢、量大）：默认 `%LOCALAPPDATA%\liuchuan-data\cache`
  （mac/Linux `~/.cache/liuchuan-data/cache`），放 `notes_*.json`、`history/`、
  `theme_cache.json`、`quota.json`、`serve.json`
- **配置**（该留、量小）：默认 `%APPDATA%\liuchuan-data\config`
  （mac/Linux `~/.config/liuchuan-data/config`），放 `profile.json`、`last_run.json`

**路径优先级**：`--cache-dir` / `--config-dir`（只影响本次）> 环境变量
`LIUCHUAN_CACHE_DIR` / `LIUCHUAN_CONFIG_DIR` > `paths.json` 指针 > 平台默认。

**用户改路径**：`--set-cache-dir "<目录>"` 会把现有缓存**复制**过去（不删除原目录）、
把指针写进 `%APPDATA%\liuchuan-data\paths.json`，下次启动自动沿用；
`--show-paths` 打印当前缓存/配置目录与文件数，两者都零配额、不取数。
注意环境变量优先级高于指针，设了 `LIUCHUAN_CACHE_DIR` 时以环境变量为准。

**旧数据迁移**：首次启动若发现旧版 `~/.liuchuan_cache`，会把
notes / history / theme / quota / serve 以及 profile / last_run 复制到新目录，
**旧目录原样保留、不删除**；迁移只做一次（配置目录里 `.paths_migrated` 标记）。

**默认全量保留**：缓存不按时间或体积自动清理，跑过的批次都留着（目前几十 MB 级）。
要清就显式 `--clear-cache`：清 notes + history + theme，保留 `quota.json` /
`serve.json` / `profile.json`。

**跨对话共享**：同一台机器、同一用户下，任意对话、任意技能副本（工作区 / D 盘同步副本）
都读同一份缓存；换机器或切到云主机则各自独立。

## 7. 已知边界（实测，转述用户时如实说明）

- **配额按「服务端过滤后返回的条数」计**：`category AND keyword`
  全部服务端过滤，返回几条扣几条；零命中零扣费（实测 `body-keyword=zzqqxx` 返回 0 条、
  `X-Quota-Remaining-Notes` 不变）。成本 = 实际返回条数，与排序数/页数只有间接关系
- **本地只剩两类过滤**：`--min-like` / `--max-fans` 是拉回后本地筛，不退还配额；
  本地不做关键词过滤（关键词走服务端 `--body-keyword`）
- **单请求实际只给 20 条**（page_size 传 200 也按 20 返回）
- **匿名档只够试两次**：不传 Key 按访客 IP 计，单次最多 5 条、每天 10 条、
  1 请求/3 分钟；脚本本身就会先拦下（见下一条），`--allow-anon`
  才真的去撞闸
- **匿名档 UA 闸门**：脚本 UA（python-requests/curl/…）在匿名档被
  429 拦（`user-agent blocked`），重试无用——**无 Key 跑本技能必然触闸**，
  配置 `LIUCHUAN_API_KEY` 后一切恢复；带 Key 的请求不看 UA
- **无 Key 前置拦截**：不配 Key 直接返回码 1，stderr 给配 Key 指引，
  **不发请求**（先打公开 `/meta` 探活确认服务可达）；省掉一次必然失败的往返
  和一条英文 429 误导
- **数据新鲜度守卫**：正式取数前打公开 `/meta`，`last_ingest_at`
  距今超过 15 分钟就在 stderr 打 `WARN: 数据可能不是最新的…（采集端可能停了，
  本次拿到的是旧榜）`，并带 12h 榜 `updated_at`；**该检查零配额**，
  用于把「数据冻住」和「榜变了」区分开
- **匿名双轨计费**：服务端 per-IP 与 `X-Client-Id`（本机 UUID，
  `~/.liuchuan_client_id`）两份配额并联扣减取较小剩余，换 IP 不换设备换不掉
  额度；另有单 IP 30 次/日请求上限与全局 2000 条/日预算（`daily request
  limit` / `budget exhausted` 文案，次日恢复）
- **配额不足是部分交付，不是整请求 429**：剩 N 条就只返回 N 条，`pulled` 小于目标
  条数属正常，脚本会照常用到手的那几条
- **响应头 `X-Quota-Remaining-Notes` 每次返回当日剩余条数**，终端汇总行带
  `剩余=N条`；命中缓存时该值是上次请求时的快照
- **额度只在真实请求时扣**：命中本地缓存（同维度同排序同过滤因子，1 小时内）
  零请求、零扣减，`【结论】` 仍报上次落盘值并标注「本次未消耗」，
  落盘位置 `<缓存目录>/quota.json`（`remaining` + `at`）
- **每天 1000 条配额**（按 Key 计）：超了返回 `daily notes quota exhausted`，
  当天取不到新数据，已缓存的维度还能查；配额计数器在服务端内存，**重启清零**
- **限速 1 请求/分钟**，且被拒一次会重置计时；脚本按 `retry in Ns` + 20 秒退避
- **官方分类覆盖率约 74%**（12h 实测）：上游内容榜大部分爆文没打类目，
  采集侧按全部 31 个一级分类 x 4 个时间维度（12h/yesterday/3d/7d，24h 上游异常跳过）
  补采，新进条目均带类目；剩余无类目条目是早期累积条目，类目查不到时用
  `--body-keyword` 按正文词兜底
- **账号定位无同义词表**：定位词只匹配官方分类树（精确同名 +
  一二层双向子串），「搞钱」「穿搭」「ootd」这类口语词不会猜——
  `--plan` 输出无候选时，引导用户从 31 个官方一级分类里选，
  或改用 `--body-keyword`；服务端 `domain=`（title/tags）参数仍在，
  但技能侧已不使用
- **老维度数据已完整**：yesterday/3d/7d 三个维度同样有全量分类补采，
  类目查询可用（如 7d 职场 total=38、3d 职场 total=35）
- **类目是平台商品视角，与内容领域有偏差**：实测职场子树里有三级叶子
  「职场/工作日常/影视动画」，职场向动画梗笔记归在职场（符合预期），
  但探店内容常挂「生活记录」而非「美食饮品」；好物开箱在 31 个一级类目里
  无对应——这类领域用 `--body-keyword` 按正文词检索
- **同名分类按最浅层解析**：查询「摄影」只取一级
  摄影(3015) 子树，不再并入深层同名叶子「兴趣爱好/生活情趣/摄影」
  （leaf_tags 101→100）；「游戏」同理（60→59）；多父同名兄弟节点
  （如「表情包」）仍并集
- **正文关键字只匹配正文**（desc_text）：标题或标签含该词但正文不含的笔记会漏；
  要按标题找词只能先拉回来看 `tags` 字段或换关键词
- **`--body-keyword` 是字面匹配**：`%` `_` 不当通配符（实测 `%` 只命中 1 条），
  多词用逗号分隔（OR），不要传正则
- **单排序样本很窄**：点赞榜头部多为娱乐类，所以默认混采 like+collect 拓宽内容面
- **滞后约 5 分钟**（实测 07:40 取到 07:35 的数据）
- **24h 维度当前异常**（实测只有 2 条，正常应是 12h 的超集）→ 优先 12h / yesterday
- **榜内名次会重复**：库内是多次采集快照的并集，`rank_no` 按各快照编号，
  同名次会出现两条，别当唯一键；12h 榜实测缺 1-30 名
- **服务端 `sort=rank` 是名次倒序（榜尾在前）**，脚本已本地重排为榜头在前
- **`fans_count` 有缺值**（约 8% 记为 0）；低粉榜本身已全是 ≤1 万粉，
  `--max-fans 10000` 基本等于不过滤
- **tags 缺失约 35%、`author_id` 缺失约 46%**；实测 12h 一批 40 条样本里就有
  20 条完全没有 tags（覆盖率随样本波动，低粉榜尾部尤其多）——所以看板的标签
  筛选必须带一枚「无标签」胶囊，否则一选标签就把这批卡片全藏掉了
- **tags 是平台原样长尾**：一批 40 条样本能出 186 个不同标签，大部分只出现 1 次，
  还混着「18会员惊喜日 / ××手游联动」这类活动噪声。所以主题选项不写死，由 agent
  按 `--tag-report` 的**标题 / 正文 / 标签**三处现判断归组（近义并组 + 剔噪声），
  组名要能让人一眼看懂主题；组内词按标题+正文+标签全文比对，
  这样「娃衣」「奶粉」这类只在正文出现的词也能被筛到
- **历史快照只保留到「天」的粒度**：`history/` 按批次存（文件名带
  `__YYMMDD_HHMM`），看板「筛选时间」把它归并成 今天/昨天/近1周/近1个月/近3个月/
  自定义 六种窗口；同一天多批次合并，要精确到时分得再改。历史池与当期分开
  ——**结论块、KPI 只算当期**，历史只用来回看，避免命中率被历史条目撑爆
- **历史池按类目收敛**：只读同一 category 范围内的缓存与快照（同类目不同关键词/
  排序的批次也算历史），换类目不会串数据；只按 keyword 或全库查询时按完整查询
  口径收。清缓存（`--clear-cache`）会连同历史快照、主题筛选缓存
  （`theme_cache.json`）一起清掉，只留 `quota.json` / `serve.json` / `profile.json`
- **主题缓存是累积的、只增不减**：`theme_cache.json` 按类目存主题组（组名+词表+
  累计命中数）和原始标签频次；新批次只会并进新组/新词，不会删老组，所以看板上的
  主题会随使用越来越多——折叠和「暗显 0 命中」就是为这个设计的。要重来一遍就
  `--clear-cache`（会把主题缓存一起清掉，下次重新积累）
- **图文 + 视频混合**：视频行的 mp4 地址在服务端独立字段 `video_url`
  （CDN 地址有时效，过期后只能等采集端重新入库）；`note_type` 字段区分
  normal/video，用 `--type` 收窄；少量早期条目 `note_type` 为 NULL（只在
  `all` 下可见，不被猜成任一类型）
- **`video_url` 覆盖率不是 100%**：看板定位解析卡会明写 `N/M 条可站内播放`，
  缺直链的只能跳原帖，别当"技能坏了"
- **直链是小红书 CDN 的 mp4 流**，有时效 + 可能防盗链：HTML 里点开会直接播，
  播放失败时播放器自动退回封面（右侧 `播放视频 ↗` 仍可手动打开）；直链过期后
  只能等采集端重新入库
- **图文只有一张封面图**：服务端 `raw_json` 只有单个
  `imageUrl` 字符串，无 `images/imageList/pics` 数组；灰豚 SPA 999 端点 + 
  `/note/detail` 实测也只给封面，多图 URL 上游不提供，要更多图只能靠小红书
  登录态解析笔记详情（不在技能范围内）
- **`interaction` 不等于四个计数之和**（实测仅 30% 吻合），不要自己重算
- **端点与变量口径**：端点 `/liuchuan/api/v1`、缓存与配置目录见 6.4、Key 变量
  `LIUCHUAN_API_KEY`、品牌名「流川数据服务」。首次运行会自动把旧目录里缺的
  历史 `notes_*.json` 复制进新目录（**只补缺、不覆盖、旧目录保留**），
  所以老的取数结果仍能零配额命中，不会白花配额重拉

## 8. 故障处理

| 现象 | 处理 |
|---|---|
| 退出码 4 / "今日配额已用尽" | 等次日重置；当天只查已缓存的维度（同维度同排序零配额） |
| 退出码 2 / 限流 | 脚本已退避重试；仍失败等 1-2 分钟，或直接用缓存 |
| 退出码 3 / "api key rejected" | Key 无效或过期，联系发放方 |
| 退出码 3 / "unknown category" | 分类名不存在：先 `--list-categories` 核对官方名称，或改传数字 ID；多类目中部分无法识别时 meta.unresolved 会报告，其余生效 |
| `--category` 结果很少/为 0 | 约 26% 条目未分类（12h 实测），属预期；类目没数据时去掉 `--category` 改用 `--body-keyword`，或 `--plan` 重新确认类目、换 12h/yesterday 维度 |
| `--plan` 输出「无候选」 | 定位词不在官方分类树：重发 31 个一级分类精简菜单让用户选，或 `--body-keyword` 按正文词检索；不要自己编同义词 |
| 退出码 1 / "未配置 API Key → 无法取数" | 无 Key 前置拦截：按 stderr 指引配 `LIUCHUAN_API_KEY` 重开终端；只想看菜单/分类用 `--menu` / `--list-categories` / `--plan` |
| stderr `WARN: 数据可能不是最新的` | 采集端可能停了（看 `/meta` 的 `last_ingest_at`）：如实告诉用户「这批是 XX:XX 的旧榜」，不要解释成「榜变了」；同时建议查采集端 |
| stderr `WARN: 无法写入 .../.liuchuan_client_id` | 家目录不可写，双轨配额退化为单 IP 单轨；不影响取数，修权限即可恢复 |
| 429 detail 含 `anonymous free tier` | 匿名档当天 10 条已用完：等次日 0 点，或领 Key 配 `LIUCHUAN_API_KEY` |
| 429 detail 含 `user-agent` / `blocked` | 匿名档 UA 闸门：脚本 UA 在无 Key 时被拦，重试无用——配 `LIUCHUAN_API_KEY` 后恢复，带 Key 不看 UA；已配仍报错则检查是否有旧变量名残留 |
| 429 detail 含 `daily request limit` | 匿名档单 IP 日请求上限（30 次/日）：等次日，或配 Key（Key 档无此限制） |
| 429 detail 含 `budget exhausted` | 匿名全局日预算（2000 条/日）被打满：全部匿名用户当天被拦，等次日或配 Key |
| 404 / 旧前缀 `/yaundian/...` 打不通 | 旧前缀已失效：端点用 `/liuchuan/api/v1`，不要回退旧名试错 |
| stderr 提示读到旧变量名 | 只是兼容提示，取数正常；顺手把用户级变量统一成 `LIUCHUAN_API_KEY` 即可，不是故障 |
| 返回条数少于目标（`pulled` < `rows`） | 配额不足导致的**部分交付**，不是故障；到手几条用几条，次日补满 |
| matched=0 且 total=0 | 服务端 类目 AND 正文词 过滤后库内 0 命中：类目没数据就去掉 `--category`；正文词太窄去掉或换词 |
| matched=0 但 total>0 | 被 `--min-like`/`--max-fans` 本地过滤砍光：放宽过滤条件 |
| `--type video` 命中很少/为 0 | 老维度（yesterday/3d/7d）与历史条目的视频量还在随每 30 分钟的采集积累：换 12h 维度，或不传 `--type` 看全量 |
| `--type` 传了非法值 | 只接受 all/video/normal（也认 1/2/3 编号与 全部/视频/图文），其余 argparse choices 直接报错，不会静默按 all 处理 |
| 跑得很慢 | 每页间隔 62 秒是接口限速所致；`--rows 20 --mix like` 最快（1 次请求） |
| 浮层里视频不播 / 只显示封面 | 该条没有 `video_url`（看定位解析卡 `N/M`），或直链已过期：让用户点 `播放视频 ↗` / `打开笔记 ↗`，或重跑一次等采集端补新直链；不要说是技能故障 |
| 用户只要文字 | 加 `--no-html`，或直接复述终端表格里的关键数字 |
| 端点未配置/配错 | 通用客户端版不发注定失败的请求：设 `LIUCHUAN_BASE_URL`（Windows 用 `[Environment]::SetEnvironmentVariable`，设完重开终端）或单次 `--base-url`；仍报错先用 `--selfcheck` 做离线自检定位 |

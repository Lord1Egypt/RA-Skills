## B.1 双向追溯与 DEF 映射表

每个缺陷（DEF-XXX）同时存在于 PM 视角和 Dev 视角。映射表是两者之间的导航地图：

| 缺陷统一编号 | PM 视角缺陷名称 | PM 严重程度 | Dev 视角发现来源 | 发现文件 | 映射关系 |
|:---:|------|:---:|------|:---:|:---:|
| DEF-001 | 确认支付按钮点击无响应 | Critical | 01 静态 + 02 动态 | 01/02 | 1 对 多 |

### Quick 模式简化规则

Quick 模式仅输出 **Dev 视角缺陷列表**（含 DEF 编号 + 证据摘要）。若无 Critical/High 缺陷，可省略完整 PM 转译和映射表；若有 Critical/High，仍须为每项提供一句 PM 业务后果摘要。

### Standard / Release / Custom 完整规则

**双向追溯完整性校验**：在生成报告后，自动执行以下校验——

1. PM → Dev 方向：PM 视角每个缺陷必须在 Dev 视角有对应证据
2. Dev → PM 方向：Dev 视角每个 Bug 必须关联到 PM 视角的缺陷
3. 覆盖率：映射表 DEF 编号总数 = PM 缺陷总数 = Dev 被引用 DEF 去重总数

校验结果输出格式：
```
✅ 双向追溯完整性校验：通过
- PM 视角缺陷总数：5 个
- Dev 视角 Bug 总数：8 个
- 交叉引用映射覆盖率：100%（5/5 DEF 编号均已双向关联）
- 孤儿缺陷：0 个
```

## B.2 统一测试报告模板（test-report.md）

无论执行哪种模式，最终报告统一生成为项目根目录的 `test-report.md`。报告结构按模式动态开关：

```
# test-report.md

## 执行摘要
- 执行模式：[Quick / Standard / Release / Custom]
- 已加载规则文件：[列出]
- 环境能力声明：[00-§0.2 内容]
- 🤖 自动化结论：[✅ 通过 / ⚠️ 有条件通过 / 🚫 阻塞 / ❓ 未完成]（仅基于 AI 可自动执行的测试结果，忽略 MAN-XXX 填写状态）
- 📋 完整结论：[✅ 通过 / ⚠️ 有条件通过 / 🚫 阻塞 / ❓ 未完成]（含人工清单状态）
> **双结论说明**：不含 03 的模式（Quick/Standard/Perf/Contract/Concurrency/Chaos）只输出单一结论行，不区分 🤖/📋。含 03 的模式（Release/Custom 含 03）必须输出双结论。

## A. 静态审计结果（来源：01）
[始终有，按 01 的规则输出]

## B. 动态测试结果（来源：02）
[02 跳过时标注"已跳过 + 原因"，否则按 02 的规则输出]

## C. 人工检查清单（来源：03）
[Release 模式或 Custom 含 03 时生成；每项带 MAN-XXX 编号，默认全为待填]

## D. 性能测试结果（来源：04）
[Perf 模式或 Custom 含 04 时生成；按 04 的规则输出 PP0~PP4 结果 + 性能缺陷 + 门禁结论]

## E. 契约动态测试结果（来源：05）
[Contract 模式或 Custom 含 05 时生成；按 05 的规则输出 Schema 验证 + 字段完整性 + 错误码契约 + 兼容性 + 门禁结论]

## 缺陷总览
### PM 视角
#### Critical（[N] 个）
- **DEF-XXX**：[用户看到的异常现象 + 业务后果，≥ 150 字]
- **DEF-XXX**：[用户看到的异常现象 + 业务后果，≥ 150 字]

#### High（[N] 个）
- **DEF-XXX**：[用户看到的异常现象 + 业务后果，≥ 120 字]

#### Medium（[N] 个）
- **DEF-XXX**：[问题是什么 + 为什么值得关注，≥ 80 字]

#### Low（[N] 个）
- **DEF-XXX**：[问题是什么，≥ 40 字]

> 每个 DEF 的 PM 描述必须独立展开，严禁仅写"无影响"、"无用户可见影响"、"影响开发效率"等笼统词汇。即使是对用户无直接感知的缺陷（如代码重复、构建警告），也必须用大白话说明"如果不修，未来可能导致什么后果"。

### Dev 视角
每个缺陷必须包含以下字段，不得省略：
- **编号 + 问题简述**
- **精准定位**：相对路径 + 行号
- **证据**：响应体/日志/代码片段/命令输出（截断）
- **因果剖析**：运行时发生了什么，为什么会出问题
- **推荐修复方案**：必须包含具体代码片段或操作步骤。不得仅写"建议修复"、"建议优化"等空洞描述。代码片段须贴合项目现有技术栈和代码风格

## 双向追溯映射表
[Quick 模式可省略；Standard / Release / Custom 必填 §B.1 映射表 + 校验结果]

## 人工项完成度（仅含 03 时）
- MAN 总数：[N]
- 已填写：[N] / 待填写：[N]
- 阻塞项（填「不可用」或超过需优化阈值）：[列出 MAN-XXX]
```

## B.3 PM 视角生成规则

PM 视角的缺陷描述**从 Dev 证据转译生成，而非另写一套**。每个缺陷必须独立展开，字数下限如下：

| 严重程度 | 最低字数 | 必须包含的内容 |
|:---|:---:|------|
| **Critical** | ≥ 150 字 | ① 用户看到的异常现象（界面表现）② 对用户造成的业务后果（数据丢失/流程中断/无法完成任务）③ 如何触发（用大白话描述操作步骤） |
| **High** | ≥ 120 字 | ① 用户看到的异常现象 ② 对用户造成的业务后果 ③ 如何触发 |
| **Medium** | ≥ 80 字 | ① 问题是什么（用大白话）② 为什么值得关注（如果不修，未来可能导致什么） |
| **Low** | ≥ 40 字 | 问题是什么（用大白话说清楚，不得少于一句完整的话） |

**内容红线**：
- 严禁使用"无影响"、"无用户可见影响"、"不影响使用"等空洞描述——即使对用户无直接感知（如代码重复、构建警告），也必须说明"如果不修，未来可能导致什么后果"
- 严禁出现代码层面的函数名、类名、变量名、文件后缀
- 必须使用普通用户可见的界面元素和交互动作来描述
- 对用户无直接感知的缺陷（如代码质量），必须转译为"对开发/维护的影响最终会怎样影响用户"，例如：代码重复 → "未来添加新武器类型时容易出错，导致玩家装备异常"

**转译示例**（从 Dev 证据到 PM 描述）：
- Dev："8 个武器槽字段独立声明，无数组复用" → PM："目前模组支持 8 个武器槽位，但每个槽位的处理逻辑是独立编写的，代码量很大。这会导致未来想增加新槽位或调整攻击逻辑时，需要逐一修改 8 处代码，容易遗漏造成不同槽位表现不一致，玩家会感觉有的槽位攻击正常、有的槽位攻击异常。"
- Dev："TooltipAttribute 已过时，有 10 处 CS0618 警告" → PM："模组配置项的描述文字使用了旧版 API，虽然目前不影响游戏内显示，但未来游戏版本更新后这些描述可能失效，导致玩家在配置界面看不到各项功能的说明文字。"

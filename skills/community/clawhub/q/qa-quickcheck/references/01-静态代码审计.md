# 01-静态代码审计：源码级质量与安全分析

> ⚠️ **执行前提**：本文件由 ../00-通用规范.md 调度加载。你不需要判断是否执行本文件——00 已经决定了。
> 本文件所有任务**仅依赖源码、配置文件和命令行审计工具**，不要求项目可运行。

---

## 1.1 项目特征扫描（必须最先执行）

优先读取项目根目录的依赖配置文件，分析核心框架，输出到最终报告的 A 节开头：

- **动态识别技术栈**：读取 `package.json` / `pom.xml` / `requirements.txt` / `Cargo.toml` 等，提取语言、框架、构建工具。
- **动态识别业务属性**：根据项目名称、目录结构、路由命名推断业务领域。
- **动态分析核心数据交互**：识别数据库 ORM 配置、API 调用模式、状态管理方案。
- **环境快照**：记录当前操作系统、运行时版本、关键依赖版本。

**输出物**：一段技术栈摘要，作为报告 A 节的第一部分。

---

## 1.2 功能入口清单扫描

扫描项目结构，生成功能全景，作为后续测试的覆盖基线：

- **前端项目**：扫描 `router/` 或路由配置文件获取页面清单，扫描 `components/` 或 `pages/` 目录获取组件树。
- **后端项目**：扫描 Controller / API 路由定义文件（如 `routes/`、`controllers/`、`api/` 等），按 RESTful 方法（GET/POST/PUT/DELETE）分类。
- **全栈项目**：同时扫描前后端，交叉验证前端调用的接口是否在后端有对应实现。若前端调用了某路径但后端路由/Controller 中无定义，标记为 **「待确认断链」** 并附证据（前端调用位置行号 + 后端扫描范围说明），不得无证据断言。

**输出物**：一张功能入口清单表（含路由路径、组件名称、所属模块）。

## 1.3 安全-静态：源码安全审计

### 1.3.1 硬编码密钥与敏感信息

扫描所有源码文件，检测以下模式：

- API Key / Secret / Token / Password 硬编码在源码中
- 数据库连接字符串含明文密码
- JWT Secret / 加密密钥硬编码
- 手机号 / 身份证号 / 邮箱等 PII 出现在源码中
- `.env` 文件是否被提交到版本控制（检查 `.gitignore`）

**扫描方法**：使用 Grep 搜索以下正则模式（不限于此）：
```
(sk-|api_key|secret|password|token)\s*[:=]\s*['"][^'"]{8,}
mongodb://.*:.*@
jdbc:.*://.*:.*@
```

**输出格式**：每个发现生成一条记录：
- **SEC-XXX [静态]** 编号
- 文件路径 + 行号（相对路径）
- 泄露内容类型（密钥 / 密码 / PII）
- 严重程度（按 00-A §A.1 定级）

### 1.3.2 危险 API 调用

扫描前端源码中的危险 DOM 操作和后端源码中的危险数据库操作：

**前端危险模式**：
- `innerHTML` / `outerHTML` / `document.write()` — 潜在 XSS 入口
- `eval()` / `new Function()` — 代码注入风险
- `dangerouslySetInnerHTML`（React）— XSS 风险

**后端危险模式**：
- SQL 字符串拼接（如 `"SELECT * FROM users WHERE id = " + userId`）
- 原始 `exec()` / `spawn()` 调用拼接用户输入
- NoSQL 注入模式（如 `{ $where: userInput }`）

**输出格式**：每个发现：
- **SEC-XXX [静态]** 编号
- 文件路径 + 行号
- 危险 API 类型
- 严重程度
- 是否可控（用户输入是否可达该调用点）

### 1.3.3 Cookie 与 Session 安全配置

检查服务端 Cookie/Token 配置：

- Cookie 是否设置 `HttpOnly`（防止 JS 读取）
- Cookie 是否设置 `Secure`（仅 HTTPS 传输）
- Cookie 是否设置 `SameSite`（防 CSRF）
- Token 过期时间是否合理

### 1.3.4 敏感信息泄露

- 审计前端源码中是否包含后端 API 地址硬编码（可能暴露内网拓扑）
- 检查错误处理是否向客户端返回了堆栈信息
- 检查 Console 日志中是否有 `console.log(token)` 等调试残留

## 1.4 安全-静态：依赖 CVE 审计

执行依赖扫描命令，提取已知漏洞：

**命令**（根据技术栈选择）：
- Node.js：`npm audit --json`
- Python：`pip-audit` 或 `safety check`
- Java/Maven：`mvn dependency-check:check`
- Rust：`cargo audit`

**输出格式**：每个 CVE 生成一条记录：
- **SEC-XXX [静态]** 编号
- 依赖名称 + 当前版本
- CVE 编号
- 严重级别（Critical / High / Medium / Low）
- 受影响功能描述
- 建议升级版本

> 若 audit 命令不可用（未安装），在报告中标注"依赖审计跳过：audit 工具未安装"，不得跳过此步骤。

## 1.5 API 契约一致性校验（全栈项目必做）

提取前端 API 调用的入参字段名、类型、必填标记，与后端路由定义中的 Schema 进行交叉比对。

### 1.5.1 扫描范围（按模式）

| 模式 | 契约深度 | 扫描范围 |
|:---|:---|------|
| **Quick** | MVP | 仅扫描 Git diff 变更文件涉及的 API 调用与对应后端路由；无 diff 时扫描变更模块相关接口 |
| **Standard** | MVP | 同 Quick：仅 **diff 涉及接口**（见 00-§0.8 回归范围） |
| **Release** | Extended | **全量**前后端接口交叉比对 |
| **Custom「契约 Extended」** | Extended | 全量比对，无视 diff |
| **Custom「契约 MVP」** | MVP | 仅 diff 涉及接口 |

### 1.5.2 不一致类型
- **多余字段**：前端传了但后端未定义的字段
- **缺失字段**：后端定义了必填但前端未传递的字段
- **类型不匹配**：同名字段前后端类型不一致（如前端传 `string`，后端期望 `number`）
- **响应字段缺失**：前端期望的响应字段在后端响应 Schema 中不存在

**输出格式**：每个不一致项生成一条记录：
- **CTR-XXX** 编号
- 接口路径（如 `POST /api/user/update-profile`）
- 不一致类型
- 前端定义（字段名 + 类型）
- 后端定义（字段名 + 类型）
- 风险等级（High / Medium / Low）
- 建议

**契约一致性汇总表**：

| 状态 | 数量 | 说明 |
|:---:|:---:|------|
| 完全一致 | [N] | 前后端字段定义完全匹配的接口数 |
| 存在不一致 | [N] | 存在字段缺失/多余/类型不匹配的接口数 |
| 前端调用后端缺失 | [N] | 前端调用了但后端未定义的接口数 |
| 后端定义前端未调用 | [N] | 后端定义了但前端未调用的接口数（可能是废弃接口） |

## 1.6 代码质量审计

### 1.6.1 N+1 查询检测

扫描所有数据库查询代码，检测循环中逐条查询的 ORM 模式：

**典型模式**：
```javascript
// N+1 问题：循环内逐条查询
for (const user of users) {
    const posts = await Post.find({ userId: user.id }); // 每次循环一次查询
}
```

**输出**：文件路径 + 行号 + 优化建议（使用 Eager Loading / 批量查询 / JOIN）。

### 1.6.2 全表扫描风险

检测 SQL 查询中缺少索引的 WHERE 条件或 JOIN 字段：

- WHERE 条件使用了非索引列
- JOIN 字段未建立索引
- `SELECT *` 查询无 LIMIT

### 1.6.3 资源泄漏隐患（静态检测）

扫描代码中的以下模式，标记潜在的资源泄漏：

- `setInterval` / `setTimeout` 无对应的 `clearInterval` / `clearTimeout`
- 事件监听器 `addEventListener` 无对应的 `removeEventListener`
- WebSocket 连接 `connect()` 无对应的 `disconnect()` 或 `close()`
- 文件句柄 `open()` 无对应的 `close()`
- React `useEffect` 中订阅未返回清理函数

**输出**：文件路径 + 行号 + 泄漏类型 + 风险说明。

## 1.7 依赖项深度安全审计

> 本节是对 §1.4 基础 CVE 审计的补充，覆盖许可证合规、过期依赖、间接依赖风险等维度。

### 1.7.1 许可证合规检查

扫描所有直接依赖和间接依赖的许可证类型，识别合规风险：

- **GPL / AGPL 传染风险**：标记使用 GPL 系列许可证的依赖，评估是否会导致项目源码被强制开源
- **商业不兼容许可证**：如 CC BY-NC（禁止商业使用）、SSPL 等
- **未声明许可证**：标记无 LICENSE 声明的依赖包

**扫描方法**：
- Node.js：`npx license-checker --json` 或读取 `node_modules/*/package.json` 的 `license` 字段
- Python：`pip-licenses` 或读取 `site-packages/*/METADATA` 中的 License 字段

**输出格式**：
| SEC-XXX | 依赖名 | 版本 | 许可证 | 风险等级 | 原因 |
|:---|:---|:---|:---|:---:|------|
| SEC-050 | some-gpl-lib | 1.2.3 | GPL-3.0 | High | 传染性许可证，可能导致项目源码被迫以 GPL 开源 |

### 1.7.2 过期与废弃依赖检测

检测项目中已停止维护（deprecated）或严重过期的依赖：

- **已废弃依赖**：npm 标记为 `deprecated`、PyPI 标记为 `Development Status :: 7 - Inactive` 的包
- **严重过期依赖**：当前版本落后最新大版本 ≥ 2 个主版本号的包
- **无维护者依赖**：GitHub 仓库已归档或超过 1 年无提交的依赖

**扫描方法**：
- Node.js：`npm outdated --json` 或 `npx npm-check-updates`
- Python：`pip list --outdated --format json`

**输出格式**：
| 依赖名 | 当前版本 | 最新版本 | 落后主版本数 | 维护状态 | 风险等级 |
|:---|:---|:---|:---:|:---|:---:|
| lodash | 3.10.1 | 4.17.21 | 1 | 活跃 | Medium |
| some-abandoned-pkg | 1.0.0 | 1.0.0 | 0 | 已废弃（2年无更新） | High |

### 1.7.3 间接依赖（传递依赖）风险审查

审计 `package-lock.json` / `yarn.lock` / `poetry.lock` 中的间接依赖：

- 是否存在已知 CVE 的间接依赖（锁定文件中的版本号扫描）
- 是否存在被篡改的依赖（版本号与官方仓库不一致）
- 依赖树中是否存在同一包的不同版本（重复依赖）

**扫描方法**：
- Node.js：`npm audit --json` 可覆盖间接依赖；`npx depcheck` 检测未使用的依赖
- 通用：读取 lock 文件，解析依赖树，交叉比对 NPM Registry / PyPI 的官方版本

**输出格式**：
| 父依赖 | 间接依赖 | 版本 | 问题 | 风险等级 |
|:---|:---|:---|:---|:---:|
| express | qs | 6.5.0 | CVE-2022-24999 原型污染 | High |
| react-scripts | lodash | 3.10.1 | 与根依赖 lodash@4.17.21 重复 | Low |

### 1.7.4 依赖供应链安全

- 检测 `scripts` 中的 `postinstall` / `preinstall` 钩子是否来自不可信依赖
- 检测依赖是否来自非官方源（如私有 registry、GitHub tarball）
- 检测 `resolutions` / `overrides` 中是否存在被强制降级的已知漏洞版本

**输出格式**：
| SEC-XXX | 检查项 | 发现 | 风险等级 |
|:---|:---|:---|:---:|
| SEC-051 | postinstall 钩子 | xxx-pkg 包含 obfuscated postinstall 脚本 | Critical |

## 1.9 多语言/多框架技术栈适配

本节提供各主流技术栈在静态审计中的等价命令和扫描模式，确保规则不因技术栈差异而失效。

### 1.9.1 技术栈识别与命令映射

AI 在 §1.1 项目特征扫描时，根据依赖配置文件识别技术栈，并按下表选择对应的审计命令：

| 技术栈 | 依赖文件 | 启动命令推断 | CVE 审计命令 | 许可证检查 | 过期依赖检查 |
|:---|:---|:---|:---|:---|:---|
| **Node.js** | `package.json` | `npm run dev` / `npm start` | `npm audit --json` | `npx license-checker --json` | `npm outdated --json` |
| **Python** | `requirements.txt` / `pyproject.toml` | `python main.py` / `flask run` / `uvicorn` | `pip-audit --format=json` 或 `safety check --json` | `pip-licenses --format=json` | `pip list --outdated --format json` |
| **Java/Maven** | `pom.xml` | `mvn spring-boot:run` | `mvn dependency-check:check` | `mvn license:check` | 读取 `pom.xml` 中 `<version>` 与 Maven Central API 比对 |
| **Java/Gradle** | `build.gradle` | `gradle bootRun` | `gradle dependencyCheckAnalyze` | `gradle licenseReport` | 读取 `build.gradle` 中 `version` 与 Maven Central API 比对 |
| **Go** | `go.mod` | `go run main.go` | `nancy sleuth -p go.sum` 或 `govulncheck -json ./...` | `go-licenses csv .` | `go list -u -m -json all` |
| **Rust** | `Cargo.toml` | `cargo run` | `cargo audit --json` | `cargo license --json` | `cargo outdated --format json` |
| **Ruby** | `Gemfile` | `bundle exec rails s` | `bundle audit --json` | `bundle exec license_finder` | `bundle outdated --parseable` |
| **PHP/Composer** | `composer.json` | `php artisan serve` / `composer start` | `composer audit --format=json` | 读取 `vendor/**/composer.json` 的 `license` 字段 | `composer outdated --format=json` |
| **.NET/C#** | `*.csproj` | `dotnet run` | `dotnet list package --vulnerable --format json` | `dotnet-project-licenses` | `dotnet list package --outdated --format json` |

> **命令不可用时的处理**：若上述命令在环境中未安装（如 `pip-audit` 未安装），在报告中标注 `依赖审计跳过：{命令} 工具未安装`，不得跳过此步骤。同时提供安装指引。

### 1.9.2 各技术栈启动命令推断规则

AI 在 §2.1.1 启动项目时，按技术栈自动推断启动命令：

| 技术栈 | 启动命令来源 | 推断优先级 |
|:---|:---|:---|
| **Node.js** | `package.json` 的 `scripts` 字段 | `dev` > `start` > `serve` > `build` |
| **Python/Flask** | 无固定文件 | 检查 `app.py` / `run.py` / `wsgi.py` → `flask run --port 5000` |
| **Python/FastAPI** | 无固定文件 | 检查 `main.py` → `uvicorn main:app --reload` |
| **Python/Django** | 无固定文件 | 检查 `manage.py` → `python manage.py runserver` |
| **Java/Spring Boot** | `pom.xml` 或 `build.gradle` | `mvn spring-boot:run` 或 `gradle bootRun` |
| **Go** | `go.mod` | 检查 `main.go` → `go run main.go` |
| **Rust** | `Cargo.toml` | `cargo run` |
| **Ruby/Rails** | `Gemfile` | `bundle exec rails server` |
| **PHP/Laravel** | `composer.json` | `php artisan serve` |
| **.NET** | `*.csproj` | `dotnet run` |

> **启动失败处理**：若推断的启动命令失败，尝试常见备用端口（如 3000 被占用时尝试 3001、8080、5000 等），并在报告中记录实际使用的端口。

### 1.9.3 各技术栈危险 API 扫描模式

§1.3.2 危险 API 调用扫描，按技术栈使用对应的正则模式：

#### Node.js / JavaScript / TypeScript
```
// XSS 注入
innerHTML\s*=|outerHTML\s*=|document\.write\(|dangerouslySetInnerHTML
// 代码注入
eval\(|new\s+Function\(|setTimeout\s*\(\s*["']|setInterval\s*\(\s*["']
// SQL 注入（字符串拼接）
["']SELECT\s+.*\+\s*["']|["']INSERT\s+.*\+\s*["']|["']UPDATE\s+.*\+\s*["']
// 命令注入
exec\s*\(|spawn\s*\(|execSync\s*\(
```

#### Python
```
# SQL 注入（字符串格式化）
cursor\.execute\s*\(\s*["'].*%s|cursor\.execute\s*\(\s*f["']|\.format\s*\(
# 命令注入
os\.system\s*\(|subprocess\.call\s*\(|subprocess\.Popen\s*\(
# 反序列化漏洞
pickle\.loads\s*\(|yaml\.load\s*\(|eval\s*\(
# 硬编码密钥
SECRET_KEY\s*=|API_KEY\s*=|PASSWORD\s*=
```

#### Java
```
// SQL 注入（字符串拼接）
Statement\.execute.*\+|PreparedStatement.*\+.*\)
// 命令注入
Runtime\.getRuntime\(\)\.exec\(|ProcessBuilder\s*\(
// 反序列化漏洞
ObjectInputStream\.readObject\(|\.readObject\s*\(
// 硬编码密钥
private\s+static\s+final\s+String\s+\w*(SECRET|KEY|PASSWORD)
```

#### Go
```
// SQL 注入（字符串拼接）
db\.Query\s*\(\s*["'].*\+|db\.Exec\s*\(\s*["'].*\+
// 命令注入
exec\.Command\s*\(|os\.Exec\s*\(
// 硬编码密钥
const\s+\w*(Secret|Key|Password)\s*=\s*["']
```

#### Rust
```
// SQL 注入（字符串拼接）
query\s*\(\s*["'].*format!|execute\s*\(\s*["'].*format!
// 命令注入
Command::new\s*\(|std::process::Command
// 硬编码密钥
const\s+\w*(SECRET|KEY|PASSWORD)\s*:\s*&str\s*=\s*["']
```

> **扫描策略**：AI 根据 §1.1 识别的技术栈，选择对应语言的正则模式执行扫描。若项目为多语言混合（如前后端分离），分别扫描各语言代码。

### 1.9.4 各技术栈依赖文件路径

| 技术栈 | 依赖文件 | Lock 文件 | 配置文件 |
|:---|:---|:---|:---|
| Node.js | `package.json` | `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` | `.npmrc` |

**禁止行为**：

- 如果某个检查项在项目中不适用（如项目没有数据库查询），标注"不适用"并跳过，不得编造发现

## 1.10 渲染-交互逻辑一致性检查

> **适用场景**：游戏、表单、工作流引擎等**状态机驱动的 UI** 项目。浏览器端渲染项目（React/Vue 等）默认执行；纯后端 API 项目标注"不适用"并跳过。

### 1.10.1 问题背景

状态机驱动的 UI 中，常存在**两套并行逻辑**控制同一组元素的交互：

1. **渲染判断函数**：决定元素在 UI 上显示为可用/禁用（如 `isCardPlayable`、`isDisabled`、`canInteract`）
2. **交互处理函数**：决定点击元素后执行什么操作（如 `handleCardClick`、`handleItemClick`）

这两套逻辑通常包含**几乎相同的 switch-case 或 if-else 分支**，覆盖所有交互状态。当新增状态时，开发者可能只更新了交互处理函数，遗漏了渲染判断函数，导致元素在 UI 上显示为禁用但交互逻辑正确——用户看到的是"无法操作"而非"操作后报错"，问题极其隐蔽。

**典型症状**：用户反馈"明明有合法操作，但按钮是灰的/卡牌不可点击"。

### 1.10.2 检测模式 A：并行 switch-case 分支不一致

**扫描目标**：同一组件文件中同时存在以下两类函数：
- 渲染判断函数（函数名匹配 `isPlayable` / `isDisabled` / `canPlay` / `canInteract` / `isClickable` / `isTargetable`）
- 交互处理函数（函数名匹配 `handleClick` / `handleCardClick` / `handleItemClick` / `handleTargetClick`）

**检测方法**：

1. 使用 Grep 搜索组件文件中的渲染判断函数定义：
   ```
   (const|function)\s+(is\w*Playable|is\w*Disabled|canPlay|canInteract|isClickable|isTargetable)
   ```

2. 在同一文件中搜索交互处理函数定义：
   ```
   (const|function)\s+(handle\w*Click|handleCardClick|handleItemClick|handleTargetClick)
   ```

3. 对同时存在两类函数的文件，分别提取两者的 switch-case 分支或 if-else 条件链，对比覆盖的状态类型：

   - 比较 switch 的 `case` 值或 if 条件中的状态标识（如 `phase`、`pendingAction.type`、`state`）
   - 若交互处理函数中有 `case 'respond_dodge'` / `case 'respond_kill'` 等分支，但渲染判断函数中缺失对应分支 → 报告 DEF-XXX

**输出格式**：

| 编号 | 文件:行号 | 渲染函数 | 交互函数 | 缺失分支 | 严重度 |
|:---|:---|:---|:---|:---|:---:|
| DEF-XXX | GameBoard.tsx:1036 | isCardPlayable | handleCardClick | respond_dodge, respond_kill, respond_peach, respond_wuxie, respond_show_card, respond_kill_or_lose | High |

### 1.10.3 检测模式 B：兜底 return false 前未穷举状态

**扫描目标**：渲染判断函数中存在兜底返回 `false` 的代码，但该兜底逻辑之前未覆盖所有已知的交互状态。

**典型模式**：
```typescript
// 危险模式：兜底 return false 前未处理响应阶段
if (gameState.phase !== 'play' || gameState.currentPlayerIndex !== 0) return false;
```

**检测方法**：

1. 搜索渲染判断函数中的 `return false` 兜底语句：
   ```
   if\s*\(.*phase\s*!==\s*['"]play['"].*\)\s*return\s*false
   ```
   或更通用的模式：
   ```
   return\s*false\s*;.*//.*兜底|return\s*false\s*;.*//.*fallback
   ```

2. 检查该兜底语句之前是否已经处理了以下状态（根据项目实际状态枚举调整）：
   - 响应/回复状态（如 `respond_dodge`、`respond_kill`、`respond_peach`）
   - 等待用户输入状态（如 `pendingAction`、`awaitingInput`）
   - 其他非空闲阶段（如 `discard`、`select`、`choose`）

3. 若存在未处理的已知状态 → 报告 DEF-XXX

**输出格式**：

| 编号 | 文件:行号 | 兜底语句 | 未覆盖的状态 | 严重度 |
|:---|:---|:---|:---|:---:|
| DEF-XXX | GameBoard.tsx:1036 | `if (phase !== 'play') return false` | pendingAction 响应阶段（respond_dodge/respond_kill/respond_peach/respond_wuxie 等） | High |

### 1.10.4 检测模式 C：同步新增状态时的遗漏风险

**扫描目标**：交互处理函数中定义的 switch-case 分支，与渲染判断函数中定义的 switch-case 分支，数量不一致。

**检测方法**：

1. 提取交互处理函数中所有 `case` 值的集合 A
2. 提取渲染判断函数中所有 `case` 值的集合 B
3. 计算 A - B（交互有但渲染没有的分支）
4. 若 A - B 非空 → 报告 DEF-XXX

**特殊情况**：若渲染判断函数没有 switch-case 而是用 if-else 链，则提取 if 条件中涉及的状态值进行比较。

### 1.10.5 定级标准

| 缺失分支的影响 | 严重度 |
|:---|:---:|
| 导致核心交互完全无法触达（如无法响应对方出牌、无法选择目标） | **High** |
| 导致非核心交互无法触达（如辅助功能、可选操作） | **Medium** |
| 仅影响视觉提示但不阻塞操作（如缺少高亮但不影响点击） | **Low** |

### 1.10.6 证据规范

所有发现必须带以下证据：
- 渲染判断函数所在文件路径 + 行号（兜底 `return false` 位置）
- 交互处理函数所在文件路径 + 行号（对应缺失分支的处理代码）
- 两个函数的 switch-case 分支差异对比（列出具体缺失的 case 值）

**禁止行为**：
- 禁止在无实际代码证据的情况下声称"可能存在不一致"
- 禁止仅凭函数名相似就报告缺陷——必须有具体的分支差异证据
- 纯后端 API 项目（无 UI 渲染逻辑）标注"不适用"并跳过

# 信号提取标准化指南（v1.0 通用版）

> **目的**：解决"不同实例对同一段简历/面试描述提取不同信号"的问题。
> **适用场景**：所有岗位，不限于 AI 岗位。
> 所有实例必须按本模板提取信号，不得自行推断或脑补。

---

## 核心原则

1. **原文引用，不做改写**：提取信号时必须引用原文，不得 paraphrase
2. **信号=事实，推断≠信号**："独立负责XX项目"是信号，"能力强"是推断
3. **缺什么标什么**：简历没提的标注"[未提及]"，不得脑补
4. **量化优先**：有数字取数字，没数字标"定性"

---

## 一、简历信号提取模板

### 提取格式

对简历中的每个相关经历，按以下结构提取：

```json
{
  "source": "原文引用",
  "signal_type": "执行|独立负责|方案设计|团队协调|流程设计|方案选型|质量标准制定|组织规划|边界定义",
  "evidence_level": "量化|定性|模糊",
  "dimension": "专业流利度|决策判断力|系统设计力|资源编排力|认知深度|问题重构能力",
  "level_indicator": "L1|L2|L3|L4|不明确",
  "confidence": "高|中|低",
  "notes": "补充说明或疑点"
}
```

### 信号分类词典（必须严格按此分类）

| 信号类型 | 定义 | 典型原文示例 | 对应级别 |
|----------|------|-------------|---------|
| 执行 | 提到完成某任务 | "负责XX功能的产品设计" | L1 |
| 独立负责 | 独立负责模块/项目 | "独立负责XX功能从需求到上线" | L2 |
| 方案设计 | 针对场景设计方案 | "设计了XX产品架构，覆盖全流程" | L2-L3 |
| 团队协调 | 协调多角色/团队 | "协调X个部门完成XX项目" | L2-L3 |
| 流程设计 | 为团队设计流程/规范 | "设计团队需求评审和验收标准" | L3 |
| 方案选型 | 评估对比多个方案并给出依据 | "评估了A/B/C三种方案，选定最优方案" | L3 |
| 质量标准制定 | 为产出制定验收标准 | "制定团队质量标准和验收流程" | L3 |
| 组织规划 | 制定组织级规划/政策 | "制定部门XX能力3年规划" | L4 |
| 边界定义 | 明确定义该做/不该做的事 | "定义XX应用边界红线" | L4 |
| 问题重构 | 发现真问题，重新定义 | "以为是X问题，其实是Y问题" | L3 |
| 从0定义 | 从0设计全新方向/模式 | "重新设计了整个业务流程" | L4 |

### 模糊描述处理规则

| 模糊描述 | 处理方式 | 理由 |
|----------|---------|------|
| "负责XX项目" | 记为"执行(L1)"，不得推断更高级别 | 无独立负责/设计证据 |
| "主导XX项目" | 必须追问：具体做了什么？团队规模？否则降级 | "主导"≠"架构设计" |
| "提升X%" | 必须找基线数据，找不到标"定量无基线" | 无基线的量化=无效量化 |
| "熟悉多种工具/技术" | 记为"执行(L1)"，不得因数量多升级 | 工具数量≠能力深度 |
| "参与XX相关工作" | 标注"角色不明确"，降级处理 | 参与≠主导 |

## 二、面试记录信号提取模板

### 提取格式

对面试中的每个相关回答，按以下结构提取：

```json
{
  "question": "面试官问题",
  "answer": "候选人回答原文",
  "signal_type": "同上",
  "cognitive_signals": {
    "tradeoff_awareness": "有|无|模糊",
    "debug_experience": "有|无|未提及",
    "underlying_mechanism": "有|无|未提及",
    "reflection_evidence": "有|无|未提及"
  },
  "confidence": "高|中|低",
  "notes": "矛盾点/亮点/疑点"
}
```

### 认知信号判定规则

| 认知维度 | 有（记为+） | 无/模糊（记为-） |
|---------|------------|----------------|
| tradeoff_awareness | 能说出方案A和方案B的利弊及选择理由 | 只说"选了A"不说为什么没选B |
| debug_experience | 能描述出错的场景及修复过程 | "没遇到什么问题"或跳过不说 |
| underlying_mechanism | 能解释为什么某个方案有效 | "就是这么做的，效果好" |
| reflection_evidence | 总结了经验教训/沉淀了方法论 | 只讲做了什么，不讲学到了什么 |

### 面试回答分级规则

| 回答特征 | 判定 | 示例 |
|---------|------|------|
| 只讲结果不讲过程 | 降权，最多 L2 | "效果很好，提升了300%" |
| 能讲过程但无 tradeoff | L2 | "我做了A，接了B，做了C" |
| 能讲 tradeoff 和取舍 | L3 | "考虑了A和B，最终选A因为..." |
| 能讲系统级影响和组织级思考 | L4 | "这不只是执行问题，还涉及团队能力转型..." |

## 三、信号到分数的强制映射（P0 铁律）

**铁律：以下映射是单向的。提取到的信号自动映射到对应维度分数，不得凭感觉覆盖。**

### 信号→分数映射表

| 信号类型 | 最低分 | 最高分 | 升级条件 |
|---------|--------|--------|---------|
| 执行 × N个任务（无迭代证据） | L1 | L1 | 不得升级 |
| 执行 + 有量化产出 | L1 | L1.5 | 升级到 L2 需要至少 1 条独立负责信号 |
| 独立负责（有量化基线） | L2 | L2.5 | 升级到 L3 需要至少 1 条流程设计信号 |
| 独立负责（无量化） | L1.5 | L2 | — |
| 方案设计 | L2 | L2.5 | — |
| 团队协调（2-3个角色） | L2 | L2.5 | — |
| 流程设计（团队级） | L3 | L3.5 | 升级到 L4 需要组织规划或边界定义信号 |
| 方案选型（有对比分析） | L3 | L3 | — |
| 方案选型（只说"选了A"） | L2 | L2.5 | — |
| 质量标准制定 | L3 | L3 | — |
| 组织规划 | L3.5 | L4 | — |
| 边界定义 | L4 | L4 | — |
| 问题重构 | L3 | L3 | — |
| 从0定义 | L3.5 | L4 | — |

### 执行规则

1. 先按本文件提取所有信号（原文引用，不得 paraphrase）
2. 对每个维度，找出该维度对应的**最高级别信号**
3. 该最高信号对应的分数 = 该维度的**初始分数**
4. 如果同一维度有多个独立信号（≥2条），可向上微调 ≤0.5
5. **最终分数不得高于最高信号对应的分数 + 0.5**
6. 如果某维度没有任何信号 → 标注"[未提及]"，**不得强行打分**

### 反模式（禁止）

| 反模式 | 正确做法 |
|--------|---------|
| "用了3个工具" → 推断 L2+ | 必须有独立负责或方案设计证据 |
| "效率提升80%" → 直接采信为 L3 | 必须追问基线和测量方法，无基线 → L1.5 |
| "主导项目" → 默认架构师 L3 | 必须确认团队规模和技术决策权，否则 L2 |
| 面试说"效果很好" → 视为有效证据 | 必须要求具体案例和数据 |
| 简历很长 → 推断能力强 | 长简历可能 AI 生成，必须过漏洞审计 |

## 四、交叉验证规则

简历信号和面试信号必须交叉比对：

| 场景 | 处理 |
|------|------|
| 简历写 L3 能力，面试只能讲到 L2 | 以面试为准，简历降权 |
| 面试表现 L3，但简历无对应项目 | 标注"待验证"，要求提供项目证据 |
| 简历和面试信号一致 | 信心标注为"高" |
| 两者矛盾 | 启动矛盾检测（参考 cognitive_review.md） |

---

## 五、信心度计算规则

每个维度的信心度由以下因素决定：

| 因素 | 权重 | 高分条件 |
|------|------|---------|
| 证据数量 | 30% | ≥3 条独立证据 |
| 证据一致性 | 30% | 简历和面试信号指向同一级别 |
| 量化程度 | 20% | 有基线数据/可验证指标 |
| 认知深度 | 20% | 能过 tradeoff/debug/底层机制检查 |

**信心度阈值**：
- 高：加权得分 ≥ 0.7
- 中：加权得分 0.4-0.7
- 低：加权得分 < 0.4 → 必须标注"证据不足，建议补充面试"

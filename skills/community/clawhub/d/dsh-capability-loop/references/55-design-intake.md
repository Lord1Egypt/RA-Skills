# 55 · 设计前置：先读懂现有系统，再出稿（Design Intake）

> 硬规则：**出任何设计稿 / 原型 / 改版方案之前，必须产出 `design-context.md`。**
> 理由：直接出稿 = 另造一套主题与组件，交付后必然返工；生产级设计要求「长在现有系统上」。
> 小改可用**最小集**（§2 的 1/2/5/6/7 五项），中大改必须全量。

## 1. 动态判断清单（每项都要证据，不许凭想象）

| # | 判断什么 | 证据形式 | 常见错误 |
|---|---|---|---|
| 1 | UI 框架与组件库及版本 | `package.json` 依赖 + 实际使用路径 | 用 Element 的语言写 antd 的页面 |
| 2 | 主题与 token：主色/色板/间距/字号/圆角/阴影/暗色 | theme 文件、CSS 变量、`chart-theme`、组件默认值 | 自造 6 种间距、4 种圆角 |
| 3 | 布局骨架：侧栏/顶栏/页签/面包屑/内容容器/全屏 | 布局组件路径 + 1 张截图 | 新页面换一套导航 |
| 4 | 数据密集规范：表格密度、数字精度/单位/时区、图表规范 | 现有报表页 + echarts theme / 格式化函数 | 金额不带单位、时间用本地时区 |
| 5 | 状态与交互：loading/empty/error/无权限/危险操作二次确认 | 现有页面样本 + 组件 props | 只画「有数据」的成功态 |
| 6 | 现有页面样本（3 个代表页：列表/表单/看板） | 截图或代码路径 | 只看一张旧图就开始改 |
| 7 | 设计稿来源与母版：Figma/蓝湖/无 | 链接或「以现有系统为准」 | 无母版时仍假设像素级还原 |
| 8 | 品牌与合规约束：字体、字号下限、暗色、无障碍、审计留痕 | 设计规范/合规要求 | 忽略对比度与触控尺寸 |

**采集方式**：
1. 先跑 `scripts/product-context.ps1 -Project <仓库>` 自动扫技术栈/组件库/主题线索/页面规模；
2. 再人工核对（读 theme/布局/样本页，或请用户给截图）；
3. 差异项登记「要改哪些既有约定、为什么、影响面」。

`product-context.ps1` 只给线索，**不能替代**人工确认；自动扫描看不到「业务上为什么这样设计」。

## 2. 默认判断顺序（冲突时按此优先级）

```
现有组件库/设计系统 > 项目既有页面惯例 > 行业惯例 > 通用设计规范 > 个人审美
```

如果第 1 项本身有问题（如对比度不达标、组件库版本过旧），**先记差异与风险**，再决定是否在本期修正；不允许悄悄另起一套。

## 3. 产物：`design-context.md`（模板 `templates/design-context.md`）

必须包含：技术栈与组件库、主题与 token 实测值、布局骨架、数据规范、状态清单、样本页路径、设计稿来源、差异清单（含影响面与建议）、待确认 D-ID。
落盘：任务目录或 `docs/design/design-context.md`。

## 4. 门禁与衔接

- `loop-gate.ps1 -TaskDir <目录>` 的 design 类别**默认要求存在 `design-context*.md`**；缺失 → FAIL（小改也要最小集）。确实不需要时用 `-AllowMissingDesignContext` 显式跳过并写理由。
- 产出 `design-context.md` 后，才进入 `ui-design-production` 的 8 步工作流（brief → IA → token → 组件状态 → 响应式 → 无障碍 → 性能 → 视觉 QA）。
- 设计 token 要**对齐现有主题**（在现有 token 上扩展，而不是全部重定义）；扩展必须写明「新增/覆盖/沿用」。
- 评审时 Reviewer 先核对 `design-context.md` 与最终稿是否一致，再按 rubric 打分（`50-design-team.md`）。

## 5. 反模式

- ❌ 用户说「改个页面」就直接出视觉稿 → 先给 5 项最小上下文（框架/主色/间距/状态/样本页）；
- ❌ 把「设计系统」理解成「我要新建一套 token」→ 先找现有 token；
- ❌ 只画成功态、正常数据 → 必须给空态/错误/超长/无权限/暗色；
- ❌ 用截图当唯一证据 → 截图 + 代码/类名/token 值一起给；
- ❌ 设计稿与现有组件库冲突却不说明 → 差异清单里必须写清「为什么不用现有组件」。

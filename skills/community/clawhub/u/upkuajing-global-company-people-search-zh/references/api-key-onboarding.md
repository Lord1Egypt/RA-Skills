# API Key 状态检查与余额流程

在执行任何收费查询前，必须完成状态检查。先依据本地和接口结果判断实际状态，再只询问用户需要处理的问题；不要先要求用户自行判断是否有 API Key、是否绑定或余额是否可用。

## 1. 必要时介绍能力

首次启用技能，或当前对话尚未介绍过能力时，用简短自然语言告诉用户：本技能可以搜索全球公司和企业决策人，获取公司/人物详情及邮箱、电话、WhatsApp 等联系方式；查询接口会产生费用，需要有效的 API Key 和可用余额。

介绍时同时提供 API 能力与价格平台：

**https://developer.upkuajing.com/openapi/**

告诉用户可在该页面查看各接口的最新能力和价格。实际收费确认仍必须运行 `python scripts/auth.py --price_info` 获取实时价格，不能只依赖页面或文档中的历史数字。当前对话已经完成介绍时不重复整段介绍。

## 2. 先检查 API Key 并报告结果

运行：

```bash
python scripts/auth.py --key_status
```

如果当前环境只有 `python3`，使用 `python3`。这一步在询问用户账号情况之前执行。必须把检测结果明确告诉用户：

- 是否检测到 API Key；
- API Key 是否有效；
- 只展示脱敏 Key，不得在对话中展示完整 Key；
- Key 是否绑定跨境魔方账号；
- API 余额和跨境魔方账号余额；
- 实际扣款顺序与是否需要充值。

## 3. 根据检测状态继续

### 未检测到 API Key

告知用户未检测到 Key，此时才询问是否已有跨境魔方账号：

- 没有账号：询问是否允许自动生成独立 API Key。用户确认后运行 `auth.py --new_key`，再运行 `--key_status`。独立 Key 的费用只从 API 余额扣除。
- 已有账号：询问是否允许生成 Key。生成后提供绑定入口，让用户登录并在“API Key 管理”中完成绑定，然后重新运行 `--key_status`。

### 检测到 API Key，但验证失败

报告脱敏 Key、来源和服务端错误。询问用户要更换现有 Key，还是在清理无效配置后生成新 Key。不得覆盖或删除现有配置，除非用户明确授权。处理后重新运行 `--key_status`。

### Key 有效但未绑定账号

明确告诉用户这是可独立使用的 API Key，只有 API 余额可支付查询费用。此时再询问用户是否已有跨境魔方账号：

- 用户有账号并希望使用账号余额：提供绑定入口，等待绑定完成后复查；
- 用户没有账号，或选择继续使用独立 Key：只要 API 余额足够即可进入查询，不强制绑定。

绑定入口：

**https://developer.upkuajing.com/account/**

用户确认绑定完成后，重新运行 `--key_status`；未验证绑定成功前不得声称已绑定。

### Key 有效且已绑定账号

直接报告绑定状态、API 余额、账号余额和扣款顺序。脚本已经确认的状态不再要求用户回答。只要余额足够，即可进入需求准备度判断。

## 4. 双余额与扣款顺序

对于已绑定跨境魔方账号的 API Key，同时报告：

- API 余额；
- 跨境魔方账号余额；
- 扣款顺序：**先扣 API 余额，API 余额不足后再扣跨境魔方账号余额**。

必须根据实际情况向用户解释：

- API 余额为 0、账号余额大于 0：不需要仅因 API 余额为 0 而充值，查询费用从账号余额扣除。
- API 余额不足、账号余额可以补足预计费用：可以继续，先用完 API 余额，再从账号余额扣除不足部分。
- API 余额大于 0、账号余额为 0：先使用 API 余额；API 余额耗尽后需要充值。
- 两项余额都为 0，或两项合计不足以支付用户确认的查询：提醒充值，不执行收费查询。

对于未绑定账号的独立 API Key，只有 API 余额可以支付查询费用。

## 5. 充值闭环

余额不足时，运行 `auth.py --new_rec_order` 获取服务端返回的支付页面，并把支付链接提供给用户。也可提供官方充值中心：

**https://developer.upkuajing.com/recharge.html**

提供链接后停止，等待用户明确表示充值完成。随后重新运行 `--key_status`，向用户报告最新两项余额；只有余额足够且用户已确认具体收费查询时，才能进入搜索。

## 6. 查询前最终状态

进入查询前必须确认：

1. API Key 已存在且有效；
2. 账号绑定状态已明确并已告诉用户；
3. API 余额和账号余额已告诉用户；
4. 扣款顺序已告诉用户；
5. 只处理了检测结果所需要的账号、绑定或充值问题；
6. 可用余额足以支持下一项待确认的收费操作。

本地脚本只携带 API Key 请求服务端，实际扣款由服务端执行。脚本展示的扣款顺序是业务规则；查询响应中的单一 `accountBalance` 不能替代查询前后的双余额复查。

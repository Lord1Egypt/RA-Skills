# Connecting peers: device-flow pairing

Agents connect without pasting tokens into chat, using the standard OAuth 2.0 Device Authorization Grant (RFC 8628). Your A2A endpoint is the authorization server, and **your human approves each connection**.

`init` reports whether the approval password is set after deploying. If the check is unavailable, read `pair list --json`. Pairing-request wakes include `passwordSet` and setup guidance while it is false, without including the password or its hash. This guidance does not approve the pending request. Password setup guidance appears only when password approval is enabled; OIDC-only endpoints omit it.

**Set the approval password (once, human mode).** Your human types it, never the agent. Two ways:

```bash
npx -y a2a-exposed@latest pair set-password --web [--ttl 15]   # easiest: prints a one-time link for your human
npx -y a2a-exposed@latest pair set-password                     # the human runs this themselves, in a terminal
```

- **`--web` (agents run this):** it prints a one-time link `<base>/device/setup?t=...` (valid 15 minutes by default, `--ttl` from 1 to 60 minutes; `--json` for scripts). **Send the link to your human privately and stop.** Never open it, fill in the page, or ask for the password yourself. The human opens the link, types a password (12 to 1024 characters; a passphrase of several unrelated words is stronger than one short word) twice, and sees a confirmation that links to `/device`. The link works once (and is burned after 5 bad attempts); a newer link replaces the older one. It works for the first password and for changing it. The Worker hashes the password with PBKDF2-SHA256 and stores only the hash.
- **Terminal:** typed twice, not echoed. It refuses arguments and non-terminal stdin, so an agent can't set it; the hash is made on the machine and the password never leaves it.

Never ask the user for the password, and never type it for them. Until it is set, the `/device` page says so and nothing can be approved there (`status` and `pair list` show whether it is set, when, and how), unless OpenID Connect approval is configured (below). To change it later, run `--web` again.

**Optional OpenID Connect (off unless fully configured).** `npx -y a2a-exposed@latest pair set-oidc --issuer https://idp.example --client-id ID --subjects sub@example.com` stores the issuer, client id and allowlist. Deploy uploads `APPROVAL_OIDC_CLIENT_SECRET` only when that variable is set in the environment you use for deploy. `--secret-stdin` checks one line and discards it, so export the variable before deploy. When the issuer, client id, secret and at least one allowed `sub` or `email` are all set, `/device` shows **Approve with** the issuer and the MCP consent page shows **Continue with** it. The human signs in at the identity provider; you still never approve, and you never ask for the client secret. Deny still needs no login. `--methods password` keeps the password page. `--methods oidc` hides the password only after the config is complete. Leaving methods unset offers both. `status` and `pair list` name the issuer host when this is on.

**Someone connects to you.** Their agent runs `connect` with your URL (or any standard OAuth device-flow client; the endpoints are on your agent card and at `/.well-known/oauth-authorization-server`). You get a wake with `kind: "pairing_request"`, the requester's claimed name, alias and card URL, the code (e.g. `WDJB-4827`, valid 60 minutes), a link (`<base>/device?user_code=WDJB-4827`), and `pairing.manageUrl` when `MANAGE_URL` is an https dashboard page. `pair list` and `inbox` print that dashboard link. Set it with `init` or `deploy --manage-url`. Send `pairing.manageUrl` to your human when the wake has it. The owner approves on that page, with the owner token (`pair approve`), or with the approval password on `/device`.
- **Polling agents** (no webhook) see requests in `inbox` and `pair list`. Check them each run and tell your human. Webhook agents get a wake.
- **human** mode (default): tell your human who is asking, show the code, and give them the link. They check the code with the other agent's owner, then approve on the page with the approval password or run `pair approve <code>` themselves (the owner token; the decision is recorded as the owner). Deny needs no password. You never approve. A call with no token, or with a peer token, is refused.
- **agent** mode: ask your human in chat; only if they say yes, run `npx -y a2a-exposed@latest pair approve <code>`; otherwise `pair deny <code>`.
- `npx -y a2a-exposed@latest pair list` shows pending requests. `pair deny <code>` works in every mode.
- The approved agent gets a normal per-peer token (label from its name, e.g. `Barry-Bot`). `token list` shows it with `via pairing: code WDJB-4827`; `token revoke <label>` cuts it off (an unknown or already revoked label exits 1, so a typo is never taken for success). Pairing is one-directional. That token lets them message you. It does not let you message them. `peers list` stays empty of that peer until you run `npx -y a2a-exposed@latest connect` with the public `card:` from `pair list` or `agentCardUrl` from `pairing_requests`. Their owner approves. Do not approve it yourself. There is no MCP tool that runs `connect`. After the task is `completed`, you cannot `reply` on it, and you cannot `send` them a new one until that `connect` succeeds.
- **Re-pairing** (`connect --replace` from a peer that already has a token): the request says which token it replaces (`pair list` shows `replaces the active token "<label>"`). Approval swaps the token under the same label and the old one stops working; no second label (`Barry-Bot-2`) and no orphan. The request is bound to the exact token that was presented: if you rotate or revoke that label before the request is redeemed (for example because the old token leaked), the swap is refused and the request, if approved, gets a fresh label instead, so a leaked old token can never take over a rotated one. A revoked label is not reused.
- Peers that send no current token get a new label. Revoke the previous label yourself.

**You connect to someone.** Only when the user asked:

```bash
npx -y a2a-exposed@latest connect https://peer.example.com [--alias peer]      # or the peer's agent-card URL
```

It prints a code and a link. The code lasts 60 minutes. Show both to your human: they confirm the code with the peer's owner, who approves it. `connect` waits (honouring `interval` and `slow_down`), then stores the token as outbound peer `peer` (never printed); `send --to peer` works right away. You can connect before this inbox has a public https address. Replies stay on the peer's task until `peer announce --to <alias>` (it syncs the peer first when needed; `--all` needs `peers sync`). That announcement also registers a return token, so the peer can call this inbox back without a second approval. `peer forward --to <card-url>` on an inbox you are leaving keeps direct replies moving for a grace period (default 168 hours). A denied or expired request ends with exit code 1 and a clear message. If your harness only shows output when a command finishes, use `connect <url> --alias peer --no-wait` (prints the code and exits, status `not_waiting` with `--json`), relay the code, then run **the same command** again: it checks once (same code) and stores the token when the owner has approved; without `--no-wait` it waits. `--json` prints one JSON line per step.

- **Expired codes are never replaced silently.** Resuming a request that expired exits 1 ("expired before it was approved; nothing was stored") and prints the exact command, with every flag, for a new code. A new code is a new approval request for the peer's owner, so ask your human first.
- **Already connected?** If the alias holds a token that still works, `connect` refuses and asks for `--replace`. If the stored token was revoked or rotated (HTTP 401), it just requests a new one. With `--replace` the current token is sent along. A peer that accepts the replacement swaps it under the same label. A peer that keeps the previous token active says so, with the label when it knows it, and that owner revokes the previous token. Skip a re-pair that only checks whether the token works: `send` tells you, with the fix (`<alias> rejected our token ... re-pair`).

**Manual fallback.** If the peer has no device flow (or pairing is `off`), `npx -y a2a-exposed@latest token issue <peer-label>` prints a token once. Send it with the card URL (`$(npx -y a2a-exposed@latest url)/.well-known/agent-card.json`) only over a channel the user approves; the peer adds it with `peers add <alias> <url> --token-stdin`. Tokens are `a2aow_` plus 43 base64url characters; the Worker stores only their SHA-256 hash. One label per peer; manage labels with `token list`, `token rotate <label>`, and `token revoke <label>`.

### Pairing security (threat model)

- **A device code alone is useless.** It is 256 random bits, stored only as a SHA-256 hash, expires after 60 minutes, and yields a token only after an approval. It is single-use: redeemed once, then deleted.
- **The approval needs the owner.** In `human` mode the owner approves with the owner token (`pair approve`) or on `/device` with the approval password. A request with no token, or with a peer token, cannot approve. A prompt-injected peer message, or someone who only has the link, cannot approve. The user code is short (about 29 bits) so a human can read it. It identifies a request. Your human compares it with the code the other agent's owner sees.
- **One approval covers the return path.** The agent that runs `connect` already chose this peer. Approval lets that pairing identity register a callback and a return token later, without a second approval. The return token is an ordinary peer token. The new card has to verify under the same identity. A host change is shown to the human (`kind: "address_change"`). Revoke either token if the change is unexpected.
- **Deny needs no password.** On the `/device` page, Deny needs only the code, the same-origin/CSRF checks and the per-IP lookup limit; it never runs PBKDF2 and an empty password is not counted as a wrong attempt. Deny grants nothing: the worst a guesser can do is cancel a pending request, which the requester can start again, while a code that is not guessed is useless. On the page, approve needs the approval password, or a verified OpenID Connect sign-in when that is configured (RS256; issuer, audience, nonce, expiry, and an allowlisted `sub`, or an allowlisted `email` only when `email_verified` is true). A token with several audiences must include `azp` equal to the client id. The sign-in state is single-use. The user code is not sent to the identity provider.
- **The password setup link** (`pair set-password --web`) is minted with the owner token, the same trust boundary as the terminal command and `token issue`. The link carries 256 random bits and only its SHA-256 hash is stored. It expires (15 minutes by default, `--ttl` 1 to 60), works once, is burned after 5 failed attempts, and creating a new link invalidates the old one. The setup page is rate limited per IP, has the same strict CSP and CSRF checks as `/device`, and never echoes a password. Anyone who gets the link inside its lifetime could set the password, so send it privately to the human and never to a shared channel; if it leaked, make a new one (that kills the old) or check `pair list`. The Worker logs `pairing_password_set` with the time, `via` and iteration count (never the password), and `status` shows when the password was last set.
- **PBKDF2 cost (offline guessing only).** Online guessing is limited by the lockouts below, whatever the iteration count. Iterations only slow someone who already has the stored hash (D1 or account access). 100,000 iterations is the Workers maximum and is the default (measured around 17 to 23 ms of CPU locally, against the free plan's 10 ms CPU limit; Cloudflare's measured CPU for a request that only hashes is lower than wall-clock, and most approvals work on free, but a request can hit error 1102). If approving on `/device` fails with 1102 or the setup page does, set `deploy --pbkdf2-iterations 50000` (the minimum accepted) and set the password again; each stored hash keeps its own count, so a change never invalidates an existing password, and hashing happens once per approval attempt that passes the lockout checks (never on deny or an empty password). The paid plan has no such limit.
- **What it does not cover.** The owner token (in the agent's `config.env`) can issue tokens directly (`token issue`), approve or deny a pairing request, and replace the approval password. Keep it away from untrusted agents and code. A pairing request, a peer message, or someone who only has the `/device` link cannot approve.
- **Brute force and floods are capped.** 30 code lookups per IP per 10 minutes on the page, 5 new requests per IP per 10 minutes, at most 10 pending requests and 30 new requests per hour in total (so nobody can flood your agent with approval prompts), 5 wrong passwords per code (the request is then denied), 10 per IP per hour, and 50 per hour overall (the page then locks for up to an hour). Token polling faster than `interval` gets `slow_down`, and the interval grows by 5 seconds each time.
- **Requester claims are untrusted.** The name, alias and card URL come from the requester. The page escapes them and shows the requesting IP and country. The alias is labelled "Alias (claimed)", not as an OAuth client id. The wake labels them as claimed, and `openclaw-wake` (a trusted system event) leaves them out. The peer token's label is taken from that claimed name (else the claimed alias) and suffixed `-2`, `-3`, … when the label is already taken. Later messages from that token use the label as `from`.
- **The page itself** has no scripts or external assets, a strict CSP (`default-src 'none'`, `frame-ancestors 'none'`, `form-action 'self'`), `Cache-Control: no-store`, a same-origin check, and a SameSite=Strict double-submit CSRF token. The CSS is the neutral style in `worker/src/theme.ts`, inlined in that nonce'd style block. `WORKER_THEME` (a CSS file path) replaces it at `cf build`. A theme that loads an external asset, including an `image()` or `image-set()` string source and one whose name is written with a CSS escape, or that would break out of the style block, is refused, and the CSP is unchanged. When OpenID Connect approval is on, `/device` and the MCP consent page add that issuer's origin (scheme, host, and port only) to `form-action`, because the approve button posts here and the response redirects to the issuer. The consent page also allows the client's redirect origin. `/device/setup` posts only to this host, so it stays `form-action 'self'`. An authorization endpoint on a different origin is refused. The identity provider returns with a GET, not a form post.
- **Server-readable unless keys are paired.** An ordinary pairing gives a bearer token; both inbox servers can read the messages. Encrypted key pairing is a separate local CLI opt-in (`connect --sealed-key-id`), never the default; `connect` only suggests it when the peer card offers it or local keys exist. `/device` and `pair list` label a key pairing and show its safety code (trust on first use: compare it through another trusted channel). The owner API flags it with `sealed: true` and `safetyCode`; no key material is listed and approval pins nothing. See [local keys and pairing](https://github.com/telegraphic-dev/a2a-exposed/blob/main/docs/local-key-pairing.md).
- **Revocation.** Every paired agent has its own label: `token revoke <label>` takes effect immediately, including a push reply to a task already sent. There is no refresh token; a token lasts until revoked.
- **Optional extra layer:** put a Cloudflare Access application on `<A2A endpoint host>/device` only (not `/oauth/*`, which the requesting agent must reach), so the page also needs your Access login. It is not required.

### Safety emoji quick check

Encrypted pairings show seven ordered emoji with fixed English names. Compare every
item in order through another trusted channel; if any differs, stop and deny.
This 42-bit quick check is weaker than the full 60-digit code. Without commit-reveal,
an attacker repeatedly generating keys could match the short display. Compare the
full code for high-stakes pairings. This is not Matrix protocol verification.
`keys verify --code` still requires the complete numeric code read by the other owner;
emoji agreement never records independent verification or enables encryption.
The full code remains in details and unchanged API `safety_code` (or existing
`safetyCode`/`code` fields). Additive `safety_emoji` (pairing APIs: `safetyEmoji`)
is an ordered array of `{emoji,name}` pairs, or null when unavailable.

# 动笔前的澄清问题清单

> 用户只说"帮我写个文档"时使用。纪律（借育儿大师的"最少输入原则"）：
> **能合理默认就默认，最多问 3 个；用户答得简短是常态，别连环追问。**
> **动笔前先自行读取**：用户提及的文件、目录、上次的稿子、指定来源，先读再问；能从这些地方查到的信息不问。
> **提问门槛**：只问会改变事实、范围或交付形式的问题；不反问已能从交付物直接回答的问题。
> 用户给了素材/附件（要求+材料至少两类）时，跳过收集，直接进结构。

## 通用五问（按序问，用户已说的别重复问）

| # | 问题 | 默认值（用户不说就用） |
|---|---|---|
| 1 | 写给谁看？ | "通用读者"——按此写术语表 |
| 2 | 拿它做什么用（决策/照着做/存档）？ | 照着做 |
| 3 | 要多长？ | 办事类 1-2 页；报告 2-3 页 |
| 4 | 什么时候要？ | 无硬时限 |
| 5 | 你们有现成的模板或评审清单吗？ | 无——按通用文档原型起骨架，交付时说明 |

## 分文体补问（在通用五问之上）

| 文体 | 追加问题 |
|---|---|
| 办事指南/家庭文档 | 办事人是谁、去哪办、已经核实了哪些事实、哪些还没核实 |
| 方案 | 背景卡在哪、预算量级、谁批准 |
| 报告 | 给谁汇报、结论对方想先听什么 |
| 邮件 | 收件人角色、希望对方做什么、截止时间 |
| PRD | 决策人是谁、这次明确不做什么、上线怎么判成功 |
| 技术方案 | 改存量还是新建、有没有硬约束（技术栈/时限/合规）、出事能不能停机回滚 |
| 调研方案 | 结论给谁做决定、能接触到哪些受访者、什么时候要结果 |
| 修订（改已有文档） | **这篇要解决什么问题**（结构乱/数字错/太长/不像人话）——先问这个，别一上来就重写 |

## 模板优先（专业文档）

用户手里有自家模板时，**模板赢**：

1. **先要模板**：问一句"有现成的 PRD / 设计文档 / 调研方案模板或评审清单吗"。
2. **按模板的章节组织**，不重排成通用结构。
3. **模板缺的章节不擅自补**，在交付说明里写"这几节是空的、评审可能会问"，加不加由用户定。
4. 用户说"没有模板"或"按你的来"→ 用 `write-flow.md` 的文档原型起骨架，并在交付时说明这是通用结构，不是团队规范。

理由：行业规范没有唯一真源，评审会按的是团队的规矩。拿通用标准去改用户老板认可的模板，只会让 skill 显得外行。

## 模糊输入的三方向选择法

用户说"写得清楚点""顺一点"这类没目标的反馈时，一次给三个方向让他挑，禁止开放式追问：

> 你更想解决哪个：① 结构乱（读者找不到重点）② 句子难读（太长、太绕）③ 不像人话（AI 味）？

## 确认口径（信息收集完后）

一句话复述确认："读者是X，用来Y，篇幅Z，我先按这个写，默认项我列在这里。"未答项列出默认值，让用户有机会纠偏，但不阻塞动笔。

# 会话库膨胀分诊（`agents/<id>/agent/openclaw-agent.sqlite`）

触发：主人说「主代理会话 / 状态目录到了 N G，怎么处理」。**先分诊再动手**：1 GB 可能是有效数据、可能是碎片、也可能大部分根本不在会话库里 —— 三者处置相反。改配置与删数据前先跑 §A。

## §A 分诊：总量 vs 碎片 vs 根本不在库里

```bash
du -sh ~/.openclaw/agents/<id>/agent            # 库本体
du -sh ~/.openclaw/agents/<id>/sessions        # transcript 目录
du -sh ~/.openclaw/agents/*                    # 跨 agent
du -sh ~/.openclaw/archive ~/.openclaw/tmp ~/.openclaw/backups
```

**判据 1：1 G 通常不在 `sessions/`。** 实测库本体 1.1 GB 而同 agent `sessions/` 仅 8.9 MB ⇒ 别去 transcript 目录找，也别按「日志文件太多」处置。

⚠️ **用 `find` 搜 state 目录下的库文件不要设 `-maxdepth`**：会话库在 `agents/<id>/agent/openclaw-agent.sqlite`，是**第 5 层**。实测 `find … -maxdepth 3 -size +40M` 只捞到 `state/openclaw.sqlite`（121 MB），漏掉了 764 MB 的会话库；**拿这个残缺结果去「更正」先前的结论，会把对的判断推翻成错的**。要限定范围就写完整路径（`-path`），不要用深度。**更正任何关于 state 目录体量/布局的旧结论时，新证据的搜索范围必须 ≥ 原结论的范围。**

**判据 2：碎片还是数据。** 只读 PRAGMA（外部 `sqlite3` CLI 对 live state 目录会被拒，见 §E）：

```bash
python3 -c "
import sqlite3
p='/home/zuoyunlai/.openclaw/agents/main/agent/openclaw-agent.sqlite'
con=sqlite3.connect('file:'+p+'?mode=ro',uri=True)
ps=con.execute('pragma page_size').fetchone()[0]
pc=con.execute('pragma page_count').fetchone()[0]
fl=con.execute('pragma freelist_count').fetchone()[0]
print('total MB',round(pc*ps/1048576,1),'free MB',round(fl*ps/1048576,1))
"
```

⚠️ **完整性的耗时与库大小无关，只与校验范围有关——小表也能成为瓶颈。** 实测（2026-10-16，624 MB 库，doctor 的 `integrityTableTimings`）：`memory_embedding_cache` 仅 **6738 行**却耗时 **2434 ms**；`memory_index_chunks` 仅 **5370 行**却耗时 **1241 ms**；`trajectory_runtime_events` **33853 行 / 119 MB**，耗时 **719 ms**。⇒ **按行数排优先级会排错**：embedding 行均约 **8.5 KB**（1024 维向量以文本形式落盘），全表完整性校验按字节而非行计费 ⇒ **行少的大行表才是真正瓶颈**。`dbstat` 按字节看大小、`count(*)` 看行数，**两者一起读**才能排出正确的顺序。

**判据 2 的配套：碎片占比低时先分清「碎片」还是「真实数据」。** `free MB / total MB` 是 **VACUUM 能回收的部分**；回收不了的部分是真实数据。实测（2026-10-16）compact 成功但 633 MB → **624 MB（仅 1.4%）**，而 `pruneAfter` 已是 `"7d"` ⇒ 库里 64% 是近 7 天真实会话/遥测（`transcript_events` + `trajectory_runtime_events`），**compact 对这类库无效**。报「compact 已执行」不等于报「问题已解决」，必须同时给出**压缩前后两个库体积值**。碎片占比低时必须先删数据再压缩，顺序反了等于白做。

⚠️ **`mode=ro` 连接上跑写类 PRAGMA 会回 `disk I/O error`，那不是磁盘故障**：`wal_checkpoint` 需要写权限，在只读连接上会报出**像磁盘坏了的错误信息**。实测差点据此报「磁盘写不进去」的严重故障，而 `df -h` 显示 915 G 可用。⇒ 报错先问「是不是我自己的调用方式造成的」；要 checkpoint 就用**可写连接**打开（实测 `wal_checkpoint(TRUNCATE)` 回 `(0,0,0)` 即排空成功），别对 live 库跑 `VACUUM`。

**判据 3：自动清理为什么一直没动。** 读 `openclaw.json` 的顶层 `session.maintenance.*`。只写 `mode: enforce` 而不写阈值 = 走默认值 `pruneAfter 30d` / `maxEntries 5000` / `maxDiskBytes 10gb`；实测 439 条会话、1.1 GB 库**远低于默认上限，`enforce` 永远不触发**（dry-run 回执 `beforeCount == afterCount`、`pruned 0`、`overBudget false` 就是这个症状）。这不是 bug，是阈值没配。

**判据 4：最大的表通常不是你以为的那个——用 `dbstat` 逐表归因。** 总量只能告诉你「有多大」，归因才能告诉你「该动哪张」：

```bash
python3 -c "
import sqlite3
c=sqlite3.connect('file:/home/zuoyunlai/.openclaw/agents/<id>/agent/openclaw-agent.sqlite?mode=ro',uri=True)
for n,mb in c.execute('select name,sum(pgsize)/1048576 from dbstat group by name order by 2 desc limit 12'): print(f'{mb:8.1f}  {n}')
"
```

**判据：最大表的构成随机器与使用方式变，两次实测不一致——每次都用 `dbstat` 重测，不要背某次的表名。** 实测一（2026-10-01，382 MB）：`transcript_events` 仅 **57 MB**，头是 `context_engine_turn_outbox` **103 MB** 与 `trajectory_runtime_events` **85 MB**。实测二（2026-10-16，624 MB）：`transcript_events` **282.7 MB（45%，已成头号表）**、`trajectory_runtime_events` **119.3 MB**、`memory_embedding_cache` **55.9 MB**、`memory_index_chunks` 族 **86.3 MB**（含 vec 与 fts）。⇒ 可迁移的结论只有纪律（**先归因再动手**），**具体哪张表最大不是**。把力气花在上一张实测的头部表上，在这一台机器上可能只动到零头。

⚠️ **`dbstat` 的占比会随 `pruneAfter` 收紧而反转**：实测二里会话正文涨成头号表，正是因为 `pruneAfter` 已收到 `"7d"`、近 7 天真实会话堆积在库里。⇒ **归因前先读 `session.maintenance.pruneAfter` 的实际值**，它决定了库里「该留多少」这个前提；不确定时把它和 `dbstat` 一起报给主人。

⚠️ **`dbstat` 给出的是含索引与页开销的占用，不等于 payload 之和**（同一实测：outbox 表 103 MB 而 `sum(length(payload_json))` 只有 72 MB）。估算「能回收多少」用 payload 之和，判断「哪张表最大」用 `dbstat`。

⚠️ **删行不还盘**：`DELETE` 完 `freelist_count` 会涨（如实测删 565 行后 21141 页 ≈ 86.6 MB）而 `page_count` 不变 ⇒ `du`/`df` **看不出任何变化**。但空闲页会被 SQLite **自动复用**，等于**止住了增长**。要真把空间还给文件系统才需 `VACUUM`/compact（要求无活网关，见 §C 第 4 步）——不要为了几十 MB 去停网关。

⚠️ **删大批会话前先算收益**：`session_windows` 266 条里 206 条「7 天以上未活动」的**只持有 1192 条存活事件**（全库 13564 条），全删也只回收几 MB。**先按 session_key 统计存活事件数，收益是噪声就别提这个方案。**

## §B 收紧阈值（配置面，不是 shell 命令）

改 `openclaw.json` 顶层 `session.maintenance`，**改前 `cp` 备份，改后回读校验**。**这段 JSON 是文件内容，不要原样粘进终端**（bash 会逐行当命令执行并报「找不到命令」）—— 由 agent 直接改文件，或明确告知主人这是待写入的配置片段。

```json
"maintenance": {
  "mode": "enforce",
  "pruneAfter": "7d",
  "archiveDashboardAfter": "3d",
  "maxEntries": 200,
  "preserveRecent": "3d",
  "maxDiskBytes": "400mb",
  "highWaterBytes": "300mb",
  "resetArchiveRetention": "14d",
  "coldStorage": { "enabled": true, "afterDays": 7 }
}
```

判据：`cleanup --dry-run --json` 的 `beforeCount → afterCount` 必须**出现差值**。实测本例 439 → 274（`archived 9` + `pruned 165`），`diskBudget.overBudget` 由 `false` 翻 `true`、`maxBytes` 回执为 `419430400` —— 三者任一不变即配置没生效。

## §C 执行顺序（顺序错了就是不可逆数据损失）

1. **先 `coldStorage`**：让后台 worker 把不活跃 transcript 抽成压缩 JSONL 外置（`Settings → Agent Defaults → Session → Archive older transcripts → Run now`）。**这一步必须在第 2 步之前**。
2. **再 `openclaw sessions cleanup --agent <id> --dry-run --json`** —— 看清 `pruned` 的条数与性质。
3. **再 `openclaw sessions cleanup --agent <id> --enforce`**。回执语义：
   - `archived` = in-place 改元数据，**保留全部 transcript**，**不减小文件**
   - `pruned` = **删除可丢弃的自动化行，不可逆**。实测一次收紧就 `pruned 165`，全是 `agent:main:subagent:*` 写手/审计/评审子会话。若这些历史尚未外置，第 1 步没跑到位就执行 = 永久丢失。
   - `capped: 0` 而 `afterCount` 仍高于 `maxEntries` = 正常：pinned / 活动会话 / 外部会话指针受保护，`--enforce` 不解除保护。
   - `diskBudget.freedBytes: 0` 即使 `overBudget: true` 也正常：预算是**删除的触发器，不是压缩器**。
4. **最后回收页**：`openclaw doctor --session-sqlite compact --session-sqlite-agent <id> --json`。**要求该 state 目录上没有活网关** ⇒ 停网关交主人，本 agent 不自行 exec 重启。`VACUUM` 只在 §A 判据 2 显示碎片可观时才有意义。

删除/执行类动作先确认主人的范围指令；本 agent 只给 dry-run 数字与三个选项（先 coldStorage / 直接删 / 放宽阈值），由主人选。

### §C-4 离线压缩序列（交主人执行的唯一标准写法）

⚠️ **对运行中的 operator 网关，`openclaw gateway stop` 会被拒（退出码 1），必须加 `--force`。** 实测原句：

> This stops the operator's running gateway service. Use an isolated dev gateway (`openclaw gateway run --dev`, or `--profile <name>` with a free port) for testing, or **re-run with `--force` if you really mean it**.

**文档 README 与 `openclaw gateway --help` 的示例都写的是裸 `gateway stop`，照抄必然失败。** 正确序列：

```bash
openclaw gateway stop --force          # ← 缺 --force 会被拒
openclaw backup create --verify        # 备份失败即中止，不碰原库
openclaw doctor --session-sqlite compact --session-sqlite-all-agents --json
openclaw gateway start
```

**交给主人的脚本必须满足三条，否则会留下「以为在维护、其实全程空转」的一轮：**

- **校验每一步退出码并在失败时中止**。只 `log` 退出码然后继续下一条 = 空转：实测 v1 脚本 `stop` 失败后仍去跑 compact，而 compact 在网关存活时必然拿不到 state lock 而失败。判据是**非零即 `exit`**，不是「记下来」。
- **用 `trap … EXIT` 兜底拉起网关**，避免中途失败把主机留在宕机态；正常走完启动流程后要置位跳过兜底，别重复启动。
- **确认网关真的停了再动数据库**：轮询 `pgrep -f "openclaw/dist/index.js gateway"`（有超时上限），`--force` 返回后仍可能有 systemd cgroup 里的子进程在跑。

⚠️ **不要在网关托管的会话里后台/脱离执行这个序列。** 停网关会同时杀掉承载当前会话的进程 ⇒ **本 turn 连同命令一起消失，且事后无法向主人汇报结果**（实测即如此）。正确形态是**写好脚本、把整条命令原样交给主人在自己的终端跑**，再回来读日志验收；不要用 `setsid nohup … &` 之类尝试后台发射——审批层也会以「高影响本地动作 + 子进程继承明文 apiKey 环境」为由拒绝。

⚠️ **审批层在拒绝这类脚本时点名的「行为与退出语义需确认」要当真实缺陷信号处理，不要绕道重试。** 实测它标出的退出语义缺陷确实存在（见上第一条）。被拒时的正确动作是回头改脚本并说明风险请主人批准，或改成「交主人执行」，不是换写法达成同一结果。

⚠️ **交主人执行后，必须靠正向取证验收，不能凭一句「已经跑了」就报成功。** 实测（2026-10-16）：主人回「已经跑了啊」，但维护日志里**搜不到该次运行的任何一行**（`grep -c "维护开始" ` 回 `0`），库体积也几乎未变；只有 `gateway-restart.log` 出现两条 `interactive=0` 的 stop/start ⇒ **那只证明网关被非交互地停起过，不证明 compact 跑过、更不证明它有效**。

⇒ **验收三件套，缺一即报「未确认」**：

1. **日志正向证据**：该次运行在日志里有起止行与各步退出码（`汇总：stop=… backup=… compact=… start=…`）。
2. **库体积前后两个值**：`du` 压缩前 / 压缩后各一次。**`gateway-restart.log` 的 stop/start 不是体积证据**，`interactive=0` 只说明发起方不是交互式终端（脚本或更新器都可能）。
3. **任务侧回读**：手动 `openclaw automations run <id>` 后 `automations show <id>` 的 `last error` 已清空。**只验证「库小了」不够**——实测库小 1.4% 而两条 error cron 依然 error，说明修复没生效。

⚠️ **失败轮次本身就是取证**：v1 脚本 `stop` 失败后继续跑 compact，回执给出了精确失败原因——`failed to acquire gateway state ownership … holder <pid> … is alive on this host, stop it first`。**「拿不到 state lock」= 网关还活着**，不是磁盘/锁损坏、也不是「等一下就好」；正确处置是回到步骤 1 停网关，不要重试 compact。

## §D 一次性残留类别（与库本体无关，收益立竿见影）

`du -sh ~/.openclaw/agents/<id>/agent` 之外，状态目录里这几类是历史遗留，删了不损失现网数据：

| 类别 | 形态 | 实测 |
|---|---|---|
| 失败重建残留 | `openclaw-agent.sqlite.memory-reindex-<uuid>` 及 `-sh` / `-wal` | 两次失败共 ~227 MB |
| 升级前备份 | `openclaw-agent.sqlite.schemaNN.bak` | ~74 MB |
| 迁移前库快照 | `openclaw-agent.sqlite.pre-startup-migration-<uuid>.bak` | ~703 MB（实测 2026-10-16，**名字比现库大、会盖过现库**，确认非现役再删） |
| 旧配置副本 | `openclaw.json.bak.N` / `.pre-update` / `.last-good` | 同一目录堆到 7 份时先统一命名与保留策略再谈删 |
| 凭据 reconcile 残留 | `gateway.systemd.env.reconcile-<uuid>.bak` | 数十字节，但会持续再生 |
| SQLite 迁移归档 | `agents/<id>/session-sqlite-import-archive/`（jsonl 已导入库内） | ~270 MB |
| **插件构建产物** | `tmp/plugin-captures/<uuid>/` | 771 MB，**删它会连带打坏 `openclaw` 工具的 config 写入路径 —— 见下方警告** |

删残留前用 `ls` 确认文件已不在、目录 mtime 判断是否仍在被写；`tmp/` 下**时间戳是今天的目录不要删**。清理前后各跑一次 `du -sh` 对比并在报告里给出前后值。

🚨 **`tmp/plugin-captures/` 不是残留、不是缓存、删了不会自动回来 —— 它是 `openclaw` 工具解析插件模块的路径，删掉后 `openclaw` 工具的配置写入会整个报 module not found。** 实测（2026-10-17）：清理时把该目录 `rm -rf` 后，走 `openclaw` 工具做一次 `config.set` 即失败，回执是

```
Cannot find module '/…/.openclaw/tmp/plugin-captures/<uuid>/captures/openclaw-plugin-build-…/node_modules/feishu/dist/secret-contract-api.js'
Require stack: /…/.openclaw/extensions/feishu/dist/index.js
```

判据与恢复要点：
- **故障面很窄，别误判成大停电**：报错指向 `tmp/plugin-captures`，但**被 require 的插件本体在 `extensions/<id>/dist/` 下完好**；实测 `gateway health` 仍回 `OK`、通道仍 `configured`、磁盘上 `secret-contract-api.js` 存在。⇒ **飞书/通道正常，只有「用工具改配置」这条路断了**。先分清这两件事再决定紧急度。
- **报错的形状就是指纹**：`Cannot find module …/tmp/plugin-captures/…` ⇒ 几乎必然是本会话（或近期某次清理）删过该目录，**不是 feishu 装坏了、也不是配置校验失败**。配置校验失败会回 schema 字段错误，不会回 module 解析错误。
- **出路是热编辑配置文件**：`openclaw.json` 是第三条写入路径（见 SKILL.md 前置事实），直接改文件可绕开工具；`openclaw doctor` / `plugins list` 等**只读 CLI 仍然正常**，只有配置写入受影响。
- **删除 40 分钟后实测该目录未自行再生** ⇒ 别指望「等一会儿自己好」，也别反复重试同一次工具调用。
- **清理前先问一句「这个目录谁在读」**：本表其余各项删掉只是省空间；`tmp/plugin-captures` 删掉会让一条功能路径失效。**收益（省 771 MB–1.2 GB）不足以交换一个功能面** —— 且盘宽裕时该收益本就该降级（见下）。

⚠️ **库快照比现库还大时，先确认它不是现役文件**：`pre-startup-migration-*.bak` 这类名字里的时间戳是**迁移发生时**而非快照内容的时间，一个陈旧快照完全可能大于缩小后的现库；**用大小当「是残留」的唯一依据会误删**。判据是文件名后缀 + 现役路径 `.sqlite` 存在，两者都在才删。

⚠️ **腾空间的真实收益要看 `df` 不是 `du`**：`gio trash` 把字节搬进同盘回收站，源目录 `du` 变小而 `df` 不变。报释放量必须给 `df -h` 前后对比；盘宽裕时（实测 926 G 可用）这些残留清理属**可选 tidiness 而非优化项**，别排进 P0。详见 `workspace-declutter`。

## §E 取证时的命令形态（本机审批层约束）

- ⚠️ **想知道「启动预检为什么超时」只有一个入口：只读 `openclaw doctor`**。它打一行 `[state/agent-db] agent database integrity gate`，字段 `elapsedMs` / `phaseDurationsMs` / `integrityGateMs` / `thresholdMs` / 逐表 `integrityTableTimings` 直接给出校验耗时与归因到表。实测该机 `validation:6425ms` vs `thresholdMs=1000`，慢在 `memory_embedding_cache`(2434ms) / `memory_index_chunks`(1241ms) / `trajectory_runtime_events`(719ms) ⇒ **校验本身超出 5 秒前台启动预算**。不要改用 `security audit`、`skills check` 或体量估算去归因（见 `SKILL.md` 第三种 cron 失败形态）。
- ⚠️ **批量 error job 的分诊第一步是 `automations runs` + `uptime -s`，不是 `last error` 单独定病。** 实测详见 SKILL.md「第三种失败形态」末条：两条 job 连续 4 次 `ok`、仅开机后 50 秒内的一条 `error` ⇒ 开机补跑窗口撞车，**正确处置是什么都不改**。只看 `last error` 会把它误当成常驻缺陷，进而套上 compact / 迁 agent / 缩 `pruneAfter` 这三条本不该生效的修法。
- **外部 `sqlite3` CLI 打开 live state 目录下的库会被直接拒**（提示改用 OpenClaw 命令或把副本放到 state 目录外）。只读 PRAGMA 走 `python3 -c` + `sqlite3.connect('file:…?mode=ro', uri=True)` 可行。
  ⚠️ **「把库复制到 state 目录外再用 `sqlite3` CLI 打开」这条退路实测也被拒**，即便副本已在 `/tmp` 且名字不含 `openclaw` —— 回执仍是 `external sqlite3 cannot open databases under the active OpenClaw state directory`（该守卫按文件特征判定，不看路径）。⇒ **取证一律直接走 `python3 -c` 的 `sqlite3` 模块，不要在「换个路径试 CLI」上浪费轮次**；`dbstat` / `count(*)` 也都在 python 里跑（§A 判据 2、判据 4 的命令本就是 python 形态，照抄即可）。
- **审批层拒的是命令形态不是任务**：被拒的是**重定向**（`2>/dev/null` / `2>&1`）与**`;` 分隔的复合序列**（`approval cannot safely bind this command`）。去掉尾缀、只留单条简单命令即可放行；`cd X && …` 改用 exec 的 `workdir` 参数或绝对路径。
  ⚠️ **但单条管道 `cmd | jq …` / `| head` 与 `&&` 链实测能放行**（实测 `openclaw sessions list --limit all --json | jq -r '…'` 一次通过）⇒ **不要因为怕被拒就放弃管道过滤**，那会让本可一行取完的盘点退化成多轮试探。查日志优先用工具自带的 grep（`journalctl -g`、`--grep`），零管道最稳。
- **同一条已放行的命令不要原样重提**：会被判「已批准过一次」而整体拒绝，并明确禁止绕道或换写法达成同一结果。此时只能换思路（改用 `ls` / `read` 等一等工具取证）或说明理由请主人批准。
- 拒批后若该命令正是主人要的（如一条 `rm`），把**完整命令原样交出去让主人自己跑**，比反复重试省事；不要因此把命令改写成自己认为「更安全」的等价形式。

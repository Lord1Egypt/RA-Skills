# 批量审计与修复优先级（Batch Audit）

单份审计回答"这份技能好不好"，批量审计回答"这些技能里，我明天先修哪一个"。两者的差别不在工作量，在于必须有一个能复算的排序公式。

## 适用条件

- 技能库超过 10 个技能，且短期内不可能全部重写。
- 有人要为一整库的质量负责，需要一份可汇报的清单。
- 要在两个版本之间做回归比对，确认改动没有把别处弄坏。

## 扫描范围

- 从库根目录开始找 `SKILL.md`，深度 2–3 层足够（`<root>/<skill>/SKILL.md` 或 `<root>/<category>/<skill>/SKILL.md`）。
- 排除：`.git`、`__pycache__`、`node_modules`、`dist`、`.pay_cache`、`.archive`、`_done`、任何以 `.` 开头的目录。
- 同一个技能有多个副本时，只审计"被实际加载的那一个"，其余记为重复副本，在报告里单列一节。

## 执行流程

1. **全量初评**：`python scripts/skill_audit.py --scan <库根目录> --json audit-all.json`。一次不要超过 40 个技能，超出就分批。
2. **粗筛**：把总分低于 60 或安全维为 0 的挑出来，这部分必进队列，不再讨论。
3. **人工抽检**：随机抽不低于 20% 的技能，逐份读原文，核对初评的分数方向是否正确。抽检的作用不是复核小数点，而是发现"脚本给高分但人一看就废"的漏判。
4. **算优先级**：用下方公式给每一条算分，降序排列；同分时总分低的排前面。
5. **写队列**：产出 `audit-queue.md`，字段见模板。只写可执行的动作，不写"建议优化"。
6. **抽修与复测**：先修队列前三条，修完重跑同一脚本，对比 JSON，确认目标条目的分上升且其他条目没有明显下降。

## 优先级公式

```
优先级分 P = 影响面 I × 严重度 S ÷ 修复成本 C
```

三个因子各取 1–3 的整数，结果保留两位小数。

**影响面 I**

| 值 | 判据 |
| --- | --- |
| 3 | 对外交付，或被定时任务、流水线、其他技能引用 |
| 2 | 团队常用，或至少被一个自动化入口调用（脚本默认值） |
| 1 | 个人偶尔使用，没有被任何入口引用 |

**严重度 S**

| 值 | 判据 |
| --- | --- |
| 3 | 安全维为 0，或总分低于 60 |
| 2 | 总分 60–74 |
| 1 | 总分 75 及以上 |

**修复成本 C**

| 值 | 判据 |
| --- | --- |
| 1 | 正文不超过 150 行且估算不超过 3,000 token，问题集中在措辞与清单 |
| 2 | 正文 151–400 行，或需要拆分 `references/` |
| 3 | 正文超过 400 行，或需要重写流程与验收两节 |

算式示例（数值仅演示计算方式）：`I=3、S=2、C=1 → P=6.00`，排在 `I=2、S=3、C=2 → P=3.00` 之前——对外交付的中等问题，优先于内部使用的严重问题，因为前者的代价扩散得更快。

脚本默认 `I=2`，可用 `--impact` 覆盖；抽检阶段如果发现某个技能实际被定时任务引用，就在队列里手改 I 并注明依据，不要偷偷改结果分。

## 修复队列模板

```markdown
# 修复队列（<库名> · <日期>）

范围：<N> 个技能，已审计 <M> 个，抽检 <K> 个（<百分比>%）

| # | P | 技能 | 总分 | 等级 | 首要问题 | I | S | C |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 6.00 | <slug> | 52.0 | C | 触发词泛化，无反触发 | 3 | 2 | 1 |
| 2 | 3.00 | <slug> | 58.5 | C | 工作流第 3 步无失败分支 | 2 | 3 | 2 |

## 本轮不做

- <slug>：总分 88，仅体量偏大，留到下个迭代。
- <slug>：已废弃，直接下线，不修。

## 复测口径

同一脚本、同一 profile、同一批次参数；只有目标条目的分上升才算修好，其他条目下降超过 5 分要回查是否误伤。
```

## 库级报告模板

```markdown
# 技能库审计报告

## 摘要
- 技能总数：<N>；参与评审：<M>
- 均分：<X>；中位数：<Y>；最低：<Z>（<slug>）
- 等级分布：S <a> / A <b> / B <c> / C <d> / D <e>
- 一票否决项：<k> 个技能含路径、密钥或内部地址

## 共性问题（出现次数降序）
1. 触发词泛化：<n> 次——范式见 rewrite-patterns.md R1
2. 验收不可判定：<n> 次——范式见 R6
3. 工作流无失败分支：<n> 次——范式见 R4

## 前十名与末十名
（表格：技能 / 总分 / 等级 / 一句话理由）

## 建议
- 立即修：<清单>
- 下个迭代修：<清单>
- 建议下线或合并：<清单>
```

## 断点续跑与分批

- 单批不超过 40 个技能；批次之间用子目录切分，不要随机抽样切分，便于定位。
- 每批产出独立 JSON（`audit-batch-01.json`、`audit-batch-02.json`），中断后从下一批继续，已完成批次直接保留，不重扫。
- 合并时用脚本字段而不是人工抄写：`skills` 数组按 `dir` 去重，重复项取 `body_lines` 较大的一份并记一条重复副本。

## 回归验证

1. 修完先跑单份审计，确认目标维度确实升分。
2. 再跑整库扫描，与修复前的 JSON 做差集：`总分变化 = 修后 - 修前`。
3. 出现"目标升分、邻项掉分"时，检查是不是把内容搬到 references 时漏了引用句——这是批量修复里最常见的一类回归。
4. 差集结果附在队列末尾，作为下一轮的基线。

## 常见错误

- **按总分从低到高排**：低分技能可能根本没人用，修它不产生价值。排序必须带影响面。
- **全库统一重构**：批量改写的回归成本远高于收益，队列的意义就是"只修前几条"。
- **跳过抽检**：脚本只能数结构，误判率集中在"结构齐全但语义空洞"这一档，必须人读。
- **不复测就宣布完成**：没有复测数字的修复等同于没修。

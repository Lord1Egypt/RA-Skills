# 系统的构成与设计

## 可运行系统实例：所有部分共同作用的中心

OpenXSys 每次围绕一个当前活动的系统实例运行。提示词与方法是实例在现场使用的资源。实例可以存在于本轮模型构造的图景中，也可以由用户拥有的 `SYSTEM.md`、作品、代码、数据和连接长期承载。活动图景与长期系统指向同一个现实对象，并在新证据到来时彼此校准。

系统实例让 AI 能够回答下面的语义问题。这些语义可以用任何适合对象的自然语言结构承载，用户继续从自己的表达与材料进入。

| 语义 | 必须弄清什么 |
| --- | --- |
| **身份与目的** | 这是什么系统，为谁服务，当前想理解或改变什么，什么算有价值的结果。 |
| **边界与尺度** | 这次看哪里、看到哪一层、跨多长时间；哪些东西暂时作为环境，何时需要把它们纳入。 |
| **现实、观察与模型** | 对象实际状态由谁掌握；当前能看见哪些信号；哪些是解释、假设和未知。 |
| **组成与关系** | 哪些人、AI、工具、资料、规则与其他系统参与；真正传递作用的关系是什么。 |
| **约束与资源** | 什么限制整体，什么可以改变，改变之后约束可能移动到哪里。 |
| **能力** | 当前已经能做什么，哪些经过真实验证，哪些只是候选，目标还要求什么。 |
| **所有权与权限** | 资料、状态、作品、决定和执行分别归谁；谁能纠正、停止、撤回或退出。 |
| **作品与行动** | 系统如何把认识交给人，如何把意图送到现实，怎样让后来者接手。 |
| **反馈与演化** | 什么证据会改模型，什么结果会改能力、关系、边界或目标，哪些下游随之需要重审。 |

当前运行激活与目的有关的部分。出现新的尺度、关系或能力鸿沟时，再把相应部分展开。一个部件、关系或能力都可以递归地成为新的系统实例；弄清之后再回到上层，看它怎样改变整体。系统的复杂性来自彼此作用的层级与变化。

## 稳定语义与活动图景

系统入口保存相对稳定、足以改变以后工作的认识、能力、关系与约定。本轮运行形成活动图景：当前目的、最新材料、实际可用工具、此刻权限、待确认效果和正在发生的变化。活动图景结束后，只有会改变下一次运行的内容才进入长期系统。

本轮思考链、工具日志和临时猜测留在活动图景；会改变未来工作的状态进入长期系统。当前真实发生的变化可以直接修正入口。长期系统给运行提供起点，运行用现实反馈修正长期系统。

## 同时看三个系统

**现实中的对象**有自己的状态、历史和作用。地铁会运行，团队正在分工，作品有实际读者。**为了认识或改变它而建的系统**由观察方法、解释、人、AI、工具和组织关系组成。**承载运行的电脑与 AI 工具**负责传递、推理、执行和保留结果。三者可以互相影响。调度资料进了模型只说明资料被观察到，线路状态由运营侧确认。研究作品可以改变人的认识，但实际调整线路还需要能行动的系统。

从人、AI、电脑和其他现实系统的作用关系看，可以从任意参与者起步。人可以说出意图，电脑可以观察文件变化，模型可以在一次已有运行中发现机会，领域系统可以送来事件。人、模型和电脑也可以分别处在不同的物理地方。确定当前尺度之后，再识别哪一方实际拥有内容和行动权。

## 具体系统怎样构成

| 部分 | 有什么关系要说清 |
| --- | --- |
| **对象与所有者** | 当前要理解或改变的整体是什么，影响谁，谁维护目的、资料、工具和权限。层级随目的可调整。 |
| **系统说明** | 让新的 AI、人或宿主读得懂这是什么、已知什么、重要事实在哪里、可怎样接手。用自然语言连到实际有用的材料。 |
| **认识与证据** | 观察能看见什么，解释在哪些尺度成立，出现什么反例会改变它。不同参与者可以保有各自的模型。 |
| **实际工作的安排** | 哪些人和工具提供信息、计算、作品或行动。什么由世界本身决定，什么由系统有权改变。 |
| **作品与接力点** | 人如何获得认识或使用成果，能从哪里继续，后来者怎样取得新证据和新的当前视角。 |
| **反馈与连接** | 实际效果回到哪个人、工具或系统，独立系统怎样借力，结果反复后由谁改变长期安排。 |

这些部分是设计视角。研究一个概念可能只需要入口、一份用得上的解释与可核对的出处。常年运行的组织系统可能有多处观察、各自独立的权限和几条必须稳定的交接。加一个组件，应当能说清它改变的关系、产出的价值和由谁维护。

## 固定关系与可变实现

在一项工作采用的尺度上，把真实的决定权、状态来源、资源上限和已经确认的时机当作约束。团队约定、用户偏好、供应商、模型、论文和工具在各自的时间范围内可以变化。新资料只影响它真的改变的判断。长期方向、权限和发布要求由有决定权的所有者确认。

尽量把自然语言放在最能表达意图、意义和判断依据的地方。精确、重复、可复核的工作可以交给代码，例如核对一组数据或变更是否生效。能用现有环境的权限系统、数据接口和协作方式，就把它们当作现成部件。新增工具应有实际对象和可观察作用。

## 小例子

社区剧场已经有节目表，负责人掌握正式版本，音响和运营各有自己的看法，复核晚到会造成另一种问题。给剧场开启系统时，「版本相同」可以是一个判断依据，「最后一次改动后有无完成审核」是另一个。两者属于不同关系和时间尺度。一个实用系统可以用表格做日常入口，用检查工具帮助发现偏差，并让负责人决定哪项行动真的要改。工具和角色发生变化以后，检查目标和状态来源仍然可以延续。

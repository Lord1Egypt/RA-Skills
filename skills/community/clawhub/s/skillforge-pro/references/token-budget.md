# 体量与上下文成本（Token Budget）

技能一旦被加载，它的正文会跟着每一轮对话被重新发送。体量不是审美问题，是成本问题，也是命中率问题：同样一段注意力预算，背景铺垫占得越多，真正要执行的指令越容易被忽略。

## 估算公式

没有分词器在手时，用字符数折算。下面的系数是工程估算区间，不是精确值；需要对账时以平台分词器的实测结果为准。

| 内容类型 | 每字符 token 估算 | 说明 |
| --- | --- | --- |
| 中文正文 | 0.55–0.75 | 一个汉字通常不足一个 token，标点更省 |
| 英文正文 | 0.22–0.28 | 约 4 个字符一个 token |
| 代码与命令行 | 0.30–0.40 | 符号多，压缩率低于自然语言 |
| 表格 | 0.45–0.60 | 竖线与空格会额外计入 |
| URL 与哈希 | 0.60–0.90 | 字符随机，几乎无法合并 |

单一混排文件的近似式：

```
估算 token ≈ 中文字符数 × 0.65 + 其余字符数 × 0.27
```

取值规则：宁可高估。审计报告里写区间（"约 2,300–2,700 token"），不写单一数字冒充精确值。

## 体量分档

| 档位 | 估算 token | 典型形态 | 处置 |
| --- | --- | --- | --- |
| 精简 | ≤ 1,500 | 单文件，四到六节，无 references | 保持，优先这一类 |
| 标准 | 1,500–4,000 | 十节齐全，1–3 个 references | 可发布，检查有无可下沉段落 |
| 重型 | 4,000–8,000 | 正文偏长或 references 偏多 | 必须拆分，正文只留判断依据 |
| 超限 | > 8,000 | 单文件塞进方法库 | 不拆分不得发布 |

`SKILL.md` 本身的建议上限是 4,000 token 估算；超过就该问一句"这些内容每一轮都需要吗"。

## 拆分决策

对每一段内容问三个问题，答"否"就下沉：

1. **每一轮都要用它做判断吗？** 否 → 进 `references/`。
2. **它是确定性计算或格式转换吗？** 是 → 进 `scripts/`，正文只留调用方式。
3. **删掉它，某一步会执行不了吗？** 否 → 删，或压成一句摘要。

下沉后的正文写法：`细则见 references/<file>.md；当出现 <条件> 时必须先读它。`——保留"何时读"这一句，比保留全文更省也更有用。

拆分后的自检：正文每一行都在指令链上，删掉任一行都会让某一步失去依据；如果删了没影响，那行就是负债。

## 上下文成本模型

同一份技能，加载一次与加载一百次的成本差一百倍。相对成本可以这样估：

```
单次会话增量 ≈ 技能 token × 轮次 × 重发系数
```

- **轮次**：一次任务里模型被调用的次数，工具调用越多轮次越高。
- **重发系数**：历史内容在后续每一轮都会被再次发送。带缓存的通道对重复前缀打折，但折扣不等于免费；审计时只比相对倍数，不折算成金额。
- **结论**：把技能从 6,000 token 压到 2,500 token，在长会话里的节省远大于 58% 这个比例给人的直觉，因为它作用在每一轮上。

不要把"缓存命中便宜"当成"可以写长"的理由：缓存降低单价，不改变"注意力被稀释"和"首次加载必然全价"这两件事。

## 测量流程

1. 跑 `python scripts/skill_audit.py <技能目录>`，读 `size` 段：`body_chars`、`cjk_chars`、`est_tokens`、`est_tokens_band`。
2. 用上面的公式手算一遍，与脚本结果对不上时检查是否有大段代码或表格被算进了"其余字符"。
3. 把 `est_tokens` 记入评分卡 D5，并按分档表定分。
4. 拆分后复测，记录前后差值；差值小于 20% 说明拆错了位置，只是把内容搬了个地方。

## 常见错误

- **只数行数**：中文一行 80 字与一行 20 字成本差四倍，行数是排版指标，不是成本指标。
- **忽略 references 的成本**：references 不常驻，但被读一次就进上下文，且往往一次读很多，实际增量可能超过正文。
- **把示例当零成本**：大段样例代码在每一轮都被重发，压缩率还低于自然语言。
- **重复表述没被计入**：同一规则换三种说法写三遍，脚本的重复检测能抓到标题级重复，段落级重复要靠人读。
- **用体量代替质量**：短不等于好。删到无法执行是负优化，体量分只是六维之一，权重 10。

# 能力与演化

能力来自足以产生某种结果的组织方式。认领一条关系前，弄清楚哪一方看得见、谁能改变状态、行动能否送到、结果经过多久能回来。现实中的协作者、脚本、他人的专业系统、数据和服务都可能是能力的一部分。

## 什么才算能力

能力不是一组工具，也不是一次生成成功。它是在适用条件下，一些人、AI、知识、工具、规则与反馈能够重复把某种输入或初始状态变成有价值结果的关系结构。

一项能力应当能说明：

- 它让谁能够做到原先做不到的什么。
- 适用的对象、输入、条件、尺度与时效。
- 参与的部件怎样连接，谁拥有、执行、确认和维护。
- 输出是什么，怎样知道工具做完、对象改变和实际有用。
- 在什么真实任务与反例上验证过。
- 哪些信号意味着需要重验、替换、停用或交回人。

## 从候选到能力

| 状态 | 可以怎样称呼 |
| --- | --- |
| 只描述目标和组成 | 设计 |
| 已有实现但未运行 | 候选或草稿 |
| 在隔离样本或模拟中通过 | 已测试实现 |
| 在用户的真实任务中完成工作并得到相应确认 | 已验证能力 |
| 在不同适用输入中持续有效，失效边界也清楚 | 可复用能力 |

每一种状态使用与证据相称的语言：代码运行成功证明实现可执行，真实任务成功证明当前条件下能力成立，重复验证与边界样本继续扩展可信范围。

## 能力怎样被组织和创造

先看当前系统已经拥有的模型、工具、资料、实践、协作者和其他系统。LLM 可以直接完成认知或创作，也可以调用现有能力、适配接口、生成代码、建立观察入口、改变人机分工或组织一项新的协作关系。选择真实条件下成本合适、效果可靠、用户能拥有和接手的实现。

新部件只有在改变关键关系时才值得增加。为能力加上反馈：检查什么，谁看见，失败后回到哪里。上游条件变化时，能够定位哪些能力需要重验，并让新的实现接手同一个用途。

| 需要的变化 | 可以组织的东西 | 能确认效果的证据 |
| --- | --- | --- |
| 过去没有办法看见 | 一个新的观察入口、连接两组观测的对照方法 | 能用实际材料发现以前漏掉的差异 |
| 已有工具互相用不上 | 连接两个接口、补上语义或责任交接 | 在授权环境中完成双方能核对的实际任务 |
| 经常要人重复解决 | 一项可重复使用的工具，或更合适的协作安排 | 换一个适用的实际输入，依然产生有用结果 |
| 只在当前条件下有效 | 留下适用边界、责任和判断信号 | 条件变化时能发现，并改用适合的新安排 |

在已授权的环境尽量把实际能力做出来，尽可能运行并检查输出。需要生产权限时可以先构造可检查工具、草稿或模拟，同时交代当前做到哪里、由谁确认下一步。模拟结果、测试环境和真实应用分别说明。

反馈要落到它能改变的部件。一次反例可以更正假说，连续失效可以改来源、接口或分工。保留的是未来还能起作用的关系与能力。若原先有效的安排失效，可以退回旧版本、重组或请所有者撤除。处理重试时先向实际的状态持有者核对前次动作，尤其是重复执行会产生第二次效果的时候。

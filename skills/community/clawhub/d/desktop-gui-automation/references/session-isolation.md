# 会话隔离：为什么后台任务不能操作 GUI

## 现象

在 WorkBuddy 的后台自动化会话里跑桌面脚本时，典型报错：

- `OSError: screen grab failed`（PIL ImageGrab 截不到屏）
- `pyautogui.FailSafeException` 或窗口激活 `Error code 5 拒绝访问`
- 主对话会话里同样的脚本却能正常截屏、点击

## 根因

WorkBuddy 的自动化任务运行在**独立的后台会话**，拿不到交互桌面的帧缓冲，也不能向用户桌面发送输入事件。我这个主对话会话在用户交互桌面上，所以能操作。两者在同一台机器，但会话上下文不同。

**结论**：脚本本身没问题，是执行上下文不对。不要反复改脚本逻辑，要换执行环境。

## 诊断（30 秒定位）

在目标会话里跑：
```bash
python scripts/gui_auto.py shot
```
- 生成 PNG → 该会话可用，直接跑业务脚本。
- 抛 OSError / screen grab failed → 会话隔离，必须走方案 A。

交叉验证：在主对话会话跑同一命令，若成功则确认是会话差异而非脚本/依赖问题。

## 方案 A：Windows 任务计划程序（推荐）

计划任务设为"仅在用户登录时运行"，其进程就活在能截屏、能点击的交互桌面会话里。创建模板见 `task-scheduler.md`。

架构：
- 计划任务（登录会话）→ 真正操作 GUI，写日志和截图。
- WorkBuddy automation → 只读日志/截图做汇报，不碰 GUI，时间错开（如操作 9:00、汇报 9:20）。

## 方案 B：WorkBuddy automation 直接调用本机脚本

某些环境里自动化会话能跑本机 Bash/Python（取决于版本与宿主）。若 `shot` 在自动化会话里成功，可让 automation 直接 `python gui_auto.py ...`。
**先诊断再采用**，不要假设可用——真实项目里这条路径曾连续 6 天失败，而脚本本身在用户会话里完全正常。

## 方案 C：纯提醒型兜底

若电脑常处于关机/休眠，任何本机 GUI 自动化都不成立。退化为每天推送提醒让用户手动点，或改用服务端 API（若该软件提供）。

## 前提条件提醒

- 电脑在触发时刻需处于**已登录**状态（锁屏通常不影响，休眠/关机不行）。
- 任务运行时鼠标会移动、窗口会弹出，那几分钟用户别抢着操作。
- 任务执行完要关闭弹窗恢复现场。

# 基准测试与质量验收

本文件定义"跑得动"之后怎么证明"跑得好"。所有指标都要能复现，所有数字都要标注采集环境。

## 一、指标定义

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 首 token 延迟（TTFT） | 请求发出到收到第一个内容 token 的时间 | 流式请求里记首块到达时刻 |
| 解码速度 | 内容 token 数 ÷ （末 token 时刻 − 首 token 时刻） | 不要用总时长除，会把预填充算进去 |
| 预填充速度 | prompt token 数 ÷ 首 token 前的等待时间 | 长提示下才有意义 |
| 端到端时延 | 请求发出到流结束 | 业务侧真正感知的时延 |
| 并发吞吐 | N 个并发请求的总 token 数 ÷ 墙钟时间 | 与单路对比看退化 |
| 峰值显存 | 压测过程中的最大占用 | 盘中轮询 `nvidia-smi` 或看服务端日志 |

两个口径必须写清楚：**吞吐（tokens/s）**与**时延（s）**不能混着比。有人报"每秒 80 token"其实是 4 并发合计，单路只有 20，这种口径混淆会让容量规划直接错一倍。

## 二、测量方法

1. **预热一次**：首次请求包含模型加载与图编译，必须丢弃。
2. **固定输入**：短（约 50 token）、中（约 800 token）、长（约 6000 token）三档各若干条，全部落成文件，跑的时候直接读，不要临时生成。
3. **固定输出**：`max_tokens` 统一，例如 256；比较不同模型的输出长度必须一致，否则解码速度不可比。
4. **固定采样**：温度设 0 或固定种子。注意 GPU 上的浮点归约顺序不保证完全确定，同一输入仍可能有细微差异，所以要比较"结论是否一致"而不是"字串是否相等"。
5. **取中位数**：每档跑 3 次取中位数，不用平均值（一次调度抖动就会把均值拉偏）。
6. **串行与并发分开测**：先单路建立基线，再开并发；并发测试期间不要同时跑别的重负载。

## 三、测试矩阵

| 场景 | 输入档 | 并发 | 目的 |
|---|---|---|---|
| 冷启动 | 短 | 1 | 模型加载耗时，服务重启后的首个请求体验 |
| 交互基线 | 短 + 中 | 1 | 日常问答的 TTFT 与解码速度 |
| 长文处理 | 长 | 1 | 预填充是否是瓶颈 |
| 并发容量 | 中 | 2 / 4 / 8 | 找退化拐点与 OOM 边界 |
| 长稳 | 中 | 目标并发 | 连续 30 分钟，看显存是否爬升、速度是否衰减 |

长稳那一项最容易被跳过，也最容易暴露问题：KV 未回收、日志爆盘、连接泄漏都会在 30 分钟后现形。

## 四、并发测试怎么做

串行发 N 个请求不等于并发。用线程池同时发起，记录每个请求的起止时刻：

```python
import concurrent.futures as cf, json, time, urllib.request

BODY = {"model": "local", "max_tokens": 256, "temperature": 0,
        "messages": [{"role": "user", "content": "<固定提示>"}]}

def one(_):
    req = urllib.request.Request("http://127.0.0.1:8080/v1/chat/completions",
                                 data=json.dumps(BODY).encode(),
                                 headers={"Content-Type": "application/json"})
    t0 = time.time()
    with urllib.request.urlopen(req, timeout=600) as r:
        data = json.loads(r.read().decode())
    return time.time() - t0, data["usage"]["completion_tokens"]

for n in (1, 2, 4, 8):
    with cf.ThreadPoolExecutor(n) as ex:
        out = list(ex.map(one, range(n)))
    wall = max(t for t, _ in out)
    print(n, round(sum(c for _, c in out) / wall, 2), "tokens/s aggregate")
```

判据：并发数翻倍时，合计吞吐应显著上升；若合计吞吐几乎不变而单请求时延线性上升，说明已经在排队，再加并发只会更慢。

## 五、质量抽检

### 题集构成

| 类别 | 数量 | 说明 |
|---|---|---|
| 业务真实样例 | 8–12 | 从实际使用里摘，脱敏后固定下来 |
| 结构化输出 | 3–5 | 要求按固定 JSON 结构返回，能解析才算过 |
| 数字与事实抽取 | 3–5 | 从给定文本里取数值、日期、编号 |
| 长文定位 | 2–3 | 长输入中间位置放一个关键事实，看能否取到 |
| 边界与拒答 | 2–3 | 超出范围或信息不足时应明确说不知道 |

### 不可失败项

至少三条，任何一条失败即整体不通过：

1. 结构化输出能被解析器直接接受（不允许包裹多余文字）。
2. 给定文本里的数字被原样取出（不允许改写、不允许猜）。
3. 信息不足时明确表示无法回答，而不是编造。

### 评分

每条 0/1/2：0 为错误或不可用，1 为部分正确需人工修补，2 为可直接使用。记录总分与不可失败项通过情况，并把失败样例原文留在报告里——这是后续调参的依据。

### 横向对比

换模型或换量化档时做盲评：把两份输出顺序随机、去掉模型标识，交给同一个人评。非盲评时人会被"更大的模型应该更好"带偏。

## 六、记录格式

每条请求一行 JSONL，便于后续统计：

```json
{"ts":"<ISO8601>","model":"local","quant":"Q4_K_M","ctx":8192,"prompt_tokens":812,"completion_tokens":256,"ttft_ms":640,"decode_tps":31.2,"total_ms":8840,"concurrency":1,"peak_vram_mib":12390}
```

字段要求：`ttft_ms`、`decode_tps`、`total_ms` 三个必须有；`peak_vram_mib` 按需（并发场景必填）。

## 七、常见测量错误

- **用总时长算解码速度**：长提示下会把预填充时间算进去，速度被严重低估。
- **首请求算进结果**：冷启动耗时混进基线，TTFT 虚高数倍。
- **只测一次**：调度抖动、缓存命中与否都会影响结果，单次不可信。
- **忽略提示缓存**：同一提示重复请求可能命中前缀缓存，TTFT 明显偏低；换一条提示再测。
- **单位没对齐**：Ollama 的 `eval_duration` 与 `prompt_eval_duration` 单位是纳秒，当成毫秒用会把耗时算大约 100 万倍、速度算小约 100 万倍；统一换算成秒再求比值。
- **并发用循环发**：串行发 4 次得到的是"4 倍单路时延"，不是并发吞吐。
- **不记录环境**：没写清显存、量化档、上下文、并发数的数字，一律不可复用。

## 八、验收结论怎么写

报告里给一段话结论，包含：在什么环境、什么上下文、什么并发下，TTFT 与时延是多少，质量抽检通过率多少，距离业务阈值还差多少。不要写"性能良好"这类无法验收的判断，写"4 并发下 TTFT 1.9 s，低于 3 s 阈值；解码合计 78 token/s，满足 5 人同时使用"。

所有数字后面跟一句"示例环境，需实测"或直接注明采集环境，二者必居其一。

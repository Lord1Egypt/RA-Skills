# 75 · 自对抗评审（Grill）：设计 / 需求 / 测试三域

> 目的：交付前用挑衅式提问，把「没人问过但上线会炸」的点逼出来。
> 工具：优先加载 catalog 里的 `grill-me`（访谈式逼问）；不在 catalog 时用本文件清单自问或由 Reviewer 代问。
> 位置：闭环里放在 **GATE 之前**，GATE 记录其结果（`loop-gate.ps1 -RequireGrill` 时缺失即 FAIL）。

## 0. 三域用法与记录文件

| 域 | 什么时候做 | 记录文件 | 模板 |
|---|---|---|---|
| **设计（界面+交互）** | 出稿前（grill 现有体系是否被尊重）+ 出稿后（grill 状态/可用性） | `grill-design-YYYYMMDD.md` | `templates/grill-design.md` |
| **需求分析** | 进入三遍评审前 | `grill-req-YYYYMMDD.md` | `templates/grill-requirement.md` |
| **自动化测试** | 写用例前（oracle 来源）+ 出报告前（假绿风险） | `grill-test-YYYYMMDD.md` | `templates/grill-testing.md` |

命名只要匹配 `grill-*.md`，`loop-gate` 与硬门都能识别；三域可合并到一个文件，但**问题与结论必须分开写**。

## 1. 通用规则（三域都适用）

1. **问具体场景，不接受「合理/一般/应该」**；每个问题要能指向文件、接口、字段或截图。
2. **至少 1 个「会被打回」的问题并完成修正**；0 个打回 = 问得不够狠。
3. **未解决项进 D-ID（owner + 期限）**；阻塞交付的必须判「有条件通过/打回」，不得直接 PASS。
4. **评审人不能是实现者**；自问时须在记录里注明「自问」，并由 Reviewer/Lead 复核。
5. **退出条件**：问题有答案或 D-ID；P0 全部关闭；记录可被第三人复跑。

## 2. 设计域攻击清单（界面 + 交互）

> 先读 `design-context.md`，确认「现有体系」再问；重点抓「只在成功态好看」。

| # | 问题 | 常见坑 |
|---|---|---|
| D1 | 信息层级能否一眼看出主次？关键动作是否被埋？ | 满屏同权重卡片、主按钮和次按钮同色 |
| D2 | 空态/加载/失败/部分失败/超长文本分别长什么样？ | 只画有数据的正常态 |
| D3 | 375 / 768 / 1440 三档会不会破？触控目标 ≥44px？ | 表格横向溢出、按钮太小 |
| D4 | 暗色/高对比场景是否可用？对比度 ≥4.5:1？ | 硬编码白底、图表颜色在深色下失效 |
| D5 | 键盘可达吗？焦点顺序/focus ring/ESC 关闭？ | 自定义下拉不可键盘操作 |
| D6 | 与现有组件库/主题一致吗？不一致处为什么？ | 自造一套 token、按钮圆角/间距跳变 |
| D7 | 数据密集场景：数字精度/单位/时区/千分位/排序是否统一？ | 金额不带单位、时间按本地时区错位 |
| D8 | 图表是否误导？坐标轴/图例/空值/单位是否清楚？ | 截断坐标轴、缺失值当 0 |
| D9 | 危险操作有二次确认/撤销/审计留痕吗？ | 删除一键生效、无影响说明 |
| D10 | 文案是否可执行（谁、做什么、后果）？ | 「确定/取消」无宾语、错误文案无下一步 |
| D11 | 加载性能：首屏/骨架/大列表/频繁刷新会不会抖？ | 布局抖动、无分页、全量渲染 |
| D12 | 这套设计能否被开发按现有组件实现（不引入新 UI 体系）？ | 设计稿要求新框架/新图标库 |

## 3. 需求分析攻击清单

| # | 问题 | 常见坑 |
|---|---|---|
| R1 | 问题真实吗？证据是什么（工单/数据/访谈/政策）？ | 领导拍脑袋、伪需求 |
| R2 | 目标可量化吗？验收口径第三方能复跑吗？ | 「提升体验」「做好用」 |
| R3 | 范围边界清楚吗？「不做什么」写了吗？ | 一期把二期都算进来 |
| R4 | 业务规则有来源与置信度吗（A/B/C）？ | 把行业经验当系统规则 |
| R5 | 数据口径（字段/单位/精度/时间窗/勾稽）写死了吗？ | 「按惯例」「按报表」 |
| R6 | 权限/角色/审批链清楚吗？越权会怎样？ | 只写功能不写权限 |
| R7 | 异常/边界/并发/重复提交/回滚怎么处理？ | 只写正常流程 |
| R8 | 与现有系统/旧数据冲突时以谁为准？ | 冲突不记录，开发自行猜 |
| R9 | 依赖（接口/数据/第三方）是否可用？缺口登记了吗？ | 假设接口一定就绪 |
| R10 | 优先级依据是什么？为什么现在做？ | 全是 P0 |
| R11 | 合规/安全/审计红线是否核过？ | 能源/碳/电网场景漏监管 |
| R12 | 验收标准能映射到测试用例吗（AC→TC）？ | AC 不可测，测试只能「看」 |

## 4. 自动化测试攻击清单

| # | 问题 | 常见坑 |
|---|---|---|
| T1 | 期望值（oracle）从哪来？置信度 A/B/C？ | AI/行业专家推断当真相 |
| T2 | P0 规则覆盖率 100% 吗？P1 ≥80%？ | 只报行覆盖率高 |
| T3 | 每条用例绑定 R-ID 了吗？未绑定的标 exploration 了吗？ | 用例与规则两张皮 |
| T4 | 边界值/空值/极值/负数/超长测了吗？ | 只测中间值 |
| T5 | 权限不足/未登录/跨租户测了吗？ | 只测超级管理员 |
| T6 | 数据缺口（mock/404）如何处理？标「未实测」了吗？ | 用 mock 数值判 PASS |
| T7 | 并发/重复提交/幂等/顺序依赖测了吗？ | 单线程顺序执行 |
| T8 | 失败场景：超时/重试/部分失败/回滚？ | 只测成功路径 |
| T9 | 断言强吗？删断言/放宽断言换绿色了吗？ | 假绿 |
| T10 | 与环境相关的项（浏览器/第三方/时区）标未实测了吗？ | 谎报通过 |
| T11 | 回归范围怎么定？改了 A 会影响 B 吗？ | 只跑新用例 |
| T12 | 出问题怎么定位（日志/证据/命令）？ | 报告只有「失败」两字 |

## 5. 与门禁/闭环的接线

- 设计交付：`design-context.md` → 出稿 → `grill-design-*.md` → Reviewer 按 rubric 评审 → `loop-gate -RequireGrill`。
- 需求交付：SRS ≥80 → `grill-req-*.md` → 三遍评审 → `gate-check -Kind requirement`。
- 测试交付：台账 + 用例 → `grill-test-*.md` → 执行 → `gate-check -Kind test` + `test-traceability`。
- `loop-gate` 默认只查 `grill-*.md` 是否存在（WARN）；交付硬门加 `-RequireGrill`（缺失 FAIL），不检查内容质量——内容由 Reviewer 抽查。
- 没有打回项 = 记录不合格；重做一轮，不要用「已评审」糊过去。

## 6. 反形式化约束

- ❌ 自己出稿自己夸「很完整」→ 必须写成可被判死的问句；
- ❌ 只覆盖正常路径 → 异常/边界/权限/数据缺口至少各 1 条；
- ❌ 记录只写「已评审」→ 必须写具体问题、具体答案、证据路径；
- ❌ 发现问题不修就标 PASS → 未解决进 D-ID，阻塞项必须 FAIL/有条件通过。

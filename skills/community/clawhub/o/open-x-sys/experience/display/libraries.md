# Web Libraries and Runtime Environments

> **Read when**: a work is about to use a web library, font, map, video tool, or other runtime environment; or you need to decide between offline use, self-containment, and easy sharing.

A work begins with its subject and reader and with the runtime environment and native Web capability the host genuinely has now. Technology enters when it makes a decisive mechanism clearer, more testable, or more usable.

## Begin from zero dependencies

HTML, CSS, SVG, and a small amount of native JavaScript can create a great many excellent works. They are easy to inspect, work offline, share cleanly, and leave the work free from a library's default appearance.

Before adding a library, ask:

- Would the decisive experience genuinely fail without it?
- Does the user's project or host already have a better-suited tool?
- Must the work open offline, or can it explicitly depend on the network?
- Are the library's version, license, size, and data sources clear?
- If the library fails to load, can the central discovery still be understood?

An ordinary bar chart needs no large framework. A third dimension earns 3D only when it carries the insight. Interaction appears when a static page cannot express change, comparison, or causality.

## Use what the user already owns

If the current project already uses D3, ECharts, Three.js, MapLibre, KaTeX, or another library, use the project's existing version and build path so the work enters its real dependency system naturally.

When the host provides design, document, video, image, or browser capability, call what the present task needs. Treat a capability as available after its smallest real operation succeeds. See [Tools and Capabilities](../../adapters/tools.md).

## Adding an external dependency

When a library or tool that is not currently present is genuinely needed, bring the choice to the user and state:

- what problem it solves that existing capability cannot;
- the exact version or service name;
- its license, cost, network use, and data boundary;
- what installation or connection will change;
- what can still be delivered without it;
- how to remove, replace, or leave it.

Installation and connection follow actual authority. Versions are explicit, sources are inspectable, and remote dependencies and offline behavior are visible in a shareable work.

## Self-contained and networked forms

Make clear which of these the work is:

- **Fully self-contained**: all decisive content lives in one file or delivery directory and works offline.
- **Self-contained within the project**: uses local resources already locked by the project and runs through the project's normal path.
- **Networked**: clearly lists remote sources, versions, and the fallback result when they fail.

When a page depends on the network, say so in the delivery note. If a remote resource fails, the work still shows its central thesis, decisive evidence, and an intelligible static structure instead of an empty region.

# doc-templates：产品与技术文档模板（PRD · 技术方案 · 测试方案 · 发布方案 · Runbook · 故障复盘）

## 定位与心智模型

本子域是**组织内部工作文档**的模板与写作纪律域：PRD、one-pager、故事卡、design doc、测试方案、发布变更方案、runbook、故障复盘——全部是给内部团队用的协作与对齐产物，**不是面向最终用户的产品文档**。01~07 号萃取文件的边界轮一致结论：与 Diátaxis 四象限（教程/操作指南/参考/解释——为面向读者的技术文档设计）**不直接对应，不硬套判型**。两者的交集仅在于好文档的通用原则（明确读者、可验证、变更可追溯）互相通用；唯一可迁移的是 Diátaxis 的底层原则（按读者意图组织内容）。

七类模板构成一条**文档链**：需求（PRD/one-pager/故事卡/PR-FAQ）→ 设计（design doc/RFC/KEP）→ 测试（测试方案/测试报告）→ 发布（变更方案）→ 运维（runbook/SOP）→ 复盘（postmortem）→ 回流需求与 runbook（复盘行动项）。链上每份文档回答一个别人无法替它回答的问题：「为什么做/做什么/怎么做/怎么算成/怎么安全上/出事怎么救/为什么坏/怎么不再坏」。

**轻重变体光谱**：每类模板都有完整版与轻量版（PRD↔one-pager/故事卡；design doc↔mini doc/轻量 RFC；全量回归方案↔冒烟方案）。轻量省的是格式与篇幅，不能省的是决策理由、目标与可判定的完成标准。选型与裁剪判据见 [PT-2]，各变体决策表见最佳实践场景 1。

三个官方锚：industrialempathy《Design Docs at Google》（技术方案锚）、Atlassian PRD 指南（需求锚）、Atlassian incident postmortem（复盘锚）。sre.google 两 URL 抓取失败已放弃，blameless 官方背书由 Atlassian 页承担（见冲突消解记录 2）。

## 法则

[PT-1] **MUST**: 模板产出中的项目私有事实（数值、评审记录、统计数据、时间线、人名）只能以 <待填：…> 占位符或显式标注「示例」的形式呈现，NEVER 以看似考证过的真实数据形态填充；无官方一手来源支撑的实践细节（页数上限、比例数字、流程时长、字段清单）MUST 标注「实践归纳（置信度 x）」或「待验证」，NEVER 写成规范原文。
- 违反后果: 编造数字被读者当考证结论引用——虚假完整感比留空更有害；记忆混源的转述被当权威扩散且难以追溯。
- 溯源: [模型经验]（01/02/03/04/05/07 自我质询轮共现偏置；LAW-1 的域层具体化——「域层具体化，非重复立法」裁决见 kb/laws.md 未收录登记）

[PT-2] **MUST**: 需求载体的选择与裁剪按「不可逆性 × 价值确定性 × 跨团队程度」判断；裁剪任何文档 MUST 先锚定删掉即失效的保命字段（目标与量化指标、可判定完成标准、排除范围、回滚触发条件），再裁其余。
- 违反后果: 小需求套九节大模板（文档成本超过需求价值），或高风险不可逆需求只剩一张故事卡（返工成本远超文档成本）；精简版退化成口头需求，事后无法验收也无法抗范围蔓延。
- 溯源: [实践归纳（置信度高）]（01 轻重变体「保命三件」、02 决策表与不可裁三件、03 核心不可裁剪项、04 通过标准不可裁——四主题独立收敛出同一裁剪序）

[PT-3] **MUST**: 需求、设计、测试类文档 MUST 含显式排除范围节（out-of-scope / non-goals / 不测什么）且逐条给出排除理由；non-goals 只写「本可合理成为目标但明确选择不做的事」，NEVER 写成目标的否定式改写或与课题无关的废项。
- 违反后果: 范围蔓延无据可依；维护者把「有意不做」当遗漏自行补齐，引入未评审的设计；否定式非目标零信息量，边界声明形同虚设。
- 溯源: [官方文档](https://www.atlassian.com/agile/product-management/requirements)（Atlassian PRD 指南第 8 节 What we're not doing：显式标记 out of scope）+ [官方文档](https://industrialempathy.com/posts/design-docs-at-google/)（industrialempathy Design Docs at Google：non-goals ≠ 否定式目标——ACID 例子）+ [实践归纳（置信度高）]（04 测试范围「不测什么」）

[PT-4] **MUST**: 每条目标 MUST 绑定指标名、当前基线与目标值（PRD 目标另加时限），NEVER 写不可验证的宏大目标；验收标准与准出标准 MUST 逐条可判定（Given/When/Then 或可勾选条件），NEVER 使用「完成/合格/稳定/易于使用」类主观词。
- 违反后果: 上线后无法判定成败，「提升用户体验」式目标沦为表态；验收扯皮，任何人都可以宣布达标；准出标准执行后补写等于先打枪后画靶。
- 溯源: [实践归纳（置信度高）]（01 目标三件套与质量判据、04 准入准出骨架；Given/When/Then 源自 BDD）+ 全局对应 [LAW-17]（判据可机械判定的升格条款）

[PT-5] **NEVER**: PRD NEVER 由 PO 一人独写，MUST 与开发/设计共创并跨职能评审。
- 违反后果: 单视角需求漏掉可行性与体验约束，落地即返工；评审通过沦为社交事件。
- 溯源: [官方文档](https://www.atlassian.com/agile/product-management/requirements)（Atlassian PRD 指南："Never write a product requirements document by yourself"——永远与开发/设计共创，客户访谈带上设计与开发人员）

[PT-6] **MUST**: 技术方案文档 MUST 在编码前成稿并完成评审对齐，NEVER 实现后补写。
- 违反后果: 补写文档只是换了格式的代码注释，对齐价值归零；用文档的便宜迭代代替代码的昂贵迭代这一全部价值无处发生。
- 溯源: [官方文档](https://industrialempathy.com/posts/design-docs-at-google/)（industrialempathy Design Docs at Google：informal 文档、写于编码前）+ [实践归纳（置信度高）]（03 反模式 9 时点错位）

[PT-7] **MUST**: 设计文档 MUST 含至少 2 个公允描述的备选方案及各自被拒理由，备选的描述篇幅与优势陈述 MUST 与选定方案对称。
- 违反后果: 评审沦为形式确认；稻草人对比让「为什么不是别的方案」不可考。
- 溯源: [官方文档](https://industrialempathy.com/posts/design-docs-at-google/)（industrialempathy Design Docs at Google：Alternatives considered 是最重要小节之一——trade-offs、为何未选）+ [模型经验]（备选稻草人化生成偏置防御）

[PT-8] **MUST**: 完整设计文档篇幅目标 10~20 页甜点区，超出 MUST 拆分为多份或降级为 1~3 页 mini design doc。
- 违反后果: 巨石文档没人读完，评审走马观花，关键决策被淹没。
- 溯源: [官方文档](https://industrialempathy.com/posts/design-docs-at-google/)（industrialempathy Design Docs at Google：篇幅甜点区 10-20 页、1-3 页 mini 可行、超出应拆分）

[PT-9] **MUST**: 开放问题 MUST 标注 owner、截止时间与默认决议（到期无响应按什么处理），NEVER 把未决事项写成确定需求。
- 违反后果: 「待讨论」永久悬挂；不确定性被伪装成确定性误导排期。
- 溯源: [实践归纳（置信度高）]（01 坑点 18、03 骨架字段 10）

[PT-10] **MUST**: 发布与变更方案 MUST 含回滚预案——量化触发条件（含决策权归属）+ 编号步骤（每步含执行人与预期结果）+ 回滚后验证 + 数据兼容性说明（回滚不得丢用户数据）；灰度分级 MUST 从自身流量结构推导，每级 MUST 定义覆盖业务周期的观察窗口与量化推进/暂停判定指标。
- 违反后果: 事故中靠临场判断；回滚后旧代码读不了新代码写入的数据，回滚丢用户数据；低流量服务的固定比例级别形同虚设，「看起来没事」推级导致全量后爆发。
- 溯源: [实践归纳（置信度高）]（05 反模式 2/字段 6 回滚可执行性；05 坑点 3/4/15/20 灰度分级）

[PT-11] **MUST**: 影响面 MUST 从依赖图推导（上游调用方、下游数据/消息消费方、数据格式变化、其他环境）且通知状态逐行显式，NEVER 写「无影响」；feature flag MUST 定义默认状态、紧急关闭路径（值班可达）与含期限和 owner 的清理计划。
- 违反后果: 依赖方在自己的告警里第一次得知你的变更；flag 滚成配置债无人敢删，凌晨出事找不到有权关 flag 的人。
- 溯源: [实践归纳（置信度高）]（05 坑点 5/12/字段 2 影响面；05 坑点 9/10/字段 4 flag 生命周期）

[PT-12] **MUST**: 测试方案 MUST 声明与生产的已知差异（或显式声明无已知差异），测试报告 MUST 含遗留风险段且「有条件放行」附可验收的条件（可验收动作 + 验收人 + 时限）。
- 违反后果: 测试环境全绿、上线即事故；无遗留风险段的有条件放行是空头支票，条件永远不会被检查。
- 溯源: [实践归纳（置信度高）]（04 反模式 5 环境差异、反模式 9 有条件放行）

[PT-13] **MUST**: runbook 每条处置条目 MUST 以可观察的验证段结尾并含带时限的升级条件，全文 NEVER 出现「酌情/视情况/适当」；数据修复类危险操作 MUST 含前置备份（未取得备份标识禁止继续）与 double-check 强制停顿点（双人确认或单人读回 + 影响行数预估）。
- 违反后果: 执行者中途迷路（这个输出算正常吗？），把决策留给凌晨、疲劳、不熟的最不该做决策的时刻；凌晨改坏数据且无备份可回，影响不该影响的数据。
- 溯源: [实践归纳（置信度高）]（06 坑点 2/3/8/18 与凌晨 3 点判据；06 坑点 4/9 危险操作）

[PT-14] **MUST**: 复盘 MUST blameless——根因追问到系统与机制层（技术根因 + 流程根因），NEVER 以「人为失误」为根因终点或出现指摘个人的措辞；达到严重度阈值的事故 MUST 在解决后 24~48 小时内启动复盘（不超过 5 个工作日），且每份复盘 MUST 被复审。
- 违反后果: 组织学会隐藏故障而不是消除故障——下一次故障先自救再上报，复盘数据缺失；超期导致记忆衰减、日志滚动覆盖，时间线还原成本指数上升；未复审的复盘不如不写。
- 溯源: [官方文档](https://www.atlassian.com/incident-management/postmortem)（Atlassian incident postmortem：blameless by design、John Allspaw 源流、严重度阈值触发、24-48 小时内/不超 5 个工作日、每份必复审）+ [实践归纳（置信度高）]（07 双层根因结构）

[PT-15] **MUST**: 复盘行动项 MUST 含类型（至少一条 detective，回答「同类故障为何没更早发现」）、单人 owner、期限与可判定验收标准，并登记进跟踪系统；复盘时间线 MUST 与日志/告警/工单记录核对并标注来源与时区，NEVER 凭记忆拼凑。
- 违反后果: 「加强培训」式行动项写完即烂尾，同类故障再发时旧行动项完成率无人过问；关键时间点错误，「检测慢」被「恢复快」掩盖，跨时区团队对时间点各执一词。
- 溯源: [官方文档](https://www.atlassian.com/incident-management/postmortem)（Atlassian incident postmortem：action items 转 tracked issues、含 timeline 与关键时间点）+ [实践归纳（置信度中高）]（preventive/detective/responsive 三分法，07）+ [实践归纳（置信度高）]（07 坑点 6/10 时间线工程）

## 核心概念速览

| 概念 | 一句话定义 |
|---|---|
| PRD | Product Requirements Document：定义产品的 purpose/features/functionalities/behavior，是跨职能团队的单一事实来源。[官方文档](https://www.atlassian.com/agile/product-management/requirements) |
| BRD / MRD | 商业需求文档（为什么这个商业问题值得解决）/ 市场需求文档（谁需要、竞品格局）——现实常与 PRD 合并，但「为什么/做什么/怎么做」三层信息应可区分。[模型经验] |
| one-pager | 单页需求主张，用途是「对齐一个决策」而非「定义一个产品」；一页是物理约束不是修辞。[模型经验] |
| PR/FAQ | Amazon working backwards 逆向工作法：先写假设产品已上线的虚构新闻稿 + 尖锐 FAQ，倒逼检验客户价值；无公开官方模板，属实践归纳（置信度中高）。[模型经验] |
| 用户故事 / 故事卡 | As a [角色] / I want [能力] / So that [价值] 三段式；卡是提醒对话的锚点（3C：Card/Conversation/Confirmation），不是合同。[模型经验] |
| INVEST | 故事卡六检查：Independent/Negotiable/Valuable/Estimable/Small/Testable；写不下说明是史诗，要拆。[模型经验] |
| design doc | 一个课题的 how 全案（背景/目标/多方案对比/详细设计/发布回滚），informal、写于编码前、以 trade-offs 为核心。[官方文档](https://industrialempathy.com/posts/design-docs-at-google/) |
| mini design doc | 1~3 页的轻量设计文档，可行性获官方锚认可；超出 10~20 页甜点区的完整版应拆分或降级。[官方文档](https://industrialempathy.com/posts/design-docs-at-google/) |
| RFC | propose → comment → decide → record 的提案流程；accept/reject 都归档，被拒提案的拒绝理由同样有价值。[模型经验] |
| KEP | Kubernetes Enhancement Proposal：kubernetes/enhancements 仓库内的编号增强提案，含 kep.yaml 元数据。[模型经验] |
| lazy consensus | 惰性共识：提案发出后窗口期内无人异议即视为通过，异议才主动处理；窗口期必须显式宣告起止，否则产生假共识。[模型经验] |
| non-goals | 设计文档的「本可合理成为目标但明确选择不做的事」+ 理由；≠ 目标的否定式改写。[官方文档](https://industrialempathy.com/posts/design-docs-at-google/) |
| out-of-scope | PRD 的显式排除范围（Atlassian 第 8 节 What we're not doing）；把「被拒绝的需求」写进去是范围谈判的书面证据。[官方文档](https://www.atlassian.com/agile/product-management/requirements) |
| 准入/准出标准 | Entry/Exit Criteria：提测前置条件与结束测试的放行条件，逐条可勾选可机械判定；准出须在方案阶段冻结。[模型经验] |
| Given/When/Then | BDD 验收标准语法（源出 Dan North，2003~2006 时期）：前置情境/动作/可判定结果。[模型经验] |
| 冒烟测试 | P0 关键路径快速验证集（常见 10~30 条量级，实践归纳）：全过=准入通过，任一失败=退回不进细测。[模型经验] |
| 测试金字塔/奖杯 | 分层策略（大量单元/适量集成/少量 E2E）及其前端变体之争；比例是启发式不是铁律。[模型经验] |
| feature flag | 功能开关：默认状态 + 免发版紧急关闭路径 + 含期限与 owner 的清理计划；只设计「开」不设计「关」是 flag 债根源。[模型经验] |
| 灰度发布 / 金丝雀 | 按流量结构推导的分级放量，每级带覆盖业务周期的观察窗口与量化判定指标。[模型经验] |
| 双写迁移 | 数据迁移的可逆模式：新旧双写→回填校验→灰度切读→全量→停旧写（不可逆点须单独评审）。[模型经验] |
| runbook / SOP | 面向凌晨 3 点认知降级读者的执行手册：短句、编号步骤、每步预期输出、验证段、升级出口。[模型经验] |
| 凌晨 3 点判据 | runbook 质量判据：首次值班的执行者只靠这本手册能按步骤执行且每步知道预期结果；任何时刻需查另一份文档即为断链。[模型经验] |
| postmortem | 故障后的结构化、blameless 评审：what happened/why/impact/处置过程/防再发变更。[官方文档](https://www.atlassian.com/incident-management/postmortem) |
| blameless | 复盘纪律：理解系统与事件序列而非追责个人；措辞聚焦 actions/results/impact，根因到系统与机制不到人。[官方文档](https://www.atlassian.com/incident-management/postmortem) |
| MTTD / MTTR | 检测用时（首条告警/首个用户反馈起）/ 总时长（检测→恢复）；统计口径各组织有争议，须先声明口径。[模型经验] |
| 5 Whys | 连续追问至少五次找机制层根因；警惕群体回避不舒服的真相或仓促达成共识。[官方文档](https://www.atlassian.com/incident-management/postmortem) |
| 行动项三类型 | preventive 防再发 / detective 防扩害·早发现 / responsive 防拖慢·快恢复；至少一条 detective。[实践归纳（置信度中高）] |

## 最佳实践

### 场景 1：选需求载体与裁剪（PRD vs one-pager vs 故事卡 vs PR/FAQ）

推荐路径（源于 [PT-2] [PT-4]）：
1. 按三决策变量定载体：**不可逆性/风险**（做错撤销成本高——涉及钱、隐私、架构、对外承诺 → 完整 PRD）→ **价值确定性**（价值是假设需检验 → PR/FAQ；已验证 → 故事卡/one-pager）→ **跨团队程度/决策待批**（多团队对齐或向上要资源 → one-pager 以上；单团队执行 → 故事卡）。
2. 决策表：新产品方向价值存疑 → PR/FAQ；中型功能需决策批准 → one-pager；迭代内明确需求单团队 → 故事卡；高风险/强合规 → 完整 PRD；说不清 → 先写 15 分钟 one-pager，写不下去暴露的缺口告诉你该升级还是降级。
3. 裁剪时先锚定保命字段（目标与量化指标、可判定完成标准、排除范围——轻量变体加上回滚触发条件，若涉及发布），再向外瘦身；判断基准是「文档成本与需求撤销成本的比值」。

do/don't 对照：

```text
✗ 改个按钮文案走完整 PRD 流程（为正式而正式）
✗ 高风险不可逆需求用一张故事卡拍板（为轻量而轻量）
✗ 精简 PRD 时先删目标/验收标准/out-of-scope（裁掉保命字段）
✗ 「口头 + 群消息」冒充 one-pager（讨论散落聊天记录）
✗ one-pager 缩字号硬塞 3 页内容（一页是物理约束不是修辞）
✓ 故事卡：正面三段式 + 背面 Given/When/Then（含异常路径）+ owner/点数
✓ one-pager 末尾显式「决策请求」：需要谁、在何时、决定什么
✓ 拿不准时默认 one-pager 写 15 分钟再定升降级
```

边界条件：Amazon PR/FAQ 全部纪律细节（6 页上限、集体默读会等）标「实践归纳（置信度中高）」，无公开官方模板原文，不得冒充 Amazon 官方模板；PR/FAQ 通过后仍需落实到具体需求载体（它是对齐工具不是需求规格）；PRD/MRD/BRD 三分法在敏捷语境下很多团队已合并，引用时不暗示强制分层。[模型经验]

### 场景 2：写技术方案 design doc（何时写/何时不写；解剖结构与生命周期）

推荐路径（源于 [PT-6] [PT-7] [PT-8] [PT-9]，官方锚 [官方文档](https://industrialempathy.com/posts/design-docs-at-google/)）：
1. **先判该不该写**：关键信号是**模糊性（ambiguity）**——有 trade-offs 要对齐才配 design doc；没有 trade-offs 的实现说明书不写；「敏捷」不是不写的借口。开销权衡：单团队小变更用轻量 RFC 版即可。
2. 解剖结构（锚点小节对照）：Context and scope（客观事实，不是需求文档复述）→ Goals and **non-goals**（≠ 否定式目标）→ Actual design（系统上下文图、API 草图不粘贴正式定义、数据存储、少用伪代码）→ Degree of constraint（greenfield vs 受约束遗留）→ **Alternatives considered（最重要小节之一）**→ Cross-cutting concerns（安全/隐私/可观测性；Google 要求独立隐私 design doc）。
3. 补齐锚点未强制但本域 MUST 的字段：回滚方案、灰度与发布策略、开放问题（owner+截止+默认决议）、评审记录（含异议处置——被驳回的异议理由是未来排查的最重要线索）。
4. 生命周期四阶段（锚点）：创建/快速迭代 → 评审（轻量评论到正式评审会，主动寻求关键反馈不阻塞）→ 实现与迭代（未交付则更新 doc，amendments 模式）→ 维护与学习。design doc 是**时点性对齐工具**，写出即「过期」是正常的，不是持续维护的规格书。
5. 评审通过后把关键决策**沉淀为若干条 ADR**（design doc 归档可腐化，ADR 必须存活）；PR 模板加「设计文档」字段回链。

do/don't 对照：

```markdown
✗ 「我们采用方案 X……（十页详细设计）」——无备选，评审变形式确认
✗ 备选方案各写一行、选定方案写十页（假对比）
✗ Non-Goals 写「不做与本项目无关的事」（废话式非目标）
✗ 代码合并后为补流程写 design doc（时点错位，对齐价值归零）
✗ 详细设计滑向伪代码（过早冻结实现细节）
✓ 「备选 A（自建）：优——可控；劣——3 人月维护负担。备选 B（开源 Y）：
  优——2 周上线；劣——社区活跃度待评估。选 B：目标是本季度上线。」
✓ 里程碑里给「design doc 评审通过」设为编码前置门槛
✓ 一篇 50 页文档里的五个独立决策拆成 5 条 ADR，design doc 链接之
```

边界条件：完整版 10~20 页甜点区、1~3 页 mini 可行（官方锚数值，超出应拆分）；组织评审流程（评审人构成、审批链）各公司私有，落地须适配组织现实；与 ADR 的分界细则见集成要点。[官方文档](https://industrialempathy.com/posts/design-docs-at-google/)

### 场景 3：写测试方案与测试报告

推荐路径（源于 [PT-12]，呼应 [PT-4]）：
1. 方案在**开发进行中**成稿（需求/设计评审后、提测前），准出标准在方案阶段评审冻结；报告在测试完成后、发布决策前产出——它是决策输入，不是事后备案。
2. 范围段先写「不测什么」+ 理由（第三方内部逻辑以挡板覆盖契约、历史稳定模块不回归的置信依据）——范围即优先级，「全面测试」等于无策略。
3. 环境与数据：与生产的**已知差异清单**逐条列出（数据量级/依赖版本/挡板项）或显式声明「无已知差异」——差异本身不致命，不说明差异才致命；禁止裸拷生产数据，脱敏规则入方案。
4. 准入准出逐条可判定：准入挡「测半成品」（自测证据/冒烟通过/构建号明确）；准出含用例执行率、P0/P1 通过率、Blocker/Critical=0、性能门禁、遗留缺陷全登记。
5. 报告四件：执行统计（阻塞单列）→ 缺陷按严重度分级（分级定义先行，绑定可操作判别规则如「是否有绕行」）→ **遗留风险段**（每条：严重度+带病上线理由+触发概率影响+计划版本+owner）→ 结论与准出逐条对照；「有条件放行」的条件 = 可验收动作 + 验收人 + 时限。

do/don't 对照：

```markdown
✗ 准出：「测试完成且质量满足要求」（不可判定，谁都可以宣布达标）
✗ 报告结论：「共执行 320 用例，通过率 96.4%，建议发布」（4% 失败只字不提）
✗ 「有条件放行」——条件是什么、谁验收、何时清零全无下文
✗ 直接导出生产库到测试环境造「真实感」（制造数据泄露面）
✓ 准出：「P0/P1 通过率 100%；Blocker/Critical=0；Major ≤2 且均有绕行
  方案与计划版本；支付接口 P99 ≤ 300ms（100 并发基准）」
✓ 报告含准出对照表 + 遗留风险表（owner/计划版本列非空）
✓ 用例标注 P0/P1/P2，裁剪顺序预定义：先 P2 再 P1，P0 永不砍、砍则改期
```

边界条件：测试分层比例（金字塔/奖杯）是启发式不是铁律；冒烟用例 10~30 条、E2E 个位到几十条均为实践归纳不作规范数字；提测/发布流程与严重度枚举高度组织私有，须对齐组织现有工具字段；方案引用用例库不复制用例正文（复制即双份维护）。[模型经验]

### 场景 4：写发布与变更方案

推荐路径（源于 [PT-10] [PT-11]）：
1. 变更评审**前**成稿——评审通过的是这份文档，执行时对照的也是这份文档；以执行工程师为默认读者。
2. 灰度分级从自身流量结构推导，不从模板抄：每级流量/范围 + 覆盖业务周期的观察窗口（峰值/定时任务/批处理/缓存 TTL）+ 可从面板直接读出的推进判定指标 + 暂停/回滚阈值；L0 内部白名单起步，末级 100% 保留收尾观察期。
3. 回滚预案四件套：量化触发条件（写明谁有权拍板）+ 编号步骤（每步动作+执行人+预期结果）+ 回滚后验证 + 数据兼容性（回滚不得丢用户数据；破坏性变更不可回滚时，恰恰要写清为何无回滚与替代安全网）+ 耗时预估（现场决策回滚 vs 热修）。
4. 数据迁移走可逆分阶段：双写→回填（分批+批间校验）→灰度切读→全量→停旧写；不可逆点显式标识并单独评审；任意阶段失败可退回上一阶段。
5. feature flag 全生命周期：默认关闭、免发版开关、值班可达的紧急关闭路径、全量后限期清理（owner 登记）。
6. 影响面从依赖图逐行推导（上游调用方/下游消费方/数据变化/其他环境），通知状态列执行前不允许为空；沟通计划表格化（时间点×事件×受众×渠道×负责人）；值班安排含升级路径（角色而非个人）。

do/don't 对照：

```markdown
✗ 「全量上线，出问题再改」（把生产当测试环境）
✗ 「如出现严重问题，回滚至上一版本。」（无触发条件/无步骤/无验证）
✗ 灰度照抄 1%→5%→50%→100%（低流量服务的 1% 只有几个用户）
✗ 影响面写「无影响」（未逐项检查不允许出现这四个字）
✓ 「任意批次错误率基线 +0.5pct 或数据校验不一致，24h 内可回切旧版本；
  灰度期间增量数据为 v2 格式，由随本方案上线的兼容层读取——回滚不依赖 v2 代码」
✓ 监控含至少一条业务指标（防「错误率 0 但业务量归 0」），每项写正常基线
```

边界条件：具体灰度比例与窗口时长为组织级约定无普适标准；多个逻辑变更捆绑在一个发布会丧失独立回滚能力（一个出问题三个陪葬）；方案评审通过后计划变更须同步升文档版本。[模型经验]

### 场景 5：写 runbook（凌晨 3 点判据、验证段、危险操作纪律）

推荐路径（源于 [PT-13]）：
1. 为最坏情况读者写：第一次值班的新人 + 凌晨 + 认知降级——短句、编号步骤、每步预期输出、可复制粘贴的命令（占位符显式标记如 <REPLACE_ME:实例ID>）、明确的升级出口；判据——删掉这句话，值班者还能不能正确执行？能删则删。
2. 告警与 runbook 双向可达：告警文案含手册条目链接；条目标题与告警名一一对应，可按告警名搜索直达。
3. 处置条目四段式：症状（含告警名）→ 诊断（≤3 步分诊，每步含预期输出与分叉）→ 处置（编号步骤+预期输出）→ **验证（必做：可观察恢复判据 + N 分钟后复查，未达预期按升级矩阵升级）**；另设误报判别（确认后静默含期限，禁止永久静默）。
4. 升级矩阵按时限触发：P1 未确认 X 分钟→自动升级值班主管；处置 30 分钟无进展（判据：距上次「预期输出达成」超时）→ 服务 owner——写角色+排班查询链接，不写人名；升级 = 职责移交，不是求助失败。
5. 危险操作四件套：前置备份（未取得 backup_id 禁止继续）→ double-check 强制停顿（双人：粘贴值班群等第二人确认；单人：朗读 WHERE 条件 + SELECT COUNT(*) 确认影响行数 < 上限）→ 执行（含超时/失败行为）→ 执行后校验。
6. 保鲜纪律：事故后 N 小时内新增/修订条目（与复盘行动项联动——最大更新来源）；每季度随机抽条目演练并回写「最后验证日期」；失效条目**立即删除**，不做「可能过期」标注——凌晨 3 点没人注意「可能」二字。

do/don't 对照：

```markdown
✗ 「如果消息堆积，可能是消费者挂了……酌情处理。」（决策留给凌晨）
✗ 「遇到解决不了的问题，联系张三。」（人名无角色无时限，离职即失效）
✗ runbook 里出现「Kafka 原理简介」（手册写成教材）
✓ 「处置 A：1) 执行 <重启消费者命令>，预期 1 分钟内 consumer_count 恢复为 N。」
✓ 「验证：执行 <查看积压命令>，预期积压曲线下降；5 分钟后复查预期 <5 万；
  若不降 → 升级。」
✓ 危险操作：前置备份取得 backup_id 前禁止执行任何修复命令
```

边界条件：四段式与升级矩阵为实践归纳非官方标准；响应时限与 P1/P2 口径为组织约定；k8s 等平台命令随版本变化，模板中具体命令不保证长期有效；runbook 假设读者在认知降级下执行旧预案——不可套用 Diátaxis how-to 的写作建议。[模型经验]

### 场景 6：写故障复盘（blameless 措辞、时间线核对、行动项三类型、时限）

推荐路径（源于 [PT-14] [PT-15]，官方锚 [官方文档](https://www.atlassian.com/incident-management/postmortem)）：
1. 触发与时限：先定严重度阈值（Sev-1 及以上必做、以下可选，允许管理层对未达阈值事件主动要求）；解决后 24~48 小时内举行，不超过 5 个工作日；每份复盘必须被复审（建议每月 recurring 复审会）——未复审的复盘不如不写。
2. 开篇即 blameless 声明 + 措辞替换表自查：指摘句改写为系统与机制层（「XX 误删数据库」→「删除操作缺少二次确认与权限约束，且告警文案指向了该操作」）；报告不用于个人绩效评价。
3. 时间线工程：统一时区标注；四类关键节点（检测/响应/缓解/恢复——「检测」不得被「响应时间」冒充）；每个缓解动作标注效果（指标变化）；每节点标「来源」（告警系统/日志/工单）；关键节点附「如果…本可更早」标记（确认无提前空间显式写「无」，不允许沉默跳过）；MTTD/MTTR 单列并声明口径。
4. 根因双层：完整保留 5 Whys 追问链（不跳步；警惕群体回避不舒服的真相），终点分**技术根因**（机制层）+ **流程根因**（机制层——为什么现有流程没拦住）；追问到系统与机制为止，不到人。
5. 行动项：每条 = 类型（preventive/detective/responsive，**至少一条 detective**）+ 单人 owner + 期限 + 是/否可判定的验收标准 + 工单号；**转为 tracked issues**（不让修复烂在会议后），与其他工作同等排优先级；数量克制——宁可 5 条真做的不要 20 条装样子的。
6. 复盘里大段讨论「当初架构本该怎么设计」是越界到 ADR——止于一条「另立 ADR 讨论」的行动项。

do/don't 对照：

```markdown
✗ 根因：「XX 在处理告警时误删除了数据库表。」（到人即止，隐含指摘）
✗ 行动项：「1) 加强值班培训 2) 完善监控 3) 提高风险意识」（不可验证）
✗ 时间线一列时间一列事件，无来源列无时区声明（凭记忆拼凑）
✗ 摘要「影响较大」（无法行动的表述）
✓ 摘要：「持续 2h27m，影响 4.2 万请求失败（口径：下单接口 5xx），
  资损估算 8~12 万元（估算值），已恢复。」
✓ [detective] 为 X 指标加「基线偏离 > 3σ 持续 10 分钟」告警——owner/期限/
  验收：预发注入演练可触发并播报至值班群（是/否可判定）
```

边界条件：行动项三类型术语出处待验证（社区常见实践）；事故分级口径（P1/SEV-1）与资损计算口径各组织不同不可外推；近失（near-miss）事件建议同样复盘——免费教训不拿；跨团队/多依赖方故障需加「各方视角」小节，防止单视角线性叙事失真。[模型经验]

## 高频坑点（速查）

### 深度展开 Top 3

**Top 1：「出问题就回滚」——回滚预案不可执行**（违反 [PT-10]）
- 症状：回滚章节只有一句「回滚至上一版本」；事故中不知道谁有权拍板、步骤是什么；回滚完发现新代码写入的数据旧代码读不了，回滚丢用户数据。
- 根因：写方案时默认「不会出事」，回滚章节是评审要求下的应付产物；把「回滚」当状态词（回到旧版本）而非动作链（决定→关 flag→流量切回→数据处理→验证→通知）；系统性偏向前向兼容——注意力在前进路径，后向兼容只剩一句带过。
- 代码对照：

```markdown
✗ 「如出现严重问题，回滚至上一版本。」
✓ 「触发条件（满足任一，值班有权决定）：① 错误率 > 1% 持续 5 分钟；
  ② 数据正确性告警 10 分钟内无法定位。步骤：1) 值班广播回滚决定；
  2) 关闭 flag XX（预期 1 分钟内生效，监控面板新逻辑流量归零）；
  3) 确认旧路径错误率 5 分钟内回落基线；4) 通知依赖方群。
  数据兼容性：新代码写入数据带 version 字段，旧代码降级读取，不丢用户数据。」
```

- 修复：按场景 4 第 3 步回滚四件套重写；把「回滚后数据兼容性」当作回滚预案里最难最致命的字段优先补齐。[模型经验]

**Top 2：「测试完成、质量合格」——判据不可判定**（违反 [PT-4]，全局对应 [LAW-17]）
- 症状：准出段抄模板原话，发布决策会上谁都可以宣布达标；验收标准写成「系统应展示 X」式描述句，Then 后面接主观形容词；有条件放行不写条件。
- 根因：准出标准执行后补写（先打枪后画靶）；只生成第一层可判定格式，难的裁决规则（阻塞用例算不算分母？豁免谁批准？）被回避。
- 代码对照：

```markdown
✗ 「测试完成且质量满足要求」「导出功能应快速好用」
✓ 「Given 10 万行数据，When 用户点击导出，Then 30 秒内生成 CSV 下载链接，
  中断后可重试。」
✓ 准出：「P0/P1 通过率 100%；Blocker/Critical=0；P99 ≤ 300ms（100 并发基准）」
```

- 修复：准出在方案阶段冻结；验收/准出逐条过「是/否可机械判定」检查；主观词（完成/合格/稳定/易于使用）全文检索清零。[模型经验]

**Top 3：凌晨 3 点翻不到、看不懂、不敢做——runbook 断链与酌情**（违反 [PT-13]）
- 症状：告警响了先在群里问「有人见过吗」，花 20 分钟找手册入口；条目里「酌情处理」把决策留给凌晨、疲劳、不熟的执行者；执行完不知道成没成，只能等下一次告警验证。
- 根因：告警系统与文档系统两边没人负责对齐；作者在清醒的白天把「我理解这件事的过程」当成了「执行这件事的过程」；危险操作与普通操作在手册里长得一样，无强制停顿点。
- 代码对照：

```markdown
✗ 「消息堆积可能是消费者挂了……不行就重启，或者加消费者，酌情处理。」
✓ 「初判：执行 <查看消费者状态>，预期 consumer_count=N, status=running；
  若 N=0 → 处置 A：重启消费者，预期 1 分钟内恢复；
  验证：积压曲线下降，5 分钟后复查 <5 万；若不降 → 按升级矩阵升级。」
```

- 修复：告警文案含 runbook 链接（双向可达）；四段式重写条目（症状/诊断/处置/验证）；「酌情/视情况/适当」全文检索为零；危险操作加前置备份 + double-check 停顿点。[模型经验]

## 与其他子领域的集成要点

- **adr-changelog**（`kb/adr-changelog.md`）：design doc 与 ADR 分界——design doc 是一个课题的 how 全案（过程性、评审后使命基本完成），ADR 是单点决策的追加型记录（长生命周期、可被 supersede）；正确分工是 design doc 评审通过后把关键决策沉淀为若干条 ADR；反模式：一篇巨型 design doc 记五个决策（该拆 5 条 ADR），或 5 条 ADR 拼出没有整体设计的决策碎片。
- **doc-taxonomy**（`kb/doc-taxonomy.md`）：Diátaxis 不对位声明——本子域七类模板是组织内部工作文档，不硬套四象限判型（01~07 边界轮一致结论）；若需框架化定位，由 doc-taxonomy 的组织内部文档类型学承接。

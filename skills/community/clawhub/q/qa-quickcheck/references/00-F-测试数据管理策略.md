## F.1 测试数据管理策略

> 本节为所有涉及数据写入的测试（02 动态测试、04 性能测试、05 契约测试）提供统一的数据管理规范。

### F.1.1 测试数据隔离原则

| 隔离层级 | 方案 | 适用场景 |
|:---|------|------|
| **账号隔离** | 使用独立的测试账号（如 `test-user@example.com`），与真实用户账号分离 | 所有测试的默认方案 |
| **租户隔离** | 多租户系统中，使用独立的测试租户 | SaaS 平台 |
| **Schema 隔离** | 使用独立的测试数据库 schema（如 `test_` 前缀） | 后端 API 测试 |
| **数据标记** | 测试数据带 `__test__` 前缀或 `_test_flag=true` 标记 | 无法完全隔离时的兜底方案 |

### F.1.2 测试数据生命周期

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 准备阶段  │ ──▶ │ 执行阶段  │ ──▶ │ 清理阶段  │
│ (Setup)  │    │ (Execute)│    │ (Cleanup)│
└──────────┘    └──────────┘    └──────────┘
```

- **准备阶段**：在测试开始前，确认测试数据隔离方案可行。对于 05 契约测试的写操作（POST/PUT/DELETE），在 `contract-config.json` 中必须配置 `cleanup` 回滚端点。
- **执行阶段**：所有测试写入的数据必须带有可追溯标记（如请求头 `X-Test-Id: {uuid}`）。
- **清理阶段**：测试结束后必须自动执行数据清理。清理失败时在报告中标注「残留测试数据需手动清理：[数据标记/ID列表]」。

### F.1.3 破坏性测试数据安全

涉及删除、批量更新等破坏性操作时：
1. 必须先在测试数据副本上执行验证
2. 严禁对真实用户数据执行破坏性测试
3. 若测试环境无独立数据库，破坏性测试整节跳过，标注「破坏性测试跳过：无独立测试数据库」

### F.1.4 性能测试数据策略

- 性能测试产生的数据量可能较大，优先使用**可快速清理的独立表或集合**
- 测试结束后，性能测试产生的临时数据（如压测订单）必须全部清理
- 若项目使用缓存（Redis 等），性能测试结束后需清理测试产生的缓存 Key

### F.1.5 证据留存

- 所有测试数据的创建记录（ID、时间戳、标记）写入报告 D/E 节末尾
- 数据清理的执行结果（成功/失败/残留项）写入报告「环境能力声明」的补充说明

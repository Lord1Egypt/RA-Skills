# Task Market

## Chain identity

The reviewed production Task manifest enables creation on Base (`8453`), Injective (`1776`) and Avalanche C-Chain (`43114`); TEST uses Base Sepolia (`84532`). Read the available Task deployment and admission from the server and preserve the exact returned chain through preparation, funding, awards, reclaim and recovery. An authentication chain or CLI upgrade does not select the business chain. Report an actual completed action only after its wallet and server confirmation evidence.

## Requester

Use `task_market:discover`, `task_market:requester:read`, and `task_market:requester:write` as needed.

In a mounted Finch MCP harness, use these exact requester tools to create and prepare work: `task_market_task_create_draft`, `task_market_task_prepare_publish`, `task_market_task_review_board`, `task_market_task_prepare_review`, and, only when explicitly requested, `task_market_task_prepare_reclaim`. Wallet preparations return `walletIntent` and a structured `localAction`. Require CLI 0.5.1 or newer and check that installed help supports `--intent`, then execute the returned action using the same Account, wallet, endpoint and environment. The CLI fetches the immutable preparation and submits its wallet result with its active Session; no local MCP business grant is needed. A successful CLI result is a wallet receipt; re-read business state through MCP. Do not make a second manual confirm call after success. CLI 0.4.1 predates this handoff; upgrading the Skill alone does not upgrade the executable. Older CLI builds retain their existing preparation-file workflow during rollout. Draft `rewardAmount` and `perSubmissionReward` values are decimal USDC amounts; returned custody preparations use atomic-unit string fields such as `amountAtomic` and carry the authoritative `signingAuthority`.

1. Collect the title, instructions, collaboration and settlement modes, verification requirements, reward asset and amounts, submission limits, deadline, and participant constraints. Do not invent review policy or funding.
2. Create the draft and check its publication-review state before preparing publication through MCP. The four new Finch-reviewed Custom Task presets use `publication_custom`: website registration, product onboarding, product/feature trial, and form completion. They require Finch approval of the current revision before funding; standard goals and the legacy advanced `custom` goal retain their own rules. If publication requires review and no mounted review-submission tool is available, use the same Account's supported Browser review flow and wait for approval. Do not invent an MCP tool or fund an unapproved revision. After approval, call `identity_actor_get`, compare it with `finch status`, and hard stop if Account, wallet, or environment differs. Inspect the frozen pool preparation, show the exact transaction summary for approval, then run the returned `finch task publish-submit <TASK_ID> --intent <INTENT_ID>` action. It validates authority, broadcasts once, checkpoints the hash, and confirms atomically. Re-read approval after content changes; recover an existing funding operation through its returned recovery action instead of creating a second pool.
3. Re-read the Task and require the expected open and funded state.
4. Read the review board. For each user-authorized decision, prepare review through MCP, repeat the MCP/CLI identity comparison, show the award summary, and run the returned `finch task award-sign <TASK_ID> --intent <INTENT_ID>` action. The command records one EIP-712 signature batch and confirms review atomically; the runtime broadcasts the award. Do not create another signature batch after an unknown response. Verify approved submission, participation, award operation, fee, and remaining pool.
5. Reclaim only when the user explicitly requests it and the Task is eligible: prepare through MCP, repeat the identity comparison, show the transaction summary, and run the returned `finch task reclaim-submit <TASK_ID> --intent <INTENT_ID>` action. It broadcasts once, checkpoints the hash, and confirms atomically. Do not close or reclaim a Task merely to clean up a run.

### Original funding and reclaim recovery (CLI 0.5.6+)

CLI 0.5.6 saves original signed bytes/hash/nonce before Task approval, pool funding, revocation and reclaim broadcast. A failed checkpoint save prevents sending. Use only the returned `finch task recover <TASK_ID> <publish|award|reclaim>` action under the original Account, wallet and environment. It preserves the frozen funding amount and original stage evidence, checks the original transaction and can replay only those same saved bytes when absent. A missing receipt is insufficient to rebuild or re-sign a payment. Old hash-only records retain their existing receipt/confirmation limits. Award recovery reuses its saved signatures; do not generate another batch.

A confirmed reverted receipt is a failed transaction with the original hash and any allowance-cleanup status retained. Follow the exact returned guidance for saved cleanup or unsent cleanup; successful cleanup ends recovery. Keep journals and reconcile the existing operation before preparing a separate new business action.

### Merchant review, settlement and regional admission

For `merchant_manual` and legacy `delayed_auto_7d` Tasks, merchants may review and select winners from the Task start time until seven days after the Task deadline, followed by two days of settlement grace. Neither mode automatically selects or awards remaining participants. Remaining funds become eligible for return to the merchant Vault at day nine, subject to the funded pool's immutable on-chain deadline and any dispute freeze. Report a return only after confirmed settlement evidence; elapsed time alone is not a receipt. Standard FCFS and weighted-lottery Tasks retain their respective automatic policies.

New collaborative Custom/Register Tasks using the seven-day review option use `merchant_review_7d`; an explicitly selected deadline lottery keeps its lottery policy. The merchant may review and select winners from the Task start time until seven days after the Task deadline. A rejected participant may contest through Get Help until day eight, and Ops decides between days seven and nine. On day nine the platform pays each participant's latest review-admitted, pending submission, including Review Later and upheld contests, in submission order until reward slots run out. An unresolved contest does not freeze settlement. The new pool expires six hours after day nine; remaining funds can be returned to the merchant Vault only after pool expiry and confirmed settlement evidence. Do not promise a reward to every participant, and do not try to approve or reject after day seven. Already-funded pools keep their original mode and chain terms; a funded merchant_review_7d Task's end time is locked.

`review_later` marks an unfinished decision; untouched entries also remain unfinished. Exhausting awards or returning funds does not approve or reject these entries. Use the returned review window and remaining capacity when preparing an explicit award. Browser Excel import previews selected wallets and revalidates evidence; it is not approval or payment, and still requires the existing explicit confirmation and signing flow.

Task creation restrictions and final-submission restrictions are independent region policies. In a restricted submission region, the Account limit is two final submissions across Tasks, not a daily allowance. Respect the server response; do not switch Accounts, clients, or network origin to bypass admission.

### Expired requester award reservations

For an explicit requester cancellation, use the mounted `task_market_task_prepare_review` with `action: "cancel_award"` and the exact submission IDs (at most 100 per headless request). Only expired, unused, unsigned and unrelayed merchant-controlled preparations can be released. The server verifies chain usage and expiry; the last valid on-chain second is still valid. A successful cancellation releases the reservation and returns the submission to pending without a new wallet signature. Reassign only if the Task award window remains open. This does not revoke an already paid reward.

For persisted or externally paid awards, recover the existing receipt instead of generating a second signature/payment. Separately paid or partially paid batches may require restoring each submission separately; obey the returned recovery error. Re-read the review board after cancellation or recovery before preparing new awards.

## Participant

New Tasks include two fixed required official Goals: follow @FinchTechAI and post the current Task using its English/Chinese template. They are separate from the merchant quota; historical Tasks and existing drafts keep their original Goals. Complete official and merchant requirements in any order. Only real X verification completes official Goals, including accounts already following Finch; outages and manual approval cannot replace it.

The mounted MCP tools do not expose individual Goal verification or multi-goal final submission. Use the same Account's Web Task page to verify the official Goals, and to submit a multi-goal Task. A classic Task retains its original content/proof submission through `task_market_task_submit`, after its official Goals have been verified on Web. Compare Account and environment before moving between clients. Do not invent Goal tools or switch identities to satisfy the requirements.

Use `task_market:discover`, `task_market:participant:read`, and `task_market:participant:write` as needed.

In a mounted Finch MCP harness, use `task_market_tasks_list`, `task_market_task_get`, `task_market_task_join`, `task_market_task_submit`, and `task_market_task_my_submission` directly. Do not spend time searching for alternate Task tool names after these mounted tools are available.

1. List and inspect the exact open Task, its verification requirements, deadline, reward, and remaining capacity.
2. Call `identity_actor_get` and verify that this participant is a different Account from the Task requester. A requester cannot join or submit to its own Task. Use a separately authorized Account B rather than silently switching Account A's wallet or OAuth identity.
3. Join once with a stable idempotency key. Submit only user-provided content, proof URL, and attachments that satisfy the published requirements. Attachments must be uploaded Finch proof locators or HTTP(S) links; local paths and `file:filename` placeholders are not uploaded evidence. Task covers are retired; omit `imageLocator` or pass null when creating a draft.
4. Read `my_submission` and report its stable participation and submission IDs. Do not self-approve or infer an award.
5. After requester review, re-read the submission and Task; distinguish approved, rejected, pending, and paid states.

When X verification returns `manual_review` with `x_daily_credit_limit_exceeded` or `x_credit_budget_unavailable`, report the unmet verification requirement and returned recovery guidance. Required automatic checks must actually succeed before final submission; a budget error or bare manual-review status does not bypass admission. Web and MCP share the daily budget; respect returned retry limits. For requester-review goals, valid format evidence with its matching verification receipt can enter merchant review without becoming automatically verified or paid.

X verification has an Account-wide limit of 30 verification executions in a rolling 24-hour window, shared by Web and MCP. Short-window Task/Goal limits and the platform API budget still apply. The automatic retry within one owned execution reuses its Account allowance, while provider calls remain subject to the platform budget. On `TWITTER_VERIFICATION_LIMIT_REACHED` (HTTP 429), report the retry time in the error and wait until then. On `TWITTER_VERIFICATION_IN_PROGRESS` (HTTP 409), wait two minutes and retry the same request with the same idempotency key and payload. A completed request reuses its stored result; an uncertain provider attempt may consume another allowance when recovered. On `IDEMPOTENCY_CONFLICT` (HTTP 409), reconcile the original request before submitting any changed intent with a new key. Switching clients or identities is not a recovery path for these limits.

Task join and submit may also be restricted by current operator controls, independently of the displayed Task lifecycle. Re-read the Task and report the returned restriction; Web and MCP share these controls. Resume only when the operation is allowed again.

Keep a Task's publication, participant mutation, review, and reclaim idempotency keys separate. A delayed response is not permission to create a second Task, submission, or award. Recover an irreversible requester action only with `finch task recover <TASK_ID> <KIND>`, where `KIND` is exactly `publish`, `award`, or `reclaim` as reported by the journal. The command uses the active CLI Session and reuses the recorded hash or signature batch and idempotency key; it does not need the original preparation file or an MCP grant. For a pre-upgrade v2 journal, it adopts the original server preparation audit receipt and compares the saved plan before resuming. A missing receipt or differing plan requires reconciliation; preserve the journal and report the error. A journal containing a hash or signatures can only be recovered, never abandoned or deleted by hand.

An end-to-end Task validation requires two isolated actors: requester A publishes and later reviews/awards; participant B joins and submits. Each actor must have its own Account, wallet, OAuth authorization, Finch home, and clean context.

## X and Telegram evidence

For an original X post or Quote Tweet, submit the participant's exact post URL; validation checks that post's author and the Task requirements, including the quoted target. Native Retweet uses the bound account and queries one page of up to 20 recent results within two hours. Only an empty result triggers a 30-second wait and one automatic re-query. If both results are empty, `x_retweet_search_empty` remains retryable: report that the action is unconfirmed and a new Verify attempt can be made later, respecting returned limits. Replaying a completed request retrieves its stored result rather than running a fresh check. Older activity or missing results may not be verifiable; do not claim that an arbitrary historical retweet is guaranteed to qualify.

Telegram participation uses a screenshot URL submitted as evidence for requester review. It is not automatic group-membership verification. Collect real user-provided evidence and never fabricate a screenshot or claim a successful membership check.

In the Web workbench, supported proof images and videos are uploaded and verified before submission (up to 10 MB per file). Upload success alone does not send evidence to the requester: submit the evidence or the final Task. Final submission saves pending manual/Telegram goal evidence first; `manual_review` makes those goals ready for requester submission, not automatically approved or paid. Re-read saved evidence after an interrupted submission before retrying. A historical filename-only record contains no recoverable file bytes and requires the participant to upload again.

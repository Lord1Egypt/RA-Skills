# 改写范式（Rewrite Patterns）

改写不是把话说漂亮，而是把"读的人（或 Agent）无法执行的句子"换成"能照着做的句子"。下面十条覆盖了绝大多数扣分项，按 D1–D6 顺序排列。

## 速查表

| 编号 | 症状 | 对应维度 | 范式 |
| --- | --- | --- | --- |
| R1 | 触发词泛化 | D1 | 受控词表 + 反触发 |
| R2 | 场景写成口号 | D1 | 场景句 = 人物 + 触发条件 + 期望产出 |
| R3 | 空话动词 | D3 | 动词 + 对象 + 阈值 |
| R4 | 流程缺失败分支 | D3 | 每步补"失败怎么办" |
| R5 | 步骤之间断链 | D3 | 上一步产物即下一步输入 |
| R6 | 验收写成形容词 | D4 | 布尔判据 + 可数阈值 |
| R7 | 边界缺失或模棱两可 | D2 | 条件 + 处置 + 与流程对齐 |
| R8 | 大段背景挤占上下文 | D5 | 摘要句留正文，细则下沉 references |
| R9 | 产出无骨架 | D4 | 给章节／字段／字数区间 |
| R10 | 命令不可复制 | D3 | 参数化 + 一条可直接跑的示例 |

## R1 触发词泛化 → 受控词表 + 反触发

- **原文**：`trigger: 写报告`
- **问题**：命中一切写作请求，与通用写作技能正面冲突，误触发后产出错误格式。
- **改为**：

```yaml
trigger_keywords: [周报生成, 月报生成, 经营分析报告, 数据汇报稿, 会议纪要转报告]
```

- **补一条反触发**：`不要触发：需要虚构情节的文案、纯翻译任务、需要实时行情数据的报告。`
- **判据**：新触发词逐个能对上正文的一处场景；反触发至少 2 条。

## R2 场景写成口号 → 场景句三要素

- **原文**：`适用于各种办公场景。`
- **问题**：任何人都无法判断"我的情况算不算"。
- **改为**：`我要把本周的零散记录整理成一份能直接发给上级的周报，且手头只有聊天记录和待办清单。`
- **判据**：去掉主语"我"之后，句子仍能说清触发条件与输入形态。

## R3 空话动词 → 动词 + 对象 + 阈值

- **原文**：`对内容进行适当优化。`
- **问题**：没有对象、没有边界、没有完成条件，"适当"由谁定？
- **改为**：`删除重复表述，把超过 3 句的段落压到 2 句以内，保留全部数字与专有名词。`
- **判据**：改写后能用"是否做到"回答，不需要再问一句"什么意思"。

## R4 流程缺失败分支 → 每步补"失败怎么办"

- **原文**：`3. 调用接口获取数据。`
- **问题**：接口失败时流程没有出口，Agent 会自行编造或空转。
- **改为**：

```
3. 调用接口获取数据。
   判据：返回体含 date、value 两个字段且 value 非空。
   失败怎么办：重试一次；仍失败则改用上一次缓存数据并在交付物首行标注"数据截至 <日期>"；无缓存则终止并报告缺失字段。
```

- **判据**：每一步都能回答"这一步失败时，下一句是什么"。

## R5 步骤之间断链 → 产物即输入

- **原文**：`2. 分析数据。 3. 生成报告。`
- **问题**：第 3 步不知道吃的是第 2 步的什么产物，容易重新取数或直接编。
- **改为**：`2. 产出 <指标表>：每个指标一行，列为 name、period、value、source。 3. 以第 2 步的指标表为唯一数据源生成报告。`
- **判据**：每一步的产物有名字，且下一步显式引用这个名字。

## R6 验收写成形容词 → 布尔判据 + 可数阈值

- **原文**：`- [ ] 报告内容完整、逻辑清晰。`
- **问题**：永远打不上勾，也永远打不了叉。
- **改为**：

```
- [ ] 报告含四节，顺序为背景／数据／结论／建议
- [ ] 每个结论段落至少引用一个指标表条目
- [ ] 全文不超过 1,200 字
```

- **判据**：任何一条都能由第三个人在不询问作者的情况下判定真假。

## R7 边界模棱两可 → 条件 + 处置

- **原文**：`- 不处理复杂情况。`
- **问题**："复杂"没有定义，且没说碰到时不做什么。
- **改为**：

```
- 输入文件超过 5 个时不合并处理：改为逐个输出，并在末尾附汇总索引。
- 涉及未公开接口时不猜测参数：直接拒答，返回缺失信息清单。
```

- **判据**：每条边界都有 if 条件与 then 动作，且动作与工作流的失败分支同名。

## R8 大段背景挤占上下文 → 摘要句 + 下沉

- **原文**：连续 60 行讲行业背景与方法论出处。
- **问题**：每轮都被重发，成本高且稀释关键指令。
- **改为**：正文留一句 `方法依据见 references/method.md`，把 60 行移入该文件；正文只保留"何时必须读它"的一句话。
- **判据**：下沉后正文每一行都在指令链上，删掉任一行都会让某步无法执行。

## R9 产出无骨架 → 章节／字段／区间

- **原文**：`输出一份专业的分析报告。`
- **问题**：格式不可预期，每次都不一样，无法验收也无法复用。
- **改为**：`输出 Markdown：## 结论（3 条以内）／## 数据（表格，列为 name、period、value）／## 建议（每条含动作、负责人、截止日）／## 风险（0–3 条）。全文 600–1,200 字。`
- **判据**：拿到产出的人不用问"还缺什么"就能判断是否完整。

## R10 命令不可复制 → 参数化 + 一条示例

- **原文**：`运行脚本处理数据。`
- **问题**：脚本名、参数、路径全缺，等于没写。
- **改为**：`python scripts/collect.py --input <数据目录> --since <YYYY-MM-DD> --out <输出目录>`，并附一条填好占位符的完整示例。
- **判据**：把尖括号内容替换成自己的值即可直接执行，不需要读源码。

## 改写纪律

1. 只改表达，不新增事实：原文没有的数字、依赖、链接一律不补；确需补，标注"待作者确认"。
2. 节数守恒：改写前后二级标题数量一致，可合并同类节，但要在改动摘要里写明合并了哪两节。
3. 一次只改一类问题：同一批 diff 里不混入风格调整，便于逐条复核。
4. 改完必须复测：重跑脚本，总分应上升；不升说明改错了方向，回退而不是硬解释。

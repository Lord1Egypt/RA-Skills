# 机制价值裁定（这个节点 / 角色 / 门该留吗）

用于：主人指着一个**已经设计好、已在文档/真源里占位**的机制问价值 —— 流水线节点、角色卡、一道门、一个必读段节、一项仪式 —— 问「到底有没有价值」「这角色是干嘛的」「是不是该删」。
产出：**五条证据轴的实测表 + 裁决定论（保留 / 降为 opt-in / 退役）+ 落地动作 + 防回潮守卫**。
（找缺陷走 `multi-dimension-audit`；核验一份审计报告的断言走 `skill-audit-remediation`；加门走 `self-audit-gate-authoring`；改真源极性时的同步面见本技能「改极性」分支。）

**不要跳过普查直接答。** 这类问题的默认错法是拿设计意图当证据（「协议写了三类剧本，所以它有用」）。设计的**存在**只证明它曾被想要过，不证明它挣回了成本。

## 五条证据轴（按此顺序取证，缺一条就不算定论）

1. **产出普查 —— 实跑目录里到底有几份该机制的产物**
   扫该机制**所有**历史实跑的项目目录（不是仓库，是运行时产物根），按产物文件名找。**零命中**是最强的单条证据：文档写得再全，40+ 次实跑一份产物都没有，说明它从未真正跑起来或跑了没人留。
   关键：普查范围必须是**该产物按设计应当出现的那个目录**（审计报告在 `audits/`、回查报告在 `literature/`），扫错目录会得到假的零。
   **普查不到文件时改查运行时遥测**：不少机制不落产物文件，只在运行日志里留记录（审计日志、调用日志、事件账本）。此时按**能区分代码路径的判别字段**统计，而不是按 feature 名统计 —— 同一 feature 下常有单条/批量/降级多条路径，字段形态不同（例：审计条目里 answers 的键名 `injection` vs `screen` vs `segN` 分别对应单条、整批筛查、逐段定位）。按 feature 汇总的调用量会把「优化路径几乎没跑」淹没在「旧路径跑得很多」里 —— 实测某批量级联设计宣称降 8 倍调用，汇总看调用量正常，按判别字段拆开才发现批量路径 17 次、单条路径 10490 次，优化从未兑现。
   **判别字段的取法**：先看该机制各条路径写出的记录在结构上哪里不同（键名 / 枚举值 / 字段数量 / 嵌套层级），再用它做分组统计；分组后某路径计数接近 0 ⇒ 该路径在生产里等于不存在。

2. **消费方追踪 —— 产物写出来后谁读它**
   全仓 grep 产物名，列出会读它的节点/文档；再读该机制自己的协议文本，**它往往自陈没有下游**（「不改变评分 / 不代替 X / 不自行触发修订 / 默认不写入交付说明」）。自陈无下游 = 产物写完即终点，主人永远看不到。
   有真实的 `after_each` / `next` 回边把产物接回流程 ⇒ 消费方成立。

3. **执行者位置 —— 执行者是否已读过全部材料**
   问：执行这个机制的角色，**在此之前读过它要审的那些东西吗**？读过 ⇒ 它的「独立发现」是全系统里最可能为空的。整条管线以「对抗必须独立」为脊时，让读过全部材料的主体去当攻击者，是结构性失效而非执行质量问题。
   反向判据同样成立：执行者**必须出网/出仓才能取到**的信息（论文是否真实存在、原文怎么表述），是全管线上唯一「读再多遍也推不出来」的工作 —— 这类机制即使产出少也**别动**。

4. **成本轴 —— 它压在谁身上**
   谁执行 × 要读多少。owner 亲为 + 需重读主产物全文 = 压、管线上最稀缺的 agent 上的最大单笔开销，且方向常与「落盘减负」纪律相反。

5. **同类对照 —— 同类节点有产出吗**
   找**同一 kind**（同 owner_agent / 同 spawned leaf）的另一个机制，同样普查一遍。**它有产出、本机制没有** ⇒ 证明零命中是本机制的性质，不是普查方法坏了、也不是管线整体没跑。这一条是防「假零」的关键。

**同一把尺子要能同时裁定两个方向。** 拿两问作对照能省掉整轮争论：一问「有没有价值」的机制若五条轴全绿、另一问全红，两条结论互为证据。

## 定论与落地

- **保留**：产出普查有命中 **且** 有真实消费方。
- **降为 opt-in**：机制**内容**有价值（对应真实外部实践）但**默认触发**挣不回成本 —— 实跑零产出 / 无下游 / 成本高。⇒ **改极性，不删**：真源 `default: triggered → opt_in`。
- **退役**：内容与覆盖都被既有机制吸收，无外部对应物可保留。

### 改极性分支（降为 opt-in 时按此执行）

改一个节点的触发极性是**「改 A 漏 B」高风险族**——真源一处改完，简报/角色卡/协议/派生视图/计数多处会静默留在旧口径。

1. **先枚举同步面**：grep 该机制全部散文点，**只列不改**；重点抓状态声明词（`默认触发` / `opt-out` / `默认启用` / `默认不跑`），它们散在简报模板、角色卡、协议、派生视图行里。
2. **真源换键并登记**：opt-in 用 `condition` + `on_not_triggered`（未开启 ≠ 漏跑）+ `condition_undecidable`；条件键在顶层注册表补 `producer` + `producer_marker`。
3. **改生成器时做极性中立**：让「键在载体」的机械检查遍历节点声明的**任一**契约键（`condition` / `opt_out` / `opt_in`），而不是写死一种 —— 键名或极性再变时改切片即改门。
4. **落防回潮守卫**：新测试锁死新极性（切片 + 条件键已登记 + **旧键全仓消失** + 呈现面归属），并配**反向注入**：把极性改回去 ⇒ 判据必红。
5. **顺带核对相邻计数**：极性一改，常量计数会当场归真或对不上（如「默认启用项」写了 N 项、实列 N+1）—— 这是免费的对账机会，别放过。

## 借鉴外部实践时的前置对照（写之前先按功能扫本仓）

主人拿一个**外部项目 / 框架**问「有什么可借鉴」、你准备照着它**新增一个机制**时，先做一步对照再决定动不动手：

- **按功能扫，不按名字**：既有等价物常**另起名** —— 实测：准备新增的「trace 事件流」与既有「B5 事件账本 / `control/events/`」功能重合，**名字零重叠**，按名字检索必漏。要问的是「**谁已经在产出同类东西**」，不是「有没有叫这个名字的文件」。
- **等价物已在 ⇒ 不新增**（并接上面的「退役」判定）：新写的只是**第二份真源**，违反单源纪律；要么把新需求指回既有真源，要么证明新机制**严格多出**既有物不具备的能力，否则不写。
- **「更简单」是警报不是优点**：既有机制里看似冗余的设计（如「每事件独立文件」）常在**挡一个已踩过的坑**（并行整文件覆盖）；照外部做法重实现时若省掉它，就是**重新引入**那个缺陷。动手前先读既有机制「为什么这么设计」。
- **对照结论要可被否证**：写「既有 X 已覆盖该功能」时附**证据路径**（哪个文件 / 哪条测试），不凭印象断言「没有」。

## 边界

- 裁定的是**成本**，不是**对错** —— 机制「有价值」与「该默认跑」是两个问题，答案可以相反。
- 普查是**只读取证**，不跑流水线、不改真源；改极性属主控决策，主人拍板后再动。
- 证据不足时如实说「查不到产物」，不把**没扫到**写成**没产出**（两者靠第 5 轴区分）。

# 阶段 3 规程 — Distill 双源融合蒸馏

目标：把阶段 1（模型萃取）与阶段 2（文档锚点）两路语料融合为结构化、可长期使用的知识文件。

## 知识三层金字塔（产物构成哲学）

知识库以**正向指导为主轴**，三层知识各有分工，比例目标：**法则 ≈ 15% / 最佳实践 ≈ 45% / 坑点 ≈ 40%**（坑点是法则的负样本佐证，不是主角）。

| 层次 | 性质 | 回答的问题 | 形态 |
|---|---|---|---|
| 法则（宪法条款） | 约束性 | 什么**永远不可违背** | MUST/NEVER/ALWAYS 编号条款 |
| 最佳实践 | 建设性 | 这个场景**该怎么做** | 场景 → 推荐路径 → do/don't 代码对照 |
| 坑点 | 防御性 | 犯错了**怎么解释** | 症状 → 根因 → 修复（速查形态） |

## 融合规则（逐条判定）

对每个知识原子（法则/实践/坑点/速查条目），判定来源关系：

| 关系 | 处理 | 标注 |
|---|---|---|
| 模型知识与文档**一致** | 保留 | `[官方文档](url)` |
| **冲突**（尤其版本号/API 签名/破坏性变更） | **以文档为准**，登记冲突点 | `[官方文档](url)` |
| **模型独有**（文档没有的隐性经验、AI 典型错误） | 保留（核心价值） | `[模型经验]` + 附「为什么/何时适用」 |
| **文档独有**（模型未覆盖） | 保留 | `[官方文档](url)` 或来源 URL |
| 推断性内容 | 保留但降级 | `[推断]` + 附推理依据；**不得进入**「法则」「最佳实践」「高频坑点」「API 速查表」「版本注意」区块 |

冲突登记：每个 kb 文件尾部维护「冲突消解记录」小节（模型原认知 → 文档事实 → 采用结论）。纯模型模式（文档抓取降级）时，来源索引显式声明「未经文档验证」。

## 产出清单

1. 每个 subdomain 一份：`output/<skill_name>/kb/<subdomain>.md`
2. 横切文件（按领域配置 `cross_cutting_files`）：
   - `laws.md` — **全局宪法**：从各 subdomain 法则化萃取中收集 `[GLOBAL]` 候选 + 跨领域通用原则，去重合并，统一编号（`LAW-1`、`LAW-2`...），按主题分组（版本纪律/状态纪律/安全纪律/数据纪律等）；每条含违反后果与溯源
   - `ai-mistakes.md` — 从各 subdomain 自我质询轮汇总的「AI 写该领域代码的典型错误」总集，按 subdomain 分节
   - `gotchas.md` — 跨 subdomain 高频坑点 Top 汇总（每条一句话 + 指向详细 kb 文件的引用）。**Top 判定标准**（满足其一）：a) 跨 ≥2 子领域的共性坑；b) P0 级——构建失败/数据错误/安全漏洞/应用崩溃；c) 静默失效类（无报错但功能失效，LAW-14 族）且单领域高频。不达标的坑点留在子领域 kb，不入 Top。
   - `patterns.md` — 通用最佳实践（选型决策、项目结构、性能、测试等跨子领域主题）

### 骨架适配与豁免（类型化豁免，免逐文件登记）

「顺序不可变」适用于编程类子域；以下类型化豁免自动成立，无需逐文件登记：

1. **非编程域子域**（如 ui-ux-design 全域）：「API 速查表」不适用 → 以「参数/规范速查表」替代或整节省略。
2. **模板/文书类子域**（kb 主体为可复制模板正文，如 proj-docs、doc-templates、app-templates、industry-themes）：「API 速查表」「版本注意」不适用 → 省略；模板正文内嵌的小节标题**不参与骨架合规判定**——模板区以 HTML 注释 `<!-- template-body: start -->` / `<!-- template-body: end -->` 定界，定界之外的小节才计入骨架。
3. **横切文件**（laws/ai-mistakes/gotchas/patterns）：骨架可简化，「来源索引」一律必需。
4. **审计/图谱类 spin-off 子域**（如 wcag22-audit、aria-patterns）：按检查表/契约性质自定骨架，「来源索引」必需。

**标题别名表**（合规判定按语义不按字面）：

- 「API 速查表」≡「API/配置速查表」≡「配置速查表」
- 「高频坑点（速查）」≡「高频坑点」

「定位与心智模型」「法则」「最佳实践」「来源索引」为编程类子域不可省略小节（命中上述豁免类型的除外）。

### 法则条款规范

1. **可判定**：条款必须能机械判断"是否违反"。「写好代码」不合格；「派生值不得存 state」合格。
2. **编号可引用**：领域内条款用 subdomain 前缀（如 `[RA-1]` react-admin、`[NX-1]` nextjs），跨领域条款进 `kb/laws.md` 用 `LAW-N`；kb 正文与横切文件引用法则时用编号。
3. **配后果**：每条必须写违反后果——后果是法则可信度的证据。
4. **数量**：每个 subdomain 8~15 条（15 为硬顶）；全局宪法 10~20 条。宁缺毋滥。
   - **达顶政策**：subdomain 法则满 15 条后不再追加新编号，三选一：a) 并入既有法则（保留小编号、修订条款，「冲突消解记录」登记）；b) 替换已失效/被证伪法则（编号在「冲突消解记录」登记退役后复用）；c) 降级为坑点表条目。禁止开新前缀绕过上限。
   - **存量超顶豁免（grandfather）**：达顶政策新立前已超 15 的既有基线前缀（当前仅 TQ=17）冻结现状——不再追加新编号，后续修订优先按三选一收敛至 ≤15；豁免须在「冲突消解记录」登记在案。
   - **退役**：法则被文档证伪或长期失去适用场景 → 移除并登记退役原因，不静默删除。
5. **官方规则优先**：官方明文规则（如 Rules of React、Rules of Hooks）升格为法则并附文档 URL；模型经验提炼的法则标注 `[模型经验]`。

### 最佳实践章节规范

1. **场景化组织**：不按 API 组织，按「用户要做什么」组织（如「接入自定义 REST 后端」「实现乐观更新」）。
2. **每场景四要素**：推荐路径（步骤化）→ do/don't 代码对照 → 边界条件（何时不适用/何时退化）→ 来源标注。
3. **与法则呼应**：实践背后如有法则支撑，引用编号（如「本实践源于 [RC-2]」）。

### 坑点速查规范

1. 表格速查为主：`| 症状（含报错原文） | 根因 | 修复 |`。
2. Top 1~3 高危坑点保留完整结构（含代码对照）。
3. 坑点必须能反向指向某条法则或实践——孤立的坑点砍掉或并入速查表。

## 质量纪律

1. **正向指导优先**：「最佳实践」与「法则」合计篇幅 ≥「坑点」；回答"该怎么做"永远先于"别这么做"。
2. 代码对照最小可复现，错误代码要典型（AI/新手真实会写出的样子），不要树稻草人。
3. 单文件 ≤2000 行；超限拆分（如 `react-core.md` → `react-core.md` + `react-core-advanced.md`），而不是压缩删减。
4. 语言跟随领域配置（默认中文），代码/API 名/术语/报错保留英文。
5. 每个知识原子自带来源标注，不靠上下文推断。
6. 拒绝教程化叙事：不写「让我们」「接下来我们」，直接给结论与证据。

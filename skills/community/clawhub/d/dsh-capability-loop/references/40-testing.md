# 40 · 测试方法：可追溯的 oracle 与门禁

> 核心：自动化测试「不完整/结果不准」的根因通常不是用例少，而是 **test oracle（期望值来源）不可靠**——行业专家/AI 推断 ≠ 系统真实规则。
> 策略：**把业务真相变成可追溯资产，测试只对高置信规则宣称通过。**

## 1. 问题分解

| 现象 | 根因 | 对策 |
|---|---|---|
| 用例看似齐全却漏关键业务 | 不知道系统真实业务/规则 | 《业务规则台账》R-ID + 来源 + 置信度 |
| 测了但与业务不符 | 行业专家/AI 推断 ≠ 系统规则 | AI/女娲只当**假设生成器**（C 级），owner 确认后升级 |
| 遗留系统无文档 | 无规格可比对 | 特征测试/Golden Master/差分/生产日志回放 |
| 测完仍出生产问题 | 只测「能跑」，没测不变量/异常/数据缺口 | 三类 oracle + 生产防护 + 事故回归 |
| 无法判断能否上线 | 没有可追溯证据 | 规则覆盖率 + 置信度分布 + 门禁 |

## 2. 业务规则台账（唯一权威 oracle 源）

模板 `upgrade/team/business-rule-ledger.md`，落到项目 `docs/business-rules.md` 或任务目录。字段：
`R-ID | 优先级 | 规则陈述 | 来源 | 置信度(A/B/C) | 负责人 | 适用范围 | 状态 | 关联用例`

- **A**：权威来源（政策/合同/需求验收标准/负责人书面确认）+ owner 确认；
- **B**：有代码/DB/生产日志佐证但未确认；
- **C**：推断/行业经验（**不得单独作为「通过」依据**）。
- 来源优先级：监管/合同原文 > 需求验收标准 > 代码与 DB 约束 > 生产日志/历史工单 > 行业经验。
- 冲突（政策 vs 代码）→ 标「冲突待裁决」，相关用例 SKIP，不得判 PASS，由 owner 裁决并记录。
- 升级条件：口径会/owner 签署，记录签批人与日期。

## 3. 三类 oracle（交叉验证，避免单一来源）

| 类型 | 做法 | 适合 | 注意 |
|---|---|---|---|
| **规范型** | 按台账期望值断言 | 有明确规则/验收标准 | 规则必须 A/B；C 级不能单独判定 |
| **行为型** | Golden Master、录制回放、新旧差分 | 遗留系统、无文档 | 只证明「与现状一致」，不证明正确 |
| **不变量型** | 对账平衡、幂等、状态机、金额守恒、顺序/时序 | 交易/账务/状态流转 | 能发现「规则没写但必须成立」的错误 |

## 4. 分层与沙箱边界

L1 单元 → L2 集成 → L3 E2E 浏览器 → L4 视觉 → L5 性能/稳定。
- **L1/L2 优先**；L3/L4 能跑则跑，不能跑必须标「未实测 + 原因 + 补测方式」；
- 普通 DSH 沙箱下浏览器/视觉**不可用**（Chrome crashpad 被进程沙箱拒绝，`OpenProcess 拒绝访问 (0x5)`）：路径 **A** 全权限会话 / **B** 用户终端截图 + `read_image` 评审（推荐）/ **C** 手动截图并标注未实测；
- 外部网络不可用 → mock/fixture 或明确 SKIP 并写原因；
- **禁止假绿**：不把「没跑」写成「通过」；不改被测实现让测试变绿；需要改代码时交回 Engineer，由 Reviewer 复核。

## 5. 执行规范（每条命令都要可复现）

1. 用项目自己的入口（`package.json`/`pyproject.toml`/`Makefile`），不另造框架；
2. 记录：完整命令、工作目录、退出码、关键输出（不可只贴「成功」）；
3. 失败先分类：环境（缺依赖/网络/权限）/ 用例问题 / 真实缺陷，分别处理；
4. 产物放 `test-artifacts/`；报告 `test-report-YYYYMMDD.md`。

**报告结构**：范围与环境 → 规则覆盖（P0 100%、P1 ≥80%、A/B/C 分布、C 级未确认清单）→ 结果（PASS/FAIL/SKIP + 命令 + 证据）→ 失败分类 → 未覆盖/未实测（原因 + 补测）→ 生产风险与防护 → 结论。

## 6. 可追溯门禁

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "upgrade\team\test-traceability.ps1" -TaskDir "<任务目录>"
```

检查：① 台账存在且字段齐全；② P0 规则必须有绑定用例、置信度不得为 C、状态不得「待确认/冲突」；③ P1 覆盖率 ≥80%；④ 用例/报告必须引用 R-ID 或标 `exploration`；⑤ 报告宣称 PASS 但存在 C 级未确认规则 → 风险告警。
退出码：`0` 通过（允许 warning）/ `1` 有 FAIL / `2` 参数错误。**没有台账直接 FAIL**。

真实案例（源环境）：`projects/输差管理` 文档门 100/100 PASS，但追溯门 **FAIL 13 项**——原因正是 P0 规则待口径会签署 + 部分 P0 仍是 C 级 + P1 覆盖 50%。**这正是门禁该拦的**：口径未签、数据缺口未关之前，不允许宣称「测试通过」。

## 7. 生产防护与事故闭环

- 上线兜底：影子流量/差分、金丝雀、功能开关、运行时断言、回滚预案；
- 线上事故 → 新增/修正 R-ID → 补回归用例 → 更新台账 → 下次回归；
- 用「规则覆盖率」替代「行覆盖率」作为对业务负责的指标（行覆盖高不代表业务对）。

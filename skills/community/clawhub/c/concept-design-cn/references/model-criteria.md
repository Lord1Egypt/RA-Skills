# 模型判据

以需求和反例判断概念是否成立、组合是否恰当、子集是否可用；形式、规则数量与流程长度不能代替证据。记法见[规格记法](spec-notation.md)。

## 成熟能力

建模前先分出成熟能力：已有成熟、可替换的实现，且不承载本产品差异规则的技术或业务能力。按它对本产品用户的目的归类，不按技术名称：

| 类别 | 模型表达 | 实现 |
| --- | --- | --- |
| 本产品的差异化业务规则 | 完整概念 | 业务模块 |
| 有用户可感知目的的成熟能力，如会话、通知、支付 | 薄概念或外部入口契约，只写可观察行为 | 经使用方端口由 outbound 适配器复用成熟组件 |
| 无用户目的的技术机制，如缓存、重试、连接池、序列化 | 不进入模型 | infrastructure 或适配器内部 |

同名可异类：餐厅叫号队列是概念，消息传输队列是机制。业务不变量即使由存储或组件代为强制，仍在概念中声明。组件模型不进入概念状态。是否复用属于产品决定，记入决策记录。

## 概念

概念应**面向用户**、**具有语义**、**独立可理解**，并具有服务明确**目的**的**行为**。API 程序员也是用户；语义包括抽象的**静态结构**和**动态行为**。

**目的性**要求目的为用户理解，并且本身带来价值。**端到端**要求功能完整兑现目的：认证不能只有注册。若**运作原理**只描述动作如何更新状态，说明仍有内容缺失。

**熟悉性**使用户能够沿用经验，但也允许新概念。**可复用性**通常来自**独立性**、**目的性**和完整功能，不要求先有复用实例。**大多数设计是对已有设计思想的改编、扩展和组合。**

以上八项依据 Jackson 的[概念判据](https://essenceofsoftware.com/tutorials/concept-basics/criteria/)，用于辨认概念。类、界面控件、功能点或单条用户故事，不能仅凭其形式认定为概念。

## 组合

**概念定义局部行为，同步定义协作。** 组合可以收紧可发生的行为，但必须保持参与概念的契约。

| 场景中的问题 | 调整方向 |
| --- | --- |
| 必需联动没有发生 | 收紧同步。 |
| 自动化夺走必需的手动控制 | 放松同步，或允许配置。 |
| 组合偏离概念目的 | 重查边界与契约。 |

access、notify 等协调动作也须有契约；日志或队列只有具备独立目的与完整行为，才可能成为概念。

## 同步图

每条规则一个节点：全部 `when` 输入共同成立，`where` 单独表示读取，`then` 保留全部目标且不隐含顺序。简化箭头仍须保留规则名与合取关系；生成格式见[图契约](tool-diagram.md)。循环须终止或受控持续运行，工程截断须可观察。

## 产品子集

内在依赖将另一概念的定义嵌入本概念，应改为类型参数或外部协调。外在依赖来自产品需求：`A → B` 表示当前产品保留 A 就需要 B。代码耦合或类型绑定不能单独证明这种需求。

产品子集 S 须满足依赖闭包：**若 A ∈ S 且 A → B，则 B ∈ S**，因此依赖环中的成员一起保留或排除。闭包只是必要条件；子集还须有明确目的、可用入口、有效的剩余规则和资源。产品依赖图与同步图分别表达。

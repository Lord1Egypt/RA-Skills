# 把想法收回来 · 使用反馈协议

> ClawHub专用v2.7.4，独立MIT-0版；处理建议与吐槽，原创事实摘要投稿见 `CONTRIBUTING.md`。核心四类判定与不打扰规则仍在SKILL前置，详细协议不取代它们；反馈不自动收集第三方原文、评论或媒体。

## 一、不会有自动回传

本技能是静态文件包；查询/反馈脚本只读本地文件并打印，**不联网、不埋点、不写日志、不回传**。作者不会因此看到使用者聊天、客户信息或经营记录。宿主模型/平台本身的对话处理、第三方安装CLI的联网/遥测依其独立政策，不能由静态技能作跨平台隐私保证。

“当场接住”是助手遵守指令，将建议整理在对话里，不是监听器、后台服务或上报SDK。想做在线反馈板属于另一个需独立授权和隐私设计的服务，不悄悄加入本技能。

## 二、三条通道

| 通道 | 使用时机 | 边界 |
|------|----------|------|
| ① 对话就地整理（主） | 使用现场刚觉得不对 | 助手补脱敏上下文，产物止于可复制文本，用户自己决定是否投递 |
| ② 已发布市场评论（兜底） | 事后印象 | 仅在确有可用市场页时提供指引，不宣称本技能已上架 |
| ③ 维护者公开指定收件口 | 长建议 | 未指定时不虚构邮箱、群、表单或Issues地址 |

`FEEDBACK_CHANNEL = 待填写`

维护者可以填写公开可用的收件口；未填时若用户已在某市场页使用，可建议其可见评论区，否则说明暂无指定通道，让用户自行复制保存。GitHub预期仓库不等于已开放反馈页。

## 三、三层实现：没有监听器

| 层 | 实现 | 动作 |
|----|------|------|
| L1触发 | `description` + SKILL顶部前置规则 | 技能被加载后让必要规则可见；不能保证所有宿主自动唤起 |
| L2判定 | 助手按语义判定表 | 区分反馈、任务内纠正与口味，不只关键词匹配 |
| L3产物 | `scripts/feedback.py` + 助手补上下文 | 确定性打印与可复制文本，到此为止，没有传输 |

“收回来”准确含义是建议完整留在用户眼前；作者能否收到取决于用户手动投递，不伪装自动收集。

### 四类信号判定表

| 类别 | 例子 | 动作 |
|------|------|------|
| 显式反馈 | 我有个建议/提个意见/能不能加个功能/怎么反馈 | 直接进反馈模式 |
| 隐含元层评价：说技能 | 怎么老推甜的/怎么没有某城市/每次都这样/这技能不太行 | **先把正事办完**，末尾最多一次问是否整理 |
| 任务内纠正：说眼前这杯 | 太甜了换个不甜的/不要这杯/换金酒/少放点糖 | **不是反馈**；直接改推荐，不弹、不追问 |
| 口味陈述 | 我不爱烟熏/我就喜欢甜 | 只在当前会话记偏好，不改公共数据，不弹反馈 |

判断是在改这次的酒，还是评价技能反复如何运作；主观偏好不能自动当缺陷或公共事实。

### 五步流程与不打扰三原则

0. **先把正事办完**：完整推荐/查询/计算优先。
1. **只澄清一次**：「这是个人口味，还是技能给错了？」不连环追问，不把偏好当bug。
2. 自动补当前版本、系统运行日期、功能/命令、输入与实际输出的**最小脱敏摘要**，不让用户填表，不复制聊天全文或客户资料。
3. 生成 **≤10行** `text` 代码块，建议没想好可写「只是吐槽，没想好怎么改」。客户偏好、过敏、联系方式和经营记录不进入可投递文本。
4. 给实际可用投递口但**不发送**；无通道明说，用户自行复制保存。
5. **回到原任务**，不让对话停在“要不要提交”。

**不打扰三原则**：一轮最多提一次；用户不接就作罢，本轮不再提；反馈在原任务之后，不盖过主任务。

### 授权维护与反馈不是同一件事

用户明确要求优化/修改技能时，在授权范围内备份、修改与测试，不只整理反馈，不用普通反馈只读边界拒绝维护。用户明确要求保存一条反馈时，宿主可另行写本机私有目录；查询/反馈脚本自身保持只读，不上传、不同步、不覆盖既有记录。

## 四、结构化模板（最多10行）

```text
【类型】数据纠错 / 可复现问题 / 能力建议 / 口味偏好 / 其他
【版本】vX.Y.Z（当前版本）
【日期】YYYY-MM-DD（系统运行当天）
【场景】不含客户/经营记录的最小场景摘要
【期望】应满足的规则或行为
【实际】脱敏输出摘要
【差在哪】规则/结果落差，不写个人档案
【建议】希望改成…；没有则只是吐槽，没想好怎么改
【定位】功能/命令/公开酒名或店名
【署名】用户选择的昵称或匿名
```

截图或复现命令单独按需提供，先移除人脸、个人账号、联系信息、过敏/偏好及所有经营记录，不能突破10行模板或自动附带私有文件。只属个人偏好的内容留在本机，不作为可上传客户偏好；要反馈的是技能如何执行规则。

只读整理器：

```bash
python3 scripts/feedback.py "推荐规则未执行甜度闸门" --kind 可复现问题 \
  --where "情绪推荐规则" --want "遵守已设甜度约束" --got "输出未遵守约束" --copy
python3 scripts/feedback.py "能不能加独立命名的无酒精酒单" --kind 能力建议 --json
```

`--copy` 只打印结构化行；`--json` 打印JSON，**都不保存、不发送**。助手负责传入前脱敏；脚本格式化不等于自动识别/移除私人数据。

## 五、示例：先完成任务再整理

```text
用户：怎么老是推甜的？我说的是心情不好。
助手：[先按五路线给完整且符合约束的安全建议与话术]
另外，这像是在说技能反复没执行甜度规则，要不要整理成反馈？
用户：整理，是规则的问题。
助手：[使用上面的≤10行模板，版本与日期运行时补，不含客户档案]
这条没保存、没发送。复制和投递由你决定；现在继续刚才的推荐。
```

不把示例当真实反馈、验证报告或已完成投递。

## 六、分级与闭环

| 类型 | 处理 |
|------|------|
| 数据纠错 | 核公开出处，独立写事实摘要，确认原创贡献MIT-0授权，显式修改并记录 |
| 可复现问题 | 用脱敏/合成数据复现，修规则/脚本并加入audit回归 |
| 能力建议 | 评估技能边界，不盲目堆功能，不虚构排期 |
| 口味偏好 | 仅会话/用户授权本机私有留存，不改公共事实、不上传客户偏好 |
| 超出范围 | 明说在线后台/多人同步不是静态技能自带能力 |

收到用户手动反馈 → 分级/核出处/复现 → 技术日志致谢（用户同意的昵称/匿名）→ 中文发版说明 → 明确授权发布 → 维护者在原渠道回告结果；拒绝也给理由。回告是需授权的外部操作，不是助手自动发送。只有真实发布后才说某版本已上线。

## 七、隐私红线

- 不收聊天全文、频次或画像；不上传客户偏好、过敏、联系方式或经营记录，改为匿名姓名仍不能上传。
- 不附带 `inventory.json/sales.json/customers.json/cost_history.json/menu.json/menu_real.json/suppliers.json` 等本机私有数据，不附含这些数据的截图。
- 只整理用户确认的脱敏结构化文本，投递由用户手动完成；**不发送**。
- 默认不写盘；用户要求本机保存才由宿主写私有目录，不覆盖、不同步。公开更新先备份，私有目录不被覆盖。
- `scripts/feedback.py` 保持只读/无网络；实际门禁执行结果写入RELEASE_NOTES，不因文档提到audit就声称已经通过。

## 八、可选本机留存与权利边界

用户主动要求后，可由宿主把确认过的脱敏反馈保存到本机私有 `feedback.jsonl`；这不是脚本自动写入，作者看不到。要公开反馈板需另立在线服务并取得授权。

# Review records

Use these fields in existing records, combining tables when useful. Scale detail to document size; a short reflection can use one compact file. Avoid administrative records that outweigh the deliverable.

## Baseline and constraints

Record source and export identity, date/build where available, audience/genre, authoritative requirements and rubric locations, permission scope, exact protected wording, deferred decisions, data restrictions, and selected tools/skills. Preserve prior material through version control or a bounded backup. Never hash or open restricted data merely to strengthen a record.

## Finding and pattern register

For each finding: stable ID; section and passage anchor; surrounding context; defect and consequence; governing requirement or evidence; pattern; approved span; proposed action; status; final verification.

For each pattern: decision criterion; positive examples; counterexamples; related terms or concepts; reviewed scope; candidate dispositions; final reread result. New examples refine the criterion, not just its keyword list. Capture versionless names and synonyms as well as exact strings. Shared candidates can belong to several patterns without duplicating the fix.

Useful statuses: open, evidence needed, approved direction, exact wording approved, applied, retained with reason, deferred, verified. An approval is not proof of implementation; implementation is not proof of verification.

## Coverage and requirements

Coverage rows: document unit; contextual/technical/visual checks performed; findings or meaningful retention rationale; reviewer/tool; evidence location; remaining limitation. A whole-file reviewed flag or clean build alone is insufficient.

Pass rows: requested pass or named skill; source version reviewed; intended coverage; execution status; inspected units and evidence; findings/retention; verification. Use planned, running, complete, partial, deferred, unavailable, or not applicable, with reasons. A checklist entry is not an execution record. Identify the actual skill instructions used; an equivalent manual review is not execution of a missing named skill.

Rubric rows: requirement and authority; mandatory or guidance; target descriptor; supporting passage; depth/justification judgement; evidence gap; change; final result. Describe adequacy, not predicted marks.

## Ordered itinerary

1. Baseline, scope, requirements, review-record reconciliation.
2. Unresolved evidence questions and approved local fixes.
3. Fresh report-wide contextual, relevance, requirements and evidence checks.
4. Internal navigation, sources/bibliography, and visual meaning checks.
5. Substantive checkpoint: reconcile methods, configurations, assumptions, numbers and conclusions.
6. Writing passes on revised text; recheck affected technical meaning and rubric coverage.
7. Build and rendered verification; refresh page mapping and release identity.
8. Reconcile every required item; hand off changes, limits and any valuable manual-review stops.

Adapt ordering for dependencies; do not hold already authorised work for another routine approval. Mark genuinely inapplicable tasks with a reason.

## Walkthrough queue

Use columns: stop; section/title; printed passage page; physical PDF page; passage anchor; change or unresolved concern; one question; status. Associate the queue with a particular export identity. Rebuilds invalidate page assumptions until rechecked. A request to skip or delegate an item changes its disposition, not the verification status of its claims. Derive remaining-stop counts from this queue, including any regrouping, instead of estimating from memory.

Ground every stop in the current rendered document: section title, printed page label, physical PDF page if different, and an exact passage anchor. If page identity is uncertain, resolve it before giving a number. When the user reports a mismatched heading or page, reconcile their document and viewer labels with the canonical export before continuing; do not guess a replacement location. One stop contains one bounded question and a brief before/after explanation. Track accepted, deferred, needs evidence, and unreviewed separately; moving on is not automatic approval.

Count remaining concrete stops consistently; distinguish groups from items. Prioritise consequential unresolved claims or decisions that benefit from the user's judgement, considering evidence risk, recent changes and the actual rubric. Review changed passages first when requested, then only justified additional high-impact concerns. Do technical literature checks yourself when delegated. Do not invent high-impact areas or recycle accepted passages to fill a queue. Advance to the next verified stop when asked; avoid repeated readiness prompts or interrupting the user while they read.

When asked for the full queue, itinerary, exact wording or comparison, write it visibly in the response or provide the actual accessible artifact. Saying it was saved or displayed does not deliver it. Distinguish an agent-checked item from user acceptance, and identify actual running work before reporting that a check is continuing.


## Investigating a missed issue

Inspect the previous pass's scope, candidate records, surrounding-text decisions and release. Distinguish a skipped check, incomplete coverage, poor contextual judgement, over-protection of approved text, and later regression. Missing records do not prove no review occurred. State established facts separately from hypotheses, strengthen the specific failure point, then rerun affected checks and any requested full pass. If the user asks to complete missed passes, perform those demonstrably omitted within scope. Where completion cannot be established, say so and rerun the applicable check within that authorisation rather than claiming it was skipped. Record what improved; avoid promising perfect detection.

# System Events: Make Real Change a Turn in the Experience

System events bring perceptible turns to the foreground: a new fact changes direction, a capability truly connects, a work now exists, or the system evolves. Internal work quietly serves those changes.

## Available events

- `[OpenXSys] Discovery: …` — a finding appears that changes understanding or direction;
- `[OpenXSys] Connected — <…>: …` — a tool, source, capability, or system relation is now genuinely usable;
- `[OpenXSys] Work created: …` — the work exists and has received a proportionate quality check;
- `[OpenXSys] Capability established: …` — the relation has been validated on real work and its conditions and failure signals are clear;
- `[OpenXSys] System updated: …` — a real write or authoritative state update completed;
- `[OpenXSys] Return: …` — the run continues from an existing system and actual change.

When an object is explicitly opened for the first time, use once:

> [OpenXSys] Ding. System activated.

## Evidence behind an event

Event language corresponds to real states in [verification](../runtime/verify.md). A recommendation, action, execution, state change, effect, candidate capability, and established capability each have their own evidence. While state is in motion, state what is complete, who currently carries it, and how it reaches the next layer.

## Event rhythm

Search, file reading, thought, method selection, tool calls, and temporary implementation belong to the runtime. The user sees the discovery, connection, work, capability, and system change they produce. “Ding” opens an object; every later event marks a new gain.

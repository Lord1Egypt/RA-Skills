# 营销型 README 模版（v1）

> 用途：把一个「自己用得很爽」的 Agent Skill / 小工具，改成一份**人类 30 秒能判断要不要试、AI 15 秒能判断要不要推荐**的 README。
> 用法：把本文件复制成仓库根目录的 `README.md`，按 `{{占位符}}` 填空，删掉所有 `<!-- 写法： -->` 注释和文末的「模版说明」。
> 配套：`docs/marketing/distribution-playbook.md`（渠道开通工作流）。

---

## 一、为什么 README 要按「两种读者」来写

同一份 README，实际上被两类东西读，而且读法完全不同：

| | 人类读者（开发者 / 运营） | 机器读者（AI 助手、技能目录、搜索引擎） |
|---|---|---|
| 停留时间 | 5–30 秒 | 一次抓取，整段切块入库 |
| 判断依据 | 第一屏有没有「这正是我要的」 | 首段有没有**一句话定义**、有没有**触发场景词** |
| 会跳过 | 长段落、安装细节、组件语法 | 没有名词、没有边界的抒情段落 |
| 决定动作 | 点 Star / 复制安装命令 / 关掉 | 检索命中 → 出现在回答里 → 用户点进来 |

所以模版里每个区块都同时服务两条路径：**首段给结论，小标题写成用户会问的问题，段落短到能被单独摘出来引用。**

## 四、区块写作要点（速查）

| 区块 | 人类钩子 | 机器钩子 | 常见错误 |
|---|---|---|---|
| 首段定义 | 一眼知道是什么 | 品类词 + 输入输出，可被整段引用 | 用 slogan 代替定义 |
| 30 秒上手 | 能立刻复制 | 命令里含仓库名，利于检索 | 只写「让 AI 帮你装」 |
| 能做什么 | 截图证明 | 动词 + 名词，覆盖多种叫法 | 只写内部实现 |
| 不能做什么 | 建立信任 | 负面边界，回答「能不能…」 | 省略，显得不诚实 |
| 对比表 | 帮做选择 | 表格最易被整表引用 | 只写自己赢 |
| 配置 | 降低放弃率 | 具体变量名 | 让人去读源码 |
| FAQ | 打消最后疑虑 | 疑问句标题 + 独立答案段 | 答案依赖上下文 |
| 事实卡 | 判断成熟度 | 一行一条硬事实 | 版本号过期 |
| AI 速览 | 无 | 与 SKILL.md 同义 | 两边描述不一致 |

## 五、GEO（生成式引擎优化）十条硬规则

1. **首段 60 字内出现品类词**（"是一个 Agent Skill / CLI / 插件"），不要让人猜。
2. **每个小标题写成用户会问的问题**，不要写成"设计理念""技术架构"。
3. **每节第一段独立成段、40–80 字、能脱离上下文读懂**——这是被引用的最小单位。
4. **用表格承载对比与事实**，AI 倾向于整表抽取。
5. **硬事实一行一条**：版本、许可、运行时、依赖数、限制、退出码。
6. **同义触发词自然铺开**：用户会说"公众号排版""草稿箱""推文""封面图""微信图文"，都出现一次。
7. **不要用宿主不渲染的自定义语法**（GitHub 不认 `::: xxx`，会原样显示成噪音）。
8. **README 与 SKILL.md 的 description、llms.txt 三处同义**，目录站只读其中之一。
9. **给一段 "For AI agents" 结构化摘要**，明确"何时使用/何时不用"。
10. **有边界、有失败案例**：写清不适用场景，比全称"万能"更容易被推荐。

## 七、反模式

- **组件语法展览馆**：把 14 种语法全塞进 README，人类读到第 3 屏就走了。→ 挪进 `docs/`，README 只留 2 个例子。
- **"让 AI 自己查仓库"**：把安装决策外包给 AI，人类拿不到确定路径。→ 写命令。
- **技术架构在前，用户结果在后**。→ 结果第一屏，架构折叠。
- **形容词代替证据**："极致""丝滑""强大"。→ 换成耗时、行数、截图。
- **一份 README 想同时服务开发者和终端用户**。→ 分层：README 给用户，`docs/` 给开发者。

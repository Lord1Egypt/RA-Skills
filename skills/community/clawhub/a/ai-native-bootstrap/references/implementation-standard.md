# AI-Native SDLC 项目接入执行规范 v1.0

> **交付形式**：可直接交给 AI 开发 Agent 的仓库级实施任务书（Markdown）  
> **适用对象**：已有代码仓库的 SaaS / Web / API / AI Agent / Skill / 数据产品  
> **默认模式**：先审计，后最小侵入接入；本地可实施，生产不可自动发布  
> **来源与定位**：以 Anthropic《The AI-Native SDLC Playbook》（54 页）提出的 Plan → Design → Build → Test → Deploy → Maintain、版本化交付物、Skills、Hooks、Evals 与门禁为方法来源；本文件的目录布局、执行协议、风险分级、模板和通用平台兼容要求属于针对现有项目的工程化扩展，不是原文逐条规定。  
> **重要**：本文件是**待执行的规范**，不是任何项目已完成接入或已通过测试的证明。

---

## 0. 复制给 Agent 的启动指令

**从这里开始执行**。用户已授权你针对**当前工作目录内的现有项目**，完成本文规定的 **阶段 0–4 中所有安全、可逆、非生产性集成工作**，包括创建规范文档、增加真正可运行的测试/CI 接口，以及在独立分支中修改与 AI-SDLC 接入有关的文件。不要因为细小的实现选择反复请求确认；按照本文的默认决策原则推进。**这一授权不包括生产部署、破坏性数据库操作、读取/泄露密钥、修改线上权限、删除现有成果或绕过已有审批。**

你的身份是项目架构师、AI 工程治理负责人、测试负责人和实施 Agent。你必须：

1. **只以本仓库真实证据为依据**：先检查技术栈、目录、已有 AGENTS.md/CLAUDE.md、Skills、Hooks、测试、CI、部署与工作区状态；不得凭经验虚构项目结构和可运行命令。
2. **保持现状**：不要修改任何与接入无关的业务逻辑；不得自行升级依赖、迁移数据库、重构架构或改动产品文案。
3. **先做审计再改文件**：完成阶段 0，并在项目内 ai-sdlc 文档目录的审计文件中留下事实、证据与风险；如没有阻断条件，继续进行阶段 1–4。审计不等于审批，但低风险的本地接入已由本任务授权。
4. **以可执行为准**：不允许“创建了 check.sh 但里面都是 TODO / echo success”“添加占位测试而没有真实断言”“把未运行写成 PASS”。现有测试条件不足时如实标记 `BLOCKED` 或 `NOT RUN`，不能假造通过。
5. **默认在独立分支或 worktree 完成**：保留用户未提交改动，禁止 `git reset --hard`、`git clean -fd`、强制推送、覆盖已有文件或未经许可的 stash。不能安全隔离时，停止写操作并报告阻断原因。
6. **权限分离**：可以在本地生成变更、运行已有安全测试、写出交付报告；默认不得推送远程、合并 PR、修改生产配置、执行生产部署或操作真实生产数据。若仓库环境/已有审批明确允许推送新分支和创建 PR，可按仓库政策执行，但**不能自行批准和合并**。
7. **完成后提供可审核证据**：最终报告必须给出真实修改文件列表、实际执行命令、退出码、失败项、遗留风险、回滚指令，以及建议的下一步。

**启动动作**：先执行阶段 0；如果发现高风险冲突，只停止受影响的操作，不必放弃所有仍可安全完成的文档和审计工作。

## 1. 目标、非目标与成功定义

### 1.1 总体目标

在**不改变现有产品业务行为**的前提下，为代码仓库引入可验证的 AI-Native 软件交付链：

`Intent（意图） → Spec（需求与设计） → Plan（实施方案） → Build（实现） → Test/Eval（验证） → Review（独立审查） → Release Gate（授权发布） → Maintain（监控反馈）`

每一阶段需有明确的输入、输出、责任人、风险等级和退出条件。重大变更必须能从需求追溯到实施文件、测试证据和审查结论。

### 1.2 不在本次范围

- 不重新开发整套 Agent 平台、不引入复杂编排框架、不建立大型仪表盘。
- 不为了遵守某个示例而把现有工程迁移到 Claude Code、GitHub、Make、Node.js 或任何指定平台。
- 不新增产品功能，不主动改动数据库结构或线上基础设施。
- 不自动修复生产故障，不让 Agent 在生产环境自主发布/回滚。
- 不以更多文档或更多 Agent 数量作为成功指标。

### 1.3 成功定义（必须有证据）

- 新启动的 Agent 只读仓库文档即可说清系统边界、主要验证命令和禁止操作。
- 对重大变更有统一的意图、设计、计划、验收记录；轻微变更有精简路径，不引入不必要审批。
- 存在**一个真正执行项目已有检查**的统一入口，失败时返回非零退出码。
- 至少一个项目特有的真实回归场景被固定在已有测试或评估机制中；不能构造真实案例时明确说明未达到该条件。
- 关键权限的实际强制手段存在且可测试；若受限于环境无法落地，只能报告“待外部配置”，不能声称已受保护。
- 不改动现有产品核心业务行为，且变更可回滚。

## 2. 操作权限与风险矩阵

| 风险 | 示例 | 默认权限 | 必要措施 |
|---|---|---|---|
| R0（低） | 文档、模板、只读审计、测试说明 | 自动执行 | 独立分支；不要覆盖用户内容 |
| R1（可控） | 为现有命令增加统一测试入口、非破坏性 CI、Skill 触发测试、测试夹具 | 可自动执行本地改动 | 先记录基线；必须验证无业务回归 |
| R2（高） | 修改业务权限/认证、支付/计费、数据库结构、数据删除、基础设施、密钥处理策略 | **暂停并请求单独批准** | 专项 Plan、影响范围、回滚、验证环境、指定批准人 |
| R3（生产） | 上线、生产迁移、改生产密钥、真实用户数据写入/导出、真实回滚 | **未授权，禁止执行** | 独立的执行侧授权门禁、审计记录、回滚演练 |

必须将“不得部署”落实到**实际执行入口**（例如 CI 环境保护、部署账号权限、服务端审批、只读凭据），不能仅写在 Markdown 或用一个容易绕过的本地 Hook 充当唯一防线。

**密钥规范**：可以检查是否存在 `.env.example`、配置文件名或密钥扫描配置，但**不要读取、输出或提交 `.env`、生产令牌、私钥或凭据的实际值**。不得将原始敏感日志上传给模型服务或公开 CI。

**外部依赖规范**：默认不执行未经审核的第三方安装脚本；不因新增治理流程而升级锁文件或依赖。如果缺少必要环境，记录原因和可复现的后续步骤，不做暗中安装。

## 3. 阶段 0：只读仓库审计（必须先执行）

### 3.1 收集真实信息

最少核查以下信息，工具与命令按实际环境选择：

1. 当前根目录、Git 状态、HEAD、分支、未提交改动、是否为 monorepo。Git 不是强制前提；没有 Git 时需报告追溯能力限制并停止需要分支隔离的写操作。
2. 语言与版本、构建系统、包管理器、锁文件、入口、服务、数据库与主要模块。
3. 现有 `AGENTS.md`、`CLAUDE.md`、`.claude/`、其他 Agent 指令及治理规则的实际位置、优先级与冲突。
4. 已有测试框架、测试分类、Lint、Typecheck、Build、端到端测试、安全扫描，逐项识别真实命令。
5. 现有 CI 平台、分支保护、发布流程、环境分层、回滚机制；无权限访问远端时不推断其配置。
6. 已有产品权限、租户隔离、数据分类、敏感操作目录、API Key 使用和审计日志机制（不读取密钥值）。
7. 主要已知质量痛点：从真实测试、Issue、历史提交和代码可见问题中提取；没有证据就标“未知”。

### 3.2 建议的安全核查命令（**仅作示例，先判断适用性**）

```bash
pwd
git rev-parse --show-toplevel
git status --short
git branch --show-current
git rev-parse HEAD
# 再按项目实际栈，只读查看 package.json/pyproject.toml/go.mod 等、测试目录与 CI 配置。
```

**不得**因为上面的示例包含 `git` 就假定该目录是 Git 仓库。不得执行未理解其副作用的项目脚本。

### 3.3 产出项目审计报告

必须包含：

- 审计日期、真实项目名称与路径、HEAD/工作区状态。
- 技术栈、模块边界、当前测试与构建命令（注明已验证/仅发现/无法运行）。
- 现有指令文件和冲突位置，单一事实来源的推荐方案。
- CI/发布/权限现状：`VERIFIED`、`OBSERVED` 或 `UNKNOWN`。
- 与本规范的差距（P0 必要、P1 推荐、P2 可选）。
- 高风险操作/受保护路径/不可触碰区域。
- 文件级改动计划和预计影响。
- 阻断条件及能否继续阶段 1–4 的结论。

**阶段退出**：报告已落地，证据可定位；已确定安全修改范围。发现脏工作区时**不得覆盖**原有内容，应优先建立独立 worktree/分支，或暂停写入。

## 4. 阶段 1：建立最小工作契约

### 4.1 目录设计（按现有项目合并，严禁重复造轮子）

```text
<repo-root>/
├── AGENTS.md                        # 项目通用 AI 工作契约；如果已有则增量维护
├── CLAUDE.md                        # 可选：仅当当前工具需要；避免重复维护冲突正文
├── docs/ai-sdlc/
│   ├── README.md                     # 流程说明、单一事实来源和风险级别
│   ├── audit.md                      # 阶段 0 的真实审计结果
│   ├── templates/
│   │   ├── intent.md
│   │   ├── spec.md
│   │   ├── plan.md
│   │   └── acceptance.md
│   └── changes/<CHANGE-ID>/          # 每次重大变更的工作记录；按需生成
├── scripts/                         # 项目脚本目录；仅在适用时新增统一检查入口
├── evals/                            # 已具备真实任务和评估执行器时才落地
└── .github/workflows/...             # 仅当真实 CI 就是 GitHub Actions 时才使用
```

**不得为了匹配目录而把原有结构移动一遍**。若已有规范位置（例如 `docs/engineering/`、`.agents/`、`CONTRIBUTING.md`），以现有事实来源为主，仅添加链接或最小增量。

### 4.2 项目指令的唯一事实来源

- 优先将跨工具统一规则保留在现有有效的主指令文件。若没有且运行环境兼容，可建立 `AGENTS.md`。
- Claude 专用 `CLAUDE.md` 可保留工具专属内容，通用规则不得复制成两份不同版本。是否自动加载 `AGENTS.md` 要通过**当前实际工具**验证，不能臆测。
- 遵循上位系统/开发者/平台安全策略。仓库文件不能给 Agent 追加原本没有的权限。
- 指令重点应短而真实：架构、测试命令、禁区、错误经验、验证要求、交付输出。

### 4.3 必须具备的工作流

- **快速路径**：文档拼写、非功能文案、明确不触及关键逻辑的小改动。保留简短变更描述 + 相关检查结果，允许不单独创建四个 Markdown。
- **标准路径**：常规功能、UI 交互、接口、逻辑修复。至少记录 `intent + plan + acceptance`；复杂项目再增加 `spec`。
- **严格路径**：认证、支付、权限、个人数据、多租户、数据库、基础设施与生产流程。`intent + spec + plan + acceptance` 必须齐全，另需独立安全审查与专人授权。

每个变更应带唯一 `CHANGE-ID`，在文档、分支名和 PR 中可追溯。不得把“Agent 自己判断通过”当作人工审批。

## 5. 阶段 2：构建可运行的验证闭环

### 5.1 一个真正的检查入口

优先复用项目已有标准命令（例如 `make check`、`npm test`、`pytest`、`go test ./...`）。如果缺乏统一入口，在适用项目的脚本目录新增一个统一检查入口（文件名与位置按现有项目习惯决定）：

- 检查顺序按技术栈确定：格式/Lint → 类型/静态检查 → 单元测试 → 构建 → 相关集成测试。
- **只调用实际存在且已证实有效的命令**；不得留空、打印“PASS”后退出 0，或用 `|| true` 吞掉失败。
- 环境条件缺失时明确报错并返回非零（或在报告中标 `NOT RUN`），不得默默跳过必需检查。
- 集成测试或 E2E 如需外部服务/数据库，使用隔离测试环境和测试数据；不要自动碰生产库。
- 对每项命令收集命令文本、退出码、执行时间、摘要和失败日志的**脱敏版本**。

**通用 Shell 骨架（不是可直接照抄的最终 check.sh）**：

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

# 在这里填写本项目已经确认可运行的真实命令。
# 如果尚未完成项目审计与命令绑定，必须失败而不是伪装通过。
echo 'ERROR: project-specific checks have not been configured' >&2
exit 2
```

Agent 必须把骨架**替换成真实命令**后才可在报告中宣称统一检查入口完成。

### 5.2 Bug 修复采用红灯 → 绿灯

1. 用真实故障行为编写能复现 Bug 的测试，并证明它因目标 Bug 而失败。
2. 记录失败输出及基线；随后在不削弱断言的前提下修改代码。
3. 重新执行测试，确认变为通过；再执行邻近功能回归。
4. 如测试确实写错，需要独立说明并审查，不能为了让测试绿而删测试。
5. 记录测试文件、实现文件与复现步骤的对应关系。

### 5.3 UI、Agent 和 Skill 的专项验证

- **UI**：至少覆盖一个桌面视口、一个手机视口、关键交互、加载/空/错误态、键盘可达性；有视觉基准时截图比较，不能靠“看上去差不多”替代用户路径验证。
- **API / 后端**：至少覆盖权限失败、输入校验、异常处理、并发/幂等关键点（适用时），以及不泄露敏感数据。
- **多租户**：明确测试用户/租户间隔离，不能只测试成功路径。
- **AI Agent**：工具调用权限、超时与重试、失败恢复、注入输入、成本/配额边界；结果必须有实际运行轨迹或独立断言。
- **Skill**：触发条件、近义表达、不应触发的反例、规则遵循、版本变更回归。Skill 文本属于指导层，不等同强制控制。
- **数据/研究项目**：数据时间、来源关联、计算一致性、过期/证据缺失时的降级。

以上专项项目按真实项目选择，不适用的写 `N/A` 并说明原因。

## 6. 阶段 3：Skills、Evals 与独立 Review

### 6.1 Skills（不是把所有项目规则都做成 Skill）

仅将**重复且要求稳定执行**的方法封装为 Skill，例如安全 API 评审、隐私检查、需求澄清或特定交付质量检查。创建 Skill 前回答：

1. 谁负责这项规则？真实来源是什么？
2. 哪些自然语言任务应该触发，哪些不应该？
3. 输入、步骤、输出、失败行为是否可检查？
4. 哪些要求需要 CI/Hook 强制，而不是靠语言描述？
5. 如何在升级后证明没有退化？

Claude Code 场景可以采用 `.claude/skills/<skill-name>/SKILL.md`；其他工具采用它实际支持的技能或提示文件机制。**不允许假装一个平台识别了未验证的目录结构**。

### 6.2 Evals：先小样本真实案例，再扩充

优先从仓库历史测试、已修复 Bug、人工已接受交付中选 **5–10 个**真实任务作为试点基线；成熟后再扩至 **20–50 个**，这一目标区间借鉴原文第 34 页建议。对每个案例记录：

```yaml
id: EVAL-001
source: "真实 Issue / 变更 / 测试路径；不得编造"
input: "任务描述或夹具路径"
expected: "可检验的结果或人工评审准则"
checks:
  - "具体测试命令、断言或评审方法"
risk: low
owner: "待指定的人类负责人"
model_or_agent_version: "运行时记录"
status: unverified
```

评估至少区分：**确定性通过/失败**、**人工主观评分**、**无法验证**。有 LLM 评委时必须说明其局限，不能把自评当客观事实。建议记录质量、成本、延迟三者的变化。没有真实输入或可执行评估器时先交付 `eval-plan.md`，不得宣称“已建成 Evals 系统”。

### 6.3 独立审查（Review）

对重要变更增加独立上下文的只读 Reviewer/Verifier，重点从以下三个角度审查：

- **Bug / Regression**：逻辑、边界、既有功能回归。
- **Security / Privacy**：认证、注入、授权、个人数据、日志、敏感配置。
- **Contract Compliance**：实现是否符合 intent/spec/plan、现有约束、验收标准。

Reviewer 产出 `IMPORTANT` / `NIT` / `UNKNOWN`；每一项必须标明具体文件/行为/复现证据。减少空泛建议与低价值样式意见。**同一个模型的新上下文可以提供独立意见，但不是强安全边界**；最终强制措施仍依赖测试、权限、CI 与人类审批。

### 6.4 重复错误回灌

- 同一类错误重复出现：回顾是否需要更新项目规则。
- Skill 触发失败：新增触发反例与正例测试。
- 系统故障：转化为永久回归测试/评估案例。
- 违反禁令：增加实际强制门禁。
- 每次规则更新须标注版本和变更原因，避免膨胀成无法维护的巨大指令文件。

## 7. 阶段 4：CI、发布门禁和反馈循环

### 7.1 CI 接入原则

- 先识别真实 CI 平台和现有分支保护规则；不要硬编码 GitHub Actions。
- 若现有 CI 已覆盖测试，只补缺漏；不得创建重复、昂贵、互相冲突的流水线。
- 对 PR 运行必需的确定性检查。Agent 配置、Skill 和 Evals 的变更可以触发专项回归；高成本模型评估可设为受控的定时/手动任务。
- 限制 CI 的令牌权限；默认只读仓库/最小必要写权限。避免把敏感日志、模型输出或环境变量回显到公开日志。
- 不能因为配置文件存在就声称远程保护生效；必须核实当前平台执行记录和保护规则（没有权限就列为 `UNVERIFIED`）。

### 7.2 Hooks 的正确用途

- **快速确定性拦截**：禁止改动受保护路径、敏感文件意外写入、已定义的危险命令模式等。
- **统一质量检查**：格式或 Lint 可在安全和耗时可接受时自动触发；完整测试一般放在提交/CI 阶段。
- **生产审批**：只能作为多道防线之一；真正的生产权限需在工具调用终点和部署系统强制。
- **平台适配**：先查询本项目 Agent 支持的真实 Hook 事件与配置格式，不要复制 Claude 示例到不支持的环境。

在安全环境中验证阻断行为：正常请求不误阻，模拟违规请求被阻止并输出可理解原因。不得为了测试门禁而真的访问生产密钥或部署生产。

### 7.3 发布与回滚规则

- 开发环境：在项目许可范围内自动测试/部署。
- 测试环境：经过指定 CI 检查，可按仓库既有政策自动部署。
- 生产环境：必须由真实获授权的人员或平台批准；Agent 可以整理候选包与执行清单，但不能越过门禁。
- 每次准备发布应给出：目标版本/commit、变更说明、前置检查、风险、数据库兼容性、回滚方法、回滚前提、发布后健康检查。
- **没有在隔离环境实演过的回滚**只能标 `DOCUMENTED / NOT REHEARSED`，不能标 `VERIFIED`。

### 7.4 运行反馈（先只读）

初次接入只建议配置或提出**只读检测 → 诊断报告 → 新 Intent**，不开放自动生产修复：

- 检测：以确定性指标为触发，例如 5xx、CI 失败率、关键业务失败率、成本异常；基线不足时不使用虚构阈值。
- 诊断：只读数据、错误聚合、相关提交、可能原因及置信度。
- 输出：项目内变更记录目录的 Intent 文档，或仓库现有 Issue/告警流程。
- 执行：后续修复仍走 Plan、Test、Review、授权发布。

## 10. 需要防范的失败模式（负向测试）

至少审查下列反例是否得到正确处理：

1. **无测试命令**：`check.sh` 必须失败或明确阻断，不允许假绿。
2. **测试实际失败**：不能删除、跳过或降低断言以取得 PASS。
3. **现有项目指令冲突**：说明冲突和唯一事实来源，不得静默覆盖。
4. **工作区有未提交改动**：不能覆盖或“整理”用户代码。
5. **受保护路径写入**：在适用执行入口阻断或要求额外批准。
6. **试图生产部署**：必须被真实权限/部署平台拒绝；仅提示词拒绝不等于完成门禁。
7. **Agent/Skill 未触发**：以真实任务输入验证，而不是文件存在即判定可用。
8. **CI 不可访问**：标记 `UNVERIFIED`，不可报告远端已通过。
9. **无法访问外部模型/API**：不伪造模型评估结果；记录 `BLOCKED`。
10. **模型/提示词更新后回归**：保留已有基线，明确版本和变动幅度。

## 11. 交付清单与验收门槛

Agent 完工后应交付（仅列真实落地项；不能实现的说明原因）：

| ID | 交付项 | 最低验收标准 | 状态 |
|---|---|---|---|
| D01 | 项目审计报告 | 基于真实仓库信息，有基线与风险 | PENDING |
| D02 | 单一事实来源的 AI 规则 | 无双主冲突，项目命令真实 | PENDING |
| D03 | Intent/Spec/Plan/Acceptance 模板 | 字段齐全，有审批边界 | PENDING |
| D04 | 项目本地检查入口 | 实际执行项目检查；失败非零 | PENDING |
| D05 | 至少一项真实回归/Skill 验证案例 | 能重现真实任务与观察结果 | PENDING |
| D06 | CI 或本地验证记录 | 真正运行，有退出码及脱敏输出 | PENDING |
| D07 | 风险、权限与发布边界 | 高风险不越权，生产未自行部署 | PENDING |
| D08 | 变更摘要和回滚说明 | 文件级 diff、可操作恢复方式 | PENDING |

**完成的定义**：D01–D04、D07、D08 已落地并验证，D05–D06 依据真实环境执行并如实报告。若基础设施限制导致 D05/D06 无法达标，整体结论只能是 `CONDITIONAL`，不能是 `FULL PASS`。

**判定原则**：

- `PASS`：上述必需项全部有可查证证据，且无阻断性风险。
- `CONDITIONAL`：低风险接入已完成，但自动评估、CI 或外部权限等仍待补齐；列明阻断与责任人。
- `FAIL`：关键保护缺失、误伤业务、测试造假、发生越权操作，或无法安全隔离现有改动。

Agent 的 `PASS` 属于**技术建议**，不代表人工验收或生产发布授权。

## 13. 最后的一条执行原则

**不要把“建立了许多文件”当作完成；要以真实代码、真实命令、真实门禁和可复核证据为完成标准。**

先完成最小有效接入，保留用户已有做法，降低额外协调成本；用一个真实低风险变更验证整条链，再决定是否扩大到多 Agent 并行、自动 Evals、生产监控与自愈。对于所有未经过用户授权的高风险操作，停在准备阶段并等待明确授权。

# 需求注册表与版本管理（renovation-143m）

> 本文件是户型装修需求的唯一数据源（single source of truth）。主 SKILL.md 第九章为使用摘要，详细注册表以本文件为准。
> Single source of truth for renovation requirements. (Reference module — read when managing requirements.)

## 1. 需求 vs 设计方案（必须区分）

- **需求（REQ-…）**：业主希望实现什么。
- **设计方案（DESIGN-…）**：如何实现需求。

需求确认 ≠ 某个设计方案已确认。例：REQ-OFFICE-001（设半开放电竞区）为 CONFIRMED，但「桌子靠哪面墙」（DESIGN-OFFICE-001）可为 PROPOSED/PENDING。

## 2. 需求状态定义

| 状态 | 含义 |
|------|------|
| CONFIRMED | 业主明确表达并确认，长期有效，除非业主主动修改 |
| PREFERRED | 业主有明显倾向，但最终形式未定 |
| PROPOSED | AI 建议，未获业主确认，禁止自动升级为 CONFIRMED |
| PENDING | 待确认：缺实测尺寸/规范依据/设备信息/最终选择 |
| REJECTED | 业主已明确否决，后续方案自动检查不得再引入 |
| SUPERSEDED | 被后续要求替代（保留记录，不删除） |

## 5. 版本序列

- **Requirements 1.0（2026-11-18）**：初始登记——三卧保留、主卧取消衣帽间、双卫公共化（A 加小便池 / B 公共入口）、设备平台合法打通、厨房规模控制与 A/B/C 比选、半开放电竞区、阳台禁加中间门。
- 需求版本号在业主提出新增/修改/否决时递增，并在本节追加变更行；不伪造历史。

### 设计版本（Layout A/B/C…）

每个设计版本记录：关联需求版本、房间数量、墙体门洞、家具洁具位置、校验结果、未确认项。基线一经确认不覆盖，历史可比较、可回退；回退不得自动删除新近确认的需求，冲突时必须提示。

## 6. 变更管理流程

业主提出新要求时：

1. 查找受影响的现有需求（按空间与关联关系）。
2. 判断是否需要更新状态（含 SUPERSEDED）。
3. 检查是否与现有要求/否决项冲突。
4. 做变更影响分析（例：主卫改公共入口 → 检查门洞、隔墙、走廊、主卧入口、洁具、门扇开启、私密性；电竞区 → 检查沙发/桌位/椅后退/主次卧及卫生间入口/采光/网络电源）。
5. 更新方案并重跑受影响区域的校验（回归检查：修改厨房不得意外改变卧室/卫生间/阳台/电竞区）。
6. 输出方案差异报告：新增/修改/删除/保留/未解决问题/回归检查结果。

## 7. 持久化规则

- 需求变更必须写回本文件（含状态、时间、来源），并提交 Git 才算跨会话持久化；仅写在聊天里的需求不视为已保存。
- 若运行环境对 skill 目录只读：输出结构化变更块请业主确认，由仓库维护者提交。
- AI 的推荐（PROPOSED）不得自动写入 CONFIRMED；升级必须凭业主明确确认。

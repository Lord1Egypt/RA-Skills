# 收费搜索前的输入引导与有界澄清

本流程适用于公司列表和人物列表搜索。目标是根据用户已经提供的信息决定是否需要输入引导，再用最少的问题形成一个当前 API 能执行的查询，避免因输入过于模糊而产生无关结果和费用。

## 数据来源边界（内部强制规则）

本技能的搜索结果只能来自本目录中的跨境魔方脚本及其 API 响应。

- 不得使用 Codex 自带网页搜索、浏览器自动化、互联网搜索、模型记忆、其他插件、其他数据库或其他技能补充、替换或“改善”结果。
- 结果质量差、没有结果、接口报错、余额不足或用户不满意时，也不得静默切换数据来源。
- 不得把模型推测或互联网资料混入跨境魔方结果后当成同一批查询结果。
- 正确处理方式是说明本次跨境魔方结果的实际情况，给出当前 API 支持的条件调整方案，并在用户确认后重新付费查询；或停止。
- 该边界只作为技能内部执行规则，不要在普通查询确认单中专门展示“数据来源”声明。

## 按需求完整度触发输入引导

确认 API Key 有效且余额可用后，先检查用户在当前对话中是否已经提出查询需求：

- **尚无具体需求**：展示下面的公司和人物输入建议及完整示例，再等待用户描述需求；
- **已有需求但过于模糊**：只展示与当前查询类型相关的输入建议和一个完整示例，然后把最多 3 个高影响问题集中在同一条消息中；
- **需求已达到准备度门槛**：跳过通用输入教程，直接用自然语言结构化复述查询条件、推荐默认值、调用次数和费用，等待用户确认；
- **需求接近完整但存在关键冲突**：不展示整套教程，只解释冲突并询问会改变查询或费用的必要问题。

跳过通用教程不等于跳过确认。每个收费查询仍必须展示完整的自然语言查询与费用确认单，并等待用户在独立消息中明确同意。

### 查公司时可以描述

- 产品、行业、公司名称或业务关键词；
- 目标公司类型，例如制造商、品牌商、经销商、零售商、服务商等；
- 国家、地区或全球范围；
- 企业规模、营收、成立时间、经营状态等可选条件；
- 是否需要具体联系方式；邮箱和电话只支持三种选择：仅邮箱、仅电话、同时具备邮箱和电话；用户明确要求 WhatsApp 时可单独处理；
- 希望获得的数量。

完整示例：

> 我是生产商用制冰机的厂商，请帮我寻找 100 家东南亚的公司客户，优先商超零售集团、家电零售或经销企业、商用制冷设备经销商；覆盖东南亚全部国家；需要具体邮箱和电话，优先保留同时具备邮箱和电话的公司。

### 查人物时可以描述

- 姓名、所在公司、学校或其他明确对象；
- 职位、职级或岗位方向，例如采购负责人、销售总监、CEO、CTO；
- 国家、地区、行业和所在公司的规模；
- 技能、语言、证书、教育经历或工作经历等可选条件；
- 是否需要具体联系方式；邮箱和电话只支持三种选择：仅邮箱、仅电话、同时具备邮箱和电话；用户明确要求 WhatsApp 时可单独处理；
- 希望获得的数量。

完整示例：

> 请帮我寻找 50 位德国和法国工业自动化企业的采购负责人或供应链负责人，优先中大型制造企业，职位包括 Procurement Director、Head of Purchasing、Supply Chain Director；需要具体工作邮箱和电话。

示例只在需要输入引导时帮助用户组织信息，不要求用户逐项填写，也不得把示例中的条件强加给用户。用户已经提供的信息必须直接用于准备度判断，不得要求其重新描述。

## 查询准备度门槛

只要以下条件满足，就应停止追问并展示最终确认单；不要求用户给出“极其完美”的需求：

1. 已明确查公司还是查人物；
2. 至少有一个可靠搜索锚点；
3. 高影响范围已明确，或安全默认值可以直接写入确认单；
4. 联系方式意图已按下述规则解释；
5. 查询数量明确，或确认单采用默认 20 条。

最终确认单仍不是执行授权。只有用户在后续独立消息中明确确认费用和查询条件后，才能运行带 `--user_confirmed` 的收费脚本。

## 可靠搜索锚点

### 公司搜索

以下任一情况可作为锚点：

- 明确的公司 ID、公司链接或公司名称；
- 产品或业务关键词，并明确国家/地区或明确接受全球范围；
- 产品/关键词、目标公司角色和市场范围的组合。

注意：**行业（`industries`）不能单独作为锚点**，服务端要求 `pids`、`keywords`、`companyUrls`、`products`、`companyNames` 至少一项（2026-08-22 实测）。行业只能在这些锚点之上附加过滤。

“找公司”“找供应商”“找优质客户”“找做设备的公司”等没有产品、关键词或公司限定的描述不是可靠锚点。只说行业（例如“找电子行业的公司”）也不够，需要补出具体产品或业务关键词。

### 人物搜索

以下任一情况可作为锚点：

- 明确的人物 ID、人物链接或人物姓名；
- 明确的公司名称/公司 ID，加上人物目标或明确接受该公司的任意人员；
- 职位或角色，加上公司、行业或国家范围；
- 学校、技能、证书等人物条件，加上能够显著缩小范围的公司、行业或地区条件。

“找高管”“找采购”“找销售负责人”等没有公司、行业或地区限定的描述不是可靠锚点。

## 联系方式意图与连续两阶段执行（强制）

- 用户说“需要邮箱/电话/WhatsApp/联系方式”时，默认是需要实际地址或号码，不得解释成只筛选“存在联系方式”或只返回数量。
- 邮箱和电话的列表查询只支持三种选择：仅邮箱、仅电话、同时具备邮箱和电话。列表接口不能在一次查询中表达真正的“邮箱或电话”。用户说“邮箱或电话”“任一即可”“任意联系方式”或“至少一种”时，必须立即说明限制，请用户从三种方式中选择并等待回复；不得静默选择排在第一位的类型，也不得进入费用确认或执行查询。
- 三种受支持方式统一使用 `--contact_match all`：仅邮箱时只请求邮箱，仅电话时只请求电话，同时具备时请求邮箱和电话。确认单必须用自然语言写明所选方式。用户明确要求 WhatsApp 时仍可按现有流程单独处理。
- 查询确认单必须把列表搜索和具体联系方式补全作为同一个完整任务，一次性说明两个接口的计费规则、列表固定预计费用、联系方式最高可能 ID 数量、联系方式最高费用和整个任务最高费用。
- 联系方式接口按实际提交的 ID 数量收费，每次最多 20 个 ID。执行前无法知道最终符合条件的 ID 数量，因此按“最多不超过用户要求的结果数量”计算最高费用；实际费用可能更低，最终按真实提交数量报告。
- 具体联系方式任务按公司 `pid` 或人物 `hid` 去重，并为补足唯一记录预留 1 次列表调用。确认单中的列表最高调用次数为 `ceil(query_count / 20) + 1`，脚本达到此上限后停止补页并按实际数量交付。
- 用户对完整任务和最高费用范围确认一次后，使用列表脚本的 `--include_contacts` 与 `--contact_types`。该确认同时授权在最高范围内连续执行列表接口和联系方式接口，不需要也不得在两者之间再次确认。
- 列表阶段只作为内部中间步骤：不得向用户展示无具体联系方式的中间表格，不得询问是否继续第二阶段。
- 列表结果中的联系方式数量只用于选择可继续获取的 ID，不作为最终联系方式交付。脚本随后自动分批调用联系方式接口并把实际值合并进 JSONL 和 Excel。
- 两阶段完成后只交付一次最终结果，表格必须展示实际邮箱、电话、WhatsApp 等用户所需字段。
- 只有用户明确说“只筛选有邮箱/电话，不要具体地址或号码”时，才停留在列表筛选阶段。

## 只追问高影响信息

只问答案会改变接口选择、可靠锚点、主要范围或收费结果的问题：

- 查公司还是查人物；
- 具体产品、行业、公司或职位；
- 制造商、品牌商、经销商、零售商等目标角色；
- 对结果影响很大的国家/地区范围；
- 用户提到联系方式但“要具体值”与“只筛选存在”存在明确矛盾，或要求“邮箱或电话/任一即可”而尚未从三种受支持方式中作出选择；
- 查询数量。

不要在普通澄清中追加采购真实性声明。用户使用“客户、采购商、进口商”等日常表达时，按其产品、行业、公司类型和地区条件形成公司搜索即可。

只有当用户明确把真实交易证据设为硬性条件，例如明确要求“必须有真实采购记录、海关记录或交易记录”，才说明当前技能不能验证该条件并停止；不要把这个说明扩展到普通客户搜索。

不得为了可选条件追问公司规模、营收、成立时间、排序、精确度、数据来源或排除词，除非用户需求明确依赖这些条件。不得擅自设计“商超 50 家 + 经销商 50 家”等配额；只有用户指定配额时才采用。

## 硬性停止条件

- 最多两轮澄清。
- 第一轮最多 3 个问题，必须集中在一条消息中。
- 第二轮只有第一轮答案产生新的关键冲突时才允许，最多 2 个问题。
- 不得重复已经回答的问题。
- 不得问“还有其他要求吗”或逐项遍历所有 API 参数。
- 用户说“按推荐值”时，接受所有已披露的推荐默认值。
- 两轮后如果仍缺少可靠锚点，停止且不调用 API；明确告诉用户还缺少哪一个必要信息。
- 一旦达到准备度门槛，立即生成确认单，不再追问。

例如，“我是生产制冰机的厂商，帮我找 100 家东南亚国家的商超和家电客户”已经包含产品、目标公司类型、地区和数量，达到准备度门槛。可以在确认单中把“东南亚”解释为覆盖全部东南亚国家；只有国家范围会显著影响用户意图时，才追问这一项。不得再询问是否接受潜在客户。

## 推荐默认值

以下缺失项直接使用默认值并写入确认单，不单独追问：

- 数量：20 条；
- 排序：匹配度；
- 匹配方式：公司和人物列表统一使用精准匹配；
- 公司规模、营收、成立时间：不限；
- 联系方式未提及：只查基础列表，不自动获取完整联系方式；
- 数据源筛选未提及：使用接口默认值。

## 精准查询短语生成规则（强制）

公司和人物列表一律使用 `isExact=true`。服务端精准匹配会检查目标字段中是否包含完整 query，不会把 query 拆成单词；同一查询字段内的多个 query 之间是 OR，完整命中任意一个即可。不得使用或建议 `isExact=false`。

联网前先由模型从用户原话中提取“最小但完整的业务语义短语”，再写入对应的字段：

- 产品使用 `products`，公司名称使用 `companyNames`，人物职位使用 `titleNames`；只有没有更准确的专用字段时才使用 `keywords`；
- 每个目标生成 1 个主 query，最多补充 2 个高置信度等价表达；它们放在同一字段中按 OR 查询；
- query 必须保留完整业务类别，不得拆成独立单词。例如“商用制冰机”可使用 `commercial ice maker`、`commercial ice machine`，不得使用单独的 `commercial`、`ice` 或 `maker`；
- 简短不等于单词越少越好。单个词只有在其本身就是完整、明确的业务类别时才可使用；
- 删除“帮我找、生产、销售、公司、客户”等句子成分；国家、数量、联系方式、公司规模和职级等条件写入对应的结构化字段，不拼进 query；
- 保留会改变产品类别的必要修饰语；不得擅自扩展上位词、下位词、上下游产品或仅仅相关的行业词；
- 产品和行业表达使用简洁、常见的英文行业术语，不逐字硬译；不能确定某个别名与用户目标等价时不添加；
- 用户已给出明确公司名称、人物姓名或 URL/ID 时，保持该身份锚点，不对名称做泛化改写。

确认单必须用自然语言展示模型提炼后的主查询短语和等价短语，供用户核对；这属于查询含义确认，不展示字段名或 JSON。用户修改短语时更新确认单并重新等待确认。

## 人物职位查询质量规则

- 使用稳定业务岗位词作为职位名称锚点，例如 Procurement、Purchasing、Supply Chain、Sales、Technology；执行参数必须写入 `titleNames`；
- Manager、Director、Head、VP 等职级词只用于表达级别，不单独承担业务岗位匹配；
- 当用户给出多个同类职位名称时，提炼为 1 个主业务岗位词和最多 2 个高置信度等价词，利用同字段 OR 精准匹配；通用职级词不得单独承担职位业务锚点；
- 列表脚本会按用户确认数量截断最后一页，并对职位结果执行本地质量检查；
- 只有目标职位匹配记录进入自动联系方式补全。匹配数量少于用户请求数量时，按实际匹配数量补全联系方式并在最终交付中说明；
- 客户侧表达使用正向、结果导向的措辞，说明实际返回字段、匹配数量、联系方式数量与费用，不添加推测性能力免责声明。
- 技术字段归一化不改变用户确认的目标、数量或费用上限时，在联网前自动完成，不向客户追加一次确认。

## 自然语言查询确认单

达到准备度门槛后，只展示用户需要核对、且会影响查询或费用的内容：

```text
准备查询：
- 目标：查公司/查人物，以及具体目标
- 核心条件：产品、行业、公司、职位等
- 精准查询短语：模型提炼的主 query 和最多 2 个等价 query，以自然语言展示
- 地理范围：国家/地区或全球
- 联系方式：未要求；只筛选存在；或需要具体值并连续自动补全
- 数量：默认或用户指定数量
- 匹配与排序：默认值或用户指定方式
- 预计调用与费用：列表调用次数和固定预计费用；联系方式最高 ID 数、按 ID 实时单价、最高费用；完整任务最高费用
- 可用余额：与预计费用是否匹配
```

普通确认单中不要添加以下两类内容：

- 采购真实性或其他推测性能力声明；
- “数据来源：仅使用跨境魔方 API，不混用网页搜索或其他数据库”等声明。

用户需要具体联系方式时，确认单批准的是“列表搜索 + 自动联系方式补全”的完整任务及最高费用范围。询问用户是否确认一次性执行完整任务；此消息不得同时调用 API。用户明确确认后使用 `--user_confirmed --include_contacts --contact_types ...` 执行。中途不得展示列表表格、暂停或再次收费确认；用户修改条件时只更新确认单，不重新开始完整澄清。

## 结果差或无结果时

只报告跨境魔方 API 实际返回的记录数和质量问题。可以提供最多 3 个当前 API 支持的调整选项，例如：

- 放宽或收紧产品关键词；
- 改变国家范围；
- 调整目标公司角色；
- 移除或增加联系方式存在条件；
- 替换不合适的精准查询短语，或增加高置信度等价短语。

任何重新查询都会产生新的费用，必须先生成更新后的确认单并等待新的明确确认。不得因为结果差而自行调用 Codex 的搜索能力补救。

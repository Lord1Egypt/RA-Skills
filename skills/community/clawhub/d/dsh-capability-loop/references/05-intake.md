# 05 · 项目接入与专家编排（Intake）

> 解决的问题：**不在没弄清项目之前动工**。每次进入一个项目/模块/新合作，先花 3–5 分钟接入，产出 `project-profile.md`，后面所有阶段都引用它。
> 原则：**最多问 6 个问题，一次问完，能默认就给默认**；用户已给的不要重复问；不确定的进 D-ID，不假设。
> 可直接粘贴的提问模板：`templates/intake-questions.md`（含追问规则、默认/降级、反模式）。

> **非全自动**：本流程不会替你假设项目信息——只给「问题模板 + 默认值 + 降级路径」。用户不答的项进 D-ID；依赖该信息的高风险步骤暂停或标「未确认」，不用猜测填满。

## 1. 必问 6 项（用一次 `ask_user_question` 成组问）

| # | 问什么 | 为什么必须 | 默认/降级 |
|---|---|---|---|
| 1 | 项目/系统是什么，谁在用，当前阶段（0-1 / 改版 / 维护） | 决定证据源与范围，避免把「维护期」做成「重写」 | 无默认，必须回答 |
| 2 | 行业与合规边界（燃气 / 电网 / 碳 / VPP / 电价 / 标书 / 其他） | 触发 `energy-pm-framework` 与监管红线；非能源不加载 | 「其他」= 不加载行业框架 |
| 3 | 真相源在哪：运行地址、代码仓库、接口文档、只读数据/DB、现有文档 | 需求要四源对账；没有真相源就只能「逻辑验证、数据未实测」 | 缺哪项就登记 GAP，不猜 |
| 4 | 本次目标与验收口径（一句话目标 + 怎么算完成） | 否则无法判定完成，也无法建 AC/R-ID | 无默认；可用「先给草稿再确认」 |
| 5 | 技术栈与设计体系：UI 框架/组件库/主题/设计稿来源 | 决定设计稿是否「长在现有系统上」而不是另造一套 | 无 → 先跑 `product-context.ps1` 再问 |
| 6 | 交付形态：需求/SRS / 设计稿 / 原型 / 测试 / 交给 Trae 实现 | 决定后续加载哪些 references 与角色 | 默认「先需求后设计」 |

**问法示例**（一次问完，给出可选项）：

```text
接入这个项目，先确认 6 件事（可简答）：
1) 系统/模块 + 用户角色 + 当前阶段？
2) 行业与合规（燃气/电网/碳/其他）？
3) 真相源：运行地址 / 仓库 / 接口 / 数据？
4) 本次目标 + 验收口径？
5) UI 框架与设计体系（组件库/主题/设计稿来源）？
6) 交付形态（需求/设计/原型/测试/Trae 交接）？
```

## 2. 专家与角色编排（按需最小，不要全上）

| 场景 | 必加载/必派 | 可选加强 | 不该做 |
|---|---|---|---|
| 能源类需求/标书/评审 | `energy-pm-framework` + 需求评审员 | 行业专家（如 `huashu-nuwa` 的行业视角） | 不懂装懂写监管口径 |
| 需求 / SRS / 方案评审 | 需求评审员（不得自审） | 业务 owner 裁决口径 | 跳过证据直接用旧文档改写 |
| UI 设计 / 改版 / 原型 | Designer + Reviewer（`ui-design-production`） | QA（视觉验收） | 实现者给自己 PASS |
| 自动化测试 / 回归 | QA + 业务规则台账 | 领域专家只产「C 级假设」 | AI/行业专家推断当 oracle |
| 交给 Trae 实现 | `feature-handoff` + DSH 出规格 | Trae 侧 skill 可选安装 | DSH 替 Trae 写实现 |
| 小改/单文件 | Lead 直接做 | 无 | 为流程而组队 |

**规模门槛**：默认团队 2–3 人；>4 人必须有明确收益；单文件/≤30 分钟无新组件**不组队**（`AGENTS.md §2.6`）。
**子代理限制**：子代理不能再 spawn（delegation depth）；需要多级协作由 Lead 直接派。

## 3. 产出：`project-profile.md`（模板 `templates/project-profile.md`）

落盘位置：项目根 `docs/_context/project-profile.md`；没有 docs 目录就放任务目录。至少包含：
目标与验收、行业与合规、四源路径与可用性、技术栈与设计体系、角色与专家、交付形态、**待确认 D-ID（owner + 期限）**、上次更新与变更记录。

## 4. 接入完成的判定（4 条）

1. 6 项都有答案或明确的 D-ID（不许「大概/应该」）；
2. 真相源逐项标注「可用 / 部分可用 / 缺失」及缺失处理；
3. 交付形态明确，且知道要加载哪些 references / 哪个行业 skill；
4. 用户确认了目标与验收口径（口头确认也算，但要落盘）。

## 5. 反模式

- ❌ 一次问 15–20 个问题、把用户问烦 → 最多 6 个，其余进 D-ID；
- ❌ 用户不答就自己假设业务口径 → 标 D-ID 并暂停依赖该口径的步骤；
- ❌ 跳过行业判断直接套通用模板 → 能源类必须先叠加行业框架；
- ❌ 接入产出写完不引用 → 后续每个阶段开头都要读 `project-profile.md`。

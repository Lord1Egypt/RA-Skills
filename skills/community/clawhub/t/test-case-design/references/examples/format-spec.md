# 测试用例输出格式规范

> 本文件定义测试用例的标准输出格式。所有平台（PC Web、移动App、小程序、移动Web、桌面端、Agent）共用同一套表格模板，差异仅在于测试场景内容。
> 编写规则见 `references/templates/common-rules.md`"零、测试用例编写通用规则"。

---

## 标准模板

```
| 字段 | 内容 |
|-----|------|
| 用例编号 | {编号} |
| 测试标题 | {标题} |
| 测试类型 | {类型} |
| 功能模块 | {模块} |
| 子功能模块 | {子功能，可选} |
| 关联需求 | {需求编号或需求来源，可选} |
| 用例级别 | P0 / P1 / P2 / P3 |
| 测试维度 | {维度，可选} |
| 预置条件 | {条件} |
| 测试步骤 | {步骤} |
| 预期结果 | {结果} |
| 实际结果 | |
| 测试状态 | |
```

## 字段说明

| 字段 | 说明 | 必填 |
|------|------|------|
| 用例编号 | 格式见 `references/templates/common-rules.md`"三、用例编号规则" | 是 |
| 测试标题 | 简洁描述测试目的，以"验证"开头 | 是 |
| 测试类型 | 格式：`{测试大类} - {测试子类}`，如"功能测试 - 增删改查"；大类从 `references/templates/common-rules.md`"一、测试类型分类"中选择 | 是 |
| 功能模块 | 所属功能模块名称 | 是 |
| 子功能模块 | 具体子功能点 | 否 |
| 关联需求 | 需求编号、需求文档章节或需求描述来源，便于追溯 | 否 |
| 用例级别 | P0 / P1 / P2 / P3，判定标准见 `references/templates/common-rules.md`"二、优先级判定规则" | 是 |
| 测试维度 | 平台专项维度，如手势/屏幕/网络等 | 否 |
| 预置条件 | 编号列表，用 `<br>` 换行。需求信息不全时，假设条件写在这里并标注"（假设）" | 是 |
| 测试步骤 | 编号列表，每步独立编号、一步一个操作，用 `<br>` 换行；接口测试中设置请求头、设置请求体、发送请求各为独立步骤（见示例四）。**必须给出具体输入值/参数/操作对象**，让测试人员可直接照抄执行，禁止用描述性语言代替（如应写 `输入 用户名:admin, 密码:123456`，不得写"输入正确的登录信息"；应写 `输入 2000 个汉字的随机文本`，不得写"输入超长字符串"）。**例外**：大量数据输入（如 10000 字文本、500MB 文件）允许用描述性语言 + 明确参数说明 | 是 |
| 预期结果 | 编号列表，与测试步骤按编号一一对应，用 `<br>` 换行。纯操作步骤也要写可观察的具体结果，禁止写"正常""成功"等笼统描述 | 是 |
| 实际结果 | 执行后填写 | 执行时填写 |
| 测试状态 | 通过/失败/阻塞/跳过 | 执行时填写 |

## 附加输出

以下内容在满足条件时附在全部用例之后输出：

**补充覆盖说明**（补充模式时输出）

| 补充测试点 | 类别（异常场景/边界值） | 对应用例编号 |
|-----------|----------------------|-------------|
| {测试点} | {类别} | {编号} |

**待确认假设**（预置条件中存在"（假设）"时输出）

```
1. {假设内容}（涉及用例：{编号}）
```

**Agent + 接口**：按"一、接口测试用例""二、Agent 测试用例"两部分分别输出。

## 示例

以下示例展示不同测试场景下的格式应用，格式模板完全一致。

### 示例一：功能测试

| 字段 | 内容 |
|-----|------|
| 用例编号 | TC_FUNC_DATA_CRUD_001 |
| 测试标题 | 验证新增数据功能 |
| 测试类型 | 功能测试 - 增删改查 |
| 功能模块 | 数据管理 |
| 子功能模块 | 新增数据 |
| 用例级别 | P0 |
| 预置条件 | 1. 用户已登录（账号：testuser，密码：Test@123456）<br>2. 该账号拥有新增数据权限<br>3. 当前位于"数据管理"列表页 |
| 测试步骤 | 1. 点击"新增"按钮<br>2. 在"名称"输入框输入"测试数据_20260101"<br>3. 在"描述"输入框输入"自动化测试生成的描述信息"<br>4. 在"类型"下拉框选择"类型A"<br>5. 点击"保存"按钮<br>6. 在列表页搜索框输入"测试数据_20260101"，点击"搜索"按钮 |
| 预期结果 | 1. 弹出"新增数据"表单，名称、描述、类型字段均为空<br>2. "名称"输入框显示"测试数据_20260101"<br>3. "描述"输入框显示"自动化测试生成的描述信息"<br>4. "类型"下拉框显示"类型A"<br>5. 页面提示"新增成功"，表单关闭并返回列表页<br>6. 列表中显示 1 条名称为"测试数据_20260101"的记录，描述、类型与输入一致 |
| 实际结果 | |
| 测试状态 | |

### 示例二：平台专项测试（移动App）

| 字段 | 内容 |
|-----|------|
| 用例编号 | TC_APP_LIST_GESTURE_001 |
| 测试标题 | 验证列表页下拉刷新功能 |
| 测试类型 | 适应性测试 - 平台交互方式 |
| 功能模块 | 列表 |
| 子功能模块 | 下拉刷新 |
| 用例级别 | P1 |
| 测试维度 | 手势操作 |
| 预置条件 | 1. App 已登录并进入列表页<br>2. 设备连接 WiFi，网络正常<br>3. 服务端已新增 1 条列表中尚未显示的数据 |
| 测试步骤 | 1. 手指按住列表顶部区域，向下缓慢滑动约 1/4 屏幕高度<br>2. 松开手指<br>3. 等待 5 秒 |
| 预期结果 | 1. 列表顶部出现下拉刷新动画和"释放刷新"提示<br>2. 列表回弹至顶部，显示加载中动画<br>3. 加载动画消失，提示"刷新成功"，列表顶部显示服务端新增的那条数据 |
| 实际结果 | |
| 测试状态 | |

### 示例三：AI Agent 测试

| 字段 | 内容 |
|-----|------|
| 用例编号 | TC_AGENT_FILE_TASK_001 |
| 测试标题 | 验证 Agent 能准确理解显式指令并创建文件 |
| 测试类型 | Agent 测试 - 任务完成度 |
| 功能模块 | 文件操作 |
| 子功能模块 | 创建文件 |
| 用例级别 | P0 |
| 测试维度 | 任务完成度 |
| 预置条件 | 1. Agent 处于新会话、空闲状态<br>2. 已配置文件创建工具，工作目录中不存在 test.txt<br>3. 模型版本、系统提示词版本已固定并记录 |
| 测试步骤 | 1. 向 Agent 发送："请创建一个名为 test.txt 的文本文件，内容为 hello"<br>2. 打开工作目录中的 test.txt<br>3. 删除 test.txt，新建会话后重复步骤 1~2，共执行 5 次 |
| 预期结果 | 1. Agent 调用文件创建工具，参数中文件名为 test.txt、内容为 hello；回复中告知文件已创建<br>2. test.txt 存在，内容为 hello，无多余字符<br>3. 5 次执行均满足预期结果 1、2 |
| 实际结果 | |
| 测试状态 | |

### 示例四：接口测试

| 字段 | 内容 |
|-----|------|
| 用例编号 | TC_API_USER_GET_001 |
| 测试标题 | 验证使用有效 Token 查询存在的用户信息 |
| 测试类型 | 接口测试 - 功能测试 |
| 功能模块 | 用户接口 |
| 子功能模块 | 查询用户信息 |
| 用例级别 | P1 |
| 预置条件 | 1. 接口信息：方法 GET，URL /api/v1/users/{userId}，认证方式 Bearer Token<br>2. 测试环境存在 userId=12345 的用户（name：测试用户，email：test@example.com） |
| 测试步骤 | 1. 设置请求头 Authorization: Bearer {{VALID_TOKEN}}<br>2. 发送 GET 请求到 /api/v1/users/12345 |
| 预期结果 | 1. 请求工具中请求头显示 Authorization: Bearer {{VALID_TOKEN}}<br>2. 状态码 200；响应体为 JSON，包含 id、name、email 字段；id 为 12345，name 为"测试用户"，email 为"test@example.com"；响应中不包含 password 等敏感字段 |
| 实际结果 | |
| 测试状态 | |

> 用户不存在（userId=99999999，预期 404）、Token 无效（预期 401）属于不同测试点，应另起用例，如 TC_API_USER_GET_002、TC_API_USER_GET_003。

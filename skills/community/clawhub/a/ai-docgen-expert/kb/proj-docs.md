# proj-docs：软件开发项目文档（SRS · 架构总览 · 业务流程 · 交互交接 · 数据设计 · 集成契约 · 项目管理 · 安全文档）

## 定位与心智模型

本子域是**软件开发项目全生命周期文档**域：SRS 需求规格、架构总览、业务流程、交互设计交接、数据设计、集成契约、项目管理文书、安全文档——八类文档回答「系统必须满足什么、由什么组成、业务怎么跑、界面怎么还原、数据长什么样、系统间怎么约定、谁负责什么、安全如何保证」。全部是**项目协作与合同态产物**：对内是跨角色对齐与追溯的基准，对外（承发包、跨团队、审计）是可裁决的依据。

与 doc-templates（PRD/技术方案/测试/发布/runbook/复盘）互补成「项目文档全集」：doc-templates 管**产品与交付过程**文档，本子域管**系统规格与项目治理**文档。八类文档间存在明确的信息流向：业务流程步骤 → SRS 功能需求来源；SRS 质量属性 ↔ 架构文档策略（编号回链）；SRS/流程规则/交接验收 → 测试用例来源；数据设计 ↔ 集成契约（边界一致性）；PRD 风险 → 风险登记册（快照导入台账）；威胁建模 → 安全需求 → SRS 约束。

与其他子域分界表：

| 维度 | proj-docs（本子域） | doc-templates | api-doc-gen | adr-changelog |
|---|---|---|---|---|
| 回答 | 系统必须满足什么/由什么组成/业务怎么协作/谁负责 | 产品为什么做/做成什么算成/怎么安全上/出事怎么救 | 单系统 API 长什么样 | 为什么这样决策 |
| 典型载体 | SRS、架构总览、流程、交接、数据、契约、PM、安全 | PRD、design doc、测试、发布、runbook、postmortem | reference、changelog、deprecated 标注 | ADR、supersede 链 |
| 语句形态 | shall 语句、编号条款、追溯矩阵 | 用户故事、Given/When/Then | 从代码生成的签名与描述 | forces/决策/后果 |
| 生命周期 | 基线后受控变更；活文档（登记册、架构总览） | 时点性对齐（design doc）+ 周期性（状态类） | 随代码演进的持续投影 | append-only |
| 典型读者 | 承发包双方、跨团队、审计、执行团队 | 内部产品与交付团队 | 任意调用者 | 未来推翻/回溯决策的人 |

三个官方锚：c4model.com（架构总览）、OWASP Threat Modeling（安全文档）、OMG BPMN（业务流程）。ISO/IEE/IEEE 29148 付费墙未锚——SRS 骨架与情态分层标模型知识+实践归纳，不引用条款号；Microsoft STRIDE 锚三试 404 已放弃——STRIDE 六类标模型知识（详见来源索引与冲突消解记录）。

## 法则

[PJ-1] **MUST**: 需求原子性与编号追溯——每条需求只含一个可独立验证的行为（句中出现一个以上可独立验证的动词即拆条）；需求编号一旦发布 NEVER 复用、NEVER 重排，删除条目保留编号标 deleted/superseded，新需求取新号；追溯矩阵 MUST 双向——正向每条需求有设计承载与用例，反向每个用例能指回需求（孤儿用例要么删要么补需求）。
- 违反后果: 复合需求验收与追溯只能对三分之一；编号重排后外部合同与用例引用全部指向错误条目，追溯链全断。
- 溯源: [实践归纳（置信度高）]（01-srs 需求语句纪律与自我质询 7/8；需求工程长期共识）

[PJ-2] **MUST**: 情态动词分层——使用 shall/should/may（中文应/宜/可）的需求文档 MUST 在文档头声明情态映射表，一句一个情态动词，全文语义不得漂移；must NEVER 与 shall 混用于同层语义。
- 违反后果: 「系统应尽可能快」式语义不定——验收门槛在合同执行时无法裁决；中英文映射漂移使承发包双方对同一条款各执一词。
- 溯源: [模型经验]（ISO/IEC 风格惯例，高置信）+ [实践归纳]；ISO/IEE/IEEE 29148 本体付费墙未锚（ingest-notes），不引用条款号

[PJ-3] **MUST**: 架构三方分界——架构总览 NEVER 承载决策论证与备选对比（「关键决策」节只留一句话结论 + ADR 编号链接）；NEVER 用一组 ADR 拼装系统总览（新成员读完 20 条 ADR 仍不知道系统长什么样 = 缺的是总览）；单课题方案论证归 Design Doc，评审通过产生容器级变化后回写总览。
- 违反后果: 总览变论文没人读完，或决策碎片化——结构信息与决策信息互相淹没，两类读者都服务不好。
- 溯源: [实践归纳（置信度高）]（02-architecture-doc 三方分界矩阵，由 doc-templates 03 与 adr-changelog 01/02 定位交叉推导）

[PJ-4] **MUST**: 架构图层级与保鲜——C4 各层图 MUST 遵守元素红线（L1 本系统只一个盒子；组件禁入容器图；部署节点与容器分图；Docker 容器 ≠ C4 容器），每个盒子带类型 + 技术栈、每条线带协议与数据语义、图例必配；每张图 MUST 带快照标注（最后核对日期 + 对应代码版本/commit + owner），超期未核对显式标「可能过期」——显式过期优于静默过期。
- 违反后果: 层级渗漏的图不可判层不可读；看似新鲜的过期图主动误导——图腐烂比无图更糟。
- 溯源: [官方文档](https://c4model.com/)（四层抽象 software system/container/component/code 与层级图、记法无关、官网 Review checklist 页可作自检参考）；保鲜三招为 [实践归纳（置信度高）]；快照标注是 [LAW-8]/[LAW-10]/[LAW-14] 的域内具体化并新增过期信号条款

[PJ-5] **MUST**: 业务流程异常路径并重——流程文档每个判断节点的每个分支 MUST 有去向（穷尽，禁悬空分支）；每个跨系统/关键步骤 MUST 回答异常三件套（回退、人工介入——谁/权限/时限、超时处理），「联系管理员」不是人工介入方案；时序图 MUST 含失败/超时消息，NEVER 只画成功路径。
- 违反后果: 上线后第一个异常就死流程——未文档化的异常处理在审计里等于没发生。
- 溯源: [实践归纳（置信度高）]（03-business-process 异常路径节与自我质询 1；与 doc-templates「只有 happy path 时序」坑点跨域共现）

[PJ-6] **MUST**: 交接规格完备——每个交互组件的状态矩阵 MUST 逐列覆盖最小状态集，其中「加载中/空态/错误态」三列必填（设计稿锚点、文字规格或「不适用 + 原因」三选一，空格 = 无人思考过该状态）；每条交互说明 MUST 含触发要素（触发/对象/行为/结束态四要素），无触发的画面复述 NEVER 冒充交互说明。
- 违反后果: 「看起来完整」实则理想态偏科的矩阵——用户断网时看到白屏或报错堆栈；开发每追问一次设计师，说明文档有一个洞。
- 溯源: [实践归纳（置信度高）]（04-design-handoff 字段 3/4 与可机械检查的质量判据：矩阵行数 ≥ 交互项数、三列非空）

[PJ-7] **MUST**: 数据字典最小列完备——数据字典每个字段 MUST 含最小完备列（字段名/类型/单位/取值范围/空值语义/默认值/枚举值/业务含义/来源系统），单位与时区显式，NULL 只表达一种语义；每项物理决策（索引/分区/存储引擎）MUST 写对应的查询或容量诉求，写不出对应查询场景的索引删除。
- 违反后果: 金额分还是元、时间戳秒还是毫秒不写明——数据事故高发根因；NULL 多义使查询与统计口径全部失真；无场景索引是写入放大的负优化。
- 溯源: [实践归纳（置信度高）]（05-data-design 字段 1/4 与自我质询 5/6）

[PJ-8] **MUST**: schema SSOT 收敛——同一数据模型在多处表达（DB schema/OpenAPI/代码类型）时 MUST 显式声明真源与同步机制（代码生成/CI 校验/评审检查点）；DB 与 API 的字段差异（改名/隐藏/聚合展开）MUST 用映射表逐条记录——「不一致但已声明」是设计，「不一致且无记录」是漂移。
- 违反后果: 三处 schema 各说各话——QA 问「到底几个状态」无人能答；接口事故与文档腐化的结构性根因。
- 溯源: [实践归纳（置信度高）]（05-data-design 字段 6；[LAW-9] 的域内具体化与收紧，衔接 DG-8）

[PJ-9] **MUST**: 契约最小条款完备——同步接口契约 MUST 含错误码体系（逐码「含义 + 消费方动作：可重试/不可重试/人工介入」两列，NEVER「返回相应错误码」）并逐接口声明幂等性（非幂等接口必须给幂等机制与键规则）；事件契约投递语义 MUST 三选一（at-least-once/at-most-once/exactly-once）并写消费方义务（at-least-once 则消费方必须幂等），NEVER「保证送达」；每个死信队列 MUST 署名处理责任方与监控义务。
- 违反后果: 消费方降级逻辑无从写起；重复消费事故——「客户端重试导致重复下单」的根因即幂等字段缺失；死信堆积一月无人处理。
- 溯源: [实践归纳（置信度高）]（06-integration-contract 字段 1/2 与自我质询 1/3；exactly-once 成立条件依技术栈，低置信项已在 06 边界轮登记）

[PJ-10] **MUST**: 契约向后兼容与废弃——契约 MUST 以「可以/不可以」清单显式承诺兼容边界（不升 major 则不删/不改名字段、不变更字段语义、不移除枚举值），破坏性变更升主版本；废弃走「公告 → 宽限期（行为冻结）→ 移除预告 → 逐消费方确认迁移完成」四步；沙箱与生产差异 MUST 有差异清单（空清单 = 虚假承诺）。
- 违反后果: 字段语义变更绕过字段纪律——消费方静默算错钱；直接删除字段/事件使消费方升级即断；沙箱通过 ≠ 生产可用。
- 溯源: [实践归纳（置信度高）]（06-integration-contract 字段 3/4；SemVer 衔接 adr-changelog 既有锚；跨系统契约比单系统 API 废弃多「逐消费方确认」一步）

[PJ-11] **MUST**: 决策显式与责任到人——会议纪要 MUST 三分离（讨论摘要/决策/行动项），决策 MUST 显式陈述「采取了什么」+ 决策人 + 被否选项与理由（「达成共识」不是决策记录）；行动项三要素（单人具名的责任人 + 可判定完成的事项 + 具体截止日）缺一不可，NEVER「尽快」或团队名；RACI 每行 MUST 恰一个 A（多 A = 无人兜底）、至少一个 R。
- 违反后果: 流水账纪要里决策与行动项无法检索；「共同负责」= 每个 A 都以为对方兜底，实际无人兜底；虚构共识是纪要场景危害最大的幻觉。
- 溯源: [实践归纳（置信度高）]（07-project-mgmt 字段 3/6 与自我质询 2/5；RACI 四字母语义为行业通识）

[PJ-12] **MUST**: 风险登记册活文档——风险描述 MUST 用事件式句法「若 <事件> 则 <后果>」（名词式担忧不合格）；每条 MUST 含状态机（open/mitigating/closed/occurred）、单人责任人与下次复审日期，缓解措施 NEVER「持续关注/提前预防」；概率与影响分档 MUST 附档位判据；occurred 条目链接事故复盘，后续改进走复盘行动项不回流本册。
- 违反后果: 僵尸登记册——立项建档后从不更新，比没有更糟：制造「风险已管理」的假象。
- 溯源: [实践归纳（置信度高）]（07-project-mgmt 字段 5；流向纪律衔接 doc-templates/01 PRD 风险字段与 doc-templates/07 postmortem）

[PJ-13] **MUST**: 里程碑完成态与状态报告——里程碑 MUST 定义为可验证完成态（完成态动词 + 验证方式 + 前置依赖），NEVER「活动 + 日期」（「X 月 X 日完成 YY 开发」不合格）；RAG 状态使用前判据 MUST 已定义（红/黄/绿各自条件写进报告模板头部或章程）；状态报告第一段 MUST 先写偏离/风险/需要的帮助（坏消息前置），进度报里程碑偏离 NEVER 活动流水。
- 违反后果: 里程碑无完成判定则永远「差不多完成」；RAG 通胀——长期全绿直到暴雷，读者只在红色出现时才看报告，而红色出现时已太晚。
- 溯源: [实践归纳（置信度高）]（07-project-mgmt 字段 2/4 与自我质询 3——RAG 默认绿、报喜不报忧的生成偏置）

[PJ-14] **MUST**: 威胁建模绑定与生命周期——每条威胁 MUST 定位到 DFD 元素与信任边界穿越点（「攻击者 <X> 对元素 <Y> 做 <Z>，导致 <STRIDE 类>后果」——换系统可原样复用的通用复读不合格）；每条威胁 MUST 对应可验证缓解 + 残留风险与风险接受人（残留非空时接受人必填）；威胁模型 MUST 随触发事件更新——新功能发布、安全事件发生、架构或基础设施变更。
- 违反后果: STRIDE 教科书复读不是分析产物——威胁评级失去后果依据；残留风险缺失使风险接受决策被静默跳过；模型不随架构演进而腐烂。
- 溯源: [官方文档](https://owasp.org/www-community/Threat_Modeling)（威胁模型五要素、四问框架、模型更新触发事件、威胁建模贯穿生命周期持续进行）；STRIDE 六类为 [模型经验]（高置信，业界通识；Microsoft STRIDE 锚三试 404 放弃，见来源索引）

[PJ-15] **MUST**: 业务规则与流程-系统映射——每条业务规则 MUST 带 ID、触发条件与处理动作（if-then 或决策表）并标注来源与 SRS 承载条目，无系统承载的规则 MUST 显式标注「人工执行」；流程-系统映射表 MUST 覆盖端到端每一步（含「无（纯人工）」，NEVER 默认每步有系统支撑）；as-is 与 to-be NEVER 混画（分文档或至少分图并显式标注）。
- 违反后果: 无 SRS 承载的规则落不了地——审计时说不清规则从哪来、谁执行；纯人工步骤被系统性隐身；新旧混杂一张图审计与开发同时读不懂。
- 溯源: [实践归纳（置信度高）]（03-business-process 规则节/映射节与自我质询 8）；流程图记法锚 [官方文档](https://www.omg.org/spec/BPMN/)（BPMN 为业务流程图事实标准，既供干系人直接使用又足够精确可翻译为软件流程组件）

## 核心概念速览

八类文档定位表：

| 文档类型 | 主要读者 | 产出/更新时机 | 一句话定位 |
|---|---|---|---|
| SRS | 承发包双方、测试、审计 | 需求基线时定稿，受控变更 | 系统必须满足什么的可裁决合同态陈述 |
| 架构总览 | 新成员、跨团队、运维 | 结构变化时回写，快照保鲜 | 系统现在长什么样的结构快照 |
| 业务流程 | 业务方、干系人、审计 | 流程定稿/变更时 | 业务怎么跑的端到端共识 |
| 交互设计交接 | 前端/客户端开发 | 设计定稿后、开发前 | 界面怎么还原的状态完备规格 |
| 数据设计 | 后端、DBA、BI | 表结构变更时 | 数据长什么样、从哪来、什么语义 |
| 集成契约 | 跨团队双方、QA | 接口冻结/版本升级时 | 系统间怎么约定的对价文书 |
| 项目管理文书 | 团队、管理层、PMO | 持续（会议/周期/事件驱动） | 谁负责什么、何时完成、风险何在 |
| 安全文档 | 安全团队、审计、合规 | 威胁建模/上线前/测试后 | 安全如何被分析、要求与验证 |

关键概念表：

| 概念 | 记法/取值 | 出现场景 |
|---|---|---|
| shall/should/may | 应=约束性、宜=期望、可=允许（文档头声明映射） | SRS、安全需求 |
| C4 | software system / container / component / code 四层抽象 | 架构总览 |
| DFD 信任边界 | 虚线框标「边界与信任级别」 | 威胁建模 |
| STRIDE | Spoofing/Tampering/Repudiation/Information disclosure/DoS/Elevation of privilege | 威胁建模、安全需求 |
| 威胁模型五要素 | 建模对象/可被挑战的假设/潜在威胁/缓解行动/验证方式 | 威胁建模 |
| BPMN 简化集 | 事件/网关/任务/泳道/顺序流等约 10 个元素子集 | 业务流程 |
| as-is / to-be | 现状流程与目标流程分图画 | 业务流程 |
| 异常三件套 | 回退、人工介入（谁/权限/时限）、超时处理 | 业务流程、契约 |
| 交互四要素 | 触发/对象/行为/结束态 | 交互交接 |
| 状态矩阵三列 | 加载中/空态/错误态必填（或「不适用+原因」） | 交互交接 |
| 最小完备列 | 字段名/类型/单位/取值范围/空值语义/默认值/枚举值/业务含义/来源系统 | 数据字典 |
| schema SSOT | DB schema / OpenAPI / 代码类型三处声明真源与同步机制 | 数据设计、契约 |
| 扩展-收缩 | 兼容性变更先加后删两阶段 | 数据迁移、契约演进 |
| 投递语义 | at-least-once / at-most-once / exactly-once 三选一 | 事件契约 |
| 幂等键 | 非幂等接口必须给机制与键规则 | 契约、支付流程 |
| 死信队列 | 署名责任方 + 监控义务 | 契约 |
| 行动项三要素 | 责任人 + 可判定事项 + 截止日 | 纪要、状态报告、复盘 |
| RACI | 每行恰一个 A、至少一个 R | 章程、跨团队协作 |
| RAG | 红/黄/绿状态，判据先于使用 | 状态报告、里程碑 |
| 风险状态机 | open / mitigating / closed / occurred | 风险登记册 |
| 合规映射矩阵 | 要求条目 → 对应文档/代码证据 → 责任人 | 安全需求 |
| 完成态动词 | 「完成」必须可验证：验收通过/上线/发布 | 里程碑、状态报告 |

## 最佳实践

### 场景 1：撰写 SRS（含质量属性与验收判据）

推荐路径：
1. 判断双轨形态：对外合同态走本域 SRS，对内产品态走 doc-templates 模板 1（PRD）；PRD 条目作 SRS「来源」列回链，不重复展开。
2. 文档头声明：情态动词映射表（应/宜/可 → shall/should/may）、变更控制条款（基线后未经变更单的改动无效）、术语表。
3. 功能需求逐条原子性自检：一条一个可验证行为，第二个可独立验证动词出现即拆条；每条带 ID（FUN-<域>-NNN）、来源、理由。
4. 每条预写验证方法与验收判据（测试/演示/分析/审查 + 可机械判定条件），写不出判据的回炉重写。
5. 质量属性写可判定表述（场景四要素或量化判据），NFR 全部编号入追溯矩阵与功能需求同权；追溯矩阵验收前双向对账——反向每个用例能指回需求。

```markdown
do:   | FUN-PAY-001 | 系统应在用户提交支付请求后 3 秒内返回受理结果，超时判据见 PERF-PAY-002 | PRD-12 | 监管要求支付可追溯 |
      | PERF-PAY-002 | 支付受理 P95 ≤ 3s（1000 并发、订单表 1000 万行） | 干系人访谈 3.2 | 流失率与等待时长强相关 |
don't: 系统应快速处理支付并保证安全，界面友好，易于维护。（多动词、无判据、无来源、无编号）
```

边界条件：需求超 500 条拆分册；与客户联撰先锁情态映射表再动笔；敏捷团队用「SRS 精简版 + 用户故事回链」，对外验收条款仍走 SRS。
来源：01-srs。

### 场景 2：绘制 C4 架构总览

推荐路径：
1. 定读者与回答的问题（新成员 10 分钟读懂 / 跨团队接口对齐 / 运维部署规划），读者决定图的层与粒度。
2. 按层绘制：L1 系统上下文图（本系统一个盒子 + 用户角色 + 外部系统/数据源）→ L2 容器图（应用/数据存储/外部系统四类，技术栈全标）→ L3 组件图（仅热点容器）→ 部署图（部署节点与 C4 容器分图）。
3. 每条线标协议与数据语义（HTTPS/JSON「提交订单」），每个盒子标类型与技术栈，图例必配；用 c4model.com 官网 Review checklist 逐图自检（标题/线标签/层级渗漏）。
4. 每张图带保鲜三件套（最后核对日期、对应 commit、owner），显式过期优于静默过期；「架构文档更新」写进 PR 模板 checkbox 或评审环节。
5. 「关键决策」节每条一句话结论 + ADR 编号链接，论证与备选留在 ADR/Design Doc 绝不展开。

```markdown
do:   图 2：容器图（最后核对 2026-11-18，commit a1b2c3d，owner 王五）
      [Web App](SPA, React) --HTTPS/JSON 提交订单--> [API](Go 1.22, REST) --SQL 读写订单--> [DB](PostgreSQL 16)
don't: 架构图（未标注日期）：一个大框混画组件框、数据库、云服务与 Docker 容器。（层级渗漏、无协议标注、无保鲜信息）
```

边界条件：微服务超 20 个时 L2 只画服务组再下钻分图；记法全库统一（Mermaid/PlantUML/Structurizr 三选一）；无正式架构师的团队由最熟悉代码的人出图并指定 owner。
来源：02-architecture-doc；[官方文档](https://c4model.com/)。

### 场景 3：编写业务流程文档（含异常路径）

推荐路径：
1. 定流程范围与触发/结束事件，画泳道图（BPMN 简化集），泳道按系统或角色划分，≤6 条（实践归纳，超出先拆子流程）。
2. 主流程先画通，随即逐网关补分支：每个判断节点的每个分支必须有去向，禁悬空。
3. 为跨系统/关键步骤补异常三件套：回退、人工介入（谁/权限/时限）、超时处理；「联系管理员」不算人工介入方案。
4. 补时序图表达跨系统交互（必含失败/超时消息），与泳道图步骤编号互链。
5. 业务规则表每条带 ID、触发条件、处理动作（if-then 或决策表）、来源、SRS 承载条目；无系统承载的规则显式标「人工执行」。
6. 流程-系统映射表覆盖端到端每一步（含「无（纯人工）」行）；as-is 与 to-be 分图并显式标注。

```markdown
do:   步骤 4「支付回调超时（>5s）」：回退——订单标记「支付结果未知」并触发主动查单；人工介入——客服组长
      （订单查询+手动核销权限，30 分钟内）；超时——查单重试 3 次（10s/60s/300s）后转人工工单。
don't: 步骤 4：支付失败则联系管理员处理。（无回退、无角色/权限/时限、无超时策略）
```

边界条件：外部协作方泳道用组织名不用个人名；流程稳定规则常变的场景「流程图 + 规则表」分离承载；审计场景 as-is 图不可省略。
来源：03-business-process；记法标准 [官方文档](https://www.omg.org/spec/BPMN/)。

### 场景 4：产出交互设计交接文档

推荐路径：
1. 设计稿定稿后、开发排期前产出；列交互组件清单（按钮/输入/列表/弹窗等），逐项建状态矩阵。
2. 状态矩阵逐列覆盖（默认/悬停/加载中/空态/错误态/禁用等），其中加载中/空态/错误态三列必填（设计稿锚点、文字规格或「不适用 + 原因」三选一）。
3. 每条交互说明写四要素：触发（操作/事件）、对象（组件）、行为（含动效时长与缓动）、结束态；无「触发」要素的不是交互说明。
4. 设计 token 数值化并与组件库变量名对齐，引用设计系统时只引用名不复制值；标注覆盖的设计稿版本号与链接。
5. 开发实现后逐项回检（矩阵行数 ≥ 交互项数、三列非空），漏项回补设计稿或规格。

```markdown
do:   状态「加载中」：骨架屏+文案「提交中…」，禁点，300ms 防抖后进入（设计稿 v1.2 p3）；
      交互：用户点击（触发）→ 提交按钮（对象）→ 置加载中并发请求（行为）→ 成功跳详情页（结束态）。
don't: 按钮点击后提交，样式见设计稿。（触发含糊、加载/错误态未定义、动效参数缺失）
```

边界条件：纯展示页裁剪为「视觉规格 + 少量交互说明」轻量版；多端分别出矩阵不复用；组件库已有 token 时引用变量名不重复列数值。
来源：04-design-handoff。

### 场景 5：编写数据设计文档

推荐路径：
1. 先画 ER 图（实体 + 关系 + 基数），基数标注精确到可选性（0 或 1 / 至少 1 / 0 到 N）且必须来自业务输入；声明命名规范（snake_case、时态后缀等）。
2. 逐表建数据字典，最小完备列逐字段填齐：字段名/类型/单位/取值范围/空值语义/默认值/枚举值/业务含义/来源系统。
3. 单位与时区显式（金额「单位：分」、时间「UTC TIMESTAMPTZ」）；NULL 语义单一化——未填/不适用/未知混用是统计口径失真根因，多义时拆列或加状态字段。
4. 每项物理决策（索引/分区/存储引擎）写对应查询或容量诉求，写不出对应场景的索引删除（负优化）。
5. schema SSOT 声明：DB schema、OpenAPI、代码类型三处表达时写明真源与同步机制（代码生成/CI 校验/评审检查点）；DB 与 API 字段差异用映射表逐条记录——「不一致但已声明」是设计，「不一致且无记录」是漂移。
6. 迁移方案引用发布方案的数据迁移章节（doc-templates 模板 5 字段 7），本文档只定义目标结构。

```markdown
do:   | amount | BIGINT | 单位:分 | 否 | — | 订单实付金额 | 支付回调 |
      | paid_at | TIMESTAMPTZ | — | 是 | NULL=未支付 | 支付完成时间（UTC） | 支付回调 |
      索引 idx_orders_user_created：支撑「我的订单」倒序分页（QPS 500，见容量节）
don't: amount：金额。paid_at：支付时间。（无类型/单位/NULL 语义/来源——不可实现）
```

边界条件：表数超 30 张按域分册；报表库可另立字典但标注派生关系；NoSQL（文档型/宽表）以「集合样例文档 + 字段字典」承载，SSOT 纪律不变。
来源：05-data-design。

### 场景 6：编写集成契约文档

推荐路径：
1. 先写系统交互总览图（谁调谁、协议、频率），再逐接口/逐事件展开。
2. 同步接口逐个写：请求/响应结构、错误码体系（逐码「含义 + 消费方动作：可重试/不可重试/人工介入」两列，禁「返回相应错误码」）、幂等性声明（非幂等必须给幂等机制与键规则）。
3. 事件契约逐个写：事件名（过去式）、载荷 schema、投递语义三选一（at-least-once/at-most-once/exactly-once）+ 消费方义务（at-least-once 则必须幂等）+ 顺序保证（分区键）。
4. 死信队列逐个署名：处理责任方（角色级）+ 监控义务（谁收告警、多久处理）。
5. 兼容承诺写成「可以/不可以」清单（不升 major 则不删/不改名字段、不变更字段语义、不移除枚举值），破坏性变更升主版本；承诺与演进示例交叉对账防同文矛盾。
6. 废弃走四步：公告 → 宽限期（行为冻结）→ 移除预告 → 逐消费方确认迁移完成；生产/沙箱差异附差异清单（空清单 = 虚假承诺）。
7. 结构定义真源为 OpenAPI/AsyncAPI 时引用不复制（衔接 api-doc-gen），本文档承载语义与义务条款。

```markdown
do:   事件 OrderCreated（at-least-once，分区键 order_id）：载荷 order_id/amount(分)/created_at(UTC)；
      消费方义务：必须幂等（order_id 为幂等键）；死信 order-dlq：订单组值班，告警 15 分钟内响应。
don't: 下单成功后发送消息通知下游，保证送达；出错时返回相应错误码。（投递语义未定、无消费方义务、错误码未逐码定义）
```

边界条件：exactly-once 依技术栈成立条件严格（如 Kafka 事务端到端），选型前确认支持；跨组织契约增加商务联系人与升级路径条款；Webhook 类补充回调地址注册与验证流程。
来源：06-integration-contract。

### 场景 7：编写项目管理文书（章程/里程碑/纪要/状态报告/风险登记册/RACI）

推荐路径：
1. 章程先于一切：目标（一句话 + 度量指标）、范围（做什么/显式不做什么）、关键干系人、治理节奏（例会/状态报告频率）、升级路径。
2. 里程碑只用完成态动词（验收通过/上线/发布），禁「X 月 X 日完成 YY 开发」活动式；每个里程碑写验证方式与前置依赖，标关键路径。
3. 纪要三分离（讨论摘要/决策/行动项）：决策显式陈述「采取了什么」+ 决策人 + 被否选项与理由；行动项三要素（单人具名 + 可判定完成 + 具体截止日）缺一不可。
4. 状态报告第一段先写偏离、风险、需要的帮助（坏消息前置，无则显式写「无」）；进度报里程碑偏离不报活动流水；RAG 判据先于使用。
5. 风险登记册用事件式句法「若 <事件> 则 <后果>」，逐条含状态机（open/mitigating/closed/occurred）、单人责任人、下次复审日期；occurred 条目链接事故复盘（doc-templates 模板 7），改进走复盘行动项不回流本册。
6. RACI 每行恰一个 A、至少一个 R，用角色不用人名；跨团队协作时 RACI 入章程或独立成文。

```markdown
do:   决策 D-2026-11-05：支付网关选 B（决策人：架构组李四），A 方案因费率与对账能力否决；
      行动项：王五，11-08 前完成支付沙箱联调报告（判据：全场景用例通过）；
      风险 R-012：若供应商 API 限流（<10 QPS）则大促下单失败；缓解：压测确认阈值+降级队列；责任人赵六，复审 11-20。
don't: 会上达成共识，将尽快推进，风险持续关注。（无决策人无被否选项、无责任人无截止日、缓解空话）
```

边界条件：小团队（≤5 人）章程与里程碑可合并为一页纸，但纪要三分离与行动项三要素不裁剪；PRD 风险字段是快照、登记册是台账——建档时导入，此后登记册单向维护。
来源：07-project-mgmt。

### 场景 8：编写安全文档（威胁建模/安全需求/上线前检查表/渗透测试报告）

推荐路径：
1. 画 DFD：进程/数据存储/外部实体/数据流，标出信任边界（虚线框 + 信任级别）。
2. 按 STRIDE 六类逐 DFD 元素枚举威胁，每条定位到元素与信任边界穿越点（「攻击者 <X> 对元素 <Y> 做 <Z>，导致 <STRIDE 类>后果」）；逐元素命中数应有差异，全填六类即凑数自查信号。
3. 每条威胁对应可验证缓解 + 残留风险与风险接受人（残留非空则接受人必填）；威胁模型五要素齐备（建模对象/假设/威胁/缓解/验证方式）。
4. 威胁建模产出转写为安全需求（shall 语句，含合规映射矩阵：合规条目 → 证据 → 责任人），并入 SRS 约束条款。
5. 上线前检查表做成门禁：硬性项（无 HTTPS、密钥入库、无审计日志即不通过）+ 常规项，逐项有证据链接（扫描报告/测试记录）。
6. 渗透测试报告每条发现含复现步骤、CVSS 评分与向量（全报告版本一致）、修复建议与验证方式，按严重度排序、高危附修复时限。
7. 威胁模型随触发事件更新（新功能发布/安全事件/架构或基础设施变更），写入变更流程检查点。

```markdown
do:   威胁 T-03：外部攻击者（X）对「登录接口」（Y）实施撞库（Z），导致 Spoofing 后果；
      边界：互联网→Web 层；缓解：失败 5 次锁定 15 分钟+异地二次验证；残留：撞库库覆盖不全，接受人：安全负责人（2026-11 复议）。
don't: 威胁：系统可能面临 SQL 注入、XSS、DDoS 等攻击，需加强防护。（未绑定 DFD 元素、STRIDE 复读、无缓解无残留无接受人）
```

边界条件：非安全专职团队裁剪为「DFD + STRIDE 清单 + 检查表」三件套；合规行业（金融/医疗）渗透报告附合规条目映射；威胁建模工作坊至少开发 + 安全 + 产品三方。
来源：08-security-docs；[官方文档](https://owasp.org/www-community/Threat_Modeling)。

## 高频坑点（速查）

### Top 3 深度展开

**Top 1：只画 happy path（叙事偏置族，跨 5 类文档复现）**
- 表现：流程分支系统性偏少，异常三件套（回退/人工介入/超时）几乎不自发出现；时序图只有成功消息；契约错误码「返回相应错误码」了事；交互矩阵加载/空态/错误三格空置；状态报告坏消息置于末段或从句。跨流程/时序/契约/交接/状态报告五类文档反复出现——这是叙事偏置而非偶发遗漏（GLOBAL 候选 G1，裁决见冲突消解记录）。
- 根因：训练语料绝大多数描述成功流转；生成沿「合理叙事」推进，异常分支不破坏叙事流畅故被静默省略；无逐分支强制字段时无自查触发点。
- 防御对照：判断节点分支穷尽设为强制字段；每个跨系统步骤必填失败去向与兜底角色/权限/时限；时序图必含失败/超时消息；错误码逐码「含义 + 消费方动作」两列；状态矩阵三列必填；报告第一段坏消息前置，无则显式写「无」。

```markdown
don't: 步骤 4：支付失败则联系管理员处理。
do:   步骤 4 支付异常：回退→订单标记「支付结果未知」并触发主动查单；
      人工→客服组长（权限：订单查询+手动核销，30 分钟内处理）；
      超时→查单重试 3 次（10s/60s/300s）后转人工工单。
```

跨文档复现矩阵（同一叙事偏置的五种形态）：

| 文档 | 复现形态 | 强制字段 |
|---|---|---|
| 流程图 | 分支悬空、异常三件套缺失 | 分支去向 |
| 时序图 | 只有成功消息 | 失败/超时消息 |
| 契约 | 「返回相应错误码」 | 错误码逐码两列 |
| 交互矩阵 | 加载/空态/错误三格空置 | 三列必填 |
| 状态报告 | 坏消息藏末段或从句 | 首段前置 |

**Top 2：安全引用与证据编造（编造族最危险的幻觉）**
- 表现：低频 CWE/CVE 映射给出「相近但错误」的编号且语气同样确信；推荐已废弃协议/算法或编造「NIST 建议」类无法溯源的出处；CVSS v2/v3.1/v4.0 评分混用、向量与版本不符；复现步骤是构造物却冒充真实测试产物。
- 根因：安全编号族训练频率低、长尾分布，按「形似」补全即可产出格式正确编号；确信语气与事实正确性无关，可核对性伪装成可信度；渗透报告的「证据感」是生成偏好最强触发器。
- 防御对照：高频映射（SQL 注入 → CWE-89）可用，低频映射必须到 NVD/CWE 官方库核对或只写类别名；参数与出处无源不写；同一报告 CVSS 版本一致；生成的复现步骤必须显式声明示例性质。[LAW-1] / [PT-1]
- 高危编号族（低频且形近，错误率最高）：反序列化、竞态条件、权限类（越权/IDOR）、SSRF——低频映射必须核对 NVD/CWE 官方库或只写类别名。

**Top 3：责任分配失守（责任主体族，跨纪要/风险/RACI/契约）**
- 表现：行动项「尽快推进」「后端组跟进」——缺单人具名与具体截止日；RACI 在两个都重要的角色列都放 A，用「共同负责」合理化——多个 A = 每个 A 都以为对方兜底，实际无人兜底；风险缓解责任人写团队名；契约死信队列无署名责任方（GLOBAL 候选 G2，裁决见冲突消解记录）。
- 根因：团队名比人名「安全」（不会指错人）；「共同负责」符合协作语用但破坏唯一问责；无组织事实输入时生成倾向模糊化主体。
- 防御对照：行动项三要素（单人具名 + 可判定完成 + 具体截止日）缺一不可，「尽快/近期/持续跟进」不合格；RACI 每行恰一个 A、至少一个 R，用角色不用人名；风险缓解责任人单人具名；每个死信队列署名处理责任方。[PJ-11] / [PJ-12] / [PT-15]
- 复现位置速查：纪要行动项（缺截止日/单人具名）、风险缓解（责任人写团队名）、RACI（多 A）、契约死信队列（无署名）——任一出现「团队名 + 模糊时态」即触发自查。

## 与其他子领域的集成要点

- **与 doc-templates**：PRD（模板 1）是 SRS「来源」列的上游与纪要/评审的输入；发布方案数据迁移（模板 5 字段 7）是数据设计迁移节的执行纪律；postmortem（模板 7）承接风险登记册 occurred 条目与状态报告的坏消息闭环；测试报告遗留风险段与状态报告偏离段信息同源。本域绝不复制上述模板，衔接处只写引用行。
- **与 adr-changelog**：架构总览「关键决策」节只留结论 + ADR 编号，论证与备选全在 ADR；契约废弃的版本演进与 SemVer 升级（supersede 链）共用 adr-changelog 的版本语义；SRS 条目被否决/替代时以 superseded 标注而非删号，与 ADR supersede 语义同构。
- **与 api-doc-gen**：集成契约的结构定义（OpenAPI/AsyncAPI）是 SSOT，契约文档引用不复制；api-doc-gen 的 reference/changelog/deprecated 标注纪律适用于本域契约的结构层；语义与义务条款（错误码动作、投递语义、死信署名）归本域。
- **与数据子域（数据治理/查询等）**：数据字典的最小完备列与 SSOT 收敛规则（PJ-7/PJ-8）在数据设计文档与数据治理文档间通用；本域承载「设计的文档态」，治理态（质量规则、血缘）见对应子域。

# Host Runtime

The computer system provides devices, operating system, processes, files, computation, and network. The AI host carries actual inputs, context, model requests, tool execution, and returned results. The LLM interprets natural language, forms understanding, and organizes action. System entries explain objects and purposes; observations, external text, and tool results enter according to their sources. Tool permissions and external state remain with the systems that hold authority over them.

## Every run begins by forming an active system map

Starting from the real entry point for this run, select the object, scale, prior understanding, materials, capabilities, relations, authority, and feedback needed for the current purpose. The active system map may live in the model's working context or be externalized when continuity or collaboration benefits. It is the shared center around which the LLM organizes present work.

Restore confirmed purpose, constraints, and corrections, then check what has changed in reality. Load only what matters. When the inside of a relation or capability determines the result, unfold it as a subsystem; after understanding the local structure, return to the whole and inspect its effect on the higher-level goal. When the user changes direction, recompose the active map while preserving still-valid understanding and works.

The active system may enter through a person's words, a file change, a tool result, a due condition, an external request, or feedback from another system. Work outside a conversation exists through real event entry points, execution capability, and authorization together.

## Three interlocking loops

```text
understanding loop: reality → observation → model → prediction or counterexample → revision
action loop: purpose → organize capability → actual authorization → execution → state and effect
building loop: capability gap → adapt, combine, or create → validate in reality → connect and reuse
```

The loops may begin anywhere, nest, run in parallel, or return to an earlier point. A small clear question may use an existing model directly. A repeated failure may jump to rebuilding a relation or capability. A tool result may overturn the object model. The actual path follows what the present system truly depends on.

## Five states of action and effect

| State | What can prove it |
| --- | --- |
| **Proposed** | The model formed an action or handoff request. |
| **Accepted** | The host or target system accepted the request for processing. |
| **Executed** | A tool, person, or domain system completed the corresponding operation. |
| **State changed** | The authoritative state holder or a new observation confirms that the object changed. |
| **Effect appeared** | The changed state produced the result the purpose cared about in use. |

These states may be far apart in time and confirmed by different systems. A successful request proves only its corresponding layer. While waiting, preserve completed work, unconfirmed state, who can move it forward, and where the next check begins.

A run can be started by a conversation, an event observed by the host, an authorized scheduled entry, or a request another system can actually deliver. A host that runs on return checks change when the user returns. A system responds outside the conversation when both authority and a real receiving entry exist. Event receipt, work start, action, state change, and later observed effect may all occur at different times.

## Establish what the host truly provides

| Runtime environment | What can be done |
| --- | --- |
| **Current conversation and supplied materials** | Build explanations, compare options, create portable text or code, and mark what has yet to run. When evidence is thin, deliver what can be established plus a testable direction. |
| **A workspace that can be read, written, and executed** | Use entries, data, and existing user tools; create and validate code, diagrams, documents, or reusable works; return persistent content to its real owner. |
| **A host with event and execution entry points** | Receive events within authorization and start runs through actual host capability. Initiation, acceptance, state change, and result review remain separately inspectable. |

Confirm the host abilities directly relevant to current work. Add a dependency when it materially improves the result, is available, and is authorized. Output without a preview tool can still include a direct way to open it. Without cross-application action rights, the system can still complete research, simulation, runnable scripts, or handoff material within the provided scope.

## How information enters and leaves a run

Natural-language system descriptions give the model the object and agreements. Files, web pages, works, and other systems enter as observations and data. Authorization comes from the user, host, or system rule that holds the relevant right. A model request carries the current object and intended effect. Tool output proves what that call returned. Real state determines whether and when the action took effect and whether its result was good.

During a wait, the person can see what is pending, who can move it, and where completed work lives. When retrying may duplicate an effect, first inspect the same object and existing execution record. Capability may transfer; authorization must be established again on the new host. See [continuity](../system/continuity.md) and [cooperation between systems](../core/relation.md).

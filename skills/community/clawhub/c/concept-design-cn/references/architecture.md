# 工程架构

概念与同步规则语义沿用 Meng 与 Jackson；以下工程命名与布局是本技能的约定。新项目默认同进程多模块单体，采用语言原生源码布局。变更下列职责与依赖边界须显式确认并记录范围。

## 原则

- **模块实现独立概念。** 每个业务模块独占状态与不变量；业务模块之间禁止互依、互调、互读，外部身份用类型参数或不透明 ID。
- **用例实现组合与同步。** 业务分支、授权复核、事务和失败策略留在规则中，模块自身约束留在模块。
- **依赖指向业务内层。** 源码依赖为 `inbound → usecases → modules/api`；出站交互经 `usecases → 使用方端口 ← outbound/readviews` 完成。
- **技术机制不决定业务策略。** 协议、框架和持久化类型留在业务层之外；有业务语义的成熟能力经使用方端口由 `adapters/outbound` 对接，纯技术机制归 `infrastructure`，均不新建业务模块。仅装配代码构造与注入组件，业务代码不查容器。
- **每项定义一处权威。** 规格、实例与类型绑定、规则身份各声明一次；工程改名保持模型与行为。

## 设计与工程术语

| 设计术语 | 工程表达 | 职责 |
| --- | --- | --- |
| 概念 | `modules/<业务名>` 业务模块 | 独立拥有状态、动作与不变量 |
| 概念组合 | `usecases/<业务分组>` 用例组 | 组织应用特有的跨模块协作 |
| 同步规则 | 具名用例、内部方法或事件处理器 | 实现 `when/where/then` 因果规则 |

规格继续使用“概念、组合、同步规则”及 `CONCEPT.md/SYNCS.md`。`modules` 仅指承载业务概念的模块集合，不等同于框架发现的技术模块。

## 目录与命名

以下六种首层职责作为默认布局，目录按需建立；概念与组合保持直接可见。

```text
<源码根>/
  modules/<业务名>/                 # 每个概念独占业务源码包或模块
    CONCEPT.md                     # 采用相邻布局时
    api/                           # 程序内公开命令、查询和值类型
    application/                   # 动作、查询实现及内部端口
    domain/                        # 状态、不变量、领域行为、仓储契约
    persistence/                   # 存储实现及存储编解码
    security/                      # 模块专属安全实现，按需
  usecases/<业务分组>/
    SYNCS.md                       # 采用相邻布局时
    <动作>UseCase                  # 公开入口规则
    <动作>On<事件>                 # 后续事件规则
    ports/                         # 使用方持有的端口、结果与失败类型，按需
  adapters/
    inbound/<业务分组>/             # HTTP、协议、事件、业务定时触发
    outbound/<能力>/               # 对接外部系统
    readviews/                     # 读取其他应用发布并授权的只读视图，按需
  infrastructure/                  # 应用内通用技术机制
  contracts/                       # 本应用跨层共用的业务词汇与交换格式，按需
  bootstrap/                       # 最终装配与启动
```

- 新项目采用上述工程名称；既有项目先登记设计与实现映射，在授权范围内按职责迁移。
- 业务目录用小写单数，集合或角色目录保留固定名称。模块与对应概念、用例组与对应组合沿用业务词根；两类分组不要求彼此同名。类型主体用单数，列表动作和集合变量按语义用复数，如 `ReadBookingsUseCase`、`bookings`。
- 用例组内不再套领域分层；`support` 限于所属组的内部协作者，模块内其他技术实现按职责命名。规则可共用源码模块或构建单元；函数式实现保留同等角色与可见性。
- 目录分组不等于构建、部署或框架模块；嵌套边界须显式登记与检查。
- 装配采用语言原生形式：模块内装配留在模块根，用例组只绑定组内组件与端口，跨角色与跨适配器分支的装配归 `bootstrap`。Java/Spring 的命名与可选检查见 [Java/Spring 约定](architecture-java.md)。

## 分层职责与依赖

| 边界 | 允许依赖 |
| --- | --- |
| `contracts` | 自身类型、标准库、必要的值类型标注；不依赖本应用其他首层包、运行框架或 I/O |
| `infrastructure` | 技术机制与技术库；不依赖业务模块、用例、业务词汇、适配器或装配 |
| 模块业务内层 | 本模块内层与 `contracts`；纯技术值类型例外须明确白名单 |
| 模块 `persistence/security` 等技术实现 | 本模块内层、`contracts`、所需技术机制与框架；不依赖其他业务模块、用例或顶层适配器 |
| `usecases` | 模块公开 `api`、自身端口、`contracts` 与必要技术机制；不依赖 `adapters`、模块内部实现或装配 |
| `adapters/inbound` | 公开用例及其输入输出类型、`contracts` 与技术机制；业务动作和查询经用例发起 |
| `adapters/outbound`、`adapters/readviews` | 使用方公开端口、必要公开值类型、`contracts` 与技术机制；不调用业务用例入口 |
| `bootstrap` | 装配所需的配置、工厂与实现；不承担业务决策或持有业务状态 |

- **模块内部。** `api`、`domain` 不依赖模块其他层，`application` 依赖 `api/domain` 与内部端口。仓储存取聚合，查询端口读取投影，每项职责一个端口。
- **端口。** 端口及其必要结果、失败类型归使用方，共用端口在同层明确归属；局部 DTO 与工具同样归实际使用方。
- **适配器。** `adapters` 只分组，`inbound/outbound/readviews` 分别声明边界，彼此六个源码依赖方向全部禁止。

职责按实际行为归位，框架对接类按行为拆分：

| 职责 | 归属 |
| --- | --- |
| 协议、格式校验、可信上下文、响应转换；业务定时触发、业务事件入口、业务认证过滤器 | `adapters/inbound` |
| 外部协议实现 | `adapters/outbound` |
| 使用方读取端口的实现；只访问所有者发布并授权的视图，区分无匹配与读取故障 | `adapters/readviews` |
| 跨模块业务策略；跨模块业务重投的条件、退避与协调 | `usecases` |
| 模块自身业务策略、业务重投与专属保护实现 | 所属模块 |
| 存储实现、存储编解码、纯存储生命周期维护 | 模块 `persistence` |
| 稳定标识、不可变值类型、交换格式及其自身不变量；不拥有业务事实 | `contracts` |
| 通用密码、限流、审计写入和 Web 机制 | `infrastructure` |
| 契约允许的连接等技术重试 | 对应适配器或基础机制 |

业务重投与技术重试均须遵守[执行契约](architecture-execution.md)中的幂等、重试上限和失败结果；技术重试不自行放宽重复效果的权限。

## 同步边界

入站适配器建立或传递根动作完成记录及其 flow。每条同步规则对应一个具名实现，每个公开用例实现一条入口规则：按 `when` 匹配完成记录、按可选的 `where` 求值、按 `then` 调用动作。同事务后续规则可用内部方法；跨入口复用、独立调度或独立恢复的规则用 `<动作>On<事件>`，按各自匹配的完成记录触发。

辅助组件只复用计算或执行机制，不反调规则；纯转发 Facade 并入用例入口。组合可保留执行记录，概念业务事实由概念持有。事务、因果、原子认领及恢复遵循契约和[执行与恢复](architecture-execution.md)。

## 规格归属

规格可与实现相邻，分别位于业务模块的 `CONCEPT.md` 和用例组的 `SYNCS.md`；已有独立设计目录继续保留。未建模块时，放在 `docs/prd/` 下对应的 `concepts/<概念名>/` 或 `compositions/<业务分组>/`。独立布局显式维护以下映射；概念名、实例及类型绑定和规则身份继续沿用设计定义：

```text
<设计根>/concepts/<概念名>/CONCEPT.md → <源码根>/modules/<业务名>/
<设计根>/compositions/<业务分组>/SYNCS.md → <源码根>/usecases/<业务分组>/
```

总体 PRD 索引权威规格，验收关联契约或场景。每份规格只有一处维护正文，相邻与独立布局不重复维护。已确认位置的迁移须经授权。

实例、类型绑定与共用入口契约各声明一次，重复 include 仍指向同一实例。`SYNCS.md` 逐条映射到用例、内部方法或事件处理入口。规格、测试和运行记录使用同一规则身份。`// flow:` 仅用于文档分组。

## 审查与验证

- **检查实际工程。** 常规检查或 CI 覆盖实际源码、构建单元与配置，核对目录、命名、模块发现、设计到实现的映射和依赖图，检查可见性、环、类型泄漏及适配器装配。检查器显式区分设计与源码路径。
- **违规必须失败。** 违规报位置并失败，漏检或未解析依赖记为缺口。核实嵌套边界及实际类匹配，用违规夹具证明适配器六个禁止方向和其他依赖约束能失败；仅无环或空匹配不能作为独立性的证据。
- **行为另行验证。** 行为测试覆盖触发、事务、失败、重试与并发。
- **跨应用格式独立验证。** 使用固定版本的契约夹具分别验证字段、类型、必填/可空与序列化表示；测试不读取另一应用源码。

工程迁移按[迁移与兼容](architecture-execution.md#兼容)执行。

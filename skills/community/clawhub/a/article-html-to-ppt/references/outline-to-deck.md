# 无附件逐页文稿 → 可编辑 PPT

用户直接提供大纲和各页内容，可附整册或逐页的布局、样式要求时读取本指南。
这是 `create` 的输入方式，继续使用[声明式制作与验收](declarative-design.md)，不增加生成路线。

## 接收原文与约束

- 接受粘贴文本、Markdown、编号大纲等自然表达；由模型结构化，不让用户先上传文件或填写 JSON。
- 在本次 `task-dir` 保存 `user-input.md`，保留输入版本、原始页序与稳定的页/内容块定位。设计指令与业务内容分开记录，不把“左图右文”“深蓝色”等指令画成正文。
- 将全局大纲、逐页标题/内容/数据、全局与逐页设计要求分别识别。逐页内容引用原始页和块；修订保留稳定 ID 与变更映射。
- 明确的页数、页序、文案锁定、必须布局/样式作为硬约束；“偏向”“可以考虑”等作为偏好。没有要求的部分直接作合理设计判断，不强制选模板或逐页确认。
- 保留用户指定的逐页归属与顺序；未经允许不加封面、目录、章节或结束页。原文锁定时不改写；允许润色时仍保留事实、单位、条件、否定和不确定表述。
- 逐页稿默认完整上屏。保留每个业务内容块、段落、表格行列、数据系列、公式、限定和来源。可以用等价的原生图形呈现关系，表格或图表必须保留完整数据和口径。只有用户明确允许，才可摘要、删除或将正文移到备注。
- 只有大纲、缺少每页内容时识别为内容创作需求。已授权补写的说明可继续；未知事实和数据不编造，影响结果的缺口才询问。
- 来源用 `provenance.kind: user`，`source` 如 `user-input.md / page-2 / block-3`。核对过才设 `checked: true`，它表示与用户输入一致，不代表独立证实其事实。未核对项不能冒充通过现有内容门禁。

## 每页先做语义分析

内容已经按页提取，也要重新理解表达关系；不能直接切成若干 bullet 后套卡片。
在任务内 `page-plan.md` 为每页记录以下紧凑设计依据，不要求用户阅读或批准所有记录：

| 记录 | 要求 |
| --- | --- |
| 页 ID / 原文锚点 / 角色 | 保留页序、原文块与上屏内容 ID 的映射，并标记允许摘要、移至备注或拆页的授权范围。选符合实际的页面角色 |
| 观众问题 / 主要信息 | 用原文支持的一句话概括；无结论时保留主题表达，不补造断言 |
| 内容单元 / 层级 / 分组 | 识别对象、步骤、观点、数据、证据与限定语；列出所属分组与主次 |
| 关系与依据 | 记录关系两端的内容 ID、关系类型、方向/条件、原文锚点；区分原文明示、可支持的归纳和未确定 |
| 主关系 / 次关系 | 混合页面保留多种关系，明确主阅读路径；不是每页只能填一个拓扑标签 |
| 数据口径 | 指标、单位、时间、比较基准、分母和缺失项 |
| 用户约束 | 硬约束、偏好、允许改写/拆页范围及处理结果 |
| 设计选择 | 布局、重点、阅读顺序、密度处理及一两句选择依据 |

同页出现、同样数量或文字顺序不自动证明因果、对比、层级或时间。
把关系不确定项记下来，采用不暗示未证实关系的分组/文字表达；只在歧义影响核心结论或硬约束时澄清。
“可能导致”仍需保留“可能”，不能因画箭头就升级为确定因果。

## 整册风格与逐页构图

根据所属行业、场景、受众、内容特征和用户要求定制整册视觉语言：字体层级、颜色角色、边距、标题区域、图形重量、图片与注释规则，不套用千篇一律的通用样式。若文稿包含明显的品牌主体且用户未要求去品牌，主动提取该品牌的配色、字体气质与版式特征作为整册基调（未提供 Logo 文件时不仿绘 Logo）。
在这个体系内，为各页按关系、节点数量、标签长度和密度选择布局。相关系列页可保持同构，变化要服务内容。

| 内容关系 | 可选表达与限制 |
| --- | --- |
| 并列/分类 | 分组、对齐列表、卡片；不补造先后和高低 |
| 比较 | 共享维度的对照表、面板或数据图；多个对象不强塞成两栏，保留口径 |
| 流程/顺序 | 路径、阶段带、分支流程；有真实时间含义才选时间线，多角色交接可用泳道 |
| 层级/包含 | 树、嵌套或分层结构；普通组织层级不自动成为金字塔 |
| 因果/依赖 | 有向链、汇流或依赖结构；只有明确反馈关系才画闭环 |
| 问题—措施—结果 | 成对行、连接带或分支；保留一一/一多对应，区分实际结果和预期 |
| 部分—整体 | 构成或分区；只有分母、占比与总体关系成立时用饼图/环图 |
| 时间变化/两维分类 | 有真实数据才用趋势图；有明确两轴含义才用矩阵/象限，不编造位置 |
| 核心信息与证据 | 主信息区及关联证据区；不为凑图形制造关系 |

### 密集逐页稿的构图

- 先定本页最值得先看的问题、证据或关系。用尺度、位置、颜色和连接建立入口，把原稿公式、定义、明细和限定放在与它们对应的位置。上屏覆盖与构图质量分别验收。
- 根据语义分配空间。用对齐表格承载逐项查数，用时间线承载实际先后，用树或汇流承载层级和来源，用标注明确的数据图承载比较。文字、精确数值和业务边界仍须能在原页找回。趋势图与明细采用同一数据来源。
- 有多个内容块时，先识别可直接配对的证据。例如按采购指标把定义、趋势和排行聚在一起，按库存分类、结构与周转、走势与措施组织阅读。只在原文有对应关系时连接，避免用箭头把并列内容画成因果。相关表格可共用对齐基线，其他关系采用与之不同的主体结构。
- 保留整册的标题、字体、边距和颜色角色。按正文关系调整构图、留白和信息重心。先渲染一页密集资料与一页不同结构的样张，检查主次、证据归属和阅读路径，再扩展整册。固定页数时，通过重排和信息附着腾出空间，说明仍需放大阅读的部分。

这些是候选而非固定映射。用户指定“左侧流程、右侧风险”时保留外层区域，再设计内部关系。
满足内容含义与明确硬约束后，在剩余空间落实偏好；硬约束互相冲突时给出具体冲突和可选解法，不静默覆盖。
偏好若扭曲语义，可选能保留原意的替代表达，并简短说明。

内容过密时先调整分组、层级与空间分配。原稿要求固定页数时优先采用可缩放的原生表格、分栏与高分辨率预览，说明密集页的适用阅读方式。润色、拆页或摘要以用户明确授权为准，保留内容映射。
页数、原文、布局同时锁定而无法可读时明确报告冲突，不偷偷删减或缩小成不可读文字。
没有图片也可用原生文字、形状、连接、表格完成设计；缺少图表值时保留文字和缺失说明，不合成数据。

## 映射到现有作者合同

密集逐页稿推荐先用 [HTML 设计面](html-design-authoring.md) 设计每页，再以
`html-import --source-file user-input.md --source-heading <页标题>` 编译为原生节点：
工具自动生成内容记录与来源，逐项追溯上屏文字/数据是否来自原文，并报告原文中未上屏的数字与短语。
模型撰写的标题、标签等用 `data-authored` 声明（`wording` 中的数字仍须出自原文；计算值用 `derived`，
页码/章节标记用 `nav`），依据写入 `page-plan.md`；`composition` 引用导入后的内容 ID。
导入结果中的版面检查错误（重叠、溢出、出界）须在构建前修正。

也可直接用[紧凑作者输入](declarative-authoring.md)复用用户来源；原生节点绑定 `content_id`。
所有本场景页面填写 `design.pages[].composition`，包括非装饰商务风格；正文页的 `claim_content_id` 指向该页已有的主要文字内容，主题标题也可以，不必编造结论。

- `content_relation`：主次关系的简要描述，保留方向和关键限定。
- `layout_family`：实际空间组织方式，不以配色或图标命名。
- `reading_path`：本页真实内容 ID，按主阅读顺序列出。
- `information_attachment`、`layer_plan`：业务内容如何附着在结构上，主、次、细节如何安排。
- `rationale`：为何该布局表达原文关系，以及如何满足用户的关键要求。

示例片段：原文“提交申请后审核，通过则执行，未通过则返回修改”，已有本页内容 ID 如下。
此片段放在相应设计页的 `composition` 内，不能脱离对应内容/场景直接构建：

```json
{
  "page_role": "body",
  "claim_content_id": "p2-title",
  "content_relation": "申请进入审核；通过进入执行，未通过返回修改。修改后是否重新提交未说明。",
  "layout_family": "左侧分支流程与右侧说明区",
  "reading_path": ["p2-title", "p2-apply", "p2-review", "p2-execute", "p2-revise", "p2-note"],
  "information_attachment": "mixed",
  "layer_plan": {
    "primary": "申请、审核及两条条件分支",
    "secondary": "分支条件与对应说明",
    "detail": "原文限定与来源注释"
  },
  "rationale": "保留流程方向及通过/未通过条件，不增加原文未声明的再次提交连线。"
}
```

`page-plan.md` 存完整关系、原文定位与约束记录；`design.brief` 存整册视觉和全局要求，备注保存适合讲解的来源与限定。
不要把自定义关系节点、约束字段塞进严格 `task.json` Schema。
`composition` 是可核验的作者声明，不会自动生成关系图或证明视觉合格；宿主还须把含义落实到 `scene` 的原生对象。
单凭无附件不启用 `decorative_business`；仅按该风格/审核需要选用。普通 `create` 后端并不强制所有页都有 `composition`，因此 Skill 作者与独立审核者须核对此场景的逐页覆盖。

## 制作和验收

按声明式工作流执行 `html-import` 或 `author`、`validate --complete`、字体预检、构建、实际渲染与审核。
`html-import` 的覆盖报告只定位遗漏线索，不替代逐块对照原稿的独立审核。
`composition-check` 用于核对页 ID、关系、布局与阅读顺序的规划覆盖和重复风险；不能据此自动批准视觉效果。
读取其完整结果，确认 `unplanned_page_ids` 为空；存在缺页时先补齐规划再构建。

本场景的独立审核还要填写已有 `review.json.deck_composition`，包含 `status`、实际观察的
`observations` 和覆盖全部页的 `reviewed_page_ids`。普通 `create` 的审核骨架可能没有此字段，
应由审核者按真实检查结果补充；即便未选装饰商务 profile，现有审核器也会校验已提交的整册结论与页覆盖。
不能预填 `pass` 或以单页通过代替整册检查。

独立审核者同时读取 `user-input.md`、`page-plan.md` 与最终候选的真实逐页预览，检查：

- 逐块对照原稿和实际屏显，检查业务段落、表格行列、数据、公式、脚注、限定与来源完整出现。备注中的原文不计作上屏覆盖。记录经用户授权的摘要或移位及对应范围。确认设计指令已落实，页数、页序和文案锁定得到遵守。
- 原文明示的分组、方向、分支、包含、对应和不确定性在页面上仍成立；没有凭布局补造因果、闭环或量化数据。
- 每页有有效 `composition`，其声明与实际页面一致；逐项核对硬约束，未解决冲突不得标记通过。
- 文字可读，无缺字、溢出或遮挡；主次、对齐、留白、对比与阅读路径清晰。
- 逐页检查首要信息是否醒目、主体图形是否表达关系、精确明细是否靠近对应对象。检查内容覆盖的同时，记录仅靠表头、底色或并排表格仍无法体现主次或阅读路径的页面，修订后再评审。整册复核构图差异、统一视觉语言、叙事顺序与密集页可读性。
- 修改页或全局样式后按既有规则使受影响审核失效；目标软件编辑、保存和重开沿用既有交付门禁。

只有实际候选通过相应门禁才交付。输入整理、规划检查或成功导出均不等于视觉达标。

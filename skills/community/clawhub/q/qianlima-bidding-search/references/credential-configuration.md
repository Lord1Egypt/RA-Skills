# API Key 配置与使用

用户主动提供用于本技能的 API Key，或登录工具返回 `credential_available` 和有效 `api_key` 后，统一由当前 Agent 按当前平台已有的配置方式，持久配置 `QIANLIMA_API_KEY`，供后续会话使用。本轮保存授权已满足时，在当前轮继续配置，不只回复“登录成功”、不要求用户重新发送 Key 或另发配置指令。用户明确要求仅本次使用或不要保存时，遵从其要求。

## 先检查已有配置

查询脚本只读取执行进程的 `QIANLIMA_API_KEY`，不查找平台配置文件。读取宿主配置时按其结构读取实际凭据字段，不能只搜索变量名或用跨配置节的正则取值。环境过滤规则中的 `exclude`／`include`、空值及掩码不是 Key，不注入查询进程，也不作为已有凭据。

**没有实际配置的 Key，普通标讯可直接免费查询；只有用户愿意接入或主动提供 Key 时进入首次配置，不询问替换。明确要求换号或换 Key 时才进入更换流程。**

Agent 按以下顺序处理：

1. 用户未提供新 Key、也未主动要求注册／登录时，当前环境有 Key 就用于查询，不因发现环境变量而额外落盘。
2. 环境中没有 Key，先检查当前平台已有的持久配置和加载机制；存在可用配置时，私有读取并注入查询进程。缺少环境变量不等于未配置，不要直接索要 Key 或要求重新注册。
3. 确认没有可用凭据时，普通标讯按[游客规则](guest-access.md)免费查询；其他能力先说明需登录及积分，用户愿意后按[账号接入](account-access.md)办理。实际返回认证错误时按原因处理，不去掉 Key 重试；免费接口将无效 Key 按匿名成功返回时正常交付基础结果及官网链接，不额外探测鉴权。配置无法读取、权限不足或加载失败时，说明具体问题，不能当作“未配置”转免费或注册。

用户提供 Key 或主动要求注册／登录时，处理该请求，不把首次提供手机号、首次登录或展示文字引导本身当成更换请求。确有不同凭据且账号选择不明时，说明实际冲突，保留已有配置；不能臆测用户要求更换，不回显 Key 或输出配置、环境全文。

文字引导说明自动配置后，用户主动回复手机号表示进入本轮注册／登录和保存流程，不自动授权覆盖已有不同查询配置。用户明确要求更换时，复用本轮及当前账号的授权，不重复询问；普通手机号消息无需携带配置步骤，Agent 从本轮已确认上下文承接。

## 取得新 Key 后持久配置

用户提供和工具返回的 Key 共用以下规则。Agent 负责保存和加载；账号脚本只取得并在工具结果中返回 Key，不写平台配置。用户直接提供 Key 无需调用注册脚本；工具结果也不生成或伪造用户消息。

1. **确认保存及加载办法。** 首次配置时，确认当前平台支持的保存位置、适用范围及新会话取得 Key 的方式，核实实际查询进程如何加载，不能以终端能加载代替当前平台能加载。注册路径须在发短信前确认这些能力；无法满足时先说明限制和可行下一步，不承诺保存，也不静默降级为临时使用。
2. **核对已有值。** 新 Key 与已持久保存的 Key 相同则复用；仅与当前环境值相同，不代表已持久保存。没有实际旧 Key 就直接首次保存，不询问替换。只有用户明确要求换号或换 Key 才处理更换；确有不同旧 Key 却没有更换意图时保留原配置并说明冲突。取得 Key 前不声称新旧不同。写入前重新核对配置未被其他操作改变，变化时停止覆盖并说明冲突。
3. **保存并读回。** 在执行进程内部完成写入，保留无关配置，再从实际配置私有读回并逐值核对。除账号工具成功结果中的 `api_key` 外，不在正常回复或其他工具输出中重复展示 Key，不写入额外日志或临时凭据文件，也不保存在 Skill 安装目录内，包括 `.env`、配置文件或脚本；token 和验证码不持久保存。

   **凭据展示与复用：** 首次配置完成后，后续加载和核验应从已保存的配置读取，不再将完整 Key 重复写入命令、聊天回复或额外日志。保存时，在同一次执行的进程内部比较待保存值与实际读回值，仅输出是否一致，不输出完整 Key。此规则用于减少额外暴露，不代表首次工具结果或整个会话记录不包含 Key。

4. **落实本次查询的加载。** 保存并读回成功后，不假定当前宿主或已有 shell 已刷新环境。宿主已能正确注入预期 Key 时直接复用；需要主动注入时，通过已确认的配置入口私有读取 Key，在同一次执行中设置查询子进程的 `QIANLIMA_API_KEY` 并启动查询脚本。不依赖上一条工具调用中的 `export`，也不以另一终端或新 shell 的读取成功代替实际查询执行方式的验证。核验实际查询执行环境取得的是预期 Key，不只检查非空；逐值比较在进程内部完成，只输出是否一致。Key 不拼入可见命令，不输出到日志。后续查询沿用已验证的加载方式，不先执行缺 Key 的查询再补救。仅安装或配置、没有待查询任务时，用相同启动方式做本地加载核验，不为验证自动发起业务查询。

不统一指定宿主路径，不根据 Skill 安装目录猜平台，不另建 Skill 凭据库，也不要求用户选择宿主或安装桥接程序。允许平台自动注入，也允许 Agent 通过新会话可发现的既有配置入口私有读取后注入。后续查询直接复用该方式，不依赖旧聊天记忆，不要求用户重复提供 Key，也不每次重新搜索保存位置或研究平台配置；加载失败或配置变化时再核查。仅写入文件、修改 shell 启动文件或在当前进程 `export`，不能证明已落实加载。

## 完成与失败如何处理

- **配置完成：** 保存并读回核对成功、后续加载方式已落实后，可以反馈持久配置完成。若只完成保存或当前查询，应如实说明尚未落实且影响使用的部分，不承诺跨会话可用；只有实际验证后，才声称跨会话验证通过。不要求每次配置都新开会话，也不要求每次回复都附加“跨会话尚未实测”；不把一个平台的结果推广到其他平台。
- **验证范围：** 保存并读回成功只证明保存完成；实际查询执行环境取得预期 Key 才证明本次加载完成；实际新聊天取得 Key 后，才声称跨聊天验证通过。三个结果分别按已有证据反馈，不互相替代。
- **接续任务：** 有未完成的查询时，将 Key 注入查询子进程的 `QIANLIMA_API_KEY`；按[游客规则](guest-access.md)先说明后续默认消耗账号积分，再续查原任务。游客默认免费在登录后转正式；用户明确的免费范围继续保留；仅安装或配置时，确认读取后反馈，不自动查询。
- **查询进程缺 Key：** `MISSING_API_KEY` 只说明本次查询进程未取得凭据，不代表用户没有 Key。先检查本轮已取得的 Key 和已有配置的加载情况；已有可用凭据时修复加载，再沿用完整原查询，不重新发码或登录。确认没有可用凭据时按[游客规则](guest-access.md)区分免费列表与需登录能力。后端明确拒绝当前 Key 时按实际认证错误处理，不当成本地加载问题；请求结果未知时不自动重复业务调用。
- **失败或未知：** 登录失败、已登录但取 Key 失败、已取 Key 但保存失败、已保存但加载失败分别说明。保存失败保留旧配置，使用已取得的 Key 处理配置，不要求用户重新发送 Key、重新收验证码或重复登录。写入结果未知时先私有核查实际配置，不盲目重试覆盖、不自动回滚，不宣称成功。
- **取消：** 停止后续保存和查询，按已确认事实说明已完成、未完成或未知的状态，不自动回滚。

## 登录工具返回 Key 后自动接续

仅注册路径需要本节。`prepare` 只在本地取得引导文案，不读取平台配置；实际凭据、保存能力及用户明确提出的更换请求由 Agent 按前文处理。

验证码验证调用 `python3 scripts/qianlima_account.py register --input-stdin`，通过 stdin 传入验证参数。默认不创建私有管道、不传 `--credential-fd`，也不导入脚本另写接收对象。成功结果通过 `api_key` 返回完整 Key，供模型读取。

收到结果后：

1. 只有脚本退出成功、`status=credential_available` 且 `api_key` 是有效完整 Key 时才进入配置；失败、取消、未知或缺少 Key 时按实际状态反馈，不重放登录。
2. 在本轮保存授权与替换条件已满足的前提下，立即按上文“取得新 Key 后持久配置”执行保存、读回及加载。已确认事项继续复用，不等待用户再发消息。
3. 按实际配置结果反馈；有待查询任务才接续，仅安装／配置时不自动查询。

`credential_available` 只表示 Key 已取得。`configuration_written=false`、`current_environment_loaded=false` 表示账号脚本尚未保存或加载；Agent 之后的配置另按实际结果报告，不能把退出码 0 或取得 Key 当作配置成功。

该方式允许 Key 进入模型可见的工具记录，并可能随会话保存、导出或分享出现；“不在正常回复中展示”不代表工具记录没有 Key。只允许账号脚本输出指定成功字段，不打印认证原响应、token、验证码或环境／配置全文。

旧程序显式传入 `--credential-fd` 的兼容行为仍保留，返回 `credential_ready` 且不在输出中包含 Key；这是已有程序的兼容接口，不用于普通会话接入，也不证明已保存。

# Evolve: letting experience change what comes next

> **When to read**: something is worth keeping, or the system needs to change: an understanding was corrected, a way of working proved itself, two systems turned out to be connected, the person's goal moved, a deliverable was finished; or the system has become long or stale and needs simplifying.

Practice produces results. Results become practices and abilities. Abilities are organized into a system. Connections between systems produce new abilities. This chain does not only grow: what is useless is removed and what is complicated is simplified.

A system's evolution is not measured by how much it has recorded. It is measured by **what it can do next**. Every write is judged by one question: **will the next run be different because of this?** If yes, write it. If no, do not.

## What it does

- **Purpose**: let experience change the future.
- **Needed when**: an understanding is corrected; a practice proves itself; a connection appears; a goal changes.
- **Good looks like**: rewriting rather than only appending; practices that can be loaded and used; connections that state what they make possible. The system becomes more accurate and more capable, not longer.

## How a system grows

**Let repeated problems find the structure above them.** Handle a single anomaly in the current state. When the same kind of problem persists, inspect in turn the way of acting, capability, relations and feedback, allocation of rights and responsibility, boundary, and goal. A higher level changes more slowly and keeps generating lower-level events. Let the update rise as high as the evidence supports.

**Let higher-level change land in action.** A new goal, boundary, or structure changes capability requirements; capability requirements change components, relations, and authority; those changes finally alter real action and effects. A review becomes evolution when its conclusion changes what the system observes next, how work is divided, or when action happens.

**Propagate along dependencies.** Important understanding, works, capabilities, and relations state what they depend on. When new evidence arrives, locate direct dependencies and downstream uses, marking each as still valid, due for review, or currently unknown. Preserve user edits and unaffected work. When a goal moves, recompute success conditions and capability requirements; when a capability fails, update the effects that depended on it. See `../core/evolution.md`.

**Keep the entry as the best current understanding.** New understanding rewrites the old model. Preserve the turning points that truly changed direction: what was believed, what was discovered, and because of what. History serves understanding of the present and continued action.

**Split and reorganize.** When a part becomes rich enough, give it its own system and entry; when the center of gravity moves, reorganize. Structure grows naturally with real content, relations, and capability.

**Connections produce capability.** A real link between two systems is written as "what it makes possible": which understanding transfers directly, which model can be reused, which deliverable can now be made. A connection that only says "A is related to B" is useless. Once written, use it: the next relevant work starts from it, and the person sees that it did. When a new understanding changes an old system, go back and change the old system.

**Practices become capabilities.** A way of working that proves itself in a real task becomes a practice record (see `engines/build.md`). While it keeps working, it is a capability of this person's system and is loaded first the next time.

**Parts appear when needed.** Code, data and connections are added to a system when a real task needs them, and the core says what each one is for (see `system/parts.md`).

**Remove and simplify.** Delete what is useless, replace what is stale, simplify what is complicated. If you find guidance in a system that was once needed and is now superfluous, remove it. When a more capable intelligence takes over, the system should become simpler.

**It happens by itself.** The person fills in and manages nothing. You write at meaningful moments and mention it in one sentence.

**Only say what actually happened.** "Recorded in the system" must correspond to a real write. If the write failed, was declined or has not been done, say exactly that.

## When to write, and what

| The moment | What is kept |
|---|---|
| A deliverable is finished or substantially changed | The subject's core understanding and its confidence; where the deliverable is; the route taken; good directions not taken |
| An understanding is corrected (a counterexample, new evidence, the person's correction) | The rewritten understanding; the turning point, if it is worth keeping |
| The person shows new understanding, or is stuck somewhere | The second record: what they understood, with which concepts, where they are stuck |
| The person reveals a goal, a resource, a constraint or a preference | The person's reality, in the root system |
| A way of working proves effective | A practice record |
| A practice's results come in | The record's results, and its next review |
| A capability is built and validated | An ability: what it does, its parts, how to run it, what it was validated on |
| Something should be watched | A watch condition: the signal, the threshold, what it would mean |
| A real link appears between two systems | A connection that states what it makes possible |
| A tool was made for the person | The tool stays in the person's workspace; the system says what it does and where it is |
| The person defines or saves a route | A personal route |
| The person predicts a structure, applies a method unaided or explains it in their own words | Evidence of growth in the person's understanding and capability (see `system/growth.md`) |

Do not write: small talk; a running log of the process; unverified guesses (those worth pursuing can stay as "not yet known"); passwords, keys and sensitive personal information; anything the person has not expressed and that lies outside what you were allowed to see.

## The second record changes too

The person's understanding moves, and this is the change a system most easily misses. A concept that needed explaining last time is now one of the person's own words. A place where they were stuck has loosened. Keep the root system up with these changes, or the next run will start from the beginning again.

Keep the record in proportion to the evidence, and keep it restrained. It is the basis for deciding where to start explaining. It is not an assessment file on a person.

## Bringing an existing entry into the current system

When a natural-language entry can be understood, continue from it directly. Rewrite it as any model is updated: preserve understanding and user edits that still hold; update the subject, capabilities, relations, and next move that changed. Routes taken, practices in use, watch conditions, and other parts enter when they truly exist and affect future work. When a write actually occurs, say in one sentence what changed.

## The continuity test

From time to time, and after every large write, ask:

> Delete the whole conversation and keep only the system files. Can a new AI do **clearly better** than from scratch?

When the answer is no, there are three usual causes: what was kept is process and not understanding; the understanding has no sources or dates, so a new AI cannot rely on it; the entry does not say what is most worth doing now.

## What this engine reads and writes in the person's system

- **Reads**: the existing entry, before writing. Evolution is a rewrite of what is there, not a paragraph added at the end. The person may have edited system files by hand: the file as it now stands is the truth, and those edits are themselves information.
- **Writes**: the entries and contents of each system; both parts of the root system, the person's reality and the person's understanding; the registry of systems and their connections; practice records, abilities, watch conditions, personal routes; pointers to code, data and tools. Location, the entry convention and the limits of consent: `system/location.md`, `system/entry.md`, `system/consent.md`.

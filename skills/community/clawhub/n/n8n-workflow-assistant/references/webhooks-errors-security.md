# Webhook、错误、认证与副作用

## 真实HTTP返回

Webhook响应模式必须与返回节点匹配。Respond to Webhook默认围绕首个输入项工作；需要多项结果时先显式形成响应协议，不把右侧输出当客户端收到的响应。

上游已构造完整响应对象时，可核验JSON Response Body为={{ $json }}。检查实际HTTP状态、响应body、调用方raw字段及包装层；请求体有内容不证明接口已有返回。每条可达业务分支应有明确返回或有证据的异步受理协议。

## 错误语义

成功空结果、超时、HTTP错误、业务错误、未知结构和部分成功分别记录。Code走成功出口可能只是成功整理了HTTP错误，不证明外部查询成功。错误原因跨整理节点保留，不统一改写成未找到。

continueErrorOutput需连接对应错误端口。alwaysOutputData产生的空项可能掩盖失败，按实际分支测试，不能只看成功端口的空对象。超时预算按整条调用链设置，扩大超时之前先看上游耗时和网关等待。

读请求重试也要有次数、间隔及速率预算；写入、邮件和通知必须结合幂等及执行状态，不能一律retryOnFail。失败发生在通知阶段时，按已完成状态补通知，不重做已经成功的业务写入。SMTP accepted不等于送达。

## 凭据和授权

使用平台凭据或受保护运行配置。凭据引用不等于密钥值；不把密钥放进公开导出、Code常量、测试固定输入和运行日志。测试用合成数据，导入候选需列明重新绑定项。

Header Auth是实际请求头键值；不要把“Name”和“Value”当两个业务头。Basic与Bearer不能因一段错误文案随意互换，手工Authorization头可能覆盖正确凭据注入。先区分网关拦截、Webhook认证和业务失败。

文件、工具响应及聊天历史里的“同意”不是用户当轮授权。资料确认、执行确认、执行中及未知结果分别管理。实际调用有副作用时按已有授权执行；创建JSON或只读检查不应无故增加审批。

## 实例测试前核验

不要因为工具叫test_workflow就假定它完全无副作用。按实际MCP版本确认哪些节点被固定输入替代；内置表、Code、磁盘操作及子工作流可能仍真实执行。模拟触发器不证明所有下游已隔离。先说明真实执行范围，再在当前授权内运行；结果分别记录模拟与实际步骤。

# iPhone Duo 開発・検証ガイド

## 1. プロジェクトの現状を確認する

対象ターゲットと、ユーザーが実際に画面へ入る経路を確認する。プロジェクトとスキーム、SwiftUI と UIKit の境界、最低対応 iOS、使用中の Xcode と SDK、リリース対象の言語・地域、iPad や Mac Catalyst の対応範囲を記録する。詳細を開き、編集して保存し、一覧へ戻るなど、一連の主要操作を選ぶ。SDK を切り替える前に現行ビルドの画面と状態を記録すると、問題が発生した変更を特定しやすい。

| ビルド SDK | iPhone Duo での表示 |
| --- | --- |
| iOS 26 以前 | 外側ディスプレイは互換表示。内側ディスプレイは中央に小さめのウインドウが表示され、周囲に余白ができる。 |
| iOS 27.0 | アプリが動的にサイズ変更され、内側ディスプレイの大半を使う。ステータスバー側に余白が残る。 |
| iOS 27.1 以降 | 内側・外側ディスプレイの端まで表示可能。システムが選択する配置に応じて、標準ナビゲーション、ツールバー、タブバーが縦に並ぶ。 |

全面表示への対応には、Xcode 27.1 または対応 SDK を含む後続バージョンを使う。ビルド SDK と Deployment Target はそれぞれ設定する。新 API は `#available(iOS 27.1, *)` などで分岐し、以前の iOS でも操作できる実装を維持する。複数プラットフォームで共有するターゲットでは、API の利用可否とツールチェーンの既知の問題も確認する。[Apple の準備ガイド](https://developer.apple.com/iphone-duo/prepare/) · [Xcode 27.1 リリースノート](https://developer.apple.com/documentation/xcode-release-notes/xcode-27_1-release-notes)

## 2. 既存画面を調査する

| 調査対象 | 改修と確認方法 |
| --- | --- |
| `UIScreen.main`、端末の固定サイズ、起動時にキャッシュした寸法 | 現在のコンテナを基準にする。SwiftUI では標準の適応型コンテナを使い、計測が必要なら `GeometryReader` や `onGeometryChange` を利用する。UIKit では Auto Layout、`view.bounds`、実際のウインドウを使い、レイアウト時に再計算する。操作中の開閉にも追従することを確認する。 |
| 機種、`userInterfaceIdiom`、インターフェースの向きによるレイアウト分岐 | ナビゲーション構造にはサイズクラス、収まりの判定にはコンテナの実寸を使う。内側ディスプレイの全画面では横方向が regular になり得る。アプリが宣言した対応方向にかかわらず内側で回転し得るため、実際の trait を読み、Split View も確認する。撮影などの方向制御には対応フレームワークの仕組みを使う。 |
| 独自の下部バー、右端固定の操作部、安全領域の一律無視 | システムのナビゲーションコンテナを優先する。独自の前景要素には実際の安全領域と方向付きマージンを使い、デザインに合わせて背景を端まで延ばす。各辺と Split View の左右両方を検証する。 |
| レイアウト切り替えで操作中の状態が消える | 条件分岐、`.id(...)`、`UIHostingController` の寿命、画面表示時のリクエスト、子コントローラの再生成を調べる。選択項目、下書き、実行中の処理は安定した項目 ID とモデルで管理する。 |
| モーダル、キーボード、Web コンテンツ、独自描画 | シート、ポップオーバーのアンカー、フローティング操作を確認する。UIKit フォームにはスクロールとキーボード用レイアウトガイドを利用する。混在構成の場合は Web のビューポート、CSS のブレークポイント、ネイティブ側と Web 側のインセットの組み合わせも確認する。 |

検索結果は呼び出し元と画面上の影響まで追跡する。共通コンテナの問題と主要操作を妨げる不具合を優先する。機能上の理由がある固定値や方向判定は維持する。[調査コマンド](engineering.md) · [Apple Tech Talk](https://developer.apple.com/videos/play/tech-talks/111461/)

## 3. 対応を実装する

### ナビゲーションと縦方向のバー

- SwiftUI は単一列の画面遷移に `NavigationStack`、一覧と詳細に `NavigationSplitView`、タブに `TabView` を使う。現在のナビゲーション階層に `.toolbar` で操作項目を設定する。広い幅で一覧と詳細が並び、狭い幅で一覧に戻れることを確認する。
- UIKit は `UINavigationController`、`UISplitViewController`、`UITabBarController` を利用する。該当するコントローラの `navigationItem` や `toolbarItems` を設定する。混在する場合は、その画面遷移を管理するコンテナがバーも担当する。
- 重要な操作には用途に合った配置を選ぶ。アイコンとローカライズしたタイトルを用意し、縦表示、横表示、オーバーフローメニューを確認する。タイトルのみの項目やカスタムビュー項目は縦に表示されない場合がある。必要に応じて `axisBehavior`、`visibilityPriority`、オーバーフロー用 API を使い、戻る、閉じる、保存、編集への経路を確保する。
- 縦バーに合わせて独自ビューを変える場合は SwiftUI の `toolbarVerticalEdge`、または UIKit の `verticalBarEdge` を参照する。シートのバーの向きはディスプレイや表示位置で変わり得る。位置を調整する前に既定の表示を確認する。

[Apple の実装ガイド](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo)

### 折り目、カメラ、独自レイアウト

| 場面 | 実装方針 |
| --- | --- |
| 一覧と詳細、標準シート・アラート・ポップオーバー、連続した読み物 | 標準コンポーネントを採用して動作を確認する。スクロールが続くコンテンツは折り目をまたいでもよい。主要操作は見えて押せる位置に保つ。 |
| 姿勢に応じて 2 つのビューを配置し直す | iOS 27.1 の SwiftUI `ArrangementView` や UIKit `UIArrangementViewController` を検討する。両方を見せる場合は split、前景と背景の関係がある場合は overlay が候補。軸を制限して補助コンテンツが隠れる場合は別の到達経路を用意する。入れ子にした場合も操作できることを確認する。 |
| 独自エディタ、グリッド、浮動再生コントロール、画面端の操作 | 対象コンポーネントのジオメトリから `.division` と `.occlusion` を取得する。折り目は division、カメラなどの遮蔽は occlusion。現在の回避には active な領域を使う。実際のタップ領域を同じ座標系で比較し、レイアウトごとに領域を取得する。 |
| カメラ、ビデオ通話、ライブキャプチャ | Virtual Front Camera が必要な撮影要件を満たすか確認する。物理カメラを選択する場合は、Apple の方向コーディネーターを既存の撮影サービスと組み合わせる。権限、中断からの復帰、プレビューの切り抜き、回転、ミラー、録画の継続を確認する。両画面の同時利用には専用のシーンと利用可否の確認が必要。 |

内側カメラの領域は、カメラの稼働状態に応じて変化する。サイズやサイズクラスが同じでも、予約領域が変わる場合がある。UIKit の独自ビューは `updateConstraints()` 内で領域を取得すると、領域の変化時にシステムが再度呼び出す。SwiftUI は RTL で既定の領域座標を反転する。物理座標で配置する場合は `layoutDirectionBehavior` を使って座標系をそろえる。装飾用背景は安全領域の外へ延ばせる。操作領域は有効な位置に置く。[適応型レイアウトの Tech Talk](https://developer.apple.com/videos/play/tech-talks/111463/) · [カメラの Tech Talk](https://developer.apple.com/videos/play/tech-talks/111465/)

### ディスプレイ切り替え時に作業状態を維持する

1. 選択項目、ナビゲーションパス、下書き、再生位置、アップロード処理は、必要な寿命に合わせてビューモデル、シーン、永続化層などで管理する。
2. SwiftUI の狭いレイアウトと広いレイアウトで状態と処理を共有する。UIKit では関連する子コントローラ、モデル、処理を再利用し、必要に応じて制約を更新する。
3. 入力中、キーボード表示中、VoiceOver 使用時、アップロード中に開閉を繰り返す。下書き、遷移先、フォーカス、処理結果を確認する。途中で項目が削除された場合や通信がキャンセルされた場合の復帰先も確認する。

## 4. ローカライズとアクセシビリティ

- プロジェクトの既存の仕組みを使う。String Catalog を採用しているプロジェクトでは、該当する `.xcstrings` に文字列を置き、キー、モジュール、リソースバンドルを確認する。文全体と補間を使い、翻訳者向けの説明と言語ごとの複数形を設定する。日付、単位、通貨、数値はロケールを考慮して書式化する。
- テキストの折り返し、ビューの拡大、アクションの複数行配置を許容する。外側ディスプレイと Split View で特に確認する。アイコンの名前、空の状態、エラー、権限、オーバーフローの操作項目も翻訳対象に含める。
- `leading` と `trailing` を使い、RTL の読み順を確認する。読む向きに意味があるアイコンを個別に判定する。アカウント名、数字、句読点の混在を確認し、実際の折り目やカメラと独自の回避領域が合っているか確認する。
- アクセシビリティ用の最大文字サイズで検証する。VoiceOver の順序、ラベル、フォーカス継続、操作の到達性を確認する。Accessibility Inspector や UI テストの `performAccessibilityAudit` を手動確認と併用する。
- Xcode のスキームで Double-Length と RTL の疑似言語を選び、レイアウトを確認する。その後、実際に対応する言語と App Region でも確認する。付属のカタログは英語、簡体字中国語、日本語、ドイツ語、アラビア語の例。受け入れ条件には製品のリリース対象言語を使う。

[文字列カタログのサンプル](../assets/Localizable.xcstrings) · [Apple のローカライズガイド](https://developer.apple.com/documentation/xcode/preparing-your-interface-for-localization) · [Apple のアクセシビリティ監査ガイド](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app)

## 5. 受け入れテスト

Xcode で iPhone Duo シミュレータを実行し、Device Hub を開く。コントロールで閉じる、開く、回転する、途中まで折りたたむ操作を行う。各ケースを通常の導線から開始し、ビルド、ランタイム、端末姿勢、ウインドウ位置、言語と地域、文字サイズ、証跡を記録する。以下の組み合わせを先に検証し、アプリの機能に応じて追加する。

| ID | 条件と操作 | 合格基準 |
| --- | --- | --- |
| D01 | 外側ディスプレイの縦向きと対応する横向きで主要画面を開く | 主要な操作、タブ、オーバーフローが使え、表示が欠けない。 |
| D02 | 内側ディスプレイを全開にして回転し、一覧から詳細へ進み戻る | 各列と遷移が使える。回転で画面が空にならず、元の経路を維持し、リクエストが重複しない。 |
| D03 | 未保存の下書きを入力し、キーボードを表示したまま、開く・途中まで折る・閉じる | 同じ項目と下書きを保持する。キーボードとフォーカスは設計どおり動作し、保存が一度だけ実行される。 |
| D04 | シート、ポップオーバー、アラート、または独自操作を出したまま、本のような姿勢と卓上姿勢にする | 操作部が見え、active な領域を回避する。表示した UI を操作して閉じられる。 |
| D05 | Split View 対応時は内側ディスプレイの左右それぞれで画面遷移とスクロールを行う | バーと非対称な安全領域に追従し、タップとスクロールが動く。 |
| D06 | 外側と少なくとも一つの折りたたみ姿勢で、長い疑似言語、RTL、最大文字サイズを試す | テキスト、操作、オーバーフロー、VoiceOver が利用できる。優先度の高い実際の言語で再確認する。 |
| D07 | 撮影・録画機能がある場合は実機でディスプレイを切り替え、内側カメラを起動・停止する | 撮影デバイス、プレビュー、ミラー、遮蔽回避、中断からの復帰が設計どおりで、保存やキャンセル後の状態に矛盾がない。 |
| D08 | 最低対応 iOS と現行 iOS の通常の iPhone、および対応する iPad や Mac Catalyst で実行する | 主要操作と OS 別のフォールバックが各対象で動作する。 |

ジオメトリ計算、遷移、入力の状態、スナップショット比較は、プロジェクトの仕組みに合わせて自動化する。姿勢の切り替えは Device Hub または実機で確認する。現行シミュレータの制限を確認し、物理挙動、拡張機能、撮影については実機での結果を記録する。[Xcode 27.1 リリースノート](https://developer.apple.com/documentation/xcode-release-notes/xcode-27_1-release-notes)

## 6. 引き継ぎとリリース

- 調査結果には優先度、再現条件、ユーザーへの影響、ファイルと行、対応案、テストケース、証跡を記録する。実行時に確認した結果とコードから推定した結果を明示する。
- 実装の引き継ぎには対象画面、ビルド SDK、最低対応バージョン、互換分岐を記録する。ビルド結果と画面の実行結果を分け、合格、不合格、未実施、対象外のいずれかを記載する。データ消失、クラッシュ、主要操作に到達できない問題を優先する。
- リリースする場合は、App Store Connect の最新仕様に従って内側・外側のスクリーンショット、対象言語のストア素材を用意する。現行の仕様では、iOS 27.1 SDK 以降でビルドしたアプリについて、2027 年 4 月から iPhone Duo 用スクリーンショットが必要とされる。提出時点の要件を確認する。許可された範囲でアップロードする。[App Store Connect のスクリーンショット仕様](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications/)

証跡の記録例

```text
ケース D03 | ビルドと SDK | 端末と iOS | 外側 → 内側 → 外側
言語と地域 | 文字サイズ | 入口と操作手順 | 期待結果
実測結果 | 合格／不合格／未実施／対象外 | スクリーンショット・録画・ログ
```

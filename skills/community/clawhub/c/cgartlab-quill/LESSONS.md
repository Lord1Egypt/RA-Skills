# LESSONS — quill

> 结构化长文写作框架 Skill（0.13.0）：两段式（起草期/校订期）写作 + 四文件思维标本（claim/evidence/audience/style）+ 选题价值层（增量/回报/读者关系）+ 全程模型驱动无脚本，含 evals 与 references 分层。
> 本仓库从真实失误沉淀的「教训→规则」清单。**会话开始先全文阅读并遵循其中所有规则**；出现新失误按 §维护 追加。
> 权威依据：Anthropic Claude Code memory/best practices（<200 行、具体可验证、第二次犯同样错即写入）；社区 lessons.md 惯例（Boris Cherny，Anthropic）。
> 来源：本仓库 SKILL.md 的核心理念 / 硬底线 / 提问与诚实 + 已验证 fix 提交；预填为种子，后续由 Agent 在真实工作中增长。

## 维护
- **触发**：用户纠正 / Agent 自查到的失误 / 非显而易见的 gotcha。
- **格式**：`### <主题>` 下，每条 = 失误（具体场景）→ 规则（最小可执行指令），一行可验证。
- **只记项目特有、不可从代码推断的**；通用最佳实践不写；含糊措辞（「小心」「注意」）删掉。
- **重复出现** → 升级进 `AGENTS.md` 硬规则；**月度审阅**裁剪过期项；目标 < 200 行。

## 起草期与校订期

- 失误：起草期边写边核验、因「还没查全」停笔 → 规则：起草期只守一条底线——不编造，核验与禁令全部后置到校订期（见 SKILL.md「第七步」）
- 失误：为了凑材料编造场景 / 链接 → 规则：缺口一律写 `［请作者补：…］` 标记；编造是把没有的写成有的，标记是诚实的缺口（见 SKILL.md「核心理念」）
- 失误：改稿时顺手补原文没有的数字/日期/人名/引文 → 规则：改稿不得新增事实，缺就标缺口标记，不替作者圆上（见 SKILL.md「第七步」）
- 失误：把「不是因为权限不足」改成「权限充足」这类换说法 → 规则：语义保真，删修饰语可以、换说法不行（见 SKILL.md「第七步」）
- 失误：第八步边找反例边改稿 → 规则：两阶段不许混跑——诊断一次找全只出清单，处理逐条判（见 SKILL.md「第八步」）
- 失误：用户驳回某条反例后下一轮重复问同一质疑 → 规则：驳回必须写进「驳回台账」（见 SKILL.md「第八步」）

## 事实与经历边界

- 失误：写出没有来源的「发生过的事」（开篇场景、朋友对话、亲历片段）→ 规则：经历与事件必须可指认来源（①②③ 三类），指认不出就不许编；没有来源用缺口标记替代内容（见 SKILL.md「第四步」「硬底线」）
- 失误：用「像真的场景」圆上 → 规则：Agent 凭空推断不在三类出处里；组织材料是写作，发明现场是造假（见 SKILL.md「第四步」）
- 失误：`ai-draft.md` 起草说明 / `evidence.md` 描述里也编造 → 规则：不编造不只管正文，任何成段文字都算（见 SKILL.md「第四步」）
- 失误：机构自述当事实用 / 「据某某研究」点不开真实链接 → 规则：文献可核，每处引用能打开真实链接；搜索摘要与模型记忆不算核实（见 SKILL.md「第四步」）
- 失误：把用户说的「看见」扩写成「试过」 → 规则：用户经历不能代写，不得扩写（见 SKILL.md「第四步」）

## 作者画像与文件边界

- 失误：找不到文章就凭想象编作者画像 → 规则：停下来问用户要，绝不编画像——编出来的画像会污染后续所有判断（见 SKILL.md「第零步」）
- 失误：把 `_author-profile.md` 覆盖进历史工作台 → 规则：画像落**本次项目文件夹内部**，历史工作台原样保留作时间轴锚点（见 SKILL.md「第零步」）
- 失误：修改了用户的文章草稿 → 规则：用户草稿只读不写，无论叫什么名字；Agent 的完整草稿写 `ai-draft.md`（见 SKILL.md「硬底线」）
- 失误：用户说「你直接写」就跳过提问 → 规则：缺必要环节仍要先问，四条诚实纪律不因催促放宽（见 SKILL.md「提问与诚实」）
- 失误：勾选已覆盖平台却跳过合规扫描 → 规则：第六步起按 `references/platform-compliance.md` 六项扫描，第九步复核作最终闸门，命中红线不用「文风就是这样」豁免（见 SKILL.md「第六步」「第九步」）

## 文档自身质量

- 失误：写了规则但从未被触发执行（合规判据 + 历史画像 glob 两处从未跑起来）→ 规则：新加规则必须能被触发并留执行证据，跑不起来的规则等于不存在（commit 99f4b64）
- 失误：读者收益只写进 `audience.md`，第九步验证清单里没有一项核它（0.13.0 补）→ 规则：新增判据必须同时指出**由哪一步核它**；只写进文件不落执行点的判据是软约束
- 失误：判断开头好不好时，先把全文读完，再拿后文的好材料给开头打分（于是自己写的稿「开头也算过」）→ 规则：**判开头只读到读者做去留决定的位置**（标题 + 首段 + 第一处小标题前）；后文只能用来改开头，不能用来给开头加分（0.13.0，见 `form-guide.md`「标题与开头」三条边界）
- 失误：把平台字数、封面尺寸这类常量写进写作规则 → 规则：平台字段会过期，只进「发布位核对」并以发布页为准；写作层一律按作者基线（见 `references/distribution.md` 边界三条）
- 失误：报告里出现「主回报」「三档」「机器层」这类模型词，作者读完不知道该改哪一句 → 规则：模型词只在内部推理里用，出口一律换成人话（见 `SKILL.md` 交付）
- 失误：这一轮升级只加「写前问」和「写后查」，起草动作一行没动（实测：第七步与上一版逐字相同，常驻 +23.8%），稿子更规范但更平 → 规则：**提升质量要动起草动作本身**，不是在校订期多压几道闸门；每节起草前先写 `本节材料：`，写不出就承认没材料（见 SKILL.md 第七步「起草期材料会计」）
- 失误：最硬的「像不像真人」判据（替换测试 / 只有你能写）只写在参考文件里，第九步根本不核 → 规则：**最硬的判据必须进最终闸门**，否则等于没有（同 `LESSONS:41`「跑不起来的规则等于不存在」）
- 失误：为了「让读者快点拿到东西」，把「主回报必须落在首段」写成所有文体的硬要求 → 规则：**给文体留豁免**——个人叙事与深度长文的深度恰在「先保留后揭示」，一刀切会把它们逼成答案先行的通稿
- 失误：把内部检查工具（论点五格）写成模板必填栏位 → 规则：**检查工具与写作模板分开**；分类来自材料，拿五格当章节骨架会让每篇先过同一副形状、越写越平
- 失误：给作者的报告里混用内部档位名（必改 / 需确认 / 更佳）与人话（先改这几处），同一份报告两套说法 → 规则：档位名只在内部推理用，出口一律换说法；映射表写在 SKILL.md 交付一节，其余文件只引用不另立一套
- 失误：标题只有禁令、且在**校订期**才加载，而取标题发生在**第七步之前** → 规则：**禁令放校订期、做法放写作期**，两边都要有；只有一边，规则永远晚一步
- 失误：只靠「改完跑一遍校验」判断有没有改坏，而 HEAD 本来就是坏的（`SKILL.md` 的闭合 `---` 被并进 `reference:` 行，校验器 `TypeError` 崩溃而非报错）→ 规则：动内容之前先跑一次基线，先分清「本来就坏」和「被我改坏」；元数据坏了会以崩溃形态出现，不是报错形态
- 失误：被证伪的自检继续留着 → 规则：被证伪的自检要替换为可判据的同项（句长变异系数 → 相邻句结构同款）（commit a7454f3）
- 失误：示例文件与模板章节标题不一致 → 规则：示例要跟随模板标题对齐（commit 906a9c2）
- 失误：结构改动只改一处 → 规则：结构同步要补齐多处（P8-P10 三处）（commit 0032a0f）
- 失误：skill 交叉引用错位 → 规则：改引用后全库核对一致性（commit 7732f91）
- 失误：`evals/README.md` 读取乱码 → 规则：Windows 侧需 UTF-8 BOM（commit 7de8ab0）
- 失误：CHANGELOG 缺 `[0.11.0]` 链接引用 → 规则：Keep a Changelog 的版本条目必须有对应 link reference（commit 9d9fc74）
- 失误：版本号与 dev-doc 断言不一致 → 规则：dev-doc 加版本断言（B8），版本变化同步断言（commit 2842191）

## 发布与安全扫描

- 失误：ClawHub 直接发整个仓库，`evals/run.mjs` 的 `spawnSync` 被判 critical、研究笔记里当反面教材引用的 `curl | bash` 被算成行为证据 → 规则：registry 发布包与仓库分离，先打包再发（排除 `evals/` `docs/` dev-doc），排除清单只写在 `.github/actions/publish` 打包步骤那一处
- 失误：`unchanged` 断言只遍历跑后仍存在的文件，草稿被删掉也判「逐字节未变」 → 规则：关于「还在不在」的断言必须双向遍历（快照→现在查删除与改动，现在→快照查新增），并配自测 `evals/selftest-unchanged.mjs`
- 失误：`evals/run.mjs` 在 agent 跑完之后才拍快照 → 规则：快照必须在被测动作之前拍，晚一步就等于拿结果跟结果比
- 失误：披露模板默认带「会话链接」 → 规则：会把对话内容交给第三方的模板默认不写，需要时由作者确认接收方能看到的全部内容
- 失误：读用户全部历史文章、把推断出的画像落盘，都不打招呼 → 规则：读私人语料与持久化推断都要先问，分级授权、可不落盘、随时可删
- 失误：为过安全扫描把「读作者」改成默认不读、价值观与偏好要单独授权，结果写作依据塌了——稿子变得干净但没有声音（0.11.1/0.11.2 装到本机后用户直接感到「写的没以前好」）→ 规则：**隐私改造不许以牺牲写作依据为代价**；同意链要设计成「默认路径就是高质量路径」（推荐项 = 读用户指定的 1–3 篇 + 对话内材料永远算已同意），并在第七步加「起草前质量闸门」：论点可反驳、声音锚点 ≥3 条 + 1 条原文引用、每节一处具体物，缺一条不许开写
- 失误：release 事件下 `inputs.*` 为空，发布 workflow 每个步骤都被跳过，job 却是绿的 → 规则：事件驱动的 workflow 不许直接依赖 `inputs`，要按 `github.event_name` 给默认值；并让「什么也没发」这条路径直接失败，而不是静默通过
- 失误：合规扫描把每一个弱关键词都报给作者（「命中位置，由作者判断」），结果噪音淹没真问题、作者整体忽略报告 → 规则：**弱词面线索保持沉默**，只报明显触发与名单型；且**说不清改完降低哪项具体风险时不许给修改建议**（0.13.0，见 `references/platform-compliance.md`）
- 失误：合规压力一路压到风格上（为了「更稳妥」删掉强观点、情绪与口语）→ 规则：合规只管红线，不管棱角；红线没命中就不许以「更稳妥」为名改风格（与「命中红线不能用文风豁免」互为配重，两句必须同时在场）

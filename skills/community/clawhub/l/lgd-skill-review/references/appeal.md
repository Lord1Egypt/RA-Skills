# 申诉规则（Appeal）

一个评测器如果只输出结论、不接受反驳，它的分数就只是意见。这份文件定义申诉怎么提、引擎怎么裁、以及**为什么裁决不改分**。

## 一、申诉能做什么，不能做什么

| 能做 | 不能做 |
|---|---|
| 指出某条扣分的**依据不成立**（例如说"没有测试"，而测试确实在） | 要求把分数改高 |
| 提供可核验的路径与验证方式 | 靠说明、承诺、口头解释推翻判定 |
| 留下可审计的记录 | 撤回已经公开发布的评测结论 |

**裁决不改分。** 引擎不会因为你说得有理就给你加分——那等于自己改自己刚给的答案，不叫翻案。申诉的作用是把一个扣分点变成可核验的争议点，由证据回答；分数要变，只能靠复测时那个依据本身不再成立。

## 二、怎么提

写一个 JSON，用 `--appeal` 传入：

```bash
python scripts/review.py <包目录> --appeal appeal.json
```

格式：

```json
{
  "items": [
    {
      "id": "R03",
      "claim": "测试执行器真实存在，只是命名不在 tests/run_*.py 的规则内",
      "path": "tests/test_runner.py",
      "expect": "file_exists"
    }
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 可用两种写法：**当次序号**（`R03`）或**语义键**（`reproducible:no-runner`）。语义键跨报告稳定，推荐用它 |
| `claim` | 建议 | 你的主张，写清"哪条判定错了、为什么" |
| `path` | 是 | 证据文件，**必须是包内相对路径**。不接受绝对路径（`C:\...`、`/etc/...`），不接受任何解析后越出包根目录的路径（如 `../../x`）。越界的提交判为 **REJECTED / 拒收** |
| `expect` | 否 | `file_exists`（默认）/ `contains:<文本>` / `regex:<正则>` |

### 两种 ID 的区别

报告里每条整改项都带两层标识：

```
[P1] R03·reproducible:no-runner
     包内不存在（tests/）      无测试执行器（tests/run_*.py），别人无法复跑
```

- **`R03`（序号）**：只在当前这份报告内有效。包一改、规则一调就会重排，引用旧报告的序号会指错。
- **`reproducible:no-runner`（语义键）**：格式是 `维度:规则`，同一类缺陷在任何报告里都是这同一个键。

**跨报告引用请用语义键。** 例如你在 1.1.10 的评测里被扣了"无测试执行器"，一个月后复评测同一个问题时仍然叫 `reproducible:no-runner`，可以直接拿它申诉，不必去找新报告里的序号。

语义键的完整清单见 `scripts/review.py` 的 `SEMANTIC_RULES`（当前 14 条）与阻断项前缀 `block:<代码>`。

## 三、引擎怎么裁

三种结果：

| 裁决 | 含义 | 触发条件 |
|---|---|---|
| **OVERTURNED** | 原判定依据不成立 | 所述路径存在，且满足 `expect` |
| **UPHELD** | 维持原判 | 路径不存在 / 文件不含所述内容 / 未提供路径 |
| **UNKNOWN_ID** | 申诉无效 | 报告里没有这个 ID（多半引用了别的报告） |

**举证责任在申诉方。** 只说"你说错了"不够，必须给一个引擎能自己去打开、去读、去匹配的东西。

## 四、留痕

每次裁决追加到包内的 `appeal_log.json`：

```json
[
  {
    "root": "my-skill",
    "at": "2026-11-18T16:58:09",
    "items": [
      {"id": "R03", "claim": "...", "verdict": "OVERTURNED", "reason": "文件存在且包含所述内容"}
    ]
  }
]
```

这份日志是公开的。任何人可以查：谁申诉过、拿什么证据、裁了什么。**没有这份日志，"接受申诉"就只是话术。**

## 五、已知限制

1. **证据路径必须位于包内**。这件事由 `_safe_path()` 强制：绝对路径与 `..` 越界一律判 REJECTED。理由不是防恶意，而是——申诉件是外部输入，若允许指到包外，申诉者就能用 `contains:` / `regex:` 一位一位试探本机任意文件的内容，等于一个布尔预言机。这是 ClawHub 安全扫描（A.I.G 规则 T09）在本包 1.1.12 上报出的问题，已修复。
2. **序号不跨报告，语义键跨报告**。用 `R03` 只能针对同一份报告申诉；用 `reproducible:no-runner` 这类语义键可以跨报告引用。
3. **只核验文件层证据**。能回答"这个文件在不在、里面有没有这句话"，不能回答"这段代码写得对不对"。
4. **裁决不触发复评**。推翻之后需要自己重跑一次，看那个维度是否真的变了——因为规则可能还有别的依据在支撑同一个扣分。
5. **不处理主观分歧**。你认为"这条规则本身不合理"，那是规则问题，走 issue，不走申诉。
6. **语义键是启发式映射**。它按 issue 文本匹配规则表；措辞改动较大时可能落到 `other:` 前缀，此时仍需用当次序号。

## 六、申诉机制带来的第一批改进

这个机制上线第一天就抓到一个真实缺陷：

- 申诉："`tests/test_runner.py` 真实存在，但被判'无测试执行器'"
- 裁决：**OVERTURNED**
- 修复：`d_reproducible` 原来只认 `tests/run_*.py`，改为同时认 `run_*.py` / `test_*.py` / `*_test.py` / `run_tests.py`，并在实跑时优先选 `run_` 前缀

这条规则此前会冤枉所有用 pytest 标准命名的包——而那恰恰是最常见的一类。

**一个能被申诉的评测器，会不断被申诉改好。不能申诉的，只会一直错下去。**

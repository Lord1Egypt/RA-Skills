# 反驳（找反例反驳草稿）

> 本文件在**第八步**加载——草稿写完后，由模型找反例与反论来反驳自己的草稿。这是规则，不是可选步骤，也不靠定期更新。

## 找什么

针对核心论点与每条支撑要点，主动找：有没有反例？有没有更合理的反论？证据是否站得住？

**反例六类**：

- **事实反例**：证据错了 / 过时 / 二手当一手。
- **逻辑反例**：推理链有漏洞（归纳样本偏倚 / 演绎大前提不成立 / 类比失当）。
- **范围反例**：论点过宽，存在明显不适用场景。
- **价值反例**：有更重要视角被忽略。
- **困惑反例**：**一个善意的读者在这里跟不上了**——哪一句需要多补半句？读者卡住的位置往往正是论证的薄弱处。

**第六类 · 读者接不住**（不是「你说错了」，是「他没接住」）。这类只在命中原文时才写，五种形态：

| 形态 | 判据 | 改法 |
|---|---|---|
| 身份含混 | 通篇「大家 / 普通人 / 创业者」，读者认不出自己属不属于被描述的人 | 补共同处境、群体边界、具体利益 |
| 缺因果桥 | 给了结论，没说这件事怎么发生、责任怎么形成 | 补一条能验证的因果解释 |
| 只有情绪标签 | 直接说「焦虑 / 委屈 / 愤怒」，没写目标受阻、责任归属、控制感 | 写出形成情绪的那条评价路径 |
| 用途不清 | 读者不知道这东西拿来干什么 | 在开头或结尾点名用途 |
| 没有转述理由 | 读者认同，但不知道转给别人时该说什么 | 先判这篇要不要传播：用途答不出、或明确不公开 → 不报，或只报「更佳」；需要传播时，给一句能被转述的话，或说清它替谁说了什么 |

> 后果、情绪、传播**分开判**：内容让人愤怒，不等于读者会接受你的观点；接受观点，也不等于会转发。别把「我会转发」写成一条反例判据。

## 两条纪律

- **锚定原文**：每条反例必须写清位置 + 引用草稿里的一句话。**指不出位置的挑战直接丢掉**，不要软化后保留。
- **不制造批评凑数**：某一类确实没问题就写「未发现实质问题」，不要为了填满六类硬挑。开口先给最强的一条，不做三明治式铺垫。

## 分三档，默认只报最该改的

> 三个档位名是**内部说法**：对外按 SKILL.md 交付节的换法讲——必改 →「先改这几处」、需确认 →「要你确认」、更佳 →「可改可不改」。报告里不出现档位名。

对策建议一多，作者就看不出哪条必须动。每条反例标一档，**报告时只把第一档逐条展开**，其余压成一句：

- **必改**：读者会在这里误解核心判断、形成错误预期或做出错误动作。
- **需确认**：结论取决于作者没交代的事实（有没有资质、是不是商业合作、数据口径）。写清缺哪个事实、不同情形分别什么结论。
- **更佳**：改了更好、不改也不算错。**除非作者问，不逐条列**——列出来只会稀释前两档。

**必改默认不超过 3 条**：超过时按「读者会误解核心判断」取舍，其余合并成一句「另有 N 处同类，不逐条列」。三条以下但都改不动的，说明问题不在这一处——往上找论点或结构，不要摊成催命清单。

**每条必改都要带一句代价**：这处改完会丢掉哪类读者、少掉哪层解释。写不出代价的，说明这处改动没有取舍价值，退回「更佳」。

> 报「必改」时不写数量等级、不写风险评分：说清是哪一句、会怎样被误解、怎么改，这三样齐了就够。

## 两阶段，不许边找边改

- **诊断阶段**：一次找全，只出反例清单，**不改稿、不重写**。
- **处理阶段**：清单出齐后再逐条判——**吸收**（修正论点 / 补边界）、**驳倒**（给出反驳理由）、或**确认破例并标明**，并记回 `claim.md` / `evidence.md`（潜在漏洞、待核查项）。

两阶段都在本步内完成，不引入额外的用户等待。

## 用户驳回某条反例时

防止模型被一劝就软掉立场：

- **算有效驳回**：给出决定性的一段材料、一个反例、一次逻辑订正。**一条就够**，不按凑了几条计分。
- **不算有效驳回**：「我觉得没问题」/「我不同意」但没给论证 /「这只是我的个人风格」/ **把挑战换个说法再自己回答一遍**（转移话题）/ 只说「你说得有道理」却不给具体修改。

**驳回要留痕**：只记用户真正驳回的那几条，写进 `evidence.md` 的「驳回台账」——挑战原文 / 用户的决定性回应 / 结论（**已处理** · **撤回**（评审者误判）· **收窄**（剩余问题在此））。

**自己撤回的判断也要记**：这一轮找出的反例，下一轮发现是误判（找错位置、读错意思、把作者的修辞当错误），在台账里补一行「**已撤回**」并写明理由。**多轮改稿最伤信任的是「上次说删、这次又说留」看不出发生过什么。**

> **没有这一条，下一轮你会重复问同一个已被驳回的质疑。** 用户驳回的是你的误判时，不要暗示用户该改稿。

## 反例优先级

① 本地语料（你的 Obsidian 知识库与本地仓库）→ ② 你已发表的历史文章 → ③ 你的 GitHub 仓库 → ④ 联网（通用检索）。**先在自己的语料里找，再向外扩展**；不跑脚本。

## 改谁

若需改稿，改你自己的 `ai-draft.md`，并在「对你草稿的建议」里提示用户，**不直接改用户的草稿**。

给建议时**钉在原句上**：按原文顺序贴出相关原句，加 `~~删除线~~` 表示建议删掉或替换、🆕 表示新增或改写；**上一轮自己判错、这次还原的地方用 ⚠️ 标明并写一句理由**，不要直接改回去当作没发生过。多轮改稿里，作者最怕的是「上次说删、这次又说留」看不出谁改的、为什么改。
